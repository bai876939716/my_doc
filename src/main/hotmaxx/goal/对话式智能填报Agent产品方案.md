# 对话式智能填报 Agent 产品方案

版本：V1.0｜日期：2026-10-30｜场景：企业内部费用报销、设备报修

## 1. 一页核心版

**产品定位：在现有 App / 网页增加智能填报入口，用户先选高频场景，AI 查询资料并预填，通过逐项问答补齐信息，用户确认后提交至原系统。**

现有长表单保留。聊天与表单共用一份草稿，支持一键切换和回填，原有审批、支付、派单流程继续使用。

| 项目 | 核心设计 |
| --- | --- |
| 用户痛点 | 不理解字段含义；重复填写人员、门店等已有信息；不知道选哪个费用项目或故障类型 |
| 入口 | 原业务页面新增「智能填报」，保留「原表单填写」 |
| 首屏 | 先选「费用报销 / 设备报修」，再展示高频场景卡片；也可直接描述或上传附件 |
| 交互 | 每轮只问一个待补信息；枚举用选择控件，日期用日期控件，附件用上传控件 |
| 自动预填 | 查询人员、组织、门店、设备、收款档案；提取原话及附件中的业务信息 |
| 追问条件 | 必填缺项、信息冲突、低置信度识别；已知且有效的信息不重复询问 |
| 草稿展示 | App 底部「查看已填内容」；网页侧边摘要；标注「系统带出 / AI 预填 / 待确认」 |
| 提交 | 展示摘要，突出金额、收款方、设备、位置等关键项；用户明确确认后调用原系统提交 |
| 兜底 | 随时切换原表单，已填字段和附件回填，待补项高亮；可切回聊天继续 |

### 六条设计原则

1. **新增入口不替换**：保留原表单，与聊天共享草稿，切换不丢内容。
2. **AI 预填、人确认**：识别及推断结果只是候选值，用户确认后才能提交。
3. **能查不问、只问该问**：系统有数据先查询，只补当前场景必需的信息。
4. **一次一问、枚举只能选不能编**：每轮一个问题；选项来自现有字典，AI 只能推荐合法候选。
5. **高频卡片起步、逐步展开**：先确定场景，再按字段依赖顺序补齐，不把长表单逐字段搬进聊天。
6. **全过程可改、提交前校验**：修改上游字段后重新检查关联项，失败保留草稿。

> 范围说明：参考截图更接近「门店费用付款申请」，涉及付款公司、费用承担门店和供应商收款账户，不能全部按员工垫付报销处理。下文费用字段按截图归类；设备报修字段为建议，需对齐现有系统。示例卡片和选项不是新增业务字典。截图内提示作为业务规则核对线索，不直接视为完整规则。

## 2. 字段分类与模块归属

获取方式分为：**系统带出、枚举选择、用户补充、AI 识别预填、系统计算**。同一字段可先识别预填，缺失时再问；系统带出信息可纠错，但不绕过原系统权限。关键字段在最终摘要中确认，无需每项单独追问。

### 2.1 费用报销 / 门店费用付款

| 所属模块 | 字段 | 获取方式 | 何时问用户 / 交互规则 |
| --- | --- | --- | --- |
| 单据信息 | 申请编号、申请日期、审批状态 | 系统生成 | 不询问，生成时机沿用原系统 |
| 人员组织 | 申请人、员工编号、手机号、所属部门、一级部门 | 登录身份及组织系统带出 | 仅信息异常或代办时处理；代办受原权限约束 |
| 门店信息 | 门店代码、名称、大区、门店类型 | 门店档案带出 | 多个可用门店时先选门店，其余联动 |
| 付款信息 | 付款公司、费用承担类型 | 规则带出 / 枚举选择 | 多个合法候选时才询问；不由 AI 自行指定 |
| 费用明细 | 门店费用项目 | 现有费用字典选择 | 高频卡片可预选对应项目；含糊描述展示候选让用户选 |
| 费用明细 | 费用承担门店、门店 ID | 规则预填 / 授权范围内选择 | 不能直接认定等于申请人所在门店；不明确时问 |
| 费用明细 | 费用金额 | 用户原话或附件识别预填 | 缺失、识别不清或与票据冲突时问；摘要重点确认 |
| 费用明细 | 开始时间、结束时间 | 用户原话或附件预填 / 日期区间控件 | 费用期间缺失或有歧义时问；不将开票日期默认当作费用期间 |
| 费用说明 | 付款事由 | 用户描述，AI 整理 | 仅含用户提供的事实；不补造业务用途 |
| 票据信息 | 是否有发票、是否含增值税发票 | 附件识别预填 / 现有枚举选择 | 未上传不等于无发票；识别不足时展示合法选项 |
| 票据管理 | 追票状态、欠票到期日期、纸质提交要求 | 原系统规则生成或预填 | 确需用户承诺日期等信息时再问；不能自定期限或提交要求 |
| 流程状态 | 冻结状态、门店请款状态 | 原系统读取 | 不作为填报问题 |
| 金额汇总 | 金额汇总、大写金额、税额合计、税额合计（前四类发票） | 原系统计算 | 不询问、不由语言模型计算；税额依据有效票据信息及规则 |
| 收款信息 | 收款单位、银行账号、开户行、支行 | 从已维护的收款档案选择并带出 | 确认收款方及账号尾号；新增账户走原维护流程 |
| 附件材料 | 发票、账单、付款依据等 | 用户上传、关联已有材料 | 按费用类型及原规则要求补充；不一律要求所有材料 |

补充规则：

- 截图重复出现的「基础信息」在对话中只呈现一次，实施时确认底层是否属于同一组字段。
- 多条费用明细逐条补齐，分别关联金额、期间、承担门店和票据，再由系统汇总。
- 若支持员工垫付报销，应配置独立场景，使用相应报销字段及本人收款规则，不能套用供应商付款逻辑。

### 2.2 设备报修

| 所属模块 | 字段 | 获取方式 | 何时问用户 / 交互规则 |
| --- | --- | --- | --- |
| 报修人 | 姓名、部门、联系方式 | 登录身份带出 | 现场联系人不同时再补问 |
| 报修地点 | 门店、楼层、具体位置 | 关联门店及设备档案预填 | 多地点时选择；缺少具体位置才问 |
| 设备信息 | 设备编号、名称、型号、保修状态 | 扫码或选择资产后带出 | 多个候选时选择；无法识别设备按原规则进入补充描述分支 |
| 故障分类 | 设备类别、故障类型 | 现有字典选择 | AI 根据描述推荐合法候选；无法匹配时重选或转原表单 |
| 故障描述 | 故障现象、发生时间 | 原话或图片预填 / 用户补充 | 图片不能证明故障原因；只补必需缺项，不猜诊断结论 |
| 影响程度 | 是否停用、业务影响、危险迹象 | 原话预填 / 按规则逐项选择 | 优先补充决定应急处理的信息；优先级由规则计算 |
| 现场材料 | 照片、视频 | 用户上传 | 是否必填按故障类型及原规则判断 |
| 服务安排 | 可上门时段、现场联系人 | 已有信息带出 / 用户选择或补充 | 需要预约或联系人不同时才问；区分预约意向与已确认时间 |
| 工单流转 | 工单号、状态、受理部门、维修人员 | 原系统生成或分派 | 不询问，不由 AI 自行承诺受理人及到场时间 |

## 3. 产品流程

**新增入口 → 高频场景卡片 → 查询与预填 → 单项补缺 → 摘要确认 → 原系统提交 → 查看进度**

### 3.1 高频卡片起步

| 业务 | 示例卡片 | 点击后的动作 |
| --- | --- | --- |
| 费用报销 | 水电费、差旅费、办公采购、直接描述 | 加载该场景字段及规则；存在唯一对应费用项目时预选 |
| 设备报修 | 空调异常、电脑故障、打印机故障、直接描述 | 载入设备候选、故障字典及该类报修规则 |

卡片由已开通业务、权限和使用频次配置，必须映射有效场景。不能因为点击「空调异常」就直接认定故障类型或故障原因。

### 3.2 自动预填与逐项问答

1. **查询已有资料**：获取身份、组织、门店及当前场景所需档案，提取用户原话和附件中的信息。
2. **展示已填进展**：例如「已带出申请人和门店，还需补充费用金额」，支持随时查看草稿。
3. **选择下一个问题**：只问当前必需且未解决的字段；优先解决影响后续选项的字段及冲突项。
4. **使用对应控件**：枚举展示真实候选，时间使用日期 / 区间控件，长列表支持搜索。
5. **更新草稿并重新判断**：用户一次提供多项信息时全部接收，不强迫逐项重述；AI 下一轮仍只问一个缺项。

推荐依赖顺序：

- **费用**：业务场景 → 承担门店 → 金额和期间 → 票据及材料 → 收款方。
- **报修**：地点与设备 → 故障现象 → 影响程度 → 现场材料 → 服务安排。

已知项直接跳过。选择门店、设备等上游字段后，再查询其关联候选。

### 3.3 条件分支与修改

| 触发条件 | 产品处理 |
| --- | --- |
| 无票或欠票 | 检查该场景是否允许，再按原规则补充日期、材料或说明 |
| 用户金额与票据金额不一致 | 单独提示冲突，让用户选择正确值或修正，不擅自覆盖 |
| 枚举无匹配项 | 搜索完整字典；仅字典存在时才可选「其他」；否则引导原流程处理 |
| 用户修改门店 | 重新检查付款公司、承担方、收款候选及字段权限，失效项标为待补 |
| 用户修改设备 | 重新带出位置、保修及可选故障类型，保留仍有效的用户描述 |
| 报修出现危险迹象 | 优先展示企业应急指引及紧急联系入口，再按流程继续登记 |
| 切换原表单 | 回填字段和附件，标记待确认 / 待补项；切回聊天读取最新草稿 |

### 3.4 确认与提交

- 展示摘要及逐项修改入口，用户明确点击「确认提交」后才发起提交。
- 调用原系统校验必填、合法枚举、权限、金额关系、材料及业务限制；不依靠 AI 判断代替校验。
- 只有原系统返回成功才展示成功和单号；失败保留草稿，指出可修正项。
- 重复点击或网络超时时，按草稿及请求标识查询提交结果，避免重复生成单据。

最小实现约束：**AI 负责理解、解释和推荐；原系统负责字典、权限、规则、计算及提交。** 草稿记录字段值、来源和确认状态；枚举存储真实 ID 与显示名称，不能仅提交模型生成的文本。
