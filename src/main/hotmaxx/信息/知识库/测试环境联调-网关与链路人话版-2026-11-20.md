# 测试环境为什么调不通——一次请求的完整旅程（人话版）

> 2026-11-20 · 背景：报修 Agent 测试环境联调，curl 打网关返回 401「未获取到接口信息」。
> 本文把整条链路和沿途所有名词，用一套「公司前台」的比喻讲一遍。
> 配套时序图：[测试环境联调-请求链路时序图-2026-11-20.puml](测试环境联调-请求链路时序图-2026-11-20.puml)（同目录有渲染好的 .png，每一步的目的标在黄底便签里）

## 一句话结论

请求死在了公司大门口：**前台的白名单登记簿上没有我们的接口，前台直接把人劝返了**，根本没走到后面的业务房间。要做的就一件事：让有权限的人往登记簿上抄几行字。

## 先把名词全部翻译成人话

**服务（后端服务）**：一个一直在运行的程序，等着别人来问它要数据。我们的报修 Agent 就是一个服务，Java 中转层也是一个服务。

**网关（Gateway）**：公司的前台。所有外部请求（App、小程序、网页）都只能先到前台，前台干三件事：看你要找谁（查登记簿）、验你工牌（token）、然后带你去对应的房间（转发给后端服务）。公司的前台是一个 Go 语言写的程序，域名 `gateway-dev.hotmaxx.cn`。

**接口登记表（eb_sys_api）**：前台桌上的登记簿，其实是数据库里的一张表。每一行写着：接口路径、是 GET 还是 POST、转发到哪个房间、要不要验工牌。**前台没有导航仪，它认识的路全靠这张簿子**——簿子上没有的路径，一律 401「未获取到接口信息」劝返。这就是我们卡住的地方：实测 dev 环境的簿子上，`/ai` 和 `/agent` 开头的路径**一行都没有**。

这张簿子有个好脾气：前台每 60 秒重新翻一遍（重新从数据库读一次），所以登记完**不用重启任何东西，最多等一分钟就生效**。

**token / JWT**：工牌。App 登录后拿到的一串乱码文字，每次请求都随身带着，前台验一下真伪和有效期。你 curl 里 `Authorization: Bearer eyJ...` 那一长串就是工牌。

**鉴权（is_auth）**：验工牌之后还要不要查「你有没有进这个房间的权限」。登记簿上每个接口有个档位：0=不验工牌直接进（白名单）；1=验工牌**还要**查你个人有没有这个房间的权限（查不到就报「未获取接口权限」）；2=验工牌但不查个人权限。我们要登记成 2 档，和公司其他业务接口（门店服务那些）一个待遇。

**K8s / 容器 / Pod**：程序们住的写字楼。每个服务住在楼里的一个工位（容器）上，写字楼管家负责它们坏了重启、多了裁员。你不需要懂更多。

**namespace（命名空间）**：写字楼的楼层，按语言分队：Python 服务住 `python` 层，Java 服务住 `dev` 层，Go 网关住 `go-dev` 层。

**Service（K8s 服务名）**：工位的**内线电话号码**。工位可以换人（程序重启、换机器），但内线号不变，别的部门拨内线号永远找得到人。比如 Python Agent 的内线是 `dev-python-provider-agent-server-center-svc`，Java 中转层的内线是 `dev-java-provider-biz-ai-middle-svc.dev`。登记簿上「转发到哪个房间」填的就是这个内线号。

**Ingress**：写字楼大门口的指路牌，把 `gateway-dev.hotmaxx.cn` 这个门牌指向前台所在的工位。已经配好，不用管。

**Nacos / 服务发现**：公司内部通讯录。Java 服务们启动时会自动到通讯录上「报到登记」，别的 Java 服务想找谁就查通讯录。我用它做了一次实测：Java 中转层在 dev 环境通讯录上**有报到、状态健康**——证明它活着，不用怀疑。

**通配符登记**：登记簿默认是精确匹配，写 `/sessions/abc123` 只能匹配这一个路径。但我们的接口里有动态段——每个会话的编号都不一样（`/sessions/编号/messages`），不可能把所有编号都抄一遍。所以登记簿支持写 `*` 星号：「`/agent/repair/v1/sessions/*`」意思是以这一串开头的都算数，一条顶一万条。公司里早有先例（彩票接口就是这么登记的），不是我们发明的黑科技。

## 一次请求的完整旅程

以店员在 App 里给报修 AI 发一句话为例：

**第 1 站：前台（Go 网关）**
App 把请求发到 `gateway-dev.hotmaxx.cn/agent/repair/v1/sessions`。前台先看你有没有说自己是哪个 App（X-PlatformId，我们的是 1）；然后翻登记簿查「这个路径+平台 1」——**现在就在这里被劝返了**，因为簿子上没这一页。等登记好了，前台接着验工牌（token），验完在请求上贴一张身份便利贴（X-UserInfo 头，写着你是谁、工号多少），然后按登记簿上的内线号把你转去 Java 中转层。

**第 2 站：翻译员（Java 中转层 provider-biz-ai-middle）**
Python 服务不懂公司的工牌体系，所以垫一个 Java 程序当翻译。它收到 `/agent/**` 的请求，从前台贴的便利贴上抄下工号，然后照着配置文件里写死的地址，原样转发给 Python。这个地址在它的 `application.yml` 里：

```yaml
hotmaxx.ai.agent.base-url: http://dev-python-provider-agent-server-center-svc...:8000
```

翻译员把工号改写成 `X-Uid` 头递进去，Python 只认这个。**dev 这一站已经配好了**，不用额外配环境变量；但那串地址本身值得看懂——

**那串 `base-url` 为什么那么长？它就是内线电话的完整号码**，不是公网地址：

```text
http://dev-python-provider-agent-server-center-svc.python.svc.cluster.local:8000
      └──── 内线号（Service 名）────┘ └楼层┘ └── 楼内总机固定后缀 ──┘  └分机┘
```

- `svc.cluster.local` 是 K8s 写字楼内部总机的固定后缀，**只有楼里的工位能拨通**；你在家（本机）拨永远不通，所以本机联调才要走前台（网关）绕。
- base-shop 的 `dev-java-provider-base-shop-svc.dev` 是**同楼层拨短号**（服务名+楼层名）；Agent 这串是**跨楼层拨全号**（Java 在 dev 层，Python 在 python 层）。两种写法都是内线，不是一套内网一套公网。
- `${AGENT_BASE_URL:默认值}` 的意思是「门口贴了张纸条：部署时另外给了号码（环境变量）就用新号码，没给就用纸上这个 dev 号码」。所以 dev 部署零配置；**生产必须给新号码**，否则他会照纸上写的把生产请求打到 dev 去。
- 反过来也成立：Agent 部署时，Service 名、楼层（namespace）、端口必须和纸上号码一字不差；对不上就换纸条（部署时注入 `AGENT_BASE_URL`），别改代码。

**第 3 站：干活的（Python Agent）**
收到请求，跑 AI 对话流程。这一站昨天已经全部调通（进程活着、电话内线通了、健康检查过了），不用再动。

## 所以整条链路上，还差的就一件事

| 环节 | 状态 |
|---|---|
| 前台指路牌（Ingress） | ✅ 本来就有 |
| 前台登记簿（eb_sys_api） | ❌ **空的，要抄 5 行字** |
| 前台→Java 的路 | ⏸ 等登记簿填好自动通 |
| Java 翻译员活着吗 | ✅ 实测健康 |
| Java→Python 的地址 | ✅ 已随代码包配好 |
| Python 本身 | ✅ 昨天已调通 |

## 要抄的那 5 行字（登记单）

全部都是：平台=1、鉴权=2 档（验工牌不查个人权限）、转发目标=Java 内线号 `dev-java-provider-biz-ai-middle-svc.dev`、端口留空。

| 路径 | 方法 | 作用 |
|---|---|---|
| /agent/repair/v1/sessions | POST | 建会话 |
| /agent/repair/v1/sessions/* | POST | 发消息/提交/退出（带会话编号的） |
| /agent/repair/v1/sessions/** | GET | 查会话（带会话编号的） |
| /ai/supplier/info/audit | POST | 顺带：旧的供应商审核接口 |
| /ai/goods/info/audit | POST | 顺带：旧的商品审核接口 |

后两行是因为同一个 Java 服务里还有两个老功能，dev 环境同样没登记，要不要一起补看你。

`*` 和 `**` 的区别：同一层楼里 GET 和 POST 要写成不同的星号才不会互相覆盖，这是公司登记簿的既有玩法（一条 `*` 管 POST、一条 `**` 管 GET），照抄彩票接口的先例即可。

**找谁抄**：有 common-center 门户权限的人（网关负责人）。正规流程是走门户的「添加接口」页面，门户会自动把带星号的路径同步到前台的通配符名单里；直接改数据库也生效，但星号那两条不会被自动同步，得手动补，所以**优先走门户**。

## 两个已知的小坑（登记完验证时留意）

1. **GET 可能报「方法不允许」**：前台匹配带星号的路径时，先翻到哪条星号规则用哪条，翻的顺序没人控制。如果登记完 GET 查会话一直报「方法不允许」而 POST 都正常，就是这个原因，拿给网关负责人看，这是他们匹配逻辑的既有特性。
2. **别拿响应头当验证通过的标志**：前台回的 `X-PassGateway: 1` 这类响应头是无条件加的装饰品，不代表任何检查通过。验证就认返回内容本身。
