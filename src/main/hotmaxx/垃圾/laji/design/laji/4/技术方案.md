# AI 填报 Agent 技术方案 · 报修 + 报销

> 一句话：**LangGraph 引擎 + 技能包框架——报修、报销都是技能包，新业务接入只写配置、不写流程。**


## 1. 背景与目标

- 门店报修、报销表单字段繁杂，填报体验差；业务在明道云，按账号收费。
- 本期以 **AI 对话式填报**落地报修信息录入；报销（门店费用通道）完成技能包设计，验证框架。
- 更重要的目标：**搭一个可复用的填报 Agent 框架**——报修、报销之后，新业务以"技能包"形式低成本接入，最终演进到多智能体。

## 2. 核心思路与实现方式

### 2.1 核心思路

> 1. **LLM 负责识别与生成**（听懂口语、抽出结构化字段）
> 2. **LangGraph 负责编排**（通用采集图管流程、interrupt 管人机确认、Checkpointer 管存档恢复）
> 3. **技能包定义业务**（字段 schema + 字典 + 话术 + 工具 + 钩子，业务差异全部收敛在包里）
> 4. **人负责确认**（AI 预填、点选提交才入库）

### 2.2 实现方式对比

| 候选 | 一句话定位 | 判定 | 理由 |
|---|---|---|---|
| A. 纯 LLM 自主对话（ReAct） | 模型每轮自己决定问什么、调什么 | ✗ | 跳步漏问不可控、易编枚举、轮次成本不可控 |
| B. 纯 LangChain 线性串联 | RunnableSequence 一路跑到底 | ✗ | 回跳只能整链重跑，随时改做不到 |
| C. 自研状态机 | 状态 × 事件转移表自管流程 | ✗ | 存档恢复 / 人机中断 / 跨会话记忆 / 流式等通用能力全部要自建自维，框架已内建 |
| **D. LangGraph 图编排** | StateGraph 节点 + 条件边，Checkpointer 内置断点续填，interrupt() 原生人机确认 | **✓ 采用** | 编排 / 存档 / 恢复 / 中断 / 记忆 / 流式全部原生；技能包可直接演进为多 Agent 的子图 |
| E. Dify | 低代码平台 | ✗ | 卡片消息协议无对应物、降级埋点需外挂网关、私有化运维重 |
| F. Coze 扣子 | SaaS 低代码 | ✗ | 数据出域；私有化部署组件重 |

## 3. 系统架构

系统架构图：[01-架构图.puml](diagrams/01-架构图.puml)

### 3.1 架构核心

- **唯一新建部署单元**：Agent 单容器（mcpServer 工具层 + LLM 网关在进程内、逻辑解耦）；接入公司已有网关（Nacos 加路由，Agent 解析 HTM-HEADER 拿 userid，❗路由 response-timeout > SSE 时长）。
- **容器内**：FastAPI 会话 API + LangGraph 引擎（通用采集图）+ 技能包（报修 repair / 报销 expense）。
- **对外**：六接口、卡片协议、SSE、URL 规范（`/agent/{skill}/v1/**`）——前端与平台组零改动（报销新增卡片形态见 §12）。
- **存储**：Redis = LangGraph 检查点（thread_id = 会话）+ 记忆（工具读写）+ 活跃索引 + 配额；MySQL = 归档 / 埋点 / 调用日志。

### 3.2 演进规划

P1 Java 服务层（限流/数据权限，放量安全门槛）> P2 LLM 网关独立 > P3 AI 网关 > P4 mcpServer 独立服务化——排序与论证见 [实现细节/演进规划.md](实现细节/演进规划.md)。

## 5. 框架设计：core 与技能包

技能包与槽位类型图：[03-技能包与槽位类型图.puml](diagrams/03-技能包与槽位类型图.puml)

### 5.1 分层

| 层 | 内容 | 变化频率 |
|---|---|---|
| **core（业务无关，一次建设）** | 会话 API/SSE · LangGraph 通用采集图 · 槽位议程引擎 · 槽位类型系统 · 防幻觉闸 · 话术模板引擎 · ToolProvider 工具设施 · 检查点/记忆 · 埋点 | 基本不动 |
| **skill（业务技能包，逐业务接入）** | 报修包 `repair` · 报销包 `expense` | 每个新业务一个包 |
| **api（接入层）** | `/agent/{skill}/v1/**`，按技能包自动挂路由 | 不动 |

### 5.2 业务接入形态：两个方案

**方案一：通用图 + 声明式技能包 —— 采用 ✓**

框架只有一张通用采集图（§6），"缺什么问什么"由槽位议程驱动；业务只交一个**配置包**（字段 schema + 字典源 + 话术模板 + 工具 + 钩子），零流程代码。业务特殊规则（如报修"类别必须点选、卡片路径免描述"）用钩子声明。

**方案二：每业务一张子图 —— 不作主形态（作逃生舱保留）**

框架只给外壳（会话/工具/日志/检查点），报修一张 StateGraph、报销一张 StateGraph，各自定义节点与边。

| 维度 | 方案一 通用图+声明式 | 方案二 每业务一张图 |
|---|---|---|
| 新表单接入成本 | 字典 + schema + 话术 ≈ **3~5 人天，零流程代码** | 画图 + 节点代码 + 测试 ≈ 8~12 人天 |
| 复杂控件（树/子表/字段组） | 槽位类型系统统一解决，**一次建设全业务受益** | 每张图各自实现，能力重复建设 |
| 流程表达力 | 线性采集类流程全覆盖；非线性流程靠钩子 | 任意流程，最灵活 |
| 调试与测试 | 通用图一套测试全业务复用；业务问题定位在 schema（数据，好改） | 测试矩阵 × 业务数；流程 bug 在代码 |
| 报修+报销实测 | **两业务同一张图跑通** | 两张图 = 两份维护、两套口径 |
| 一致性 | 话术/卡片/降级口径天然统一 | 各图各写，易漂移 |
| 与多 Agent 终态 | 技能包 = 未来子 Agent 的技能定义，supervisor 直接挂 | 可挂，但需先统一图约定 |
| 主要风险 | 极端流程表达不了 → 钩子膨胀（对策：真长成图的业务允许挂自定义子图，框架不拦） | 接入成本高，框架复用度低 |

### 5.4 槽位类型系统（10 类）

| 类型 | 采集策略 | 卡片形态 | 报修用例 | 报销用例 |
|---|---|---|---|---|
| `context` 带出 | 工具带出，不问 | 状态条展示 | 门店/报修人/日期 | 申请编号/申请日期/大区/门店类型等只读项 |
| `enum` 枚举（含下拉） | LLM 给 Top3 → **必须点选**（白名单过滤） | 单选卡/搜索选择卡 | 报修类别 · 期望上门 · 影响营业 | 门店费用项目 · 付款公司 · 办公地点 · 是否有发票 · 费用承担类型 |
| `tree` 树筛选 | LLM 抽名字 → 树模糊匹配 Top3 **路径** → 点选 | 路径确认卡 | — | 所在部门 · 一级部门 |
| `text` 自由文本 | LLM 抽取 + 按范式整理 | 文本 + 可编辑 | 故障描述 | 付款事由 |
| `money` 金额 | LLM 抽取 / 数字键盘，格式校验 | 金额输入卡 | — | 费用金额 |
| `date` 日期 | 带出默认 / 选择 | 日期卡 | — | 开始时间 · 结束时间 |
| `media` 照片附件 | 上传 + 按清单**规则校验** | 拍照引导卡 | 现场照片 | 发票影像 / 附件 |
| `subgroup` 字段组 | 组内逐项问，或记忆预填一次确认 | 分组确认卡 | — | 收款人四件套（收款人/银行账号/开户行/支行） |
| `subtable` 子表 | 行卡片增删改；**一句话抽多行**，逐行确认 | 行卡片列表 | — | 费用明细（多行） |
| `computed` 计算 | 程序计算，不问不抽 | 确认单展示 | — | 期间天数 · 大写金额 · 税额合计 |

**痛点 → 共性对照**（报销实测暴露的痛点如何被框架吸收）：

| 业务痛点 | 沉淀为什么 |
|---|---|
| 部门树层级深、翻半天找不到 | `tree` 类型 + 路径确认卡（说部门名 → AI 给 Top3 完整路径 → 点一下） |
| 收款人四件套每次重复填 | `subgroup` + **跨会话记忆**（按 uid 存，二次填报只确认不改） |
| 子表不知道怎么填、填几行 | `subtable` 行卡片 + 一句话抽多行草稿 |
| 一级部门重复选 | 联动推导钩子：由所在部门路径自动带出，不问 |
| 期间天数/大写金额手算易错 | `computed` 程序计算 |
| 付款公司/费用项目下拉选错 | `enum` 统一防幻觉闸（字典白名单 + 必须点选） |

## 6. 通用采集图（LangGraph StateGraph）

通用采集图：[02-通用采集图.puml](diagrams/02-通用采集图.puml)
执行与 State 变化：[05-LangGraph执行与State变化图.puml](diagrams/05-LangGraph执行与State变化图.puml)
落地细节：[实现细节/LangGraph落地设计.md](实现细节/LangGraph落地设计.md)

### 6.1 节点

| 节点 | 职责 | LLM |
|---|---|---|
| `load_context` 带出 | 调技能包 context 工具带出字段，下发状态条 + 高频卡片 | — |
| `extract` 联合抽取 | **每条打字消息一次**：意图 + 槽位增量 + 类别/树候选 + 描述整理 + 子表行草稿 | ✓ 全流程唯一调用点 |
| `update` 校验入库 | 防幻觉闸（枚举白名单/树路径匹配/金额格式）→ 写槽位 → 联动失效 | — |
| `route` 议程路由 | 缺什么问什么；必填齐了进确认；边界/连续失败降级 | — |
| `ask` 追问下发 | 话术模板 + **槽位类型 → 卡片形态** | — |
| `confirm` 确认单 | **interrupt() 挂起**，等提交或改字段 | — |
| `submit` 提交 | order_key 幂等建单 → 出单号 | — |
| `fallback` 降级 | 卡片向导（0 LLM 调用） | — |

条件边由**意图 + 槽位议程**驱动：`provide`→update→route；`update`（改字段）→原地覆盖、议程不变；`exit`→EXITED；`off_scope/inject`→拉回；连续 2~3 轮失败→fallback。

### 6.2 关键机制

- **断点与存档**：Checkpointer 每个节点执行后自动落 Redis；恢复 = `get_state(thread_id)` 重放；TTL 7 天 + 每日清理兜底。
- **确认单**：`interrupt()` 挂起，`POST /submit` = `Command(resume)` 恢复；确认单上改字段 = 带新值恢复回 extract。
- **随时改**：打字 = extract 识别 `update` 意图 → 槽位原地覆盖、议程不变；类别/费用项目例外——钩子联动失效（照片清单、明细行重校验）。
- **双路径**：高频卡片点选 = 消息直接携带槽位值 → 跳过 extract，0 LLM。
- **子表多行**：报销场景一次抽取输出多行草稿（"房租 5000、电费 1200"→两行），行卡片逐行确认。

### 8.1 字段映射（依据真实表单截图 + OCR，❗=待对齐）

**系统自动 / 只读（13 项，不问不抽）**：申请编号 · 申请日期 · 审批状态 · 大区 · 门店类型 · 欠票到期日期 · 冻结状态 · 门店请款状态 · 大写金额 · 税额合计 · 税额合计(前四类发票) · 费用承担门店(接口同步) · 费用承担门店 ID —— 全部 `context`/`computed`。

**对话采集（11 项）**：

| 字段 | 槽位类型 | 策略 |
|---|---|---|
| 所在部门 | `tree` | 说部门名 → Top3 完整路径卡点选 |
| 一级部门 | `tree` + 推导钩子 | **由所在部门路径自动带出**，确认单可改 |
| 办公地点 | `enum` | 地点字典 Top3 |
| 付款公司 | `enum` | 下拉字典 Top3，常用项前置 |
| 费用承担类型 | `enum` | 默认"门店"，可改 |
| 付款事由 | `text` 必填 | LLM 整理；规则"一个门店相关付费、最多 10 个子项" |
| 费用明细 | `subtable` | 行 = 门店费用项目(enum) + 费用金额(money) + 开始/结束时间(date)；期间天数 computed；**≤10 行**钩子 |
| 是否有发票 | `enum` 三选一 | 有发票/收据 · 无发票/无收据 · 欠票/收据 → 欠票时确认单提示到期规则 ❗ |
| 收款人银行信息 | `subgroup` 四件套 | 收款人 · 银行账号 · 开户行 · 支行；**记忆预填**：上次填过 → 直接确认 |
| 附件 / 发票影像 | `media` | ❗是否必填待对齐 |
| 手机号 | `context` ❗ | 截图提示"填门店代码自动匹配"，语义待对齐 |

### 8.2 钩子清单

| 钩子 | 规则 |
|---|---|
| 子表行数 | ≤ 10 行，超出引导拆单 |
| 一级部门推导 | 随所在部门路径自动带出 |
| 欠票联动 | 选"欠票/收据"→ 确认单展示欠票到期日期提示 ❗规则待财务对齐 |
| 金额一致性 | 大写金额 = Σ 子表金额，computed 单源 |

### 8.3 交互剧本（主路径）

> AI：说下这次报什么费用就行，比如「11月房租5000、电费1200，发票还没到」。
> 店长：「这个月房租 5000，电费 1200，发票都还没到」
> AI：建了两行费用明细（房租 ¥5000 · 电费 ¥1200），发票状态先按「欠票/收据」登记——**费用项目确认**：[门店费用-房租] [门店费用-电费]（Top3 点选）
> → 办公地点/付款公司卡片 → **收款人**：上次给「张三 工行XX支行 尾号6688」，这次还用吗？[用上次的] [改]（记忆命中）→ 确认单（期间天数/大写金额自动算）→ 提交。

## 11. 会话草稿与退出恢复

| 机制 | 实现 |
|---|---|
| 存档 | Checkpointer 每个节点后自动落 Redis（AsyncRedisSaver） |

## 13. 降级与成本

- 三级降级：LLM 失败 / 配额超限 / 连续识别失败 → fallback 卡片向导（0 LLM）→ 引导回老表单；**框架运行时异常走同一向导**。
- 成本口径：**打字才调 LLM（每条消息一次联合抽取）、点选 0 调用、话术全模板化**；子表多行抽取在同一次调用内完成。

**用户"聊很多"的四层控制**：

| 层 | 机制 | 效果 |
|---|---|---|
| 边界拉回 | 意图六类：跑题/闲聊/注入 → 槽位零写入 + 模板话术拉回（每条消息最多 1 次调用）；连续 2~3 轮 → fallback 卡片向导 | 无效输入不推进流程、不连环追问 |
| 配额硬闸 | 单会话 LLM ≤6 次；单人单天次数 + token 双限额（`quota:{uid}:{date}`）；全局日配额熔断。超限 42901 → **降级卡片向导**（❗初始值，上线按数据调） | 成本有上限且不阻塞——向导照样填完单 |
| 上下文恒定 | extract 只喂 schema + 槽位快照 + 最近 4 条消息（≈2k token）；全量 messages 只用于重放/审计，不进 Prompt | 聊 100 条，第 100 次调用成本 ≈ 第 1 次 |
| 少聊的动机 | 点选 0 调用 · 一句话一次抽全 · 确认单点哪改哪 · text 上限 500 字符 | 正常路径 2~3 次调用封顶 |
