# 门店 IT 设备报修 · 产品方案

> 版本 v0.1 · 2026-11-24 · 用于产品方案汇报
> 依据：与业务方沟通记录、现有「门店IT设备报修申请表」截图、hotshop 报修现状、AgentServerCenter 代码与《输入优化》实施文档
> 标注约定：**【待确认】**=业务事实我没法从现有资料核实，汇报前或汇报中需要问到；**【待拍板】**=需要业务/管理层做决定

---

## 0. 一页结论

**问题不是"表单字段多"，而是四件事叠加：**

1. **让门店填了系统本来就知道的信息**——现有表单 9 个必填项，其中门店编号、店长姓名、电话、区域、地址 5 项都能由登录身份带出。
2. **序列号没有数据底座**——没有完整的"设备—门店—供应商"台账，只能靠人找标签、运维一个个核。
3. **流程到派单就断了**——有没有修好、谁在处理、什么时候完成，门店和运维都看不到。
4. **群是唯一的协同工具**——分诊、催办、核对身份、报价全在群里靠人肉匹配。

**方案三句话：**

- **门店侧**：hotshop 新增「IT 报修」入口，表单按设备类型显示不同字段，门店实际只需填 4 项（设备类型、故障现象、照片、序列号）；对话式作为同一套字段的另一种填法接入。
- **运维侧**：提交即自动预检，运维只处理例外，在一个工作台里完成审核、派单、核价，不再翻群。
- **闭环**：报修单有明确状态，供应商接单、报价、完工、门店确认、结算每一步都回写，门店在 hotshop 能看到进度。

**要做成的前提**：补齐设备台账（至少覆盖在用的两种电脑型号和手机）、确认明道云现有工作流能否按大类分流。

### 1.1 现有表单逐项拆解

| 表单项 | 现状 | 问题 | 应该由谁提供 |
|---|---|---|---|
| 门店编号 | 手填 | 店员要记编号 | 系统带出 |
| 店长姓名 | 手填 | 报修人不一定是店长 | 系统带出（可改） |
| 联系电话 | 手填 | 重复劳动 | 系统带出（可改） |
| 门店所在区域 | 手填"如上海一区" | 格式不统一，运维还要拿去匹配 | 系统带出 |
| 门店地址 | 手填"可寄送地址" | 同上；版式上和上一项说明文字挤在一起 | 系统带出 |
| 故障设备 | 单选：手机/电脑/显示器 | 合理，保留 | 用户 |
| 故障照片 | 选填 | 合理，建议必填 | 用户 |
| 故障描述 | 必填，出现两个输入框，提示语重复 | 用户不知道写到什么程度算够 | 用户（结构化） |
| 设备序列号 | 必填，两段长说明 | 核心痛点：标签可能被撕、用户不认识 SN、运维要远程指导 | 系统辅助获取 |
| 紧急程度 | 三档单选 | "紧急（影响营业）"有用；"一般/不急"区别模糊 | 用户（简化） |

另外两点观察：

- 序列号说明里那句"请认真对待，胡乱填写总部后台无法提供任何帮助和服务"，说明乱填已经是普遍问题，靠警告文案解决不了，要从输入方式上解决。
- 分诊（运维先远程看）是好的做法，但它发生在群里、不留痕，运维的重复劳动都在这一步。

### 1.2 各角色痛点归因

| 角色 | 痛点（原话） | 归因 |
|---|---|---|
| 门店 | 字段繁琐 | 5 项不该填 + 描述无引导 |
| 门店 | 序列号不知道是什么 | 没有辅助获取手段；只有 2 种电脑型号却让用户抄一串字符 |
| 门店 | 群里沟通麻烦 | 没有自助入口；进度不可见只能靠问 |
| 运维 | 处理用户抱怨情绪 | 等待无反馈、流程不透明 |
| 运维 | 序列号填不对，要沟通指导 | 同上，且没有校验 |
| 运维 | 群身份要和表单对、消息内容不清晰 | 缺少带身份的入口；缺结构化输入 |
| 运维 | 对接的人太多忙不过来 | 全量人工审核 + 小问题也占用人 |
| 公司 | 是否修好不知道；费用沟通无留痕 | 流程没有状态和回写 |

## 3. 对初步方案的评估

| 初步想法 | 判断 | 说明 |
|---|---|---|
| 页面按分类显示不同字段 | 合理，建议照做 | 但要先做减法：不分类型的字段（门店信息）直接带出，动态的只是"和设备有关"的那部分 |
| 对话式接入 IT 类，字段不一样 | 合理，建议做成**独立技能包** | IT 的字段（设备类型、SN、紧急程度）和现有工程报修（类别树）差异大；现有引擎的槽位是按技能包声明的，独立技能包不用改框架层 |
| 明道云推给运维审核 | 部分合理 | 明道云适合做"单据和流程的载体"，不适合做"运维的工作入口"——运维不会常驻明道云，且目前是单账号，操作留痕有限。建议：明道云存单据，审核动作在运维工作台或群通知卡片上完成，结果回写 |

两点补充判断：

- **"审核真实性"需要重新定义。** 现在审核实际在做三件事：信息是否完整、SN 是否可信、该不该走这个流程。前两件可以由系统预检完成大部分，人工只看例外。如果保留全量人工审核，至少要有响应时限，否则审核本身成为新的卡点。【待拍板】
- **"是否并入现有门店报修表"要先定。** 现有「门店报修」表已经有报修单状态、接单时间、维修完成时间、接单/维修超时、店长评价、费用结算单这些闭环字段，而 IT 表是一张独立的简单表，所以"后续流程无"。我建议 IT 作为「门店报修」的一个大类接入，补上设备类型和序列号两个控件，直接继承现有闭环。前提是现有工作流能按大类分流到运维。【待确认】

## 4. 详细设计

完整交互流程图：[产品交互流程图.puml](产品交互流程图.puml)

### 4.1 入口与前置自助排查

hotshop 报修入口增加「IT 设备」分类，进入后：

- 顶部显示当前门店和联系人（由登录身份带出，让用户知道"不用填这些"）。
- 三个设备入口：手机、电脑、显示器；"其他设备"兜底走原流程。
- 每个设备下方放 2–3 条常见问题的自助指引（如电脑卡顿：先重启、清理缓存、看磁盘空间）。用户点"没解决"直接进入报修，系统记下"已尝试的步骤"，运维不用再从头问。

注意：自助指引不能成为强制步骤。选择"影响营业"的用户直接进表单。

### 4.2 表单式：按设备类型动态显示字段

**所有类型通用，用户实际要填 4 项：**

| 字段 | 形式 | 必填 | 说明 |
|---|---|---|---|
| 设备类型 | 大按钮三选一 | 是 | 手机 / 电脑 / 显示器 |
| 故障现象 | 按设备类型的选项卡，可多选 | 是 | 见下表；选"其他"时才要求写描述 |
| 补充说明 | 文本，限 100 字 | 否（选"其他"时必填） | 替代现在两个描述框 |
| 现场照片或录屏 | 拍照 / 上传 | 是，至少 1 张 | 屏幕报错、损坏部位 |
| 设备序列号 | 输入框 + 辅助获取 | 是（允许"找不到"） | 见 4.4 |
| 影响营业吗 | 开关 | 是 | 开=加急，进优先队列 |

**按类型变化的只有"故障现象"选项：**

| 电脑 | 手机 | 显示器 |
|---|---|---|
| 开不了机 / 自动关机 | 碎屏 / 屏幕显示异常 | 不亮 / 黑屏 |
| 卡顿、死机 | 无法开机 | 花屏、闪屏、线条 |
| 蓝屏、报错 | 充不进电、耗电快 | 颜色异常 |
| 黑屏、无显示 | 系统卡顿、闪退 | 接口松动、无信号 |
| 无法联网 | 无法联网 | 其他 |
| 键盘、鼠标失灵 | 声音、听筒异常 | |
| 软件问题（收银系统等） | 其他 | |
| 其他 | | |

选项内容我按常见情况拟的，上线前要用历史报修记录的故障分布校准。【待确认：拉 IT 报修历史单的故障类型分布】

**去掉的项**：门店编号、店长姓名、区域、地址（带出）；联系电话改为带出后可修改；"一般 / 不急"合并为一档。

### 4.3 对话式：IT 报修技能包

对话式不是另一个产品，是同一套字段的另一种填法。槽位设计：

| 槽位 | 类型 | 采集方式 |
|---|---|---|
| 门店、报修人、电话、日期 | 带出 | 沿用现有 `get_user_context` |
| 设备类型 | 枚举卡 | 从首句识别（"收银电脑开不了机"→电脑），识别不出弹卡 |
| 故障现象 | 枚举卡（选项随设备类型变） | 首句命中则带 Top 候选让用户点确认 |
| 补充说明 | 文本 | 走卡片路径时不追问 |
| 照片 | 拍照引导卡 | 带拍摄建议（整机、屏幕、标签） |
| 序列号 | 文本 + 辅助卡 | 同 4.4，对话里支持"拍标签我来识别" |
| 影响营业 | 枚举卡 | 从"收银用不了"这类表述识别，仍需用户确认 |

两点要提前评估：

- 引擎现有机制里，选项随另一个槽位变化的只有"拍照引导清单按类别取"，故障现象选项随设备类型变需要确认能否用同样的方式声明，不能的话是框架层的小改动。
- 对话式打字轮有 5–8 秒等待，门店店员更习惯点选，所以**默认入口建议还是卡片式表单**，对话式作为入口并列提供。

### 4.4 序列号：分四层解决

这是方案里最关键的一项。两种电脑型号、两家租赁供应商，说明序列号背后有稳定的对应关系，应该让系统去记，而不是让人去抄。

| 层级 | 做法 | 依赖 | 阶段 |
|---|---|---|---|
| ① 台账选设备 | 门店报修时直接列出"本店设备"让用户点选，序列号自动带入 | 设备台账（SN—门店—型号—供应商—购置/起租日期） | P1 |
| ② 拍标签识别 | 拍机身标签，识别出序列号后让用户确认；低置信度不让自动填 | 多模态识别；需要一批真实标签照片做验证 | P0 |
| ③ 自助获取指引 | 电脑：把现有脚本产品化（双击即显示序列号，可生成二维码让手机扫码带入）；手机：指引查 IMEI/SN | 现有脚本；确认供应商登记用的是 SN 还是 IMEI | P0 |
| ④ 兜底 | "标签掉了 / 找不到"：允许提交，标记给运维补录；加急单不因序列号卡住 | 无 | P0 |

补充两条规则：

- 序列号输入后做格式校验，并在台账里查"这个序列号属于哪家店"。属于别的门店要提示，防止抄错。
- 同一序列号 7 天内有未完结单，提示"这台设备已在维修中"，避免重复报修。
- 【待确认】两家供应商的序列号是否有可区分的前缀或长度规则——有的话，供应商推荐在台账不全时也能用。

### 4.5 运维审核

**提交即预检（自动，秒级）**

| 检查项 | 不通过时的处理 |
|---|---|
| 必填完整、照片齐全 | 前端已拦，后端兜底 |
| 序列号格式 | 提示用户重新获取 |
| 序列号在台账中的门店 ≠ 当前门店 | 转人工审核 |
| 存在重复在修单 | 提示用户，可选继续 |
| 设备超过三年（手机） | 提示"建议换新"，用户可选走 IT 申请 |

**人工审核只看例外，工作台包含：**

- 待办列表：加急单置顶，每单带预检标签（"SN 未命中" "疑似重复"）。
- 详情：照片、设备信息、台账信息（型号、供应商、起租日期、在保状态）、这台设备的历史报修。
- 操作：通过并派单（供应商已按台账预选）、驳回并说明缺什么（门店收到具体提示后修改重提）、转 IT 申请（换新）。
- 每个单记录审核人、审核时间、审核结论，不依赖明道云账号体系。

**响应时限建议**：加急 30 分钟、一般 4 小时，超时提醒。【待拍板：全量人工审核还是"预检通过自动放行、例外人工"。我的建议是先全量人工加时限，跑一个月看驳回率，再放开自动通过。】

### 4.6 派单与供应商协同

- 系统按台账推荐供应商（易点租 / 小熊U租），运维确认；台账未命中时手动选。
- 供应商需要能收到单、确认接单、更新进度（远程处理中 / 已预约上门 / 已完成）。初期如果供应商不愿用系统，由运维代为更新状态，但**状态必须有**。
- 【待确认】两家供应商目前怎么接单（电话/微信/邮件）、合同里有没有响应和完成时限、两家怎么分工（按设备类型还是按区域）。

### 4.7 报价与费用承担

这是现在完全在群里的环节，需要线上留痕：

1. 供应商报价 → 运维核价（工作台里登记报价、备注是否合理）。
2. 门店在 hotshop 收到"报价确认"卡片：故障、方案、金额、承担方、截止时间。
3. 门店选择：同意维修 / 不同意（转评估换新）/ 需要沟通。
4. 结果回写报修单，作为后续结算依据。

【待确认】有没有门店无需确认、运维直接决定的金额上限；"门店损坏"由谁认定。

### 4.8 维修还是换新

- 手机超过三年，财务建议换新：提交时系统按起租/购置日期自动提示，用户可一键转 IT 申请，报修单关联 IT 申请单号。
- 维修中判定换新（修不了、报价过高）：运维在工作台点"转换新"，报修单状态置为"已转换新"而不是直接作废，便于统计。
- 【待确认】电脑是否也有年限规则；IT 申请流程的入口和表单是什么。

### 4.9 完工、评价与结算

- 供应商完成后，门店收到"请确认是否修好"，可评价（沿用现有「店长评价单」）。
- 门店 48 小时未确认，自动视为完成并记录。【待拍板】
- 费用结算沿用现有「费用结算单」，运维核对后关单。

### 4.10 进度透明

hotshop「我的报修」按时间轴展示：已提交 → 审核中 → 已派单 → 供应商已接单 → 维修中 → 待确认报价 → 待验收 → 已完成。每个节点显示时间和处理方。这样门店不用在群里问进度，运维也不用逐个回复。

### 5.1 状态机

系统链路图：[diagrams/04-系统链路图.puml](diagrams/04-系统链路图.puml)

### 5.2 每个状态的责任与时限

| 状态 | 责任方 | 建议时限 | 超时动作 |
|---|---|---|---|
| 待审核 | 运维 | 加急 30 分钟 / 一般 4 小时 | 提醒运维，加急单升级到负责人 |
| 待补充 | 门店 | 24 小时 | 提醒门店，48 小时未补自动关闭 |
| 待派单 | 运维 | 1 小时 | 提醒 |
| 待接单 | 供应商 | 【待确认：合同 SLA】 | 运维电话跟进 |
| 维修中 | 供应商 | 【待确认：合同 SLA】 | 提醒并记录超时 |
| 待确认报价 | 门店 | 24 小时 | 提醒 |
| 待验收 | 门店 | 48 小时 | 自动确认 |
| 待结算 | 运维 / 财务 | 【待确认】 | — |

### 5.3 现在闭环缺失的三块

1. **供应商侧没有回写**：没人更新接单和完成，状态机走不起来。这是闭环的最大缺口，要和供应商约定（哪怕先是运维代填）。
2. **费用确认无留痕**：门店同意承担费用要有记录，否则结算和争议没有依据。
3. **评价和重复维修没有关联**：现有表有"是否在二次维修范围"字段，IT 单没接进来。

## 6. 群怎么处理

现状群承担了四个功能：报修入口、分诊、身份核对、催办。方案上线后：

| 功能 | 去向 |
|---|---|
| 报修入口 | hotshop；群公告固定入口链接（带门店参数） |
| 身份核对 | 不需要，登录即身份 |
| 分诊 / 远程解决 | 自助指引先过滤一部分；剩下的进工单，运维在工作台远程处理后可直接关单并记录 |
| 催办 | 进度可见 + 超时提醒 |
| 人工兜底 | 群保留，用于紧急升级和系统解决不了的情况 |

不建议 P0 做群机器人：群里消息不清晰是输入问题，先把入口迁走，群的量自然下降。

## 10. 风险与需要拍板的事

**风险**

- 台账补不齐，"选设备带序列号"落空，序列号问题只能靠识别和指引缓解。
- 供应商不配合回写状态，闭环停在"已派单"。
- 并表会动到现有「门店报修」的工作流，影响工程类报修，需要明道云管理员配合并在测试环境验证。
- 自动预检放过错误的单（例如抄错但格式合法的序列号），需要人工审核兜底一段时间。

**待拍板**

1. 全量人工审核，还是预检通过自动放行、例外人工。
2. IT 报修并入「门店报修」表，还是独立表补齐状态字段。
3. 门店 48 小时未验收是否自动确认完成。
4. 门店无需确认费用的金额上限（如果有）。
5. 对话式与表单式哪个作为默认入口。
