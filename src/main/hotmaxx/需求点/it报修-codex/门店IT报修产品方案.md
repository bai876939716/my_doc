# 门店 IT 报修方案｜从第一次求助到恢复营业

**评审稿 · 2026-11-24**　适用设备为门店电脑、手机、显示器。面向营运、IT 运维、HotShop 产品、财务及供应商对接人。

## 汇报先讲这三件事

1. **门店只讲一次故障。** 群内保留求助习惯，置顶 HotShop「我要报修」入口。门店选择 IT 设备、说清现象与营业影响、核对联系方式即可提交。序列号找不到也有人接。已经在群内描述清楚的紧急事件，运维可代录并让门店确认，避免先救火再让店员重填。
2. **明道云适合作为运维受理队列。** 首期 IT 单由当班运维认领，预填身份、提示相似未结单、给出有证据的供应商候选。小问题远程处理，复杂问题再核实资产和派单。全量受理有利于摸清真实分布，但逐张走多级审批会把群里的积压原样搬到后台。只有费用、换新等需要授权的决策才进相应审批。
3. **以门店实际恢复使用作为成功条件。** 供应商完工后，门店在原单点「已恢复」或「仍有问题」。转 IT 申请、供应商说已修、超期无人回复都要能区分。汇报决策点是：谁对未结工单负责、供应商怎么反馈、谁有权同意费用，以及哪些单允许结束。

## 一、现在的交接在哪里断了

| 交接点 | 已知情况 | 产品要改变的动作 |
|---|---|---|
| 群消息 → 运维 | 运维从昵称、零散描述和抱怨中判断哪家店、什么设备、急不急。简单故障可能直接解决，无记录 | 群只发入口或已有单号。按登录门店建记录，让门店能看到谁在跟、下一步等什么。营业中断优先转人工 |
| 运维 → 表单 | 群里沟通过又要填店号、店长、电话、区域、地址、设备、照片、描述、序列号、紧急度 | 基础资料按店号取，联系人允许改。先受理，再按维修方式补寄送信息 |
| 表单 → 供应商 | 运维核真实性、完整性，靠序列号判断归属。仅最近发出的约 100 台有记录；两种电脑型号不足以确定是哪一台 | 用可验证的资产候选辅助核对。缺失或冲突进待核验队列，运维有明确下一步 |
| 供应商 → 门店 | 易点租、小熊U租直接联系门店。派出去之后是否恢复未知 | 原单记录接单、约定时间、处理结果与验收。供应商没系统账号也可回给运维代录 |
| 报价或换新 | 门店损坏时运维先核价、议价，再与门店谈费用。手机超过三年财务建议换新，另走 IT 申请 | 报价版本、责任依据、授权、申请号与交付结果都留在原单。实际收付款另行核销 |

**信息边界。** 上述流程来自业务描述。约 100 台是可盘点的起点，无法据此估算全量覆盖率。三年是手机换新评估提示，设备年限、能否维修、谁批准换新均需核实。现有相邻目录的 IT 草案也提出设备分类与台账；本稿首期保留人工派单，并沿用通用报修入口，方便小范围试点。

## 二、门店从哪里进，具体要填什么

服务助手首页保留「我要报修」与历史记录；进入报修表单后顶部仍是「AI 智能填报」。表单选择 IT 类才展开设备分支；对话也可从“电脑开不了机”起步，助手给出类别候选，由门店确认。两条路径读取同一份字段规则、同一份草稿，提交前展示同一张核对单。普通工程、广告及营运用具继续走现有分类。

| 字段 | 受理时的规则（表单和对话共用） | 后续用途与例外 |
|---|---|---|
| 门店编号、名称、所在区域 | 登录上下文带入已授权门店。多店员工先选发生故障的店；大区按主数据映射 | 编号用于查历史与资产，区域缺失由运维补映射。不能从群昵称猜门店 |
| 店长姓名、报修人、现场联系人 | 保存实际提交人身份。联系人默认本人，可改为当班同事；店长信息仅在费用授权需要时查组织档案 | 报修人、联系人、费用确认人分别记录，换班无需换单 |
| 联系电话、门店地址 | 电话带出并确认，无有效号码再填。地址受理时可空 | 上门或寄修才核对详细地址、收件人与可联系时段；地址档案读不到可补录 |
| 故障设备 | 电脑／手机／显示器必选。可选择本店资产或「不确定是哪台」 | 电脑按两种在用机型提供对应图示，真实机型和标签位置待采集；手机提示查设备信息；显示器看背面铭牌 |
| 故障描述 | 现象必填，可选常见现象或说一句话。收银电脑卡顿须区分磁盘空间、内存、应用故障 | 运维看到用户原话；AI 提取的摘要供确认，不能仅凭“内存满”指示删除文件 |
| 营业影响／紧急程度 | 选「营业中断」「部分受影响」「可继续营业」，用于排序。允许补充是否有备用机 | 运维可调整优先级并记原因。中断直接人工接手，紧急响应时段待确定 |
| 故障照片 | IT 受理建议选填。明显物损引导拍损坏位置；黑屏、软件问题可先描述 | 报价、认责前按需补证，避免拍到顾客信息。旧普通报修仍按原规则至少一张 |
| 设备序列号（SN） | 显示为「机身编号」，可选本店设备、抄标签或选择「标签缺失／看不清」 | 保留来源与核验状态。照片识别若后续接入，仅作建议。换设备后清空旧资产、编号、供应商候选并重新核对相关照片 |

**少问一轮的标准。** 门店在对话里已说“收银电脑开不了机，无法营业”，确认设备与影响即可；不再逐项问用户重述。模型不可用时回到带值表单。换大类时提示哪些专属项会清除；切回原类允许从原草稿恢复。一次事件涉及多台设备先关联主单，由运维拆分供应商任务，门店仍从同一入口查进度。

## 三、运维如何分诊、核验和派单

| 场景 | 运维看到什么 | 可执行决策和证据 |
|---|---|---|
| 远程可解 | 原话、影响、是否有备机及既往同类单 | 接单后电话或在线指导，写明处理动作和验证方法，交门店试用。复发回原单 |
| 本店台账唯一匹配 | 门店、设备类型、SN、供应商、来源单据和最后核验时间 | 运维对照设备确认后派给易点租或小熊U租，记录联系人和接单期限。签收前责任仍在运维 |
| SN 错一位、跨店、多台同型、设备已调拨 | 候选冲突原因，缺少哪项证据 | 禁止仅按型号、相似字符串或 AI 推断自动派单。先问标签／系统信息，再查出库或调拨单，必要时联系供应商核实 |
| 标签缺失、设备开不了机、台账无记录 | 工单照常受理，归属标记「待核验」 | 运维先远程排障；需外修时由资产对接人核证。仅在电脑可用且门店同意时指导使用公司认可的查询方式 |
| 同店同设备已有未结单 | 旧单号、现象与当前负责人 | 提醒门店补充或坚持新建，运维确认后关联重复单；同型号或同一天不足以合并 |
| 明显物损或费用争议 | 检测依据、保修范围、费用明细、过往报价 | 运维核价、议价并记录版本；只有有权人确认当前版本后才授权收费维修，拒绝返回协商或换新评估 |
| 手机年限超过三年、修复困难 | 购置或启用日期来源、维修估价、备机可用性 | 提请 IT 申请。旧单关联申请号，拒批回运维重新处理；批准后追踪到货、交接、可用性和旧机回收去向 |

**台账从哪里来。** 试点前导入最近约 100 台记录，按店号、类型、SN、供应商及证据来源检查缺项和重复。已退租、换机、跨店调拨的记录须标记失效。每次核实成功形成待更新记录，由资产负责人确认后入账，保存有效期与操作人；换新交付同步旧机退役与新机归属。无记录的老设备走人工支路，可随试点逐步补齐。

## 四、让每一单都有下一步

以明道云 IT 工单为业务状态主记录，HotShop 展示门店语言。AI 的「采集中／待确认／已提交」仅描述填报阶段。工单号贯穿电话、群、供应商反馈和换新流程。[查看工单状态及退回路径](diagrams/03-工单状态.puml)

| 工单阶段 | 下一责任人 | 进入下一步所需记录 | 停滞怎么办 |
|---|---|---|---|
| 待受理／处理中 | 当班运维认领后成为全程负责人 | 当前负责人、分诊结果、下次更新时间 | 未认领进班组长队列；交班需转交未结单 |
| 待补充 | 门店或资产对接人；运维跟踪 | 指明一个具体缺口，回原单补齐后回到处理队列 | 到期提醒责任人，营业中断同时回拨，禁止自动算已修复 |
| 待接单／维修中 | 供应商执行，运维跟踪 | 派给谁、实际接单人、预约时间、处理结论。无供应商入口时由运维据电话／回执代录并注明来源 | 拒单、超时未接或失约回运维协调，记录改派依据 |
| 待核价／待确认费用 | 运维核价 → 授权人确认 | 原因与证据、费用明细、含税口径、版本及有效期。改价作废原确认 | 拒绝回议价。责任争议交营运／财务裁定，未经确认不启动收费作业 |
| 换新跟踪 | IT 申请办理人，运维追踪 | 申请号、审批结果、到货交接与现场试用 | 拒批／缺货回运维给临时方案及下次联系时间 |
| 待验收 | 门店现场联系人 | 远程处理、维修完工、换新到货均写处理说明，再让门店实测 | 「仍有问题」回原负责人；失联提醒、升级后记未验收，单独统计 |
| 已恢复／费用跟踪 | 门店确认恢复；如涉及费用，财务核销 | 确认人、时间、验证结果；应收、到账凭证或争议结论关联原单 | 业务恢复和收款分列。可分别算恢复率与到账率，未收款仍有财务待办 |

**通知**发在认领、需门店补充或确认、预约变更、完工四类节点，附单号与详情入口，群里无需公开电话、地址和照片。无消息推送能力时以 App 待办列表加人工联系起步。中断优先级、首次响应、各阶段超时及夜间值班口径由试点双方约定，系统记录实际等待时长。

## 六、试点与汇报决策

**试点选择。** 营运选有近期台账与无台账的门店各一组，覆盖两家供应商。先复盘近一段时间群反馈和原表单，去重为独立事件，记录现有填报时长、追问次数、已知维修结果及未知数。群内即时解决的事件也抽样纳入，避免把原表单当作全部需求。

| 阶段 | 交付物 | 放量条件 |
|---|---|---|
| P0 人工闭环 | 双入口、动态字段、无 SN 受理、运维队列、人工回执、报价确认、换新关联、验收与退回 | 两家供应商各跑通一单；无 SN、物损拒价、换新拒批、未修复、断网重复提交分别走查；越权访问被拒绝 |
| P1 减少重复劳动 | 唯一台账匹配、常见故障自助卡、分级提醒、供应商回填、IT 申请状态同步 | 候选与实际派单抽检达双方认可阈值，误派可追溯并能暂停自动化 |
| 试点回退 | 停止新 IT 单分流，恢复原有人工作业入口；导出未结清单按原单号跟踪 | 每张未结单均有接手人。普通报修继续运行；未结 IT 单仍可查询并完成验收 |

| 看板指标 | 计算口径与用途 |
|---|---|
| 填报成功率／用时 | 成功建单人数次 ÷ 进入 IT 填报的会话数（按会话去重）；从首个有效输入到成功建单取中位数，按表单／对话、有无 SN 拆分 |
| 首响与追问 | 建单到首次人工有效响应的 P50／P90；每单需门店补充的轮次。按中断级和工作时段分别看，自动回执不算人工响应 |
| 已知恢复率 | 对同一建单批次截至观察日，门店确认已恢复单数 ÷ 有效 IT 单数；单列仍处理中、待验收、验收失败、转换新未交付，保留观察窗 |
| 运维负担与资产质量 | 每单人工接触次数、在途积压与最长等待；已核验归属数 ÷ 需派单数；误派／退单按供应商和原因分组 |
| 费用与体验 | 应收单中的已核销比例；报价被退回原因；验收后抽访“还需要回群追问吗”。试点前定基线，再定目标和退出标准 |

**评审会需要带回的答案**

| 找谁确认 | 请对方拿什么来 | 决定什么 |
|---|---|---|
| 店长、现场员工、营运 | 跟做一次开不了机且标签缺失的求助，核对谁知道店号、谁能接电话、谁能同意费用 | 表单默认值、代录、验收与费用确认权限 |
| 运维、资产管理员 | 最近约 100 台记录样本、两种电脑的真实机型／标签照、抽样群会话及调拨记录 | 身份核验、SN 清洗、可远程处理清单、排班与升级阈值 |
| 易点租、小熊U租 | 各自保修条款、实际接单方式、检测／报价／完工回执样本 | 责任争议、保内外、拒单、时限和代录证据 |
