> **来源：** 读 `haotemai/wms/` 下 11 个仓库的代码和 git 历史（2026-11-26 的 master）得出的。
>
> **状态：** 初稿。优先级是我的判断，不是团队的结论。每条分「现象、证据、影响、建议、怎么验证」五项。

>
> **行号约定：** `仓库简称 路径:行号` 都相对 `haotemai/wms/`，用之前先按方法名搜一下。

## 判断

**「在途、差异说不清」不是一个 bug，是四类东西叠在一起。** 记账的规则在治理范围之外（P0-1）；差异这一环失败之后没有出口（P0-2）；「在途」有好几套口径（P0-3）；用来事后追溯的工具，流水和对账表，自己有缺口（P0-4、P0-5、P2-2）。先把这四样摆清楚，再谈重构。

**「卡单」是「定时任务扫表加状态位」这套机制自带的。** 每轮只取一条，队头一卡全停；失败之后，有的状态没有人再读，有的无限重试；而且大多只打日志，不告警（P1-1 到 P1-5）。

**过去的补丁方式，是关掉补偿步骤、加手工入口。** 治理之前得先知道，现在靠哪些手工动作在维持（P1-5、P2-3）。

## P0 先补认知

### P0-1 记账规则不在治理范围内

| 项 | 内容 |
|---|---|
| 现象 | 所有出入库记账、预占、释放预占，都先调 `provider-biz-inventory-middle`。它不在这 11 个仓库里。同样缺的还有 `provider-ops-job`（关单、作废的中台入口）、`provider-ops-hdg`（海鼎适配）、`provider-biz-scms`（门店侧）。 |
| 证据 | biz-scm `provider-biz-scm-api/…/client/middle/InventoryOperationClient.java:15`；biz-scm 里 10 个服务类调它的出入库记账和预占；base-scm 也调。 |
| 影响 | 在途仓什么时候加、门店收货时怎么转、幂等靠什么，这些最核心的问题现在只能猜。[业务内容.md](../02-业务现状/业务内容.md) 里 2-Q4、2-Q6、6-Q1 的最终答案都在这里。 |
| 建议 | 诊断开始前，把 inventory-middle 和 ops-job 拉进来。拿不到代码，至少拿到接口说明和表清单。 |
| 怎么验证 | 不需要数据。 |

### P0-2 差异单的库存处理失败一次就永久挂起

| 项 | 内容 |
|---|---|
| 现象 | 差异单的库存调账（在途仓和差异仓之间）由定时任务逐张处理。处理失败时，把差异单置成「处理中」（`stock_state = 10`）；但之后没有任何地方再读 10。 |
| 证据 | 取数只取 0：base-scm `service/impl/HtmScmDiffOrderServiceImpl.java:758`。失败置 10：biz-scm `service/impl/DiffOrderServiceImpl.java:70`。改状态是不带条件的 update：base-scm `mapping/HtmScmDiffOrderMapper.xml:53`。全仓库对 `stock_state` 的读取只有取数那一处。异常分支只有日志，没有告警：`DiffOrderServiceImpl.java:68`。 |
| 影响 | 该从在途转到差异（或反过来）的数量停在原处，在途仓和差异仓的余额和单据对不上，而且没有人会发现。这是「在途、差异说不清」最直接的一个候选成因。另外，取数没有加锁，也没有用带条件的更新，多实例同时跑有重复调账的可能；会不会真的重复，取决于库存流水的幂等。 |
| 建议 | 先查存量。修复方向：失败态改成可以重试，加告警和上限；取数改成带条件的认领，仓里已有现成写法（见附录一第 2 条）。 |
| 怎么验证 | SQL ①。 |

### P0-3 「在途」有好几套口径

| 项 | 内容 |
|---|---|
| 现象 | 至少三处各自表达「在途」。一是库位类型 20、40 的库存余额，这是实际记账的落点。二是报表宽表上的「采购在途」「调拨在途」两个字段，由 base-scm 的定时任务按「请求数减实收数」算出来，经 MQ 刷进去。三是数仓的配货在途日志，由初始化任务累加写进类型 40 的库位。 |
| 证据 | 库位类型：base-ivm `constant/BaseWarehouseLocationConstant.java:217`。第二处：base-scm `consumer/listener/MqMessageSendUtil.java:113`、定时任务 `inTransitInventoryPush`；base-ivm `service/impl/HtmIvmBusinessInventoryCombinationServiceImpl.java:743`、`:820`。第三处：base-ivm `service/impl/DwDeliveryWayLogServiceImpl.java:75`、`:169`。 |
| 影响 | 同一个仓、同一个商品，三处的「在途」可以不相等，更新时间也各不相同。财务报表取的是哪一套，决定了对账该用哪一套。 |
| 建议 | M2 的口径表，先把「在途」定义成唯一一个口径（建议以库位余额为准），其余两处明确标成派生、只供报表。 |
| 怎么验证 | 抽几个仓位和商品，把三处的值和更新时间拉出来比。 |

### P0-4 库存初始化任务是累加的，失败还被吞

| 项 | 内容 |
|---|---|
| 现象 | 两个初始化任务（海鼎日库存、配货在途）每执行一次就加一笔，单号是现生成的雪花号，业务类型记成「库存调整」。另外三个任务（日末库存、日末备份、组合库存同步）的 `finally` 里写死了 `return SUCCESS`。 |
| 证据 | base-ivm `service/impl/DwHdDailyStockLogServiceImpl.java:60`、`DwDeliveryWayLogServiceImpl.java:75`；`task/IvmBusinessInventoryInitialTask.java:103`。 |
| 影响 | 初始化任务重复执行一次，库存就翻一倍，事后按单号追不回去。调度台上那三个任务永远显示成功。这些初始化任务现在是否还在调度，不可见。 |
| 建议 | 到 XXL 控制台确认这几个任务是否还在调度、上次执行是什么时候。还要用的，改成按来源批次幂等；`finally` 里的 `return` 去掉。 |
| 怎么验证 | SQL ②；XXL 控制台。 |

### P0-5 对账表的 ERP 侧不刷新

| 项 | 内容 |
|---|---|
| 现象 | WMS 对 ERP 的对账表，记录已存在时走更新分支：组装了新对象，却把旧对象传给了 update，等于没更新。遇到重复键的分支里，用到的对象在这种情形下是空的。 |
| 证据 | base-ivm `service/impl/HtmIvmWarehouseInventoryComparisonServiceImpl.java:86`、`:153`。 |
| 影响 | 这张表里的 ERP 数是第一次写入时的值。拿它做差异归因，ERP 侧是错的。 |
| 建议 | 修好之前不用这张表。差异归因直接从余额表取 ERP 数。 |
| 怎么验证 | 抽几行，把表里的 ERP 数和余额表当前值比一下。 |

### P0-6 「是不是虚拟仓」不是主数据

| 项 | 内容 |
|---|---|
| 现象 | 判断一个仓位是不是虚拟仓，是每次运行时调 base-rule 的接口，base-rule 再去读算法系统的一份配置清单。作废、审核、通知单推送都按这个结果分叉。 |
| 证据 | biz-scm `client/AlgorithmPHClitent.java:11`；base-rule `service/impl/AlgorithmPHServiceImpl.java:98`；biz-scm `service/impl/DeliveryOrderServiceImpl.java:871`、`NoticeOrderServiceImpl.java:661`。 |
| 影响 | ERP 的库里查不到哪些仓是虚拟仓。清单一改，在途单据的作废路径跟着变。算法服务不可用时，审核和作废直接失败。 |
| 建议 | 把虚拟仓清单落成 ERP 的主数据，至少留快照和变更记录；单据创建时把标记固化到单据上。 |
| 怎么验证 | 找算法那边要这份清单和修改记录。 |

## P1 卡单和重复处理

### P1-1 记账任务：一个任务串五步、每轮一条、队头阻塞

| 项 | 内容 |
|---|---|
| 现象 | `inoutOrderDealwith` 顺序做五件事：入库记账、出库记账、释放通知单的预占、配货单自动审核、差异单库存处理。任何一步抛异常，后面的当轮全停。每一件事每轮只取 1 条。处理时加的锁只租 5 秒，出库是 10 秒。 |
| 证据 | biz-scm `task/WarehouseOrderTask.java:40`。取数 SQL：base-scm `mapping/HtmScmInboundOrderMapper.xml:6`、`HtmScmOutboundOrderMapper.xml:6`，里面还写死了一个起始日期。锁：`service/impl/WarehouseOrderServiceImpl.java:251`、`:371`。释放预占的取数：`mapping/HtmScmNoticeOrderMapper.xml:157`。 |
| 影响 | 吞吐量等于调度频率。释放预占那一步最明显：失败后状态是 11，仍然在选取范围里，一张释放不掉的通知单会让后面所有通知单的预占都释放不了，可用库存一直偏低，没有告警。 |
| 建议 | M1 的卡单看板先按「每个队列的队首加队列长度」做，不用等改造。改造方向：五步拆开；取数改成带条件的批量认领；失败态移出选取范围并告警。 |
| 怎么验证 | SQL ③、④。 |

### P1-2 作废、审核任务：每轮一步，无锁、无上限、无告警

| 项 | 内容 |
|---|---|
| 现象 | 作废和审核走任务表，每个任务分几步，定时任务每轮取最早的一个任务、只走一步。没有锁，没有重试上限，出错只打日志。 |
| 证据 | biz-scm `service/impl/domain/BizOrderTaskAppServiceImpl.java:112`；取数 `domain/entity/delivery/BizOrderTaskQuery.java:44`、`BizOrderTaskItemQuery.java:24`。 |
| 影响 | 虚拟仓配货单的作废有五步。卡在中间，就是「单据已经作废、预占还没释放」或者「门店没收到通知」。一个任务卡住，后面的作废全部排队。 |
| 建议 | 看板加「进行中超过 N 小时的任务」；给任务加失败计数和告警；释放预占这一步改成可以重复执行。 |
| 怎么验证 | SQL ⑤。 |

### P1-3 通知单先标「已推送」再发消息

| 项 | 内容 |
|---|---|
| 现象 | 推送通知单的任务，先把通知单标成「已推送」，再发 MQ。发送抛异常只打日志，标记不回滚。另外，虚拟仓的库存调整单在这里被标成已推送，但不发消息。 |
| 证据 | biz-scm `service/impl/NoticeOrderServiceImpl.java:655` 到 `:679`。 |
| 影响 | 消息没发出去，通知单却显示已推送，WMS 收不到指令，也没有重推。 |
| 建议 | 先发后标；或者先标「推送中」，发送成功再改「已推送」。看板加「已推送但长时间没有回传」。 |
| 怎么验证 | SQL ⑥。 |

### P1-4 物流网关回传链路的几处硬伤

| 项 | 内容 |
|---|---|
| 现象 | 一，通知单类型认不出来时，本该报错的判断写反了，回传被当成成功丢掉。二，关单靠起一个裸线程睡 2 分钟再做，服务重启就丢。三，海鼎调拨单先置「推送中」（状态值 12）再调接口，接口异常或一单拆成多单时只打日志，状态留在「推送中」。四，取消订单先通知中台、再请求 WMS，中台通知失败被吞，后面还有一处判空判错了对象。五，全局异常处理整份被注释。 |
| 证据 | 都在 provider-ops。一：`scm/service/impl/HtmScmNoticeOrderServiceImpl.java:489`、`:512`、`:529`。二：`wms/upload/service/impl/WmsUploadBusinessImpl.java:637`。三：`scm/service/impl/HtmScmBigdataInitTransferDataServiceImpl.java:185`、`:257`、`:262`。四：`wms/cancel/service/impl/HtmOrderCancelServiceImpl.java:86`，`helper/OpsJobFeignHelper.java:124`。五：`utils/GlobalExceptionHandler.java`。 |
| 影响 | 在单据上分别表现为：WMS 说做完了、中台没反应；通知单一直不完成；调拨单没到海鼎。都只有看日志才发现。 |
| 建议 | 看板覆盖「通知单已回传但出入库单没生成」「调拨单推送中超过 N 小时」。五处代码改动都很小，可以放在止血阶段。 |
| 怎么验证 | 日志；SQL ⑦。 |

### P1-5 补偿步骤被注释掉，原因没有记录

| 项 | 内容 |
|---|---|
| 现象 | 主记账任务里有四段被注释：配货单自动审核里的一步、差异单判责后的库存处理、差异单历史修复、通知单库存预占。其中两个还作为独立的定时任务保留着，是否在调度不可见。 |
| 证据 | biz-scm `task/WarehouseOrderTask.java:70`、`:86` 到 `:110`；独立任务 `task/DiffOrderTask.java:31`、`task/NoticeOrderTask.java:26`。 |
| 影响 | 判责之后的库存处理到底还跑不跑，取决于 XXL 上有没有单独配这两个任务。不弄清楚，「判责后差异仓怎么平」这条链路就画不出来。 |
| 建议 | 到 XXL 控制台看这几个任务的调度状态，再问当时为什么关。 |
| 怎么验证 | XXL 控制台。 |

### P1-6 幂等靠约定，不靠机制

| 项 | 内容 |
|---|---|
| 现象 | 有的地方有。库存流水按「单据号加明细」判断：增加时已有记录就跳过，扣减时按已扣数量补差。出入库单创建先查后插，「已存在」当成功。没有的地方也有。通知单实绩回写的接口本身不判重，靠同一个事务里翻状态来避免重复，手工重推就会重复累加。管理后台近 600 个接口只有 1 处幂等注解。另有一处并发隐患：库存记账的仓位锁，在事务提交之前就释放了。inventory-middle 内部怎么样，不可见。 |
| 证据 | base-ivm `service/impl/HtmIvmBusinessInventoryServiceImpl.java:549`、`:636`、`:858`。biz-scm `service/impl/WarehouseOrderServiceImpl.java:162`。base-scm `service/impl/HtmScmInboundOrderServiceImpl.java:528`。 |
| 影响 | 现在不重复记账，靠的是调用方守规矩。任何重推、重试、并发都会打破它。 |
| 建议 | M2 做出入库幂等时，以流水表的唯一键（单据号、明细、类型、仓位）兜底，而不是在每个入口加判断。 |
| 怎么验证 | 看流水表有没有同单据、同明细的重复记录。 |

### P1-7 负库存的开关和盲区

| 项 | 内容 |
|---|---|
| 现象 | 开关是库位表上的两个字段。在途、差异这类虚拟仓位的负库存不记日志。海鼎同步新建的库位，两个开关默认都打开。改效期的入口不加锁，锁被注释掉了。负库存的来源，靠备注里有没有「手动」两个字来区分。 |
| 证据 | base-ivm `service/impl/HtmIvmBusinessInventoryServiceImpl.java:590`、`:652`、`:712`、`:2140`；`service/impl/HdWarehouseServiceImpl.java:59`。各库位开关的实际值，不可见。 |
| 影响 | 负库存日志只覆盖在库库位，虚拟仓的负库存没有留痕。新接入的海鼎仓默认允许负库存。 |
| 建议 | M2 的负库存拦截，先盘一遍哪些库位允许。虚拟仓位的负库存也要进日志。 |
| 怎么验证 | 按库位导出两个开关的当前值；看负库存日志的来源分布。 |

## P2 可维护性和安全

### P2-1 单据表没有唯一的属主

| 项 | 内容 |
|---|---|
| 现象 | 10 个服务共用一份库配置。provider-ops 在自己的 XML 里直接写 16 张 ERP 表，主要是通知单、出入库单、差异单、调拨单；provider-mms-ops 直接写配货单和通知单。同一张通知单表，三个服务各有实体类。 |
| 证据 | 各服务的 `bootstrap.yml`；provider-ops `provider-ops-api/src/main/resources/mapper/scm/` 下的 XML；provider-mms-ops `service/impl/HtmScmDeliveryOrderServiceImpl.java:756`。明细见 [表关系.md](../03-系统现状/表关系.md) 第七节。 |
| 影响 | 改表、改状态含义要同时改多处；出了问题不容易看出是谁写的。 |
| 建议 | 短期不动结构。先在表关系的基础上，明确每张表的属主和「只允许谁写」；重构时按属主收口。 |
| 怎么验证 | 不需要数据。 |

### P2-2 追溯能力不足

| 项 | 内容 |
|---|---|
| 现象 | 库存流水有单据号和明细号，能按单据追。但没有操作人：创建人这个字段从来不赋值。批次对冲、清箱、越库预占不进主流水，流水的查询接口不能按单据号过滤。后三条来自代码盘点，我没有逐条复核。 |

| 建议 | 差异归因之前先补两样：流水记操作人；不进主流水的几类操作，至少记一张旁表。 |
| 怎么验证 | 按来源类型和创建人分组，看流水的分布。 |

### P2-3 手工入口多

## 建议的顺序

对应里程碑草案里的 M0 到 M2。

- **M0 诊断：** P0-1 把仓库拉齐；P0-2、P0-4、P1-1、P1-2、P1-3 用文末的 SQL 把存量量化；P0-3 抽数比三处的在途；P2-3 盘手工入口；P1-5 确认被注释的任务还在不在调度。
- **M1 卡单看板和清零：** P1-1、P1-2、P1-3、P2-4；顺手改 P1-4 的五处小问题。
- **M2 负库存拦截、幂等、口径表：** P1-6、P1-7、P2-7；P0-6 把虚拟仓落成主数据。
- **长期：** P2-1、P2-2、P2-5、P2-6。

## 附录一：仓里现成可以照着做的三处

1. **回调重试。** 司机端有一套完整的写法：失败落表、指数退避、有上限、可以手动重试（provider-mp-driver-biz-scm `service/impl/ArrivalTimeoutSignNotifyRetryServiceImpl.java:40`）。卡单的重试可以照这个做。
2. **带条件的认领。** 差异调整任务用 `update … where id = ? and handle_status = ?` 来认领，多实例不会抢到同一条（base-scm `mapping/HtmScmDiffOrderInvAdjustTaskMapper.xml:5`）。P0-2、P1-1、P1-2 的取数可以照这个改。
3. **卡单监控表。** `htm_wms_order_monit` 和它的枚举已经在了，扩两类异常就能覆盖中台内部的卡单。

## 附录二：验证用的 SQL（草稿）

字段名是按实体类转成下划线写的，执行前对照一下真实的列名。库名按 `hotmaxx_erp_scm` 写的。

```sql
-- ① P0-2 差异单卡在「处理中」
select count(*) cnt, min(create_time) earliest
from htm_scm_diff_order
where stock_state = 10 and is_delete = 0;

-- ② P0-4 初始化任务留下的流水（以海鼎日库存初始化为例：单号是纯数字、类型记成库存调整）
select date(create_time) d, count(*) cnt, sum(inv_change_qty) qty
from htm_ivm_business_inventory_log
where source_busi_order_type = 40
  and source_order_no regexp '^[0-9]+$'
group by date(create_time)
order by d;

-- ③ P1-1 出入库单卡在「处理失败」，按业务类型分
select source_busi_order_type, count(*) cnt, min(create_time) earliest
from htm_scm_inbound_order
where state = 30 and is_delete = 0
group by source_busi_order_type;
-- 出库单同理，表名换成 htm_scm_outbound_order

-- ④ P1-1 通知单已完成，但预占一直释放不掉
select count(*) cnt, min(create_time) earliest
from htm_scm_notice_order
where order_type = 10 and state = 300
  and lock_inv_state = 20 and release_inv_state = 11;

-- ⑤ P1-2 作废、审核任务「进行中」超过 1 天
select order_type, operation_type, count(*) cnt, min(create_time) earliest
from hotmaxx_biz_order_task
where status = 10
  and create_time < date_sub(now(), interval 1 day)
group by order_type, operation_type;

-- ⑥ P1-3 通知单「已推送」超过 1 天，但还没完成（条件是推测）
select source_busi_order_type, count(*) cnt
from htm_scm_notice_order
where syn_state = 20 and state = 20
  and create_time < date_sub(now(), interval 1 day)
group by source_busi_order_type;

-- ⑦ P1-4 调拨单停在「推送中」（state = 12 是 provider-ops 自己的枚举里的值）
select count(*) cnt, min(create_time) earliest
from htm_scm_transfer_order
where is_delete = 0
  and state = 12;
```
