# 仓储单据字典

> **来源：** base-scm 的 `constant/` 和 `enumcreate/`、biz-scm 的 `config/common/enums/`、base-ivm 的 `constant/` 里的枚举，脚本抽取后人工核对。
>
> **状态：** 初稿。只列了和 8 张单据、通知单、出入库单、差异单、库存有关的；来源系统、操作类型这类没有列全。值和中文照代码原样抄，包括对不上的地方。
>
> **相关：** [表关系.md](表关系.md)、[服务介绍.md](服务介绍.md)。哪些状态会卡住、卡在哪，见 [治理与风险.md](治理与风险.md)。

| 码 | 含义 | 备注 |
|---|---|---|
| 10 | 采购单 | |
| 20 | 门店配货单 | |
| 30 | 仓间调拨单 | |
| 40 | 库存调整 | |
| 50 | 门店退货单 | |
| 60 | 退供单 | |
| 70 | 库位转移 | 有的常量类里写成「仓位调拨」 |
| 100 | 库存转移 | 只在配货单常量类的来源类型里出现 |
| 510、520 | 采购单发货单 | 只在通知单的来源类型里出现 |

这个枚举在 6 个仓库里有十几份拷贝，各份的枚举名和中文略有出入，改一处其余不会跟着变。

## 二、业务单的状态

### 2.1 采购单

| 值 | `state` | `orderState`（同一常量类里的另一套） |
|---|---|---|
| 0 | 未审核 | 未审核 |
| 10 | 已预审 | 已预审 |
| 20 | 已审核 | 待收货 |
| 200 | 进行中 | 进行中 |
| 300 | 已完成 | 已完成 |
| 500 | 已作废 | 已作废 |

另有两个进度字段：`send_state`（0 初始、10 部分发货、20 发货完成）和 `receive_state`（0 初始、10 部分收货、20 收货完成）。

采购单创建就是 20。回传之后只有「实收 = 计划」才置 300；实收大于 0 但不等于计划（少收、超收都算）置 200，收货状态记「部分收货」；实收为 0 回到 20。代码里对超收留了 2022 年的待办，没有另外处理（base-scm `service/impl/HtmScmPurchaseOrderServiceImpl.java:594` 起）。

### 2.2 门店配货单

| 值 | 含义 | 备注 |
|---|---|---|
| 0 | 未审核 | |
| 10 | 已预审 | 预占失败会退回这里 |
| 11 | 审核中 | 自动审核任务处理中 |
| 12 | 待合并审核中 | |
| 20 | 已审核 | |
| 21 | 待发货日合单 | |
| 22 | 已合单 | 非虚拟仓的配货单只能作废到这一步之前 |
| 100 | 已发货 | 虚拟仓的配货单可以作废到这一步之前 |
| 110 | 到仓签到 | |
| 120 | 到仓交接 | |
| 121 | 仓库发货 | |
| 130 | 到店签到 | |
| 140 | 到店交接 | |
| 200 | 已收货 | 门店收货和仓库实发对不上 |
| 300 | 已完成 | 门店收货和仓库实发一致 |
| 500 | 已作废 | |

配货单上还有几个辅助字段：

| 字段 | 取值 | 用途 |

| `virtual_warehousing` | 0 初始化、1 虚拟入库、2 处理成功、3 处理异常 | 虚拟入库补偿任务用 |
| `cls` | 5 销售出库、10 统配出、20 团购单、30 游戏配货、40 特需配货 | 配货类型 |

### 2.4 仓间调拨单、库位转移单

两种单共用一张表，靠 `order_type` 区分：10 仓间调拨单，20 库位转移单。

| 值 | `state` |
|---|---|
| 0 | 未审核 |
| 5 | 审核中 |
| 10 | 已预审 |
| 20 | 已审核 |
| 200 | 已收货 |
| 300 | 已完成 |
| 500 | 已作废 |

进度字段 `send_state`：0 初始、10 部分发货、20 发货完成；`receive_state`：0 初始、10 部分收货、20 收货完成。

provider-ops 自己的枚举里，调拨单还有一个状态 12「推送中」，是它往海鼎推调拨单时用的；base-scm 的这套枚举里没有 12。

### 2.5 库存调整单

| 值 | `state` |
|---|---|
| 0 | 未审核 |
| 10 | 已预审 |
| 20 | 已审核 |
| 200 | 进行中 |
| 300 | 已完成 |
| 500 | 已作废 |
| 404 | 未知 |

调整类型 `adjust_type`：1 盘盈亏、2 报损单、3 损耗、4 溢余、5 盘盈、6 盘亏、7 未知。方向在创建时就定了：明细的申请数量大于 0 是盘盈，小于 0 是盘亏。

审核时「审核数量 = 申请数量」。代码注释里自己写着「产品设计缺陷，审核时没有输入审核数量」（base-scm `service/impl/HtmScmAdjustOrderServiceImpl.java:636`）。

## 三、通知单

下发给 WMS 的指令单。`order_type`：10 发货、20 收货。

| 字段 | 取值 |
|---|---|
| `state` | 0 未审核、10 已预审、15 待签到、20 已审核、300 已完成、500 已作废 |
| `syn_state`（推送状态） | 0 初始化、10 待推送、20 已推送、30 已回传 |
| `lock_inv_state`（预占） | 0 初始化、10 待处理、20 已处理 |
| `release_inv_state`（释放预占） | 0 初始化、10 待处理、20 已处理；biz-scm 失败时写 11「处理失败」，这个值只在 biz-scm 自己的那份常量里有 |
| `source_order_type`（来源单据类型） | 10 采购单、20 门店配货单、30 仓间调拨单、40 库存调整、50 门店退货单、60 退供单、70 仓位调拨、510 和 520 采购单发货单 |
| `from_code_type`、`to_code_type` | 10 仓位、20 门店、30 供应商 |

## 四、出入库单

WMS 回传的实绩。入库单和出库单各有一套 `state`，入库单另外还有一套 `orderState`。

| 值 | 入库单 `state` | 入库单 `orderState` | 出库单 `state` |
|---|---|---|---|
| 0 | 待入库 | 待入库 | 待出库 |
| 10 | 入库中 | 入库中 | 出库中 |
| 20 | 已入库 | 已入库 | 已出库 |
| 30 | 入库处理失败 | 入库处理失败 | 出库失败 |
| 40 | — | 待作废调账 | 待作废调账 |
| 50 | — | 已作废调账 | 已作废调账 |
| 51 | — | 作废调账失败 | — |
| 52 | — | 作废调账反向冲单 | 作废调账反向冲单 |
| 60 | 待作废 | 待作废 | 待作废 |
| 70 | 已作废 | 已作废 | 已作废 |
| 71 | — | 作废失败 | — |
| 80 | — | — | 作废反向冲单 |

两种单共用的字段：

| 字段 | 取值 |
|---|---|
| `busi_state`（回写业务单）、`notice_state`（回写通知单） | 0 未处理、10 待处理、20 处理中、30 处理成功、40 处理失败、50 待作废、60 作废处理中、70 作废已处理、80 作废处理失败 |
| `audit_state` | 10 待审核、20 已预审 |
| `source_order_type` | 10 发货通知单、20 收货通知单、100 入库单、200 出库单 |
| `source`（谁创建的） | 10 本系统、20 OPS（出库单这里是「海鼎」）、50 海鼎洗数据、60 海鼎经 ops 网关创建、70 中台页面创建、80 中台页面导入、90 中台大数据推送、100 门店组导入、110 采购组推送、120 WMS 回传 |

入库单还有「是否推 CRM」`isPushCrm`：0 未推送、1「不需要推送」、2「已推送」、3 推送失败。枚举名和中文是对不上的：名字叫 `Y` 的值是「不需要推送」，名字叫 `NOT_NEED` 的值是「已推送」。

## 五、差异单

| 字段 | 取值 |
|---|---|
| `state` | 0 未审核、10 已预审、20 已审核、100 已发货、200 已收货、300 已完成、500 已作废 |
| `stock_state`（库存处理） | 0 待处理、10 处理中、20 已处理 |
| `process_inv_state`（判责） | 0 待判责、10 判责待处理、11 判责库存处理失败、20 判责已处理 |
| `confirm_state` | 0 未确认、10 已确认 |
| `diff_logic_repair_state`（历史数据修复） | 0 初始化、2 已修复、3 异常 |
| `order_type` | 10 发货、20 收货 |
| `source_erp` | 10 本系统、20 海鼎 |

判责结果 `process_mode` 写在明细上：100 仓库原因、200 门店加库存、300 门店减库存、400 门店不调整库存。

和库存关系最直接的是 `stock_state`：定时任务只取 0，处理成功置 20，失败置 10，之后没有任何地方再读 10（详见 [治理与风险.md](治理与风险.md) P0-2）。

## 六、库存侧

**库位类型** `warehouse_location_type`：在途和差异就是靠它区分的。

| 值 | 含义 |
|---|---|
| 10 | 在库库位 |
| 20 | 仓间调拨在途 |
| 30 | 仓间调拨差异 |
| 40 | 仓间配货在途（实际用于门店配货） |
| 50 | 仓间配货差异（实际用于门店配货） |

**负库存开关**，都在库位表上：`is_negative_inv`（是否允许负库存，扣减时看它）和 `is_negative_use_inv`（是否允许负可用库存，预占时看它），0 否、1 是。

**库存流水** `htm_ivm_business_inventory_log`：

| 字段 | 取值 |
|---|---|
| `type` | 10 预占加、20 预占减、30 可用加、40 可用减 |
| `source_order_type` | 10 入库记录、20 出库记录、200 出库通知单 |
| `source_busi_order_type` | 单据类型码，见第一节 |

**库存操作类型** `operationType`（调用记账接口时传的）：1 增加库存、2 减少库存、3 预占库存、4 释放库存。

**作废、审核任务**（biz-scm）：

| 字段 | 取值 |
|---|---|
| `order_type` | 10 采购发货单、20 门店配货单、30 仓间调拨单、40 库存调整、50 门店退货单、60 退供单、70 仓位调拨单、520 库存冻结单 |
| `operation_type` | 10 作废、20 审核 |
| `status` | 10 进行中、20 完成 |
| 明细 `execution_action_result` | 10 处理中、20 处理成功 |

任务的步骤按 `execution_sequence` 一步一步执行，每轮只走一步：1 作废并更新单据、2 释放预占库存、3 消息推送门店（只有虚拟仓有）、4 同步计划配货单、5 虚拟仓冲正库存（只有虚拟仓有）。

## 八、枚举名、注释和实际对不上的地方

- 通知单「是否推 CRM」：`Y` 是「不需要推送」，`NOT_NEED` 是「已推送」。
- 通知单的来源系统 `sourceErp`：枚举名是 `DELIVERY`、`COLLECT`、`ERP`，中文是「本系统」「海鼎」「erp」，名字沿用了通知单类型的叫法。
- 库存操作日志类型 `logType`：`ADDITION_STOCK` 的中文是「预占入库」，`LOCK_STOCK` 的中文是「入库」，名称和中文交叉错位。
- 采购单同一个常量类里，`state` 的 20 是「已审核」，`orderState` 的 20 是「待收货」。
- 释放预占的状态，biz-scm 的常量比 base-scm 的多一个 11「处理失败」。
- 库位类型 40、50 的中文是「仓间配货在途」「仓间配货差异」，实际用在门店配货上。
- 库存扣减时，拿「是否允许负可用库存」的枚举去比「是否允许负库存」的字段（base-ivm `service/impl/HtmIvmBusinessInventoryServiceImpl.java:652`）。两个值都是 1，结果没错，读的人会绕。
- 待合并商品表 `hotmaxx_biz_delivery_consolidated_goods` 的 `status`，枚举是 0、10，实体注释是 0、1、2、3。
- 任务表实体的注释写「单据类型 10 发货单、20 配货单」，枚举写的是「采购发货单」「门店配货单」。
- 调拨单的状态，provider-ops 的枚举里有一个 12「推送中」，base-scm 的枚举里没有。
