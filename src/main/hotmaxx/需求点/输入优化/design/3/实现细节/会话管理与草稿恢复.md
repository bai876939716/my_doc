# 会话管理与草稿恢复 

> 一句话：**会话即草稿**——不依赖用户点"保存"，每次状态或槽位变更服务端先落 Redis 再推送；无论哪种退出（杀 App、断网、主动退出），进度天然不丢，回来一个请求就能接着填。
> 接口报文见同目录《[接口文档.md](./接口文档.md)》

---

## 一、管理过程（草稿的一生）

1. **出生**：`POST /agent/repair/v1/sessions`——服务端先查 `rp:active:{uid}` 有无活跃会话，有则**复用**（`is_resumed=true`，前端弹「继续上次报修」），无则新建并带出 3 字段（门店/报修人/日期），**首次快照落 Redis**。
2. **成长**：填报中每次**状态变更或槽位变更**（答完类别、传完照片、打字改电话），服务端**先存再推**。顺序不能反：先存后推，推送失败数据也已在 Redis；SSE 断线重连从快照重放即可。打字改字段不改状态，**同样触发保存**（否则草稿丢这处改动）。
3. **三种终态**：
   - **DONE**：提交成功（order_key 幂等建单）→ Redis 草稿清除、完整会话转 MySQL 归档（对账 / 回放用）；
   - **EXITED-keep**：主动退出选「保存」，再存一次快照，保留 7 天，重进下发「继续上次报修」卡片；
   - **EXITED-abandon**：选「放弃」，标记废弃，保留 24h 供排查后删除。
4. **过期**：TTL 到期自动清除，不需要定时任务；超期重进静默开新会话，用户无感知。

**为什么「错误退出零处理」**：保存时机是「每次变更后」而不是「退出时」——杀 App、闪退、断网根本来不及发请求，但快照早就是最新的。

**并发说明（已知简化）**：同一会话不做多端并发控制——双端同时编辑时后写覆盖先写；单用户单会话场景下概率极低，防重复提交由 order_key 幂等保证。若未来要支持多端协同编辑，再加版本号乐观锁（约 0.5 人天）。

## 二、数据留存（存哪、存什么、留多久）

| 存储 | Key / 表 | 内容 | 留存策略 |
|---|---|---|---|
| Redis | `rp:{session_id}` | 会话快照 JSON（见下） | TTL 7 天**滑动续期**：每次保存顺延，活跃会话永不过期 |
| Redis | `rp:active:{uid}` | **活跃会话索引**：指向该用户当前 session_id | 建会话写入；DONE / abandon / 过期清除；重进复用靠它，不依赖前端本地 |
| Redis | `quota:{uid}:{yyyyMMdd}` | 单人单天 LLM 调用 / token 配额 | 当日 24:00 自动过期 |
| MySQL | 会话归档表 | 终态会话全量（状态轨迹 + 字段 + 消息） | 长期，对账与回放 |
| MySQL | 埋点明细 | 埋点事件 | 长期，指标计算 |
| 前端 | localStorage（传统表单草稿） | 老表单字段值 | **与 AI 草稿不同空间，互不覆盖** |

快照 JSON 结构：

```json
{
  "session_id": "rp_9f3k2m", "user_id": "u_1001", "store_no": "11522",
  "state": "PHOTO", "branch": "B", "status": "active",
  "slots": {
    "category": "工程类 - 制冷设备/冷柜",
    "detail": "故障现象：…；发生时间：…；影响范围：…",
    "photos": ["m_001", "m_002"],
    "expect_visit": "尽快上门", "impact": "是",
    "expect_process": null,
    "slot_meta": { "phone": {"value": "138****1234", "source": "system_default"} }
  },
  "context": { "store": "11522 安徽商之都OK店", "reporter": "白云翔", "date": "2026-11-04" },
  "updated_at": "2026-11-04T12:00:00Z"
}
```

要点：**session_id 从哪来、恢复靠什么**——建会话时服务端返回，前端可存一份作加速（刷新 / 断线重连直接 `GET /{id}`）；但**恢复不依赖本地**：重进统一 `POST /agent/repair/v1/sessions`，服务端按 `rp:active:{uid}` 复用，换设备、清缓存都能续。照片本体在 OSS，快照只存 media_id 引用；槽位带 `source`（system_default / ai_filled / user_edited）作审计留痕。

## 三、接口的关系（谁在什么时候动草稿）

| 接口 | 触发时机 | 草稿动作 | 数据变化 |
|---|---|---|---|
| `POST /agent/repair/v1/sessions` | 进 AI 入口（**统一恢复入口**） | 查 `rp:active:{uid}`：有 → 复用；无 → 新建 + 首次保存 | Key 创建 / 复用，TTL 起算 |
| `POST /messages` | 每条消息**且状态或槽位变更** | **先存再推** | state / slots 更新，TTL 续期 |
| `POST /upload` | 附件上传完成 | media_ids 并入 photos 后保存 | 同上 |
| `GET /{id}` | 会话内刷新 / SSE 断线重连 | 只读 | 不改数据，返回快照 + 消息重放 |
| `POST /submit` | 确认单点提交 | 提交成功 → 草稿终态化 | Redis 清除，MySQL 归档 |
| `POST /exit` | 主动退出弹窗选择 | keep：最后一次保存；abandon：标记废弃 | status=EXITED / abandoned |

两处防坑：消息不产生状态变更时（如 CONFIRM 态补充描述）只更新 slots 不动 state，照样先存再推；配额 Key 与草稿 Key 完全独立，超限降级不影响已有草稿。

## 四、三个典型场景走查

**场景 1 · 错误退出**：填到照片步骤 App 被杀——没有任何退出请求，但快照停在 `{state: PHOTO}`；重进 AI 入口，服务端按 `rp:active` 复用会话并**重放消息**，界面直接回到拍照那一步，已答内容全部回显。零 LLM 调用。

**场景 2 · 主动退出 keep**：点返回 → 三选项弹窗 → 选「保存草稿退出」；快照保留 7 天；期间再进入口，检测到 keep 会话 → 下发「继续上次报修」卡片（draft_resume 埋点）→ 点选即恢复。

**场景 3 · 7 天过期**：keep 后一直没回来，TTL 到期自动清除；重进时无活跃会话，前端静默开新会话——用户感知就是「新的一次报修」，没有报错。

## 五、实现难度与工作量

| 模块 | 难度 | 工作量 | 说明 |
|---|---|---|---|
| 状态机引擎（含会话驱动） | ★★☆ | 2 人天 | 转移表 + 状态处理函数 + 单测（含 EXITED / exit 事件） |
| Redis 快照保存 | ★☆☆ | 1 人天 | 单 Key JSON，读写各一行（引擎内置，不工具化） |
| 断点恢复（读档重放） | ★☆☆ | 0.5 人天 | 快照读出按状态渲染对应界面 |
| 主动退出（exit 接口 + keep/abandon） | ★☆☆ | 0.5 人天 | 一次保存 / 一个废弃标记 |
| **合计** | | **≈ 4 人天** | 全部成熟组件，无自造轮子 |

（SSE 服务端推送 1 人天 + 前端接收 1 人天另计，协议格式见《接口文档.md》§2.2。）
