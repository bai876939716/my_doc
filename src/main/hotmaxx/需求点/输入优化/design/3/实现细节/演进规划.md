# 演进规划 

> 主文档 §3.2 的一句话版：**五个未来组件按必要性排序（P1 Java 服务层 → P5 图编排），做不做评审拍板。**
> 本篇是完整版：每个组件的成本 / 收益 / 必要性思考 + 建议时机。
> 演进主线（与架构图白色虚线一致）：本期「已有网关 + Agent 单体」 → 后续「AI 独立网关 → Java 层（数据权限 / 并发处理 / 基础数据查询）→ Agent」→ 多 Agent 终态。

## 一、总表（按必要性排序 · 评审拍板做与不做）

| 优先级 | 组件 | 解决什么问题（不做会怎样） | 成本 | 必要性思考 | 建议时机 |
|---|---|---|---|---|---|
| **P1** | **Java 服务层** | 并发限流 / 数据权限 | 中：**样本证据**（已搜的三个仓）——Gateway/Nacos/Redisson/认证体系在用；Sentinel 仅声明未启用、熔断无、自研 Redis 限流闲置。**盲区待补**：Nacos 线上配置 / 运维层限流 / 其他仓库搜不到，最终以平台组确认为准。限流落地方案不受影响：网关自带 RequestRateLimiter（配置级） | **唯一的「不做会出事」**——放量安全门槛：单门店试点不需要，灰度扩门店前必须有；这也是把鉴权从 Agent 下沉的承接层 | 灰度扩门店前 |
| **P2** | **LLM 网关独立服务** | 多模型主备切换、token 预算核算、多业务分摊模型成本 | 低：选型开源（LiteLLM / OneAPI）一个容器，不自研 | 单业务期应用内薄封装（≈1 人天）已够用；**收益在「多模型 / 多业务」出现时才兑现**——成本低，可提前也可等需求 | 多模型需求或多业务出现 |
| **P3** | **AI 网关**（公司级统一入口） | 全公司智能体的统一入口：模型路由 / 计费 / 限流共享 | 高（自研）｜低（若由 P1+P2 合并演进） | **P1 + P2 的公司级合并形态**（业务流量权限 + 模型治理合到一个入口）——单独建必要性最低，公司统一建则直接接入 | 第 2~3 个智能体业务出现 |
| **P4** | **mcpServer 独立服务化** | 报销 / 多 Agent 共用同一套工具层 | 极低：工具接口已解耦，抽出独立部署 ≈1 人天 | 期权型——没有第二个调用方就永远不需要；接口画对了，什么时候要什么时候拆 | 第二个调用方出现 |
| **P5** | **图编排**（LangGraph） | 复杂多分支回环的流程编排 | 中：框架学习 + 迁移改造 | 现在的线性采集流程吃不到红利；状态 = 节点、转移表 = 边，路径已留 | 流程真长成图 |

## 二、并发四板斧（P1 落地时的具体做法）

限流（Redis 令牌桶 / 网关 RequestRateLimiter，维度：全局 QPS / 单用户 / 并发流数）、排队（对话场景甜点：超额进队列等 LLM 槽位，typing 动画天然掩护）、熔断（连续失败率超阈值直接走降级；MVP 期靠应用内三级降级兜住，网关层熔断等出过事故再加）、隔离（SSE 长流与短请求分线程池，防长连接饿死短请求）。技术关键：SSE 转发必须 reactive（WebFlux/Netty，Spring Cloud Gateway 天生是）。

## 三、各组件迁移路径（为什么说「已钉死」）

| 组件 | 迁移动作 | Agent 侧改动 |
|---|---|---|
| 接入已有网关（本期已定） | Nacos 加路由 + response-timeout > SSE 时长 | 解析 HTM-HEADER 拿 userid（≈半天） |
| P1 Java 层 | 网关后加一层（或增强网关规则） | 鉴权下沉，Agent 收已鉴权用户上下文 |
| P2 LLM 网关独立 | LLMGateway 类换成指向新网关的 HTTP client | 零改动（调用全收口在这一个类） |
| P4 mcpServer 独立 | ToolProvider 换 McpToolProvider 适配器（≈1 人天） | 零改动（引擎只依赖接口抽象） |
| P5 图编排 | 状态 = 节点、转移表 = 条件边平移 | 迁移改造（成本中等，触发即接受） |
