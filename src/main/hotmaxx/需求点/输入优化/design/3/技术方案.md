## 1. 产品考虑的点

### 1.1 强约束

| # | 约束点            | desc                                                              |
|---|----------------|-------------------------------------------------------------------|
| 1 | 流程可控，不跳步、不漏问   | 1.沟通没完没聊，不断的问答，却解决不了问题；  <br/> 2.表单字段有先后顺序 （可能关联性）；<br/>3.字段要保证齐全 |
| 2 | 类别绝不能选错        | AI 只能给候选，必须用户确认                                                   |
| 3 | 任意字段随时可改       | 不能让用户被流程绑架 中途有问题还得重来                                              |
| 4 | 填一半退出，回来接着填    | 草稿保留 7 天                                                          |
| 5 | AI 挂了不能耽误报修    | 降级成卡片点选或回老表单                                                      |
| 6 | 对话有边界（新增）      | 只采表单内 10 个字段；问进度/闲聊/越权/注入一律拉回；连续失败降级                                |

## 2. 核心思路与实现方式对比

### 2.1 核心思路

> 1. LLM 负责识别与生成（听懂口语、抽出结构化字段） <br/>
> 2. 程序负责流程（ 编排方式、 状态机方式） <br/>
> 3. 人负责确认（AI 预填、点选提交才入库）

### 2.2 实现方式对比

**A. 纯 LLM 自主对话（ReAct）**

**实现过程**：一个系统提示词 + 若干工具（查字典、查档案、建单），llm每轮自己决定调哪个工具、问什么，循环直到参数补齐。

**考虑的点**：每轮流程都是模型临时决策——跳步漏问不可控、容易编造枚举，轮次太多成本也不可控

**B. 纯 LangChain 线性串联（Runnable）**

**实现过程**：把"类别识别→详情抽取→确认单"写成 RunnableSequence 管道（prompt | 模型 | 解析器一路串），一次 invoke 跑到底；流程顺序写死在管道形状里，把进度、全历史 塞回 prompt 让模型自己读。

**考虑的点**： 回跳只能整条链重跑 （做不到随时改-约束点1） ，强行实现需要自己加if调度 繁杂且僵硬。

**C. LangChain + 状态机 —— 这次采用 ✓**

**实现过程**：流程是一张 状态转移表（状态 × 事件 → 下一状态），每条用户消息是事件，查表转移；全流程 LLM 只被调用在理解环节（每条打字消息一次联合抽取），其余全是规则代码。

**考虑的点**：步数和llm调用次数可控；满足产品需求，支持中途修改 和断点恢复。

**D. LangGraph 图编排 —— 后续考虑**

**实现过程**： StateGraph 定义节点（=状态）与条件边（=转移），Checkpointer 内置断点续填，interrupt() 原生支持人机确认。

**考虑的点**：能力最强，单业务的线性流程 吃不到图编排的红利  。

**E. Dify**

**考虑的点**：适合简单知识库； 前后端对接 （比如卡片 、降级方案）、数据埋点 需要挂一层服务去处理； 灵活性较差 （回跳实现较复杂）

**F. Coze 扣子**

**考虑的点**：编排问题同dify一样；  saas(数据出域)， 本地部署 组件更重； 官方的定义就是用来验证

## 6. 对话状态机（12 状态）

状态机图：[02-对话状态机图.puml](./diagrams/02-对话状态机图.puml)

| 状态 | 职责要点 | LLM | 出口 |
|---|---|---|---|
| INIT | 工具带出 3 字段，下发状态条 + 高频卡片 | — | 文字→A_DESC；卡片→B_LOCK |
| A_DESC | 自由描述 → **联合抽取**（类别 Top3 + 描述整理 + 影响预判） | ✓ 1次 | 有效→A_ENUM；失败/候选滤空→FALLBACK |
| A_ENUM | Top3 枚举单选卡（AI 预选首位，**必须点选**） | — | 点选→PHOTO |
| B_LOCK | 卡片即类别，**免类别免描述**，直接拍照（购物袋类提示拍袋底供应商标识） | — | →PHOTO |
| PHOTO | 现场照片，按类别拍摄清单**规则校验** | — | 齐→EXPECT；缺→补拍循环 |
| EXPECT | 期望上门二选一（尽快上门 / 可等待安排） | — | 点选→IMPACT |
| IMPACT | 影响营业 是/否；A 路径已预判→点选确认，B 路径直接问 | — | 点选→PHONE |
| PHONE | 联系电话默认本人（+86），可改 | — | 确认/改→CONFIRM |
| CONFIRM | 10 字段确认单，全部 ✏️ 可改；B 路径描述为空自动填「类别＋详见现场照片」 | — | 提交→DONE；重选类别→回 PHOTO 联动重校验 |
| DONE | 出单号，跳已有记录页；**提交后不可改**（驳回重提/人工） | — | 终态 |
| EXITED | 主动退出（任意非终态可触发） | — | keep 草稿 7 天可续 / abandon 废弃 |
| FALLBACK | 全量类别点选；LLM 不可用降级卡片向导 | — | 选定→PHOTO；切老表单→终态 |

两分支差异只在入口（B_LOCK 免确认免描述、A_ENUM 必须点选），汇合后完全一致。**随时改**：任意状态打字 → 联合抽取识别 update → 普通字段原地覆盖、**状态不变**；类别是唯一例外（连带照片与描述，回跳重校验）。

## 7. Prompt 工程（详见 [实现细节/提示词工程.md](./实现细节/提示词工程.md)）

| Prompt | 用途 | 关键约束 |
|---|---|---|
| 系统提示词 | 注入每次调用 | 只采 10 字段；禁字典外枚举；一轮一事；JSON 输出 |
| 联合抽取（全流程唯一调用点） | 每条打字消息一次：意图+槽位+类别候选+描述整理+影响预判 | 类别字典注入；用户消息三引号包裹当数据；候选限 3 个过白名单 |
| 话术模板（不调 LLM） | 追问 / 拉回 / 改字段确认 / 报错 | 按状态 + 槽位缺失拼装；口径统一、可运营 |

**不做置信度**：识别成功一律 Top3 单选卡（首位预选、必须点选）；失败或候选被白名单滤空 → FALLBACK 全量点选。

## 8. 防幻觉 和 结构化输出[：](./实现细节/防幻觉与结构化输出.md)


| 环节 | 机制 |
|---|---|
| 输出格式 | JSON mode；解析失败重试 1 次，再失败进 FALLBACK |
| 枚举校验 | 候选逐个与字典白名单比对，非法丢弃；丢弃后为空→FALLBACK |
| 候选排序 | Top3 首位预选仅影响卡片顺序——**必须用户点选才入库** |
| 意图边界 | intent 限定六类 + 字段白名单（10 字段外一律丢弃拉回）；注入当数据 |
| 描述校验 | 整理结果（现象/时间/范围）在确认单展示可编辑，≤100 字截断 |
| 提交校验 | 前端 + 服务端双重校验 10 字段必填（B 路径描述自动补默认值），缺一不进 DONE |

## 10. 前后端接口

完整报文：[实现细节/接口文档.md](./实现细节/接口文档.md)

| 接口 | 方法 | 说明 |
|---|---|---|
| `/agent/repair/v1/sessions` | POST | 建会话 / 恢复入口（复用活跃会话，返回 is_resumed）+ 首屏消息 |
| `/agent/repair/v1/sessions/{id}/messages` | POST | 用户消息，响应 SSE 流（typing→message→done） |
| `/agent/repair/v1/sessions/{id}/upload` | POST | multipart 附件 → media_ids |
| `/agent/repair/v1/sessions/{id}` | GET | 会话内刷新 / SSE 断线重连（快照重放） |
| `/agent/repair/v1/sessions/{id}/submit` | POST | CONFIRM 提交（order_key 幂等），调 create_repair_order |
| `/agent/repair/v1/sessions/{id}/exit` | POST | 主动退出，mode=keep（存草稿）或 abandon（废弃） |

> 用户消息 type 6 种：`text` / `card` / `enum_pick` / `seg_pick`（期望上门·影响营业通用）/ `upload_done` / `phone`；
> 提交走独立接口 `POST /submit`（order_key 幂等）。
> 服务端消息 type 10 种（与前端组件一一对应）：`status_bar` / `text` / `quick_cards` / `enum_card` / `photo_guide` / `system_tip` / `seg_card` / `phone_confirm` / `confirm_card` / `result`。

## 12. 埋点清单

| 事件 | 支撑指标 |
|---|---|
| session_start / session_end | 填报时长、步数 |
| branch_a_input / branch_b_card_click | 路径占比 |
| **enum_first_pick** | **类别识别准确率**（AI 首选 vs 用户最终确认） |
| fallback_enter / switch_to_form | 兜底率、转老表单率 |
| session_exit(keep/abandon) / draft_resume | 中途放弃率、续填恢复率 |
| field_edit | 确认单改动量（AI 预填质量侧写） |
| submit_success / submit_fail | 完成成功率、卡壳定位 |
| llm_call（次数/token/耗时/失败） | 成本对账、模型质量 |

对账口径：AI 渗透率 = AI 提交单量 / 明道云总报修单量；查询模块使用度由已有记录页埋点承担；上线前导出老表单 2 周数据做基线。
