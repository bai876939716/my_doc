## 一、一分钟读懂

整个方案就四句话：**在现有 App 里加一个对话页**（表单页顶部入口，别的都不动）；**AI 只负责听懂人话**（认类别、理描述、预判影响），**流程由一张状态表管着**（不跳步不漏问，AI 说了不算）；**最后一步永远是人点确认**才提交，提交走服务端**唯一明道云账号**（省账号费的核心）；**AI 挂了就退回点卡片/填表单**，报修永远有路。

一句话成本账：一次报修 AI 只调用 1~2 次大模型（B 路径点卡片 0~1 次），话术全是模板拼的，不烧钱。

## 二、总体架构：商场里加个问询台（主方案 §3~§5）

**白话**：不动商场里任何一家店（现有表单页、记录页、明道云都保持原样），只新增一个问询台（Agent 服务）。店员在对话页说话 → 问询台后面的大脑（状态机 + LLM）听懂、填好单子 → 店员确认 → 问询台拿着**公司唯一的一把明道云钥匙**去后台开单。钥匙只在问询台手里，各门店不用再买账号。

**和旧方案（13 字段时代）的差别**：带出字段 9 项变 3 项；工具 7 个收成 4 个（草稿改引擎内置、照片校验并入字典清单、查询干脆不建——历史记录页已有现成接口）；工具层改为 **ToolProvider 接口抽象 + 进程内直调**（零协议开销，独立服务化时引入 MCP 协议，引擎零改动）。

**图**：[01-架构图](./diagrams/01-架构图.puml)（部署视角：彩色 = 本期临时方案 · 白色虚线 = 未来独立形态）。加什么不加什么（AI 网关不建 / LLM 网关应用内薄封装 / mcpServer 暂在 Agent 进程内 · 工具层解耦 / 自研状态机 / Python 单栈留多语言出口）的结论见主方案 **§3.2 关键决策表**，展开论证见本文第四、五节。

**难度：低~中 ｜ 工作量：服务骨架 1.5 人天**

## 三、MVP 裁剪：哪些必须做、哪些先不做（主方案 §13.1）

**白话**：必须做的是「从说话到出单号」这条主干（10 组，对齐蓝图 ⭐19 项）；砍掉的全是**主干通了才有意义的安全气囊**（限流、监控、审计、脱敏）。MVP 期用土办法顶：限流先只做「单会话最多 6 次 AI 调用」，全套配额熔断等放量给全公司门店用之前再补——**演示可以不带，不齐不放量**。

判断口诀就一条：**砍掉的东西，必须有降级路顶住，不能让店员报不了修。**

**难度：低（裁剪是决策不是代码）｜ 工作量：0，但决定了 15 人天装得下**

## 四、技术选型：四个最值得问的为什么（主方案 §2~§4）

**1. 为什么自己写状态机，不让 AI 自己聊？**（难度：中 ｜ 2 人天）
餐厅比喻：服务员（LLM）耳朵灵——能把「冰柜不对劲」听成「制冷设备类」；但**上菜顺序由后厨流程单（状态机）定**，服务员说不上话，收银（提交）必须客人自己确认。AI 自由聊天式填报等于让服务员即兴发挥——跳步、漏问、编造菜单外菜品全拦不住。LangGraph 图编排能力确实强，但这条流程是「排队打饭」不是「走迷宫」，留作多智能体终态。

**2. 为什么工具 4 个就够，不照旧方案做 7 个？**（难度：中 ｜ 1.5 人天）
新表单砍掉了 6 个字段，带出信息一个 `get_user_context` 全带回来；草稿是引擎自家 Redis 读写，包成工具给谁用？照片校验是「对着清单数照片」的规则活，跟字典一起下发就行；查询——历史记录页是现成的，接它就是。**工具越少，联调和出错面越小**。

**3. 为什么话术全模板化，不让 AI 自己说？**（难度：低 ｜ 0.5 人天）
AI 的话术不可控还费钱。追问、拉回、报错全部从模板库拼装，LLM 只产出结构化数据和整理后的描述文本。口径统一、零调用成本、放量前还能做成话术配置化让运营自己改。

**4. 为什么工具层不上 MCP，用接口直调？**（纯选型 ｜ 0 人天）
一句话：**单体内直接接口调用是零损耗的，MCP 的价值在跨进程/跨消费者——本期两个都没有，先不付协议税。**展开：同进程走 MCP 每次调用多 2~10ms（性能可忽略，被 LLM 秒级延迟淹没），真正的成本是握手/JSON-RPC/会话管理的复杂度摩擦；改用端口-适配器——引擎只依赖 `ToolProvider` 接口，本期 Local 实现进程内直调，未来独立服务化时换 `McpToolProvider` 适配器（≈1 人天）或直接部署为 MCP 服务（想用 Java 重写也行），**引擎一行不改，迁移成本封顶**。一句话：**MCP 留到工具层独立那天再上，正当时。**

## 五、Agent 核心：一条消息的旅程（主方案 §6、§7）

**点餐厅比喻走一遍**：店员说「冷柜不制冷了，早上开始的，鲜奶都下架了」——

1. **快筛**：点按钮直接走流程（0 调用），打字才进 LLM 管线
2. **联合抽取**（一次调用听全）：类别候选 Top3 + 描述整理（现象/时间/范围三段式）+ 影响营业预判（鲜奶下架=影响）**一次全拿到**——不是问一句调一次
3. **校验**：候选逐个对菜单（枚举白名单），菜单外扔掉；全扔没了给全量菜单自己点（FALLBACK，AI 不猜）
4. **分诊**：问进度、闲聊、报别家店、「忽略之前指令」——一律一句话拉回，不执行
5. **状态机**：查表定下一步（拍照→期望上门→影响营业→电话→确认单）；中途说「电话换成店长的」——**只改单子不重排队**；改类别才回炉（照片要求可能变）
6. **执行**：话术模板拼一句，SSE 推给前端

**槽位=点菜单**：10 字段一菜一位，记着「谁填的」（系统带出/AI 预填/人改过）。**快照=游戏存档**：每走一步先存档再说话，退出 7 天内回来接着打。

**图**：[02-对话状态机图](./diagrams/02-对话状态机图.puml)（流程单）、[03-系统交互泳道图-简易](./diagrams/03-系统交互泳道图.puml)、[03-系统交互泳道图-详细](./diagrams/03-系统交互泳道图-详细.puml)（真实接口怎么走）。

**难度：管线中（LLM 输出稳定性要调）、状态机低（表驱动可单测）｜ 工作量：状态机 2 + 管线 2 + 校验 1 = 5 人天**

## 六、评审问答（8 问）

**Q1：为什么不用 Dify / Coze 这类现成平台？**
一句话：平台解决的是「能对话」，我们难的是「流程可控 + 系统对接 + 降级兜底」，恰好都是平台短板。展开：①我们的对话是**带状态的表单流程**（随时改、类别回跳、断点续填），平台线性编排做回头路很别扭；②卡片消息、配额降级、埋点都要在平台外面再挂一层网关，架构变四层；③Coze SaaS 版数据出域直接否决，私有化又太重。平台的合适位置：以后做知识库问答（RAG）。自研核心其实很小：状态机约 300 行表驱动代码。

**Q2：用户乱输入、提示词注入怎么办？**
一句话：AI 的输出里没有「执行」这个词。四道防线：①**内容**——输出限定 JSON + 字段白名单，表外一律丢弃拉回；②**流程**——LLM 输出里没有「提交/跳步」这类动作枚举，想越权没有通道；③**安全**——用户输入当数据不当指令（三引号包裹），识别出注入当普通文本扔掉；④**兜底**——连续 2~3 轮听不懂就甩卡片点选或引导回表单，绝不僵持。

**Q3：AI 挂了、明道云挂了，会不会耽误报修？**
一句话：永远有路。AI 超时重试 1 次就换高频卡片（纯规则）；AI 整体不可用进卡片向导；明道云提交失败本地存待发表重试 3 次后转人工；店员任何时候可「切回表单录入」。降级是 MVP 就带的。

**Q4：11.16 交付现实吗？**
一句话：15 人天数得过来，但硬前提是依赖先到位。后端 ≈11.5 + 前端 ≈3.5，1+1 并行，11.9 基建 / 11.11 打通 / 11.13 联调 / 11.16 验收。**risk 不在代码在依赖**：真实枚举字典、员工档案接口、明道云 IP 白名单——11.9 前不到位里程碑就滑，评审会上定责任人和时间点。

**Q5：单账号之下，A 店能看到 B 店的单吗？**
一句话：钥匙只有一把，但门上装了过滤网。业务身份（门店/报修人/电话）写进表单字段而非靠账号区分；服务端按登录人绑定门店过滤，越权直接拒绝；明道云密钥只在服务端进程内。建议给授权密钥加 IP 白名单（TODO 已列）。

**Q6：会不会重复提交、丢单？**
一句话：取餐号制度。提交带 order_key 幂等键——同一个键重试几次明道云只落一单；ver 乐观锁防两个手机同时改；失败进待发表重试，耗尽转人工，本地永远有底。明道云侧幂等机制需上线前实测确认（TODO）。

**Q7：类别识别错了怎么办？**
一句话：AI 只有提名权，没有决定权。候选过白名单、最多 Top3、**必须店员点选**才入槽；识别不了给全量列表，AI 不猜；确认单上随时重选（回跳重校验照片）。上线后用 enum_first_pick 埋点度量「AI 首选 vs 用户确认」一致率。

**Q8：成本多大、怎么控？**
一句话：一张单一两次调用，三级闸兜底。测算：日均 100 单 × 1.5 次调用 × 1~2 千 token，月成本百元级，相对省下的门店账号费忽略不计。三级闸：会话 ≤6 次（MVP 就有）→ 单人单日限额（放量前）→ 全局日配额熔断（放量前）；超限自动降级卡片模式，报修不停。
