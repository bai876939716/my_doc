# 设备报修 · AI 填报 Agent 技术方案

> 一句话：**LangGraph 引擎 + 报修技能包——流程是引擎的一张通用图，业务是包里的一份字段说明书；本期落地报修，新业务按技能包低成本接入。**

---

## 1. 背景与目标

- 门店报修业务在明道云，按账号收费、表单字段繁杂；通过 **AI 对话式填报**实现信息录入：说一句话，AI 识别、整理、预填，店员点选确认后提交。
- 两个目标：**报修录入本期端到端落地**；**架构按可复用搭**——核心资产（引擎 / 消息协议 / 槽位类型 / 工具设施）一次建设，后续业务（报销已做接入推演）按技能包接入，最终演进到多智能体。

## 2. 核心思路与实现方式

### 2.1 核心思路

> 1. **LLM 负责识别与生成**（听懂口语、抽出结构化字段）
> 2. **LangGraph 负责编排**（通用采集图管流程、interrupt 管人机确认、Checkpointer 管存档恢复）
> 3. **技能包定义业务**（字段 schema + 字典 + 话术 + 工具 + 钩子，业务差异全部收敛在包里）
> 4. **人负责确认**（AI 预填、点选提交才入库）

### 2.2 实现方式对比

| 候选 | 一句话定位 | 判定 | 理由 |
|---|---|---|---|
| A. 纯 LLM 自主对话（ReAct） | 模型每轮自己决定问什么、调什么 | ✗ | 跳步漏问不可控、易编枚举、轮次成本不可控 |
| B. 纯 LangChain 线性串联 | RunnableSequence 一路跑到底 | ✗ | 回跳只能整链重跑，随时改做不到 |
| C. 自研状态机 | 状态 × 事件转移表自管流程 | ✗ | 存档恢复 / 人机中断 / 流式等通用能力全部要自建自维，框架已内建 |
| **D. LangGraph 图编排** | StateGraph 节点 + 条件边，Checkpointer 内置断点续填，interrupt() 原生人机确认 | **✓ 采用** | 编排 / 存档 / 恢复 / 中断 / 流式全部原生；技能包可直接演进为多 Agent 的子图 |
| E. Dify | 低代码平台 | ✗ | 卡片消息协议无对应物、降级埋点需外挂网关、私有化运维重 |
| F. Coze 扣子 | SaaS 低代码 | ✗ | 数据出域；私有化部署组件重 |

## 3. 系统架构

系统架构图：[01-架构图.puml](./diagrams/01-架构图.puml)

- **唯一新建部署单元**：Agent 单容器（mcpServer 工具层 + LLM 网关在进程内、逻辑解耦）；接入公司已有网关（Nacos 加路由，Agent 解析 HTM-HEADER 拿 userid，❗路由 response-timeout > SSE 时长）。
- **容器内**：FastAPI 会话 API + LangGraph 引擎（通用采集图）+ 报修技能包。
- **对外**：六接口、卡片消息协议、SSE——前端与平台组零改动。
- **存储**：Redis = LangGraph 检查点（thread_id = 会话）+ 配额；MySQL = 消息表（全量对话，每轮批量入库）/ 归档 / 埋点 / 调用日志。

## 5. LangGraph 编排过程（技术核心）

> 通用采集图：[02-通用采集图.puml](./diagrams/02-通用采集图.puml) ｜ 实现细节：[实现细节/LangGraph落地设计.md](./实现细节/LangGraph落地设计.md)

### 5.1 State：

| 字段 | 类型 | 内容 |
|---|---|---|
| `skill` | str | 技能包名（repair） |
| `context` | dict | 带出字段（门店 / 报修人 / 日期 / 手机号） |
| `slots` | dict | **槽位值**：每个字段一格 `{value, source, updated_at}`；source ∈ system_default / ai_filled / user_edited |
| `agenda` | list | **待问清单**：由技能包 schema 的必填槽位生成，答一个划一个——"问到哪了"是数据不是代码 |
| `messages` | list | 对话消息（**最近 10 轮滑动窗口**；全量每轮批量入库 MySQL、复原两源拼接；不进 Prompt） |
| `meta` | dict | 分支 / 失败计数 / 退出状态 |

> State 完整数据结构、真实快照与设计理由：[实现细节/State设计.md](./实现细节/State设计.md)。

### 5.2 图与节点

节点结构图：[02-通用采集图.puml](./diagrams/02-通用采集图.puml) ｜ 场景版（剧本对话 × 节点流转对照）：[03-场景流转图.puml](./diagrams/03-场景流转图.puml)

```
START → load_context → extract → update → route ─┬→ ask → END(本轮结束)
                        ↑                     ├→ confirm(interrupt) ─┬→ submit → DONE
                        └── 下一条打字消息        └→ fallback → END      └ resume(改字段) → extract
```

| 节点 | 职责（输入 → 输出） | LLM |
|---|---|---|
| `load_context` | 建会话：调工具带出 3 字段 → 下发状态条 + 高频卡片 | — |
| `extract` | 每条打字消息一次**联合抽取**：意图 + 槽位增量 + 类别候选 Top3 + 描述整理 + 影响预判 | ✓ **全流程唯一调用点** |
| `update` | 过防幻觉闸（枚举白名单）→ 写槽位 → 钩子联动失效 | — |
| `route` | 看议程与意图：缺什么问什么 / 齐了进确认 / 越界拉回 / 连续失败降级 | — |
| `ask` | 话术模板 + 槽位类型 → 卡片形态，下发后本轮结束 | — |
| `confirm` | 生成 10 字段确认单 → `interrupt()` 挂起等人 | — |
| `submit` | order_key 幂等建单 → 出单号 | — |
| `fallback` | 全量类别点选 / 卡片向导 | — |

**每轮 = 一次图执行**：messages 接口收到用户消息 → `graph.ainvoke(消息, thread_id=会话ID)` → 图跑到 ask 或 confirm 挂起 → 本轮结束。跨轮状态全靠 Checkpointer。

### 5.3 一次报修的完整执行（剧本 A · 逐轮走查）

| 轮 | 用户动作 | 经过的节点 | State 变化 | 检查点 | 下发 |
|---|---|---|---|---|---|
| 1 | 进入口 | load_context | context 3 字段入板；agenda=[类别,描述,照片,上门,影响,电话] | v1 | 状态条+开场+高频卡片 |
| 2 | 打字"冷柜不制冷…" | extract→update→route→ask | 描述入槽(ai_filled)；类别=候选未定稿；描述划出议程 | v2 | 类别 Top3 单选卡（必须点选） |
| 3 | 点选类别 | update→route→ask | 类别定稿(user_edited)；类别划出 | v3 | 拍照引导（按类别清单） |
| 4 | 传 2 张照片 | update→route→ask | photos 入槽（清单规则校验过）；照片划出 | v4 | 期望上门二选一卡 |
| 5 | 点选上门/影响/电话 | 三轮：update→route→ask | 每点一次写一格、划一项（点选 **0 LLM**） | v5→v6→v7 | 下一问 / 电话确认卡 |
| 6 | 议程清空 | route→confirm | 7/7 齐 → **interrupt() 挂起** | v8（挂起状态也存档） | 确认单（全部 ✏️ 可改） |
| 7 | 点【确认提交】 | (resume)→submit→DONE | 单号产生；终态 | v9→删检查点+归档 MySQL | result 单号 → 跳记录页 |

> 全程 LLM 调用 **1 次**（第 2 轮）；其余全是规则与模板。卡片路径（点高频卡直锁类别）跳过第 2 轮的抽取，**0 LLM** 也能走完全程。
> 四个场景（0 LLM 卡片路径 / 随时改与重选类别 / 断线恢复与降级）的节点运转过程与每版 State 全量 JSON：[场景演示.html](diagrams/场景演示.html)（变化字段标红，点开查看）。

### 5.4 条件边路由（route 节点的判定表）

| 意图（extract 输出，六类枚举） | 议程状态 | 下一跳 |
|---|---|---|
| provide（提供信息） | 有缺槽 | ask（问议程首项） |
| provide | 必填全齐 | confirm（interrupt 挂起） |
| update（改字段） | 任意 | update 原地覆盖 → 回当前焦点，**议程不变** |
| query_progress / smalltalk / off_scope | — | ask（模板话术拉回，一轮一事） |
| inject_attempt（提示词注入） | — | 同上：输入三引号包裹当数据，槽位零写入 |
| 连续 2~3 轮识别失败 | — | fallback（卡片向导，0 LLM） |
| exit | 任意非终态 | EXITED（keep 7 天 / abandon） |

### 5.5 存档与恢复（Checkpointer）

- **存什么**：整个 State（槽位 + 议程 + 全部消息）——每个节点执行完自动落 Redis，即"先存再推"的原生版，业务代码零存档逻辑。
- **thread_id = 会话 ID**：断线重连 / 会话刷新 = `get_state(thread_id)` 重放消息；错误退出（杀 App / 断网）零特殊处理，重进按活跃索引复用会话。
- **确认单**：`interrupt()` 挂起；`POST /submit` = `Command(resume)` 恢复走 submit；确认单上改字段 = 带新值 resume 回 extract。
- **留存**：TTL 7 天（配置 + 每日清理任务兜底 ❗POC 项）；DONE 后删检查点、终态归档 MySQL。

### 5.6 随时改（产品约束的图上实现）

打字 = extract 识别 `update` → 槽位原地覆盖、议程不变（改内容 ≠ 改流程）；**类别是唯一例外**：钩子触发照片与描述联动失效，重新进入议程问照片——产品语义"类别重选回跳"由数据失效实现，体验一致。

### 5.7 降级

LLM 失败 / 配额超限 / 连续识别失败 / 引擎运行时异常 → 同一出口：fallback 卡片向导（0 LLM）→ 引导回传统表单，填报永远有路。

### 5.8 设计考量：图为什么这样设计，为什么能支撑后续业务

**（1）产品约束倒推**——图的每个机制都对应一条产品硬约束（§1.1），没有为技术而技术的设计：

| 产品约束 | 图上的落点 |
|---|---|
| 流程可控、不跳步不漏问 | 议程驱动：route 只认 agenda，答完一项才放下一项；必填不齐进不了 confirm |
| 类别绝不能选错 | extract 只产候选（进卡片消息不进槽位）+ update 白名单过滤 + 必须点选定稿 |
| 任意字段随时可改 | 任意时刻打字 → extract 识别改字段意图 → 槽位原地覆盖、议程不变 |
| 填一半退出能续填 | Checkpointer 每个节点后自动存档；interrupt 挂起状态也存档 |
| AI 挂了不误事 | fallback 是图上的一等节点（不是异常分支）：0 LLM 向导走完全程 |
| 对话有边界 | 意图六类枚举 + 字段白名单 + 连续失败计数 → fallback |

**（2）节点切分的考量**：每节点单一职责（单测矩阵最小）；**LLM 收口在 extract 一个节点**——成本可算、可 Mock 测试、可整体跳过（跳过即降级路径）；"问什么"不写在任何节点里——ask 只按议程首项 + 槽位类型下发。由此得到采集类业务的**七步不变量**：带出 → 理解 → 校验 → 路由 → 追问 → 确认 → 提交——它对任何表单填报业务成立，这是"一张图跑所有业务"的依据。

**（3）为什么能支撑报销**——报销比报修难在字段（24 个、树/子表/字段组），不难在流程（仍是"缺什么问什么→确认→提交"）。它带来的全部新东西都不触碰图的节点与边：

| 报销的新增 | 触碰图？ | 落在哪 |
|---|---|---|
| 6 种新槽位类型（tree/money/date/subgroup/subtable/computed） | 否 | 槽位类型系统（core 设施）+ 技能包 schema |
| 一句话抽多行明细 | 否 | extract 输出 schema 的技能包模板扩展 + 行卡片 |
| 一级部门推导 / 行数上限 / 欠票联动 | 否 | 钩子声明 |
| 收款人四件套记忆 | 否 | 记忆工具（ToolProvider，预留） |
| 4 种新卡片形态 | 否 | 消息协议增量（type 只增不改，v1 内兼容） |

一句话：**图编排的是采集流程的共性（缺什么问什么、齐了确认、挂了降级），不承载业务个性（字段、字典、话术、规则）**——报销与报修在流程形状上同构，差异全部收敛进技能包（字段映射推演见 §8.4）。边界同样明确：流程形状真不同的业务（对话查询、审批流）不强塞通用图，走子图逃生舱（§8.5）。

## 6. 报修技能包（本期实现）

| 槽位 | 类型 | 策略 |
|---|---|---|
| 门店名称 / 报修人员 / 报修日期 | `context` | 登录人绑定门店 + 当天带出；报修人员可改（替报场景） |

钩子 3 条：类别必点选；重选类别联动照片/描述重校验；卡片路径空描述自动填「类别+详见现场照片」。

## 7. 会话草稿与退出恢复

会话即草稿：Checkpointer 每节点自动存档；重进统一 `POST /sessions` 复用活跃会话（`rp:active:{uid}` 索引，不依赖前端本地）；主动退出三选项（继续 / keep 7 天 / abandon）。细则：[实现细节/会话管理与草稿恢复.md](./实现细节/会话管理与草稿恢复.md)。

## 8. 业务接入的思考与设计点

### 8.1 分层：core 一次建设，技能包逐业务接入

| 层 | 内容 | 变化频率 |
|---|---|---|
| **core（业务无关）** | 会话 API/SSE · 通用采集图 · 槽位议程 · 槽位类型系统 · 防幻觉闸 · 话术模板引擎 · 工具设施（ToolProvider） · 检查点 · 埋点 | 基本不动 |
| **skill（业务技能包）** | 报修包 `repair`（后续：报销 `expense` …） | 每个新业务一个包 |
| **api** | `/agent/{skill}/v1/**`，按技能包自动挂路由 | 不动 |

### 8.2 技能包契约（五件套）

字段 schema（类型/必填/字典源/校验/联动）+ 字典源 + 话术模板 + 工具 + 钩子。**业务差异全部收敛为数据与配置，不含流程代码**；URL 前缀即技能包（`/agent/repair/v1`、报销届时 `/agent/expense/v1` 独立升版）。

### 8.3 槽位类型系统（通用性的落点）

| 类型 | 采集策略 | 卡片形态 | 报修用例 | 后续业务用例（报销推演） |
|---|---|---|---|---|
| `context` 带出 | 工具带出不问 | 状态条 | 门店/报修人/日期 | 申请编号 / 大区等只读项 |
| `enum` 枚举 | LLM 给 Top3 → 必须点选 | 单选卡 | 报修类别 · 期望上门 · 影响营业 | 费用项目 / 付款公司 / 是否有发票 |
| `tree` 树筛选 | 名字 → 树匹配 Top3 路径 → 点选 | 路径确认卡 | — | 所在部门 / 一级部门 |
| `text` / `money` / `date` | LLM 抽取整理 / 格式校验 | 文本 / 键盘卡 | 故障描述 | 付款事由 / 费用金额 / 起止时间 |
| `media` 附件 | 上传 + 清单规则校验 | 拍照引导卡 | 现场照片 | 发票影像 |
| `subgroup` 字段组 / `subtable` 子表 | 逐项或整组确认 / 行卡片 | 组卡 / 行卡列表 | — | 收款人四件套 / 费用明细多行 |
| `computed` 计算 | 程序算，不问不抽 | 确认单展示 | — | 期间天数 / 大写金额 |

### 8.4 接入推演的验证结论

用真实报销表单（24 字段：只读 13 + 采集 11，含部门树、动态子表、收款人四件套）做过全字段映射推演：全部字段落入既有类型，**最难的三个字段由三个新机制承接**（树→路径确认卡、子表→行卡片+一句话抽多行、四件套→记忆工具预填），引擎与流程零改动——推演详见 [实现细节/技能包实例-报修.md](./实现细节/技能包实例-报修.md) §二（报销技能包待业务访谈后定稿立项）。

### 8.5 新业务接入 SOP 与形态取舍

接入五步：字段清单标类型（0.5 人天）→ 字典/树接口对接（1）→ 话术+卡片（0.5~1）→ 提交工具+幂等（1）→ 剧本联调（1~1.5）≈ **4~5 人天，零流程代码**。
形态取舍：以通用图 + 声明式技能包为主；某业务流程真长成图（查询智能体、审批流）时，允许该技能包挂自定义子图，框架不拦——即"简单业务零代码、复杂业务有逃生舱"。

### 8.6 多智能体演进

技能包即未来子 Agent 的技能定义；查询闭环（报修/报销智能体）= 新增技能包；统一调度用 LangGraph supervisor，同一条技术栈到终态无二次迁移。

## 11. 降级与成本

- 三级降级见 §5.7；超限不是拒绝是**换通道**（卡片向导照样交单）。
- 成本口径：**打字才调 LLM（每条消息一次联合抽取）、点选 0 调用、话术全模板化**。

**用户"聊很多"的四层控制**：

| 层 | 机制 | 效果 |
|---|---|---|
| 边界拉回 | 跑题/闲聊/注入 → 槽位零写入 + 模板拉回（每条消息最多 1 次调用）；连续 2~3 轮 → fallback | 无效输入不推进流程、不连环追问 |
| 配额硬闸 | 单会话 LLM ≤6 次；单人单天次数+token 双限额；全局日配额熔断；超限降级卡片向导（❗初始值，上线校准） | 成本有上限且不阻塞 |
| 上下文恒定 | extract 只喂 schema+槽位快照+最近 4 条消息（≈2k token）；全量消息不进 Prompt | 聊 100 条，第 100 次调用成本 ≈ 第 1 次 |
| 少聊的动机 | 点选 0 调用 · 一句话一次抽全 · text ≤500 字符 | 正常路径 2~3 次调用封顶 |
