## 3. P1 —— 应修（影响评审印象分与实施安全）

1. **门店隔离写进主方案**（现在只在解读 Q5 口头）。落点：§5 或 §3.1 加"安全与隔离"三条——身份唯一来源=网关注入 userid；**接口文档 `store_no` 参数（督导多店显式指定）必须加"服务端校验归属，非本人绑定门店直接 422"**，否则这是前端传编号绕过隔离的后门；明道云密钥不出进程。
2. **出公网依赖缺失**：部署环境是内网机房、出公网受限，而 llm网关 三家候选全是公网 API。TODO 与"开放问题"都没有"网络开通（指定模型 API 域名白名单/代理）"这一项——这是和枚举字典同级的阻塞项，评审当场就要责任人。
3. **解读 §二引用修复**：改指演进规划.md（或恢复决策表），否则评委按图索骥扑空。
4. **槽位命名统一**（§8.5 有统一表）：提示词 schema、防幻觉白名单、会话快照三处对齐，防止评审现场被问"字段到底叫什么"。
5. **接口文档 §2.5 请求表补齐**：写明"无请求参数；服务端以会话快照为准，order_key=会话 ID 由服务端派生"（当前空表会被当成没写完）。
6. **数据合规一句话**：评审大概率问"门店故障描述发给别人家模型合规吗"。备答口径见 §8.6——特别提醒：**会话快照的 `context`（门店名含编号+报修人姓名）注入 Prompt 前应剔除，只注入 slots**（提示词工程已做手机号掩码，但 context 整包注入是当前设计里真实的超发）。

## 7. 评审预演：三个未备答的必问点

**Q：领导让这次做"API 独立网关"，你的方案里怎么没有？**（chat 里你自己的疑问，评审最大概率第一问）
备答分两层——**流量网关**：本期"独立"的部分就是 Agent 服务这个独立部署单元；入口复用公司现有 Spring Cloud Gateway，Nacos 加路由零代码，response-timeout 调大即可，这已经满足"API 独立"的全部现实需要。**AI 网关**（模型路由/计费/租户）：按演进规划 P2/P3，第 2~3 个智能体业务出现时选型开源（LiteLLM/OneAPI）独立部署、不自研、不提前——本期把所有 LLM 调用收口在 LLMGateway 一个类，就是留给未来网关的接入点（换实现零改引擎）。一句话：**基建的价值在"收口+触发条件"，不在"先建网关"**。这段话建议直接进解读 Q&A 当 Q0。

**Q：只有你 1 个后端，11.16 验收现实吗？**
备答：后端 11.5 人天单人 8 个工作日排满可行（解读 Q4 已有分解），**风险在前端 3.5 人天无人承接**。两条退路当场要资源：①评审拍 1 名前端 11.5 起并行（首选）；②退而求其次，final4 原型 HTML 已实现全部交互（含确认单/草稿恢复/降级演示），把它工程化接真接口压缩到 ~3 人天由后端兼——**验收口径同步调整为"核心链路+两形态灰度开关"，动效与边缘交互后补**。

**Q：门店数据、故障描述发给外部大模型，合规吗？**
备答口径（§8.6 可直接粘贴）：只发必要字段、身份字段（门店编号/姓名/手机号）脱敏或剔除后再进 Prompt；候选厂商均为国内服务、选型时核对"数据不用于训练"条款并签数据处理协议；会话与调用日志留存期限明示。数据面走向：用户文本→模型 API（脱敏后）、照片→自有 OSS（**不经模型**，当前设计照片仅作附件不识别，这点主动讲，很加分）。

其余高频问题（为什么不用 Dify/乱输入/单账号隔离/幂等/成本/类别错了怎么办）解读 Q1/Q2/Q5~Q8 已备好，过审前把上面三个补进解读即可。

### 8.7 接口 URL 方案对比（**已定稿：`/agent/repair/v1/sessions/**`**，2026-11-05 落库）

> **定稿形态**：服务前缀 `/agent` + 业务二级 `/repair` + 版本三级 `/v1`（资源随后）。比我原推荐的 `/agent/v1/repair` 更优的一点：版本归属于业务技能包——报销将来是 `/agent/expense/v1` 自起版本，两个业务的协议演进互不牵连。已全库替换（接口文档 §0~§5、主方案 §9/§10、会话管理、03 两张泳道图）；Base URL=`https://{gateway-host}/agent/repair/v1`，网关 `/agent/**` 路由，StripPrefix 待平台组确认（接口文档 §0 已注明）。

**现状的病根**：①`/api/**`——/api 是公司网关的公共命名空间根，新服务直接占根等于宣称拥有全局 API 顶层，网关没法按前缀区分服务，任何服务再叫 `/api/sessions` 就撞名；②`sessions` 无业务身份——报修会话与将来的报销会话是不同资源，URL 分不出来（存储层已有 `rp:`/`ex:` 前缀，URL 层反而没有）；③无版本号——消息 type 协议已多轮变更（6 种/10 种、ver 增删），没有 /v1 下次改协议只能改语义。

| 候选 | 形态（以发消息为例） | 一级身份 | 优 | 劣 |
|---|---|---|---|---|
| 一 · 业务命名空间 | `/api/v1/repair/sessions/{id}/messages` | 业务 | 未来某业务拆独立服务 URL 不动；网关按业务分流直观 | 占用 /api/v1 全局版本池，需公司层面认领分配规则；服务身份不进 URL，监控限流按服务聚合不便 |
| **二 · 服务前缀+业务二级（推荐）** | `/agent/v1/repair/sessions/{id}/messages` | 服务 | 网关一条 `/agent/**` 路由搞定；日志/限流/监控按服务维度天然聚合；业务二级与技能包、`rp:`/`ex:` 存储前缀、埋点维度一一对应；未来按业务二次分流（`/agent/v1/repair/**` 单独路由）留了位；不占 /api 全局根 | URL 稍长；"agent" 是实现词汇（接口消费方是自家前端，可接受） |
| 三 · 最小降调 | `/agent-api/v1/sessions`，业务放 body：`{"skill":"repair"}` | 服务（弱） | 改动最小、URL 最短 | 业务藏在 body：网关日志/权限/埋点按业务切分不便；skill 参数会演变成隐式路由器，多业务一来还得升级进路径——过渡形态 |

**推荐候选二**，理由浓缩：服务身份进 URL（新服务在网关里的门牌号）、业务身份进二级（直接映射 FA §十 的报销/多智能体规划）、/v1 给协议版本（type 表变更史证明需要）。

**三个执行注意**：①服务名一次定死别再改（agent / ai / assistant 三选一，建议 agent 最直白）；②定 StripPrefix——网关剥前缀转发还是服务感知全路径，接口文档 §0 Base URL 要写清（如 `https://{gateway-host}/agent/v1`）；③**优先对齐公司网关现有惯例**——若平台组已有 `/{service}/v1` 或 `/api/{service}` 的既定分配方式，跟随惯例优于新发明，此项列评审确认。定稿后接口文档 §0/§1/§2/§5 全文一次替换（报文结构不动）。
