# 门店 AI 报修技术方案评审意见

评审对象为 `design/3` 的主方案、解读、六份实现细节、四张设计图及 `chat` 中记录的关注点。需求基准为 `prd/final4` 的 FA.md、交互流程图与 HTML 原型。本次为文档审查；线上网关配置、业务接口、模型效果、供应商授权及人力均未实测。下文的样本量、时限和放量规则是建议值。

## 一、建议评审决议

**建议通过“单部署单元 + 受控状态机 + 模型联合抽取”的架构方向，有条件进入开发。现稿不足以批准生产试点，也不足以承诺 11 月 16 日交付全部范围。** 主要风险来自单明道云账号下的数据访问、建单超时后的重复派单，以及原型承诺与接口能实际表达的操作之间的差距。增加一层 Java 服务或换编排框架都不能代替这三项设计。

**值得保留的设计**有三项。快捷卡与结构化按钮不调用模型，保障低成本和可降级；任意步骤可修改、类别重选回查关联字段，适合表驱动状态机；模型适配器与工具适配器分别封装，有利于以后分别复用语言理解与业务操作。补齐边界后，没必要推翻重做。

| 评审阶段 | 决策与证据 | 谁负责 |
|---|---|---|
| 设计会当场 | 签认历史记录可见范围、MCP 是本期硬约束还是允许偏离、附件规格、哪些字段可改、何为“两周交付”。指定试点门店和各依赖负责人。 | 产品、架构负责人、业务负责人 |
| 开发前两天 | 两个测试门店通过真实登录链路，验证带照片建单和回读；确认外部键能力、真实选项 ID、单号/状态来源及旧记录接口授权方式。形成字段映射表与脱敏调用证据。 | 后端、App/平台、明道云管理员 |
| 生产试点前 | 两条报修路径、隔离、防重、未知结果核对、降级、隐私、回滚通过下文用例；值班人员能找到并处理未决单。 | QA、后端、运营 |

## 三、可直接补入主方案的交易和权限设计

**身份与范围。** 网关验证登录凭证，移除客户端自带的内部身份头并重新签发或注入受信上下文。Agent 限制可信入口，禁止公网绕过网关，按有效授权重查门店绑定。actorId 代表实际操作人；reporterName 和 contactPhone 是业务字段。设计会明确历史记录是“本店共享”还是“本店且本人创建”。FA 两处口径不同，未签认前使用较窄范围。列表在分页前加授权条件，详情和图片独立鉴权。历史单缺可验证门店字段时排除并报告覆盖率；若仅本人可见，还需可验证的创建人字段。

**提交契约。** 服务端核对有效类别、九个必填项、附件归属和确认标记，生成包含最终模板描述的十字段快照。确认卡携带 draftVersion；用户点击后提交该版本和 requestId。相同已受理请求返回已记录结果，版本过期返回 409 并重新核对。写接口不接受客户端覆盖门店、状态或正式单号。建议新增结果查询接口，已清理草稿仍能查询该次提交。

| 状态 | 服务端动作 | 用户看见什么 |
|---|---|---|
| 待确认 → 待发送 | MySQL 事务冻结快照并插入 submission，业务单元内 draftId 唯一、orderKey 唯一。修改、提交共用版本控制，冻结后拒绝继续修改；可用 MySQL 作版本及冻结的权威记录，Redis 作会话缓存。 | 已受理，可安全重复查询 |
| 待发送 → 发送中 | 一个执行者条件认领并记录发送开始；向下游传同一个外部关联键。重启后，对可能已发出的记录进入核对。 | 提交中 |
| 收到真实成功回执 | 先保存 remoteRowId、业务单号、状态与审计，再清缓存。重复确认和刷新返回同一结果。 | 正式单号与历史入口 |
| 明确拒绝且确认未建单 | 保存拒绝原因；字段问题返回对应字段，允许修订后重新确认。保留旧尝试和关联标识，重新投递前确认旧尝试已终止。 | 待修正或稍后再试 |
| 超时、断连或写回执失败 | 标记 UNKNOWN。远端保证相同键幂等时可限次重发；仅可按键查询时只查回执，单次查空不能证明没建单；没有可靠关联能力时转人工核单。 | 结果核实中，提供状态查询和客服入口，禁止切回表单对同一草稿另建一单 |

**数据与降级。** 建议把七天承诺建立在能恢复的草稿上。若维持 Redis 为唯一快照，平台须交代持久化、淘汰策略、恢复测试及可接受丢失窗口；若业务要求保存成功即能续填，用已有 MySQL 持久化有效字段与版本，Redis 仅加速。活跃索引与快照同步过期，恢复前校验归属、授权、附件、字典版本。keep 保留原步骤，abandon 使未提交附件失效并安排清理，已提交照片按工单生命周期保留。Redis 过期不会自动删除 OSS 对象。

**切回表单要明确承接方式。** 原稿把 AI 草稿与传统表单 localStorage 隔开，符合互不覆盖，却没有说明店员是否需要重填。建议显式操作“带入本次已填信息”，复用草稿身份和确认校验；若传统页已有未完成内容，先让用户选保留哪份。若本期只能保留 AI 草稿并打开空白表单，需在评审中写明体验及工作量。模型故障可以继续规则表单，明道云故障只能保存和核对，两个故障的用户承诺不同。

## 四、模型、网关与会话协议

**模型选型按业务样本定。** 固定真实类别字典和一批标注话术，用同一提示词、相同输入输出上限比较获准接入的候选模型。记录 Top3 命中、应拒识时回退率、关键事实忠实度、结构解析失败率、P95 时延和每份成功单费用。任何候选未通过数据使用范围、安全或关键事实门槛即淘汰；在通过者中选时延与费用合适者。保留模型版本、提示词版本、字段契约及字典版本。暂不要求双供应商。

**一处模型调用点，不等于一张单只调用一次。** 每次打字修改、格式修复及传输重试都可能产生计费尝试。《llm网关》先示例 structured_output 再用 invoke + json.loads，代码只记录成功路径，INCR 未示例 TTL。建议统一一条异步调用路径，锁定依赖版本，用真端点验证结构化支持、usage 缺失和异常映射。由一层统一控制重试与总截止时间，明确“每会话最多 6 次”统计实际外发尝试，原子预占并设置有效期。8 秒单次超时叠加重试可能让店员等超过 16 秒；达到单轮预算即退点选，记录超时、解析失败和已消费费用。监测延迟与失败率，提供按门店或全局关 AI 的开关。

**输出验证落实到字段。** JSON 合法只证明可解析。《防幻觉》示例允许通用 dict，直接取候选的 name，缺键或不合法类型仍会出错。候选、字段变更、意图分别设强类型，拒绝未知字段并限制数组长度。用户原文与系统指令按角色分开；三引号仅用于排版。模型拿不到工具凭据与执行权限。状态机据“当前状态 × 允许事件 × 可编辑字段”执行；impact 的推断和用户点选确认分开保存。对数字、时间、否定词和新原因保留原文证据，无法支持时保留原文供编辑。界面以文本渲染用户与模型内容。

**两个容易漏测的交互。** ① 已到 PHOTO，再说“电话换成……”，即使类别候选为空，也只处理电话修改，不能跌回全量选类别；只有请求分类时才消费候选。② 快捷卡写“冷柜/空调”，但真实字典可能区分两条派单队列；一张卡只能绑定一个已核准且启用的选项 ID。若不能统一派单，拆卡或先选设备。旧草稿遇停用选项应重选，其余已确认内容保留，只有系统生成的模板描述随类别更新。

**网关裁决。** 现有网关负责 App 入站认证、路由和入口流控；应用内 LLMGateway 负责模型出站的凭据、超时、预算和观测。二者故障影响和扩容依据不同。建议本期优先采用现网独立路由、独立配额和开关，由平台组提供路由测试记录。若领导要求物理独立入口，明确是网络隔离、独立值守还是容量隔离，再估证书、认证联通、配置发布、告警与值班成本。仅复制网关无法自动产生这些能力。首期权限、并发上限必须有人实现，可以在当前部署中完成，不依赖将来增加 Java 层。

**SSE 取舍。** 当前没有逐 token 输出，最小可交付协议可以是 POST 同步 JSON + 客户端输入中状态；若保留 SSE，约定仅 messages 流式、建会话与提交返回 JSON。App WebView 实测带授权的 POST 流读取、代理缓冲、断连和切后台。每个动作带 actionId/expectedVersion，返回新版本；断线后先按 session 获取权威快照，只重试同一动作。事件 seq 表示会话内顺序，GET 返回快照与最近渲染结果即可；若承诺完整重放，要保存带 seq 的消息。已经发完 HTTP 200/typing 后遇错，用流内 error + done；握手前失败返回 JSON 错误体。接口须补明道云超时、未知提交、附件超限和版本冲突的前端动作。

## 五、两周范围、工期和上线证据

主文标注 11 月 5 日到 16 日。按 2026 年周一至周五计，**两端含首尾共 8 个工作日**。解读给出的后端 11.5 人天、前端 3.5 人天即使总计 15，人力也不能简单相加：1 名后端在此窗口只有 8 个工作日，缺口至少 3.5 后端人天，尚未计评审整改、联调等待、QA 和返工。建议评审人择一：增加能独立负责模型适配/评测或明道云适配的后端并明确 QA；或者保留原人力，将 11 月 16 日定义为集成候验，试点另定。下表是补足人手后的目标，不是已经完成的计划。

| 恢复 | 模拟杀 App、SSE 断线、Redis 重启、草稿第七天边界、OSS 链接过期、重复 upload_done；模型端关闭。 | 已保存字段与有效附件可恢复；过期附件不计入提交；明道云可用时无模型仍可完成报修。 |
| AI 质量 | 建议 60 条可归类、20 条应回退、20 条含否定/注入/越权样本，另加 20 组多轮修改；调参与验收分集。 | 建议起点为 Top3 ≥54/60、正确回退 ≥18/20；样例中新增关键数字/原因、越权写入、未经点选锁类均为 0。在线首推一致率单列，不当人工标注准确率。 |
| 容量与运维 | 按试点忙时输入、列表刷新、上传、建单混合压测并留峰值余量；模拟单账号 429、模型超时和实例滚动重启。 | 记录并发、峰值 QPS、P95、超时率和恢复时间；上传/查询拥塞不能耗尽所有建单资源。上线前按实测签 SLO，保留服务端限并发、排队超时与停写开关。 |

## 六、成本、放量与基建复用

《解读》以每日 100 单、每单 1.5 次、每次 1–2 千 token 估算。按 30 天，仅能推出 **4,500 次逻辑调用、约 450 万到 900 万总 token**；模型、输入输出占比和成交单价未定，推不出“月成本百元级”。失败会话、重试和试用未提交也可能计费。

- **月模型费**按各模型的输入和输出 token 分别乘对应单价求和，计量单位统一到每百万 token。每张 AI 成功单成本以同期全部 AI 花费除以 AI 渠道成功单数。另列对象存储、网络、服务实例、人工核单；账号节省按确实能取消的席位核算，并由管理员确认共享账号的授权用途。
- **最小看板**按门店灰度批次看入口曝光、AI 会话、两路径占比、最终提交渠道、成功单、转表单、保存后七天内续填、记录页使用次数；看模型和明道云各自的失败率、P95、核实中数量/最老等待时间。用匿名会话与提交 ID 去重，埋点禁存电话、原文和可下载的附件 URL。首推与最终选择比较应关联最终确认版本，不能只记首次点选。
- **灰度与回滚**先选固定少量门店走形态一，逐单对账；拿同类门店或旧表单同期数据比较时长、放弃率与一次提交成功率。指标达到双方商定阈值后扩店，AI 首屏独立开关。出现泄露立即停相关读接口，出现重复派单停新写并核单，模型异常只关 AI；保留未决单查询与对账能力。值班手册写明谁操作开关、谁看台账、谁通知门店以及恢复条件。
- **复用的判据**是报销接入时能复用认证上下文、模型适配、版本化草稿、确认提交、埋点评测，而新增报销专属规则。票据、明细行、金额校验和审批分别设计。第二个消费者需要同一工具时再评估独立部署；跨业务模型配额、密钥轮换或发布互相影响时再拆模型网关。对话查单先做只读、再考虑跨业务动作。把“零改动、约 1 人天封顶”改成兼容性验收和独立估算。
