**A. 纯 LLM 自主对话（ReAct）—— 补充否决理由**

你现有的（流程临时决策、编枚举、成本）之外：

1. ★ **安全通道问题**：function calling 意味着把 `create_repair_order`（写明道云）的调用权交给模型——“模型自主触发提交”这条路就存在。FA 原则是“点确认才入库”，要堵死它就得在工具外面包一层审批拦截，那等于又造了个状态机，只是绕了一圈。
2. ★ **可测试性**：ReAct 同一输入可能走不同路径，没法写表驱动单测，回归测试必须跑真模型——又贵又不可重复；状态机是纯代码，转移表可穷举，CI 秒级跑完。两周工期里“改一处敢不敢发版”靠的就是这个。
3. **模型漂移隔离**：状态机方案里模型只影响“抽取质量”，不影响“流程正确性”——换模型/模型升级时风险面小一个量级；ReAct 把模型放在流程关键路径上，换型=全量行为回归。
4. **会话恢复的形状不对**：ReAct 恢复要把整段历史塞回去让模型“想起自己在哪”，上下文越长越不可控；状态机恢复=读一个 JSON 快照，零调用。
5. **排障成本**：生产事故要回答“它为什么问了这句”，ReAct 只能翻模型日志推理；状态机查转移表，一分钟定位。

**B. 纯 Runnable 线性串联 —— 补充否决理由**

1. ★ **状态被塞进 prompt = 把状态机的职责转嫁给模型**：全历史让模型自己读，读漏了就跳步——约束1 的风险从架构上又回来了，而且 token 随轮次线性膨胀。
2. ★ **入口形状不匹配**：我们不是“一次输入一次输出”，是事件驱动——点选/上传/打字/退出六种手势从不同入口进来；RunnableSequence 单入口管道根本接不住，接得住的时候它就不是 Runnable 了。
3. **断点恢复没有挂点**：链是一次 invoke 跑到底的批处理形状，“先存再推、7 天草稿”这些会话级持久化没有地方下手；硬做要把链拆段手工管进度——那就是手写状态机，只是没承认。
4. ★ **它没被否决，是被降级吸收**：联合抽取模块内部就是一条 Runnable（prompt | llm | parser）——B 的合理形态已经作为组件活在 C 里。这句话评审时讲出来很加分：说明不是不会用，是放对了位置。

**C. 状态机 + LangChain —— 补充采纳理由**

你现有的（可控、支持中途修改/断点恢复）之外：

1. ★ **埋点天然齐**：状态号+事件就是现成的指标维度——FA 八项指标里“填报时长/步数/卡壳点”在 ReAct 里根本没法定义（没有稳定的“步骤”概念），状态机的状态轨迹直接算出来。
2. ★ **降级是同一台状态机的另一套消息**：FALLBACK/卡片向导=不调 LLM 的转移分支，一套代码两种模式——“AI 挂了不耽误报修”能成立，结构性原因就在这；其他架构里降级要另做一套流程。
3. **与产品剧本同构**：FA 的剧本就是固定顺序问答，状态机是产品文档的直接翻译——图=剧本，评审一讲就通；将来改需求=改表，产品和技术说同一种语言。
4. **团队风险对冲**：状态机是所有后端都会的朴素模式（查表+转移），零框架学习曲线；LangChain 只用最薄一层（一次 ChatOpenAI 调用+结构化输出），框架升级影响面被压到最小。1 人项目，这两条是实打实的交付保险。
5. **水平扩展无状态障碍**：会话=独立快照 Key，无全局状态，加副本就扩——不需要框架级 Checkpointer。

**D. LangGraph —— 补充推迟理由**

1. ★ **逐项对位“它解决的问题我们已有更便宜的解”**：断点=Redis 快照、人审=确认单、条件分支=转移表——LangGraph 三大卖点在本期各有等价物，且都更简单。这个论证方式（不是不会用，是不需要）比“吃不到红利”更硬。
2. **版本风险**：LangGraph/LangChain 正处于 API 演进期，锁版本+踩框架坑的隐性成本在两周关键路径上不可预算；朴素状态机零外部依赖。
3. **调试成本**：流程跑偏要在图运行时/channel 写入里打断点，比自己查转移表贵——可维护性不只是写的时候，是三个月后半夜排障的时候。
4. **反着说也有力**：等真到多 Agent/查询智能体阶段再引入，那时买到的是成熟稳定的终态框架，学习投资更值——现在上 D，将来流程简化还要把图拆回来。

**E. Dify —— 补充否决理由**

1. ★ **网络与部署一票否决的前提**：内网机房出公网受限，SaaS 版连“通”都做不到；私有化=向量库/pg/redis/sandbox/worker 一整套 Docker Compose，1 人两周背不动它的运维和升级。
2. ★ **数据主权**：“会话即草稿”（rp:active 索引、先存再推、TTL 滑动）是业务核心逻辑，落进平台内部存储=关键业务数据在别人家的 schema 里，对账、迁移、审计、180 天留存策略全都失控。
3. **幂等工具别扭**：order_key 幂等+待发表重试+门店归属过滤是带状态的工具逻辑，塞进平台的 HTTP 节点非常难看；这些恰恰是不能错的代码。
4. **测试盲区**：防幻觉八道闸里的闸2~6（schema/白名单/sanitize）要以外部代码挂进平台节点之间——平台变成“必须绕过它才能保证质量”的东西。
5. **协议适配成本**：typing→message→done 的自定义 SSE 事件流、六种用户手势、确认单组件——平台对话流里没有对应物，前后端要双层映射。
6. 留用场景重申（把“否决”说成“放对位置”）：RAG 知识库问答（维修手册、SOP）是它的甜点，以后真有这需求直接用。

**F. Coze —— 补充否决理由**

1. **SaaS 数据出域是合规一票否决**：门店编号、人员姓名、故障描述出境，不用讨论技术。
2. **私有化 Studio 同样重，且组件面向 C 端 bot 生态**（插件商店、发布渠道、IM 卡片）——企业内网 API-first 集成场景利用率低，装了一堆用不上的东西。
3. **卡片组件面向它自家 IM 生态**，和我们 H5 深度自定义协议的距离比 Dify 还远。
4. **平台治理成本**：空间/账号/权限归属、DSL 版本随平台变动——企业使用的管理成本常被低估。
