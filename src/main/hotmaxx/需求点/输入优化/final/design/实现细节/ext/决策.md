## 〇、我们讨论中真实问过的问题（口语版）

**Q0-1 State 放了会话内容，怎么防止无限膨胀？**
窗口 + 入库 + 裁剪三件套：State.messages 只保留**最近 10 轮**，每轮结束时本轮消息先批量入库（一条 multi-row SQL）再裁剪——被裁掉的必已入库（写入顺序钉死）。另外两层边界：消息**不进 Prompt**（extract 只拿槽位快照+最近几条，聊多少条 LLM 成本不变——膨胀不影响成本，只影响存储）；会话有终态+TTL（提交/过期即删检查点，活跃数据不堆积）。量级：剧本 A 全程 13 条 ≈ 4KB。（详见 State设计.md 决策 9）

**Q0-2 会话内容怎么恢复？（用户退出去再回来）**
两源拼接，前端无感：重进 `POST /sessions` → 查活跃索引 `rp:active:{uid}` 命中会话 → `get_state` 拿槽位+议程+焦点+**窗口尾巴**（最近 10 轮）→ MySQL 查更早的全部消息（按 seq）→ 拼接下发 + 按焦点渲染当前步骤。keep 7 天内回来=完整复原；**TTL 过期后回来**=草稿按设计失效开新会话，但消息在库永久可查。复原顺带对账：DB 的 max(seq) 落后于窗口就现场补写。（会话管理与草稿恢复.md §四）

**Q0-3 为什么同步写入数据库？不同步的话有什么问题？**
选**同步单轮批量**（一轮 3~5 条消息合成一条 SQL）：行为好推理、试点流量毫无压力、规则少。**不同步（异步批量）的问题**：存在"未落库窗口"——进程崩了，内存队列里的消息就没了；要零丢失必须配三个机制：裁剪同步门槛（裁前必 flush）、复原对账、每日对账——机制不复杂，但多三个必须永远正确的点，一期不值得背。窗口天然是缓冲区（落后上限=窗口容量），所以异步版留着当放量后的演进项，届时切换是纯内部替换，接口和复原逻辑不动。（State设计.md 决策 9 演进项）

**Q0-4 State 为什么这么设计？**
六条核心：①**单一事实来源**——填到哪了只在 State，不在前端不在 LLM 上下文；②**可序列化、最小完备**——检查点机制的前提，往里加字段的门槛只有一条"恢复需不需要"；③**槽位只存定稿事实**，候选住消息里（防幻觉）；④**agenda 派生但显式存**——钩子副作用要有载体，"问什么"由此从代码变成数据；⑤**控制与业务分离**（meta vs slots）；⑥**消息窗口化**（Q0-1）。每条的设计理由在 State设计.md §四，共 11 条决策。（结构全表见同文档 §一）

**Q0-5 通用采集图为什么这么设计？**
产品约束倒推：六个硬约束（不跳步/类别不能错/随时改/断点续填/挂了不误事/有边界）逐条映射到图机制——议程驱动、候选不入槽、原地覆盖、每节点存档、fallback 一等节点、意图枚举+失败计数，没有为技术而技术的设计。节点切分三考量：单一职责、**LLM 收口在 extract 一个节点**（可算/可测/可跳过）、"问什么"不写在节点里。产出七步不变量：带出→理解→校验→路由→追问→确认→提交。（见本档 · 专题一：通用采集图设计考量）

**Q0-6 怎么考虑的，能让报销方便接入？**
一条原则：**图编排采集流程的共性（缺什么问什么、齐了确认、挂了降级），不承载业务个性（字段/字典/话术/规则）**。报销难在字段不难在流程（仍是缺什么问什么），它带来的全部新东西——6 种新槽位类型、一句话抽多行、推导钩子、收款人记忆、4 种新卡片——**全部不触碰图的节点与边**（逐项表见《实现细节/技能包设计.md》），落点是槽位类型系统/技能包 schema/消息协议增量。接入按 SOP 走 ≈4~5 人天零流程代码；流程形状真不同的业务（查询智能体）有子图逃生舱，框架不拦。已用真实报销表单做过全字段推演验证。

## 一、选型类

**Q1 为什么用 LangGraph，不自研状态机？**
一句话：编排/存档/恢复/中断/流式这些通用能力框架全有，自研等于重铺已铺好的路。
抉择与原因：自研状态机在"单业务线性流程"下成立，但目标定为搭架子后，每吃一个新能力（报销的树/子表、人机中断、断点恢复）都要往自研引擎里加东西。LangGraph 的 Checkpointer（存档恢复）、interrupt（人机确认）、条件边（转移表）全部原生。否掉的备选：纯 LLM 自主对话（跳步漏问不可控）、纯 LangChain 串联（回跳做不到）、Dify/Coze（卡片消息协议无对应物、数据出域/运维重）。

**Q2 为什么一张通用图 + 技能包，而不是每个业务一张图？**
一句话：新业务接入只写配置不写流程代码（4~5 人天 vs 8~12 人天），复杂控件（树/子表/字段组）一次建设全业务复用。
抉择与原因：所有表单填报业务的流程形状同构（带出→理解→校验→路由→追问→确认→提交七步不变量），差异只在字段集合与字段类型——把差异收敛成"技能包"（schema+字典+话术+工具+钩子）。留了逃生舱：流程形状真不同的业务（查询智能体、审批流）允许挂自定义子图，框架不拦。备选"每业务一张图"被否：能力重复建设、测试矩阵×业务数、话术口径易漂移。

**Q3 为什么 Python + FastAPI，工具层又是什么形态？**
一句话：LangGraph/LangChain 生态在 Python，这是主战场；工具层 = ToolProvider 抽象 + 进程内直调，独立服务化时换 MCP 适配器，引擎零改动。
抉择与原因：LLM 我们用得薄（每条打字消息一次调用），但编排框架的生态红利只有 Python 栈吃得全。工具层不引入 MCP 协议开销（同进程直调零损耗），但接口按 MCP 语义画——未来第二个调用方出现时再拆，届时任意语言（如 Spring Boot）重实现，协议不变。

## 二、编排与 State 类

**Q4 原来的状态机去哪了？12 个状态怎么没了？**
一句话：状态没有消失，是从"每业务 12 个代码状态"降维成"全业务一张图 + 字段议程"——"问到哪了"变成了黑板上的数据。
抉择与原因：议程（agenda）由技能包 schema 生成，答一个划一个；原 INIT=load_context 节点、CONFIRM=interrupt、FALLBACK=fallback 节点、PHOTO/EXPECT 等=议程里的槽位。业务接入零流程代码的根基就在这。

**Q5 类别为什么必须点选，AI 识别了不能直接填吗？**
一句话：AI 只提名、人定稿——枚举候选只进下发的卡片消息，不进槽位，点选才写入。
抉择与原因：选错类别会被驳回重提（产品硬约束），槽位定义为"已定稿事实"、卡片消息是"待确认提议"，两者不混——防幻觉语义干净，重放时提议与事实都能还原，AI 提名永远不可能直接入库。

**Q6 用户中途改字段，状态机要回跳吗？**
一句话：普通字段原地覆盖、议程不动（改内容≠改流程）；类别是唯一例外，钩子把照片/描述标失效塞回议程——"回跳拍照"由数据失效实现，图上没有一根往回的边。
抉择与原因：如果做真回跳，每个字段都要定义回跳目标，流程代码随字段数膨胀；数据失效让"重问"自然发生（议程里有了就问），通用图零改动。

**Q7 State 里为什么要存会话内容（messages）？**
一句话：State 是框架唯一自动原子持久化的容器——消息与槽位变更在同一个检查点版本里，重放看到的永远是同一瞬间的完整现场。
抉择与原因：否掉的备选都有明确硬伤——单独 Redis List（两套存储无事务，崩溃产生"消息在、状态没跟上"）、前端持有（换设备/清缓存就丢，违反恢复不依赖前端）、只落 MySQL（活跃重放多一跳）、BaseStore（为跨会话记忆设计，无版本链）。消息分两段安放：**窗口在 State 保一致性，全量在 MySQL 保持久**（见 Q8）。

**Q8 会话内容为什么只留 10 轮窗口、每轮批量入库？**
一句话：State 恒有界（不赌"会话天然短"），消息即时持久（abandon/崩溃的会话记录也在库），审计零缺口。
抉择与原因：四条规则钉死正确性——①先入库再改 State（被裁掉的必已入库）；②(session_id, seq) 唯一键 + upsert 后写覆盖（崩溃在两写之间时，中断轮次重执行重发同 seq 消息，upsert 自愈，不靠事务）；③裁剪只在轮末；④seq 用 meta.seq_counter（裁剪后 messages.length 不可再用）。落库方式选了**同步单轮批量**（一轮一条 multi-row SQL）而非异步：简单、行为好推理；异步版（进程内写器攒批 + 裁剪同步门槛 + 复原/每日对账——窗口天然是缓冲区）列为放量后的演进项。终态归档因此简化成只写会话摘要一行。

**Q9 断点续填、确认单挂起是怎么实现的？**
一句话：Checkpointer 每个节点执行完自动把整个 State 落 Redis（"先存再推"的原生版）；confirm 节点 interrupt() 挂起（挂起状态也存档），POST /submit = Command(resume) 从该检查点续跑。
抉择与原因：自研这两样 ≈2.5 人天且有"忘了存"的窗口；框架版零存档代码、粒度到每步、还送时间旅行调试。

**Q10 恢复为什么不依赖前端存的 session_id？**
一句话：重进统一 POST /sessions，服务端按活跃索引 rp:active:{uid} 找到会话复用——换设备、清缓存都能续。
抉择与原因：前端 localStorage 只作加速（刷新/断线重连），恢复链路不能押在前端状态上。TTL 过期后回来：草稿按设计失效开新会话，但消息在库永久可查。

## 三、成本与降级类

**Q11 用户一直聊怎么办？成本可控吗？**
一句话：四层控制——边界拉回（跑题槽位零写入、每条消息最多 1 次 LLM）、配额硬闸（单会话 ≤6 次 + 单人单天次数/token + 全局日配额，超限降级不是拒绝）、上下文恒定（extract 只喂 schema+槽位快照+最近几条，全量消息不进 Prompt）、点选 0 调用。
抉择与原因：最坏结局是用户多点几张卡（fallback 向导照样交单），不存在聊崩成本。存储增长也 有界：窗口 + 入库 + TTL + 终态删除。

**Q12 AI 挂了会不会耽误报修？**
一句话：不会——LLM 失败/配额超限/连续识别失败/引擎运行时异常走同一个出口：fallback 卡片向导（0 LLM）→ 实在不行引导回传统表单，填报永远有路。
抉择与原因：降级被设计成图上的一等节点而不是异常分支——它有测试、有埋点、有话术，不是 try/except 里的一行日志。

**Q13 为什么话术不让 LLM 说，全用模板？**
一句话：口径统一可运营、零成本、零翻车——LLM 只干"听懂"这一件它不可替代的事。
抉择与原因：追问/拉回/报错的话术是产品资产（改文案不走发版），LLM 生成会有语气漂移和幻觉风险；点选路径全程 0 LLM 就是这套纪律的红利。

## 四、业务接入与演进类

**Q14 报销为什么不本期做？架构上准备好了吗？**
一句话：报销的**业务规则还没摸清**（欠票/审批/驳回规则待访谈），贸然实现容易做错单；架构上已用真实表单做过全字段推演——24 个字段落入既有槽位类型，最难的三个（部门树/子表/收款人四件套）都有承接机制且不碰图的节点与边。
抉择与原因：推演证明架子装得下复杂业务（评审点），实施等业务访谈后按接入 SOP 走（4~5 人天）。这期先跑通报修端到端。

**Q15 收款人记忆为什么做成工具而不是引擎直读写？**
一句话：和业务工具走同一条 ToolProvider 路径——同等的可测试、可限流、可审计；未来工具层独立服务化/多 Agent 共享时，记忆天然跟着走。
抉择与原因：框架的 BaseStore 可以直读写，但那会让引擎背包（多一条隐式 I/O 路径）；工具化把记忆变成普通能力，报销接入时直接注册。本期不实现，预留设计。

**Q16 语音输入好加吗？**
一句话：好加——语音进来就是一条 text 消息，引擎零改动；活全在输入端（App JSBridge + ASR SDK + 识别文本回填输入框让用户改完再发），≈3 人天。
抉择与原因：ASR 错字的爆炸半径被槽位系统框住（类别/树匹配不上就落点选卡，不会错入库）；字典可导出成热词表提升识别率。不进本期 MVP。

**Q17 多 Agent 终态怎么走？现在的设计会不会白做？**
一句话：不会——技能包就是未来子 Agent 的技能定义，查询闭环=新增技能包，supervisor 统一调度用 LangGraph 原生方案，同一条技术栈到终态无二次迁移。
抉择与原因：这正是当初选 LangGraph 的理由之一（多 Agent 是它的主场）。

## 五、专题 · 通用采集图设计考量（图为什么这样设计，为什么能支撑后续业务）

**（1）产品约束倒推**——图的每个机制都对应一条产品硬约束，没有为技术而技术的设计：

| 产品约束 | 图上的落点 |
|---|---|
| 流程可控、不跳步不漏问 | 议程驱动：route 只认 agenda，答完一项才放下一项；必填不齐进不了 confirm |
| 类别绝不能选错 | extract 只产候选（进卡片消息不进槽位）+ update 白名单过滤 + 必须点选定稿 |
| 任意字段随时可改 | 任意时刻打字 → extract 识别改字段意图 → 槽位原地覆盖、议程不变 |
| 填一半退出能续填 | Checkpointer 每个节点后自动存档；interrupt 挂起状态也存档 |
| AI 挂了不误事 | fallback 是图上的一等节点（不是异常分支）：0 LLM 向导走完全程 |
| 对话有边界 | 意图六类枚举 + 字段白名单 + 连续失败计数 → fallback |

**（2）节点切分的考量**：每节点单一职责（单测矩阵最小）；**LLM 收口在 extract 一个节点**——成本可算、可 Mock 测试、可整体跳过（跳过即降级路径）；"问什么"不写在任何节点里——ask 只按议程首项 + 槽位类型下发。由此得到采集类业务的**七步不变量**：带出 → 理解 → 校验 → 路由 → 追问 → 确认 → 提交——它对任何表单填报业务成立，这是"一张图跑所有业务"的依据。

**（3）为什么能支撑报销**——报销难在字段不难在流程（仍是"缺什么问什么→确认→提交"），其全部新增（6 种新槽位类型、一句话抽多行、推导钩子、记忆、4 种新卡片）**均不触碰图的节点与边**，逐项落点表见《实现细节/技能包设计.md》。一句话：图编排采集共性、不载业务个性；流程形状真不同的业务走子图逃生舱（实现细节/技能包设计.md）。

## 六、专题 · State 设计决策（10 条）

**1. 单一事实来源。** 字段填到哪了，真相只在 State——不在对话历史、不在前端、不在 LLM 的上下文里。换来的三件事：断线/退出恢复只需读 State 重放；喂给 extract 的是槽位快照而非聊天记录（上下文成本恒定）；审计时一处可查全部。

**2. 可序列化、最小完备——这是检查点机制的前提。** State 必须 整体转 JSON 落 Redis，因此：只放数据不放对象（照片存 media_id 引用，本体在 OSS）；只放"恢复现场需要"的字段，过程性中间产物（LLM 原始返回，抽取完即丢）不进——黑板永远最小，检查点体积可控。**往 State 加字段的门槛就一条：恢复时需不需要它。**

**3. 槽位只存"定稿事实"，候选住在消息里。** extract 产出的类别 Top3 不写 `slots.category`，只进下发的 `enum_card` 消息——槽位为空直到用户点选。理由：槽位是"已确认的事实"、卡片消息是"待确认的提议"，两者不混，防幻觉语义干净（AI 提名永远不入库）；重放时提议与事实都能还原。

**4. agenda 是派生数据，但显式存储。** 理论上 agenda 可由 schema 必填减 slots 已填实时算出；选择存下来，是因为它要承载**钩子的副作用**——重选类别把照片/描述"塞回议程"这种动作需要一个明确载体，实时计算无处落副作用。"问什么"由此从流程代码降维成数据（业务接入零流程代码的根基）。

**5. focus 是议程的影子。** 恒等于 `agenda[0]`，单独存是为了对外输出（`done.focus` / GET 返回）零计算；一致性由"agenda 变则 focus 同步变"的唯一写入点保证。

**6. 每个槽位值带 source 三值。** system_default / ai_filled / user_edited 不只是审计留痕：确认单上"AI 识别"角标、field_edit 埋点（AI 预填质量）、争议追溯（这个值是谁写的）都取自它。

**7. messages 只追加、永不进 Prompt。** append-only 保证重放/审计的不可篡改；"全量消息不进 Prompt、extract 只拿快照+最近几条"是成本恒定的根基——聊一百条，第一百次调用的输入和第一次几乎一样。

**8. 控制信息与业务数据分离。** branch/mode/fail_count/llm_calls/confirm_pending 这些"引擎怎么运转"的信号全部收在 meta，不与 slots 混放——业务规则读 slots，引擎逻辑读 meta，互不污染，后续技能包复用 slots 结构时也不用关心 meta。

**9. 消息持久化：State 放滑动窗口（最近 10 轮），全量每轮批量入库 MySQL。** State.messages 不承担全量留存——每轮结束时，本轮消息（用户 + 服务端卡片）**同步批量 upsert** 进 MySQL 消息表（一条 multi-row SQL），然后才裁剪窗口（保留最近 10 轮）。四条实现规则：① 写入顺序 = 先入库再改 State（含裁剪）——保证被裁掉的必已入库；② 消息表 (session_id, seq) 唯一键 + **upsert 后写覆盖**——崩溃在两写之间时，中断轮次重执行会重发同 seq 消息，upsert 自愈，不靠事务；③ 裁剪只在轮末做（本轮消息完整入窗，下轮才可能被裁）；④ seq 由 meta.seq_counter 生成（窗口裁剪后 messages.length 不可再用）。由此：State 恒有界（不依赖会话天然短的假设）、消息即时持久（abandon/崩溃的会话记录也在库）、审计零缺口。演进项（放量后）：改异步批量——轮末只投进程内写器（攒批 flush），配**裁剪同步门槛**（裁前必 flush）+ **复原/每日对账**（DB max(seq) 对比窗口最早 seq，落后就补）——窗口天然是缓冲区，落后上限=窗口容量，零丢失。
**10. 会话内容为什么放在 State 里（而不是单独存）。** 消息必须持久化、必须能随会话恢复——而 LangGraph 中唯一被框架自动原子持久化的容器就是 State。放进去白得四样东西：每步自动存档（零保存代码）、**消息与槽位变更同版本**（重放 / 时间旅行看到的永远是同一瞬间的完整现场，不会出现"消息在了、状态没跟上"的裂缝）、`add_messages` 按 ID 幂等合并、interrupt 挂起时对话现场随快照同存。备选方案均评估过：

| 备选 | 做法 | 为什么不选 |
|---|---|---|
| 消息单独存（Redis List `msg:{sid}`） | State 只存槽位，消息独立 Key | 两套存储无事务：崩溃窗口产生不一致；重放要自己对齐版本；seq 生成 / 清理 / 归档全部自写——等于把"先存再推"的活拿回一半 |
| 前端持有消息，服务端不存 | 断线靠前端本地恢复 | 违反"恢复不依赖前端本地"：换设备 / 清缓存重进无法还原，审计缺失 |
| 消息只落 MySQL，State 留最近 N 条 | 活跃会话重放查库 | 活跃路径多一跳 DB 依赖；未终态会话在 Redis 无完整重放材料；归档需合并去重——超长会话才值得 |
| 外挂 BaseStore 存消息 | 跨会话 KV | 为"按人长期记忆"设计，无版本链无 reducer，等于自管 |

边界：消息独立存储只在两种需求出现时才值得重开——千条级长会话（分页重放已预留）、消息需被第三方独立消费（质检 / 搜索流）。届时把 messages 拆到独立存储、State 只留游标即可，接口层（seq 分页）不用动。

> **决策 9 与 10 的关系**：消息的「窗口部分」在 State 里（与槽位同版本原子写，保重放一致性——决策 10 成立）；「全量持久」由每轮批量入库承担（幂等 upsert 自愈——决策 9）。上表否决的是「窗口外消息只存 Redis 独立 Key」的形态，不否决入库本身。

## 七、快答区（一句话带过）

- **为什么槽位值带 source？** 审计（值是谁写的）+ 确认单"AI 识别"角标 + field_edit 埋点（AI 预填质量）。
- **为什么归档存 JSON 不建范式化表？** 归档即快照——冷数据不做字段级建模，要分析再 ETL，避免两处结构漂移。
- **为什么接口 URL 带 /repair/v1？** 版本归属技能包：报销独立升版（/agent/expense/v1），互不拖累。
- **POC 三个验证是什么？** Checkpointer TTL、interrupt↔SSE、流式事件——都有降级路径，任一不过不回头。
- **为什么不做置信度？** 识别成功一律 Top3 卡首位预选必须点选；识别失败降级全量点选——用交互解决判别问题，不引入一个说不清阈值的数字。
