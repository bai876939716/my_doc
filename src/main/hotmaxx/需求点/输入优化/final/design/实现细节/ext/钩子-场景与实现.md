## 一、30 秒版（背这个）

钩子 = **技能包贴在字段上的规则标签**；引擎走到固定时机（候选产出时 / 值被改时 / 进确认前 / 提交前）逐个查标签、执行对应动作。引擎认识标签**类型**（MustPick 意味着拦、OnChange 意味着作废），但不知道具体业务挂了**哪些**标签——报修挂三条、报销到时候挂几条，运行时查表才知道。

为什么这么设计：如果把"类别必须点选"写死在引擎里，就是 `if 业务==报修 and 字段==类别: ...`，报销来了再加一行 if，引擎被业务淹没。钩子把这行 if 倒过来：**引擎只写"谁声明了 X 我就做 Y"，业务在填空**。这就是"业务接入零流程代码"的具体落点。

## 二、四个钩子逐个跑给你看

### ① MustPick —— 挂在类别上，时机"候选产出时"

**声明**（slots.py，纯标签不带逻辑）：

```python
Slot(name="category", type=ENUM, ..., hooks=[MustPick(), ...])
```

**没有它会出的事**：AI 听完"冷柜不制冷"直接把类别写进表单——万一听岔（店员说冷柜、AI 填了照明），错值没经人手就生效，选错类别=驳回重提。

**跑起来的样子**：

```
店员打字「冷柜不制冷了」
  AI 返回候选：[制冷设备/冷柜, 暖通/空调, 特别紧急]
  引擎正要把「制冷设备/冷柜」写进类别栏
    ↓ 查声明表：category 挂了 MustPick
  改主意：不写栏，改发一张点选卡（AI 推荐的排第一）
  店员点了一下 → 现在才写进类别栏
```

一句话：在"AI 说出答案"和"表单生效"之间**插一道门**——AI 的答案只能变成按钮给人看，人点了才放行。注意它拦的是"未经确认就入库"，不拦打字（用户嘴说类别，AI 听懂后只是把卡片排得更准，最后一击仍是点选）。

### ② OnChange —— 挂在类别上，时机"值被改时"

**声明**：

```python
hooks=[..., OnChange(invalidates=["photos", "detail"])]
```

声明说的就一句："类别的值一旦被改，把照片和描述作废。"（invalidates 是张清单，引擎照单执行。）

**没有它会出的事**：确认单上把冷柜改成灯箱，照片栏里躺着的还是**冷柜的照片**——错单照交。

**跑起来的样子**（场景 C 的 v10）：

```
店员重选类别：制冷设备/冷柜 → 照明/招牌
  引擎检测到 category 的值要变
    ↓ 查钩子：OnChange(["photos","detail"])
  执行：照片清空、描述清空、两个名字塞回待问清单
  下一轮自然重新问拍照（照明类的拍摄清单）
```

引擎不知道"换类别要重拍照"这个业务道理——它机械执行清单；道理在技能包里。产品语义的"回跳拍照"由数据失效实现，图上没有一根往回的边。

### ③ DefaultFill —— 挂在描述上，时机"进确认前"

**声明**：

```python
Slot(name="detail", ...,
     hooks=[DefaultFill(when=lambda rt: rt.card_mode(),
                        value=lambda rt: f"{rt.category_short()}，详见现场照片")])
```

两个参数都是**函数不是值**（延迟求值）：when—"什么时候填"（走的是点卡片路径时）；value—"填什么"（运行时才拼：类别短名当场才知道）。

**没有它会出的事**：点高频卡的用户从头到尾没打过一个字，描述却是必填——提交校验把他卡死在确认单上。

**跑起来的样子**：店员点"❄️冷柜/空调不制冷"一路点到底 → 进确认前引擎发现描述空、when 成立 → 调 value 函数现场拼出"制冷设备/冷柜，详见现场照片"填入（source=system_default）→ 确认单展示、可改。

### ④ SubmitCheck —— 包级（不挂具体字段），时机"提交前"

**声明**：

```python
SUBMIT_CHECK = SubmitCheck(rule=lambda rt: None if rt.photo_list_ok() else "现场照片未按拍摄清单传齐")
```

约定：返回 None=通过；返回字符串=给用户看的错误文案。挂在包级因为它是**跨字段校验**（照片数量对不对得上当前类别的拍摄清单），不归任何一个字段管。在引擎通用的"必填齐"检查之后执行。

## 三、引擎侧的实现形状

引擎里没有"钩子处理器"组件，就是固定时机各一段循环（伪码）：

```python
# update 节点内 · 候选产出时
for h in slot.hooks:
    if isinstance(h, MustPick):  候选改卡片不写槽
# update 节点内 · 值被改时
for h in slot.hooks:
    if isinstance(h, OnChange):  作废 h.invalidates 里的槽位并塞回议程
# confirm 之前
for h in slot.hooks:
    if isinstance(h, DefaultFill) and h.when(rt):  槽位 = h.value(rt)
# submit 之前
err = pack.submit_check.rule(rt)
if err: 停在确认单，高亮缺项
```

注意钩子对象**没有 run 方法**——执行逻辑全在引擎，钩子只是数据。时机是写死的四五个，引擎到点统一问一遍。

## 四、报销会用到的新钩子（预告）

| 钩子 | 场景 | 规则 |
|---|---|---|
| OnChange(derives=...) | 一级部门 | 所在部门变 → 一级部门按路径[0]重推（与 invalidates 同一时机、两种动作：作废 vs 重算） |
| 行数上限 | 费用明细子表 | 超过 10 行 → 引导拆单 |
| 欠票联动 | 发票状态 | 选"欠票" → 确认单展示补票提示 |

同款模式、换个业务规则——报销接入时就是往 slots.py 里再挂几个这样的小块，引擎一行不改。

## 五、快答

- **钩子和路由什么关系？** 无关。路由决定"下一步去哪"（引擎的事），钩子决定"这一步里按我们业务的规矩办什么"（业务的声明）。
- **钩子会拖慢流程吗？** 不会，全是内存里的对象判断和字典操作，微秒级。
- **钩子能调 LLM 吗？** 设计上不出现这种钩子——需要模型判断的不是"规则"，规则才做成钩子；模型的事全在 extract。
- **怎么测？** 每个钩子两个用例：触发的、不触发的（pytest 纯函数测试，零 LLM）。
