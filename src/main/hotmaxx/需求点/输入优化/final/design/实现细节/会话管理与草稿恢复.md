# 会话管理与草稿恢复

> 一句话：**会话即草稿**——Checkpointer 每个节点后自动把 State 落 Redis（窗口内消息在 State、全量在 MySQL 消息表）；无论杀 App、断网还是主动退出，进度不丢，重进一个请求续填。

---

## 一、生命周期

1. **出生**：`POST /sessions`（带 `store_no`，门店由入口决定——一人可能多店）→ 查活跃索引 `rp:active:{uid}:{store_no}`（后续技能包同构）：有则复用（`is_resumed=true`，弹「继续上次填报」；换店不复用、各开各会话），无则新建并 `load_context` 带出，首个检查点落盘。
2. **成长**：每条用户消息 = 一轮图执行，**每个节点后自动存档**（零业务存档代码）；轮末把本轮消息**同步批量 upsert 入 MySQL 消息表**，再裁剪 State 窗口至最近 10 轮。三条规则保证正确性：**先入库再裁剪**（被裁必已入库）、**(session_id, seq) 唯一键 + upsert**（崩溃后重执行重发同 seq，后写覆盖自愈）、**seq 用计数器生成**（裁剪后 length 不可当序号）——推演见《[ext/关键决策问答.md](ext/决策.md)》State 设计决策 9。
3. **三种终态**：**DONE**（建单成功 → 摘要归档一行 → 删检查点 + 活跃索引）；**keep**（检查点保留 7 天，重进提示续填）；**abandon**（标记废弃，留 24h 排查）。
4. **过期**：TTL 到期自动清 + 每日清理任务兜底（删前确认消息已全量在库）；超期重进静默开新会话。

**错误退出零处理**：存档时机是"每个节点后"而非"退出时"——杀 App、断网来不及发请求，检查点早已最新。**并发（已知简化）**：同一会话不做多端并发控制（后写覆盖），防重复提交由 order_key 幂等保证。

## 二、数据与存储设计

先定调：**热路径在 Redis，MySQL 不在填报关键路径上**——全系统只有一处热写（每轮一次批量 upsert 消息），其余都是终态写入和事后分析。

### 2.1 Redis Key 规格

| Key | 结构 | TTL | 用途 |
|---|---|---|---|
| LangGraph 检查点（thread_id = 会话 ID） | 框架管理 | 7 天（活跃滑动续期） | State 全量快照，每节点后自动写 |
| `rp:active:{uid}:{store_no}` | string → session_id | 随会话 | 活跃索引：重进找回会话（一人多店，跨店不串） |
| `quota:{uid}:{yyyyMMdd}` | INCR 计数 | 当日 24:00 | 单人单天 LLM 配额 |
| `dict:{skill}:{name}` | 字典 JSON | 1 小时 | 枚举/树缓存，miss 时回源工具 |

### 2.2 MySQL 三张表

**表 1 · 消息表 `agent_message_archive`**（唯一热写，每轮一条批量 upsert）：

```sql
CREATE TABLE agent_message_archive (
  id         BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  session_id VARCHAR(32) NOT NULL COMMENT '会话ID（rp_/ex_ 前缀）',
  skill      VARCHAR(16) NOT NULL,
  seq        INT          NOT NULL COMMENT '会话内单调递增（meta.seq_counter）',
  role       VARCHAR(8)   NOT NULL COMMENT 'user / server',
  type       VARCHAR(24)  NOT NULL COMMENT '消息 type，与接口文档 §2.2 一致',
  data       JSON         NOT NULL,
  created_at DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  UNIQUE KEY uk_session_seq (session_id, seq)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='对话消息全量（每轮批量 upsert，唯一键幂等）';
```

写入即 `INSERT ... ON DUPLICATE KEY UPDATE`——重发覆盖，崩溃自愈（见 §一 三条规则）。

**表 2 · 会话归档表 `agent_session_archive`**（终态一行，DONE / EXPIRED / ABANDONED 时写）：

```sql
CREATE TABLE agent_session_archive (
  session_id   VARCHAR(32) PRIMARY KEY COMMENT '一行一会话',
  skill        VARCHAR(16) NOT NULL,
  status       VARCHAR(12) NOT NULL COMMENT 'DONE / ABANDONED / EXPIRED',
  order_no     VARCHAR(32) NULL COMMENT '明道云单号（DONE 时）',
  order_key    VARCHAR(64) NULL COMMENT '幂等键（=会话ID）',
  context      JSON NOT NULL,
  slots        JSON NOT NULL COMMENT '含 source：审计与事后分析',
  meta         JSON NOT NULL COMMENT 'llm_calls / branch / fail_count 等',
  started_at   DATETIME(3) NOT NULL,
  finished_at  DATETIME(3) NOT NULL,
  archived_at  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  KEY idx_skill_time (skill, finished_at),
  KEY idx_order (order_no),
  KEY idx_status_time (status, finished_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='终态会话摘要';
```

**表 3 · 埋点事件表 `agent_event_log`**（事件流，llm_call 调用日志并入此表，props 带次数/token/耗时/失败）：

```sql
CREATE TABLE agent_event_log (
  id         BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  session_id VARCHAR(32) NULL,
  skill      VARCHAR(16) NOT NULL,
  user_id    VARCHAR(32) NOT NULL,
  event      VARCHAR(32) NOT NULL COMMENT 'session_start / enum_first_pick / submit_success / llm_call …',
  props      JSON NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  KEY idx_event_time (event, created_at),
  KEY idx_session (session_id),
  KEY idx_user_time (user_id, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='埋点事件（指标计算源）';
```

### 2.3 三条设计原则

1. **归档即快照**：slots/meta 存 JSON 原样，冷数据不做字段级建模，要分析再 ETL——避免两处结构漂移（事后算类别准确率 = 消息表里 enum_card 的 AI 首选 vs 归档表 slots.category，两表就够了）。
2. **无外键**：会话 ID 逻辑关联，删除无级联负担。
3. **唯一键只给幂等需要的地方**（消息表），其余靠主键。

量级：试点期（单门店、日均几十单）单表单月无压力，预留按月分区即可。报销接入**不新增表**（skill 字段区分）。

要点：**恢复不依赖前端本地**——重进统一 `POST /sessions` 按活跃索引复用，换设备/清缓存都成立；前端存的 session_id 只作刷新/响应超时对齐加速。照片本体在 OSS，检查点只存 media_id。

## 三、接口与草稿的关系

| 接口 | 草稿动作 |
|---|---|
| `POST /sessions` | 查活跃索引：复用（get_state 重放）/ 新建 + 首存 |
| `POST /messages` | 一轮图执行，节点逐个自动存档；轮末消息入库 + 裁剪 |
| `POST /upload` | media_ids 并入槽位后存档 |
| `GET /{id}` | 只读：会话内刷新 / 响应超时对齐（快照 + 消息重放） |
| `POST /submit` | resume → submit；成功后归档 + 清检查点/索引 |
| `POST /exit` | keep：保留 7 天；abandon：标记废弃 |

两处防坑：闲聊拉回轮次只追加消息、议程不动，同样存档；配额 Key 与检查点独立，超限降级不影响草稿。

## 四、复原（两源拼接，前端无感）

```
POST /sessions → 活跃索引命中
 → get_state：槽位 + 议程 + focus + 窗口尾巴（最近 10 轮）
 → MySQL 查 seq < 窗口首条 的全部消息
 → 拼接下发：老消息（库）+ 窗口（Redis）+ 按焦点渲染当前步骤
```

- **错误退出重进**：检查点停在 `focus: photos` 之类，重放回原步骤、已答全回显，零 LLM。
- **keep 7 天内重进**：弹「继续上次填报」→ 点选恢复（draft_resume 埋点）。
- **TTL 过期后**：草稿按设计失效开新会话，但消息在库永久可查（"上次对话记录还在，重新填一次"）。
- **对账兜底**：复原时 DB 的 max(seq) 落后于窗口最早 seq 就现场补写；每日任务全量对账，异常（只可能是规则违背）告警。

## 五、演进项（放量后）

同步批量 → 异步批量：轮末只投进程内写器（攒批 flush），配**裁剪同步门槛**（裁前必 flush）+ 每日对账——窗口天然是缓冲区，零丢失；主路径不再等待 DB。
