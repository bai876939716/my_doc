# 图节点设计（v2）

> 按 2026-11-13 实现重写。与旧版《图节点设计.md》的三处机制差异：①confirm 不再 interrupt 挂起——确认等待是数据（meta.confirm_pending），消息直接落 State（11-12 拔根）；②submit 不走 Command(resume)——/submit 接口注入内部手势 `{"type":"submit"}` 经入口直达；③新增 intake 节点——用户手势落 role=user 档。检查点也从 Redis 切到 PG。旧版留档对照。
> 配套图：《02-通用采集图-v2.puml》（同目录 diagrams/）。

## 一、通用图：节点与边

**每轮 = 一次图执行**：`START → intake →（entry_router 条件边分流）→ 负载节点链 → END`。跨轮状态全在 Checkpointer，接口层不自己写"先存再推"。

| 节点 | 输入→输出 | 说明 |
|---|---|---|
| `intake` | 外部手势 → role=user 消息入 State | **恒为本轮第 1 条**（seq = 进轮前计数器 + 1）；data = 请求体除 type 外原样；submit（内部手势）与建会话轮（incoming 为空）不落档。审计 / 指标 / GET 重放的真值 |
| `load_context` | context 空 → 调技能包 context 工具填 | 建会话轮专属；下发状态条 + 开场白 + 高频卡片；启动参数（uid/store_no）从 config 注入不走 State |
| `extract` | 打字消息 → 意图 + 槽位增量 + 类别候选 + 描述整理 | **全流程唯一 LLM 调用点**（点选/卡片/上传跳过此节点）；注入 flow_state 流程状态行（正在问什么/停在确认/挂起等值）——裸值消解的依据 |
| `update` | 增量 → 过闸（白名单/枚举/原话印证/格式）写 slots | 说到的直填 ai_filled（无 MustPick 的枚举，类别除外）；直填后话术前置复述；被拦值点名善后（非法枚举递回选项卡、非法手机号请重发）；无值修改转 `pending_update` 轻量挂起，下轮裸值消解；钩子联动失效在此触发 |
| `route`（条件边） | 看 agenda + 意图定下一跳 | **不变量：每轮以下一个待办收尾**——议程非空一律 ask 重发当前问题卡，议程空回 confirm；挂起轮以追问话术收尾（END）；连续边界轮达阈值转 fallback |
| `ask` | agenda 首项 → 话术模板 + 槽位类型映射卡片 | 0 LLM；类别轮懂 Top3（候选只进卡片永不入槽）与全量兜底；下发即回采集态 |
| `confirm` | DefaultFill 补默认值 → 组确认单消息 | **数据态非挂起**：消息直接落 State、置 meta.confirm_pending=True；confirm_quiet 标志控制重挂时不重复"信息齐了"开场；确认态收到任意消息处理完必回确认单 |
| `submit` | 全量校验 → SubmitCheck → 调技能包提交工具（order_key=会话 ID 幂等） | 仅 `/submit` 接口可注入（IncomingMsg 无 submit 类型，外部传不进来）；缺项塞回议程停在确认前；建单失败置 submit_error 保持确认态可重试；成功清活跃索引 + 归档 |
| `fallback` | 全量字典卡片向导 | 0 LLM；branch=b 免描述（否则纯文本槽无手势可填必卡死）；照样能交单 |

## 二、与六接口的对接（接口零改动的原因）

| 接口 | 图侧动作 |
|---|---|
| `POST /sessions` | 查活跃索引（uid+store_no）复用或新建 thread（换店不串）；建会话轮 incoming={} 走 load_context；is_resumed 时 get_state 全量重放（含 role=user 用户回显） |
| `POST /messages` | `invoke({"incoming": payload})`——先经 intake 落档（打字→extract；点选/卡片/上传→update，0 LLM）；响应按 role≠user 过滤只回服务端消息 |
| `GET /{id}` | `get_state` 全量重放（含 role=user）+ collected（响应超时对齐/刷新/换端恢复） |
| `POST /submit` | 注入内部手势 `{"type":"submit"}` 经入口直达 submit 节点（图上无 confirm→submit 边）；幂等=meta.order + order_key |
| `POST /exit` | keep=检查点留存（7 天滑动）；abandon=先归档再销毁检查点（旧 sid 再访问 40401） |
| ~~`POST /upload`~~ | **已废除**——照片走明道云直传，前端拿 URL 后以 `upload_done` 消息带 `attachments:[{name,url}]` 引用进来 |

响应形态：**同步 JSON**——图执行完毕，State.messages 里即本轮全部产出，接口层直接组装返回；SSE 为二期演进，届时卡片协议不变。

## 三、Checkpointer 配置与 Key 布局（PG 版）

| 项 | 设计 |
|---|---|
| Saver | `PostgresSaver`（langgraph-checkpoint-postgres）；`CHECKPOINT_MODE=memory\|postgres` 双模式切换，代码零改动（当前默认 memory，PG 到位即切） |
| 存什么 | **整个 State 快照**：槽位 + 议程 + 上下文 + **消息全量**（含 role=user；无窗口裁剪——崩溃/重启恢复 = get_state 完整重放） |
| thread | `thread_id = session_id`（rp_*） |
| 活跃索引 | PG 表 `agent_active_index`（key=rp:active:{uid}:{store_no} 语义；惰性过期 + resume_count 续填计数列） |
| TTL | 清理线程兜底：索引过期（7 天没动）删整 thread；终态归档后的检查点到期回收、归档行永久保留 |
| 归档 | submit 成功 / abandon 时落 PG 两表：`agent_session_archive`（摘要+过程指标列）+ `agent_message_archive`（消息逐条含 role=user，审计与指标 SQL 直接查） |
