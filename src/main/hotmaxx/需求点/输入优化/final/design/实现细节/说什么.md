## 一、原理：一句话和三个分工

**一句话**：整套系统就是把“填表单”拆成四个角色各干各的——**LLM 只负责听懂，引擎只负责流程，技能包只负责声明业务，人负责拍板**。互相之间不越界，越界的地方全部用“查表”和“闸门”焊死。

支撑这句话的核心洞察只有一个：**“问到哪了”不是流程，是数据。** 传统状态机里“现在该问照片了”是一个代码状态；我们把它变成黑板上一张待办清单（agenda）——报修的清单是 [类别, 描述, 照片, 上门, 影响, 电话]，答完一项划掉一项。既然“进度”是数据，那换个业务就只是换一份清单，流程代码一行不用动——这就是能搭架子的根本原因。

黑板（State）上就五样东西：**槽位**（每个字段一格，值+谁写的+什么时候写的）、**议程**（还缺什么）、**消息窗口**（最近 10 轮对话）、**上下文**（带出来的门店/人/日期）、**meta**（计数器们）。整个会话的任何时刻，这块黑板就是全部现场。

## 二、运行：跟着店员xxx走一遍

**第 0 步：进场。** 店员在表单页点「AI 智能填报」，前端 `POST /sessions`。服务端先查活跃索引（这个用户有没有没填完的会话）——没有就新建，跑图的第一个节点 **load_context**：调工具把门店/报修人/日期从员工档案带出来写上黑板，议程按技能包清单生成。执行完，**框架自动把整个黑板存进 Redis**（这就是检查点 v1），然后 SSE 推三条消息：状态条（📍11522 安徽商之都OK店｜白云翔）、开场白、六张高频卡片。**推送完毕，HTTP 连接关闭**——记住这个模式，它贯穿全程：**每轮对话都是一次独立的短请求，图执行几秒钟就结束，服务端不为任何人挂着长连接**。会话的连续性不靠连接活着，靠 Redis 里那份黑板。

**第 1 轮：他打字了。**“冷柜不制冷了，今早开始的，鲜奶都不敢卖全下架了”。前端 `POST /messages`，服务端 `ainvoke(这条消息, thread_id=会话ID)`——图从上次结束的地方恢复黑板，开始跑：

- **extract 节点**（全流程唯一调 LLM 的地方）：拼一份“窄而准”的 brief 发给模型——系统词（引擎通用段 + 技能包动态注入的“本业务字段清单和类别字典”）+ 槽位快照（现在填到哪了）+ 最近几条消息 + 用户原话（三引号包裹，定性为数据不是指令）。模型回一段 JSON：意图=provide，描述整理好了，类别候选 Top3。
- **update 节点**：八道闸在这里——候选逐个对字典白名单，编的丢掉；多抽的字段整键丢弃；描述超 100 字截断。然后按**时机的钩子**执行：现在是“候选产出时”，查 category 槽声明的钩子，发现 MustPick——**候选只准进卡片，不写入槽位**。
- **route**（条件边函数，不占节点）：看议程——描述这次填上了划掉，类别还没定 → 去 ask。
- **ask 节点**：话术模板取一句（“听下来了。我认出的类别如下——点一下确认”），按槽位类型查表出卡片形态（enum → 单选卡）。下发，本轮 SSE 推完 done，**连接关闭，图执行结束**。刚才每过一个节点，框架都自动存了一版检查点（v2 已落盘）。

**第 2~5 轮：点选的流水。** 他点类别卡片、传两张照片、点“尽快上门”、点“影响”、点“用本人号码”——每一动都是一次新的 `POST /messages` + 一次图执行。**这些轮次全都不调 LLM**（点选消息自带结构，跳过 extract 直进 update），每轮就干三件事：写一格槽位、划一项议程、存一版检查点。每轮结束时还有两个后台动作：这轮的消息**批量写进 MySQL 消息表**，然后把窗口外的老消息从黑板裁掉（先入库再裁，被裁的必已入库）。

**第 6 轮：确认单。** 议程清空，route 判定必填全齐 → 进 **confirm 节点**：生成十字段确认单，然后 `interrupt()` **挂起**——图执行到此终止，挂起状态也存档。店员看到确认单，逐项可改。

**第 7 轮：提交。** 他点【确认提交】→ `POST /submit` → 服务端用 `Command(resume)` 从挂起的检查点恢复 → **submit 节点**带着 order_key（=会话ID，防重复提交）调明道云建单工具 → 出单号 BX-xxx → 摘要归档 MySQL、删检查点、清活跃索引。完事。

**全程账单：LLM 调用 1 次，Redis 存档 9 版，MySQL 每轮一批消息 + 最后归档一行。**

## 三、异常路径（产品要求的另一半全在这里）

- **填一半杀了 App**：什么都没丢——最后一版检查点就是最新现场。重进 `POST /sessions` → 活跃索引找到会话 → 读黑板 + 窗口尾巴从 Redis、更早消息从 MySQL 拼回来 → 界面回到上次问到的那一步。**换手机、清缓存同样成立，因为恢复不依赖前端存任何东西。**
- **中途打字改字段**（“电话换成店长的 139…”）：extract 听出意图是 update → 电话那一格原地覆盖，**议程纹丝不动**——改内容不等于改流程。
- **重选类别**（唯一例外）：update 执行 category 声明的 OnChange 钩子（“值变化时”）→ 照片、描述两格清空、塞回议程 → 自然重新问拍照。老的“回跳”变成了数据失效，图上没有一根往回的边。
- **跑题/闲聊/注入**：每条打字最多花 1 次调用来“听懂”，识别为越界 → 槽位零写入、模板话术拉回；连续 2~3 次 → **fallback 节点**接管（图上一等公民，不是异常处理）——纯卡片向导、0 LLM，照样能走完提交。AI 挂了同理：换通道，不换结果。
- **7 天没回来**：草稿过期、重新开填，但对话记录在库里永久可查。

## 四、产品八条要求逐条对上（证“能满足”）

| FA 原则 | 承接机制 |
|---|---|
| 输入方式并行互不干扰 | AI 入口叠加在表单页，对话页一键切回 |
| AI 预填、人确认 | 候选永不入槽（MustPick）+ 确认单平铺 + 提交双重校验 |
| 能查不问、只问该问 | context 工具带出 + 议程只问缺的 |
| 高频预选+渐进追问 | 六张 quick_cards 直锁类别；议程逐项收敛 |
| 全程可改 | update 原地覆盖 + 类别钩子例外 |
| 单账号服务端代理 | 明道云唯一账号在 mcpServer 工具后面，业务身份写进字段 |
| 按门店隔离 | 网关注入 uid → 带出门店 → 服务端过滤 |
| 对话有边界 | 意图六类枚举 + 字段白名单 + 失败计数降级 |

## 五、静态组装（代码怎么长成这样）

三层目录：`core/`（引擎+契约，业务无关，一次建设）、`skills/repair/`（五件套声明：slots/dicts/talks/tools/prompts）、`api/`（六个接口按技能包自动挂路由 `/agent/repair/v1`）。**启动那一刻**：`repair.load()` 把五件套装起来做自检（槽位重名？话术缺失？字典没注册？——错了当场炸，不留到店员填单时）；引擎拿到的是一个 Map，之后所有节点都是查这份 Map 干活——**ask 查槽位类型定卡片、update 查钩子定规则、route 查议程定去向、extract 把字段清单注入 Prompt**。业务在系统里的全部存在形态就是这份 Map。
