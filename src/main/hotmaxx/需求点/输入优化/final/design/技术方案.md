# 设备报修 · AI 填报 Agent 技术方案

> LangGraph 引擎 + 报修技能包——流程是引擎的一张通用图，业务是包里的一份字段说明书；
> 本期落地报修，新业务按技能包低成本接入。

---

## 1. 核心思路与实现方式


### 1.1 产品强约束

| # | 约束点            | desc                                                              |
|---|----------------|-------------------------------------------------------------------|
| 1 | 流程可控，不跳步、不漏问   | 1.沟通没完没聊，不断的问答，却解决不了问题；  <br/> 2.表单字段有先后顺序 （可能关联性）；<br/>3.字段要保证齐全 |
| 2 | 类别绝不能选错        | AI 只能给候选，必须用户确认                                                   |
| 3 | 任意字段随时可改       | 不能让用户被流程绑架 中途有问题还得重来                                              |
| 4 | 填一半退出，回来接着填    | 草稿保留 7 天                                                          |
| 5 | AI 挂了不能耽误报修    | 降级成卡片点选或回老表单                                                      |
| 6 | 对话有边界（新增）      | 只采表单内 10 个字段；问进度/闲聊/越权/注入一律拉回；连续失败降级                                |



### 1.1 核心思路

> 1. **LLM 负责识别与生成**（听懂口语、抽出结构化字段）
> 2. **LangGraph 负责编排**（通用图 管流程、interrupt 管人机确认、Checkpointer 管存档恢复）


### 1.2 实现方式对比

| 候选 | 一句话定位 | 判定 | 理由 |
|---|---|---|---|
| A. 纯 LLM 自主对话（ReAct） | 模型每轮自己决定问什么、调什么 | ✗ | 跳步漏问不可控、易编枚举、轮次成本不可控 |
| B. 纯 LangChain 线性串联 | RunnableSequence 一路跑到底 | ✗ | 回跳只能整链重跑，随时改做不到 |
| C. 自研状态机 | 状态 × 事件转移表自管流程 | ✗ | 存档恢复 / 人机中断 / 流式等通用能力全部要自建自维，框架已内建 |
| **D. LangGraph 图编排** | StateGraph 节点 + 条件边，Checkpointer 内置断点续填，interrupt() 原生人机确认 | **✓ 采用** | 编排 / 存档 / 恢复 / 中断 / 流式全部原生；技能包可直接演进为多 Agent 的子图 |
| E. Dify | 低代码平台 | ✗ | 卡片消息协议无对应物、降级埋点需外挂网关、私有化运维重 |
| F. Coze 扣子 | SaaS 低代码 | ✗ | 数据出域；私有化部署组件重 |

> **兼容后续业务规划** ：最好只加配置和代码 不改框架，业务接入的容易程度
> </br>**扩展性**：临时性方案也要考虑迁移的容易度

## 2. 系统架构

系统架构图：[01-架构图.puml](diagrams/01-架构图.puml)

- **唯一新建部署单元**：Agent 容器（mcpServer 工具层 + LLM 网关在进程内、逻辑解耦）；接入方式：网关 → Java 层（provider-biz-ai-middle 加转发，照 LayoutDrawingProxy 模式）→ Agent 内网 Service（base-url 直调），Agent 解析 HTM-HEADER 拿 userid，接口在 common-center 登记。
- **容器内**：FastAPI 会话 API + LangGraph 引擎（通用采集图）+ 报修技能包。
- **对外**：六接口、卡片消息协议、**同步 JSON 响应**（每轮一次请求返回全部新消息；SSE 为二期演进）——前端按普通 fetch 对接。
- **存储**：Redis = LangGraph 检查点（thread_id = 会话）+ 活跃索引 + 配额 + 字典缓存；MySQL = 消息表（全量对话，每轮批量入库）/ 归档 / 埋点 / 调用日志。

## 4. LangGraph 编排过程 

> 通用采集图：[02-通用采集图.puml](diagrams/02-通用采集图.puml) ｜ 实现细节：[实现细节/LangGraph落地设计.md](实现细节/图节点设计.md)

### 4.1 State：

| 字段 | 类型 | 内容 |
|---|---|---|
| `skill` | str | 技能包名（repair） |
| `context` | dict | 带出字段（门店 / 报修人 / 日期 / 手机号） |
| `slots` | dict | **槽位值**：每个字段一格 `{value, source, updated_at}`；source ∈ system_default / ai_filled / user_edited |
| `agenda` | list | **待问清单**：由技能包 schema 的必填槽位生成，答一个划一个——"问到哪了"是数据不是代码 |
| `messages` | list | 对话消息（**最近 10 轮滑动窗口**；全量每轮批量入库 MySQL、复原两源拼接；不进 Prompt） |
| `meta` | dict | 分支 / 失败计数 / 退出状态 |

> State 完整数据结构、真实快照与设计理由：[实现细节/State设计.md](实现细节/State设计.md)。

### 4.2 图与节点

节点结构图：[02-通用采集图.puml](diagrams/02-通用采集图.puml) ｜ 场景版（剧本对话 × 节点流转对照）：[03-场景流转图.puml](diagrams/03-场景流转图.puml)

| 节点 | 职责（输入 → 输出）                                          | LLM |
|---|------------------------------------------------------|---|
| `load_context` | 建会话：调工具带出 3 字段 → 下发状态条 + 高频卡片                        | — |
| `extract` | 每条打字消息一次**联合抽取**：意图 + 槽位增量（**说到的低风险字段直接 ai_filled 入槽**）+ 类别候选 Top3 + 描述整理 + 影响预判 | ✓ **全流程唯一调用点** |
| `update` | 过防幻觉闸（枚举白名单；**类别候选只进卡片、绝不入槽**）→ 写槽位（无 MustPick 的枚举槽允许抽取值直填）→ 钩子联动失效 | — |
| `route` | 路由判定：看议程与意图决定下一跳                                     | — |
| `ask` | 话术模板 + 槽位类型 → 卡片形态，下发后本轮结束                           | — |
| `confirm` | 生成 10 字段确认单 → `interrupt()` 挂起等人                     | — |
| `submit` | order_key 幂等建单 → 出单号                                 | — |
| `fallback` | 全量类别点选 / 卡片向导                                        | — |

**每轮 = 一次图执行**：messages 接口收到用户消息 → `graph.ainvoke(消息, thread_id=会话ID)` → 图跑到 ask 或 confirm 挂起 → 本轮结束。跨轮状态全靠 Checkpointer。

> 四个场景（0 LLM 卡片路径 / 随时改与重选类别 / 断线恢复与降级）的节点运转与每版 State 全量 JSON：[场景演示.html](diagrams/场景演示.html)（变化字段标红，点开查看）。

### 4.3 条件边路由（route 节点的判定表）

| 意图（extract 输出，六类枚举） | 议程状态 | 下一跳 |
|---|---|---|
| provide（提供信息） | 有缺槽 | ask（问议程首项） |
| provide | 必填全齐 | confirm（interrupt 挂起） |
| update（改字段） | 任意 | update 原地覆盖 → 回当前焦点，**议程不变** |
| **confirm 态收到任意消息** | — | 一律合法：改字段值留在 confirm（重发确认单，source→user_edited）；唯一例外 enum_pick 重选类别 → 照片/描述作废回跳重采；submit 接口 = 提交 |
| query_progress / smalltalk / off_scope | — | ask（模板话术拉回，一轮一事） |
| inject_attempt（提示词注入） | — | 同上：输入三引号包裹当数据，槽位零写入 |
| 连续 2~3 轮识别失败 | — | fallback（卡片向导，0 LLM） |
| exit | 任意非终态 | EXITED（keep 7 天 / abandon） |

### 4.4 存档与恢复（Checkpointer）

- **存什么**：整个 State（槽位 + 议程 + 消息窗口）——每个节点执行完自动落 Redis，即"先存再推"的原生版，业务代码零存档逻辑（窗口与入库见 §6）。
- **thread_id = 会话 ID**：响应超时对齐 / 会话刷新 = `get_state(thread_id)` 重放消息；错误退出（杀 App / 断网）零特殊处理，重进按活跃索引复用会话。
- **确认单**：`interrupt()` 挂起；`POST /submit` = `Command(resume)` 恢复走 submit；确认单上改字段 = 带新值 resume 回 extract。
- **留存**：TTL 7 天（配置 + 每日清理任务兜底 ❗POC 项）；DONE 后删检查点、终态归档 MySQL。

## 5. 报修技能包（本期实现）

| 槽位 | 类型 | 策略 |
|---|---|---|
| 门店名称 / 报修人员 / 报修日期 | `context` | 入口 store_no 带出门店（一人多店）+ 当天带出；报修人员可改（替报场景） |
| 报修类别 | `enum` | 钩子：必须点选；高频卡片直锁（免类别免描述） |
| 描述具体故障 | `text` | 按「故障现象/发生时间/影响范围」范式整理，≤100 字 |
| 现场照片 | `media` | 通用拍照引导（按类别的差异化清单与警示：二期） |
| 期望上门 / 影响营业 | `enum` | **说到的（含推断）直接 ai_filled 预填**，确认单核对；没说到才发二选一卡 |
| 联系电话 | `context` | 默认本人带出，确认卡（进议程，可改） |
| 期望处理 | `text` 选填 | 不问，确认单可补 |

工具 4 个：`get_user_context`（门店由入口 store_no 决定、人按 uid 查——一人多店）/ `get_category_dict` / `upload_media` / `create_repair_order`（order_key 幂等）。
钩子 3 条：类别必点选；重选类别联动照片/描述重校验；卡片路径空描述自动填「类别+详见现场照片」。

## 6. 会话草稿与退出恢复

### 6.1 自动存档

店员每回一条消息，引擎走完几个节点，每走完一步就把当前进度——已填了什么、还缺什么、最近几轮对话——自动存进 Redis 一次。这是引擎自带的行为，业务代码一行不用写；也不存在"忘了保存"的时机，因为保存不发生在退出时，而是发生在每一步之后。对话记录不会无限堆在存档里：只保留最近 10 轮，更早的进数据库 ）。

### 6.2 消息入库

每一轮结束时，这一轮的消息（店员说的、AI 发的卡片）先写进 MySQL 消息表，然后才把更早的消息从存档窗口里裁掉。先入库、再裁剪，顺序不能反——被裁掉的内容一定在库里有底。写入带唯一键（会话 + 序号），同一轮重复写会直接覆盖：就算进程半路崩溃，重来的那轮把同样的消息再写一遍，结果依然正确，不需要人工修复。会话即使中途放弃或异常中断，完整对话也都在库里。

### 6.3 断点复原

填一半退出——杀 App、断网、主动退出都一样——下次进来，服务端通过"该用户当前活跃的会话"找回原进度：已答内容全部回显，界面停在上次问到的那一步；更早的对话从数据库按顺序补齐。超过 7 天没回来，草稿过期、重新开填，但历史对话在库里永久可查。整个恢复不依赖手机本地缓存，换设备、清缓存都能续。

### 6.4 主动退出

返回时三个选择：继续填写；存草稿离开（保留 7 天，再进提示"继续上次报修"）；放弃本次（保留 24 小时供排查后清理）。

> 细则：[实现细节/会话管理与草稿恢复.md](实现细节/会话管理与草稿恢复.md)。

## 7. 业务接入的思考与设计点

### 7.1 底座有哪些 ，之后报销怎么接

**底座**：图规则、会话的保存与恢复、跟前端约定的接口和消息、防错和降级的整套机制——这些跟着报修建一次，之后基本不动。
</br>**业务包**：每个业务一份，报修是第一份，报销是第二份，里面装的就是这个业务的字段清单、选项字典、话术和提交接口——全是配置，不是代码。


### 7.2 技能包约定

一个技能包就是五样东西：
- 字段 schema、
- 字典源、
- 话术模板、
- 工具、
- 钩子
> 装的全是数据和规则，没有流程代码——业务之间的差异 。

## 10. 降级与成本

- 降级：LLM 失败 / 配额超限 / 连续识别失败 / 引擎运行时异常 → 同一出口 fallback 卡片向导（0 LLM）→ 引导回传统表单；超限**换通道**（照样交单）。
- 成本口径：**打字才调 LLM（每条消息一次联合抽取）、点选 0 调用、话术走模板**。

**用户"聊很多"的四层控制**：

| 层 | 机制                                                        | 效果                          |
|---|-----------------------------------------------------------|-----------------------------|
| 边界 | 跑题/闲聊/注入 → 槽位零写入 + 模板拉回（每条消息最多 1 次调用）；连续 2~3 轮 → fallback | 无效输入不推进流程、不连环追问             |
| 配额 | 单会话 限制；单人单天次数+token 双限额；全局日配额熔断；超限降级卡片向导                  | 成本有上限且不阻塞                   |
| 上下文恒定 | extract 只喂 schema+槽位快照+最近 几条条消息  ；全量消息不进 Prompt           | 聊 100 条，第 100 次调用成本 ≈ 第 1 次 |
| 少聊的动机 | 点选 不调用 · 一句话一次抽全                                          | 正常路径 2~3                    |
