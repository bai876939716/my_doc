## 一、先一句话说清整个引擎

店长打一句话 → 引擎**抽出**字段 → **卡片问**缺的 → 齐了出**确认单** → 点提交入库。
**LangGraph 就是管"流程走到哪、状态存在哪、哪里要停下来等人"的那副骨架**；字段怎么抽是 LLM 的事，骨架自己不聪明，但很稳。

把它想象成一条**流水线 + 一个自动存档的工位牌**：每个工位（节点）干一小步活，干完自动拍照存档（Checkpointer），到质检工位（确认单）流水线自动停，等工人（用户）按下"通过"才继续。

## 二、LangGraph 六个概念，逐个说透

### 1. State —— 一块所有人共用的黑板

一次填报会话里的所有数据：已填的槽位、还缺什么、聊天记录。每个节点读这块黑板、往上面写增量。

**像 Spring 里什么**：一次请求里贯穿的 Context/DTO，只不过它活得比请求久（存在 Redis）。

**为什么需要它**：没有黑板，每个节点就得自己传参收参；有了黑板，节点都是"读黑板→干活→写结果"的纯函数，好测好换。

### 2. 节点（node）—— 流水线上的一个工位

就是一个普通 Python 函数：输入 State，返回要更新的字段。比如 `extract` 节点里调一次 LLM 把"房租5000电费1200"变成两条明细草稿，写回黑板。

**像 Spring 里什么**：一个 @Service 方法。真没什么神秘的。

### 3. 条件边（conditional edge）—— 配置化的 if-else

"下一站去哪"不是写死在节点里的，而是单独一个路由函数看黑板决定：还缺字段 → 去 `ask`（追问）；全齐了 → 去 `confirm`（确认单）；识别连续失败 → 去 `fallback`（降级）。

**为什么重要**：我们的"缺什么问什么"全靠它——问哪个字段不是流程写死的，是看黑板上还缺什么算出来的。**这就是"业务不改流程代码"的根基**。

### 4. Checkpointer + thread_id —— 自动存档 + 档位号

每个节点干完活，框架**自动**把整块黑板存进 Redis；`thread_id` 就是档位号（= 我们的会话 ID）。用户中途杀 App，什么都没丢——下次拿着同一个 thread_id，黑板原样恢复。

**像 Spring 里什么**：以前你可能自己写"每步变更后存 Redis 快照、重启后读快照恢复"——这活框架包了，而且每一步都存，粒度比自己写的还细。

**游戏比喻**：自动存档。走到哪存到哪，退出重进就是"继续游戏"。

### 5. interrupt() —— 流水线上按暂停等人的按钮

`confirm` 节点生成确认单后调用 `interrupt()`，整条流水线**就地挂起**（挂起状态也被存档）。用户点"确认提交"（POST /submit），后端用 `Command(resume=...)` 把"答案"递回来，流水线从暂停处继续——走 `submit` 建单。

**像 Spring 里什么**：像一个 await 外部事件的挂起线程，但挂起状态由框架托管在 Redis，进程重启都不丢。

**为什么需要它**：人机确认（HITL）是对话式填报的核心动作，以前要自己做"确认态"的状态管理，现在一行挂起一行恢复。

### 6. 跨会话记忆 —— 按人开的长期抽屉（我们用工具实现）

Checkpointer 存的是"这一次会话"；跨会话要的是"这个人"的长期数据——收款人四件套首次填过，下次报销直接"用上次的？[确定/改]"。

**实现选择**：LangGraph 自带 BaseStore 可以直接读写，但我们选择**做成两个工具** `recall_payee` / `save_payee`——和查字典、建单走同一条 ToolProvider 路径。好处：记忆和其他工具一样可单测、可限流、可打日志；将来工具层独立服务化或多个 Agent 共用时，记忆天然跟着走，引擎不背包。

**像 Spring 里什么**：按 userId 存的 KV 缓存，只是访问方式收敛成了两个 Service 方法（工具），而不是让流程代码直接摸 Redis。

## 三、我们自己造的四个词（评审必被问到的）

### 槽（slot）—— 表单字段在引擎里的格子

一个槽 = 表单上的一个字段在黑板上的格子。每个格子有三要素：

| 要素 | 例子（报销·收款人） |
|---|---|
| **类型**（10 类之一） | `subgroup`（字段组） |
| **值 + 来源 source** | 值"张三"，来源 user_edited（另两种：system_default 带出 / ai_filled AI 预填） |
| **状态** | 空 / 待确认 / 已定稿 |

**类型决定一切**：怎么问（卡片形态）、怎么防错（哪道闸）、值从哪来（问用户/带出/计算）。这是"从复杂业务里抠共性"的成果——部门树、子表、下拉、四件套，全都归进 10 类，新业务标类型就行。

### 议程（agenda）—— 还缺什么的清单

黑板上一张清单：还有哪些必填槽没填。每轮答完划掉一项，`ask` 节点永远问清单第一项。**"随时改"的实现**：用户中途打字改电话 → 槽位原地覆盖 → 清单不动，流程不回退。

### 技能包（skill pack）—— 一份"业务说明书"

报修一张说明书、报销一张说明书，内容是五件套：**字段 schema + 字典源 + 话术模板 + 工具 + 钩子**。引擎（core）读说明书干活，说明书里没有一行流程代码。

**比喻**：引擎是洗衣机，技能包是洗衣程序卡——洗羽绒服和洗衬衫用不同卡片，洗衣机永远那一台。接入新业务 = 印一张新卡，不是造新洗衣机。

### 钩子（hook）—— 特殊规则的挂钩子

业务总有"不合群"的规则，不为例外改流程，只在说明书的钩子上声明"什么时候触发什么规则"：

| 钩子 | 规则 | 所属技能包 |
|---|---|---|
| must_pick | 类别 AI 只能提名，必须用户点选才入库 | 报修 |
| on_change | 重选类别 → 照片清单重校验 | 报修 |
| rows_limit | 子表最多 10 行 | 报销 |
| derive | 一级部门 = 所在部门路径自动推导，不问 | 报销 |
| invoice_link | 选"欠票" → 确认单展示补票提示 | 报销 |

**像 Spring 里什么**：@PostLoad、事件监听器这类"声明在配置上、框架在固定时机回调"的机制。

## 四、一条消息的完整旅程（报销场景走一遍）

店长输入：**"这个月房租 5000，电费 1200，发票都还没到"**

1. `POST /agent/expense/v1/sessions/{id}/messages`，图带着 thread_id 启动；
2. **extract**（唯一调 LLM 的地方）：一次拿回 → 意图=provide + 两行明细草稿（房租5000/电费1200）+ 发票状态候选"欠票"；
3. **update**：过闸（费用项目在字典白名单里吗？金额格式对吗？）→ 写进黑板明细槽 → 自动存档；
4. **route**：看议程——部门、办公地点、付款公司、收款人还没填；
5. **ask**：话术模板拼装，下发子表行卡片 + 费用项目 Top3 点选卡；
6. SSE 推给前端，本轮结束，图安静地等下一条消息。

店长后续每点一张卡（点选不走 LLM，0 调用）、每打一个字（走一次 extract），就重复 2→5。全齐后 route 把它送进 confirm——interrupt 挂起，确认单亮出来。

## 五、存档与确认的故事（把机制串起来）

- **填一半退出**：没有退出请求？没关系，第 3 步每轮都自动存档了。重进 App → `POST /sessions` → 服务端按活跃索引找到 thread_id → `get_state` 恢复黑板 → 重放消息，界面回到上次那一步。
- **确认单**：confirm 节点 interrupt 挂起。点"确认提交" → `POST /submit` → `Command(resume)` → submit 节点带 order_key 幂等建单 → DONE，黑板归档 MySQL，抽屉里存回收款人。
- **在确认单上改字段**：不是前端偷偷改——带新值 resume 回 extract，重新过闸写槽，再回确认单。改内容和改流程是两码事。

## 六、POC 三验证是什么、为什么排最前

| POC | 验什么 | 不过怎么办 |
|---|---|---|
| Checkpointer TTL | 检查点能不能配 7 天过期（我们要"草稿保留 7 天"） | 每日清理任务全托管，成本 +0.5 人天 |
| interrupt ↔ SSE | 确认单挂起时 SSE 流正常收尾、提交后 result 正常推出 | confirm 退化为普通节点自管提交，+0.5 人天 |
| 流式事件 | 节点产出 → 卡片消息的映射稳定不漏 | 降级为节点结束后一次性推送 |

排最前是因为它们决定落地细节怎么写——所以放在 11.5~11.6 动手第一件事。

## 七、FAQ

**Q1 LangGraph 和 LangChain 什么关系？**
一家出的。LangChain 是工具箱（封 LLM 调用），LangGraph 是编排框架（流程+存档+中断）。我们两个都用：LangChain 封模型，LangGraph 当引擎。

**Q2 以前的状态机去哪了？**
没消失，换了单位。以前"每个业务 12 个状态"写死在代码里；现在全业务一张通用图，"问到哪了"变成了黑板上的议程数据——状态从流程代码降维成了数据。

**Q3 为什么点选 0 调用 LLM？**
点卡片时用户意图是明确的（选了什么就是什么），不需要理解，直接写槽位；只有打字才需要 LLM"听懂"。成本就是这么控住的。

**Q4 子表多行数据放哪？**
State 里一个 `rows` 列表，每行是几个槽位的小模板实例；行卡片每次操作一行，确认一行定稿一行。

**Q4.5 Checkpointer 保存了字段，用户聊天内容会保存吗？**
会。检查点存的是**整个 State 的快照**，messages（对话消息通道）就在 State 里——用户每句打字、每个点选、服务端下发的每张卡片都追加在这个通道上，每步自动存档。断线重连/重进会话时把整段对话重放还原，用的就是它；extract 给 LLM 的上下文也从这取。注意两点：服务端卡片消息也要主动 append 进通道（否则重放缺半边对话）；附件本体不进快照，只存 media_id。

**Q5 换模型要动引擎吗？**
不用。模型调用全收口在 LLMGateway 一个类，换型改配置；这就是"LLM-XXX 待定"敢写进方案的原因。

**Q6 图/框架本身挂了怎么办？**
运行时异常走 fallback 节点同款降级——卡片向导（0 LLM）+ 引导回老表单，填报永远有路可走。
