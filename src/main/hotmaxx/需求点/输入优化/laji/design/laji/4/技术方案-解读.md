## 一、一句话读懂

**引擎不自研了，直接用 LangGraph；业务不做进代码了，全部装进"技能包"；报修是第一个技能包，报销用完整设计证明这张架子装得下复杂业务。**

## 二、四句核心设计

1. **LLM 只干一件事**：每条打字消息做一次"联合抽取"（听懂意图+抽出字段+给候选）——点选零调用，话术全是模板，成本可控。
2. **LangGraph 管流程**：一张固定的"通用采集图"（带出→抽取→校验→路由→追问→确认→提交），缺什么问什么。
3. **技能包定义业务**：一个业务=一份"字段说明书"（schema）+字典+话术+工具+钩子。报修一份、报销一份，core 零改动。
4. **人负责确认**：AI 预填、确认单点选提交才入库——interrupt() 原生挂起，提交接口恢复。

## 三、比喻

- **通用图+技能包 vs 每业务一张图**：方案一是"一套报税软件"（问卷引擎+每年换税率表），方案二是"每个税表手写一个程序"。表会越来越多，程序不该越写越多。
- **Checkpointer**：游戏自动存档。以前是我们自己写存档代码（每步手动存 Redis），现在是引擎自带的——走到哪存到哪，退出重进就是"继续游戏"。
- **interrupt()**：客服转人工。图跑到确认单这一步自动挂起等人，用户点"提交"才继续——这个"挂起等人"以前要自己做状态管理，现在框架原生。
- **槽位类型系统**：乐高接口。部门树、子表、字段组这些"复杂控件"做成标准件后，下一个业务直接拼。

|---|---|
| 像 demo，手搓多 | 手搓四件（状态机/快照/恢复/确认流程）全部退役换 LangGraph 原生；剩下的"手搓"是话术库、卡片协议、防幻觉闸——那是产品资产，不是轮子 |

## 五、选用 LangGraph 的账（换来什么 / 付出什么）

| | 内容 |
|---|---|
| **换来** | ① 图编排（条件边=转移表、子图=业务逃生舱）② Checkpointer 断点存档（"先存再推"原生版，不用自己写）③ interrupt() 人机确认（确认单挂起/恢复原生支持）④ BaseStore 跨会话记忆（收款人四件套按人存）⑤ 流式事件（astream_events 直对接 SSE）⑥ 生态：图可视化导出、时间旅行调试、多 Agent supervisor |
| **付出** | ① 学习曲线 1~2 人天（概念就六个：State/节点/条件边/Checkpointer/interrupt/BaseStore，教学篇半天能看完）② 版本迭代快 → requirements 锁版本，升级走评审 ③ 深层排障要进框架源码（缓解：社区活跃 + 我们只用到稳定子集）④ Checkpointer 的 TTL 语义要 POC 验证（不过就上清理任务，成本很小） |

一句话：付的是一次性的学习成本，换的是"存档/恢复/中断/记忆/流式"这五样永远不用自己写、不用自己修。

## 七、评审问答（备答）

**Q1 之前论证自研状态机够用，现在为什么又换？**
不是论证错，是前提变了。单业务线性流程，自研确实够；但评审定调本次主要目的是搭架子——报销的部门树、子表、字段组、记忆、人机中断，每一样自研都要重新造，LangGraph 全有原生。且现在代码只有骨架，是替换成本最低的时刻。

**Q2 LangGraph 和 LangChain 什么关系？为什么不是"用 LangChain"就行？**
LangChain 是工具箱（封 LLM 调用、Prompt），我们继续用它封 LLM；LangGraph 是 LangChain 家的编排框架（流程+存档+中断）。缺的从来不是 LLM 封装，是编排——所以换的是 LangGraph。

**Q3 换引擎，前端要改吗？**
零改动。六接口、卡片协议、SSE 格式、URL 全部不变；引擎是容器内换血。报销新增 4 种卡片形态是**报销前端页**的新增，不是改造。

**Q4 手搓还剩什么？为什么它们 OK？**
话术模板库（产品口径资产）、卡片消息协议（前端契约）、防幻觉闸（业务规则）、槽位类型系统（架子的标准件）。它们是"业务资产"，换框架也要带着走；真正通用的轮子（流程/存档/恢复/中断/记忆/流式）已全部交给框架。

**Q5 报销接入要几天？凭什么说第三个业务只要 3~4 天？**
报销 4~5 人天（字段说明书 0.5 + 字典树接口 1 + 话术卡片 1 + 提交工具 1 + 剧本联调 1）。槽位类型 10 类覆盖后，下个表单业务大概率只是"已知类型的重新组合"——只花对齐和联调的时间。

**Q6 子表（费用明细）在对话里怎么填？体验不崩吗？**
三个层次：一句话抽多行（"房租5000电费1200"→两行草稿）→ 行卡片逐行确认/修改 → 想手填就"加一行"进表单式行编辑。AI 先干粗活、人只做确认，和单字段一个哲学。行数上限 10 是表单规则，钩子兜住。

**Q7 Checkpointer 比自研快照好在哪？风险呢？**
好：每步自动存（不用记得"先存再推"）、恢复/重放/时间旅行原生、代码量直接归零。风险：TTL 语义要 POC 验证（不行就每日清理任务托管，成本很小）——已列进 POC 三验证，不通过有降级路径。

**Q8 部门树那么深，AI 能选对吗？选错怎么办？**
AI 不"选"，只"提名"：抽取部门名→树里模糊匹配出 Top3 条完整路径→用户点选确认，和报修类别一个防幻觉模式。匹配不到就下发财搜索卡。选错的唯一入口是用户自己点错的路径，确认单上还能改。

**Q9 收款人四件套每次都要填吗？**
不用。首次填过存进跨会话记忆（按人），下次直接"用上次的/改"二选。这是报销最大的体验痛点，也是记忆能力的第一个应用场景；报修的常用联系人同理复用。

**Q10 为什么不用 Dify / Coze 搭这个架子？**
口径不变：卡片消息协议在低代码平台事件流里没有对应物（要双重映射）、降级/配额/埋点要外挂网关变成四层架构、SaaS 数据出域/私有化太重。且"技能包+通用图"这种架子恰好是低代码平台做不了的——它们编排的是"流程"，我们抽象的是"字段类型"。

**Q11 乱输入怎么处理？（注入/闲聊/报别家店）**
沿用 design/3 口径：意图六类枚举 + 字段白名单（schema 外一律丢弃拉回）+ 用户输入三引号包裹当数据 + 连续 2~3 轮失败降级卡片向导。图上的实现就是 route 条件边，规则没变只是搬了家。

**Q12 多 Agent 终态怎么走？**
技能包=未来子 Agent 的技能定义；查询智能体（报修/报销闭环）来的时候，就是新增技能包+挂子图；supervisor 统一调度用 LangGraph 原生方案，同一条技术栈一路走到底，不需要二次迁移。
