# 会话管理与草稿恢复（检查点版）

> 一句话：**会话即草稿**——LangGraph Checkpointer 在每个节点执行后自动把整个 State（槽位 + 议程 + 全部对话消息）落 Redis；无论哪种退出（杀 App、断网、主动退出），进度天然不丢，回来一个请求就能接着填。
> 接口报文见《[接口文档.md](接口文档.md)》｜State 结构见《[LangGraph落地设计.md](LangGraph落地设计.md)》

---

## 一、管理过程（草稿的一生）

1. **出生**：`POST /agent/{skill}/v1/sessions`——服务端先查 `rp:active:{uid}`（后续技能包同构，如报销 `ex:active:{uid}`）有无活跃会话，有则**复用**（`is_resumed=true`，前端弹「继续上次填报」），无则新建 thread 并跑 `load_context` 带出字段，首个检查点自动落盘。
2. **成长**：填报中每次用户消息触发一轮图执行，**每个节点执行完框架自动存档**——不需要业务代码记得保存，也不存在"忘了存"的窗口。轮末另有一步：本轮消息（用户 + 服务端卡片）**同步批量 upsert 入 MySQL 消息表**，然后裁剪 State 窗口至最近 10 轮（规则见 §五）。
3. **三种终态**：
   - **DONE**：提交成功（order_key 幂等建单）→ 会话摘要归档 MySQL（消息早已逐轮在库）→ 删除检查点 + 活跃索引（后续技能包的收尾动作同理挂在这里）。
   - **EXITED-keep**：主动退出选「保存」，检查点保留 7 天，重进下发「继续上次填报」卡片（draft_resume 埋点）。
   - **EXITED-abandon**：选「放弃」，标记废弃，保留 24h 供排查后清理。
4. **过期**：检查点 TTL 到期自动清除 + 每日清理任务兜底；超期重进静默开新会话，用户无感知。

**为什么「错误退出零处理」**：保存时机是「每个节点后自动」而不是「退出时」——杀 App、闪退、断网根本来不及发请求，但检查点早就是最新的。

**并发说明（已知简化）**：同一会话不做多端并发控制——双端同时编辑时后写覆盖先写；单用户单会话场景下概率极低，防重复提交由 order_key 幂等保证。

## 二、数据留存（存哪、存什么、留多久）

| 存储 | Key / 表 | 内容 | 留存策略 |
|---|---|---|---|
| Redis | LangGraph 检查点（`thread_id = session_id`） | **整个 State**：槽位（含 source）、议程、上下文、**全部对话消息**（用户输入与服务端卡片都追加，断线重放靠它）、子表行 | TTL 7 天（配置 + 清理任务兜底 ❗POC）；keep 会话保留，活跃会话滑动续期 |
| Redis | `rp:active:{uid}` / `ex:active:{uid}` | **活跃会话索引**：指向该用户当前 session_id | 建会话写入；DONE / abandon / 过期清除；重进复用靠它，不依赖前端本地 |
| Redis | `quota:{uid}:{yyyyMMdd}` | 单人单天 LLM 调用 / token 配额 | 当日 24:00 自动过期 |
| MySQL | 消息表 `agent_message_archive` | **全量对话消息，每轮批量 upsert**；(session_id, seq) 唯一键幂等 | 长期：审计 / 回放 / 复原数据源 |
| MySQL | 会话归档表 | 终态会话摘要一行（context/slots/meta JSON；消息已在消息表不重复归档） | 长期，对账与回放 |
| MySQL | 埋点明细 | 埋点事件（含 skill 维度） | 长期，指标计算 |
| 前端 | localStorage（传统表单草稿） | 老表单字段值 | 与 AI 草稿不同空间，互不覆盖 |

要点：**session_id 从哪来、恢复靠什么**——建会话时服务端返回，前端可存一份作加速（刷新 / 断线重连直接 `GET /{id}`）；但**恢复不依赖本地**：重进统一 `POST /sessions`，服务端按活跃索引复用，换设备、清缓存都能续。照片本体在 OSS，检查点只存 media_id 引用；槽位带 `source`（system_default / ai_filled / user_edited）作审计留痕。

## 三、接口的关系（谁在什么时候动草稿）

| 接口 | 触发时机 | 草稿动作 | 数据变化 |
|---|---|---|---|
| `POST /sessions` | 进 AI 入口（**统一恢复入口**） | 查活跃索引：有 → 复用（get_state 重放消息）；无 → 新建 + 首轮存档 | thread 创建 / 复用，TTL 起算 |
| `POST /messages` | 每条用户消息 | 一轮图执行，节点逐个自动存档 | slots / rows / messages 更新，TTL 续期 |
| `POST /upload` | 附件上传完成 | media_ids 并入槽位后存档 | 同上 |
| `GET /{id}` | 会话内刷新 / SSE 断线重连 | 只读（get_state） | 不改数据，返回快照 + 消息重放 |
| `POST /submit` | 确认单点提交 | 恢复 interrupt 挂起 → submit 节点 | 成功 → 检查点删除、MySQL 归档、记忆写回 |
| `POST /exit` | 主动退出弹窗选择 | keep：检查点保留 7 天；abandon：标记废弃 | status=EXITED |

两处防坑：消息不产生槽位变化时（如闲聊拉回）State 只追加消息、议程不动，同样存档；配额 Key 与检查点完全独立，超限降级不影响已有草稿。

## 四、三个典型场景走查

**场景 1 · 错误退出**：填到照片步骤 App 被杀——没有任何退出请求，但检查点停在 `focus: photos`；重进 AI 入口，服务端按活跃索引复用会话并**重放消息**，界面直接回到拍照那一步，已答内容全部回显。零 LLM 调用。

**场景 2 · 主动退出 keep**：点返回 → 三选项弹窗 → 选「保存草稿退出」；检查点保留 7 天；期间再进入口，检测到 keep 会话 → 下发「继续上次填报」卡片（draft_resume 埋点）→ 点选即恢复。

**场景 3 · 7 天过期**：keep 后一直没回来，TTL 到期自动清除；重进时无活跃会话，前端静默开新会话——用户感知就是「新的一次填报」，没有报错。

## 五、消息持久化与复原（窗口 + 入库）

**四条规则**（详见 State设计.md 决策 9）：先入库再改 State；(session_id, seq) 唯一键 + upsert 后写覆盖；裁剪只在轮末（窗口=最近 10 轮）；seq 用 meta.seq_counter 生成。

**复原流程（两源拼接，前端无感）**：

```
POST /sessions → 查活跃索引命中
 → get_state：槽位 + 议程 + focus + 窗口尾巴（最近 10 轮）
 → MySQL 查 seq < 窗口首条 的全部消息（按 seq）
 → 拼接下发：老消息（库）+ 窗口（Redis）+ 按焦点渲染当前步骤
```

**边界行为**：keep 7 天内回来——完整复原；**TTL 过期后回来**——草稿（槽位/议程）按设计失效开新会话，但消息在库永久可查（「上次对话记录还在，重新填一次」）。复原时顺带对账：DB 该会话 max(seq) 落后于窗口最早 seq 就现场补写（防御写入遗漏）。

**清理联动**：每日清理任务删过期检查点**之前**，确认该会话消息已全量在库（规则①保证）；DONE 归档只剩会话摘要一行。

**演进项（放量后）**：同步批量 → 异步批量（进程内写器攒批 flush），配裁剪同步门槛 + 每日对账；主路径不再等待 DB。
