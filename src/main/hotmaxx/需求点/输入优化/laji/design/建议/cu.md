# design/3 评审意见

评审对象：`design/3` 全部 13 个文件。对照：`prd/final4`（FA.md、产品交互流程图、交互原型）。  
用途：11.5 技术方案过审。本文只评判和补口径，不另起一套架构。

## 结论

方向可以通过。状态机管流程、模型只做联合抽取、话术用模板、工具用进程内接口、部署先做一个 Python 容器，这些选择和 final4 的约束是对齐的，也够两周落地。

这一包现在不能原样过审。主方案 §13.1、§14 是空的，节号跳过 11；解读、接口、状态机、泳道图对同一件事有两套说法。评审若只翻《技术方案.md》，会看到一份没写完的稿；若三份一起翻，会抓住互相矛盾的承诺。

过审前要收成一句话，并写进主方案，不要只在口头解释：

> 本期新建一个 Agent 进程，经现有网关接入。模型不决定下一步，也不调用工具。明道云只有一把服务端钥匙。传统表单和历史记录是否已在用这把钥匙，会上三选一，选完写死。

选不出来之前，开篇不要同时说「省账号费已经靠这个服务完成」和「记录页、表单页保持原样」。

## 阻塞项

下面 8 条，会前改文档或会上写进决议。不处理的话，评审通过了也无法按同一份稿施工。

### 1. 单账号降本和「记录页保持原样」不能同时成立

final4 的目标是：唯一明道云账号只在服务端，录入和查询都走它，店与店靠服务端按门店过滤。  
《技术方案-解读》写的是：表单页、记录页、明道云保持原样；查询不建工具，因为记录页已有接口。

若记录页今天仍用门店账号，或查的不是 Agent 即将写入的那张工作表，会出现两件事：账号费降不下来；用户在对话里提交成功，记录页看不到这张单。

会上只选一个，写进主方案 §5 后面：

| 选择 | 含义 | 本期工具 |
|---|---|---|
| A. 查询和传统表单已经在别的服务里用同一把钥匙，且按门店过滤 | 说出那个服务名、接口、账号放在哪。验收标准加上「AI 提交后，记录页能打开同一单号」 | 维持 4 个 |
| B. 证明不了 | Agent 补 `list_repairs`、`get_repair`。过滤条件由服务端写成登录门店，请求里的门店号不参与过滤。传统表单提交也走 `create_repair_order` | 6 个 |
| C. 本期只做 AI 录入体验 | 降本和查询隔离明确写到下期。开篇删掉「省账号费的核心已经在这个问询台完成」 | 维持 4 个 |

没有证据时按 B。A 只有在接口负责人当场指认现网路径时成立。C 可以过审，但不能再把降本当本期结果。

### 2. 建单门店不能信客户端

接口文档 `POST /api/sessions` 允许 body 带 `store_no`，说明是「督导多店时显式指定」。final4 没有督导代报多家店，越权报别家店要求拉回。

本期规则写成：

- 门店编号、门店名称只来自网关注入的登录身份，再由 `get_user_context` 核对。
- body 里的 `store_no` 忽略。
- 模型输出里的门店字段丢弃。
- `create_repair_order` 组包时再次覆盖门店和报修日期。日期用服务器 `Asia/Shanghai` 的当天，不读档案、不读模型。
- 活跃草稿键用 `rp:active:{uid}:{store_no}`。即使用户以后有多店，也不会续到另一家店的草稿上。

督导多店若业务真要，单独立项：档案返回「可操作门店列表」，编号必须落在列表内。不要在这个接口上先开一个口子。

### 3. 失败和降级有四套口径

| 出处 | 说法 |
|---|---|
| 主方案状态机 | 识别失败进 FALLBACK；LLM 不可用进卡片向导 |
| 《防幻觉》 | 连续 2～3 轮失败：全量点选 → 卡片向导 → 传统表单 |
| 《llm网关》 | 超时进 FALLBACK；不可用进卡片或表单；会话超过 6 次进卡片 |
| 《解读》Q3、Q6 | 明道云失败进待发表，自动重试 3 次，再转人工 |

待发表、重试 3 次在架构、状态机、接口、Redis 结构里都不存在。这是解读多出来的一个子系统。final4 的兜底是「稍后再试 + 客服电话」，草稿还在。

评审稿统一成下面这张表，解读 Q3/Q6 改成同一张表。`fail_count` 放进 Redis 快照。

| 条件 | 行为 | 计数 |
|---|---|---|
| 卡片、点选、上传、提交 | 不调用模型 | 不动 |
| 文本回合 JSON 失败或超时（含已有的 1 次重试） | 还没有类别：FALLBACK 全量点选。已有类别：停在当前状态，模板说没听清 | +1 |
| 候选被白名单滤空 | 同上 | +1 |
| 闲聊、问进度、报别店、注入 | 模板拉回一句，槽位不变 | +1 |
| 点选成功，或文本确实改动了允许修改的槽位 | 继续当前空缺 | 归零 |
| 计数到 3 | 下发高频卡片和「可切回传统表单」。会话不结束，点卡片仍可继续 | 下发后归零 |
| 进程起来但模型不可用 | 建会话仍然成功。卡片路径不依赖模型。只有 `text` 走上一行 | — |
| 明道云提交失败 | 状态留在 CONFIRM，Redis 不删。返回错误和配置里的客服电话。用户再点提交，仍用同一个 `order_key` | — |
| 本会话模型调用超过 6 次 | 拒绝新的 `text`，点选不受影响 | — |

不建待发表，不自动重试 3 次。

### 4. 类别重选会把后半段再问一遍

状态机图上是 `CONFIRM → PHOTO`，PHOTO 的出口只有 EXPECT。主方案又写「连带照片与描述，回跳重校验」。按图实现，改个类别会把期望上门、影响营业、电话再走一遍。这和约束「不能重来」冲突。照片清单变化只说明要复查照片，不说明要重排已确认的选项。

统一成：

- 确认单上重选类别，只重开枚举；选完回到 CONFIRM。
- 新类别的拍摄清单不满足：停在确认单，`missing` 标照片，不进入 EXPECT。
- 描述的 `source` 是模板时，用新类别名重算「子类，详见现场照片」。`source` 是 `ai_filled` 或 `user_edited` 时保留原文。
- 已选的上门、影响营业、电话、报修人保留。

状态机图上的 `CONFIRM --> PHOTO` 改成 `CONFIRM --> A_ENUM`（或一条不离开 CONFIRM 的 `recat` 事件）。

### 5. 模型能把「必须人点」的字段直接写进槽位

红线是类别必须点选，影响营业是预判后点选确认。  
提示词 schema 却让模型输出 `slots.category`、`slots.impact`。《防幻觉》的 `ALLOWED_FIELDS` 又包含 `category`。校验通过之后若状态机照单写入，红线就破了。

采纳规则写成代码注释级别的一句：

- `category_candidates` 只用来画 `enum_card`。`slots` 里的类别丢弃。类别只来自 `card` 和 `enum_pick`。
- `impact_business` 在点选前只影响 `seg_card` 的预选和文案，不写入最终槽位。
- `detail` 可以在抽取后写入，确认单可改。
- `expect_visit` 不接受模型填写，避免跳过二选一。
- 提示词里的 `clarify` 删掉。下一步问什么只由状态机决定。这个字段一旦被前端展示，模板化就不成立，也多一条把模型文字直接给用户的通道。

### 6. 接口真值和图不一致，提交请求体是空的

| 动作 | 《接口文档》 | 两张泳道图 |
|---|---|---|
| 建会话 | JSON，带 `messages` | SSE |
| 提交 | JSON，`order_no` | SSE `result` |
| 上传 | 返回 `media_ids`，再发 `upload_done` | 会话文又写上传接口自己并入槽位 |

以接口文档为准，改图，不要反过来。理由：建会话和提交都是一次短请求；只有 `POST /messages` 需要 SSE（`typing` → 若干 `message` → `done`，然后关掉）。

网关那句「response-timeout 要大于 SSE 会话时长」会导成错误配置。这里的会话若被理解成用户填单的十几分钟，超时会被放得很大，占住连接。实际一条 SSE 只活一个回合：模型 8 秒超时再重试 1 次，大约 16 秒。网关单回合约 60 秒，并关掉对该路由的响应缓冲。心跳 15 秒只在这一次流里面需要。

`POST /submit` 的请求表是空的。写明：body 为空；`order_key` 由服务端取 `session_id`，前端不传。

上传只做一件事：`POST /upload` 存对象并返回 id，不改会话。`upload_done` 才把 id 并入 `photo_ids`，按 id 去重。两处都追加会重复计数。

本期附件只收图片。原型是照片、单张 3MB。接口里的 `video/*` 和 10MB 超出 final4，也会先撞上明道云附件限制。张数至少 1，界面文案仍建议两张；上限 5 张可以保留。

### 7. 快照存的是掩码手机号，恢复协议和产品文案不一致

快照示例里电话是 `138****1234`，而且放在 `slots.slot_meta` 里。建单需要明文。掩码只出现在给前端的响应和给模型的快照里。Redis 里的号码是明文，日志和 MySQL 埋点里是掩码。

恢复和 final4 不一致。《会话管理》场景 1 是重进后直接回到拍照；场景 2 又是弹「继续上次」。final4 是重进提示继续，并提供继续 / 重新开始。

统一成：

- `POST /api/sessions` 发现活跃草稿：`is_resumed=true`，`messages` 只有一张恢复卡（继续、重新开始），不把 PHOTO 界面直接推下来。
- 继续：再要一次当前状态的界面（沿用 `GET /api/sessions/{id}` 即可）。
- 重新开始：服务端按 abandon 处理再新建。前端不要自己清本地假装新会话。
- 杀进程、断网、点「保存草稿」都走这张卡。TTL 从最后一次保存起 7 天。删掉「活跃会话永不过期」。
- 恢复的是状态和槽位，按当前状态生成这一步的界面。不重放历史气泡。快照里不必存全量消息。`GET` 文案里的「消息重放」改成「按状态生成当前步」。
- 终态归档到 MySQL 的是槽位、状态轨迹、单号，供对账。不承诺过程回放。
- Redis 要开持久化。只靠内存的话，重启等于全部草稿丢失，而 MySQL 只在终态才有数据。

### 8. 主方案像没写完，解读指向不存在的章节

《技术方案.md》没有 §11；§13.1 的「必须做 / 先不做」是空标题；§14 TODO 是空的；里程碑三个 `11.xx`。  
《技术方案-解读》开头链接到 `技术方案5.md`；写「见主方案 §3.2 关键决策表」，主方案 §3.2 只是指向演进规划的一个链接。解读里的 11.9 / 11.11 / 11.13 / 11.16 和人天，主方案里没有。

### 幂等（替换「待发表重试 3 次」）

1. `order_key = session_id`，服务端生成。
2. 提交前查 MySQL 归档。这个键已有单号则直接返回，不请求明道云。
3. 明道云若没有幂等参数：工作表加一个外部单号字段，值为 `order_key`。创建前按该字段查，查到则返回原单，查不到再创建。11.11 前用测试环境证明「连点两次只有一单」。证明不了就不要承诺幂等。
4. 创建成功后写归档，再删 Redis 活跃键。进程死在「明道云已成功、本地未归档」时，靠第 3 步查重补归档。
5. 失败停留 CONFIRM。错误码建议增加 `50201` 明道云失败，前端 toast 加客服电话。

### 埋点口径（替换「enum_first_pick = 准确率」）

`enum_first_pick` 如果只在用户点了第一项时才打，分母就没了，准确率算不出来。

自由描述路径每次点选类别打 `category_confirm`：`suggested[]`、`picked`、`hit_top1`、`hit_top3`。  
准确率 = A 路径 `hit_top1` 次数 / A 路径 `category_confirm` 次数。B 路径不进这个分母。Top3 命中率另算，不替代 final4 的「首选与最终确认是否一致」。

| 指标 | 怎么算 |
|---|---|
| 填报时长 | `session_start` 到 `submit_success` 的毫秒。放弃、切走不计入时长中位数，单独看 |
| 步数 | 改变了槽位的用户消息数。SSE 条数、模板气泡不算 |
| 完成成功率 | 有过至少一次用户操作的会话中，`submit_success` 的占比。`fail_count` 到 3、`submit_fail`、`switch_to_form` 算卡壳 |
| AI 渗透率 | 来源为 AI 的成功单 / 同一门店范围、同一时间窗口的全部成功单。传统表单也要能标来源。分母暂用「明道云总单量」时，写明工作表和门店过滤，避免把未灰度门店算进来 |
| 转老表单率 | 必须有事件。只靠用户自己按返回，服务端看不见。补一个客户端上报：`switch_to_form`，带 `state` |
| 放弃与续填 | `exit(abandon)` / 进入过的会话；`resume_continue` / `is_resumed=true` 的次数 |
| 查询模块使用度 | 可以仍由记录页埋点承担，但要写出现有事件名。写不出就本期不算，不要在表里留一个没有数据源的指标 |

事件公共字段：`session_id`、`store_no`、`uid`、`state`、`branch`、`morph`、表单定义或字典版本。对话原文和明文手机号不进埋点表。

## 其他维度

**架构。** 一个新部署单元这个判断对，能回答「要不要把现有网关复制一份」：不要。现有网关做路由和鉴权，Agent 解析已经注入的用户头。补上图里的网关节点即可。Agent 只接受来自网关的流量，避免有人绕过网关伪造 `HTM-HEADER`。

**和后续业务。** 报销要复用的是转移表机制、消息 type、ToolProvider、草稿和埋点，不是把报修状态名配成报销。主方案写「目标只加配置（字典/转移表/Prompt/工具）」偏满。转移表和校验规则本期会写成代码。会上改成：协议和端口复用；新业务加一张转移表和一组工具，不改引擎循环。这仍然符合「不改框架」。多 Agent 的路由器放在进入具体状态机之前，不要把报修状态机改成万能循环。

**安全。** 纵深防御的结构可以讲。补三句具体规则：建单覆盖门店、类别不采纳模型槽位、埋点和提示词用掩码电话。三引号、JSON mode 保持为辅助。注入样本继续用《防幻觉》第六节那张表做单测。

**数据。** 会话真源是 Redis，终态才进 MySQL，这个划分清楚。补持久化、明文电话、`fail_count`、`order_key`。不要把 `slot_meta` 和业务槽位混在一个对象里。

**模型。** 换型只改 `base_url` 和模型名，这个方向对。不要在评审里把 LangChain 说成这些能力都已白捡到可上线：各家 JSON mode 严格度不同，所以才需要白名单和失败计数。样本代码收成一种写法。字典注入只放编码、名称、别名，不要把拍摄清单整段塞进提示词。

**前端契约。** 10 种服务端消息和 6 种用户消息够接 H5。补 `switch_to_form` 的上报方式，以及恢复卡的两种选择。确认单 `editable` 按槽位表，不要前端自己把 10 个字段都做成可点。

**运维。** 方案没写这个进程谁发布、日志进哪、告警谁看。会上用一句答完即可：容器走现有发布，日志走 stdout，`GET /health` 只表示进程活着，不探测模型、不探测明道云。模型不可用由对话降级处理，不能让健康检查把实例摘掉，否则卡片路径一起没了。

**测试。** 《防幻觉》的表驱动样本保留。再加验收 10 条里的 2、4、5、6、9，用假的 ToolProvider 就能测，不必等明道云。明道云只留探针和一条联调用例。
