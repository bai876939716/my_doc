## 1. 编排方案对比（核心决策）

| 编排候选 | 一句话定位 | 核心原因 | 判定 |
|---|---|---|---|
| 纯 LLM 自主对话 | 提示词 + 工具，模型自己决定下一步 | 每轮流程都是 LLM 决策：跳步漏问不可控、枚举编造无法根除——直接冲击"选错即驳回"的业务底线 | ✗ |
| 纯 Runnable 串联 | 一条链跑到底，状态藏在消息里 | 链式单向无状态：中途改字段 = 重跑整条链、断点续填做不出；只适合一次性极简表单 | ✗ |
| **自研状态机 + LangChain** | 转移表驱动流程，LLM 只做理解抽取 | 流程白盒确定性（转移表可单测可回放）+ 枚举白名单防幻觉；全流程仅 2 处 LLM 调用，成本延迟最优、换模型只改两处；引擎 2 人天工期稳 | ✓ **本期采用** |
| LangGraph | 节点 = 状态、条件边 = 转移、Checkpoint 内置 | 能力最强，但学习曲线挤压 8 个工作日工期，且单业务线性流程吃不到图编排红利——留作终态：状态即节点候选、工具已 MCP 化，触发信号出现时迁移约 3~5 人天 | ◐ 终态 |
| Dify | 低代码画布平台 | chatflow 线性 DAG 回跳靠重跑；8 种卡片消息在平台事件流无对应物、需双重映射；配额/降级/埋点仍要外挂网关——四层架构 + 全家桶运维 | ✗（留作知识问答场景） |
| Coze | 字节 Agent 平台（SaaS / Studio） | SaaS 版员工/门店数据出域、边界不过关；Studio 私有化组件太重装不下；编排问题同 Dify | ✗ |

补充：E/F 平台路线被否不是"快不快"的问题，而是编排确定性、卡片协议、工程面、数据边界四重硬伤。逐维度深对比见《技术选型与方案设计对比.md》§2。
## 1. 编排方案对比（核心决策）

| 维度 | A 纯 LLM 自主对话 | B 纯 Runnable 串联 | **C 自研状态机 + LangChain** | D LangGraph | E Dify | F Coze |
|---|---|---|---|---|---|---|
| 流程可控（不跳步漏问） | ✗ 每轮 LLM 决策 | △ 链式单向 | ✅ 转移表白盒 | ✅ 图定义 | △ 画布 DSL | △ 画布 DSL |
| 枚举防幻觉（选错=驳回） | ✗ 编造无法根除 | △ 校验外挂 | ✅ 白名单+强制点选 | ✅ 同 C | △ 校验口径不可控 | △ 同左 |
| 中途改字段 / 回跳 | ✗ | ✗ 重跑链 | ✅ 转移表加边 | ✅ 条件边原生 | △ 靠重跑分支 | △ 同左 |
| 断点续填 | ✗ | ✗ | ✅ Redis 快照 | ✅ Checkpoint | △ 只恢复上下文 | △ 同左 |
| LLM 调用次数（成本/延迟） | 每轮 | 每步 | **全流程仅 2 处** | 按节点 | 按节点 | 按节点 |
| 数据边界 / 运维 | ✅ | ✅ | ✅ / 低 | ✅ / 低 | △ / 高（全家桶） | ✗ SaaS 出域；Studio 重 |
| 多 Agent 演进 | ✗ | ✗ | △ 迁移已预留 | ✅ 原生 supervisor | △ 较浅 | △ 较浅 |

**选择：C。** 核心原因三条：① 报修是字段固定的表单流程，驳回率是业务底线，流程必须确定性——LLM 只做理解抽取、不做流程决策；② 全流程仅 2 处 LLM 调用点，成本延迟最优，换模型只改两处；③ 终态迁移已铺好：状态即 LangGraph 节点候选、工具全 MCP 化，触发信号出现（≥2 业务 / 状态>20 / 并行子 Agent）时只搬编排不搬资产，预估 3~5 人天。

## 2. 技术栈选型（现定）

| 层 | 选型 | 一句话理由 |
|---|---|---|
| Agent 服务 | Python 3.11 + FastAPI | 原生 async + 流式 + 自动 OpenAPI 文档 |
| 编排 | 自研状态机（11 状态转移表）+ LangChain（仅封装 LLM 调用） | 流程确定性；LLM 不做流程决策 |
| 模型 | **LLM-XXX（待定）** | 四维评测（识别准确率/抽取质量/成本/速度），11.9 前定 |
| H5 ↔ Agent 通信 | REST + SSE（fetch POST + 流式响应） | 消息带 body、回复流式、断线快照重放 |
| Agent ↔ MCP 通信 | MCP **Streamable HTTP**（fastmcp + 官方 SDK client） | 单端点 /mcp、独立进程跨机部署、跨业务复用 |
| 工具层 | MCP Server（独立进程，7 工具） | 与框架解耦，报销 / 多 Agent 直接复用 |
| 存储 | Redis（会话/草稿/配额，TTL 7 天）+ MySQL（归档/埋点） | TTL 原生 + 亚毫秒 |
| 前端 | App 内 H5 聊天页 | 消息协议与原型一一对应 |

## 5. 对话状态机（11 状态）

> 📊 [diagrams/02-对话状态机图.puml](../../../diagrams/02-对话状态机图.puml)

| 状态 | 职责要点 | LLM | 出口 |
|---|---|---|---|
| INIT | 调工具带出字段，下发状态条+Top6 | — | 文字→A_WAIT；卡片→B_LOCK |
| A_WAIT | 自由描述→类别识别 | ✓ 候选 Top3+三要素 | 有效→A_ENUM；失败→FALLBACK |
| A_ENUM | 枚举单选卡（AI 预选首位，**必须点选**） | — | 点选→DETAIL |
| B_LOCK | 卡片即锁定类别 | — | →DETAIL |
| DETAIL | 三要素抽取润色，缺则追问一轮 | ✓ | 齐→PHOTO；缺→追问后带占位符 |
| PHOTO | 按类别清单校验照片 | — | 过→CONTACT；缺→补拍 |
| CONTACT | 默认本人，可改店长/他人 | — | →CONFIRM |
| CONFIRM | 13 字段确认单，全部 ✏️ 可改 | — | 提交→DONE；重选类别→PHOTO 重校验 |
| DONE | 出单号+状态，推埋点 | — | 终态 |
| EXITED | 主动退出终态（任意非终态可触发） | — | keep 草稿 7 天可续 / abandon 废弃 |
| FALLBACK | 全量类别树点选；LLM 不可用降级卡片向导 | — | 选定→DETAIL；切老表单→终态 |

两分支差异只在入口（B_LOCK 免确认、A_ENUM 必须点选），汇合后完全一致。改字段分层：带出字段/联系人全程可改（字段级更新不动状态）；回头改收敛到确认单；改类别因联动拍摄清单，走 CONFIRM→PHOTO 回跳边。

## 6. Prompt 工程（全流程仅 2 处调用）

**系统提示词（状态机注入到每次调用）**：角色 = 好特卖门店报修填报助手，引导店员最短路径完成报修单；采集范围只限表单内字段（类别 / 详情三要素 / 联系人 / 手机号）；禁止——问表单外信息、编造字典外枚举、用户确认前生成提交动作、一轮追问多个问题；口语简短、每次只处理一件事；输出按 schema 返回 JSON。

| 调用点 | 任务 | 输出 Schema |
|---|---|---|
| ① A_WAIT 类别识别 | 从描述映射字典枚举，只准输出字典内值（字典由 `get_category_dict` 注入） | `{"candidates":[{"name":"…"}]}` 取 Top3 |
| ② DETAIL 三要素抽取 | 抽取表现/原因/后果并润色短句；口语原意优先、不添加未提及事实；缺失返 null 并生成一句仅针对缺失要素的追问 | `{"表现":…,"原因":…,"后果":…,"追问":…}` |

Prompt 版本化管理（改动走版本号）；few-shot 示例与完整原文见《设备报修-AI填报Agent技术实现方案.md》§4，联调时随真实字典迭代。

## 7. 防幻觉与结构化输出

| 环节 | 机制 |
|---|---|
| 输出格式 | JSON mode；解析失败重试 1 次，再失败进降级 |
| 枚举校验 | 候选逐个与字典白名单比对，非法丢弃；丢弃后为空→FALLBACK |
| 候选排序 | Top3 首位预选仅影响卡片顺序——**A 分支必须用户点选才入库** |
| 详情校验 | 三要素 schema 校验，润色结果与原文一并展示可改 |
| 提交校验 | 前端+服务端双重校验 13 字段必填，缺一不进 DONE |

## 8. 会话草稿与退出恢复

**会话即草稿**：每次状态变更先 `draft_save` 再推送（Redis 单 Key JSON，TTL 7 天滑动续期，ver 乐观锁防并发）；错误退出（杀 App/断网）零特殊处理，重进 `GET /sessions/{id}` 快照重放恢复到上次状态。**主动退出**：前端弹「继续填写 / 保存退出 / 放弃」，keep 再存快照进 EXITED（重进下发「继续上次报修」卡片），abandon 标记废弃。与老表单草稿不同 Key 空间，互不覆盖。

## 9. 前后端接口

> 📄 完整定义（请求/响应 JSON、SSE 事件流、MCP JSON-RPC 报文）：[详细点/接口文档.md](../详细点/接口文档.md)

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/sessions` | POST | 建会话，返回 session_id + 首屏消息 |
| `/api/sessions/{id}/messages` | POST | 七种消息 type；响应 SSE 流（typing→message→done） |
| `/api/sessions/{id}/upload` | POST | multipart 附件 → media_ids |
| `/api/sessions/{id}` | GET | 恢复会话（断点续填/换端） |
| `/api/sessions/{id}/submit` | POST | CONFIRM 提交（ver 乐观锁），调 create_repair_order |
| `/api/sessions/{id}/exit` | POST | 主动退出，mode=keep（存草稿）或 abandon（废弃） |

服务端消息类型 8 种（text/quick_cards/enum_card/photo_guide/contact_confirm/confirm_card/result/system_tip），与原型组件一一对应。

## 10. 工程降级与成本控制

| 故障 | 处理 |
|---|---|
| LLM 超时（>8s） | 重试 1 次→提示稍后+Top6 卡片（纯规则可用） |
| LLM 整体不可用 | 降级卡片向导模式，不阻塞报修 |
| 识别/解析失败 | FALLBACK 全量点选 |
| 明道云提交失败 | 本地落待发表+定时重试 3 次→转人工 |
| SSE 断线 | GET 会话快照重放，消息不丢 |
| Redis 故障 | 降级内存会话，提交前强校验 |

成本限额（LLM 调用层统一拦截）：单人单天调用次数 + token 双限额（Redis 当日 Key）、单会话 6 次、全局日配额熔断；超限降级卡片向导。

## 11. 埋点清单

| 事件 | 支撑指标 |
