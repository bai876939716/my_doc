# 设备报修 · AI 填报 Agent 技术方案 v3


## 1. 实现方案对比

### 1.1 产品需求硬约束

方案好不好，先过这十条再说——前八条来自产品方案和原型，后两条是演进要求：

| # | 硬约束 | 说白了 |
|---|---|---|
| 1 | 11.16 端到端可验收 | 评审后只剩 8 个工作日，再好的方案做不完也白搭 |
| 2 | 流程可控，不跳步、不漏问 | 也不许问表单以外的信息，店员多答一句都嫌烦 |
| 3 | 类别绝不能选错 | 选错 = 驳回重提，这是立项目标；AI 只能给候选，必须店员点选 |
| 4 | 任意字段随时可改 | 改类别还要联动重校验拍摄清单，不能让用户被流程绑架 |
| 5 | 填一半退出，回来接着填 | 草稿保留 7 天，且与老表单草稿互不覆盖 |
| 6 | 分支有差异 | 高频卡片直锁类别、自由描述走识别；购物袋还要拍袋底供应商 |
| 7 | AI 挂了不能耽误报修 | 降级成卡片点选或回老表单，永远有路可走 |
| 8 | 可单测、可回放、埋点打得出来 | 时长 / 准确率 / 渗透率要能算账，出了问题要能定位 |
| 9 | 二期报销直接复用 | 最好只加配置不改框架，别为第二个业务重写一遍 |
| 10 | 终态是多 Agent（路由 / 抽取 / 质检） | 现在选的路不能堵死将来的迁移 |

### 1.2 我们的核心思路

**LLM 负责识别与生成（听懂口语、抽出结构化字段），状态机负责流程（下一步问什么由转移表决定），人负责确认（AI 预填、点选提交才入库）。**

翻译一下：模型只干它擅长的事（理解一句话、抽出三个要素），不碰它不擅长的事（决定流程走向）；流程走向是代码和配置，白盒可测；最后一步永远留给人。上面第 2、3、7、8 条约束，全靠这个分工来兜住。

### 1.3 六个候选逐一过

**A. 纯 LLM 自主对话（ReAct）—— 一票否决**

怎么做的：一个系统提示词 + 若干工具（查字典、查档案、建单），模型每轮自己决定调哪个工具、问什么，循环直到建单。

为什么不行：每轮流程都是模型临时决策——跳步漏问不可控、编造枚举无法根除，直接踩第 2、3 条红线（"选错即驳回"）。

**B. 纯 LangChain 线性串联（Runnable）—— 否决**

怎么做的：把"类别识别→详情抽取→确认单"写成 RunnableSequence 管道（prompt | 模型 | 解析器一路串），一次 invoke 跑到底；流程顺序写死在管道形状里，当前进度靠把全历史塞回 prompt 让模型自己读。

为什么不行：管道没有"停下来等用户"的概念——回跳只能整条链重跑（踩第 4 条）、断点续填做不出（踩第 5 条）；硬写下去要么滑向 A，要么自己加 if 调度——那其实已经是 C 了。

**C. LangChain + 状态机 —— 本期采用 ✓**

怎么做的：流程是一张 11 状态转移表（状态 × 事件 → 下一状态），每条用户消息是事件，查表转移；LangChain 降级为工具函数，全流程只在 2 处被调用（类别识别、三要素抽取），其余全是规则代码。

为什么选它：流程白盒确定——转移表可单测、会话可按快照回放（第 8 条）；枚举白名单 + 强制点选（第 3 条）；全流程只调 2 次模型，成本延迟最优；引擎 2 人天就能出来，工期稳（第 1 条）。

**D. LangGraph 图编排 —— 留作终态 ◐**

怎么做的：StateGraph 定义节点（=状态）与条件边（=转移），Checkpointer 内置断点续填，interrupt() 原生支持人机确认。

为什么本期不用：能力最强，但学习曲线会挤压 8 个工作日（第 1 条），且单业务线性流程吃不到图编排的红利。留作终态：状态即节点候选、工具已全 MCP 化，触发信号出现时迁移约 3~5 人天（第 10 条不堵死）。

**E. Dify —— 不作底座，留作知识问答场景 ✗**

怎么做的：低代码平台，画布拖出 chatflow / workflow，平台托管对话与知识库，自建 H5 走它的 API。

为什么不行：线性 DAG 回跳靠重跑（第 4 条）；我们的 8 种卡片消息在平台事件流里没有对应物，要双重映射；配额 / 降级 / 埋点还得自己外挂一层网关——架构变四层，还多一套平台运维。

**F. Coze 扣子 —— 否决 ✗**

怎么做的：字节 Agent 平台，SaaS 开箱即用或 Studio 私有化部署，画布编排 + 插件生态。

为什么不行：SaaS 版把员工档案 / 门店数据带进 prompt，数据出域（第 9、10 条之外的一票否决项）；Studio 私有化组件太重，8 个工作日装不下；编排问题同 Dify。

> 逐维度深对比（六候选 × 十六维度）见同目录《技术选型与方案设计对比.md》§2。

## 2. 技术栈选型

| 层 | 选型 | 一句话理由 |
|---|---|---|
| Agent 服务 | Python 3.11 + FastAPI | 原生 async + 流式 + 自动 OpenAPI 文档 |
| 编排 | 自研状态机（11 状态转移表）+ LangChain（仅封装 LLM 调用） | 流程确定性；LLM 不做流程决策 |
| 模型 | **LLM-XXX（待定）** | 四维评测（识别准确率 / 抽取质量 / 成本 / 速度），11.9 前定 |
| H5 ↔ Agent 通信 | REST + SSE（fetch POST + 流式响应） | 消息带 body、回复流式、断线快照重放 |
| Agent ↔ MCP 通信 | MCP Streamable HTTP（fastmcp + 官方 SDK client） | 单端点 /mcp、独立进程跨机、跨业务复用 |
| 工具层 | MCP Server（独立进程，7 工具） | 与框架解耦，报销 / 多 Agent 直接复用 |
| 存储 | Redis（会话 / 草稿 / 配额，TTL 7 天）+ MySQL（归档 / 埋点） | TTL 原生 + 亚毫秒 |
| 前端 | App 内 H5 聊天页 | 消息协议与原型一一对应 |

## 5. 对话状态机（11 状态）

状态机图：[02-对话状态机图.puml](../../../diagrams/02-对话状态机图.puml)

| 状态 | 职责要点 | LLM | 出口 |
|---|---|---|---|
| INIT | 调工具带出字段，下发状态条 + Top6 | — | 文字→A_WAIT；卡片→B_LOCK |
| A_WAIT | 自由描述 → 类别识别 | ✓ Top3 候选 + 三要素 | 有效→A_ENUM；失败→FALLBACK |
| A_ENUM | 枚举单选卡（AI 预选首位，**必须点选**） | — | 点选→DETAIL |
| B_LOCK | 卡片即锁定类别 | — | →DETAIL |
| DETAIL | 三要素抽取润色，缺则追问一轮 | ✓ | 齐→PHOTO；缺→追问后带占位符 |
| PHOTO | 按类别清单校验照片 | — | 过→CONTACT；缺→补拍 |
| CONTACT | 默认本人，可改店长 / 他人 | — | →CONFIRM |
| CONFIRM | 13 字段确认单，全部 ✏️ 可改 | — | 提交→DONE；重选类别→PHOTO 重校验 |
| DONE | 出单号 + 状态 | — | 终态 |
| EXITED | 主动退出（任意非终态可触发） | — | keep 草稿 7 天可续 / abandon 废弃 |
| FALLBACK | 全量类别点选；LLM 不可用降级卡片向导 | — | 选定→DETAIL；切老表单→终态 |

两分支差异只在入口（B_LOCK 免确认、A_ENUM 必须点选），汇合后完全一致。

## 6. Prompt 工程（全流程仅 2 处调用）

### 6.1 系统提示词（状态机注入到每次调用）

```text
你是好特卖门店的设备报修填报助手，引导店员用最短路径完成报修单。
【采集范围】只允许采集以下表单字段：报修类别、报修详情（故障表现/产生原因/导致后果）、联系人、手机号码、问题照片或视频。
【禁止】1) 询问表单以外信息（如故障发生时间、天气、客流）；2) 编造字典外的枚举值；3) 在用户确认前生成提交动作；4) 一轮追问多个问题。
【风格】口语、简短、每次只处理一件事。所有输出按 reply_schema 返回 JSON。
```

### 6.2 类别识别（A_WAIT，LLM-XXX）

```text
## 任务
从店员的问题描述中识别报修类别。只能从 <类别字典> 中选择，禁止输出字典外的值。

## 类别字典（由工具 get_category_dict 注入）
{category_dict}

## 用户描述
{user_text}

## 输出 JSON Schema
{"candidates": [{"name": "字典内类别"}], "need_detail": true}

## 示例
描述："店里的冷藏风幕柜不制冷了，温度显示15度，鲜奶都下架了"
输出：{"candidates": [{"name": "制冷设备 - 风幕柜/立式冷柜"},
                     {"name": "制冷设备 - 卧式冰柜"}], "need_detail": true}
```

**不做置信度分流**：识别成功一律出 Top3 单选卡（首位为 AI 预选项），识别失败或候选全被白名单过滤才进 `FALLBACK` 全量点选；识别质量由 `enum_first_pick` 埋点观测（AI 首位被直接点选的比例）。

### 6.3 三要素抽取与润色（DETAIL，LLM-XXX）

```text
## 任务
从描述中抽取报修详情三要素，并润色为规范短句。要素缺失时对应字段返回 null，并生成一句"仅针对缺失要素"的追问。
## 输出 JSON Schema
{"表现": "…", "原因": "…|null", "后果": "…|null", "追问": "…|null"}
## 边界
- 用户口语原意优先，不添加未提及的事实（原因常为"初步判断"）
- "追问"只能是：表现 / 原因 / 后果 三者之一的补齐请求
```

## 7. 防幻觉与结构化输出

| 环节 | 机制 |
|---|---|
| 输出格式 | JSON mode；解析失败重试 1 次，再失败进降级 |
| 枚举校验 | 候选逐个与字典白名单比对，非法丢弃；丢弃后为空→FALLBACK |
| 候选排序 | Top3 首位预选仅影响卡片顺序——**A 分支必须用户点选才入库** |
| 详情校验 | 三要素 schema 校验，润色结果与原文一并展示可改 |
| 提交校验 | 前端 + 服务端双重校验 13 字段必填，缺一不进 DONE |

## 8. 会话草稿与退出恢复

会话即草稿：每次状态变更先 `draft_save` 再推送（Redis 单 Key JSON，TTL 7 天滑动续期，ver 乐观锁防并发）；错误退出（杀 App / 断网）零特殊处理，重进 `GET /sessions/{id}` 快照重放恢复。主动退出：前端弹「继续填写 / 保存退出 / 放弃」，keep 进 EXITED 保留草稿（重进提示续填），abandon 标记废弃。与老表单草稿不同 Key 空间，互不覆盖。

实现细节：[SSE与状态保存-详细解读.md](../详细点/SSE与状态保存-详细解读.md) · [关键代码骨架.md](../详细点/关键代码骨架.md)

## 9. 前后端接口

完整定义（请求 / 响应 JSON、SSE 事件流、MCP JSON-RPC 报文）：[接口文档.md](../详细点/接口文档.md)

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/sessions` | POST | 建会话，返回 session_id + 首屏消息 |
| `/api/sessions/{id}/messages` | POST | 七种消息 type；响应 SSE 流（typing→message→done） |
| `/api/sessions/{id}/upload` | POST | multipart 附件 → media_ids |
| `/api/sessions/{id}` | GET | 恢复会话（断点续填 / 换端） |
| `/api/sessions/{id}/submit` | POST | CONFIRM 提交（ver 乐观锁），调 create_repair_order |
| `/api/sessions/{id}/exit` | POST | 主动退出，mode=keep（存草稿）或 abandon（废弃） |

服务端消息类型 8 种（text / quick_cards / enum_card / photo_guide / contact_confirm / confirm_card / result / system_tip），与原型组件一一对应。

## 10. 工程降级与成本控制

| 故障 | 处理 |
|---|---|
| LLM 超时（>8s） | 重试 1 次 → 提示稍后 + Top6 卡片（纯规则可用） |
| LLM 整体不可用 | 降级卡片向导模式，不阻塞报修 |
| 识别 / 解析失败 | FALLBACK 全量点选 |
| 明道云提交失败 | 本地落待发表 + 定时重试 3 次 → 转人工 |
| SSE 断线 | GET 会话快照重放，消息不丢 |
| Redis 故障 | 降级内存会话，提交前强校验 |

成本限额（LLM 调用层统一拦截）：单人单天调用次数 + token 双限额、单会话 6 次、全局日配额熔断；超限降级卡片向导。

## 11. 埋点清单

| 事件 | 支撑指标 |
|---|---|
| session_start / session_end | 填报时长、步数 |
| branch_a_input / branch_b_card_click | 分支占比 |
| **enum_first_pick** | **类别识别准确率** |
| fallback_enter / switch_to_form | 兜底率、转老表单率 |
| session_exit / draft_resume | 中途放弃率、续填恢复率 |
| photo_reject / contact_change | 前置拦截量、代报占比 |
| submit_success / submit_fail | 完成成功率、卡壳定位 |

对账口径：AI 渗透率 = submit_success 数 / 明道云总报修单量；上线前导出老表单 2 周数据做基线。

## 12. 演进与待定项

本期单体 Agent + 状态机（报修）→ 二期加报销（同框架加配置，9~12 人天；阻塞：报销真实字段未拿到）→ 终态多 Agent（迁移只搬编排，3~5 人天）。
