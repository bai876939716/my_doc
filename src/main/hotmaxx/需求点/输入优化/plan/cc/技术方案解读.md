# 技术方案解读 · 常见问题 Q&A

> 配套文档：[设备报修-AI填报Agent技术实现方案.md](./设备报修-AI填报Agent技术实现方案.md)（下称"方案"）。本文回答评审和开发中最常被问到的"为什么"，以及关键场景的完整过程。

## 一句话读懂

把"填 13 个字段的表单"变成"聊 5 句天"：**状态机管流程，LLM 管理解，工具管数据，用户管确认**。每一层只干自己最擅长的事。

## 核心设计四句话

1. **LLM 不持有流程控制权**——下一步问什么由状态机决定，LLM 只做理解和抽取。这样每次对话行为都确定、可测试、可回放，不会出现 AI 忘问、乱问、编枚举。
2. **枚举只选不编**——类别候选先过白名单过滤，再让用户点选确认，AI 的判断永远不直接进数据库。
3. **能查不问**——9 个字段系统静默带出，用户只回答 AI 无法推断的 2~3 件事。
4. **永远有路可走**——LLM 挂了降级成卡片向导，识别不了降级成全量点选，实在不行引导回老表单，报修永远不被阻塞。

## Q1：为什么用状态机，不直接让 LLM 自由对话？

三个硬理由：

| 维度 | 纯 LLM 对话 | 状态机编排 |
|---|---|---|
| 流程确定性 | 每轮靠模型决策，可能跳步、漏问、重复问 | 转移表写死，该问什么一定问什么 |
| 成本与延迟 | 每次对话都过模型（本流程 8~10 轮） | 全流程只调 2 次 LLM（类别识别、详情抽取） |
| 可测试性 | 只能人工体验测试 | 转移表可以写单元测试，一次回归全覆盖 |

关键认知：**报修是一个字段固定的表单流程，不是开放对话**。流程越固定，越应该把控制权从模型手里拿回来，模型只在小范围（理解一句话、抽出三个要素）内发挥。这也是"防幻觉"最根本的手段——不是提示词写得多严，而是模型压根没有编造的机会。

## Q2：为什么不用 LangGraph 一步到位？

LangGraph 是终态方向（多 Agent），但本期不选它的原因：报修只有 10 个状态，自研转移表一天写完、全组都看得懂、出问题一条日志定位；LangGraph 的学习/调试成本对这个规模是负收益。**但迁移路径已预留**：状态机的每个状态 = 未来 LangGraph 的一个节点，工具层已全部 MCP 化，届时只搬编排层，工具和数据层一行不动（见方案 §0.2、§10）。

## Q3：用户中途退出怎么办？会话怎么保留？

机制是**"会话即草稿"**，不依赖用户点保存：

1. 每次状态变更（答完一个问题、传完照片）服务端立刻 `draft_save`，把 `{当前状态 + 已采集字段}` 写入 Redis，TTL 7 天
2. 退出没有任何特殊处理——数据已经在 Redis 里了
3. 用户重新打开入口时，前端发现本地有 session_id，调 `GET /api/sessions/{id}` 恢复：服务端返回当前状态，前端重放到对应步骤（如照片步骤），已答内容直接回显
4. 7 天内随时可续；超期草稿过期，用户重开新会话（此时老表单也从未有过"草稿保留 7 天"的能力，体验只升不降）

**不小心退出（杀 App / 闪退 / 切后台）**：与主动退出完全同路径，因为保存时机是"每个状态变更后"而不是"退出时"——退出动作本身不需要被感知。

## Q4：填到一半想切回老表单，已填内容丢吗？

本期：不回填，两边草稿独立（设计原则 1）。AI 侧已采内容仍在 Redis，7 天内切回 AI 继续填。二期可做单向同步（AI → 老表单回填），协议上只差一个字段映射函数，架构无改动。

## Q5：接口为什么这么设计？一次消息交互的完整过程

四个接口各司其职：`POST /sessions` 建会话、`POST /messages` 发消息（SSE 流式回）、`GET /sessions/{id}` 恢复、`POST /submit` 提交。**为什么用户消息用 POST 而回复用 SSE**：用户发消息是明确的请求-响应动作，POST 天然可靠（失败可重试）；AI 回复需要流式体验（typing → 文本 → 卡片逐条出现），SSE 单向推送刚好，比 WebSocket 少一半复杂度。

以"店员点高频卡片"为例的完整过程（对应泳道图）：

1. 店员点卡片 → `POST /messages {type: "card_click", value: "pos"}`
2. Agent 服务读 Redis 拿到会话状态 `INIT` → 状态机查转移表：`card 事件 → B_LOCK`
3. B_LOCK 处理器执行：卡片映射枚举、锁定类别、组装"请描述三要素"消息 → `draft_save`
4. SSE 依次推送：`typing`（店员立即看到"输入中"）→ `text` → 下一步骤卡片
5. 全程 LLM 一次都没调用——这就是"能不用模型就不用"，延迟只有 Redis + 规则计算，毫秒级

而分支 A（自由描述）的第 3 步换成：调 LLM 类别识别 → 白名单过滤 → 出枚举卡，延迟 = 一次 LLM 调用（约 1~2s），typing 动画正好覆盖这个等待。

## Q6：会话数据具体长什么样？为什么放 Redis 不放 MySQL？

结构见方案 §6（`session_id / state / collected_fields`）。选 Redis 的原因：会话是**高频读写、短生命周期**的数据（每个动作读写一次、7 天过期），Redis 的 TTL 原生过期 + 亚毫秒读写正好；MySQL 留给"会话归档 + 埋点"这类要长期分析的数据。Redis 挂了的降级：方案 §9，退化为内存会话，牺牲断点续填但提交不受影响。

## Q7：为什么不引入置信度打分？

刻意省掉：置信度是模型自报的数字，校准成本高（不同模型、不同类别的分布都不一样），而它在本流程里**不承担任何正确性职责**——无论打分多高，类别都必须经用户点选确认才入库。所以直接简化为：识别成功一律出 Top3 单选卡（首位预选），失败或候选全被白名单过滤才降级全量点选。识别质量用 `enum_first_pick` 埋点观测（AI 首位被直接点选的比例），准确、免维护。

## Q8：照片校验为什么用规则清单，不用多模态模型看图？

购物袋类的必拍清单（袋底供应商标识 + 问题部位）是**确定性的配置规则**，逐项核对 media_id 列表即可，零成本零延迟零误判。多模态判断"这张图拍得对不对"准确率不可控，还引入新的失败面。多模态留给二期可选增强（识别照片内容自动匹配清单项），但不作为卡点——卡点永远是规则。

## Q9：并发和安全考虑了什么？

并发：Agent 服务无状态（会话在 Redis），直接水平扩；LLM 调用有限流队列，防止高峰打爆配额。安全：手机号在会话与前端均为脱敏展示（138\*\*\*\*1234），完整号码只在服务端提交明道云时使用；H5 与 Agent 服务走登录态 token，会话与用户强绑定，不能越权读别人会话；所有 LLM 输出不直接入库，最终以用户确认的数据为准。

## Q10：后续接报销等新业务，要改多少代码？

按 §10.1 扩展表：换字典配置 + 换 Prompt 组 + 换转移表 + 挂工具子集（报销多一个 OCR 发票工具），框架层零改动。预估新业务接入 = 配置工作 + 新工具开发，不碰状态机引擎和消息协议。

## 留给评审的开放问题

1. **会话 TTL 7 天**是否合适？（店员跨周报同一故障的场景是否存在，要不要"继续上次报修"入口）
2. **AI → 老表单回填**是否列入二期？（当前只做 AI 侧草稿保留）
3. **多模态照片质检**（自动判断拍摄是否合规）二期是否值得做？先看上线后 `photo_reject` 埋点量。
4. **明道云提交幂等**：网络超时重试可能造成重复单，需要确认明道云 API 是否支持业务幂等键，否则服务端要先落本地单号再提交。
5. **语音输入**：本期"语音转文字"依赖输入法自带能力，是否需要接入 ASR 服务统一体验？
6. **类别字典维护**：由谁运营（总部 IT / 各大区）、变更审批流程，需要配套一个极简配置后台还是直接改表？
