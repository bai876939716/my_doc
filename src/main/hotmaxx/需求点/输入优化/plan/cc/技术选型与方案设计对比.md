任何编排 / 整体方案，逐条过这 10 条。R1~R8 来自《报修产品方案.md》五原则、兜底与指标；R9/R10 来自技术备忘（报销二期、多 Agent 终态）。

## 2. 编排方案深对比（核心决策）

### 2.1 四个候选

| 候选 | 一句话定位 | 流程控制权在谁 |
|---|---|---|
| A. 纯 LLM 自主对话（ReAct / function-calling 循环） | 一个系统提示词 + 工具，模型自己决定下一步 | LLM |
| B. 纯 LangChain Runnable 线性串联 | prompt → 模型 → 解析一条链跑到底，状态藏在消息列表里 | 无（隐式） |
| C. **LangChain + 自研状态机**（LangChain 仅封装 LLM 调用） | 转移表驱动流程，LLM 只做理解 / 抽取 | 状态机（代码，白盒） |
| D. LangGraph 图编排 | 节点 = 状态、条件边 = 转移、Checkpoint 内置 | 图定义（代码） |

> 与 todo 草稿表的对应：「纯 LangChain Runnable 串联」= B，「LangChain 自研状态」= C，「LangGraph」= D；A 是反例基准（此前方案 §0 已否决）。**本节结论与 todo 草稿一致：C 本期、D 终态。**

### 2.2 逐维度对比

维度融合 todo 草稿的行 + 工程补充：

| 维度 | A 纯 LLM | B 纯 Runnable | C 自研状态机 | D LangGraph |

### 2.3 各候选展开

**A. 纯 LLM 自主对话 —— 否决。** 开发最快（1 个系统提示词 + 3 个工具即可跑通 demo），但每轮流程都是 LLM 决策：跳步漏问不可控、枚举编造无法根除、长会话上下文漂移、每轮全量上下文计费。R2/R3/R8 三条硬伤直接命中业务底线（驳回率），一票否决。

**B. 纯 LangChain Runnable 串联 —— 否决。** 学习成本最低、代码最直观，但链是单向无状态的："中途改联系人后重算确认单""照片校验失败退回拍照"这类回跳要把链重跑一遍；会话状态只能自己外挂拼装。适合一次性极简表单和 demo，不适合多轮、可回跳、要断点续填的生产会话（R4/R5 做不出）。

**C. LangChain + 自研状态机 —— 本期采用。** 流程 100% 确定性：10 状态转移表配置化，状态职责三列分明（状态 / LLM 职责 / 规则职责）；LLM 只在 A_WAIT（类别识别）与 DETAIL（三要素抽取润色）两处出现；每个状态可单测、会话可按状态快照回放；与原型 stage 一一对应，前端消息协议天然对齐。代价：状态逻辑自己维护（10 状态约 300 行，量小）；无现成 checkpointer，用 Redis 快照替代（先存再推 / TTL 滑动 / ver 乐观锁，《SSE与状态保存-详细解读》已设计，状态机 2 人天 + 保存恢复 2.5 人天）。

**D. LangGraph —— 终态，本期不选。** 图编排原生支持回跳 / 循环 / 并行；Checkpointer（Redis / PostgreSQL）断点续填开箱即用；interrupt() 人审机制与"AI 预填、人确认"天然同构；subgraph / supervisor 是多 Agent 的正路。不选本期的唯一主因是 R1：学习曲线（图 / 状态 / reducer 新思维）+ 调试工具链磨合，在"一人 + 8 个工作日 + 并行 H5 联调"约束下 11.16 风险高；且单业务线性流程吃不到图编排的主要红利（并行 / 复杂分支），红利要等报销 + 质检多 Agent 时才兑现。

> 佐证 D 定位为终态而非淘汰：LangChain 1.x 官方 create_agent 底层就是 LangGraph 封装——官方路线也在向图编排收敛；反过来说明"纯链式串联做可控流程"不是长线路径，B 的否决与官方方向一致。

### 2.4 结论与 C → D 迁移路径

**结论：本期 C，终态 D，否决 A / B。** 三点理由：① 业务底线 R3（驳回率）要求流程确定性，C 是唯一白盒可控且工期内的；② C 的 LLM 调用点最少（2 处），成本与延迟最优，且未来直连换网关只改两处；③ C→D 迁移成本已被三个设计压到最低。

| 切换信号（出现其一即启动迁移） | 迁移动作 | 预估 |
|---|---|---|
| 报销等 ≥2 业务接入，状态总数 >20 | 状态机整体换成 StateGraph，节点 = 现有状态 | 3~5 人天 |
| 需要并行子 Agent（如抽取 + 质检并行） | 工具已全 MCP 化，直接挂给新 Agent | — |
| 出现跨业务编排（意图路由入口） | supervisor 图接管路由，报修 / 报销变子图 | — |

迁移时**只搬编排、不搬资产**：MCP 工具层、消息协议、H5、Prompt、埋点全部原样保留。

## 3. 通信方式对比（专题：SSE / WebSocket / Streamable HTTP）

### 3.1 两条链路，两套选型

先澄清一个容易混的点：**Streamable HTTP 是 MCP 协议的传输规范**（2025-03-26 版引入，取代旧的 HTTP+SSE 传输），不是通用前端技术。所以两条链路要分开评：

| 链路 | 候选 | 结论 |
|---|---|---|
| ① H5 ↔ Agent 服务（自有消息协议） | EventSource(GET) / fetch POST+SSE / WebSocket / 轮询 / Streamable-HTTP 风格 | **fetch POST + SSE 流** |
| ② Agent ↔ MCP Server（MCP 协议） | stdio / HTTP+SSE（旧规范） / Streamable HTTP（现行） | **Streamable HTTP** |

### 3.2 链路①：H5 ↔ Agent 服务

| 方式 | 原理 | 优点 | 缺点 | 判定 |
|---|---|---|---|---|
| EventSource（浏览器原生 SSE） | 常驻 GET 长连接收事件 | 零依赖、自动重连 | **只支持 GET**：用户消息、卡片点击、上传完成事件都带不了请求体；自定义鉴权头困难 | ✗ |
| WebSocket | 全双工长连接 | 双向、低延迟 | 本场景用户消息低频（POST 一次即可）、服务端单向下推为主，双工能力浪费；过企业网关要额外配置（升级 / 超时 / 粘性会话）；HTTP 中间件（鉴权 / 限流 / 重试）全部失效，得自己做 | △ 能用但不值 |
| 轮询 | 定时 GET 拉状态 | 最简单 | 延迟高、空转浪费、打字机效果做不出 | ✗ |
| **fetch POST + SSE 流** | 消息走 POST，响应体是 `text/event-stream`，用 ReadableStream 逐块读 | 消息能带 body、响应能流式（typing / 打字机 / 卡片渐进渲染）；纯 HTTP，过网关代理最省事；断线用 `GET /sessions/{id}` 快照重放 | SSE 帧要自己解析（约 50 行）+ 心跳 | ✓ 本期 |
| Streamable-HTTP 风格 | 单端点 POST；客户端可要求响应以 SSE 流返回；会话 ID 头维持状态；Last-Event-ID 断点续传 | 与上一行**同构**：POST + 可选 SSE 响应 + 会话恢复 | 它是 MCP 的传输层规范（JSON-RPC、initialize 握手、工具发现那一套）；H5 ↔ Agent 跑的是自有消息协议（text / quick_cards / enum_card…），用不上 JSON-RPC | 概念借鉴 ✓ |

**结论**：H5 ↔ Agent 用 **fetch POST + SSE 流**。它与 Streamable HTTP 的设计同构（POST + 可选 SSE 响应 + 会话恢复），我们用 ver 乐观锁 + 快照重放达到 Last-Event-ID 的同等效果；若未来前端要直连统一 AI 中台 / MCP 网关，协议概念与前端代码可平移。实现细节（typing 先行 / 心跳 / 断线重放 / 状态快照）见 [详细点/SSE与状态保存-详细解读.md](./详细点/SSE与状态保存-详细解读.md)。

### 3.3 链路②：Agent ↔ MCP Server

| 传输 | 规范版本 | 原理 | 判定 |
|---|---|---|---|
| stdio | 最初标准 | 客户端把 MCP Server 当**本机子进程**拉起，stdin/stdout 通信 | ✗ 只能同机部署——与"MCP Server 独立部署、给报销 / 多 Agent 复用"直接矛盾 |
| HTTP+SSE | 2024-11-05（已废弃） | 双端点：GET /sse 建流 + POST /messages 发消息，会话靠端点 URL 参数 | ✗ 官方已标记 deprecated，新项目不采用 |
| **Streamable HTTP** | 2025-03-26 起 · 现行标准 | 单端点（如 /mcp）POST 进，JSON 或 SSE 流出；MCP-Session-Id 头维持会话；Last-Event-ID 断线续传；无状态服务端也可跑（无需常驻连接） | ✓ 独立进程跨机部署的正确选择 |

落地：fastmcp 原生支持（启动时指定 streamable-http 传输即可），Agent 侧用官方 SDK 的 streamable http client 连接。**工作量影响 ≈ 0**（SDK 内置），换来 MCP Server 可独立扩缩容、被报销模块与未来多 Agent 共享——这正是"工具层选 MCP"的价值兑现点。

### 3.4 为什么 H5 不直接当 MCP 客户端连 MCP Server（评审备答）

| 质疑 | 回应 |
|---|---|
| 前端直连 MCP，是不是少一层？ | ① 鉴权：员工身份体系与 MCP 会话鉴权要在 MCP 层重做一遍，暴露面更大；② 编排：状态机 / 降级 / 配额 / 埋点必须在服务端，放前端则 App 端无法复用、逻辑双份；③ 密钥：LLM 与数据源凭证不能下发到浏览器 |

## 4. 全栈选型对比

| 层 | 备选 | 关键对比 | 结论 | 选错的重置成本 |
|---|---|---|---|---|
| 服务框架 | FastAPI / Flask / Django | FastAPI：原生 async（SSE 流式 + 并发 LLM 调用的关键）+ 自动 OpenAPI 文档（前后端联调省 1~2 天）；Flask：async 支持弱、SSE 靠插件；Django：ORM/Admin 优势在本场景用不上，过重 | **FastAPI ✓** | 换框架 = 重写 API 层 ≈3 人天 |
| 工具层 | MCP Server / REST 客户端内嵌 / LangChain Tool 装饰器 | MCP：独立进程、跨业务跨 Agent 复用、行业生态（未来接第三方 MCP 工具零成本）；REST 内嵌：换业务要改 Agent 代码；@tool 装饰器：与 LangChain 绑死，无法独立共享给多 Agent | **MCP（fastmcp + Streamable HTTP）✓** | MCP 可退回 REST（工具本是无状态函数）；REST 升 MCP 要重构 |
| 存储 | Redis / MySQL / 前端 localStorage | Redis：TTL 原生（会话 7 天滑动续期）、亚毫秒、配额 INCR 原子计数；MySQL：TTL 要自管，但归档 / 对账必须它；localStorage：换端即丢、用户可清，不可信 | **Redis 主 + MySQL 归档 ✓** | — |
| 模型接入 | 直连厂商 SDK / LLM 网关 / 开源自部署 | 直连：本期最快（2 个调用点，各约 20 行）；网关：多模型路由 / 降级 / 配额统一管理，二期再上（识别用强、改写用轻的分档）；自部署：GPU + 运维成本与门店场景不匹配 | **直连 ✓（网关预留）** | 直连 → 网关：调用点只有 2 处，半天迁完——LLM 调用点少的复利 |

### 5.1 总览

| | 方案一 · 极简直连 | **方案二 · 状态机 + MCP（推荐 · 本期）** | 方案三 · LangGraph 全托管 |

| 11.16 单人可达 | ✅ 有余量 | ⚠️ 需前端并行（§6） | ✗ |
| R1~R8（本期质量） | R3/R4/R5/R7/R8 ✗ | **全 ✓** | 全 ✓ |
| R9 报销复用 | ✗ 从头写（≈再 7 人天） | ✓ 加配置 9~12 人天（技术方案 §8.3） | ✓ 新增子图 |
| R10 多 Agent | ✗ 无基础 | △ 迁移 3~5 人天 | ✓ 原生 |
| 一句话 | 快，但到顶即天花板，驳回率不可控 | 质量与工期的平衡点，演进已铺路 | 终态提前，但一人一期限内交付不了 |

### 5.2 方案一：极简直连（否决）

H5 → FastAPI 单服务（Agent 全权决策，流程写在提示词里）→ REST 直连明道云 / 员工档案 / 主数据；会话状态放内存。组件最少，7 人天，11.16 无压力——适合**内部技术验证 / demo**。致命伤：枚举防幻觉只剩提示词约束（R3✗，驳回率恰是立项目标）；改字段 = 重新对话（R4✗）；服务重启会话丢（R5✗）；LLM 故障 = 入口故障（R7✗）；无埋点结构（R8✗）；报销 / 多 Agent 零基础（R9/R10✗）。
可留用途：联调明道云 API 的临时脚手架，其 REST 调用代码将来搬进 MCP 工具。

### 5.3 方案二：自研状态机 + MCP（推荐）

即《设备报修-AI填报Agent技术实现方案.md》全案，此处只列对比要点：全链路 H5（POST+SSE）→ FastAPI Agent 服务（状态机 + LangChain 封装 LLM，调用点 2 处）→ MCP Server（Streamable HTTP，7 工具）→ 明道云 / 主数据 / OSS；Redis 会话草稿配额 + MySQL 归档埋点。10 条硬约束逐条满足（§1 × §2.2 C 列）。**唯一需要评审拍资源**：15 人天 vs 8 个工作日，缺口与解法见 §6。

### 5.4 方案三：LangGraph 全托管（终态，本期不选）

与方案二只差编排层：StateGraph 节点 = 状态、条件边 = 转移、Redis Checkpointer、interrupt() 做"预填人确认"。回跳 / 循环 / 断点全部原生，多 Agent 是正路——但本期不选的主因就是 R1（§2.3 D 段），且单业务线性流程吃不到图编排红利。缓解：方案二守住三条纪律（状态即节点候选 / 工具全 MCP 化 / Prompt 版本化），迁移时只搬编排不搬资产（§2.4）。
