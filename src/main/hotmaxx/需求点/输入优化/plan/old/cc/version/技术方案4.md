# 设备报修 · AI 填报 Agent 技术方案 v3


## 1. 实现方案对比

### 1.1 产品需求考虑的点


#### 强约束

| # | 约束点            | desc                                                              |
|---|----------------|-------------------------------------------------------------------|
| 1 | 流程可控，不跳步、不漏问   | 1.沟通没完没聊，不断的问答，却解决不了问题；  <br/> 2.表单字段有先后顺序 （可能关联性）；<br/>3.字段要保证齐全 |
| 2 | 类别绝不能选错        | AI 只能给候选，必须用户确认                                                   |
| 3 | 任意字段随时可改       | 不能让用户被流程绑架 中途有问题还得重来                                              |
| 4 | 填一半退出，回来接着填    | 草稿保留 x 天                                                          |
| 5 | AI 挂了不能耽误报修    | 降级成卡片点选或回老表单                                                      |


#### 后续演进准备

| # | 考虑点                      | desc                  |
|---|--------------------------|-----------------------|
| 5 | 二期报销直接复用                 | 最好只加配置不改框架，别为第二个业务重写一遍 |
| 6 | 终态是多 Agent（路由 / 抽取 / 质检） | 现在选的路不能堵死将来的发展        |

### 1.2 核心思路

> 1. LLM 负责识别与生成（听懂口语、抽出结构化字段） <br/>
> 2. 程序负责流程（ 编排方式、 状态机方式） <br/>
> 3. 人负责确认（AI 预填、点选提交才入库）


### 1.3 实现方式对比

**A. 纯 LLM 自主对话（ReAct）**

**实现过程**：一个系统提示词 + 若干工具（查字典、查档案、建单），llm每轮自己决定调哪个工具、问什么，循环直到参数补齐。

**考虑的点**：每轮流程都是模型临时决策——跳步漏问不可控、编造枚举无法根除，轮次太多成本也不可控

**B. 纯 LangChain 线性串联（Runnable）**

**实现过程**：把"类别识别→详情抽取→确认单"写成 RunnableSequence 管道（prompt | 模型 | 解析器一路串），一次 invoke 跑到底；流程顺序写死在管道形状里，  把进度、全历史 塞回 prompt 让模型自己读。

**考虑的点**： 回跳只能整条链重跑 （做不到随时改-约束点1） ，强行实现需要自己加if调度 繁杂且僵硬。

**C. LangChain + 状态机 —— 这次采用 ✓**

**实现过程**：流程是一张 状态转移表（状态 × 事件 → 下一状态），每条用户消息是事件，查表转移； 全流程只在 2 处被调用（类别识别、三要素抽取），其余全是规则代码。

**考虑的点**： 流程白盒确定而且可控；步数和llm调用次数可控；满足产品需求，支持中途修改 和断点恢复。

**D. LangGraph 图编排 —— 后续考虑**

**实现过程**： StateGraph 定义节点（=状态）与条件边（=转移），Checkpointer 内置断点续填，interrupt() 原生支持人机确认。

**考虑的点**：能力最强，单业务的线性流程 吃不到图编排的红利。

**E. Dify**

**考虑的点**：适合简单知识库； 前后端对接 （比如卡片 、降级方案）、数据埋点 需要挂一层网关； 灵活性较差 （回跳实现较复杂）

**F. Coze 扣子**

**考虑的点**：编排问题同dify一样；  saas(数据出域)， 本地部署 组件太重； 官方的定义就是用来验证

## 5. 对话状态机（11 状态）

状态机图：[02-对话状态机图.puml](../../../../diagrams/02-对话状态机图.puml)

| 状态 | 职责要点 | LLM | 出口 |
|---|---|---|---|
| INIT | 调工具带出字段，下发状态条 + Top6 | — | 文字→A_WAIT；卡片→B_LOCK |
| A_WAIT | 自由描述 → 类别识别 | ✓ Top3 候选 + 三要素 | 有效→A_ENUM；失败→FALLBACK |
| A_ENUM | 枚举单选卡（AI 预选首位，**必须点选**） | — | 点选→DETAIL |
| B_LOCK | 卡片即锁定类别 | — | →DETAIL |
| DETAIL | 三要素抽取润色，缺则追问一轮 | ✓ | 齐→PHOTO；缺→追问后带占位符 |
| PHOTO | 按类别清单校验照片 | — | 过→CONTACT；缺→补拍 |
| CONTACT | 默认本人，可改店长 / 他人 | — | →CONFIRM |
| CONFIRM | 13 字段确认单，全部 ✏️ 可改 | — | 提交→DONE；重选类别→PHOTO 重校验 |
| DONE | 出单号 + 状态 | — | 终态 |
| EXITED | 主动退出（任意非终态可触发） | — | keep 草稿 7 天可续 / abandon 废弃 |
| FALLBACK | 全量类别点选；LLM 不可用降级卡片向导 | — | 选定→DETAIL；切老表单→终态 |

两分支差异只在入口（B_LOCK 免确认、A_ENUM 必须点选），汇合后完全一致。

## 6. Prompt 工程 

### 6.1 系统提示词（状态机注入到每次调用）

```text
你是好特卖门店的设备报修填报助手，引导店员用最短路径完成报修单。
【采集范围】只允许采集以下表单字段：报修类别、报修详情（故障表现/产生原因/导致后果）、联系人、手机号码、问题照片或视频。
【禁止】1) 询问表单以外信息（如故障发生时间、天气、客流）；2) 编造字典外的枚举值；3) 在用户确认前生成提交动作；4) 一轮追问多个问题。
【风格】口语、简短、每次只处理一件事。所有输出按 reply_schema 返回 JSON。
```

### 6.2 类别识别（A_WAIT，LLM-XXX）

```text
## 任务
从店员的问题描述中识别报修类别。只能从 <类别字典> 中选择，禁止输出字典外的值。

## 类别字典（由工具 get_category_dict 注入）
{category_dict}

## 用户描述
{user_text}

## 输出 JSON Schema
{"candidates": [{"name": "字典内类别"}], "need_detail": true}

## 示例
描述："店里的冷藏风幕柜不制冷了，温度显示15度，鲜奶都下架了"
输出：{"candidates": [{"name": "制冷设备 - 风幕柜/立式冷柜"},
                     {"name": "制冷设备 - 卧式冰柜"}], "need_detail": true}
```

**不做置信度分流**：识别成功一律出 Top3 单选卡（首位为 AI 预选项），识别失败进 `FALLBACK` 全量点选；

### 6.3 报修详情三要素  提取和改写（DETAIL，LLM-XXX）

```text
## 任务
从描述中抽取报修详情三要素，并润色为规范短句。要素缺失时对应字段返回 null，并生成一句"仅针对缺失要素"的追问。
## 输出 JSON Schema
{"表现": "…", "原因": "…|null", "后果": "…|null", "追问": "…|null"}
## 边界
- 用户口语原意优先，不添加未提及的事实（原因常为"初步判断"）
- "追问"只能是：表现 / 原因 / 后果 三者之一的补齐请求
```

## 7. 防幻觉 和 结构化输出  注意的点

| 环节 | 机制 |
|---|---|
| 输出格式 | JSON mode；解析失败重试 1 次，再失败进降级 |
| 枚举校验 | 候选逐个与字典白名单比对，非法丢弃；丢弃后为空→FALLBACK |
| 候选排序 | Top3 首位预选仅影响卡片顺序——**A 分支必须用户点选才入库** |
| 详情校验 | 三要素 schema 校验，润色结果与原文一并展示可改 |
| 提交校验 | 前端 + 服务端双重校验 13 字段必填，缺一不进 DONE |

## 8. 会话草稿与退出恢复

会话即草稿：每次状态变更先 `draft_save` 再推送（Redis 单 Key JSON，TTL 7 天滑动续期，ver 乐观锁防并发）；错误退出（杀 App / 断网）零特殊处理，重进 `GET /sessions/{id}` 快照重放恢复。主动退出：前端弹「继续填写 / 保存退出 / 放弃」，keep 进 EXITED 保留草稿（重进提示续填），abandon 标记废弃。与老表单草稿不同 Key 空间，互不覆盖。

实现细节（生命周期图 / 数据留存 / 恢复时序图）：[会话草稿与退出恢复.md](../详细点/会话草稿与退出恢复.md)

## 9. 前后端接口

完整定义（请求 / 响应 JSON、SSE 事件流、MCP JSON-RPC 报文）：[接口文档.md](../详细点/接口文档.md)

| 接口 | 方法 | 说明 |
|---|---|---|
| `/api/sessions` | POST | 建会话，返回 session_id + 首屏消息 |
| `/api/sessions/{id}/messages` | POST | 七种消息 type；响应 SSE 流（typing→message→done） |
| `/api/sessions/{id}/upload` | POST | multipart 附件 → media_ids |
| `/api/sessions/{id}` | GET | 恢复会话（断点续填 / 换端） |
| `/api/sessions/{id}/submit` | POST | CONFIRM 提交（ver 乐观锁），调 create_repair_order |
| `/api/sessions/{id}/exit` | POST | 主动退出，mode=keep（存草稿）或 abandon（废弃） |

服务端消息类型 8 种（text / quick_cards / enum_card / photo_guide / contact_confirm / confirm_card / result / system_tip），与原型组件一一对应。

## 10. 工程降级与成本控制

| 故障 | 处理 |
|---|---|
| LLM 超时（>8s） | 重试 1 次 → 提示稍后 + Top6 卡片（纯规则可用） |
| LLM 整体不可用 | 降级卡片向导模式，不阻塞报修 |
| 识别 / 解析失败 | FALLBACK 全量点选 |
| 明道云提交失败 | 本地落待发表 + 定时重试 3 次 → 转人工 |
| SSE 断线 | GET 会话快照重放，消息不丢 |
| Redis 故障 | 降级内存会话，提交前强校验 |

成本限额（LLM 调用层统一拦截）：单人单天调用次数 + token 双限额、单会话 6 次、全局日配额熔断；超限降级卡片向导。

## 11. 埋点清单

| 事件 | 支撑指标 |
|---|---|
| session_start / session_end | 填报时长、步数 |
| branch_a_input / branch_b_card_click | 分支占比 |
| **enum_first_pick** | **类别识别准确率** |
| fallback_enter / switch_to_form | 兜底率、转老表单率 |
| session_exit / draft_resume | 中途放弃率、续填恢复率 |
