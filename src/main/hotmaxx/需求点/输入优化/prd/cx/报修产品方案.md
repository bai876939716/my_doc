# 门店报修产品方案 · V2.0（CX 闭环版）

版本：V2.0｜日期：2026-11-02｜状态：产品评审稿

配套文件：[交互流程图](./产品交互流程图.puml) · [可交互原型](./原型/门店报修-AI交互原型.html)

## 1. 本次要解决的问题

当前店员使用各自的明道云账号处理业务，企业需要承担相应账号成本。旧版方案主要解决“如何更轻松地填报”，尚未形成提交后的查询闭环。本次将报修能力收敛到现有 App：员工用自己的 App 身份进入，以统一的后台接入身份连接明道云，完成“填报 → 确认提交 → 查询本店记录 → 查看处理进度”。

**产品目标：门店员工不需要单独登录明道云，就能发起报修并查看本门店所有人的报修记录。** 企业侧维修受理、派单及处理仍沿用现有明道云流程，本期不重做维修后台。

“一个账号”指企业服务端统一接入身份，不是让所有店员共用同一套 App 登录凭据。App 员工身份、门店权限与实际报修人仍独立保留。能否通过现有明道云账号／应用凭证满足接入和授权、最终减少多少付费账号，需要由系统管理员结合现有配置验证，本方案不把节省额度视为已确认结果。

### 1.2 与旧版的变化

| 维度 | 旧版 | 本版 |
|---|---|---|
| 业务范围 | 填报输入优化 | 新建报修 + 本店记录 + 工单详情及进度 |
| 入口 | 原表单中的 AI 按钮 | App 服务助手 → 报修中心；卡片内“历史记录”直达列表 |
| 登录和归属 | 按登录人带出信息，身份边界不清晰 | App 用户身份与明道云接入身份分离，服务端校验门店权限 |
| 字段基准 | 大区、地址、门店属性等旧字段 | 以截图的 9 个可见字段为准；旧字段按下游需要隐藏映射 |
| 报修人 | 联系人可修改 | 报修人固定为当前员工；联系电话可以修改，不改变报修人 |
| 附件 | 照片或视频 | 本期现场照片；不开放视频，单张不超过 3MB |
| 提交结果 | 提交完成后结束对话 | 成功页可查看本单、查看本店全部记录、再报修 |
| 查询范围 | 无 | 当前门店全部报修，不按明道云创建人或 App 提交人过滤 |
| 进度通知 | 描述为会推送 | 本期以主动查询为准；未验证通知能力前不承诺推送 |

## 2. 范围、角色与身份

### 2.1 本期范围

- **输入模块**：传统表单、AI 描述整理、缺失字段补齐、确认卡、提交、7 天草稿。
- **查询模块**：本店记录、工单编号／故障内容搜索、状态和时间筛选、分页、详情、处理时间线、刷新。
- **接入能力**：App 登录态校验、授权门店映射、统一接入明道云、提交幂等与结果核验、查询隔离。
- **本期不包含**：报销、费用审批、维修派单后台、用户撤销／修改已提交工单、催单、评价、确认完工、通知订阅。后续可根据真实工作流扩展。

### 2.2 身份与数据归属规则

| 概念 | 来源及规则 |
|---|---|
| App 操作人 | 后端从已验证登录态取得 `appUserId`；不得信任前端自行填写的员工 ID |
| 报修人 | 当前员工姓名 + 员工 ID，自动带出、只读。人员姓名用于展示，员工 ID 用于追溯 |
| 当前门店 | 优先沿用 App 当前门店；必须属于该员工的有效授权门店集合 |
| 单店员工 | 自动定位该店，不出现全量门店选择器 |
| 多店员工 | 只可在授权门店列表中切换；切换后列表、统计、草稿均按新门店重载 |
| 无有效门店 | 显示“暂未绑定可报修门店，请联系门店管理员”，阻止创建和查询；不回退到全部门店 |
| 明道云创建人 | 可能是统一接入账号，仅作为技术创建身份，不用于展示实际报修人或决定可见范围 |
| 业务门店键 | `storeId` 对应稳定业务主键，并映射明道云门店关联记录 ID；名称、编号仅辅助展示 |

查询条件必须满足：**App 登录有效 AND 所选门店属于授权集合 AND 工单归属门店等于所选门店**。同店甲、乙员工均可查看该店全部报修，包括接入前可正确映射归属的历史数据。跨店记录即使知道工单编号或详情链接也不可访问。

员工调店／离职后按当前权限重新鉴权，不沿用旧缓存权限。门店改名不改变归属；历史记录缺少稳定门店键时，先做确定性映射及异常清单，由运营确认后纳入查询，不做名称模糊匹配。提交时同时保留当时的门店名称和报修人姓名快照。

## 3. 入口与页面结构

```text
App → 服务助手
  └─ 我要报修卡片
       ├─ 卡片主体 → 报修中心 → 新建报修（默认传统表单，可切 AI）
       └─ 历史记录 → 报修中心 → 本店记录

新建报修 → 核对确认 → 提交结果 → 查看本单详情／本店记录／再报修
本店记录 → 搜索／筛选 → 工单详情 → 处理时间线 → 返回原列表位置
```

报修中心顶部固定显示“门店编号 + 名称”和当前报修人，一级切换为“新建报修／本店记录”。“历史记录”仍可作为 App 上的快捷入口，列表页使用“本店记录”明确这是门店维度，而非“我的报修”。截图中重复出现的两张“我要报修”卡片不照搬，正式入口保留一张，灰度期以配置切换新旧路径。

## 4. 新版字段及采集策略

### 4.1 可见字段（以截图为基准）

| 字段 | 必填及编辑 | 来源／交互 | 校验与写入规则 |
|---|---|---|---|
| 门店名称 | 系统必备；不可自由编辑 | App 当前授权门店，显示编号 + 名称 | 服务端复核权限后写入门店关联 ID；通过门店选择器切换 |
| 报修类别 | 必填，可改 | 传统表单选择；AI 推荐后由用户确认 | 必须匹配有效字典 ID；未知或低置信度时展示候选，不猜测枚举 |
| 报修人员 | 系统必备；只读 | 当前 App 员工姓名 | 写入真实员工 ID／姓名，不能以统一账号替代；下游成员字段不可用时增加独立业务字段承载 |
| 报修日期 | 系统必备；只读 | 页面显示当前业务日期 | 最终以服务端成功受理时间（Asia/Shanghai）记录；不使用客户端时间作为审计依据 |
| 描述具体故障 | 必填，可改 | 自由文本或 AI 整理 | 去空白后 1～100 字；按 Unicode 码点计数，前后端一致；AI 超长时提示用户精简确认，不静默截断 |
| 现场照片（3MB 以内） | 必填，可增删／预览 | 手机相册／拍照 | 至少 1 张，单张 ≤ 3 × 1024 × 1024 bytes；本期建议最多 6 张、JPEG／PNG／WebP。数量、格式及字节口径需与现有接口确认；不支持视频 |
| 期望上门 | 必填，可改 | 按后端配置选择 | 截图未展开选项。本原型用日期时间演示，要求晚于当前时间；生产需确认是时段枚举还是日期时间，不能先写死 |
| 影响营业 | 必填，可改 | 是／否显式选择 | 不默认“否”；AI 只能建议，须由用户确认；仅有“设备坏了”不足以判断 |
| 联系电话 | 必填，可改 | 优先员工资料预填；缺失时输入 | 修改电话不修改报修人。本原型使用大陆 11 位手机号演示；生产是否支持座机／其他地区号码待业务确认 |

截图的三项系统字段未标红，但仍是创建记录的前置数据；系统带出失败时阻止提交并提示重试，不能让用户随意补一个门店／报修人。

### 4.2 旧字段与隐藏业务字段

- 大区、门店属性、门店地址、营业时间：从门店主数据映射，若下游仍要求则作为隐藏字段传入；不额外追问店员。主数据缺失且下游强制必填时明确返回配置异常。
- “联系人”不再单独出现在本期表单；截图中的“报修人员”与“联系电话”分别承担身份和联络作用。
- 新增／明确隐藏字段：`source=app`、`appUserId`、`reporterEmployeeId`、`storeId`、门店关联 ID、`clientRequestId`、提交时间、记录来源方式（form/ai）、业务工单 ID、明道云行 ID。
- AI 不要求店员提供“故障原因”；用户推测必须写成“店员反馈／疑似”，不能变成已确认诊断。

## 5. 输入模块

### 5.1 传统表单

进入即展示“基础信息”和“期望处理”两组，与截图字段顺序一致。顶部保留“AI 助手填报”卡片。底部“核对并提交”先校验必填项、长度、照片上传结果、时间与电话，再展示确认单；确认单点击“确认提交报修”才触发真实创建。

### 5.2 AI 助手填报

1. 自动带出门店、报修人、日期及可用电话，提示“描述故障现象、发生时间和影响，知道多少说多少”。
2. 保留高频卡片降低输入成本，设备描述用于推荐类别；卡片不是未经确认的正式字典值。
3. AI 整理 100 字以内的故障描述，并给出有效类别候选。类别只允许选有效字典；识别失败可手动选择，字典不存在“其他”时不生成“其他”。
4. 用结构化补充卡一次收集缺失的照片、期望上门、影响营业、联系电话。已有内容不重复追问；AI 不可替用户默认营业影响。
5. 展示完整 9 字段确认单。门店／报修人／日期只读，其他字段可回编辑区修改。修改后须查看最新确认单再提交。
6. 用户点击确认提交；按钮进入提交中并禁用重复点击；仅收到明确成功结果才进入成功页。

传统表单和 AI 各自有独立草稿，按 `App 用户 + 门店 + 输入方式` 隔离，切换方式时不覆盖。生产草稿保留 7 天，过期清理；附件应使用服务端临时附件 ID 并有到期回收机制，上传未完成不能提交。离开提示“继续填写／保存草稿退出／放弃本次”，成功后只清除已提交的那一份草稿。

### 5.3 提交结果与重复提交

| 状态 | 页面表现 | 后续动作 |
|---|---|---|
| 明确成功 | 展示工单编号、当前状态、当前门店、提交时间 | “查看本单进度”为主按钮；另有“本店全部记录”“再报修一单” |
| 已确认失败 | 展示可读原因，保留全部输入及已成功上传附件 | 修正／重试；同一业务请求不得生成重复记录 |
| 超时、结果未知 | “正在确认提交结果”，展示查询进度入口 | 使用同一个 `clientRequestId` 核验；不能直接宣称失败、换新 ID 重建 |
| 已成功但列表暂未同步 | 成功页保留已确认的工单信息；列表顶部可显示临时回执卡“同步中” | 通过业务 ID 定向刷新并合并去重，不能因为暂时查不到就提示重新报修 |

建议由接入服务维护幂等请求台账；若明道云不能按请求号去重，则在写入前串行化相同请求并先核验既有行。待确认状态下锁定该份草稿，查询结果明确不存在／可重试后再释放；草稿修改成新的报修意图才生成新请求号。

## 6. 查询模块：本店记录

### 6.1 列表

顶部始终显示当前门店和“本门店所有人的报修记录”，不出现“当前账号创建的记录”。默认全部状态、全部时间，按提交时间倒序，同时间按业务 ID 稳定排序，每页 20 条，“加载更多”保留已有结果。

每张卡片展示：工单编号、状态、类别、故障摘要、提交时间、报修人、是否影响营业。点卡片进入详情。新增工单出现在当前门店列表顶部，返回时恢复原关键词、筛选及滚动位置。

搜索支持工单编号精确／部分匹配、故障描述关键词匹配，点击“搜索”或键盘确认后执行；空关键词恢复列表。条件组合为：`当前门店 AND 状态条件 AND 时间条件 AND（工单编号包含关键词 OR 故障描述包含关键词）`。关键词作为普通文本处理，不拼接进动态指令或 SQL。

筛选建议：全部／待受理／处理中／已完成／已关闭，时间为全部时间／近 7 天／近 30 天。时间范围按 Asia/Shanghai 的自然日计算，含今天，不包含未来提交时间。统计数按当前门店全量数据计算，不拿当前页数量冒充总量；后端不支持准确总数时省略统计，不影响列表。

### 6.2 业务状态展示（待对照真实工作流确认）

| 前台归并状态 | 示例来源状态 | 展示规则 |
|---|---|---|
| 待受理 | 已提交、待受理、待派单 | 显示源状态作为补充说明，等待后端推进 |
| 处理中 | 已派单、已接单、维修中、待配件 | 详情尽量展示真实子状态及更新时间 |
| 已完成 | 已完工、已完成 | 以业务约定的完成节点为准，不根据时间推测 |
| 已关闭 | 已取消、已关闭、已驳回 | 显示具体源状态／原因，不将驳回伪装成成功完成 |
| 状态待确认 | 未知或尚未映射的源状态 | 在“全部”可见，显示原始可读状态；不得默认归到已完成 |

### 6.3 详情与处理进度

详情从列表或提交成功页进入，均须重新检查当前用户对工单门店的权限。展示内容：

- 工单编号、当前状态、来源更新时间。
- 处理时间线：提交、受理／派单、处理、完成／关闭等**实际已经发生**的节点及时间；不伪造未来节点或完成时间。数据仅有当前状态时显示“暂无可展示的过程记录”。
- 提交信息：9 个字段完整回显；现场照片可预览。
- 处理信息：处理说明、安排上门时间、处理结果、处理人／可公开的联系电话，仅展示明道云真实返回且获准面向门店展示的字段；无数据则不出现操作入口。
- 底部“刷新进度”；非静默轮询。期望上门是店员需求，不等于实际安排，不承诺 SLA。

本期不提供编辑状态、撤销或确认完工按钮。若后端有“待门店确认”节点，先展示真实状态与说明，由评审确认是否另行增加操作范围。

### 6.4 查询异常

| 场景 | 展示及动作 |
|---|---|
| 首次加载 | 骨架／加载中；不提前显示“暂无数据” |
| 本店确无记录 | “本店暂无报修记录”，可新建报修 |
| 筛选后无结果 | “没有找到符合条件的报修记录”，提供清除条件 |
| 查询失败 | “暂时无法获取报修记录”，提供重试；不当作空列表 |
| 已有内容刷新失败 | 保留旧内容，标记数据时间和刷新失败，允许重试 |
| 翻页失败 | 保留前几页，提供重试当前页，不重置到第一页 |
| 详情不存在／已无权限 | “该记录不存在或当前无权查看”，返回列表；不透露其他门店信息 |
| 门店权限失效 | 清理当前门店内容，提示重新选择有效门店或联系管理员 |
| 切换门店 | 清空旧店列表、分页、统计、详情和搜索条件；取消或丢弃旧请求响应 |

## 7. 服务端与明道云 MCP 的衔接

```text
App（个人登录态）
  → 报修接入服务：员工身份、授权门店、字段校验、业务审计、幂等、状态映射
    → 明道云 MCP 适配层（统一后台凭证）
      → 明道云报修工作表 + 现有维修工作流
```

MCP 用于后台调用能力，不承担最终权限判断。AI 仅负责输入辅助；查询条件由接入服务的确定性逻辑构建，不让模型决定门店范围。前端不接收统一账号密码、应用密钥或 MCP 凭证。

### 7.1 逻辑能力清单（非真实工具名）

| 逻辑能力 | 输入 | 输出／约束 |
|---|---|---|
| 获取身份和授权门店 | App 登录凭据 | 员工身份、授权门店 ID、默认门店；来自现有 App 组织体系 |
| 获取填报元数据 | 已授权门店 | 有效报修类别、期望上门类型、附件限制、必要默认字段 |
| 上传现场照片 | 已授权门店、文件 | 临时附件 ID、上传状态；检查类型、大小和归属 |
| 创建报修 | `clientRequestId` + 业务字段 | 明确成功／失败／待核验，业务 ID、明道云行 ID、初始状态 |
| 核验提交结果 | `clientRequestId` | 台账状态与既有记录；沿用原请求，不产生副作用 |
| 查询本店记录 | `storeId`、关键词、状态、时间、分页游标 | 明道云查询执行前强制附加门店条件；返回列表、下一页、可用时的准确统计 |
| 查询详情与进度 | 工单 ID + 当前门店 | 先鉴权，再返回允许展示的字段、附件访问链接、真实处理节点 |

分页游标需绑定门店及筛选条件；游标不能跨门店复用。明道云服务若不能直接完成某个过滤，应由服务端在**已限定门店的数据集**内完成并正确分页，不能拉全企业数据到 App 后再过滤。缓存按用户权限版本、门店和查询条件隔离，权限失效时立即失效。列表请求采用请求版本号，切店后晚到的旧响应不得覆盖新店页面。

附件访问亦需验证归属；返回短时授权链接或受鉴权代理地址。审计保存真实 App 操作人、门店、请求号、工单 ID、结果及时间，避免把统一接入账号误记为实际报修员工。

### 7.2 联调需要落表的映射

| 映射项 | 需确认内容 |
|---|---|
| 门店 | App 稳定门店 ID → 明道云关联表行 ID；历史门店归属补齐规则 |
| 员工 | App 员工 ID／姓名 → 业务报修人字段；原成员字段的兼容策略 |
| 表单 | 9 个可见字段及下游隐藏必填字段的控件 ID、类型、长度、枚举 ID |
| 工单 | 业务编号生成规则、创建行 ID、幂等请求号字段或台账关联 |
| 进度 | 源状态 → 展示分组；节点日志来源、处理结果字段、允许公开的联系人字段 |
| 附件 | 上传流程、格式、数量、大小、有效期、读权限 |
| MCP | 列表过滤、分页、搜索、单条查询、日志读取、写入和结果核验的实际能力及限流 |

若查询 MCP 已可用但无创建工具，输入链路沿用已验证的后台提交接口；两条链路均通过同一接入服务鉴权。上线前必须验证明道云原有按“创建人”派单／审批的逻辑是否受统一身份影响，确保路由依赖业务门店／报修人字段。

## 8. 核心演示剧本

### A. AI 填报后立即查到本单

店员在 11522 安徽商之都OK店进入“我要报修” → 点击 AI 助手 → 输入“冷柜从上午开始不制冷，饮料不够凉” → AI 生成草稿并推荐类别 → 店员确认类别、上传照片、选择期望上门、明确选择是否影响营业、核对电话 → 查看 9 字段确认单 → 确认提交 → 成功页查看本单进度 → 返回本店记录，最新工单位于顶部。

### B. 同店同事查看历史报修

另一位有同店权限的员工从 App 卡片内“历史记录”进入 → 看到本店不同报修人的记录 → 搜索工单编号／“冷柜” → 按处理中筛选 → 查看工单原始报修人、期望上门、当前进度和实际处理说明。列表没有因统一账号或个人提交人而丢失记录。

### C. 多店与异常

多店员工切至另一授权门店 → 搜索、列表、详情和草稿全部切换到新门店 → 返回原门店可继续原店未完成草稿。查询失败可重试；提交超时进入结果核验；重复点击不新增工单。无授权门店时无法填报／查记录。

## 9. 验收清单

| 编号 | 验收场景 | 通过标准 |
|---|---|---|

| A02 | 字段对齐 | 9 字段与截图一致；无旧版大区／地址等额外必填输入 |

| A05 | 双方式草稿 | 同人同店两方式独立；换店不串草稿；7 天过期；附件失效要求补传 |
| A06 | 成功闭环 | 成功后可打开本单详情，本店列表可找到本单；同步延迟有回执与刷新提示 |
| A07 | 同店全员记录 | 甲、乙不同 App 员工登录同店均能看见该店所有报修 |

| A10 | 状态与时间线 | 与明道云一致，未知状态不误归类，只显示真实节点，无日志时有明确说明 |

## 10. 指标与实施顺序

指标：填报完成率、填报耗时中位数、AI 采用率及转表单率、提交成功率、未知结果比例、重复工单数、提交后详情打开率、查询成功率／耗时、门店映射失败数、越权拦截次数。成本指标以实际减少的付费席位和新增接入成本计算，不只看创建账号数量。

按依赖推进，不沿用旧版未确认排期：① 完成字段、身份和状态映射；② 打通带门店权限的列表／详情查询；③ 打通传统表单、幂等提交及成功回查；④ 接入 AI 填报；⑤ 单店及多店灰度、验证原工作流和历史数据后扩量。灰度异常可切回现有已验证入口，已创建工单不重复迁移或重建。

### 上线前必须确定的事项

1. 明道云统一接入身份及实际授权方式；是否影响账号计费或原审批流。
2. App 员工—门店权限的可信来源，门店稳定 ID 与历史记录映射。
3. 类别真实枚举、期望上门控件类型、电话格式及照片限制。
4. 明道云列表、详情、过程日志、上传、写入、请求号核验的实际能力。
5. 前台状态映射、可展示处理人信息、完成／关闭口径及刷新时效。

## 11. 原型使用说明

双击打开同目录 HTML，无外部网络依赖。沿用旧版视觉语言，新增服务助手入口、本店记录、详情时间线和成功回查。左侧及手机右上角提供演示选项：授权门店切换、查询失败、本店无记录、无权限、提交结果待确认、AI 不可用、恢复演示。

演示边界：AI 为本地规则模拟，不调用真实模型；提交在浏览器内生成演示记录，不写明道云；类别和状态均为演示字典；示例现场照片以“演示附件”占位。记录和草稿在当前浏览器本地保存，草稿 7 天过期；真实照片只保留在本次打开页面中，重新打开后需重新上传。原型提供可走通的主路径与异常样例，权限校验、MCP、真实上传、服务端幂等、生产分页等须按正文另行实现验收。
