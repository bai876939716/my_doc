## 1. 背景与产品定位

> **账号成本**：店员此前各自登录明道云处理报修/报销，明道云按账号收费，账号数随门店规模线性增长。
> **单账号方案**：明道云全公司只保留 **1 个服务账号**，由服务端 Agent 服务持有；店员只登录自研 App（服务助手），业务身份由 **登录态绑定的「门店 + 报修人员 + 联系电话」** 承载，不再依赖明道云账号体系。提交与查询全部经服务端 MCP 工具代理，前端零明道云凭据。

**现状与缺口（2026-11 新版表单已上线）：**

| 现状 | 问题 |
|---|---|
| 服务助手已有「我要报修」入口，新版表单 10 字段（见 §3） | 字段仍偏多，店员不知道类别怎么选、故障描述怎么写 |
| 「历史报修记录」页面已存在 | **暂无数据**——数据在明道云，未接通，报修只有输入没有回音 |

**本版定位**：在服务助手内交付**双模块闭环**——

```
服务助手（App · 首页双入口：两卡片同图标同名，仅以「新版」标签区分）
├── 我要报修 —— 传统表单（新版 10 字段）
└── 我要报修「新版」—— 对话式填报（v1 方案升级到新 10 字段）
      └ 提交成功页「查看报修记录」→ 形成「报修 → 查进度」完整闭环
```

## 2、核心设计点

| # | 原则 | 落地方式 |
|---|----------|----------|
| 1 | 输入方式并行，互不干扰 | 首页双入口：「我要报修」（传统表单）与「我要报修 · 新版」（对话）图标名称一致、仅以「新版」标签区分，随时切换，两边草稿独立、互不覆盖；表单页内保留「AI 助手填报」横幅作为切换路径。 |
| 2 | AI 预填、人确认 | AI 负责抽取与整理，生成「报修确认卡片」，用户点【确认提交】才入库。 |
| 3 | 能查不问、只问该问 | 门店/报修人员/报修日期自动带出；只问类别、故障描述、照片、期望上门、影响营业、电话。 |
| 4 | 高频预选 + 渐进式追问 | 首屏给高频故障快捷卡片（降低开口成本），先描述问题再定向补缺。 |
| 5 | 全程可改 | 确认卡片上任意字段可改，类别可重选。 |
| 6 | **单账号、服务端代理**（新） | 明道云唯一账号只在服务端；提交/查询走 MCP 工具，业务身份写进表单字段而非账号。 |
| 7 | **按门店隔离**（新） | 查询服务端按登录门店编号过滤后返回，店与店互不可见；单账号下的数据隔离靠这一层保证。 |
| 8 | **提交即可查、闭环**（新） | 提交成功页直达「历史报修记录」，进度随时可查。 |

## 3、表单字段拆解与获取策略（以 2026-11 新版表单为准）

> 新版「我要报修」共 10 个字段（旧版 13 字段中的 大区/门店编号/门店属性/门店地址/营业时间 已合并或移除，门店编号并入门店名称展示）。用户实际需要动手的从 10 项缩减至 **几步**。

### 1. 系统自动带出（能查不问）

| 字段名称 | 是否必填 | 获取逻辑与默认策略 |
| :--- | :--- |:-------------------------------|
| **门店名称** | ✅ | App 登录人绑定门店带出（编号+名称，如 `11522 安徽商之都OK店`） |
| **报修人员** | ✅ | 默认当前登录人姓名；**支持修改**（店长替店员报修场景） |
| **报修日期** | ✅ | 默认当天日期带出 |

### 2. 需要 AI 沟通输入的

| 字段名称 | 是否必填 | 获取逻辑与默认策略 |
| :--- | :--- |:-------------------------------|
| **报修类别** | ✅ | 枚举点选确认（AI 从描述识别 Top3 推荐，防选错驳回）；字典以明道云实际配置为准（主类：特别紧急 / 工程类 / 运营用具类，细分待对齐 ❗todo） |
| **描述具体故障** | ✅ | 自由描述（支持语音）→ AI 按「故障表现/原因/后果」整理，≤100 字 |
| **现场照片(3MB以内)** | ✅ | 拍摄/上传，AI 引导拍清问题部位 |
| **期望上门** | ✅ | 快捷选项（今天 / 明天 / 本周内 / 自选日期）|
| **影响营业** | ✅ | 是/否；AI 可从描述预推断（如「商品已下架」→是），用户确认 |
| **联系电话** | ✅ | 默认登录人手机号（+86），可修改 |

### 3. 选填

| 字段名称 | 是否必填 | 获取逻辑与默认策略 |
| :--- | :--- |:-------------------------------|
| **期望处理** | ⭕ | 用户口述期望的解决方式，AI 整理；不问可跳过 |

## 四、产品交互流程

> 完整交互流程图：[产品交互流程图.puml](./产品交互流程图.puml)

### 关键环节说明
1. **入口**：App「服务助手」首页两个入口卡片，图标、名称、描述与现有卡片完全一致，仅第二张多「新版」标签——「我要报修」（进入传统表单）与「我要报修 · 新版」（点整卡直接进入对话）；两卡片内均含小号「历史提报记录」直达记录查询。
2. **AI 入口**：首页「我要报修 · 新版」点整卡直接进入对话（表单页顶部「AI 助手填报」横幅为次要切换路径），进入后顶部状态条：`📍 11522 安徽商之都OK店 ｜ 报修人：白云翔 138****1234 [修改]`。
3. **高频预选卡片**：首屏不让用户面对空白输入框，直接给出高频故障卡片（❄ 冷柜/空调不制冷、💻 收银机/扫码枪故障、💡 照明/招牌灯不亮、🛍️ 购物袋/物料质量、🚰 水电/下水道、🔧 货架/门锁）。
4. **类别获取**：口语问题映射为明道云标准枚举，易混淆类别给 Top3 点选，AI 不猜。
5. **预填确认**：10 字段汇总为确认卡片，扫一眼改两处即可提交。
6. **闭环**：提交成功 → 单号 +「查看报修记录」直达记录模块。

## 六、报修记录查询模块设计（新增）

> 补齐闭环：报修不只是「填完就走」，进度随时可查。

| 项 | 设计 |
|---|---|
| **入口** | ① 服务助手两个入口卡片（我要报修 / 我要报修 · 新版）内的「历史提报记录」；② 提交成功页「查看报修记录」 |
| **数据链路** | App → Agent 服务 → MCP 查询工具 → 明道云（单账号）→ **服务端按门店编号过滤** → 返回本店记录 |
| **门店范围** | 固定为登录人绑定门店，**不可切店**（单账号下的数据隔离关键） |
| **列表** | 状态 Tab：全部 / 处理中 / 已完成；下拉分页加载 |
| **列表卡片** | 报修单号、报修类别、状态、提交时间、期望上门 |
| **详情** | 全字段回显 + 现场照片 + **处理进度时间线**（提交 → 派单 → 上门维修 → 完工验收；状态枚举与明道云映射待对齐 ❗todo） |
| **刷新** | 进入拉取 + 手动刷新；本期不做实时推送 |
| **MCP 工具要求** | `list_repair_orders(store_id, status, page)`、`get_repair_order(order_id)`（工具命名以技术方案为准） |

## 七、兜底方案

| 场景 | 兜底策略 |
|----------|--------------------------------|
| 类别匹配失败 | AI 不猜枚举：降级为全量类别点选或「其他」 |
| AI 服务不可用 | 聊天入口降级提示「暂不可用」，自动引导回传统表单，绝不阻塞报修 |
| 用户主动退出 | 返回时弹「继续填写 / 保存草稿退出 / 放弃本次报修」；草稿保留 7 天，重进提示「继续上次报修」 |
| 明道云接口异常（新） | **提交失败**：本地暂存待网络恢复自动重试，绝不丢单；**查询失败**：提示稍后再试 + 人工客服电话兜底 |
| 门店过滤异常（新） | 查无数据时区分「本店确实无记录」与「过滤异常」，异常时引导刷新重试，不展示空白误导用户 |

## 八、度量指标

| 指标 | 定义与采集方式 |
|-----------|--------------------------|
| 填报时长和步数 | 从进入 AI 会话到提交成功的耗时和完成的步数 |
| 报修执行完成成功率 | 是否有卡壳，失败案例 |
| 类别识别准确率 | 方式A中 AI 识别类别与用户最终确认类别的一致 |
| AI 入口渗透率 | AI 填报单量 / 总报修单量 |
| 转老表单率 | 进入 AI 会话后切回老表单的占比 |
| 中途放弃与续填率 | 主动退出（保存/放弃）占比；保存后重进「继续上次报修」的恢复率 |
| **明道云账号数**（新） | 活跃明道云账号数收敛情况（目标：门店侧归零，仅剩 1 个服务账号） |
| **闭环查看率**（新） | 提交后 7 天内点击过「查看报修记录」的单量占比 |
| **查询模块使用度**（新） | 记录模块周活店数 / 店均查询次数 |
