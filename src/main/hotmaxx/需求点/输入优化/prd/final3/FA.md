## 1. 背景与目标

### 1.1 背景

- 目前门店的报修、报销业务由店长登录明道云处理，明道云按账号收费，**账号使用成本**较高。

- 报修、报销过程表单录入过程字段繁杂 **用户体验较差**。

### 1.2 目标

- **AI 赋能，对话式报修**：通过 AI 对话的方式实现报信息录入——本期先落地报修的信息录入3，AI 完成类别识别与信息整理，确认后提交。

- **剥离门店账号，降低使用成本**：明道云全公司只保留一个服务账号 ，通过单账号实现报修单的**录入和查询**——历史报修记录经 API 查询、按用户过滤展示，省掉各门店的账号费用。

## 2、核心设计点

| # | 原则 | 落地方式                                         |
|---|----------|----------------------------------------------|
| 1 | 输入方式并行，互不干扰 | 首页入口：灰度切换新旧入口按钮，新入口对话式录入 ，对话页面放置切回表单录入的按钮做兜底 |
| 2 | AI 预填、人确认 | AI 负责抽取与整理，生成「报修确认卡片」，用户点【确认提交】才入库。          |
| 3 | 能查不问、只问该问 | 门店/报修人员/报修日期自动带出；只问类别、故障描述、照片、期望上门、影响营业、电话。  |
| 4 | 高频预选 + 渐进式追问 | 首屏给高频故障快捷卡片（降低开口成本），先描述问题再定向补缺。              |
| 5 | 全程可改 | 确认卡片上任意字段可改，类别可重选。                           |
| 6 | **单账号、服务端代理** | 明道云唯一账号只在服务端；提交/查询走 MCP 工具，业务身份写进表单字段而非账号。   |
| 7 | **按门店隔离** | 查询服务端按登录门店编号过滤后返回，店与店互不可见；单账号下的数据隔离靠这一层保证。   |

## 3、表单字段拆解与获取策略

> 新版「我要报修」共 10 个字段，用户实际需要动手的从 10 项缩减至 **几步**。

### 1. 系统自动带出（能查不问）

| 字段名称 | 是否必填 | 获取逻辑与默认策略 |
| :--- | :--- |:-------------------------------|
| **门店名称** | ✅ | App 登录人绑定门店带出（编号+名称，如 `11522 安徽商之都OK店`） |
| **报修人员** | ✅ | 默认当前登录人姓名；**支持修改**（店长替店员报修场景） |
| **报修日期** | ✅ | 默认当天日期带出 |

### 2. 需要 AI 沟通输入的

| 字段名称       | 是否必填 | 获取逻辑与默认策略 |
|:-----------| :--- |:-------------------------------|
| **报修类别**   | ✅ | 枚举点选确认。**自由描述路径**：AI 从描述识别 Top3 推荐；**高频卡片路径**：卡片即类别，直接锁定，不再追问（字典以明道云实际配置为准，主类：特别紧急 / 工程类 / 运营用具类，细分待对齐 ❗todo） |
| **描述具体故障** | ✅ | **自由描述路径**：一句大白话说清哪儿坏了（支持语音），AI 按「故障表现/原因/影响」范式整理，≤100 字；**高频卡片路径**：无需描述，提交时自动填写「类别 + 详见现场照片」，可随时打字补充 |
| **现场照片**   | ✅ | 拍摄/上传，AI 引导拍清问题部位 |
| **期望上门**   | ✅ | 二选一：**维修人员尽快上门 / 可等待安排** |
| **影响营业**   | ✅ | 是/否；AI 可从描述预推断（如「商品已下架」→是），用户确认 |
| **联系电话**   | ✅ | 默认登录人手机号（+86），可修改 |

### 3. 选填

| 字段名称 | 是否必填 | 获取逻辑与默认策略 |
| :--- | :--- |:-------------------------------|
| **期望处理** | ⭕ | 用户口述期望的解决方式，AI 整理；不问可跳过 |

## 四、产品交互流程

> 完整交互流程图：[产品交互流程图.puml](./产品交互流程图.puml)

### 关键环节说明
1. **入口**：App「服务助手」首页新增卡片，图标、名称、描述与现有卡片完全一致，灰度切换 。
2. **AI 入口**：仅首页「我要报修」点整卡进入对话，进入后顶部状态条：`📍 11522 安徽商之都OK店 ｜ 报修人：白云翔 138****1234 [修改]`。
3. **高频预选卡片**：首屏给出高频故障卡片（❄ 冷柜/空调不制冷、💻 收银机/扫码枪故障、💡 照明/招牌灯不亮、🛍️ 购物袋/物料质量、🚰 水电/下水道、🔧 货架/门锁）。**点卡片即锁定报修类别，不再追问类别与故障描述**，直接走后续流程。
4. **类别获取（先通过描述路径识别）**：口语描述映射为明道云标准枚举，AI 识别后给 Top3 点选确认，识别不了给全量列表，AI 不猜。「具体表现、可能原因、导致后果」只是 AI 整理描述的**范式**，不生硬甩给用户——话术口语化引导（见剧本）。
5. **预填确认**：10 字段汇总为确认卡片，扫一眼改两处即可提交。
6. **闭环**：提交成功 → 单号 +「查看报修记录」直达记录模块。

## 七、兜底方案

| 场景 | 兜底策略                                               |
|----------|----------------------------------------------------|
| 类别匹配失败 | AI 不猜枚举：降级为全量类别点选或「其他」                             |
| AI 服务不可用 | 聊天入口降级提示「暂不可用」，自动引导回传统表单，绝不阻塞报修                    |
| 用户主动退出 | 返回时弹「继续填写 / 保存草稿退出 / 放弃本次报修」；草稿保留 7 天，重进提示「继续上次报修」 |
| 明道云接口异常 | **提交、查询失败**：提示稍后再试 + 人工客服电话兜底                      |

## 八、度量指标

| 指标 | 定义与采集方式                         |
|-----------|---------------------------------|
| **查询模块使用度** | 记录模块使用次数                        |
| 填报时长和步数 | 从进入 AI 会话到提交成功的耗时和完成的步数         |
| 报修执行完成成功率 | 是否有卡壳，失败案例                      |
| 类别识别准确率 | 方式A中 AI 识别类别与用户最终确认类别的一致        |
| AI 入口渗透率 | AI 填报单量 / 总报修单量                 |
| 转老表单率 | 进入 AI 会话后切回老表单的占比               |
| 中途放弃与续填率 | 主动退出（保存/放弃）占比；保存后重进「继续上次报修」的恢复率 |
