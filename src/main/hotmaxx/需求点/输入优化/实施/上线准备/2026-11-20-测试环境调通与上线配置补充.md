## 2. App 请求地址与内部转发地址

两者用途不同：

```text
HotShop App
  → https://{gateway-host}/agent/repair/v1/sessions
  → 公共网关查询接口登记
  → http://{Java Service 内网域名}:{端口}/agent/repair/v1/sessions
```

- App 配置的是公共网关地址，不直接访问 `dev-java-...` 内网域名。
- 公共平台登记的是网关访问 Java Service 的协议、内网域名和端口。
- App 请求需要带 HotShop 登录 token 和实际的 `X-PlatformId`。
- dev 使用 `gateway-dev.hotmaxx.cn`；生产网关地址沿用 HotShop App 现有生产配置，不把 dev 域名写死到 App。

## 3. 新增登记后不会立刻生效

网关每 60 秒从数据库刷新一次接口列表。新增登记后立即请求，可能仍返回：

```json
{"code":401,"msg":"未获取到接口信息","data":null}
```

先确认公共平台能查到记录，再等待一个刷新周期后重试；不需要因为这个提示直接重启网关。

本次还验证了：如果仍提示“未获取到接口信息”，请求尚未进入 Java；如果返回 Java 统一响应格式和 `reqId`，说明登记已经生效，应继续查 Java 日志。

## 4. Java 用户身份解析兼容问题（本地已修，待发布验证）

### 现象

使用有效的 HotShop token 创建会话，HTTP 状态为 200，但业务响应为：

```json
{"code":401,"msg":"未授权","data":null,"success":false,"reqId":"..."}
```

同一个 token 调已有 HotShop 商品接口成功，因此不是 token 失效。

### 原因

请求已经到达 Java，且请求头中存在网关写入的 `x-userinfo`、`x-headeruid`。但报修 Controller 接收 `HotmaxxHeader` 参数，触发旧公共组件提前解析身份，组件没有从当前网关请求头中解析出所需信息，直接抛出“未授权”，报修转发方法和 Python Agent 都没有执行。

### 本地修复

`provider-biz-ai-middle/src/main/java/com/hotmaxx/biz/controller/RepairAgentController.java`：

- 删除 `HotmaxxHeader` 方法参数，避免触发旧组件的错误解析。
- 改读网关验证 token 后覆盖写入的 `X-HeaderUid`，再按原逻辑转成 Python Agent 需要的 `X-Uid`。
- 不信任客户端自行传入的 `X-Uid`；网关会覆盖客户端传入的同名 `X-HeaderUid`。

本地仅有该 Java 文件改动，JDK 8 编译已通过；尚未提交、尚未发布，不能把当前状态记为测试环境已调通。

上线包必须包含这项 Java 修复。发布 dev 后先用同一请求复测，再推进生产；只改公共平台配置不能解决这个 401。

## 6. 公共平台登记完整清单（报修 AI 全部接口，2026-11-20 晚补）

前面第 1 节只登记了创建会话一个入口，这里是全部应登记条目。分两组，用途别混淆：

- **A 组：App → Java 转发层**（`provider-biz-ai-middle`）。真实 App 链路必须登记；本地演示页直连 Agent，用不到。
- **B 组：本地 Python Agent → base-shop**。仅本机经 gateway-dev 联调需要；Agent 部署到集群后走内网直调，不需要登记。Java 转发层 → Agent 这段也是集群内直调（`dev-python-provider-agent-server-center-svc.python.svc.cluster.local:8000`），同样不需要登记。

公共项（各条相同）：系统 HotShop、启用、数据权限关闭、验证token不鉴权、info/debug 日志关闭、预警 1/500、协议 `http://`、端口 `80` 或留空。

| 组 | 地址 | 方式 | 域名 | 用途 | dev 状态 |
|---|---|---|---|---|---|
| A | `/agent/repair/v1/sessions` | POST | `dev-java-provider-biz-ai-middle-svc.dev` | 创建会话 | ✅ 已登记（见第 1 节），通配生效后由下面的 POST 通配接管 |
| A | `/agent/repair/*` | POST | 同上 | 建会话/发消息/提交/退出 | ⬜ 待补（通配） |
| A | `/agent/repair/*` | GET | 同上 | 查询会话 | ⬜ 待补（通配） |
| B | `/shop/infoByCode` | GET | `dev-java-provider-base-shop-svc.dev` | 门店信息 | ✅ 已登记并调通（dev 库无 11522 门店，需换真实门店编码） |
| B | `/employee/queryByEmployeeId` | POST | 同上 | 员工档案（报修人/手机号） | ⬜ 待登记 |
| B | `/shop/queryShopOrgRegionList` | POST | 同上 | 门店大区 | ⬜ 待登记 |

**A 组通配说明**：

- 报修接口路径带会话 ID（如 `/agent/repair/v1/sessions/{sid}/messages`），精确登记覆盖不到，必须用 `/agent/repair/*` 通配；POST、GET 各一条，只登记 POST 会让查询会话的 GET 报“方法不允许”。
- 通配生效后，所有 `/agent/repair/` 下的请求都归一到通配记录匹配，第 1 节的精确 sessions 记录不再被命中，不必重复维护。
- 若通配保存后仍报“未获取到接口信息”，需网关运维把 `/agent/repair/*` 加入 Redis `go:gateway:wildcard` 集合。

**B 组注意**：

- 地址是 base-shop 服务真实路径，**不带 `/baseShop` 前缀**：网关按请求路径精确匹配并原样转发，带前缀会对不上、转发后也是 404。
- 调用头 `Authorization` 必须是 `Bearer <token>` 格式，裸 token 会报“登录失败,请传递正确的token”。
- **本地联调方式（2026-11-21 改为进程外代理，业务代码零侵入）**：Agent 代码不含任何网关鉴权逻辑，本机起 `AgentServerCenter/scripts/dev_gateway_proxy.py`（`export HOTSHOP_TOKEN='<HotShop dev token>'` 后 `uv run python scripts/dev_gateway_proxy.py`），`.env` 里 `BASE_SHOP_URL=http://127.0.0.1:18080`。代理转发到 gateway-dev 并自动补 Bearer 和 `X-PlatformId: 10`；token 只存在于代理进程环境变量，`.env` 不再保存个人 token。集群/生产内网直调，不需要代理。
- 员工接口参数在 query string（`?employeeId=`），无请求体；大区接口 body 是 JSON 数组 `["门店编码"]`，取 `data[0].parentOrgName`。

**报错对照**（均可能以 HTTP 200 返回，看 body 的 code/msg）：

| 返回 | 原因 |
|---|---|
| `未获取到接口信息` | 没登记 / 地址和请求路径不一致 / 协议或域名没填 / 未过 60 秒刷新 |
| `方法不允许` | 请求方式选错 |
| `登录失败,请传递正确的token` | Authorization 缺 `Bearer ` 前缀 |
| `该接口已被禁用` | 登记记录被停用 |
| `code:200` 但 `data:null` | 链路已通，dev 库查无此数据 |
