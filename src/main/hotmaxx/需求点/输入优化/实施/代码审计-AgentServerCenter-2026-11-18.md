## 第一部分 · 会真的伤到人的四个

### 1. Java 转发层忘了带身份头 → A 店员的草稿被 B 店员接着填

**现在的行为**：请求里没带 `X-Uid` 身份头时，服务端不拒绝，而是把人当成一个叫 `anonymous` 的公共用户。草稿是按"身份+门店"存的，于是不带身份的所有人共享同一条会话。

〔测〕两个用户都不带身份头，第二个直接拿到第一个填了一半的单子：

```
A sid=rp_c04f4c9bdfcac…  resumed=False
B sid=rp_c04f4c9bdfcac…  resumed=True     ← 同一条会话
B 重放到的消息数 =3  报修人=白云翔          ← B 看到了 A 的现场
```

**为什么会这样**：`app/api/routes.py:184,199,236,258,295` 五个接口都写着 `default="anonymous"`。而归属校验 `routes.py:144` 只比"会话主人是不是你"——两边都是 anonymous，必然通过。README 里"网关必须注入 X-Uid"是写在文档上的约定，服务端没有执行它。

**怎么修**：缺身份头直接 401 拒绝（听不懂就报错，别猜）。本地调试想省事，加一个 `ALLOW_ANONYMOUS=true` 开关显式放行。

✅ **已修（2026-11-18）**：`routes.py` 新增 `_uid` 依赖（缺头/空白头 → `401`＋`{"code":40101}`），五个接口签名换成 `Depends(_uid)`；开关 `ALLOW_ANONYMOUS` 默认 false。〔测〕无身份两人各建各的会话（直接被拒，压根拿不到 sid），带身份全流程不受影响，pytest 157 绿。详见 实现变更记录 #10。

**谁 / 工时**：我，约 1 小时（含测试）。
**要配套的**：ai-middle 转发层现在只做到 25%，这条得同时写进前端/后端对接文档——否则将来漏注入会被当成 Python 的 bug 查半天。

### 2. 员工档案里没填手机号的人，点开报修页面就是"服务不可用"

**现在的行为**：生成状态条上那句"138\*\*\*\*1234"掩码时，代码假设手机号一定存在、一定是 11 位。

〔测〕拿三种真实档案试：

| 档案里的手机号 | 结果 |
|---|---|
| 空（没录） | **整个建会话请求 503**，报 `TypeError: 'NoneType' object is not subscriptable`，用户页面都进不去 |
| `0551-65801234`（座机） | 显示成 `055****1234`（13 个字符，首尾重叠） |
| `8001`（店内短号） | 显示成 `800****8001`（数字重复了一遍） |
| 正常 11 位 | 正常 |

还有一层：电话槽位只认"1 开头 11 位"，所以**座机和短号永远填不进去**，用户会一直被弹"看着不像有效手机号"，走不掉。

**为什么会这样**：`app/core/engine.py:310` 无条件切片。同一套掩码逻辑在项目里有四份：`engine.py:40`（日志）、`engine.py:310`（带出）、`routes.py:244`（GET 收集状态）、`cards.py:29`（确认单）。只有 `cards.py` 那份做了长度判断和"未填"兜底——它的注释还写着"此前 v("phone")[:3] 直切会 TypeError"，说明同一个坑在别处已经踩过、修过，但没收口。

**怎么修**：①掩码收成一个 core 函数，非 11 位就原样显示或显示"未填"，绝不崩也绝不伪造；②档案没带出手机号时，把电话当作"没带出来"，正常开口问用户要，而不是摆一个号让他确认"用这个吗"。

✅ **已修（2026-11-18）**：①掩码四处收一处——新增 `app/core/redact.py:mask_phone`（缺值显示「未填」、11 位手机 `138****1234`、带区号座机 `0551****1234`、店内短号原样，不崩也绝不伪造），`engine.py` 的日志与状态条、`routes.py` 的 GET collected、`cards.py` 的确认单全部改调它；确认单与要号话术改读**槽位现值**，不再读档案快照。②带出来的号只有过得了本槽声明的识别器（`detector`，手机号=11 位大陆号）才配当"默认号"，否则改用口语要号 `repair.ask_phone_none`，并且 `use_default` 手势带着空值一律不清议程——两头堵死原来那条「未填 → 提交被打回 → 又弹同一张确认卡」的死循环。

〔测〕掩码九种输入（`None`/空/全空格/`13800001234`/`0551-65801234`/`010 6580 1234`/`+8613800001234`/`8001`/`abc`）+ 档案四种异常号（缺/空/座机/短号）建会话轮都不再抛 `TypeError`（就是它冒到 API 层变成 503、页面进不去），问电话一律改口语要号；老前端仍发 `use_default` 也不带空号冲进确认单；座机档案全程走到底能真实出单。pytest 157 → 172 绿（+15，变异测试反证过：把判据改回"永远放行"这 5 条立刻红）。详见 实现变更记录 #13。

**谁 / 工时**：我，约 2 小时。
**需要你拍的口径**：座机/店内短号到底算不算有效联系方式？放宽规则，还是话术里一开始就说明"留一个能接到的手机号"。

### 3. 逼着用户回答的两个问题，答案根本没进报修单

**现在的行为**：「期望上门」「影响营业」是必填、系统会开口问，但提交时只写进日志、不写进明道云单据。表上没有对应控件。

| 槽位 | 会不会问用户 | 会不会进单 |
|---|---|---|
| 报修类别 | 问（必须点选） | 进（按叶子 rowId 写，11-17 已打通） |
| **期望上门** | **必填，问** | **不进**（旧表无控件） |
| **影响营业** | **必填，问** | **不进**（同上） |
| 期望处理 | 选填，不问 | 不进 |
| 大区 | 不问 | 不进（代码写了但没接线，见第 7 条） |
| 门店名/编号/日期/描述/电话/照片 | — | 进 |

这件事的份量：FA-v2 里写的是"取消『特别紧急』大类，紧急程度改由『影响营业』字段表达"。也就是说，**这条产品主张现在断在最后一米**——问了，收了，没送出去。

另外：真实建单已经打开（`.env` 里 `REAL_ORDER_ENABLED=true`），而报修人和电话还是写死的假值，所以这几天进表的测试单联系人全是"白云翔 / 13800001234"。

**为什么会这样**：`app/skills/repair/fields.py:54` 明确列了三个"旧表无控件"的槽位，出路是加控件或并入详情，目前两个都没做。假值在 `app/skills/repair/tools.py:47-49`，代码里打了 ⚠️ mock 标记等员工档案接口。还有个更隐蔽的：点"用默认号码"这个手势只把电话从待办里划掉、**不写值**（`engine.py:380-383`），槽位里留着那个 mock 号，所以假号会一路带到单上。

**我建议的解法（两步走）**：

1. **今天你就去提需求**：让明道云管理员在报修表上加「期望上门」「影响营业」两个控件。这条有外部前置时间，越晚提越可能拖到上线后。

**谁 / 工时**：第 1 步只能你去提；第 2 步我 1 小时做完。
**不推荐的方案**：直接取消这两个提问。技术上最省事，但那是把产品主张删掉。

## 第二部分 · 不致命、但不还就变债的六条

### 5. 说好的"一张图跑所有业务"，目前还没做到

框架层（`app/core/`，本该业务无关）里还留着二十多处报修专属字段名：电话、照片、描述、类别、报修人、门店。提示词、字典、话术、字段白名单这四样确实已经外提到技能包了，但**"点选手势写到哪个槽位"** 和 **"提交前的逐项校验"** 没提。

举例：`engine.py:385` 收到"电话"手势就写死往 `phone` 槽写；`engine.py:800` 提交校验里又手写了一遍手机号正则，而这个槽位其实早就声明了 `detector="cn_mobile"`（`_admit` 里也已经有 detector 闸门可用）。

**结论**：README 那句"报销等后续业务以新技能包接入，框架层零改动"**目前不成立**——报销来了要动框架代码。

**我的建议**：现在不动大手术，但立刻做一件便宜事——把 README 那句话改成"报销接入时框架层需小改（清单见本审计 S-1 表）"，别让你自己和领导按错误的预期排期。真正的重构等报销立项时单开窗口做（估 2~3 天）。

### 6. 同一条"字典值怎么拼"的规则写了四遍，其中一遍漏了「购物袋」

字典是一棵树（主类 + 细分），拼平成 `"主类 - 细分"` 这个字符串的规则实现了三遍：`engine.py:204`、`skills/repair/__init__.py:23`、`api/routes.py:57`（内联）。`category_source.py:33` 的注释自己都写了"三处拷贝"。

第四遍在提示词里（`prompts.py:78`），而且写法不同，导致**没有细分项的主类被丢掉**。

〔测〕验证结果：

```
字典里的叶子主类（无细分）: [('购物袋', [])]
提示词中出现「购物袋」吗? -> 没有
引擎合法性白名单里有它吗? -> 有
```

后果：模型压根不知道"购物袋"是个合法类别，用户打字说"购物袋破了"，AI 提名的候选卡里不会出现它（点卡片和规则直填还活着，只有"AI 猜候选"这一路少了个选项）。

**怎么修**：四处收成同一个函数，顺手修掉漏的那个。另外 `routes.py:50` 还把"哪种手势允许点哪个字段"写死在接口层（类别 / 期望上门 / 影响营业），加字段就得回来改接口——这也是业务知识，应该跟着技能包声明走。

**谁 / 工时**：我，1~2 小时。**建议马上做**，因为这类"改一处忘三处"的 bug 一定还会再来。

### 7. 连点两次提交，防重复的保险装在了错的层

现在靠两层挡：接口层进来先查"这单出过单没有"（`routes.py:261`，而且在加锁之前查），以及工具层在进程内存里记一笔（`tools.py:81`）。真正该把关的**建单节点自己不查**（`engine.py:787`）。

两个请求几乎同时点提交：都通过接口层检查 → 被会话锁排队 → 第二个照样走到建单 → 这时只有那个进程内存字典能救。进程重启、或者将来多开副本，就救不了。

这不是我瞎担心：`tools.py:69` 的注释写着"双单窗口由建单先占位方案堵（真实建单接通时落地）"，但同一个文件 `:138` 的 TODO 承认还没做。你们自己把"连点提交"标成了红线场景。

**怎么修**：建单节点开头加一行守卫——已经有单号就直接返回原单号。半小时。

### 8. 每小时会有一个用户的某一轮特别慢

类别字典现在从明道云在线拉，缓存 1 小时。缓存一过期，**正好撞上这个请求的那个人**要在自己的响应时间里现场翻页拉完整张分类表、重建树。你们自己在 `mingdao.py:34` 的注释里记录过实测："Mac 到 b.hotmaxx.cn 首次 TLS 握手可达 6.8 秒"。

**怎么修**：过期了先把旧值返回给用户，后台线程悄悄刷新（或者学 `pgstore.py` 那个清理线程，挂个定时器提前刷）。1~2 小时。
