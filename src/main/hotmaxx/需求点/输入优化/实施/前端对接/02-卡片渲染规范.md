# 02 · 卡片渲染规范（10 种服务端卡片 × 6 种用户手势）

> 核心模型：对话流 = 一串 `messages`，每条 `{seq, type, data}`。`type` 决定渲染成什么；用户的操作回发到 `POST /messages`，`type` 决定含义。**前端只渲染、回发，不决策。**
> 正式版 HTML 里每张卡片都有现成实现（脚本里的 `RENDER` 对象），要改样式抄着改即可，协议以本文为准。

## 用户手势（6 种，`POST /sessions/{sid}/messages` 的 body）

| type | 附加字段 | 什么时候发 |
|---|---|---|
| `text` | content（≤500 字） | 输入框打字 / 语音转文字后 |
| `card` | card_id | 点高频卡片（开场那 6 张） |
| `enum_pick` | field / value | 点类别单选卡（含确认单上【重选类别】） |
| `seg_pick` | field / value | 点二选一卡。**当前报修流程不会触发**（原"期望上门/影响营业"字段已下线），协议保留给以后的技能包 |
| `upload_done` | attachments: `[{name, url}]` | 前端直传明道云成功后通知后端 |
| `phone` | use_default 或 phone | 电话确认卡二选一 |

## 服务端卡片（10 种）

### 1. `status_bar` 状态条
`{store, reporter, phone_masked}` —— 页面顶部固定条：📍门店 ｜ 报修人 电话 [修改]。只在首屏出现一次（重复出现时覆盖刷新）。

### 2. `text` 文本气泡
`{content}` —— 普通对话气泡，支持 `**加粗**` 简单标记。所有 AI 话术都是它。

### 3. `quick_cards` 高频卡片墙
`{cards: [{id, icon, title}]}` —— 6 张常见故障卡（冷柜/收银机/照明灯/空调/招牌灯/断电着火漏水）。点整卡 → 发 `{"type":"card","card_id":"xxx"}`。点完这面卡墙就完成使命，后端不再重发。

### 4. `enum_card` 类别单选卡 ⭐核心
`{field, mode(top3|full|grouped), options, preselect, grouped?}` —— 三种形态：

- **top3**：AI 提名 2~3 个候选（`options` 是字符串数组，平铺竖排）。`preselect≥0` 时该项高亮预选——**只是视觉提示，用户必须点一下才生效**（AI 不代替用户选类别）。响应里同时带 `grouped` 字段（全量两级联动）：top3 只是本轮提名不是全集，确认单上「重选类别」的弹窗要用 `grouped` 做数据源。
- **grouped**：全量两级联动（AI 没把握时下发）。`options: [{group:"一级类", items:["一级 - 细分", ...]}]`——先渲染一级类；点开进入该组 items（可返回）；**items 为空数组 = 叶子一级类（如「购物袋」），点组即完成选择**。
- **full**：平铺全量列表。仅平字典兜底用，当前报修类别是树形字典，实际不会下发。

点击项 → 统一发 `{"type":"enum_pick","field":"category","value":"选项原文"}`；grouped 的 value 就是 items 里的拍平串原文（叶子一级类 = 组名原文）。选项原文直接落库，前端不要改写字典词。

### 5. `photo_guide` 拍照引导
`{need_count, tips}` —— `tips` 是**纯字符串数组**（按当前类别挑的拍摄建议，如"设备整体"、"问题部位特写"），逐条列出即可。`need_count` 是建议张数，**实际 1 张即可继续**，单会话上限 5 张。

用户操作：点卡上「＋ 拍照 / 上传」→ 宿主调起相机/相册 → 明道云直传（见 01 的 `uploadPhotos` 钩子）→ 页面发 `{"type":"upload_done","attachments":[{"name":"现场.jpg","url":"完整http(s)地址"}]}`。

### 6. `seg_card` 二选一卡
`{field, options: [{value, label}]}` —— 横向两按钮，点击 → 发 `{"type":"seg_pick","field":"...","value":"..."}`。**当前报修流程不会下发**，渲染层保留为通用能力，收到未知 field 按通用逻辑渲染即可。

### 7. `phone_confirm` 电话确认卡
`{phone_masked, use_default}` —— "用本人号码 138\*\*\*\*1234 吗？"。两个动作：`{"type":"phone","use_default":true}` 或 `{"type":"phone","phone":"139..."}`（11 位校验在前端做）。

⚠️ **这张卡不一定出现**：员工档案没带出可用手机号（没录入 / 登记的是座机或店内短号）时，服务端只发一条 `text` 开口要号、不发这张卡。渲染逻辑不能假设"轮到电话就有卡"，按 messages 里的 type 走。

### 8. `confirm_card` 确认单 ⭐核心
`{groups: [{group_name, items: [{field, label, value, editable, source}]}], missing: []}` —— 两组共 7 项：基础信息 3 项（门店/报修人/日期，系统带出不可改）+ 报修内容 4 项（类别/故障情况/照片/电话，可改）。`source=ai_filled` 的项加"AI 识别"角标；`missing` 非空时高亮缺项。

交互：

- 点【确认并提交】→ `POST /sessions/{sid}/submit`（是独立接口，**不是** messages）；
- 改描述/报修人 → 发 text 消息（如"电话改成 139..."），响应会带一张新确认单（旧单置灰）；
- 重选类别 → 发 `enum_pick`（field=category）。**照片不作废**：服务端只回一条提示让用户自查（拍的不是新设备就重传，对得上就保留）；category 项自带 `options`（全量两级联动，形状同 enum_card grouped 的 options），重选弹窗优先用它——快捷卡路径没经过类别卡、页面没有缓存时也能直接弹框；弹窗要能取消关闭、回显当前已选值；
- 确认单上 `photos` 项的 `value` 是 `[{name, url}]` 数组（不是"2 张"这种字符串）：数量用数组长度，缩略图用 url，文件名用 name。

### 9. `system_tip` 系统提示条
`{content, level(info|warn|error)}` —— 非对话语气的居中提示条（降级提示、建单失败原因等），按 level 着色。

### 10. `result` 结果卡
`{order_no, status, tip}` —— 提交成功的终点卡：单号 + 状态 +【查看报修记录】按钮（调 `onViewRecords` 钩子）。提交成功后这张卡会进服务端消息档案，刷新/重进时随会话查询重放回来。

## 渲染通则

- 消息按 `seq` 升序 append，全会话严格递增、永不重复；已渲染过的 seq 直接跳过（幂等去重，重进对齐时靠它防止双气泡）；
- 同一时刻**最后一张可交互卡片**是当前操作焦点（配合响应的 `focus` 字段高亮）；
- 任何卡片都可能在降级态下重发，渲染逻辑不用区分，照常画；
- **每轮响应以"当前待办"收尾**：用户跑题/改值/追问后，服务端一定把当前问题卡重发一遍——界面上"现在该干嘛"永远清楚；
- 降级态（fallback）五种结构化手势（card/enum_pick/seg_pick/upload_done/phone）照常放行，只拦 text——点选是降级向导的唯一通道；
- 边界行为：说"改手机号"但没给号 → 服务端追问；发的值不在选项里 → 服务端提示并把选项卡递回。这些都在服务端处理，前端不用管。
