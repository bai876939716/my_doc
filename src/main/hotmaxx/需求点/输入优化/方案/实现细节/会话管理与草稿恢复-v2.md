# 会话管理与草稿恢复（v2 · 对齐 2026-11-13 实现）

> v1 已交付留档（[会话管理与草稿恢复.md](会话管理与草稿恢复.md)）。本文修订四处根本变化：**①存储从 Redis+MySQL 切到 PG 单库；②State 内消息全量、无 10 轮窗口裁剪（v1 的"先入库再裁剪"三规则整体作废）；③确认单不再 interrupt 挂起；④upload 接口废除、照片改 URL 引用**。逐条日志见《[变更记录/实现变更记录.md](变更记录/实现变更记录.md)》。

## 一、生命周期（v2 口径）

1. **出生**：`POST /sessions`（带 store_no）→ 查 PG 活跃索引 `agent_active_index`（key = `rp:active:{uid}:{store_no}`）：有则复用（is_resumed=true，resume_count+1，弹「继续上次填报」）；无则新建并 load_context 带出，首个检查点落盘。
2. **成长**：每条用户消息 = 一轮图执行，**每个节点后检查点自动落 PG（先存再推，零业务存档代码）**；intake 把用户手势落 role=user 档（恒为本轮第 1 条）；活跃索引每轮续期 7 天。
3. **三种终态**：**DONE**（建单成功 → 归档两表落一行/逐条 → 清活跃索引，检查点再留 7 天供 GET done 查询后回收）；**keep**（检查点与索引都保留，7 天滑动，重进提示续填）；**abandon**（先归档（status=abandoned）再销毁检查点，旧 sid 访问 40401）。
4. **过期**：索引惰性过期（get 时判定）+ 后台清理线程（启动首扫 + 每 30 分钟一轮）兜底；超期重进静默开新会话。

## 二、与 v1 的机制差异对照

| 机制 | v1（作废口径） | v2（当前实现） |
|---|---|---|
| 检查点载体 | Redis（AsyncRedisSaver，TTL） | **PG**（PostgresSaver，`CHECKPOINT_MODE` 双模式开关） |
| 消息窗口 | State 只留最近 10 轮，每轮批量 upsert MySQL 后裁剪（先入库再裁剪/唯一键自愈/计数器 seq 三规则） | **State 消息全量不裁剪**；seq 由计数器生成、全会话连续单调（无预留空洞）；归档在终态一次完成 |
| 断点复原 | State 窗口 + MySQL 两源拼接 | **get_state 单源完整重放**（含 role=user 回显） |
| 确认单 | interrupt() 挂起；/submit = Command(resume) | **meta.confirm_pending 数据态**；/submit 注入内部手势直达 submit 节点（见《[图节点设计-v2.md](图节点设计-v2.md)》） |
| 消息表 | MySQL 每轮批量写 | **agent_message_archive 终态归档**（2026-11-13 起含 role=user 手势回显；此前存量行为纯服务端消息） |

## 三、留存参数（可配置）

| 项 | 值 | 改法 |
|---|---|---|
| 活跃索引 TTL | 7 天滑动（每轮续期） | `.env` 的 `ACTIVE_TTL_DAYS` |
| 终态后检查点保留 | 7 天后回收，归档永存 | 同上 |
| 清理线程 | 启动首扫 + 每 30 分钟 | `app/core/pgstore.py` 常量 |
