## 2026-11-12 真机联调日：引擎三刀

### 1. 确认单去 interrupt 化（结构性变更，最大一刀）

- **变更**：confirm 从 `interrupt()` 挂起改为**普通节点**——确认单消息直接落 State，"等待确认"是数据不是控制流：`meta.confirm_pending`（confirm 置位；ask / fallback 清位；submit 成功或校验失败清位；建单失败保持）。提交：POST /submit 由接口层注入**内部手势** `{"type":"submit"}` 经入口路由直达 submit 节点（HTTP 六种消息 type 契约不变，外部无法伪造 submit）。图内 confirm→submit 边删除，改 confirm→END。
- **删除的补丁**：seq 预留块（routes）、挂起载荷合并读取（_round_messages）、Command(resume) 通道。
- **契约影响**：六接口对外契约 v2.2 零变化；seq 恢复连续单调（无预留空洞）。
- **影响文档**：图节点设计（confirm/submit 节点与挂起语义章节作废）；会话管理与草稿恢复（"interrupt 挂起"相关表述作废，检查点机制本身不变）；State设计（Meta.confirm_pending 含义）；技术方案 §5。diagrams 01/02 已随代码更新（AgentServerCenter/diagrams/）。
- **判别法则（备忘）**：interrupt 适用于"人的答复是**正在执行的节点**的计算输入"（工具审批/AI产出人改后同节点续用/跨天审批）；表单确认是"轮与轮之间的等待"，天然走 ask→END 模型。

### 10. 身份闸门落地：缺 X-Uid 不再兜底 anonymous（2026-11-18 审计#1）

- 契约同步：apifox-openapi.json 的 X-Uid 改 `required: true`（仓内与 my_doc 前端对接副本各一份）；`01-接口导入与调试.md` 补 40101 码含义（直连必带 X-Uid；经网关收到 401＝登录态/网关头没配上，不是 Agent 的 bug）；poc 两个演示页注释同步。
- Java 侧（provider-biz-ai-middle `34b5789` 已从 HTM-HEADER 取 userid 注入 X-Uid）：无 userid 时改为照常转发、由 Agent 一处出 401（错误口径不分两家），仅把"Agent 侧按匿名兜底"的过时注释与 warn 日志改准。

### 12. 本地演示入口 `poc/local_demo_app.py`：CORS 只活在这一层（2026-11-18）

- 现象：演示页连不上后端，服务日志 `OPTIONS /agent/repair/v1/sessions/rp_… 405 Method Not Allowed`。
- 原因：11 删了 CORS 中间件后没人应答浏览器的预检 `OPTIONS`——路由只声明 GET/POST，FastAPI 就回 405（真正的生产链路是 H5 经网关同源，本来不需要 CORS）。
- 解法（不改生产）：新增 `poc/local_demo_app.py`，import `app.main` 后 `add_middleware(CORSMiddleware, allow_origins=["*"], …)` 再导出 `app`——与 `poc/mock_llm_app.py` 同一种"换入口不加开关"的路子。本地起 `uvicorn poc.local_demo_app:app --port 8000 --reload`，生产仍载 `app.main:app`（零 CORS）。
- 没有顺手放开身份：该入口只补 CORS，`X-Uid` 缺失照样 401（实测过），联调时演示页仍要 `?uid=&store_no=` 或页面自带 uid。
- 附带记录：`app/main.py` 的注释与 README（本地开发段 + CORS 约束条）都改成指向这个入口，不再写"临时加中间件"这种口头方案。
- 验证：8011 端口起本地入口，预检 `OPTIONS`（Origin: null 与 http://localhost:5500 两种）200 + `Access-Control-Allow-*`；无 `X-Uid` 仍 401/`40101`；带 `X-Uid` 建会话 200。pytest 157 全绿。

### 13. 手机号掩码收口 + 档案没号时改口要号（2026-11-18 审计#2）

- 现象：员工档案没录手机号的人，点开报修页＝服务不可用（建会话 503）；档案登座机时状态条显示 `055****1234`（首尾重叠看不成号）；用户点了"就用这个吗"之后提交被打回、又弹同一张确认卡，绕不出去。
- 原因：掩码逻辑散在四处（`engine.py` 日志、`engine.py` 状态条、`routes.py` GET collected、`cards.py` 确认单），只有确认单那份判了长度，状态条那份无条件 `phone[:3]` → `None` 直接 `TypeError` 冒到 API 层成 503。确认卡又不看"带出来的号能不能用"，议程轮到就发——发出去的那个号提交时必然被拦。
- 解法①（收口）：新增 `app/core/redact.py:mask_phone` 一处实现——缺值「未填」（常量 `MISSING`）、11 位手机 `138****1234`、8 位以上遮中段 `0551****1234`、店内短号/脏值原样；上面四处全改调它。顺手修掉日志那份"非 11 位就整号进日志"的漏掩码。
- 解法②（不摆假默认）：core 新增通用判据 `_usable_default(槽位, 值)`——值必须过本槽声明的 `detector`（手机号=`cn_mobile`）才配当默认，正则仍只有一份真值、core 不出现 `phone` 字段名。不过判据 → ask 节点发口语要号、不发 `phone_confirm` 卡；`use_default` 手势带着不可用值不再清议程（防老前端/旧草稿带着空号冲进确认单）。话术与卡片改读**槽位现值**，不再读档案快照。
- 契约新增一个可选字段：`Slot.ask_talk_no_default`（与 `ask_talk_top3` 同款），报修声明 `repair.ask_phone_none`；`repair.load()` 的启动自检顺带覆盖两个话术变体（缺键是运行时 KeyError＝整轮 500，现在启动就拦）。
- 话术措辞：不写"没查到你的电话"——座机场景那是假话（档案里有，只是师傅打不通）。统一问：「维修师傅上门前会打你电话——发我一个能接到的手机号（11 位，1 开头）」。
- 没做的（划边界）：座机/短号能不能算有效联系方式仍是产品口径未定（审计动作表第 7 项待你拍），本条只保证不崩、不绕圈、不显示错号，**没有放宽 11 位手机号闸**；`engine.py` 提交校验里那条 `sd.name == "phone"` + 硬编码正则（第五处副本）留给 #6「规则收口」一起动。
- 验证：新增 15 条测试（`tests/test_engine.py`，档案异常靠换 `pack["tools"]` 里的同名工具实现，不碰生产 Mock 常量）——九种掩码输入表驱动、四种异常档案（缺/空/座机/短号）建会话不崩且改口语要号、`use_default` 空值防御、座机档案走完全程真实出单（确认单显示 `139****1111`）。变异反证：把 `_usable_default` 改成永远放行，5 条立刻红。pytest 157 → 172 全绿。
- 收工前连带（同日，Harvey 发起）：`poc/` 两个演示页「更换联系电话」弹窗——①`input` 不再写 `pattern`/`required`（浏览器原生气泡那句「请与所请求的格式保持一致。」改不掉，`title` 在 Chrome 里对校验气泡无效，实测 `validationMessage` 照旧；而且它抢在 `onsubmit` 之前，我们自己的提示根本看不到），校验只留 JS 一条路径；②删掉「新手机号（11 位）」标签（标题已说清是要什么，不必再讲格式）；③提示语定为「请输入有效的手机号」，加 `inputmode="numeric"`、保留 `maxlength="11"`。〔测〕真点击提交：`123` 与空值均 `checkValidity()==true`（原生不再拦）→ toast「请输入有效的手机号」、弹窗不关；合法号照常发出。
