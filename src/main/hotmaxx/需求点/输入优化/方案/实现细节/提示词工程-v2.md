# 提示词工程（v2 · 对齐 2026-11-13 实现）

> v1 已交付留档（[提示词工程.md](提示词工程.md)）。v2 的根本变化：**提示词业务隔离**——核心引擎的系统提示词收敛为业务无关协议壳，报修业务内容全量移入技能包 `repair/prompts.py`，直填规则由槽位声明自动生成。v1 的报修 Prompt 原文仍是 repair 包 prompts.py 的底稿，字段清单等业务段以技能包为新真值。逐条日志见《[变更记录/实现变更记录.md](变更记录/实现变更记录.md)》第 4 条。

---

## 一、两层结构（v2 核心口径）

| 层 | 内容 | 真值位置 | 约束 |
|---|---|---|---|
| **协议壳 SYSTEM_BASE**（core） | 纪律 / 意图分类 / 修改语义 / 输出 JSON 骨架 | `app/core/llm.py` | **零业务词**——测试锁定（断言提示词不含任何报修业务字段名/字典项），接报销不用动它 |
| **业务段**（技能包） | 角色 / 直填规则 / 示例 / 字典 / 字段清单 | `app/skills/repair/prompts.py` | 报修的都在 repair 包；新业务各带各的 |

**拼装顺序 = 业务段在前、协议壳收尾**（一份系统提示词，两段拼接）。

## 二、与 v1 的差异点

1. **v1 的系统提示词把"好特卖门店报修助手 + 采集范围 + 字段清单"写死在 core**——已拆走：字段清单由技能包 `slots.py` 的槽位声明**自动生成**（报修 10 槽位；后续技能包各自带 schema，换业务换包不换词）。v1 文末"增补 · schema 驱动注入"的设想已落地为常态。
2. **直填规则自动生成**：哪些枚举字段"说到的直接 ai_filled"不再手写在提示词里，由槽位声明（有无 MustPick 等）推导。
3. **flow_state 注入**（行为增强）：联合抽取 Prompt 注入流程状态行（正在问什么 / 停在确认 / 挂起值）——裸值消解的依据（"可以等待安排吧"不带"改成"也听懂是给答案）。
4. **越界应和**：joint_extract 输出新增 `reply`（仅边界意图，≤30 字；空则罐头拉回兜底）——模型先接半句话再拉回，不再一句罐头甩脸。
5. **update 语义增强**：模型可报 `update_targets`（想改哪个字段），引擎按字段追问（改类别→重发全量类别卡）；手机号漏抽时代码正则兜底。

## 三、效果基线（模型对拍）

| 模型 | 识别率 | 平均耗时 | 注 |
|---|---|---|---|
| qwen-plus | 9/10 → 10/10* | 1300ms | 注入对抗失守一例 |
| **qwen-flash（选定）** | 9/10 → 10/10* | **594ms** | 快 2.2 倍 |

\* 业务隔离改造后 plus/flash 双 10/10（此前各 9/10）。30 场景对拍脚本 `poc/model_bench.py` 入仓，正式报告见《[../../实施/模型对比测试结果.md](../../实施/模型对比测试结果.md)》。

## 四、不变项（v1 继续有效）

联合抽取"一次调用拿全"、三引号包裹防注入、输出校验链（JSON mode → 枚举白名单 → 字段校验 → 意图白名单）、话术模板化不让 LLM 自由发挥——全部保持。

## 五、已知债（重构窗口处理）

- `category_candidates` 键名偏业务（应为 `enum_candidates`，通用化时改）；
- ALLOWED_DELTA 字段白名单仍在 core（应随业务段下沉技能包）。
