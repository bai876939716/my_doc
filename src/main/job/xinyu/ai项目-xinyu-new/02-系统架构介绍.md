# 系统架构介绍

## 整体架构思路

系统采用**两层分工**的架构模式：

```
Java 微服务层  ←→  Python AI Agent 层
   (业务逻辑)         (AI 推理生成)
```

**为什么这样划分？**
- Java 层擅长业务规则、状态机、数据一致性、高并发事务
- Python 层擅长 AI 框架集成（LangChain/LangGraph）、LLM 调用编排
- 两层通过 AgentRun HTTP API 解耦，各自独立部署扩容

---

## xinyu-world-simulator-core — Java 微服务架构

### 架构模式：API + Impl 分离

每个业务域都由两个 Maven 模块组成：
- `xxx-service-api`：定义 Protobuf IDL 契约（RPC 接口 + 数据结构）
- `xxx-service`：实现业务逻辑，注册为 Dubbo Provider

**好处**：接口变更有版本控制，调用方依赖 API jar 而非实现

### 调用链路

```
App (iOS/Android)
    ↓ HTTPS
soul-haven-web-service (BFF :8080)
    ↓ Dubbo 3 Triple Protocol + Protobuf
业务服务 (各 :13xxx 端口)
    ↓ MyBatis-Plus
PostgreSQL (业务数据)
    + Redis (缓存 & 分布式锁)
    + RocketMQ (异步事件)
    + Hermes (长连接实时推送)
    + Nacos (服务注册 & 配置中心)
```

### 关键技术决策

**为什么用 Dubbo Triple 而非 HTTP REST 做服务间通信？**
- Protobuf 序列化：强类型契约，性能高于 JSON
- 服务发现：Nacos 自动注册，无需手写 URL
- 负载均衡：Dubbo 内置多种策略
- 版本管理：接口版本字段内置支持

**为什么用 RocketMQ 做异步？**
- 星梦结束后需要并行执行 4+ 任务（回忆卡、私信、记忆更新、消息Tab）
- 不阻塞主流程，提升响应速度
- 消息可靠投递（不丢失），支持延迟消息（24h过期计时）

**为什么用 Hermes 长连接？**
- AI 生成文本需要流式推送（打字机效果）
- 星梦邀请卡需要实时到达（不能轮询）
- Topic 模型 `chat_session_{id}` 天然隔离不同会话

## xinyu-agents — Python AI Agent 架构

### 技术选型

**AgentRun** (阿里云无服务器 Agent 平台)
- 提供 OpenAI 兼容 HTTP 接口（`POST /openai/v1/chat/completions`）
- 内置模型网关（qwen、deepseek 等）
- Serverless 部署（s.yaml）自动扩缩容

**LangGraph StateGraph**
- 将复杂 AI 工作流定义为状态图
- 每个步骤（节点）独立处理，节点间通过 TypedDict 状态传递
- 条件边（conditional edges）实现错误路由
- 相比链式调用，更易调试和扩展

**LangChain Agent**
- 包装 LLM + Tools 为可调用的 Agent
- 工具调用（MCP Tools）由 ReAct 框架驱动

### 四个 Agent 的架构差异

```
stranger-feed:  validate → generate → validate_output → translate → persist (MCP)
                                                            ↑
                                              [并行翻译 zh-TW + en-US]

acquaintance-feed: validate → generate → assemble_post (含时间校正) → return
                                              ↑
                                   [Java Core 负责最终落库]

xingmeng-content: validate → [Phase1→Phase2→Phase3→Phase4→Phase5] → assemble_result
                              ↑
                   [5阶段流水线，每阶段独立 LLM 调用]

xingmeng-opening: validate → query_mcp(并行) → assemble_prompt → invoke_llm → cleanup → log(异步)
                              ↑
                   [低延迟优先，快模型，< 2秒]
```

### MCP 集成模式

```python
# 标准初始化模式
client = MultiServerMCPClient({
    "service_key": {
        "transport": "streamable_http",
        "url": "http://mcp.server/mcp-servers/service-name"
    }
})
tools = await client.get_tools()
agent = create_react_agent(llm, tools)
```

**MCP 的价值**：Agent 不直接操作数据库，通过 MCP 工具调用 Java Core，实现 AI 层与数据层解耦。

**为什么用 XML？**
- 结构清晰，LLM 对有语义标签的格式理解更好
- 便于程序化替换占位符
- 各段落独立，便于版本化管理

### JSON 解析鲁棒性设计

LLM 输出格式不稳定，采用多层兜底：
1. 移除 `<think>` 推理块（DeepSeek 思维链输出）
2. 提取 ` ```json ``` ` 围栏内容
3. 定位 `[` `]` 边界
4. `json.loads()` 标准解析
5. 去尾逗号重试
6. `json_repair.loads()` 终极兜底

## 数据一致性策略

### 三种落库模式

| 场景 | 落库方 | 方式 |
|------|--------|------|
| Stranger Feed | Agent | MCP Tool → Java Core → PG |
| Acquaintance Feed | Java Core | 直接写 DB（Agent 不涉及） |
| Xingmeng Content | Agent | MCP Tool → Java Core → PG |

### 为什么 Acquaintance Feed 由 Java 落库？

- 需要在落库前做**业务规则阻断**（时间冲突、字数不足等 AGENT_OUTPUT_RULE_FAILED）
- Java 侧有完整的用户上下文和时区转换逻辑
- Agent 只做 AI 生成，保持职责单一

### 错误处理策略

```
每个 LangGraph 节点都有条件边：
  ① 节点内出错 → state.error = ErrorCode
  ② 条件边检查 → error 存在 → 路由到 END
  ③ 主流程不继续执行

错误码体系：
  PARAM_INVALID   入参错误
  LLM_FAILED      模型调用异常
  PARSE_FAILED    JSON 解析失败
  SCHEMA_FAILED   字段校验失败
  RULE_FAILED     业务规则不通过
  MCP_FAILED      工具调用失败
  MCP_NOT_CONFIGURED  MCP 未配置
```

## 部署架构

### xinyu-agents 部署

- **平台**：阿里云 AgentRun (Function Computing 2.0)
- **配置文件**：`s.yaml`（测试）/ `s-prod.yaml`（生产）
- **资源**：
  - stranger-feed: 1 vCPU / 2GB / 100 并发
  - xingmeng-content: 2 vCPU / 4GB / 10 并发（批处理重）
  - xingmeng-opening: 1 vCPU / 2GB / 100 并发（低延迟）
- **网络**：VPC 访问内部 MCP 和 LLM 网关

### xinyu-world-simulator-core 部署

- **容器化**：各服务独立 Docker 镜像
- **服务发现**：Nacos 注册中心
- **配置**：Nacos 配置中心（热更新无需重启）
- **多环境**：dev / fat / prod 三套环境

---

## 性能优化关键点

1. **并行翻译**：Stranger Feed 的 zh-TW + en-US 同时翻译（asyncio.gather）
2. **库存优先**：Xingmeng Content Phase3 先读库存，不足才 LLM 生产（省 Token 费用）
3. **快模型选型**：实时场景（开场白改写）用 qwen3-max，批处理用 deepseek-v4-flash
4. **MCP 单例**：全局共享 MultiServerMCPClient，避免每次请求重建连接
5. **异步非阻塞日志**：开场白改写的 MCP 日志记录异步执行，不影响主链路延迟
6. **AgentRun 实例并发**：Serverless 自动扩容，无需手动管理连接池
