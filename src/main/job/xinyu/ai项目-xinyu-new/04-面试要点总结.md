# 面试要点总结

## 项目一句话介绍（STAR 开场）

> 我参与开发了心屿 App 的 AI 后端系统，这是一个以 AI 角色社交为核心的产品。后端由两部分组成：Java 微服务集群负责业务逻辑和数据持久化，Python AI Agent 集群负责内容生产和 AI 推理。其中最核心的是**星梦系统**——用户与 AI 角色的沉浸式线下见面体验，以及**每日内容生产流水线**，通过 5 阶段批处理为用户生产个性化星梦内容。

---

## 高频面试问题与回答

### 1. 项目整体架构是什么？为什么这样设计？

**回答**：

系统采用两层架构：
- **Java 微服务层**（xinyu-world-simulator-core）：13 个微服务，处理业务规则、状态机、数据持久化、实时推送。采用 Dubbo 3 Triple 协议做服务间通信，Protobuf 强类型契约。
- **Python AI Agent 层**（xinyu-agents）：4 个 Agent，基于 LangGraph 状态图编排 AI 工作流，通过 MCP 工具链读写 Java Core 数据。

**为什么分层**：
- Java 擅长业务规则强、事务要求高的场景
- Python 生态有 LangChain/LangGraph，AI 框架集成更简洁
- 两层 AgentRun HTTP API 解耦，可以独立扩容、独立部署

---

### 2. 介绍一下 LangGraph 在项目中的应用

**回答**：

我们用 LangGraph 的 `StateGraph` 来编排多步 AI 工作流。以陌生角色新鲜事生产为例：

```
节点: validate_params → generate → validate_output → translate → persist
边:   每个节点有条件边，出错时直接路由到 END
状态: TypedDict 在节点间传递（request_id、inp、llm_raw、posts、error）
```

**核心优势**：
1. 节点职责单一，每步可独立测试
2. 条件边实现错误路由，出错不继续执行
3. 状态图可以可视化，便于调试
4. 支持异步并行（翻译节点并行 zh-TW + en-US）

对比链式调用：LangGraph 更容易处理分支逻辑和错误恢复。

---

### 3. MCP 在项目里是怎么用的？

**回答**：

MCP（Model Context Protocol）是我们解耦 AI 层与数据层的关键：

- **不用 MCP 的做法**：Agent 直接连接 PostgreSQL，AI 层和数据层耦合
- **用 MCP 的做法**：Agent 调用 MCP 工具（HTTP Streamable），MCP 服务实现层对接 Java Core，Java Core 写数据库

我们有 6 个 MCP 服务：角色信息、用户信息、短对话历史、星梦库存/日计划、记忆画像、世界观数据。

**代码层面**：
```python
client = MultiServerMCPClient({
    "dream-service": {
        "transport": "streamable_http",
        "url": "http://mcp.xxx/xmc-pub-sub-dream-service-mcp"
    }
})
tools = await client.get_tools()
agent = create_react_agent(llm, tools)
```

### 4. 星梦系统最复杂的点在哪里？你是怎么解决的？

**回答**（亮点问题，多展开）：

**复杂度来自多个层面**：

**① 并发冲突**：用户同时可能有多个星梦邀请到达，或者进入星梦时网络抖动导致重复请求。
- 解决：Redis 分布式锁（StarDreamAcceptLockService），幂等 inviteId

**② 预扣费时序**：AI 生成失败时需要退款，成功后才正式扣费。
- 解决：消息发送前校验余额（预扣），AI 生成成功后正式结算

**③ 关系等级不匹配**：批处理时 Lv1 生产的开场白，用户进入时已升至 Lv3。
- 解决：实时改写 Agent（xingmeng-opening-rewrite），< 2 秒内用快模型重写

**④ 结束时多任务并行**：回忆卡片、后私信、消息 Tab 更新、记忆写入需要同时完成，但不能阻塞主流程。
- 解决：RocketMQ 异步事件，主流程 30ms 响应，各任务异步执行

**⑤ 邀请频率控制**：太频繁的邀请破坏体验，太稀少影响参与感。
- 解决：多维度限流（10分钟冷却 / 每日8次上限 / 拒绝后5分钟冷却 / 完成后30分钟冷却）

### 5. 每日内容批处理的 5 阶段是怎么设计的？

**回答**：

**先说背景**：系统每天早上 6 点要给每个用户"备好当天的星梦菜单"——提前生成好内容放在库里，用户随时点进来立刻有内容看，不用临时等 AI 生成。一天被分成 12 个 2 小时时间窗（W01 清晨 ~ W12 黎明），每个窗口都需要有对应的星梦内容。

**具体举例**：用户小明有 3 个角色：陆承宇(Lv3)、林诗雨(昨晚 Lv1 升 Lv2)、苏凛(Lv5)

---

**Phase 1 — 扫描谁升级了（无 LLM）**

昨晚林诗雨关系升级，Java Core 标记了 `upgrade_pending = true`。
Phase 1 把这些角色找出来，同时清掉她 Lv1 时生成的旧库存——那些内容措辞太生疏，不能再用。

---

**Phase 2 — 改写旧内容适配新等级（每角色 1+ 次 LLM）**

林诗雨 Lv1 版本的开场白："你好，我们约好在这里见面。"
升到 Lv2 后应该更熟悉："嘿，终于来了，我等你一会儿了。"

把旧星梦内容交给 LLM，注入新等级的亲密度描述，改写措辞后存回库。

---

**Phase 3 — 把角色分到 12 个时间窗，缺内容就现场生产（最多 LLM 调用）**

- **3a 分配**：按角色等级 / 活跃度把角色分配进各时间窗，每窗约束 ≥1 多人星梦 + ≥8 总星梦
- **3b 生产**：先查库存，有现成的直接用（省 LLM 调用）；库存不够才调 LLM 生成新星梦

这一阶段是 LLM 调用最多的地方，也是成本控制的核心——库存复用率越高越省钱。

---

**Phase 4 — Lv3+ 角色强制全天覆盖（补漏）**

陆承宇是 Lv3，系统承诺高等级角色全天 12 个窗口都有内容。Phase 3 可能某些窗口没分配到他，Phase 4 专门扫这个漏洞，强制补充，保证高等级关系的体验完整。

---

**Phase 5 — 给星梦补"星事钩子"（增强体验）**

星事是星梦的延伸内容，比如星梦结束后角色发的一条感慨，或者对这段记忆的一句评语。不是每个星梦都要有，但缺少星事体验不完整。Phase 5 扫描所有缺星事的星梦，逐条补充。

---

| 阶段 | 核心问题 | LLM 调用 |
|------|----------|----------|
| Phase 1 扫描升级 | 谁的关系等级变了？ | 0 次 |
| Phase 2 批量改写 | 旧内容措辞不对，怎么修？ | 每角色 N 次 |
| Phase 3 分配+生产 | 今天各时间窗放什么内容？ | 缺口才调用 |
| Phase 4 全量补充 | Lv3+ 角色有没有全天覆盖？ | 补漏调用 |
| Phase 5 星事补充 | 哪些星梦还缺延伸内容？ | 逐条调用 |

**关键设计决策**：
- **库存优先**：Phase 3b 先读库存再生产，省 Token 费用
- **等级分层保障**：Phase 4 专门给高等级用户兜底，避免 VIP 用户体验差
- **LangGraph 编排**：每个阶段是独立节点，某个 Phase 失败可以精确定位，不影响其他阶段的计数

### 6. 提示词工程你们是怎么做的？

**回答**：

我们采用**XML 结构化提示词**，每个 Agent 独立维护版本化提示词模板：

1. **结构化**：把任务拆分为多个语义明确的 XML 段落（角色设定、任务目标、创作规则、禁止项、输出格式），LLM 对有标签的格式理解更好

2. **版本管理**：代码中定义 `DEFAULT_PROMPT_VERSION = "v4.0-stranger-lv0"`，新版本新增函数而不覆盖旧函数

3. **创作约束**：
   - 字数范围（zh: 20-50字，en: 15-120词）
   - 禁用词（禁止 @用户、禁止"你"以防止对话化）
   - 关系等级映射（Lv1 初识措辞 vs Lv5 灵魂羁绊措辞）
   - 时段情绪一致性（早晨轻快 vs 深夜宁静）

4. **翻译分离**：生成和翻译用不同模型（省钱），翻译有独立术语表（glossary.md）保证一致性

### 7. JSON 解析为什么需要多层兜底？

**回答**：

LLM 输出的格式不稳定，常见问题：
1. 带思维链的模型（DeepSeek R1）会先输出 `<think>...</think>`，需要剥离
2. 模型可能加 Markdown 围栏（` ```json ```）
3. 末尾可能有多余逗号
4. 极端情况下格式错乱

我们的 4 层处理：
```python
# 1. 移除 <think> 块
raw = strip_think_blocks(raw)
# 2. 提取 ```json 围栏
content = extract_json_fence(raw)
# 3. 标准解析
try:
    result = json.loads(content)
except:
    # 4. 去尾逗号 + json_repair 终极兜底
    result = json_repair.loads(content)
```

### 8. 关系等级系统是如何驱动内容的？

**回答**：

关系等级（Lv0~Lv5）是内容个性化的核心驱动：

- **Lv0**：只能看公开的陌生角色新鲜事（Stranger Feed），无法触发星梦
- **Lv1+**：激活个性化新鲜事（Acquaintance Feed）、星梦系统
- **Lv3+**：星梦内容强制覆盖所有 12 个时间窗（Phase 4 保障）
- **Lv4+**：新鲜事可以 @用户昵称，更强的个人连接感
- **关系升级**：次日 06:00 批处理 Phase 2 自动改写旧星梦，适配新 Lv 措辞

**实时处理**：用户进入星梦时，如果关系等级已升级但内容是旧版，`xingmeng-opening-rewrite-agent` 实时改写开场白（< 2 秒）。

### 9. 系统的可观测性怎么做的？

**回答**：

**结构化日志**（execution_log.py）：
```
[workflow] execution step=VALIDATE_PARAMS detail={request_id: "xxx", elapsed_ms: 12}
[workflow] execution step=LLM_GENERATE detail={request_id: "xxx", model: "qwen3-max"}
[workflow] execution step=WORKFLOW_END detail={success: false, error_code: "RULE_FAILED"}
```

**追踪字段**：每个请求都有 `request_id`（uuid），贯穿整个工作流，便于日志关联。

**workflow_context**：出参中携带完整执行上下文（模型调用 token 数、各步耗时、翻译追踪）。

**ARMS 监控**：AgentRun 部署自动对接阿里云 ARMS，可查看每次调用的延迟、成功率。

**环境变量调试**：`LOG_FULL_PROMPT=1` 打印完整提示词，`LOG_FULL_AGENT=1` 打印模型原始输出。

### 10. 项目中有哪些值得讲的技术亮点？

**推荐选 2-3 个展开**：

**亮点 1：LangGraph 状态图工程化复杂 AI 工作流**
- 把 5+ 步骤的 AI 流程图化为可视化状态图
- 错误路由精确，出错步骤可定位
- 异步并行节点（翻译）减少 RT

**亮点 2：MCP 实现 AI 层与数据层解耦**
- Agent 不直接写数据库，通过 MCP 工具调用 Java Core
- AI 层和业务层可以独立演进
- 6 个 MCP 服务覆盖所有上下文数据读写

**亮点 3：5 阶段内容生产流水线**
- 每日定时为所有用户生产个性化内容
- 库存优先节省 LLM 成本
- 12 时间窗保证全天内容覆盖
- 关系升级自动触发改写

**亮点 4：实时开场白改写的低延迟设计**
- 批处理内容与实时 Lv 不匹配时自动修正
- < 2 秒内完成：MCP 查询 + LLM 推理 + 返回
- 快模型选型（qwen3-max）+ 异步非阻塞日志

**亮点 5：多维度频率限制保护用户体验**
- 邀请卡：10分钟冷却 + 每日8次上限 + 拒绝5分钟冷却
- Redis 原子计数器实现高并发下的准确限流
- 防止过度打扰降低用户留存
