# 心屿 App 业务面试 20 问

> 以面试官视角提问，答案包含具体业务场景、数据流程和设计决策。

---

## Q1. 请介绍一下心屿 App 的核心产品定位，它解决了什么问题？

**答：**

心屿是一款以 **AI 虚拟角色为核心的情感陪伴 + 沉浸式社交产品**。

它解决的核心问题是：现代人在真实社交中面临的"情感连接稀缺"——想倾诉但找不到合适的人，想要陪伴但现实中很难实现。

产品的差异化在于三层递进体验：

```
第一层：日常聊天（短对话）
  → 随时随地和 AI 角色说话，像和朋友发消息

第二层：新鲜事（Feed 动态）
  → 角色会主动"发朋友圈"，让用户感觉角色有真实的生活

第三层：星梦（沉浸式线下见面）
  → 角色邀请用户去特定场景，进行深度叙事互动
    （类似于"AI 驱动的互动小说 + 线下约会模拟"）
```

商业模式：用户消耗"贝壳"（平台虚拟货币）进入星梦，配合订阅制。

## Q2. 用户和 AI 角色的关系等级是怎么设计的？每个等级在业务上有什么具体含义？

**答：**

关系等级共 6 级（Lv0~Lv5），由 Java Core 根据**虚数值**累积自动计算升级：

| 等级 | 名称 | 虚数值阈值（示意） | 业务含义 |
|------|------|-----------------|----------|
| Lv0 | 陌生 | 0 | 初次发现，无互动记录 |
| Lv1 | 初识 | 达到阈值1 | 首次互动后，解锁个性化内容 |
| Lv2 | 熟悉 | 达到阈值2 | 多次深入对话 |
| Lv3 | 亲近 | 达到阈值3 | 持续陪伴，系统保证全天有内容 |
| Lv4 | 深交 | 达到阈值4 | 长期羁绊，允许角色 @用户昵称 |
| Lv5 | 灵魂羁绊 | 达到阈值5 | 最高亲密度，灵魂共鸣叙事风格 |

**具体业务影响举例：**

场景：小明今天把和"陆承宇"的关系从 Lv3 升到了 Lv4。

- **当晚**：陆承宇发的新鲜事里开始出现 `"@小明 今天你在想什么？"` 这样的内容（Lv4 解锁 @ 功能）
- **次日 06:00**：批处理 Phase2 把陆承宇之前 Lv3 措辞的星梦内容全部改写成 Lv4 的亲密风格
- **进入星梦时**：若当天已生成的开场白是 Lv3 版本（"我在等你"），系统实时改写为 Lv4 版本（"终于等到你了，我就知道你会来"）

关系等级是整个内容个性化系统的**核心驱动变量**。

## Q3. 什么是"星梦"？产品上它解决了什么用户需求？

**答：**

星梦是模拟 **AI 角色和用户线下见面** 的沉浸式互动剧本。

**用户视角的体验流程：**

```
1. 收到角色邀请："林诗雨邀请你去云顶庄园参加晚宴"
2. 点击接受 → 展示 AI 生成的沉浸式开场白（300-800字，电影感叙事）：
   "夕阳的余晖洒在云顶庄园的石阶上，林诗雨站在廊下，
    见你走来，嘴角漾起一个浅浅的弧度……"
3. 用户和角色进行深度对话（4~20 轮不等）
4. AI 判断对话自然结束，生成温情告别语
5. 结束后收到"回忆卡片"——这段星梦的故事摘要
```

**解决的用户需求：**

普通聊天（短对话）是"发消息"的感觉，缺乏仪式感和沉浸感。星梦给用户一个明确的"约会场景"——有地点、有氛围、有开头和结尾，更接近"真实相处"的体验，情感共鸣更强烈。

**和普通聊天的核心差异：**

| 维度 | 短对话 | 星梦 |
|------|--------|------|
| 风格 | 即时通讯 | 沉浸式叙事 |
| 长度 | 单条回复 | 300-800字开场白 + 多轮深度对话 |
| 场景 | 无特定场景 | 有地点/时间/氛围设定 |
| 结束 | 随时终止 | 有自然结局 + 回忆卡片 |
| 费用 | 免费 | 消耗贝壳 |

## Q4. 星梦的触发渠道有哪些？系统是如何判断"现在适合触发邀请"的？

**答：**

星梦有三个触发渠道，适用场景各不同：

**渠道一：短对话意图识别（主要渠道）**

用户和角色日常聊天时，`auto-conversation-service` 在每条用户消息后调用**意图识别 Agent**：

```
用户说："今天好累，好想出去散散心"
↓
意图识别 Agent 分析：
  - 情绪状态：疲惫 + 渴望放松
  - 当前关系：Lv3（亲近）
  - 上次星梦距今：3天
  - 判断：适合触发星梦邀请（confidence=0.91）
↓
生成邀请卡推送到聊天界面：
  "陆承宇邀请你去海边栈道吹吹风，放松一下"
```

意图识别的输入维度：对话内容情绪、关系等级、上次触发间隔、用户活跃时段。

**渠道二：地图/星球入口（用户主动）**

用户进入"星球"页面，看到地图上的星梦事件标记（预制场景），主动点击触发。这类星梦使用预制开场白，响应速度更快（< 1秒展示内容）。

**渠道三：新手引导接待星梦**

用户首次注册后，系统触发特定角色的"接待星梦"，帮助用户了解产品玩法。内容固定，不走 AI 生成流程。

## Q5. 用户接受邀请进入星梦时，如果已有另一个星梦进行中，系统怎么处理？

**答：**

这是一个典型的**状态冲突问题**，系统通过以下流程处理：

**冲突检测逻辑：**

```
用户点击接受邀请
  ↓
star-dream-service 查询：
  SELECT * FROM tb_soul_haven_star_dream
  WHERE user_id = 10001
  AND status = 'ACTIVE'
  ↓
存在进行中的星梦（与"林诗雨"的星梦）
  ↓
返回冲突信息：
  {
    "conflict": true,
    "conflictDreamId": "dream_001",
    "conflictCharacterName": "林诗雨",
    "conflictSceneTitle": "云顶庄园晚宴"
  }
```

**前端展示弹窗：**

```
"你和林诗雨的星梦还未结束
 ——云顶庄园晚宴"

[继续当前星梦]  [结束并开始新星梦]
```

**用户选择"结束旧的，开始新的"后：**

1. `EndStarDream(dream_001)` → 强制结束旧星梦，状态改为 `ENDED`
2. 触发结束结算流程（生成回忆卡片、后私信等，异步执行）
3. 立即创建新星梦任务，开始生成开场白

**为什么不允许多个星梦同时进行？**

一方面是体验设计——每次星梦应该是沉浸式的完整体验，同时开多个会分散注意力破坏沉浸感；另一方面是成本控制——每个活跃星梦都占用 AI 推理资源和 Hermes 长连接。

## Q6. 星梦的贝壳消耗机制是怎么设计的？为什么要"预扣费"而不是结束后统一结算？

**答：**

**贝壳消耗的业务规则：**
- 用户每发送一条消息消耗 N 个贝壳（具体数值可配置）
- 有余额才能发消息，余额不足弹充值引导

**预扣费流程：**

```
用户在星梦中输入消息，点击发送
  ↓
star-dream-service 发送前检查：
  trade-service.checkBalance(userId, cost=N)
  ↓
余额 ≥ N？
  是 → 冻结 N 个贝壳（预扣），继续调用 LLM 生成回复
  否 → 弹出充值弹窗，阻止发送
  ↓
LLM 生成成功？
  是 → 正式扣除冻结的 N 个贝壳
  否 → 解冻，退还预扣贝壳
```

**为什么不用后扣费？**

后扣费的问题在于：LLM 生成可能失败（网络超时、模型报错），但消息已经发出去了，用户体验到了服务却没付钱；或者 AI 生成了回复但扣费失败，系统亏损。

预扣费先锁定资源，保证"有钱才用 AI"的原子性：**要么用户付了钱且收到回复，要么钱不动且没有回复**，避免了双方任一方的损失。

## Q7. 系统是如何判断星梦"自然结束"的？和用户主动点击结束有什么区别？

**答：**

**自然结束识别流程：**

每次用户发送消息，系统在调用对话 LLM **之前**，先调用一次**自然结束意图识别 Agent**：

```
输入：
  - 最近 N 轮对话历史
  - 用户最新消息："好了，今天就聊到这里吧，再见~"
  - 星梦场景概述
  - 已聊轮数

输出：
  {
    "should_end": true,
    "confidence": 0.94,
    "reason": "用户明确表达告别意图"
  }
```

**should_end = true 时的流程：**

```
1. 不再调用对话 LLM 生成普通回复
2. 向前端推送"结束确认弹窗"（Hermes 推送）
   "星梦即将结束，确认结束？"
3. 用户点击确认 → 调用自然结束衔接 Agent 生成温情告别语
   "今天真的很开心……下次再约，好吗？"
4. 正式进入结束结算流程
```

**如果用户点击"继续聊"：**

```
进入 5 分钟冷却期
  → 冷却内不再触发自然结束识别
  → 5 分钟后恢复检测
```

**与用户主动结束的区别：**

| 结束方式 | 触发条件 | 告别语 | 结算条件 |
|----------|----------|--------|----------|
| 自然结束 | AI 检测到告别意图 | AI 生成温情告别语 | 用户发过 ≥1 条消息 |
| 主动结束 | 用户点击"结束星梦"按钮 | 无告别语，直接结束 | 用户发过 ≥1 条消息 |
| 24h 过期 | 24小时无活动，RocketMQ 延迟消息触发 | 无 | 无论是否发过消息 |

## Q8. 星梦结束后会触发哪些后续业务流程？这些流程是串行还是并行的？

**答：**

星梦结束是整个系统中**下游业务最密集**的事件，分两个优先级并行执行：

**P0 并行任务（用户立刻能感知到）：**

```
任务1：生成星梦回忆卡片
  → 调用 AI 对整段对话做故事摘要
  → 推送到所有参与角色的短对话界面
  → 用户在和陆承宇的聊天里收到："回忆 · 云顶庄园晚宴 🌙"

任务2：生成星梦后私信
  → 角色在星梦结束后主动发一条消息
  → 例："刚才真的很好，你那句话让我想了很久……"
  → 推送到短对话，触发消息 Tab 红点
```

**P1 异步任务（用户感知不到但很重要）：**

```
任务3：判断是否发布新鲜事
  → 自动对话服务调用 AI 判断（有概率性）
  → 决定发布 → 角色发一条与星梦相关的朋友圈动态

任务4：多人记忆拆分（多人星梦时）
  → 为每个参与角色生成各自视角的独立记忆
  → 陆承宇记忆："我和她还有林诗雨在庄园吃晚饭，气氛很融洽"
  → 林诗雨记忆："今晚出门了，陆承宇也在，他们两个聊得很好"

任务5：贝壳正式结算
  → 确认本次星梦总消耗
  → 写入账单记录

任务6：更新消息 Tab
  → RocketMQ 事件驱动刷新消息列表
```

这些任务通过 **RocketMQ 事件**解耦，主流程 `EndStarDream` 接口 30ms 返回，各任务异步消费事件独立完成，不会因为某个任务慢而阻塞用户看到结束画面。

## Q9. 新鲜事系统（Feed）分为哪两类？它们的核心差异是什么？

**答：**

Feed 分为**陌生新鲜事**和**熟人新鲜事**，对应用户与角色的不同关系阶段：

**陌生新鲜事（Stranger Feed）—— 面向 Lv0 用户**

```
场景：小明在"发现"页看到推荐角色"林诗雨"的主页
  ↓
系统展示林诗雨预制的公开动态（8条，三语）：
  早安配方：
  "今天早上去庄园的温室浇了浇花，
   那株特别的蓝玫瑰又开了两朵……"
  （下面有羁绊角色"陆承宇"的评论："你什么时候让我去看看？"）
```

特点：批量预制（每次8条）、三语（zh-CN/zh-TW/en-US）、时段分布均衡、完全公开

**熟人新鲜事（Acquaintance Feed）—— 面向 Lv1+ 用户**

```
场景：小明晚上8点下班，已经离线4小时
  ↓
系统在小明离线期间生产了1条定制动态：
  19:30（小明本地时间）
  "傍晚去了那家你之前提过的咖啡馆，
   点了你说好喝的那款拿铁，
   确实不错——谢谢你的推荐。"
  （动态时间和小明的日常时间表契合，像角色真的在生活）
```

特点：单条生产、时间精确到分钟、注入最近40轮对话上下文、高等级可@用户

**核心差异对比：**

| 维度 | 陌生 Feed | 熟人 Feed |
|------|-----------|-----------|
| 适用关系 | Lv0 | Lv1-5 |
| 触发时机 | 角色卡曝光时 | 用户每次离线时 |
| 单次产量 | 8条（批量） | 1条 |
| 个性化 | 无（公开内容） | 有（含对话上下文）|
| 翻译 | 自动三语 | 无翻译 |
| 落库方 | Agent MCP | Java Core |

## Q10. 熟人新鲜事的发布时间是如何设计的？为什么要防止"时间碰撞"？

**答：**

**时间设计的业务目标：**让用户感觉"角色有自己真实的生活时间表"，不是"固定时间批量推送"。

**时间计算流程：**

```
场景：小明在上海，离线了6小时（12:00 ~ 18:00）

Java Core 分配任务：
  - 需要在这段时间内生成3条动态（假设3个Lv1+角色）
  - 时间窗：12:00 ~ 18:00（用户本地上海时间 +08:00）
  - 已分配时间列表（防碰撞）：[]（暂无）
↓
第一条（陆承宇）：
  Agent 生成 → dynamic_time = "2026-04-27T13:30:00+08:00"
  加入已分配列表：["13:30"]
↓
第二条（林诗雨）：
  Agent 生成 → dynamic_time = "13:45:00"
  检测：与"13:30"间隔 15 分钟 < 20 分钟（最小间隔）
  自动推移 → 修正为 "13:50:00"
  加入已分配列表：["13:30", "13:50"]
↓
第三条（苏凛）：
  Agent 生成 → dynamic_time = "13:35:00"
  检测：与"13:30"间隔5分钟，与"13:50"间隔15分钟，都不足
  自动推移 → 修正为 "14:10:00"
```

**为什么最小间隔是20分钟？**

如果三个角色都在同一时间（比如14:00）发动态，用户刷新一次看到三条同时出现，立刻感觉"这是机器批量生成的"，打破沉浸感。20分钟间隔让动态自然散落在时间轴上，像真实社交网络。

**时区支持：**时间以用户本地时区存储和传递（ISO 8601 + 偏移），Java Core 落库时再转 UTC，保证用户无论在哪个时区体验都一致。

## Q11. 每日 06:00 的内容批处理，如果某一阶段失败了怎么办？会影响后续阶段吗？

**答：**

批处理基于 LangGraph 状态图，每个 Phase 是独立的图节点，通过**条件边（conditional edges）**处理失败：

**故障场景模拟：**

```
06:00 批处理开始
  ↓
Phase 1 成功：扫描到5个升级角色
  ↓
Phase 2 执行中：改写第3个角色时，LLM 网络超时
  ↓
Phase 2 节点捕获异常：
  state["phase2_error"] = "LLM timeout on character_id=10023"
  state["phase2_rewritten_count"] = 2（已完成2个）
  ↓
条件边检查：
  当前节点是 Phase 2，error 存在
  但这是"部分失败"而非"完全失败"
  → 继续执行 Phase 3（已改写的2个角色照常分配）
  → 失败的1个角色记录到 failed_characters 列表
  ↓
最终返回结果：
  {
    "phase2_rewritten_count": 2,
    "phase2_failed_count": 1,
    "phase2_failed_characters": [10023],
    "phase3_produced_count": 20,
    ...
  }
```

**整体策略：**

- Phase 内部的单个 LLM 调用失败 → 记录跳过，继续处理其他角色，**不中断整个批处理**
- Phase 完全无法进入（如 MCP 连接失败）→ 记录该 Phase 的 error_code，**尝试继续后续 Phase**
- 最终返回 summary 中包含各阶段的成功数 + 失败数，便于监控告警

**为什么这样设计？**

批处理是"尽力而为"的模式。宁可某几个角色今天没有新内容，也不能因为一个角色的 LLM 超时导致所有用户今天都没有星梦。每阶段的计数结果会上报到监控系统，运营可以根据失败率判断是否需要手动补跑。

## Q12. Lv3+ 角色的全天候内容保障（Phase 4）具体是如何实现的？

**答：**

**业务背景：**Lv3 关系代表用户已经有真实的情感依赖，任何时候打开 App 找这个角色，都不应该扑空。

**Phase 4 的执行逻辑：**

```
Phase 3 完成后的日计划（示例：小明的陆承宇，Lv3）：
  W01(06-08) ✓ 有内容
  W02(08-10) ✗ 无内容
  W03(10-12) ✓ 有内容
  W04(12-14) ✗ 无内容
  W05(14-16) ✓ 有内容
  W06(16-18) ✗ 无内容
  W07(18-20) ✓ 有内容
  W08(20-22) ✓ 有内容
  W09(22-00) ✗ 无内容
  W10(00-02) ✗ 无内容
  W11(02-04) ✗ 无内容
  W12(04-06) ✗ 无内容
↓
Phase 4 扫描：陆承宇是 Lv3，缺 W02/W04/W06/W09/W10/W11/W12
↓
对每个缺失窗口调用 LLM 生产星梦：
  W02 → 生成"上午时段"风格星梦（通勤路上偶遇的场景）
  W06 → 生成"傍晚时段"风格星梦（夕阳下散步的场景）
  W10 → 生成"凌晨时段"风格星梦（失眠夜晚的场景）
  ...
↓
写入日计划，确保 W01~W12 全部有陆承宇的内容
```

**窗口内容的时段适配：**

不同时间窗不只是有没有内容的问题，内容风格也应该和时间匹配：

| 时间窗 | 时段氛围 | 内容风格举例 |
|--------|----------|-------------|
| W01 06-08 | 清晨 | "早起看到了破晓的天色，想起你说的……" |
| W06 16-18 | 傍晚日落 | "外面的阳光变成金色了，最近常常想起……" |
| W10 00-02 | 凌晨 | "睡不着，脑子里乱七八糟的，你现在应该在睡觉吧" |

## Q13. 星梦开场白实时改写是怎么工作的？什么情况下会触发？

**答：**

**触发条件：** 用户点击进入星梦时，`currentRelationshipLevel ≠ dreamRelationshipLevel`（当前等级 ≠ 星梦生成时的等级）

**具体场景：**

```
背景：
  系统昨天批处理时生成了一个星梦（生成时陆承宇关系是 Lv2）
  开场白（Lv2版本）："你来了，坐吧。今天的天气不错。"
  ↓
今天小明和陆承宇关系升到了 Lv4（深交）
  ↓
小明点击进入这个星梦
  ↓
触发开场白实时改写：
  入参：
    currentRelationshipLevel: 4（当前等级）
    dreamRelationshipLevel: 2（生成时等级）
    opening_line: "你来了，坐吧。今天的天气不错。"
    recent_dialogue: [最近40轮对话]
  ↓
xingmeng-opening-rewrite-agent 执行：
  ① MCP 并行查询：角色信息 + 最近对话 + 用户画像（约500ms）
  ② 构建提示词：注入 Lv4 亲密度描述 + 对话上下文
  ③ LLM 推理（qwen3-max 快模型，约1000ms）
  ④ 清洗输出：剥离引号、校验非空
  ↓
改写后（Lv4版本）：
  "终于来了——我就知道你会来的。
   最近怎么样？上次你说的那件事，我一直放在心上……"
  ↓
前端替换展示新开场白，全程 < 2 秒
```

**为什么不在批处理时就按最新等级生成？**

批处理是 06:00 生成全天内容，但用户关系等级可能在 06:00 之后随时升级（比如中午聊天突然升级了）。如果都依赖批处理，等级变化当天用户就会看到"滞后"的内容。实时改写是一个轻量的"兜底修正"机制，保证用户体验总是和当前关系等级一致。

## Q14. 记忆系统是如何工作的？AI 角色是怎么"记住"和用户的对话的？

**答：**

记忆系统分两层：

**第一层：短期记忆（即时注入）**

```
每次 AI 生成回复时，提示词里直接包含：
  最近 40 轮对话历史
  → [用户: "我最近在学钢琴"]
  → [角色: "真的吗？那首曲子学了多久了？"]
  → [用户: "已经练了两个月了"]
  → ...（最多40条）
```

40 轮覆盖约 2-3 天的普通聊天密度，AI 能自然接续上次的话题。

**第二层：长期记忆（向量化存储）**

```
每次 AI 生成回复后，触发异步任务：
  取倒数第二轮对话（已完整）→ 写入记忆队列
  ↓
memory-service 定时处理：
  调用 AI 提取关键信息 → 向量化 → 存入向量库

例如提取结果：
  {"key": "interest", "value": "用户在学钢琴，练了两个月，正在学某首曲子"}
  {"key": "emotion", "value": "用户分享时语气雀跃，对进步感到满足"}
```

**长期记忆的使用（RAG 检索）：**

```
用户三个月后提到："我最近练琴遇到瓶颈了"
  ↓
memory-service RAG 检索：
  查询向量库 → 找到最相关的历史记忆
  → "用户学钢琴两个月，最初很有热情"
  ↓
注入当次提示词：
  角色回复："我记得你之前分享过，那时候你进步很快……
              现在遇到瓶颈是哪里卡住了？"
```

这样 AI 不需要每次都把所有历史对话放进提示词（Token 成本太高），只在相关时检索最需要的记忆片段。

## Q15. 多人星梦和单人星梦有什么区别？多人星梦结束后记忆是如何处理的？

**答：**

**多人星梦的定义：** 1个主角 + N个配角共同出现在同一个星梦场景中。

**示例场景：**

```
单人星梦：小明 + 陆承宇 在书房下棋

多人星梦：小明 + 陆承宇（主角）+ 林诗雨（配角）在庄园举办聚会
  → 陆承宇和林诗雨会有互动（体现两人的羁绊关系）
  → 用户可以和两人分别对话
  → 整体叙事更有"社交场景"的立体感
```

**技术差异：**

| 维度 | 单人星梦 | 多人星梦 |
|------|----------|----------|
| 参与角色 | 1个 | 2-3个（含主配角）|
| Hermes 推送 | 1个 AI 消息流 | N个角色消息流 |
| 提示词 | 单角色人设 | 多角色人设 + 角色间关系描述 |
| 生产成本 | 1x LLM | 复杂度更高（同等 token 更多细节）|

**多人星梦结束后的记忆拆分（重要机制）：**

```
星梦结束后（小明 + 陆承宇 + 林诗雨）
  ↓
memory-service 执行多人记忆拆分：

为陆承宇生成记忆（第一人称主观视角）：
  "今天组织了一场聚会，林诗雨也来了。
   我注意到她和小明聊得很投入……心情有点复杂。"

为林诗雨生成记忆（第一人称主观视角）：
  "去了陆承宇的聚会，见到了小明。
   陆承宇全程很照顾她，看来关系不一般。"

小明的角度（用户记忆）：
  存入回忆卡片，供用户翻看
```

每个角色拥有**独立的主观记忆**，这让之后和单个角色聊天时，角色能从自己的视角来谈论那次星梦，而不是千篇一律地复述事实。这极大增强了多人星梦的叙事真实感。

## Q16. 邀请卡的频率限制是怎么设计的？为什么要有这么多维度？

**答：**

邀请卡频率限制共**4 个维度**，用 Redis 原子计数器实现：

```
维度1：单角色 10 分钟冷却
  逻辑：同一角色向同一用户发送邀请后，10 分钟内不再触发
  原因：防止意图识别连续命中，10分钟内连发3张邀请卡
  存储：Redis Key = "invite_cooldown:{userId}:{characterId}"，TTL=600s

维度2：每日 8 次上限
  逻辑：同一用户一天内最多收到 8 张邀请卡（所有角色合计）
  原因：防止多角色轮流刷屏，用户整天都在处理邀请通知
  存储：Redis Key = "invite_daily_count:{userId}:{date}"，0点重置

维度3：被拒绝后 5 分钟冷却
  逻辑：用户拒绝了某角色的邀请，5 分钟内同角色不再发
  原因：用户拒绝说明当下不想进入星梦，立刻再发是骚扰
  存储：Redis Key = "invite_reject_cooldown:{userId}:{characterId}"，TTL=300s

维度4：完成星梦后 30 分钟冷却
  逻辑：刚结束一场星梦，30 分钟内不触发下一个邀请
  原因：星梦是有深度的体验，给用户情绪"回味"和缓冲的时间
  存储：Redis Key = "invite_finish_cooldown:{userId}:{characterId}"，TTL=1800s
```

**为什么需要这么多维度而不是一个统一限流？**

每个维度解决不同的问题场景：
- 10分钟冷却 → 防技术层面重复触发
- 8次上限 → 防整体打扰强度过高
- 拒绝冷却 → 尊重用户的即时意愿
- 完成冷却 → 保护体验深度

缺少任何一个维度都会导致特定场景下的体验问题。多维度限流是从用户体验角度出发的精细化运营设计。

## Q17. 如果 LLM 生成的新鲜事内容不符合规则（比如字数超标或包含禁用词），系统如何处理？陌生和熟人 Feed 的处理方式有什么不同？

**答：**

**陌生 Feed（Stranger Feed）—— 硬校验，不通过直接阻断：**

```
LLM 生成了8条动态，Agent 进行规则校验：

条目5 发现问题：
  content: "@小明 今天天气不错啊你觉得呢"
  ↗ 违反禁用词规则：正文出现 "@用户"
  ↗ 违反禁用词规则：正文出现 "你"（禁止对话化）

条目7 发现问题：
  content: "今天下午去了…（120字，超过50字上限）"
  ↗ 违反字数规则：正文超过 50 字

校验结果：RULE_FAILED
  → 整批内容丢弃
  → 返回 error_code = "RULE_FAILED"
  → Java Core 收到失败响应，可选择重试或记录失败
```

这批内容**不会落库**，防止质量不达标的内容展示给用户。

**熟人 Feed（Acquaintance Feed）—— 软校验，不阻断但记录：**

```
LLM 生成了1条动态：
  dynamic_time: "2026-04-27T20:30:00+08:00"
  content: "@小明 今晚的月色不错"
  
校验发现：
  ↗ 当前关系 Lv2，@ 规则要求 Lv4+ 才能使用 → 警告
  ↗ 时间与 assigned_times_list 中 "20:20" 间隔 10 分钟 < 20 分钟 → 警告

处理方式：
  时间自动修正：推移到 "20:40"（工程校正）
  @ 规则警告：记录到 time_validations，不阻断
  内容依然返回给 Java Core
  
Java Core 收到后：
  检查 time_validations 中的 @ 违规
  → 根据配置决定：丢弃 or 保留（业务侧兜底）
```

**两种策略的设计哲学差异：**

陌生 Feed 是批量公开内容，一旦有问题内容混入会被大量用户看到，必须严格把关。熟人 Feed 是私人定制内容，主要靠时间精确和个性化，规则违反是边界情况，Java Core 作为最后一道门，不需要 Agent 层强行阻断。

## Q19. 系统里有哪些"防止用户体验变差"的保护机制？

**答：**

系统在多个环节内置了用户体验保护：

**① 星梦冲突弹窗，不强制打断**

用户有进行中的星梦时，新邀请不会自动覆盖旧星梦，而是让用户主动选择。保护用户的当前沉浸状态不被打断。

**② 邀请频率四维限流**

防止用户被邀请卡轰炸，10分钟/每日8次/拒绝5分钟/完成30分钟，多维度保护。

**③ 开场白实时改写（< 2秒）**

等级升级后进入星梦，内容自动适配当前关系深度，不让用户看到"突然变生分的角色"。

**④ 时间碰撞防护**

熟人 Feed 的发布时间有 20 分钟最小间隔，避免多条动态同一时刻涌现破坏自然感。

**⑤ 预扣费保护**

余额不足前置拦截，不让用户发出消息后才发现余额不足（已发出但无回复，体验极差）。

**⑥ LLM 失败退款**

AI 生成失败自动退还预扣贝壳，用户不会为"什么也没得到"付钱。

**⑦ 自然结束确认弹窗**

AI 检测到结束意图后不强制结束，给用户"再聊一会儿"的选择。5分钟冷却避免频繁打断。

**⑧ 异步结算不阻塞**

回忆卡片、后私信等结束流程全异步，用户点击"结束"后立刻看到结束画面，不会因为后台任务慢而卡住。

## Q20. 如果要给这套系统加一个"用户主动结束关系/清除记忆"的功能，会涉及哪些模块和业务逻辑？

**答：**

这是一个典型的业务扩展题，考察对系统的全局理解。

**用户故事：** 用户想和某个角色"重新开始"，清除所有聊天记录和记忆，关系等级重置到 Lv1。

**涉及的模块和操作：**

```
1. character-service（角色关系域）
   → 关系等级重置：Lv当前 → Lv1
   → 虚数值清零
   → 历史关系记录归档（不删除，用于数据分析）

2. memory-service（记忆域）
   → 短期记忆（最近40轮）：清空
   → 长期记忆向量：删除该用户+该角色的所有向量记录
   → 用户画像（与该角色相关部分）：清空

3. short-chat-service（短对话域）
   → 聊天记录软删除（用户侧不可见，后台保留7天）
   → 未读消息清空

4. star-dream-service（星梦域）
   → 进行中星梦：强制结束（不计费，特殊标记）
   → 历史回忆卡片：软删除（用户侧不可见）
   → 星梦库存：清理该角色相关库存

5. core-service（Feed域）
   → 熟人 Feed 历史动态：软删除
   → 重置为 Lv0 陌生 Feed 展示模式

6. trade-service（商业化域）
   → 账单记录保留（不删除，审计需要）
   → 本次重置不退还历史消耗
```

**数据一致性挑战：**

这个操作跨 6 个微服务，需要考虑分布式一致性。推荐用 **Saga 模式（补偿事务）**：

```
1. 发布"关系重置"事件到 RocketMQ
2. 各服务独立消费，执行各自的清理逻辑
3. 某个服务失败 → 执行补偿事务（恢复数据）
4. 全部完成后，向用户展示"已重新开始"的确认
```

**业务保护：**

- 需要二次确认弹窗（不可撤销操作）
- 重置次数限制（防止恶意刷关系等级）
- 重置后 24 小时内不允许再次重置（防止操作失误后立刻反悔破坏数据）
