## 一、为什么 AI 对话系统需要记忆？

不带记忆的 AI 每次对话都是"初次见面"：

```
用户："上次我说我喜欢养猫，你还记得吗？"
AI：  "我不知道您之前说过什么。"  ← 体验崩塌
```

情感陪伴产品对记忆的要求尤为苛刻——用户期待 AI 角色像真正的朋友一样"了解自己"。这是心屿记忆系统要解决的核心问题。

## 二、心屿的双层记忆架构

> 图示见 [diagrams/memory/01-双层记忆架构.puml](diagrams/memory/01-双层记忆架构.puml)

架构分两层：**短期记忆（热）** 存放最近 40 轮原文对话，由 PostgreSQL 承载；**长期记忆（冷）** 存放经 LLM 提炼的关键事实与用户画像，由 PolarDB 向量引擎承载。Agent 每次调用时通过 MCP 工具同时读取两层，写入则全部异步走 RocketMQ 解耦。

### 2.1 短期记忆

| 维度 | 详情 |
|------|------|
| **存储位置** | PostgreSQL — `tb_short_chat_message` |
| **存储内容** | 原文对话消息（`role` + `content`），无任何 LLM 处理 |
| **容量** | 最近 40 轮（user + AI 各 1 条 = 1 轮） |
| **读取方式** | MCP 工具 `getAppShortChatMessage(userId, characterId, batchSize=40)` |
| **注入位置** | 提示词 `<近期对话摘要>` 标签，原文直接注入 |
| **更新时机** | 每次对话实时写入，无延迟 |
| **"滑出窗口"** | 消息在 DB 中永远保留，但已总结的批次不再被查询到，对 AI 不可见 |
| **触发总结** | 累计到 `triggerRoundCount=40` 轮时，发布 RocketMQ 事件，批次大小 `publish-round-count=20` |

**数据结构（`tb_short_chat_message`）：**

```sql
id           BIGINT PK
session_id   VARCHAR   -- chat_{type}_{userId}_{charId}_{ts}
user_id      BIGINT
character_id BIGINT
role         VARCHAR   -- "user" / "assistant"
content      TEXT      -- 消息原文
feedback     SMALLINT  -- 1=点赞 -1=点踩
send_time    TIMESTAMPTZ
```

### 2.2 长期记忆

长期记忆的核心是**事实提取 + 向量存储**，依托阿里云 PolarDB 的记忆管理能力实现。

> 触发流程见 [diagrams/memory/02-记忆总结触发流程.puml](diagrams/memory/02-记忆总结触发流程.puml)

`MemorySummaryProcessor` 收到 MQ 事件后执行五步：① Dubbo Generic Call 查询 N 轮对话；② 构造 `AddMemoryRequest`（含 `FACT_RETRIEVAL_PROMPT`）；③ `POST /v1/memories` 调用 PolarDB，LLM 提取事实并决策新增/更新/忽略；④ 标记已总结批次防重复；⑤ 异步触发用户画像提取。

**关键配置（可通过 Nacos 热更新）：**

```yaml
soul-haven.memory-summary:
  summary-trigger: 30           # 星梦：30 轮触发
  summary-batch-size: 30        # 每批处理 30 轮

chat.admin.short.memory-summary:
  trigger-round-count: 40       # 短对话：40 轮触发
  publish-round-count: 20       # 每次打包投递 20 轮

  mini-merge-threshold: 5       # 积累 5 条 mini 记录后触发合并
  max-attempts: 3               # 失败最多重试 3 次
  retry-interval-ms: 5000       # 重试间隔 5s
  confirm-timeout-ms: 16000     # 单次超时 16s
```

### 2.3 用户画像

用户画像是从对话中提炼的**结构化用户信息**，独立于事实记忆存在。

> 提炼链路见 [diagrams/memory/06-用户画像提炼链路.puml](diagrams/memory/06-用户画像提炼链路.puml)

| 维度 | 详情 |
|------|------|
| **存储** | PolarDB Profile 服务 |
| **生成时机** | 每次记忆总结完成后异步触发 |
| **生成方式** | `USER_PROFILE_EXTRACTION_PROMPT` → 结构化字段 |
| **合并方式** | `PROFILE_MERGE_PROMPT_v1` 新旧画像合并，保留最新最具体 |
| **读取方式** | MCP 工具 `getUserProfile(userId, roleId, saveId)` |
| **注入位置** | 提示词 `<用户画像>` 标签内 |

```json
{
  "nickname": "林夏",
  "profile": "产品设计师，正赶 UI 改版项目；习惯夜晚找角色倾诉；喜欢芋泥波波奶茶解压"
}
```

## 三、7 种记忆场景类型与隔离机制

> 场景类型关系见 [diagrams/memory/08-7种记忆场景类型.puml](diagrams/memory/08-7种记忆场景类型.puml)

```java
// SummarySceneType — sceneType 决定 runId 命名空间，彻底隔离不同业务的记忆
SHORT_CHAT(1)                    // 短对话：userId__characterId
GROUP_CHAT(2)                    // 群聊会话：sessionId
STAR_DREAM(3)                    // 单人星梦会话：roleId__saveId
GROUP_CHAT_ROLE_MEMORY(4)        // 群聊拆分到每个角色视角
STAR_DREAM_ROLE_MEMORY(5)        // 单人星梦拆分到每个角色视角
MULTI_STAR_DREAM(6)              // 多人星梦会话
MULTI_STAR_DREAM_ROLE_MEMORY(7)  // 多人星梦拆分到每个角色视角
```

**runId 空间隔离：**

| 场景 | runId 格式 | 隔离粒度 |
|------|-----------|---------|
| 短对话 | `userId__characterId` | 同用户不同角色互不干扰 |
| 单人星梦角色记忆 | `roleId__saveId` | 同存档内按角色隔离 |
| 多人星梦角色记忆 | `roleId__saveId` | 多角色各自独立视角 |
| 群聊 | `sessionId` | 按群聊会话隔离 |

**miniMerge 触发白名单**（仅星梦场景）：

```java
// SHORT_CHAT / GROUP_CHAT / MULTI_STAR_DREAM_ROLE_MEMORY 不进入合并流程
if (sceneType != STAR_DREAM(3)
 && sceneType != MULTI_STAR_DREAM(6)
 && sceneType != STAR_DREAM_ROLE_MEMORY(5)) {
    return;
}
```

原因：星梦是沉浸式长对话，单场产生事实多，需场内滚动压缩。短对话积累慢，PolarDB 自身去重已足够。

## 五、四个核心机制详解

### 5.1 记忆对比：谁来做，怎么做

心屿代码**只负责组装请求**，对比逻辑完全委托给 PolarDB 内部。关键开关是 `infer=true`：

```java
// MemorySummaryProcessor.buildAddMemoryRequest()
AddMemoryRequest.builder()
    .infer(Boolean.TRUE)       // 开启 LLM 推断：触发事实提取 + 与已有记忆对比
    .asyncMode(Boolean.FALSE)  // 同步等待（心屿自己控制 16s 超时）
    .messages(flattenRounds(batch))
    .prompt(singletonMap("FACT_RETRIEVAL_PROMPT", factRetrievalPromptName))
    .build();
```

**PolarDB 内部三步流程：**

```
① FACT_RETRIEVAL_PROMPT → LLM 从对话原文提取事实列表
   输入：[{role:user, content:"我养了只猫叫小饼"}, ...]
   输出：["用户养了一只橘猫，名字叫小饼"]

② 将新事实向量化，在 runId 空间内检索已有记忆做相似度对比

③ UPDATE_MEMORY_PROMPT → LLM 对每条新事实做三选一决策：
   ADD    → 全新事实，无相似条目 → 直接写入
   UPDATE → 与已有记忆冲突或更具体 → 覆盖旧版本
   NONE   → 与已有记忆高度重复 → 丢弃，不写入
```

**返回结构：**

```java
// AddMemoryResponse.results[]
{id:"mem_101", event:"UPDATE", memory:"用户名叫林夏，职业是产品设计师"}
{id:"mem_102", event:"ADD",    memory:"UI大改版项目，设计稿反复被推翻"}
{id:"mem_103", event:"NONE",   memory:"林夏是设计师"}  // 重复，不存
```

**LLM 推断失败的降级处理：**

```java
// persistRawConversationAfterDegraded()
AddMemoryRequest fallbackRequest = request.toBuilder()
    .infer(Boolean.FALSE)   // 不推断，把原始对话文本直接存入向量库
    .build();
memoryManagementHttpClient.addMemory(fallbackRequest);
// 后续可通过 POST /v1/memories/retry 对原文补跑推断
// 降级记录 status = FAILED_DEGRADED，仍纳入 miniMerge 计数
```

---

### 5.2 积累计数：不是内存计数器，是查数据库

每次 `addMemory` 成功后，`MemoryAddSuccessRecordAsyncWriter` 异步在 PostgreSQL 写入一行：

**`tb_memory_summary_task` 表结构：**

```sql
id               BIGINT PK
scene_id         VARCHAR   -- sessionId / saveId（场景维度 key）
scene_type       INT       -- 1=SHORT_CHAT 3=STAR_DREAM 等
user_id          BIGINT
summary_type     VARCHAR   -- "mini" / "merged"
message_id       VARCHAR   -- PolarDB 返回的批次 ID
memory_summarized BOOLEAN  -- false=未合并，true=已被 miniMerge 消费
status           VARCHAR   -- COMPLETED / FAILED_DEGRADED
created_at       TIMESTAMPTZ
```

**判断逻辑：**

```java
// MemorySummaryProcessor.mergeMiniMemoriesIfNeeded()
List<String> miniMessageIds = taskStateStore.listUnmergedMiniMessageIds(
    event.getSceneId(), threshold);  // threshold = miniMergeThreshold = 5

if (miniMessageIds.size() < threshold) {
    return;  // 不足 5 条，本次不触发合并
}
```

**等效 SQL：**

```sql
SELECT message_id FROM tb_memory_summary_task
WHERE scene_id = ?
  AND summary_type = 'mini'
  AND status IN ('COMPLETED', 'FAILED_DEGRADED')  -- 降级的也参与合并
  AND memory_summarized = false
  AND message_id IS NOT NULL
ORDER BY created_at ASC
LIMIT 5;
```

---

### 5.3 去重：两个层次

| 层次 | 执行者 | 时机 | 粒度 | 方式 |
|------|--------|------|------|------|
| **第一层** | PolarDB LLM（NONE 事件） | addMemory 时，实时 | 单条事实 vs 向量库 | 向量相似度 + LLM 判断，NONE 直接丢弃 |
| **第二层** | PolarDB LLM（mergeMemories） | 积累 5 条后，批量 | 跨批次语义级 | 取出 5 批全部事实，LLM 统一审阅融合 |

第一层解决**单次写入内部重复**；第二层解决**跨批次语义重叠**——即使每次 `addMemory` 都去重了，5 批记忆之间仍可能有相似表述，需合并时统一精简。

---

### 5.4 合并：滚动收敛

```java
// MemorySummaryProcessor.buildMergeRequest()
MergeMemoriesRequest.builder()
    .messageIds(mergeIds)       // 最早的 5 条 messageId
    .deleteOld(true)            // 合并成功后删除 5 条源记忆
    .prompt(Map.of(
        "FACT_RETRIEVAL_PROMPT", factRetrievalPromptName,
        "MERGE_MEMORY_PROMPT",   mergeMemoryPromptName
    ))
    .build();
```

**PolarDB mergeMemories 内部流程：**

```
① 按 messageId 取回 5 批所有事实（可能共数十条）
② LLM 用 MERGE_MEMORY_PROMPT 做融合决策：
   · 保留最具体、最新的版本
   · 合并语义相近的描述（多条→一条）
   · 彻底删除冗余重复条目
③ deleteOld=true → 删除 5 条原始向量记录
④ 写入融合后的精华记忆，返回 mergedMessageId
```

**合并后 PostgreSQL 状态变更：**

```java
// MybatisSummaryTaskStateStore.markMemoriesMerged()

// 操作一：批量标记 5 条旧记录已合并
UPDATE tb_memory_summary_task
SET memory_summarized = true
WHERE message_id IN ('batch_001', 'batch_002', ..., 'batch_005')

// 操作二：插入新合并记录，继续参与下一轮
INSERT INTO tb_memory_summary_task
  summary_type      = 'merged'
  message_id        = 'merged_001'   -- PolarDB 返回的新 ID
  memory_summarized = false          -- 继续参与下轮
  status            = 'COMPLETED'
```

**滚动收敛机制：**

```
第 1 轮：[A, B, C, D, E] → mergeMemories → M1
第 2 轮：[M1, F, G, H, I] → mergeMemories → M2
第 3 轮：[M2, J, K, L, M] → mergeMemories → M3
...
最终收敛为一条持续被精炼的高质量长期记忆
```

每轮合并的输入都包含上轮结果（M1、M2…），确保全量历史的精华不丢失。

---

### 5.5 四个机制对比总结

| 机制 | 执行者 | 触发时机 | 粒度 | 存储介质 |
|------|--------|---------|------|---------|
| **记忆对比** | PolarDB LLM（FACT RETRIEVAL + UPDATE MEMORY Prompt） | addMemory 时，实时 | 单条事实 vs 向量库 | PolarDB 向量库 |
| **积累计数** | PostgreSQL 查表行数 | 每次 addMemory 成功后 | scene_id 下的 mini 记录数 | PostgreSQL |
| **去重** | ① PolarDB NONE 事件 ② mergeMemories LLM | ① 实时 ② 批量 | ① 事实级 ② 跨批次语义级 | PolarDB 向量库 |
| **合并** | PolarDB LLM（MERGE MEMORY Prompt） | 积累到 miniMergeThreshold(5) 条后 | 多批次 → 一条精华记忆 | PolarDB + PostgreSQL |

## 六、各业务场景的记忆细节

### 6.1 短对话（Short Chat）

> 完整 9 阶段流程见 [diagrams/memory/09-短对话记忆完整流程.puml](diagrams/memory/09-短对话记忆完整流程.puml)

Agent 通过 MCP 并行读取：短期 40 轮原文 + 用户画像 + 长期记忆 TopK，全部注入提示词。当轮次达到 40 轮阈值，异步发布 `SummaryReadyEvent`，不阻塞当前回复。**不触发 miniMerge**，PolarDB 自身的 ADD/UPDATE/NONE 去重已足够。

记忆隔离维度：`runId = userId__characterId`，同用户与不同角色的记忆完全隔离。

### 6.2 星梦（Star Dream）

> 三层结构见 [diagrams/memory/05-星梦三层记忆结构.puml](diagrams/memory/05-星梦三层记忆结构.puml)

星梦记忆分三层嵌套：

| 层 | 温度 | 内容 | 触发条件 |
|----|------|------|---------|
| 层 1（热） | 当场上下文 | 本场所有对话原文，实时读 PostgreSQL | 每轮实时写入 |
| 层 2（中） | 场内 mini summary | 场内关键情节提炼，替换原文节省 token | 积累 `miniMergeThreshold=5` 条触发 |
| 层 3（冷） | 跨场景长期记忆 | `STAR_DREAM_ROLE_MEMORY(5)`，PolarDB 向量存储 | 星梦结束后沉淀 |

**场景举例：** 第 1 次星梦：用户和角色去海边，提到害怕浪花 → 沉淀为长期记忆。第 5 次星梦：角色主动说"我特意选了背海的那张桌子" → 通过向量检索到"害怕浪花"，体现角色记忆。

### 6.3 多人星梦（Multi Star Dream）

> Fan-out 流程见 [diagrams/memory/04-多人星梦记忆拆分.puml](diagrams/memory/04-多人星梦记忆拆分.puml)

多人星梦结束后：先触发会话级总结（`sceneType=6`），再并行 fan-out 为 N 条角色维度任务（`sceneType=7`），每条用 `MULTI_STAR_DREAM_SINGLE_PERSPECTIVE` Prompt 从各自第一人称视角提炼事实，写入各自独立的 `runId = charX__saveId` 空间。A 和 B 的记忆相互隔离，不混用对方视角。

### 6.4 熟人新鲜事（Acquaintance Feed）

熟人 Feed 是**离线批量生产**，记忆不由 Agent 通过 MCP 读取，而是 Java Core 主动查询后打包传入：

```python
# AcquaintanceFeedInput 字段
recent_short_chat_messages: List  # Java 直接传最近 40 轮
long_term_memory: str             # Java 查询后拼接为字符串传入
user_profile: str                 # Java 查询后传入
```

原因：Feed 生产是离线调度，无实时会话上下文，由 Java Core 统一准备数据作为请求参数传入，Agent 不需要主动 MCP 拉取。

## 七、技术难点与解法

### 7.1 记忆幂等性（防重复总结）

MQ 消费可能重复，同一批轮次被总结两遍导致记忆污染。

```
Redis Key: memory:summary:idempotency:{userId}:{characterId}:{sessionId}
TTL: 7 天
流程：投递 MQ 前生成幂等键 → 消费时先检查 Redis → 已存在则跳过
```

### 7.2 超时与重试

```yaml
confirm-timeout-ms: 16000   # addMemory 超时 16s → 标记失败 → 进入重试队列
max-attempts: 3             # 最多重试 3 次，间隔 5s
retry-failed-job:
  cron: "0 */10 * * * ?"   # XXL-Job 每 10 分钟扫描兜底
  parallelism: 8            # 8 个并行线程
```

降级路径：超时或 LLM 静默失败 → `infer=false` 存原文 → `status=FAILED_DEGRADED` → 后续 `/v1/memories/retry` 补跑推断。降级记录仍纳入合并计数，不影响整体流程。

### 7.3 记忆隔离（runId 命名空间）

```
同一用户与角色A 的记忆（userId__charA）
↕ 完全隔离
同一用户与角色B 的记忆（userId__charB）
```

PolarDB 所有查询都带 `runId` 过滤，彻底防止跨角色记忆污染。

### 7.4 短期窗口管理

短期记忆不是删除旧消息，而是通过 `memory_summarized` 标记控制可见性：
- 消息永久存在 PostgreSQL（审计/历史）
- 已总结批次标记后不再被 `getAppShortChatMessage` 查到
- AI 视角：超过 40 轮的内容"自然退出"上下文窗口

## 八、业内主流记忆方案对比

> 方案七（分层记忆）与心屿对照见 [diagrams/memory/07-MemoryOS分层方案.puml](diagrams/memory/07-MemoryOS分层方案.puml)

| 方案 | 核心思路 | 代表产品/框架 | 心屿使用 |
|------|---------|-------------|---------|
| **滑动窗口** | 保留最近 N 条消息，旧消息丢弃 | 基础聊天机器人 | ✓ 短期记忆 |
| **摘要压缩** | 定期对旧对话 LLM 压缩为摘要字符串 | ChatGPT Memory、LangChain Summary | ✓ 星梦 mini summary |
| **RAG 向量记忆** | 提取关键事实，向量化按需检索 | Mem0、Zep、PolarDB Memory | ✓ 长期记忆核心 |
| **用户画像** | 结构化提炼用户属性，独立于事件流 | ChatGPT Memory、Character.AI | ✓ 用户画像 |
| **知识图谱** | 实体+关系图，支持多跳推理 | GraphRAG、Zep v2、LangChain KG | ✗ 未使用 |
| **分层记忆** | 短/中/长三层，各有温度和 TTL | MemoryOS（2025 论文） | 参考，天然对应 |
| **情节记忆** | 完整保存事件快照（时间/场景/情绪） | 游戏 NPC AI | ✓ 星梦角色记忆 |

### RAG 向量记忆核心实现（心屿 vs Mem0）

心屿的长期记忆架构与 Mem0 高度相似，PolarDB Memory API 相当于托管版 Mem0：

| Mem0 概念 | 心屿实现 |
|-----------|---------|
| `user_id` | userId |
| `agent_id` | characterId（角色作为 agent） |
| `run_id` | `userId__characterId` / `roleId__saveId` |
| `add()` 事实抽取 | PolarDB addMemory + `FACT_RETRIEVAL_PROMPT` |
| 向量存储 | PolarDB 内置向量引擎 |
| `search()` 检索 | Agent 调用时 MCP 注入 TopK |
| `memory merge` | `mergeMemories`（miniMerge 滚动收敛） |

### 分层记忆（MemoryOS）对应关系

| MemoryOS 层 | 温度 | 类比 | 心屿对应 |
|-------------|------|------|---------|
| Working Memory | Hot | RAM | 短期记忆（40 轮原文） |
| Episodic Memory | Warm | SSD | 星梦 mini summary（场内提炼） |
| Semantic Memory | Cold | 归档 | 长期事实 + 用户画像（PolarDB） |

心屿天然对应三层，但层间流动由 `summaryTrigger` **阈值驱动**，而非 MemoryOS 中的 LLM 实时决策。

## 九、心屿记忆架构的优缺点分析

### 优点

**职责分离清晰**：短期记忆（short-chat-service）、长期记忆（memory-service）、画像（PolarDB Profile）各自独立，MCP 工具调用解耦，Agent 不直接依赖 Java 服务实现。

**异步不阻塞**：记忆总结走 RocketMQ 异步，不影响用户等待 AI 回复的延迟。

**幂等 + 重试保障**：Redis 幂等键 + XXL-Job 扫描重试 + 降级存原文，记忆总结最终一致。

**场景隔离充分**：7 种 SummarySceneType + runId 命名空间，短聊/星梦/群聊/多人星梦的记忆互不干扰。

**滚动收敛不丢信息**：miniMerge 的合并结果继续参与下轮合并，早期对话的关键事实通过多轮精炼持续保留。

### 不足 / 可优化方向

**记忆检索透明度低**：`long_term_memory` 是字符串，Agent 不知道检索了哪些记忆、各条相关度如何。优化：注入时携带得分和来源场景标注。

**记忆遗忘机制缺失**：用户信息可能变化（换了工作、搬了城市），旧事实持续影响 AI 输出。优化：引入 TTL 或"记忆置信度"衰减机制，低置信度事实权重降低。

**用户画像跨角色共享问题**：`getUserProfile` 查全局画像，不区分角色。对某角色说的私密内容可能通过画像"泄露"给另一个角色。优化：画像按角色维度分层（全局属性 + 角色特有认知）。

**多人星梦视角拆分质量依赖 Prompt**：`MULTI_STAR_DREAM_SINGLE_PERSPECTIVE` 由 LLM 拆分视角，边界模糊时 A 的记忆可能混入 B 的视角。

**miniMerge 粒度固定**：阈值 5 条固定，高频用户可能积累过快，低频用户等待时间长。优化：按用户活跃度动态调整阈值。

## 十、面试常见追问

**Q：为什么选 PolarDB 存记忆，而不是 Pinecone / Weaviate 等专业向量数据库？**

> PolarDB 是阿里云托管服务，已内置 LLM 事实抽取 + 向量存储 + 合并去重的完整 pipeline，相当于"托管版 Mem0"。自建需要额外维护 embedding 模型、抽取逻辑、合并策略，成本高。对初期产品选择开箱即用的托管服务是务实之选，且阿里云生态更符合国内合规要求。

**Q：短期记忆 40 轮这个数字怎么定的？**

> 这是 token 预算和记忆效果的折衷。以平均每条 50 字估算，40 轮约 4000 字，占用约 5500 token，留给角色设定和输出的空间足够。可通过 Nacos 热更新，根据模型 context window 大小动态调整。

**Q：短期记忆超过 40 轮的消息被删掉了吗？**

> 不是删除，是"退出窗口"。消息永久存在 PostgreSQL 中（可用于历史查看、审计）。超过 40 轮的批次在被异步总结后标记为已处理，`getAppShortChatMessage` 查询时自动不包含这些记录。旧消息变成了 PolarDB 里的事实，以更精炼的形式继续影响 AI。

**Q：如果 PolarDB 记忆服务宕机，用户体验有影响吗？**

> 短期内无感知。短期记忆（40 轮原文）和用户画像仍正常工作，只是长期记忆不再更新。RocketMQ 消息持久化等待重新消费，XXL-Job 定时重试兜底。超过 40 轮的老用户在窗口滑过后，AI 可能"忘记"超出部分——这是唯一的实质影响。

**Q：addMemory 里的 NONE 事件和 mergeMemories 都能去重，两者有什么本质区别？**

> NONE 是**单次写入内的实时去重**，粒度是"新提取的单条事实 vs 向量库已有记忆"，防止同一个事实被反复写入。mergeMemories 是**跨批次的语义合并**，粒度是"5 批记忆（可能几十条）之间的语义重叠"，即使每次写入都去重了，不同批次之间仍可能有相似表述（比如"林夏是设计师"和"林夏是产品设计师"），需要合并时统一精简到最具体的版本。

**Q：用户画像和长期记忆有什么区别，为什么要分开？**

> 长期记忆存的是"发生了什么"（事件/事实流，如"林夏今天加班到九点"），画像存的是"用户是什么样的人"（稳定特征，如"职业：产品设计师，喜欢奶茶"）。分开的原因：①检索方式不同，事实需要按相关性向量检索，画像每次全量注入；②更新频率不同，画像是对所有对话的提炼，事实是每批次实时更新；③隔离边界不同，当前画像是全局的（跨角色共享），事实是按 runId 隔离的。
