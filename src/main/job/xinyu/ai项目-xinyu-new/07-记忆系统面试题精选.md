## 第一部分：架构设计

### Q1 ⭐ 你们的 AI 记忆系统整体是怎么设计的？为什么要分两层？

**考点**：能否用清晰的框架描述系统，而非罗列技术词汇。

**参考答案**

记忆系统分**短期记忆**和**长期记忆**两层，各自职责清晰：

| | 短期记忆 | 长期记忆 |
|--|---------|---------|
| 存什么 | 最近 40 轮对话原文 | LLM 提炼的结构化事实 + 用户画像 |
| 存在哪 | PostgreSQL `tb_short_chat_message` | PolarDB 向量引擎（Memory API） |
| 怎么读 | 直接 SQL 查询，全量注入 Prompt | 向量相似度检索，TopK 注入 |
| 更新时机 | 每次对话实时写入 | 累计 40 轮后异步触发，LLM 提炼 |

**为什么分两层？**

单层设计的问题：
- 如果只有短期：40 轮之外的对话 AI 完全遗忘，长期关系无法维持
- 如果只有长期向量：检索有 TopK 上限，连续对话上下文丢失，且向量化有延迟
- 如果把全部历史塞进 Context：超出模型 token 限制，成本爆炸

两层分工的本质是**温度分层**——热数据（近期原文）直接访问，冷数据（历史精华）按需召回，兼顾完整性和效率。

### Q2 ⭐ 记忆总结为什么用 RocketMQ 异步触发，而不是对话完成后同步执行？

**考点**：理解异步解耦的工程动机，不只是说"为了性能"。

**参考答案**

有三个具体原因：

**① 不阻塞用户体验**  
记忆总结要调用 PolarDB Memory API，内部要跑两次 LLM（事实提取 + 冲突决策），加上用户画像提取又是两次 LLM（画像提取 + 画像合并），整体耗时可能 10~20 秒。如果同步执行，AI 回复完成后用户要等这 20 秒才能发下一条消息——体验完全不可接受。

**② 可靠投递**  
RocketMQ 消息持久化，PolarDB 临时宕机时消息不丢，恢复后自动重新消费。同步调用若失败，只能在业务代码里加重试逻辑，复杂且不可靠。

**③ 解耦部署**  
对话服务（short-chat-service）和记忆服务（memory-service）可以独立扩缩容——记忆总结是 CPU/IO 密集型，需要较多实例；对话服务是高并发低延迟型，两者资源诉求不同。

### Q3 ⭐⭐ 记忆系统有 7 种 `SummarySceneType`，为什么要按场景类型隔离记忆，隔离是如何实现的？

**考点**：多租户 / 多维度数据隔离的设计思路。

**参考答案**

**为什么隔离？**

不同场景产生的记忆语义完全不同：
- 短对话里"林夏说她喜欢奶茶"→ 个人偏好
- 群聊里"三个角色讨论了城市探店"→ 多角色共同事件
- 多人星梦里 A 角色视角 vs B 角色视角 → 对同一场景的不同感知

若不隔离，短对话的记忆会污染星梦体验，群聊事件会混入私人对话——AI 的行为会变得不可预期。

**如何隔离？**

通过 `runId` 命名空间实现：

```
SHORT_CHAT(1)              → runId = userId__characterId
STAR_DREAM(3)              → runId = roleId__saveId
STAR_DREAM_ROLE_MEMORY(5)  → runId = roleId__saveId（角色视角）
MULTI_STAR_DREAM(6)        → runId = sessionId
MULTI_STAR_DREAM_ROLE_MEMORY(7) → runId = roleId__saveId（多人场景角色视角）
GROUP_CHAT(2)              → runId = sessionId
```

PolarDB 所有 `addMemory` 和 `searchMemories` 调用都带 `runId` 参数过滤，彻底防止跨场景记忆污染。同一个用户与角色 A 的记忆和与角色 B 的记忆完全独立，检索不会跨界。

### Q4 ⭐⭐ 你们用 PolarDB 存向量记忆，为什么不用 Pinecone、Weaviate 这类专业向量数据库？

**考点**：技术选型的务实判断，而非追求"最先进"。

**参考答案**

核心原因是 **PolarDB Memory API 是"托管版 Mem0"**，不只是一个向量数据库，而是包含完整记忆管理 pipeline 的托管服务：

| 能力 | 自建专业向量库 | PolarDB Memory API |
|------|-------------|-------------------|
| 向量存储 + 检索 | ✓ | ✓ |
| 事实提取（LLM） | ❌ 需自己实现 | ✓ 内置（`infer=true`） |
| ADD/UPDATE/NONE 冲突决策 | ❌ 需自己实现 | ✓ 内置 |
| 批次合并去重 | ❌ 需自己实现 | ✓ `mergeMemories` |
| runId 命名空间隔离 | ❌ 需自己实现 | ✓ 内置 |

选自建方案意味着要自己维护：embedding 模型服务、事实抽取 Prompt 逻辑、冲突决策算法、合并策略——这是完整的工程子系统，对初期产品不划算。

另外，阿里云生态更符合国内合规要求（数据不出境），和 RocketMQ、Nacos 等在同一 VPC 内访问延迟更低。

### Q5 ⭐ 短期记忆说是"滑动窗口 40 轮"，超过 40 轮的消息被删掉了吗？

**考点**：细节理解，"滑动窗口"不等于"删除"。

**参考答案**

不是删除，是**退出可见窗口**。

所有消息**永久保存在 PostgreSQL** `tb_short_chat_message` 中，供历史记录查看和审计。

"滑出窗口"的机制：
1. 每次对话写入新消息后，`getAppShortChatMessage` 查询只取最近 40 轮（`LIMIT 40 ORDER BY send_time DESC`）
2. 当某批 20 轮被异步总结后，`memory_summarized` 字段被标记为 `true`
3. 被标记的消息不再被 MCP 工具返回，从 AI 的视角"自然消失"

超出 40 轮的历史并没有丢失——它已经被 LLM 提炼为 PolarDB 里的事实，以更精炼的形式继续影响 AI 的行为。这是从"原文存储"到"语义存储"的转换，不是遗忘。

### Q6 ⭐⭐ 记忆写入时 `infer=true` 具体触发了什么？PolarDB 内部做了什么？

**考点**：对核心接口语义的深度理解。

**参考答案**

`infer=true` 是 PolarDB Memory API 的关键开关，触发内部完整的**三步记忆处理 pipeline**：

```
① FACT_RETRIEVAL_PROMPT → LLM 从对话原文提取结构化事实

输入：
  [
    {role: "user", content: "今天加班到九点了，UI 改版设计稿又被推翻了"},
    {role: "assistant", content: "又加班？什么项目这么紧，说来听听"}
  ]

输出（候选事实列表）：
  ["林夏是产品设计师", "UI 大改版项目设计稿被推翻", "林夏习惯加班到深夜"]
```

```
② 将候选事实向量化，在 runId 命名空间内检索已有记忆，找相似条目
```

```
③ UPDATE_MEMORY_PROMPT → LLM 对每条候选事实做三选一决策：

ADD    → 全新事实，向量库中无相似内容 → 直接写入新记忆
UPDATE → 与已有记忆语义冲突或新版更具体 → 用新版覆盖旧版
NONE   → 与已有记忆高度重复 → 丢弃，不写入
```

返回的 `AddMemoryResponse.results[]` 包含每条事实的处理结果：

```json
[
  {"id": "mem_101", "event": "UPDATE", "memory": "林夏是产品设计师"},
  {"id": "mem_102", "event": "ADD",    "memory": "UI改版设计稿被推翻"},
  {"id": "mem_103", "event": "NONE",   "memory": "林夏是设计师"}
]
```

心屿代码只负责组装请求，这三步全在 PolarDB 内部执行，不需要心屿侧写任何 LLM 调用代码。

### Q7 ⭐⭐ 什么是 `miniMerge`？为什么只有星梦场景触发，短对话不触发？

**考点**：场景差异驱动机制差异的设计思维。

**参考答案**

**miniMerge 是什么**

`miniMerge` 是跨批次的记忆合并机制：当某个 `scene_id` 下累积了 `miniMergeThreshold=5` 条 mini 记忆（即 5 次 `addMemory` 成功记录）后，调用 PolarDB `mergeMemories` 接口，把 5 批记忆中的事实统一融合，去掉跨批次的语义重叠，输出一条精炼的合并记忆。

**触发白名单（只有以下三种场景）：**

```java
if (sceneType == STAR_DREAM(3)
 || sceneType == MULTI_STAR_DREAM(6)
 || sceneType == STAR_DREAM_ROLE_MEMORY(5)) {
    triggerMiniMerge();
}
```

**为什么短对话不触发？**

原因是**事实密度不同**：

- 短对话：内容零散，每 40 轮触发一次总结，一次对话可能只提炼 1~3 条事实。PolarDB 在 `addMemory` 时的 ADD/UPDATE/NONE 单次去重已经足够。
- 星梦：沉浸式长对话，单场景产生事实密度高，一场星梦可能产生几十条事实，且跨批次语义重叠大（同一场景的描述会多次出现），必须通过 `mergeMemories` 做跨批次精炼。

简单说：**短对话积累慢，PolarDB 自身去重够用；星梦积累快，必须主动合并防止记忆膨胀**。

### Q8 ⭐⭐⭐ 系统里有几层去重？每层的粒度和执行者分别是什么？

**考点**：多层次设计的理解，能分清每层解决什么问题。

**参考答案**

共两层，各解决不同粒度的重复问题：

**第一层：单次写入内去重（实时，PolarDB 内部）**

- **执行者**：PolarDB LLM，通过 `UPDATE_MEMORY_PROMPT`
- **触发时机**：每次 `addMemory` 调用时
- **粒度**：新提取的单条事实 vs 向量库已有记忆
- **机制**：向量相似度匹配 + LLM 语义判断 → 返回 `NONE` 事件 → 直接丢弃，不写入
- **解决的问题**：同一个事实被反复提取，防止"林夏是设计师"这条记忆被写入十次

**第二层：跨批次语义合并去重（批量，PolarDB mergeMemories）**

- **执行者**：PolarDB LLM，通过 `MERGE_MEMORY_PROMPT`
- **触发时机**：积累 5 条 mini 记忆后触发 miniMerge
- **粒度**：5 批记忆（可能几十条事实）之间的语义重叠
- **机制**：取出 5 批全部事实，LLM 统一审阅，相似表述合并为最具体版本，冗余删除
- **解决的问题**：即使每次写入都去重了，不同批次间仍可能存在"林夏是设计师" vs "林夏是产品设计师"的语义近义，需统一精简

**两层的本质区别：**  
第一层是**防止重复写入**，第二层是**消除历史积累的冗余**。缺少第二层，记忆库会随时间膨胀，检索时噪音越来越多。

### Q9 ⭐⭐⭐ 描述一下 miniMerge 的"滚动收敛"机制，第 N 轮合并的输入里包含什么？

**考点**：对合并机制的深度理解，能否说清楚"历史不丢"是如何保证的。

**参考答案**

`miniMerge` 使用**滚动收敛**（rolling convergence）策略，每轮合并的产物参与下一轮合并：

```
第 1 轮：取前 5 批  [A, B, C, D, E]           → mergeMemories → M1
第 2 轮：取下 5 批  [M1, F, G, H, I]          → mergeMemories → M2
第 3 轮：取下 5 批  [M2, J, K, L, M]          → mergeMemories → M3
...
最终：一条持续被精炼的高质量长期记忆
```

关键点：`M1` 是第一批的合并结果，进入第二轮时它作为普通的一条 mini 记录，和 F/G/H/I 一起被输入。这意味着 A-E 中的精华已经蒸馏进 `M1`，不会在第二轮被丢弃。

**PostgreSQL 侧的状态变化：**

合并完成后 `MybatisSummaryTaskStateStore.markMemoriesMerged()` 执行两步：
1. `UPDATE tb_memory_summary_task SET memory_summarized=true WHERE message_id IN (A,B,C,D,E)` — 5 条旧记录标记为已合并
2. `INSERT INTO tb_memory_summary_task (summary_type='merged', message_id='M1', memory_summarized=false)` — 合并结果作为新记录继续参与后续计数

`memory_summarized=false` 确保 M1 会被下一轮的 `listUnmergedMiniMessageIds` 查到，形成滚动链条。

### Q10 ⭐⭐ 用户画像（Profile）和长期记忆（Memory）有什么区别？为什么要分开存？

**考点**：理解两种信息的本质差异，而非把它们当成同一类数据。

**参考答案**

**本质区别：**

| | 长期记忆 | 用户画像 |
|--|---------|---------|
| 存的是什么 | "发生了什么"（事件流、情节） | "用户是什么样的人"（稳定特征） |
| 举例 | "林夏今天加班到九点，UI 改版稿被推翻" | "职业：产品设计师；喜好：芋泥波波奶茶" |
| 更新频率 | 每 40 轮实时更新 | 每次总结后异步触发，频率低 |
| 读取方式 | TopK 向量检索（按相关性按需召回） | 全量读取，每次完整注入 Prompt |
| 生命周期 | 每条事实独立存在，按 runId 隔离 | 合并式存储，新旧画像 LLM 融合，保留最新最具体 |
| 存储位置 | PolarDB Memory API（向量） | PolarDB Profile API（纯文本 JSON） |

**为什么分开：**

1. **检索方式不同**：记忆需要"按相关性召回"（TopK），每次查询关键词决定哪些记忆被检索到；画像每次必须全量注入，因为"用户是产品设计师"这条信息每次都相关。
2. **合并语义不同**：记忆的 UPDATE 是"覆盖旧版本"，画像的 merge 是"融合新旧字段，保留最具体"——两套 Prompt，两套逻辑。
3. **隔离粒度不同**：当前实现中，画像是全局的（跨角色共享），记忆按 `runId` 隔离。这是设计取舍（优化点之一）。

### Q11 ⭐⭐ 记忆总结是异步 MQ 触发的，如果同一批消息被消费两次怎么办？

**考点**：分布式消息幂等性的具体实现。

**参考答案**

通过 **Redis 幂等键** 解决，整体是一个"先占锁再执行"的模式：

```
Key 格式：memory:summary:idempotency:{userId}:{characterId}:{sessionId}
TTL：7 天
```

**执行流程：**

```
1. 对话服务发布 MQ 事件之前，生成幂等键并写入 Redis（SET NX + TTL）
2. 消费端 RedisSummaryIdempotencyStore.tryAcquire() 检查 Key：
   - Key 已存在 → 重复投递 → 直接跳过，记录日志
   - Key 不存在 → 首次消费 → SET 并继续执行
```

**为什么 TTL 是 7 天？**

防止合法的"7 天后再次触发同一批次"被误判为重复——7 天内同一批次的重复消费都会被过滤，7 天后自动解锁，极端情况下可允许补跑。

**TTL 设计的注意点：**  
TTL 过短，重复消费拦截失效；TTL 过长，消息积压导致 Redis 内存膨胀。7 天是 MQ 消息最大重试窗口的经验值。

### Q12 ⭐⭐ `addMemory` 调用失败了怎么处理？失败的批次还会参与后续 miniMerge 计数吗？

**考点**：降级策略和最终一致性的理解。

**参考答案**

失败处理分两个层次：

**层次一：超时/LLM 失败的降级**

```java
// MemorySummaryProcessor.persistRawConversationAfterDegraded()
AddMemoryRequest fallbackRequest = request.toBuilder()
    .infer(Boolean.FALSE)   // 关闭 LLM 推断
    .build();
memoryManagementHttpClient.addMemory(fallbackRequest);
// → 原始对话原文直接存入向量库，不做事实提取
// → PostgreSQL 记录 status = FAILED_DEGRADED
```

降级的意义：原文存入后，用户再次对话时 TopK 检索能召回这段原文（语义效果弱于提炼后的事实，但不至于记忆完全丢失）。后续可通过 `POST /v1/memories/retry` 对原文补跑 LLM 推断，追平正常链路。

**层次二：定时重试兜底**

```yaml
retry-failed-job:
  cron: "0 */10 * * * ?"   # 每 10 分钟扫描一次失败记录
  parallelism: 8             # 8 线程并行重试
  max-attempts: 3            # 最多重试 3 次
```

**关键：失败记录（FAILED_DEGRADED）仍纳入 miniMerge 计数**

`listUnmergedMiniMessageIds` 的查询条件：

```sql
AND status IN ('COMPLETED', 'FAILED_DEGRADED')
```

即使降级的批次也参与计数，防止失败批次"卡住"合并流程——合并时 PolarDB 按 messageId 取回内容，降级批次取到的是原文，合并 LLM 会将其和正常提炼的事实一起处理，质量有所降低但不阻塞。

### Q13 ⭐ 多人星梦结束后，三个角色的记忆是怎么拆分的？A 角色的记忆会不会混入 B 角色的视角？

**考点**：并发 fan-out 处理与隔离设计。

**参考答案**

多人星梦结束后，记忆拆分走**两阶段 fan-out**：

**阶段一：会话级总结（sceneType=6）**

对整场多人星梦产生一次汇总记忆，`runId = sessionId`，记录"这场星梦发生了什么"。

**阶段二：角色维度并行拆分（sceneType=7）**

并行触发 N 条独立任务（N = 参与角色数），每条任务：
- 使用独立的 `MULTI_STAR_DREAM_SINGLE_PERSPECTIVE` Prompt
- Prompt 明确指定"只从角色 X 的第一人称视角提取"
- 写入独立的 `runId = charX__saveId`

A 角色的记忆写到 `charA__saveId`，B 角色写到 `charB__saveId`，**PolarDB 的 `runId` 过滤保证检索时只能查到各自命名空间内的记忆**，不会跨界。

下次用户与 A 单独聊天，LLM 召回的是 `charA__saveId` 下的记忆——A 只知道自己视角看到的事，不会"知道" B 心里的想法。

**潜在缺陷：**  
视角拆分质量依赖 `MULTI_STAR_DREAM_SINGLE_PERSPECTIVE` Prompt 的精确性，当场景中三个角色同时发言时，LLM 可能混淆归属，这是已知的优化点。

### Q14 ⭐⭐⭐ 心屿记忆系统的短期记忆为什么选 40 轮这个阈值？触发总结时又为什么只发 20 轮，不发全部 40 轮？

**考点**：工程参数背后的设计逻辑，而非死记数字。

**参考答案**

---

#### 第一问：为什么是 40 轮？

本质是 **token 预算** 和 **体验质量** 的折衷，不是拍脑袋定的数字。

以平均每条消息 50 字估算，40 轮 = 80 条消息 ≈ 4000 字 ≈ **5500 token**。

整个 Prompt 各部分的 token 消耗：

```
角色人设          ~800 token
用户画像          ~300 token
长期记忆 TopK     ~500 token
短期 40 轮原文    ~5500 token
输出预留空间      ~1000 token
─────────────────────────────
合计              ~8100 token
```

qwen3-max 的 context window 约 16K token，8100 只用了一半，还有余量应对长消息的波动。

40 轮是"刚好够覆盖一段完整对话上下文"的经验值，可以通过 Nacos 热更新随时调整，不需要重启服务。

#### 第二问：为什么触发时只发 20 轮，不是全部 40 轮？

先看一个具体的时间轴，理解"窗口"是怎么移动的：

```
第 1 轮 ─ 第 20 轮：[  批次 A（第1-20轮）  ]
第21 轮 ─ 第 40 轮：[  批次 B（第21-40轮）  ]
                                              ↑
                              累计到 40 轮，触发总结
```

**触发时，AI 的短期记忆窗口是什么？**

`getAppShortChatMessage` 始终返回"最新的 40 轮"，此时正好是：

```
AI 当前能看到的内容：[批次 A（第1-20轮）] + [批次 B（第21-40轮）]
```

**如果把全部 40 轮都发给 PolarDB 总结会发生什么？**

```
发给 PolarDB：[批次 A] + [批次 B]（全部40轮）
总结完成后，这 40 轮被标记 memory_summarized=true，AI 不再能看到它们

AI 下一条消息能看到的内容：【空】← 什么都看不到了！
```

用户刚说完"我今天加班到九点"，AI 下一句就完全遗忘了这件事，体验直接崩塌。

**正确做法：只发最老的 20 轮（批次 A）**

```
发给 PolarDB：[批次 A（第1-20轮）]   ← 快要"滑出"窗口的旧内容
保留在短期记忆：[批次 B（第21-40轮）] ← AI 还在活跃使用的新内容
```

总结完成后：

```
AI 当前能看到的内容：[批次 B（第21-40轮）]  ← 还在，用户无感知
批次 A 变成了 PolarDB 里的事实             ← 以精炼形式继续存在
```

**接下来又发生什么？（第二轮触发）**

```
第21 轮 ─ 第 40 轮：[  批次 B（第21-40轮）  ]
第41 轮 ─ 第 60 轮：[  批次 C（第41-60轮）  ]
                                              ↑
                          又积累了 20 轮，再次触发总结

发给 PolarDB：[批次 B（第21-40轮）]   ← 现在它变成最旧的了
保留在短期记忆：[批次 C（第41-60轮）] ← AI 继续看最新内容
```

**整体规律：**

```
首次触发：在第 40 轮（积累满40轮）
后续触发：每新增 20 轮触发一次（不是再等40轮）
每次总结：始终只发"最老的那20轮"
AI看到的：始终是"最新的20轮"（上一批总结完前保留的那批）
```

总结一句话：**40 轮是触发门槛（够老才触发），20 轮是每次总结的批次大小（只处理已经不在"活跃区"的旧内容）。两个数字配合，保证 AI 的短期记忆永远有内容可看，同时旧内容被及时异步转化为长期记忆。**

### Q15 ⭐⭐⭐ 你们的记忆系统有哪些明确的缺陷？如果让你优化，你会从哪里入手？

**考点**：能否客观评价自己设计的系统，并给出有深度的改进思路。

**参考答案**

**已知缺陷：**

**① 记忆没有遗忘机制（最严重）**

用户三年前说"我在北京上大学"，这条事实永久保留在向量库，不会因为用户毕业、换城市而失效。AI 可能持续用过期信息影响回复。

优化方向：引入**置信度衰减**——每条事实携带写入时间戳，检索时按时间加权（近期事实权重高，旧事实降权）；或者引入 TTL，超过 N 个月的事实自动降级为"历史信息"标签。

**② 用户画像跨角色共享**

当前 `getUserProfile` 查全局画像，不区分角色。用户对角色 A 讲的私密经历，会通过全局画像"泄露"给角色 B 知道。

优化方向：画像分两层——**全局属性**（职业、城市等客观属性，对所有角色可见）+ **角色特有认知**（只有该角色"听到过"的信息），按 `userId + characterId` 双维度存储。

**③ 记忆检索透明度低**

现在注入 Prompt 的 `long_term_memory` 是拼接成的字符串，LLM 不知道这些记忆的来源、时间、和当前问题的相关度。高度相关的记忆和边缘相关的记忆权重相同。

优化方向：注入时携带结构化元信息：`{"memory": "...", "score": 0.87, "created_at": "...", "scene": "星梦"}` ，让 LLM 能感知相关性，自主降权旧/低分记忆。

**④ miniMerge 阈值一刀切**

`miniMergeThreshold=5` 对高频用户（每天聊天）和低频用户（一周一次）用同一个触发条件——高频用户合并过于频繁造成计算浪费，低频用户可能跑了几个月才触发一次合并。

优化方向：按**用户活跃度动态调整阈值**，活跃用户适当提高阈值（减少触发频次），沉睡用户在重新激活时立即触发一次合并（清理历史积累）。

**优先级建议：**  
缺陷①（遗忘机制）优先级最高，因为记忆污染是随时间恶化的系统性问题，且对用户体验的影响最直接；缺陷②（画像隔离）优先级次之，因为有潜在的隐私合规风险。
