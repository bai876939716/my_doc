# 核心数据库表数据字典

> 数据来源：直接读取 `xinyu-world-simulator-core` 仓库里各服务 `sql/`、`doc/sql/` 目录下的建表 DDL（`CREATE TABLE` + `COMMENT ON COLUMN`），不是从代码反推猜测的，字段名、类型、默认值、约束均与建表脚本一致。
>
> 与 [03-数据模型说明.md](03-数据模型说明.md) 的关系：那份文档里星梦相关几张表的字段是按代码调用方式推测重建的（比如把 `dream_id` 猜成 `VARCHAR(128) UNIQUE`、给 `daily_plan` 加了并不存在的 `plan_date` 列），与实际建表 SQL 有出入；本文档以实际 DDL 为准，字段对不上时以本文档为准。
>
> 表名前缀 `tb_soul_haven_` 是历史项目代号"soul haven"遗留的统一前缀，和当前"心屿"品牌名不一致，不影响功能，面试被问到可以如实说明是历史命名沿用。

## 一、记忆系统（soul-haven-memory-service）

记忆总结走"任务表 + 调用明细表 + 降级表"三张表的组合，对应面试材料里反复提到的"两级去重、失败降级补偿"设计（见 [06-记忆系统设计.md](06-记忆系统设计.md)），这里给出这几张表真实落地的字段结构。

### 1.1 tb_soul_haven_memory_summary_task（记忆总结任务主表）

编码约定（建表脚本头部注释）：
- `summary_type`：1=MINI（星梦小总结）/ 2=EVENT（事件总结）
- `scene_type`：1=short_chat / 2=group_chat / 3=star_dream / 4=group_chat_role_memory / 5=star_dream_role_memory / 6=multi_star_dream / 7=multi_star_dream_role_memory
- `status_code`：0=PENDING / 1=PROCESSING / 2=RETRYING / 3=COMPLETED / 4=FAILED_DEGRADED / 5=DATA_ABNORMAL
- `task_source`：1=APP（应用侧）/ 2=BACKEND（后台任务）
- MINI 类型总结只允许在星梦相关场景（3/5/6/7）下出现（`ck_memory_summary_task_mini_only_star_dream` 约束）

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| id | BIGINT (IDENTITY) | 否 | 自增 | 主键 |
| idempotency_key | VARCHAR(256) | 否 | - | 幂等键，唯一约束；防止同一条记忆总结任务被重复创建/消费 |
| message_id | VARCHAR(128) | 是 | - | 触发本次总结的消息/事件 ID |
| status_code | INTEGER | 否 | 0 | 任务状态码（见上方编码） |
| attempt | INTEGER | 否 | 0 | 已重试次数 |
| summary_type | INTEGER | 否 | - | 总结类型：1=MINI / 2=EVENT |
| task_source | INTEGER | 否 | 1 | 任务来源：1=APP / 2=BACKEND |
| scene_type | INTEGER | 否 | - | 场景编码（1-7，见上方） |
| scene_id | VARCHAR(128) | 否 | - | 场景内唯一标识（如会话ID/星梦存档ID） |
| start_cursor / end_cursor | BIGINT | 是 | - | 本批次总结覆盖的消息轮次区间；为空表示由业务方返回全量 |
| user_id / agent_id / run_id / app_id | VARCHAR(128) | 是 | - | 与 PolarDB Memory API 写入参数对齐的业务标识；三者至少一个非空（`ck_memory_summary_task_business_identifier`） |
| user_name | VARCHAR(128) | 是 | - | 用户昵称，供合并记忆 prompt 变量使用 |
| memory_summarized | BOOLEAN | 否 | TRUE | 是否已被下一级合并处理；MINI 合并后置 true，EVENT 默认 true |
| original_message_ids | TEXT | 是 | - | 星梦事件总结时，本次合并覆盖的小总结 message_id 列表（逗号分隔） |
| error_message | TEXT | 是 | - | 失败原因 |
| created_at / updated_at | TIMESTAMPTZ | 否 | NOW() | 创建/更新时间；`updated_at` 由触发器 `fn_memory_summary_set_updated_at` 自动维护 |

关键索引：`(scene_type, scene_id)`、`(status_code, updated_at DESC)`（补偿扫描用）、`(scene_id, summary_type, status_code, memory_summarized, created_at)`（miniMerge 滚动合并扫描用）。

### 1.2 tb_soul_haven_memory_summary_call_log（调用明细表）

每次对 PolarDB Memory API 的出站 HTTP 调用都落一条，用于排查和审计。

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| id | BIGINT (IDENTITY) | 否 | 自增 | 主键 |
| task_id | BIGINT | 是 | - | 外键关联 `tb_soul_haven_memory_summary_task.id`，级联删除 |
| attempt_no | INTEGER | 否 | - | 本任务的第几次调用尝试 |
| endpoint | VARCHAR(128) | 否 | '/v1/memories' | 调用的 Memory API 端点 |
| request_id | VARCHAR(128) | 是 | - | 远端请求 ID |
| request_payload / response_payload | TEXT | 否/是 | - | 原始请求/响应 JSON 文本（存 TEXT 非 JSONB，便于 JDBC 直接以字符串写入） |
| http_status | INTEGER | 是 | - | HTTP 状态码 |
| success | BOOLEAN | 否 | FALSE | 是否成功 |
| timeout_flag | BOOLEAN | 否 | FALSE | 是否超时 |
| error_message | TEXT | 是 | - | 失败信息 |
| cost_ms | INTEGER | 是 | - | 耗时（毫秒） |
| requested_at / responded_at | TIMESTAMPTZ | - | - | 请求/响应时间 |

唯一约束 `(task_id, attempt_no)`，天然防止同一次重试被记两条。

### 1.3 tb_soul_haven_memory_summary_degraded（L2 降级表）

重试耗尽后仅记录待修复任务，不落原始轮次内容（避免降级表本身膨胀）。

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| id | BIGINT (IDENTITY) | 否 | 自增 | 主键 |
| task_id | BIGINT | 否 | - | 外键，唯一，关联 `tb_soul_haven_memory_summary_task.id` |
| degraded_reason | TEXT | 是 | - | 降级原因 |
| repaired | BOOLEAN | 否 | FALSE | 是否已被 XXL-Job 补跑修复 |
| repaired_at | TIMESTAMPTZ | 是 | - | 修复时间 |
| repair_note | TEXT | 是 | - | 修复备注 |
| created_at / updated_at | TIMESTAMPTZ | 否 | NOW() | 创建/更新时间 |

对应面试话术里"LLM 失败自动降级存原文并打标，XXL-Job 定时补跑 retry 接口"——这张表就是"打标"的落地位置，`repaired` 字段就是补跑扫描的过滤条件。

### 1.4 tb_soul_haven_memory_add_success_record（记忆添加成功留痕表）

字段设计参考 1.1 的任务表，去掉了状态机/幂等/重试相关字段，纯粹是成功后的审计记录。

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| id | BIGINT (IDENTITY) | 否 | 自增 | 主键 |
| message_id | VARCHAR(128) | 是 | - | 关联消息 ID |
| summary_type / task_source / scene_type / scene_id | 同 1.1 | - | - | 语义与任务表一致 |
| start_cursor / end_cursor | BIGINT | 否 | - | 本次覆盖的轮次区间（此表要求非空，任务表允许为空） |
| user_id / user_name / agent_id / run_id / app_id | VARCHAR(128) | 是 | - | 同 1.1 |
| original_message_ids | TEXT | 是 | - | 同 1.1 |
| request_payload / response_payload | TEXT | 是 | - | 成功调用的请求/响应快照 |
| created_at / updated_at | TIMESTAMPTZ | 否 | NOW() | - |

### 1.5 tb_soul_haven_profile_schema（用户画像模板本地镜像表）

与 Java DTO `ProfileSchemaResponse` 对齐，缓存 PolarDB 记忆服务返回的用户画像 Schema 定义。

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| schema_id | VARCHAR(256) | 否 | - | 主键，对应 PolarDB 记忆接口返回的 schema id |
| name | VARCHAR(256) | 否 | - | Schema 名称，与配置 `soul-haven.user-profile.schema-name` 一致 |
| description | TEXT | 是 | - | 描述 |
| attributes_json | TEXT | 否 | '[]' | 画像属性数组序列化后的 JSON 文本（元素含 name/type/description/required/default） |
| created_at_source | TIMESTAMPTZ | 是 | - | 远端返回的创建时间（字符串解析后写入） |
| synced_at / created_at / updated_at | TIMESTAMPTZ | 否 | NOW() | 同步/创建/更新时间 |

## 二、星梦系统（soul-haven-star-dream-service）

对应面试材料里"五阶段星梦日内容批处理流水线"，落库主要是这三张表：库存表（生产出来的内容池）、日计划表（分配给具体用户具体时间窗的展示计划）、星事表（星梦的附属动态）。

### 2.1 tb_soul_haven_generation_dream_inventory（星梦库存表）

存储所有预生成和新生产的星梦内容，是"库存优先、LLM 兜底"策略里"库存"的物理载体。

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| dream_id | BIGINT (IDENTITY) | 否 | 自增 | 主键 |
| user_id | BIGINT | 否 | - | 所属用户 |
| save_id | VARCHAR(64) | 否 | - | 存档 ID（世界线） |
| character_id | BIGINT | 否 | - | 关联角色 |
| title | VARCHAR(50) | 否 | - | 星梦卡片标题，≤8字 |
| scene_overview | TEXT | 否 | - | 现场概述正文，150-300字，角色第一人称视角 |
| context_summary | TEXT | 是 | - | 上下文摘要，供改写时了解原星梦背景 |
| opening_line | TEXT | 否 | - | 开场白文本，20-50字 |
| dream_type | VARCHAR(10) | 否 | - | 星梦类型：1=单人 / 2=多人 |
| main_character_id | BIGINT | 是 | - | 多人星梦的主视角角色 |
| supporting_character_ids | BIGINT[] | 是 | - | 多人星梦的配角 ID 数组 |
| relationship_level | INT | 是 | - | 预生成时对应的关系等级（0-5） |
| location_base / location_detail | VARCHAR | 是 | - | 大地点 / 具体子空间 |
| universe | VARCHAR(100) | 是 | - | 所属宇宙/世界观标识 |
| star_event_id | BIGINT | 是 | - | 关联星事 ID，一个星梦至多一条星事 |
| status | VARCHAR(20) | 否 | '待分配' | 库存状态：待分配 / 已曝光 / 已游玩 |
| source_type | VARCHAR(20) | 是 | - | 来源：预制 / 改写 / 新生产 / 兜底新生产 |
| time_slot | VARCHAR(5) | 是 | - | 所属时间窗口：W01(06-08)~W12(04-06) |
| language | VARCHAR(10) | 是 | 'zh-CN' | 语言：zh-CN / en-US / ja-JP |
| needs_supplement | BOOLEAN | 是 | FALSE | 是否缺少星事需要补充（阶段五扫描条件） |
| is_first_encounter | BOOLEAN | 否 | FALSE | 是否为初遇星梦（关系 Lv0 预制库存） |
| attached_content_id | BIGINT | 是 | - | 初遇星梦附带内容 ID |
| consumed | BOOLEAN | 是 | FALSE | 是否已被消费（曝光或游玩） |
| create_time / updated_at | TIMESTAMP | 是 | NOW() | 创建/更新时间 |

索引覆盖了库存查询的四条主要路径：按用户+角色取库存、按状态过滤、按是否缺星事扫描、按初遇标记扫描。

### 2.2 tb_soul_haven_generation_daily_plan（用户每日内容计划表）

"每窗口≥1个多人+≥8个总量"的落地表，是分配给具体用户在具体时间窗展示哪条星梦的计划表，和 2.1 库存表是多对一的引用关系（`dream_id` 指向库存表）。

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| plan_id | BIGINT (IDENTITY) | 否 | 自增 | 主键 |
| user_id | BIGINT | 否 | - | 用户 ID |
| save_id | VARCHAR(64) | 否 | - | 存档 ID |
| time_slot | VARCHAR(5) | 否 | - | 时间窗口：W01~W12 |
| dream_id | BIGINT | 否 | - | 展示的星梦 ID，关联 2.1 |
| character_id | BIGINT | 否 | - | 角色 ID |
| event_id | VARCHAR(64) | 否 | - | 外部事件源 ID（如推送事件） |
| dream_type | VARCHAR(10) | 是 | - | 1=单人 / 2=多人 |
| relationship_level | INT | 是 | - | 分配时的关系等级（0-5） |
| source_type | VARCHAR(20) | 是 | - | 预制 / 改写 / 新生产 / 兜底新生产 |
| status | VARCHAR(20) | 是 | '已分配' | 已分配 / 已曝光 / 已游玩 / 已过期 |
| consumed | BOOLEAN | 是 | FALSE | 是否已消费 |
| deleted | BOOLEAN | 否 | FALSE | 软删标记；Agent 批处理成功后归档已消费条目 |
| created_at / updated_at | TIMESTAMP | 是 | NOW() | - |

`idx_daily_plan_unconsumed`（部分索引，`WHERE consumed = FALSE`）和 `idx_daily_plan_active`（`WHERE deleted = FALSE`）是两条典型的"只索引有效行"设计，减少索引体积、加速批处理阶段三/四的缺口扫描。

### 2.3 tb_soul_haven_generation_star_event（星事表）

星梦的附属动态内容，一个星梦至多绑定一条星事。

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| star_event_id | BIGINT (IDENTITY) | 否 | 自增 | 主键 |
| bound_dream_id | BIGINT | 否 | - | 绑定的星梦 ID |
| publisher_id | BIGINT | 否 | - | 发布该星事的角色 ID |
| content | TEXT | 否 | - | 星事正文，50-150字，角色第一人称 |
| image_description | TEXT | 是 | - | 配图描述，≤50字 |
| relationship_level | INT | 是 | - | 关联的关系等级（0-5） |
| trigger_type | VARCHAR(5) | 否 | - | 触发类型：A=曝光触发 / B=定时同步 / C=登录触发 |
| trigger_delay_minutes | INT | 是 | 0 | 触发延迟分钟数，B类为0 |
| publish_time | TIME | 是 | - | 预定发布时刻（仅时分秒）；B类填窗口开始时刻 |
| location_base / location_detail | VARCHAR | 是 | - | 发生地点 |
| reason | TEXT | 是 | - | 触发类型选择理由，工程日志用 |
| source_type | VARCHAR(20) | 是 | '星梦附属' | 来源类型 |
| publish_status | VARCHAR(20) | 否 | 'pending' | pending / published / abandoned |
| actual_publish_time | TIMESTAMP | 是 | - | 实际发布时间 |

`idx_star_event_publish_status_pending`（部分索引，`WHERE publish_status = 'pending'`）专门服务定时扫描待发布星事的查询，不用扫已发布/已放弃的历史行。

## 三、角色与关系（soul-haven-character-service）

对应面试材料里"关系等级驱动内容生产策略"（Lv0~Lv5），核心是角色卡表 + 两套关系维度：一套是"角色之间"的关系（用户视角下 A 角色和 B 角色是朋友/羁绊关系），一套是"用户和角色之间"的羁绊值/等级。这是容易讲混的两张表，面试时要分清楚。

### 3.1 tb_soul_haven_character_card（角色卡主表）

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| id | BIGSERIAL | 否 | 自增 | 主键 |
| language | VARCHAR(16) | 否 | 'zh-CN' | 默认语言（首次创建时由大模型判断），创建后可翻译写入 i18n 副表 |
| planet_id / region_id / location_id | BIGINT | 是 | NULL | 所属星球/区域/地点 |
| gender | SMALLINT | 否 | - | 0-无性别 1-男性 2-女性 |
| tags | VARCHAR(200) | 否 | NULL | 标签，逗号分隔，需翻译+文本审核 |
| avatar_url / background_image_url / short_chat_background_image_url / half_body_image_url | VARCHAR(512) | 是 | NULL | 各类展示图 URL，图片审核不翻译 |
| status | SMALLINT | 否 | 1 | 0-下架 1-上架 |
| translation_status | SMALLINT | 否 | 1 | 1-翻译中 2-翻译完成（仅初次创建时更新） |
| sort_order | INTEGER | 否 | 0 | 排序权重，越大越前 |
| created_at / updated_at | TIMESTAMP | 否 | CURRENT_TIMESTAMP | - |
| deleted | SMALLINT | 否 | 0 | 0-未删除 1-已删除 |

人设正文、对话样例等文本字段在 `tb_soul_haven_character_card_i18n` 多语言副表（未展开，逻辑与 3.5 系 Feed 的 i18n 副表一致：主表存语言无关元数据，正文按 language 分行存副表）。

### 3.2 tb_soul_haven_user_character_relation（角色关系表 / 羁绊图谱）

这是"角色 A 和角色 B"之间的关系表（比如"陆离的朋友是苏晚"），不是用户和角色的羁绊值——这张表决定了多人星梦选配角、Feed 里"提到了 TA 的朋友"这类逻辑。

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| id | BIGSERIAL | 否 | 自增 | 主键 |
| user_id | BIGINT | 否 | - | 用户 ID |
| character_id | BIGINT | 否 | - | 当前角色 ID |
| related_character_id | BIGINT | 否 | - | 关联角色 ID |
| is_original_bind | SMALLINT | 否 | 0 | 是否原卡绑定；详情页"TA的朋友"初始关联默认点亮 |
| relation_value | BIGINT | 否 | 0 | 关系数值 |
| is_light | SMALLINT | 否 | 0 | 羁绊是否点亮：0-未点亮 1-已点亮 |
| save_id | BIGINT | 否 | - | 存档 ID |
| created_at / updated_at | TIMESTAMP | 否 | CURRENT_TIMESTAMP | - |

唯一约束 `(user_id, character_id, related_character_id, save_id)`——同一用户同一存档下，同一对角色关系只有一行。

### 3.3 tb_soul_haven_user_character_bond（用户-角色羁绊主表）

这才是"用户和某个角色"之间的羁绊值/等级，驱动内容生产策略的关系等级机制来源于这张表。

| 字段 | 类型 | 可空 | 默认值 | 说明 |
|------|------|------|--------|------|
| id | BIGSERIAL | 否 | 自增 | 主键 |
| save_id / user_id / character_id | BIGINT | 否 | - | 存档 + 用户 + 角色三元组，唯一约束 |
| bond_value | INT | 否 | 0 | 羁绊分数（连续值，驱动下方等级配置表分档） |
| digital_level | SMALLINT | 否 | 0 | 数字等级（1-15，见 3.4 配置表） |

## 面试要点速查

结合上面字段结构，容易被追问、也值得主动提的几个设计点：

1. **`save_id`（存档/世界线）几乎贯穿所有表**：短对话、星梦、Feed、羁绊全部以 `user_id + save_id` 作为业务隔离维度，而不是只用 `user_id`——说明这套系统在设计之初就考虑了"用户可以有多条平行故事线"这个需求，不是后补的。
2. **两张容易混淆的关系表**：`tb_soul_haven_user_character_relation`（角色和角色之间的关系图谱，驱动多人剧情选配角）与 `tb_soul_haven_user_character_bond`（用户和角色之间的羁绊值/等级，驱动内容生产策略）——面试被问"关系系统怎么设计的"时，先分清楚问的是哪一种关系，再回答。
3. **只有短对话消息/会话表做了物理分区**：64/32 两个不同的分区数是按预估数据量级差异定的（消息量远大于会话量），其余表都是普通单表，说明分区不是无脑全上，而是按增长曲线挑真正需要的表做。
4. **部分索引（Partial Index）在这套库里用得很密集**：`WHERE consumed = FALSE`、`WHERE deleted = FALSE`、`WHERE publish_status = 'pending'`、`WHERE phone_index IS NOT NULL` 等，核心思路都是"只索引会被频繁按该条件查询的那部分行"，减少索引体积、提升命中率，这是一个可以主动展示的 SQL 优化意识点。
5. **记忆总结的幂等键落在业务表而不是 Redis**：`tb_soul_haven_memory_summary_task.idempotency_key` 唯一约束是数据库层面的幂等兜底，和之前面试材料里提到的"Redis SETNX 做消费幂等"是两层不同的幂等设计——Redis 那层防的是 MQ 重复消费触发处理逻辑，这张表的唯一约束是任务持久化层面的最后一道防线，两者不冲突，是纵深防御的体现。
