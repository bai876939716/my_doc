# xinyu 技术栈选型深度解析

> 面向面试：不只是"我们用了什么"，而是"为什么用这个、当时权衡了什么、跟同类方案比优劣在哪"。本文按 Java 微服务层 / AI Agent 层 / 全局架构决策 三个维度展开，每一项选型都配"为什么这么选 + 需要考虑的问题 + 竞品对比"。

---

## 前言：技术选型的通用评估框架

面试官问"为什么选 X 不选 Y"时，最怕回答"因为 X 好"。更有说服力的回答是"在我们这个场景下，按下面几个维度权衡后选了 X"：

| 评估维度 | 关注点 |
|---------|--------|
| 团队技术栈匹配度 | 团队已有 Java 背景，还是要从零学习成本 |
| 生态成熟度 | 社区活跃度、文档完整度、踩坑案例是否好搜 |
| 性能与规模适配 | 当前量级是否真的需要这个方案的复杂度 |
| 运维成本 | 是否需要额外专职团队维护 |
| 供应商锁定风险 | 换厂商/换开源方案的迁移成本有多高 |
| 与现有基础设施的整合度 | 是否能复用已有的 Nacos/RocketMQ 等基础设施 |
| 成本 | License 费用、云厂商计费方式、LLM 调用成本 |

下面每一节选型都按这套框架去answer。

---

## 一、Java 微服务层选型

### 1.1 RPC 协议：Dubbo 3 Triple

**选了什么**：Dubbo 3 Triple 协议 + Protobuf 3.25.5 做服务间通信。

**为什么这么选**：
- Protobuf 强类型契约，比 JSON 序列化性能更高、体积更小，接口变更有版本控制
- Triple 协议兼容 gRPC，同时保留 Dubbo 生态的服务治理能力（负载均衡、服务降级、流量染色）
- 和 Nacos 服务发现原生整合，不需要额外接入层

**需要考虑的问题**：
- 团队 Java 背景下 Dubbo 学习成本低，如果团队更熟悉云原生生态，直接上 gRPC + Kubernetes Service 可能更轻量
- Triple 协议对非 Java 生态（比如要给 Python Agent 层直接暴露 RPC）支持没有 HTTP 友好，这也是后来选择用 **HTTP AgentRun API** 而不是 Dubbo 打通两层的原因之一

**竞品对比**：

| 方案 | 优势 | 劣势 | 适用场景 |
|------|------|------|----------|
| **Dubbo 3 Triple（选用）** | 服务治理能力完整，Nacos生态整合好，向下兼容Dubbo2 | 主要服务Java生态，跨语言支持弱于原生gRPC | Java为主、需要成熟服务治理能力的团队 |
| gRPC 原生 | 跨语言支持最好，云原生生态标准 | 服务治理（限流/熔断/灰度）需要额外接入Istio等 | 多语言微服务、已上K8s+Service Mesh的团队 |
| Spring Cloud OpenFeign(HTTP) | 简单直观，调试方便（可以直接curl） | JSON序列化性能低于Protobuf，缺少强类型契约 | 服务数量少、对性能要求不高的早期项目 |

---

### 1.2 服务发现与配置中心：Nacos

**为什么这么选**：Spring Cloud Alibaba 生态原生支持，服务发现和配置中心二合一，配置支持热更新（比如退货政策调整不需要重启服务）。

**需要考虑的问题**：Nacos 集群本身的高可用要单独运维；如果团队已经在用 Zookeeper 或 Consul 做其他系统的服务发现，多引入一套注册中心会增加运维复杂度。

**竞品对比**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **Nacos（选用）** | 服务发现+配置中心一体化，阿里生态整合好，控制台友好 | 集群运维复杂度高于纯配置中心方案 |
| Consul | 多数据中心支持更成熟，HashiCorp生态整合好 | 配置中心能力弱于Nacos，需要额外工具补齐 |
| Zookeeper + Apollo | 组件职责分离更清晰，各自都是成熟方案 | 需要维护两套系统，运维成本更高 |

---

### 1.3 数据库：PostgreSQL

**为什么这么选**：业务数据模型里有较多 JSON 字段（角色配置、多语言内容）和复杂查询场景，PostgreSQL 的 JSONB 类型和索引能力比 MySQL 更适合；后续记忆系统的向量检索也依赖阿里云 PolarDB（PostgreSQL 内核）生态。

**需要考虑的问题**：团队如果历史上主要用 MySQL，PostgreSQL 在运维工具链、DBA 经验上需要额外投入；分库分表生态成熟度上 MySQL 的开源方案（ShardingSphere等）更丰富。

**竞品对比**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **PostgreSQL（选用）** | JSONB原生支持好，扩展性强（PostGIS/pgvector等插件生态），和PolarDB向量能力无缝衔接 | 国内团队MySQL经验更普遍，分库分表工具链不如MySQL丰富 |
| MySQL | 国内生态最成熟，运维工具和DBA经验最多，分库分表方案多 | JSON类型支持和复杂查询能力弱于PostgreSQL |

---

### 1.4 消息队列：RocketMQ

**为什么这么选**（已在系统架构文档详细展开，这里做竞品补充）：星梦结束后需要并行执行多个下游任务（回忆卡、私信、记忆更新），需要可靠投递和延迟消息（24h过期计时）能力。

**需要考虑的问题**：消息积压时的降级策略、消费者幂等设计（防止重复消费导致重复退款/重复推送）。

**竞品对比**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **RocketMQ（选用）** | 延迟消息原生支持，事务消息成熟，阿里生态整合好，中文文档和社区活跃 | 国际化生态不如Kafka |
| Kafka | 吞吐量业界最强，生态最成熟，适合日志/流式场景 | 延迟消息需要额外实现，运维复杂度更高，为中等量级业务消息场景显得"杀鸡用牛刀" |
| RabbitMQ | 轻量、协议标准（AMQP）、延迟队列插件成熟 | 吞吐量和水平扩展能力弱于RocketMQ/Kafka，海量消息场景较吃力 |

---

### 1.5 实时长连接：Hermes（自研/内部长连接中间件）

**为什么这么选**：AI 生成文本需要流式推送打字机效果，星梦邀请卡需要实时到达；Topic 模型 `chat_session_{id}` 天然按会话隔离。

**需要考虑的问题**：自研/内部中间件意味着踩坑只能靠内部经验，社区资料少；如果没有现成的内部长连接中间件，从零建设的成本和选用成熟第三方方案的成本要仔细权衡。

**竞品对比**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **Hermes（内部长连接中间件，选用）** | 与现有业务系统深度整合，Topic隔离模型贴合业务场景 | 依赖内部维护，文档和踩坑经验局限于团队内部 |
| 原生 WebSocket 自建 | 完全自主可控，无额外依赖 | 需要自己解决断线重连、多端同步、水平扩展等一整套工程问题 |
| 第三方 IM SDK（融云/环信等） | 开箱即用，断线重连/多端同步等能力成熟 | 按用户量/消息量计费，成本随规模上升；深度定制（比如星梦特殊消息类型）灵活性不如自建 |

---

### 1.6 ORM 框架：MyBatis-Plus

**为什么这么选**：轻量、SQL 可控性强（复杂查询场景多，比如时间窗分配、关系等级计算），团队 Java 背景下学习成本低。

**竞品对比**：MyBatis-Plus（选用，SQL灵活可控） vs JPA/Hibernate（开发效率更高但复杂查询和性能调优的可控性较弱，ORM"黑盒"debug成本更高）。

## 二、AI Agent 层选型

### 2.1 编排框架：LangGraph

**为什么这么选**：复杂 AI 工作流（5 阶段批处理、多节点意图识别）需要清晰的状态管理和错误路由；相比链式调用，StateGraph 把每一步定义成节点，条件边处理分支和错误，更易调试和扩展。

**需要考虑的问题**：LangGraph 本身也在快速迭代，版本升级可能带来 API 变化；团队需要掌握"状态图思维"而不是简单的顺序脚本思维，学习曲线比直接写 if/else 脚本更陡。

**竞品对比**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **LangGraph（选用）** | 状态图可视化，条件边处理错误路由清晰，与LangChain生态无缝整合（可直接用现成的Tool/Agent组件） | 框架本身仍在快速演进，版本升级有breaking change风险 |
| 手写 Agent Loop（无框架） | 完全自主可控，没有框架依赖和黑盒逻辑 | 状态管理、错误处理、重试逻辑都要自己造轮子，维护成本随Agent数量增长而上升 |
| CrewAI / AutoGen | 面向"多Agent对话协作"场景设计，开箱即用的角色分工抽象 | 更适合Agent之间需要"互相对话"的场景；本项目每个Agent职责单一、独立部署，用不上这类框架的多Agent对话能力，引入反而增加不必要的复杂度 |

---

### 2.2 Agent 运行时：阿里云 AgentRun（Serverless）

**为什么这么选**：按调用量自动扩缩容，不需要预留常驻资源；提供 OpenAI 兼容的模型网关，统一接入 DeepSeek/Qwen 等多个模型来源，不需要自己维护模型调用的底层适配层。

**需要考虑的问题**：Serverless 冷启动延迟对实时场景（开场白改写 < 2 秒）是否有影响，需要针对性做预留实例或者预热策略；深度绑定阿里云生态，迁移到其他云厂商有一定成本。

**竞品对比**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **阿里云 AgentRun（选用）** | Serverless自动扩缩容，内置模型网关统一多模型接入，与阿里云其他基础设施（Nacos/RocketMQ同属阿里生态）整合成本低 | 供应商锁定，冷启动延迟需要额外优化，批处理重负载场景资源规格需要精细调优 |
| 自建 K8s + 常驻服务 | 完全自主可控，冷启动问题不存在，可以精细控制资源调度 | 需要自己搭建模型网关抽象层、自动扩缩容策略，运维团队投入更大 |
| AWS Lambda / Bedrock Agents | 海外生态成熟，Bedrock自带Agent编排能力 | 面向国内业务，网络延迟和合规成本更高，且需要额外对接国内模型（DeepSeek/Qwen）反而更麻烦 |

---

### 2.3 模型选型：DeepSeek-v4-flash + Qwen3-max 混用

**为什么这么选**：批处理场景（内容生产流水线）调用量大、对延迟不敏感，用便宜的 `deepseek-v4-flash` 控制成本；实时场景（开场白改写 < 2秒）用响应更快的 `qwen3-max`。这是"按场景选模型"而不是"一个模型打天下"的思路。

**需要考虑的问题**：
- 多模型混用意味着要处理不同模型的输出格式差异（比如 DeepSeek 推理链路的 `<think>` 块），Output Parser 层要做兼容
- 模型路由策略需要有明确的成本/延迟基准数据支撑，不能拍脑袋决定哪个场景用哪个模型
- 供应商价格和限流策略变化时（模型厂商经常调价/调整限流），路由策略要能灵活切换

**竞品对比**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **DeepSeek + Qwen 混用（选用）** | 按场景成本/延迟最优，双供应商降低单点依赖风险 | 需要维护Model Gateway抽象层和输出兼容层，工程复杂度更高 |
| 全部用单一闭源模型（如GPT-4/Claude） | 输出格式统一稳定，工具调用能力成熟，工程简单 | 按量付费成本高，批处理这种大调用量场景成本压力大，且强依赖单一供应商 |
| 全部自部署开源模型（vLLM本地推理） | 边际成本最低，数据完全自主可控 | 需要自建GPU集群和推理运维团队，可用性SLA需要自己保证，前期投入大 |

---

### 2.4 工具调用协议：MCP（Model Context Protocol）

**为什么这么选**：让 Agent 不直接连数据库，通过标准化协议调用 Java Core 的业务能力，AI 层和业务层可以独立部署、独立演进；业务规则变更只需改 MCP 服务实现，不需要动 Agent 核心逻辑。

**需要考虑的问题**：MCP 是相对新的协议，生态工具链（调试、监控）还在完善中；多个 MCP 服务的连接管理（`MultiServerMCPClient`）需要做好单例复用，避免每次请求重建连接。

**竞品对比**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **MCP（选用）** | 标准化协议，模型和工具解耦，Agent层可以独立换模型不影响工具集成 | 协议较新，生态成熟度不如传统RPC，调试工具链还在完善 |
| 直接 RPC/HTTP SDK 调用 | 技术成熟，调试和监控工具链完善 | 每接入一个新Agent框架都要重新写一套调用适配代码，工具与AI框架强耦合 |
| LangChain 原生 Tool（无独立协议） | 开发最简单，和LangGraph无缝整合 | 工具定义和调用方式绑定在LangChain框架内，换成其他Agent框架（比如后续想用其他编排引擎）需要重写 |

---

### 2.5 记忆与向量存储：阿里云 PolarDB 记忆管理能力

**为什么这么选**：依托 PolarDB 内置的记忆管理和向量检索能力，不需要自己维护独立的向量数据库集群，事实提取、去重、合并这些逻辑由 PolarDB 侧的 LLM 能力承担一部分。

**需要考虑的问题**：深度依赖 PolarDB 的记忆管理 API，如果未来要切换到其他向量数据库，事实提取和去重的逻辑需要重新实现；向量检索的召回质量依赖 PolarDB 侧的模型能力，自主调优空间相对有限。

**竞品对比**：

| 方案 | 优势 | 劣势 |
|------|------|------|
| **PolarDB 记忆管理（选用）** | 开箱即用，事实提取/去重/合并逻辑内置，运维成本低 | 深度绑定阿里云，自主调优和迁移空间有限 |
| 自建 Milvus/Qdrant + 自研提取逻辑 | 完全自主可控，可以精细调优召回策略和阈值 | 需要自己实现事实提取、去重、冲突消解的完整逻辑（工作量接近重新实现一遍Mem0），运维一套向量数据库集群 |
| 直接用 Mem0 等开源记忆框架 | 社区维护的成熟方案，事实提取/冲突消解逻辑现成 | 需要额外适配到现有Java+Python混合架构里，且深度定制业务特有的多人星梦记忆拆分逻辑时不如自研灵活 |

## 三、贯穿全局的架构决策

### 3.1 Java + Python 双语言架构，而不是统一技术栈

**为什么这么选**：Java 团队处理业务规则、状态机、数据一致性有成熟经验；Python 生态在 AI 框架（LangChain/LangGraph）上明显领先。

**需要考虑的问题**：两个语言栈的团队协作成本、联调成本；接口契约（AgentRun HTTP API）的版本管理需要格外严格，否则容易出现"Java侧改了字段，Python侧没同步"的联调事故。

**如果统一成单一技术栈**：
- 全 Java：AI 框架生态（LangChain类库）远不如 Python 成熟，很多能力要自己造轮子
- 全 Python：业务规则强、高并发事务场景下，Python 的性能和类型安全不如 Java，微服务治理生态（Dubbo等）也不如 Java 成熟

### 3.2 同步与异步的边界划分

核心原则：**用户能感知延迟的环节走同步**（短对话LLM生成、开场白改写），**用户不能立刻感知、但需要保证最终执行的环节走异步**（记忆总结、多任务并行的星梦结算）。这个边界划分本身也是一种"选型"——每新增一个功能都要重新判断它该同步还是异步。

### 3.3 成本与 LLM 调用预算控制

模型调用是这套系统里持续增长的成本项，选型时始终要考虑：批处理场景"库存优先"（先查已有内容，不够才调 LLM）、模型路由按场景选择便宜/快速模型、翻译和生成拆分成不同模型调用（翻译用更便宜的模型）。这些不是单一技术选型，而是渗透在每个技术决策里的成本意识。

## 四、如果重新设计，会有哪些取舍空间（面试加分项）

面试官喜欢听到"我知道这个方案不是唯一解"，展示你对技术选型的思考深度而不是"别人怎么用我就怎么用"：

- 如果团队更年轻、更倾向云原生：Dubbo 可能会换成 gRPC + Service Mesh，服务治理能力交给基础设施而不是 RPC 框架本身
- 如果对 LLM 调用成本控制要求更极致：可以考虑更多自部署开源模型的比例，用自建 GPU 集群替代部分 Serverless 网关调用，但要接受更高的运维投入
- 如果 MCP 生态进一步成熟：可以把更多内部 RPC 调用逐步迁移到 MCP，让 AI 层的工具集成方式更统一
- 如果向量检索精度要求更高：可以考虑把 PolarDB 记忆管理换成自建向量库 + 自研提取逻辑，换取更大的调优自由度，代价是运维复杂度上升

## 五、面试话术总结（一句话开场）

> 我们的技术选型整体原则是"业务规则强的地方用成熟的 Java 生态保证稳定性和事务一致性，AI 推理和编排的地方用 Python 生态换取开发效率"，具体到每个组件的选择，都是在团队技术栈匹配度、生态成熟度、运维成本、供应商锁定风险这几个维度上做权衡，而不是"因为流行所以用"。比如 RocketMQ 而不是 Kafka，是因为我们的消息量级不需要 Kafka 的吞吐量优势，但需要它没有的延迟消息能力；比如 DeepSeek + Qwen 混用而不是单一模型，是因为批处理和实时场景对成本、延迟的要求完全不同。
