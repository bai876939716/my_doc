# 心屿 AI 系统 — 技术选型深度分析

> 面试用参考文档：每个选型背后的"为什么"，配候选方案对比与真实代码印证

## 一、整体架构：Java 微服务 + Python AI Agent 双层分工

### 选择

不是单体 Java / 不是纯 Python，而是**两层独立部署**：
- `xinyu-world-simulator-core`（Java）：13 个微服务，处理业务逻辑、状态机、数据持久化
- `xinyu-agents`（Python）：4 个 Agent，处理 LLM 推理与内容生成

### 核心依据

| 维度 | Java 层 | Python 层 |
|------|---------|-----------|
| 擅长 | 强类型事务、并发、状态机 | AI 框架生态（LangChain/LangGraph）|
| 不擅长 | LLM 工作流编排、prompt 动态拼接 | 重型 OLTP 业务规则 |
| 扩容粒度 | 按业务域独立扩（memory-service、star-dream-service） | 按 Agent 独立扩（批处理重 Agent 给更多 CPU/内存）|

### 解耦方式

两层通过 **OpenAI 兼容 HTTP 协议**通信（AgentRun 暴露 `POST /openai/v1/chat/completions`），Java 调用 Agent 不感知内部 LangGraph 实现细节。这使得：
1. Python 端可以随时重写 workflow 而不影响 Java 调用方
2. 同一 Java 接口将来可以换成不同的 Agent 实现（A/B test）

### 候选方案为何被排除

| 候选 | 问题 |
|------|------|
| 全 Java（Spring AI） | Spring AI 的 Agent 编排能力远弱于 LangGraph，条件边、状态图可视化调试都不支持 |
| 全 Python（FastAPI + SQLAlchemy） | 缺乏成熟的分布式锁、MQ 生态；事务型业务代码不如 Java 生态稳健 |
| gRPC 直连 | 双向依赖耦合，AI 层必须了解 Java 服务的 Protobuf 定义 |

## 二、LangGraph — AI 工作流编排

### 选择

用 `StateGraph + add_conditional_edges` 编排 5+ 步骤的 AI 工作流，而非链式调用。

### 核心依据

**状态图 vs 链式调用** 本质区别在于「错误路由」：

```python
# 链式调用：某步出错则全部崩掉
validate() → generate() → translate() → persist()

# LangGraph：节点出错 → 条件边 → 直接 END，不继续执行
g.add_conditional_edges(
    "phase1_scan", _route_on_error,
    {"end": "assemble_result", "continue": "phase2_rewrite"},
)
```

xingmeng 批处理工作流有 9 个节点（validate_params → load_daily_plan → phase1_scan → phase2_rewrite → phase3_allocate → phase3_produce → phase4_full_coverage → star_event_supplement → assemble_result），每个节点都有独立的错误码（`PHASE1_FAILED`、`PHASE3_ALLOC_FAILED` 等）。这种设计的好处：

1. **定位精确**：某次失败能直接从 `error_code` 定位到哪个阶段出了问题
2. **局部可测**：每个节点函数可以单独 mock 上下文做单元测试
3. **异步并行内置**：Stranger Feed 翻译节点用 `asyncio.gather` 并行跑 zh-TW + en-US，LangGraph 原生支持
4. **TypedDict 状态传递**：`XingmengBatchGraphState` 在节点间流动，类型安全，避免 dict key 拼写错误

### 候选方案为何被排除

| 候选 | 问题 |
|------|------|
| LangChain LCEL Chain | 没有分支路由，错误处理只能全局 try/catch；流程图不可视化 |
| Celery Task Graph | 适合后台任务队列，不适合 LLM 推理型工作流；缺乏状态传递 |
| 手写 Python 函数调用链 | 可以，但每次新增步骤都要手写错误分支，随时间腐烂 |
| LangGraph Cloud（托管） | 国内网络、合规问题；阿里云 AgentRun 已提供类似价值 |

## 三、MCP — AI 层与数据层解耦

### 选择

Agent 不直接操作 PostgreSQL，所有数据读写通过 **MCP（Model Context Protocol）工具**调用，MCP 服务再对接 Java Core。

```python
# mcp_client.py — 6 个 MCP 服务挂载
client = MultiServerMCPClient({
    "user-service":    {"transport": "streamable_http", "url": "http://..."},
    "dream-service":   {"transport": "streamable_http", "url": "http://..."},
    "profile-service": {"transport": "streamable_http", "url": "http://..."},
    ...
})
tools = await client.get_tools()
agent = create_react_agent(llm, tools)
```

### 核心依据

**若 Agent 直连数据库会发生什么**：
- Python 需要维护 JDBC 连接池或 SQLAlchemy session，与 Java 服务共享同一个 DB，造成连接资源竞争
- AI 层做了 schema 变更（加字段）会影响 Java 业务逻辑，耦合极深
- Agent 的 SQL 拼接无法利用 Java 层的业务规则（如时区转换、权限校验）

**MCP 的真实价值**：
1. Java Core 是「数据的唯一写入者」，保证业务规则（余额预扣、限流计数）不被绕过
2. AI 层 Serverless 部署（无状态），MCP 服务在 Java 侧统一维护连接池
3. 工具名路由自动分发：`MultiServerMCPClient` 按工具名找到对应 MCP 服务，Agent 端无感知

**信号量保护 MCP 并发**（防止 Serverless 实例 OOM）：

```python
_mcp_invoke_semaphore = asyncio.Semaphore(get_mcp_concurrency())  # 默认 8
```

批处理场景下多个 Phase 并发调 MCP，不加限制会导致 Serverless 实例建立过多 HTTP 连接而 OOM。

### 候选方案为何被排除

| 候选 | 问题 |
|------|------|
| Agent 直连 PostgreSQL | 耦合 DB schema，破坏业务规则封装 |
| gRPC Stub（Python 调 Java）| 需要 Python 维护 Protobuf IDL，跨语言 IDL 同步成本高 |
| REST API 直调 Java | 可行，MCP 本质就是 REST 的标准化封装；MCP 的额外价值是 LLM 可以自行决定调用哪个工具（ReAct） |

## 四、存储选型

### 4.1 PostgreSQL — 业务主库

**选择理由**：

标准关系型选择，没有特别激进的理由。重点是为什么**没有用 MySQL**：
- Dubbo Triple Protocol 配合 Protobuf，Java 侧强类型字段映射；PG 的 JSONB 类型让存半结构化数据（如 Agent 输出摘要）更灵活
- PolarDB 是阿里云 PG 兼容版，已有 PG 团队的基础，同一生态管理成本低
- `tb_memory_summary_task` 用了 `TIMESTAMPTZ`（时区感知时间类型），MySQL 的 DATETIME 不带时区，情感陪伴产品的多时区用户时间处理更容易出 bug

### 4.2 PolarDB 向量引擎 — 长期记忆

**选择理由对比**：

| 方案 | 优点 | 问题 |
|------|------|------|
| Pinecone | 专业向量数据库，性能好 | 需额外维护 embedding 模型、事实提取逻辑、去重合并 pipeline |
| Weaviate | 开源，功能全 | 自建运维成本；国内合规问题 |
| pgvector（自建） | 简单，与 PG 同机 | 需自己实现 ADD/UPDATE/NONE 决策逻辑 + mergeMemories |
| **PolarDB Memory API** | 内置「托管版 Mem0」：事实提取 + 向量存储 + 合并去重全 pipeline | 与 Mem0 的 `add()` 概念完全对应，阿里云托管合规 |

**PolarDB 的核心价值**是内置了 `infer=true` 的三步流程：
1. `FACT_RETRIEVAL_PROMPT` → LLM 提取事实列表
2. 向量化后在 `runId` 命名空间内检索相似度
3. `UPDATE_MEMORY_PROMPT` → ADD / UPDATE / NONE 三路决策

这相当于**开箱即用的 Mem0**，自建相同能力至少需要额外 2 周工程投入。

**runId 命名空间**是另一个关键设计，彻底隔离不同场景的记忆：

```java
// SummarySceneType 决定 runId 格式
SHORT_CHAT       → runId = "userId__characterId"
STAR_DREAM       → runId = "roleId__saveId"
GROUP_CHAT       → runId = "sessionId"
```

### 4.3 Redis — 幂等 + 分布式锁 + 限流

三类用途，各自选 Redis 的原因：

**幂等键**（`SET NX TTL 7天`）：MQ 在 Rebalance 窗口期、ACK 丢失、消费超时三类场景都会重投消息，数据库的唯一索引也可以做幂等但需要一次 INSERT 才能检测，Redis 的 NX 在内存层就拦住，性能更好。

**Redisson 分布式锁**（Watch Dog 自动续期）：星梦会话创建需要防并发重复，Watch Dog 解决了「业务执行时间 > 锁 TTL」的经典续期问题，避免锁提前失效导致并发穿透。

**三级限流计数器**：原子 INCR + EXPIRE，比数据库 UPDATE 更轻量，支持高并发；三个维度（10分钟冷却 / 每日8次 / 拒绝后5分钟冻结）分别覆盖三类滥用场景。

### 4.4 为什么没有用 MongoDB / Cassandra

- 项目的核心是关系型业务（用户-角色关系、等级计算、订单余额），关系型数据库更合适
- 记忆存储的非结构化部分交给了 PolarDB，无需再引入 MongoDB
- Cassandra 适合写多读少的时序数据，这里写入量不大，引入复杂度不必要

## 五、消息队列：RocketMQ

### 选择

星梦结束后 4 个后处理任务（回忆卡、后私信、记忆写入、消息 Tab 更新）通过 RocketMQ 异步并行剥离主链路，主流程响应控制在 **30ms** 内。

### 核心依据

**为什么 RocketMQ 而非 Kafka**：

| 维度 | RocketMQ | Kafka |
|------|----------|-------|
| 延迟消息 | 原生支持（24h 星梦过期计时） | 需要额外方案（如 Kafka Streams + 定时扫描） |
| 消息过滤 | Tag + SQL 过滤，消费端减少无用消息 | 只能 Consumer 端过滤 |
| 运维 | 阿里云 MQ 托管，符合项目云原生策略 | 自建复杂度高 |
| 顺序消息 | 队列级顺序 | Partition 级顺序，配置更复杂 |

**At-Least-Once 可靠投递 + Redis 幂等** 的组合是标准解法：

```
MQ 重投场景:
  1. Rebalance 窗口期：Consumer 实例重启，消息重新分配
  2. ACK 丢失：消费成功但 ACK 未到 Broker
  3. 消费超时：Business 处理太慢，Broker 认为失败重投

防御：
  idempotencyStore.tryAcquire(event.getIdempotencyKey())  // Redis SET NX
  → 已存在 → 直接 return false，跳过重复消费
```

### XXL-Job — 定时任务兜底

每日内容批处理（06:00 启动 5 阶段流水线）和记忆总结失败重试（`retry-failed-job cron: "0 */10 * * * ?"`）都用 XXL-Job：

- 相比 Spring @Scheduled：集群下只有一个节点执行（分布式），有任务执行日志、失败告警
- 相比 Quartz：阿里云生态，运维更简单；分片广播支持并行（parallelism: 8）

## 六、部署：阿里云 AgentRun（Serverless）

### 选择

Python AI Agent 层不部署在传统容器，而是用 AgentRun（基于 Function Computing 2.0 的 Agent 专用平台）。

### 核心依据

**Serverless vs 长驻容器**：

| 维度 | AgentRun Serverless | 长驻 Docker 容器 |
|------|---------------------|-----------------|
| 流量特征 | 批处理有明显峰值（06:00-09:00），平时低 | 需要按峰值预留资源，浪费 |
| 扩容 | 自动（并发实例扩缩容） | 手动 K8s HPA，需要配置 |
| 冷启动 | 存在（约 1-2s） | 无，但常驻有资源成本 |
| LLM 网关 | 内置（模型路由、限流配额） | 需自建 |
| 成本 | 按调用计费，适合低频高峰 | 按时计费，适合高频低峰 |

**批处理场景 Semaphore 的作用**：Serverless 实例内存固定（xingmeng-content: 4GB），并发 LLM 请求会占用大量内存（streaming buffer）。`asyncio.Semaphore` 统一限制并发数，防止单实例 OOM：

```python
# llm_parallel.py 推断：LLM 调用也有信号量保护
_llm_semaphore = asyncio.Semaphore(LLM_CONCURRENCY)  # 实例级并发上限
```

**不同 Agent 资源配置差异化**（体现在 s-prod.yaml 中）：
- stranger-feed: 1 vCPU / 2GB / 100 并发（轻量，高并发）
- xingmeng-content: 2 vCPU / 4GB / 10 并发（批处理重，低并发）
- xingmeng-opening: 1 vCPU / 2GB / 100 并发（低延迟，< 2s）

## 七、多模型选型策略

### 按场景选型，不绑定单一模型

| 场景 | 模型 | 选型理由 |
|------|------|---------|
| 实时开场白改写（< 2s） | Qwen3-Max | 阿里云生态延迟低，快速生成 |
| 批处理内容生产 | DeepSeek-V4-Flash | 成本低，速度快，质量够用 |
| 多语言翻译 | 独立翻译模型 | 翻译任务与生成任务解耦，节省高端模型 Token |
| 记忆事实提取 | PolarDB 内置 LLM | 与存储绑定，不另外消耗 Token |

**MiniMax-M2.7** 在长文本叙事（星梦沉浸式开场白 300-800 字）场景使用，其 M2 架构在长序列输出质量上有优势。

### 模型失败降级链路

记忆总结 LLM 失败时：
```java
// infer=false：不做事实提取，把原文直接存入向量库
AddMemoryRequest fallbackRequest = request.toBuilder()
    .infer(Boolean.FALSE)
    .build();
memoryManagementHttpClient.addMemory(fallbackRequest);
// status = FAILED_DEGRADED，等待 XXL-Job 扫描后补跑 /v1/memories/retry
```

降级后数据不丢失，只是质量稍差（原文 vs 提炼事实），最终一致性由 XXL-Job 保障。

## 八、提示词工程：XML 结构化 + 多版本管理

### 选择

12 节 XML 语义标签统一所有 Agent 的提示词格式，多版本并存，支持灰度切换。

### 核心依据

**为什么用 XML 而非 Markdown / 纯文本**：

| 格式 | LLM 理解准确率 | 程序化替换 | 版本化管理 |
|------|--------------|-----------|-----------|
| 纯文本 | 低（无结构边界） | 难（正则脆弱） | 难 |
| Markdown 标题 | 中 | 中 | 中 |
| **XML 标签** | **高（语义清晰的闭合边界）** | **易（模板变量替换）** | **易（标签不变，内容迭代）** |

Claude、Qwen 等主流模型都在 XML 格式化数据上表现更稳定，这是选 XML 的核心依据。

**版本化管理的实际意义**：

```python
DEFAULT_PROMPT_VERSION = "v4.0-stranger-lv0"
# 新版本：新增函数 get_prompt_v5()，不覆盖 get_prompt_v4()
# 灰度：10% 用户用 v5，其余用 v4，出问题立刻回滚
```

对情感陪伴产品来说，提示词变更直接影响内容质量和用户体验，灰度回滚能力是生产必需。

## 九、JSON 解析：六层递进容错

### 核心依据

LLM 输出格式不稳定是工程事实，初始失败率约 **8%**，六层容错将其降至 **< 0.5%**：

```python
# 层 1：剥离 DeepSeek 思维链 <think>...</think>
raw = strip_think_blocks(raw)

# 层 2：提取 ```json ... ``` Markdown 围栏
content = extract_json_fence(raw)

# 层 3：定位 [ ] 边界（模型可能在 JSON 前后输出额外文本）
content = locate_json_boundaries(content)

# 层 4：标准解析
try:
    return json.loads(content)
except json.JSONDecodeError:
    pass

# 层 5：尾逗号修复（LLM 偶发输出 {"a":1,} 这种非法 JSON）
content = fix_trailing_comma(content)
try:
    return json.loads(content)
except:
    pass

# 层 6：json-repair 终极兜底
return json_repair.loads(content)
```

**为什么不只用 json_repair**：`json_repair` 会做激进的猜测修复，可能把格式错误的字段"猜成"错误值。前五层是无损的（只做剥离 / 提取 / 小修正），保证数据准确性；`json_repair` 是最后兜底，宁可修复率高也要先保前几层的准确性。

## 十、记忆系统：三层分级 + runId 隔离

### 整体方案

```
短期记忆（热）: PostgreSQL — 最近 40 轮原文，无 LLM 处理，实时写入
长期记忆（冷）: PolarDB 向量 — LLM 提炼事实，按 runId 隔离
用户画像（结构化）: PolarDB Profile — 稳定属性，全量注入
```

### 三层分级的依据

**类 MemoryOS 分层**：

| 层 | 类比 | 特点 | 心屿实现 |
|----|------|------|---------|
| Working Memory | RAM | 快、全量、临时 | 40 轮原文直接注入 |
| Episodic Memory | SSD | 中速、按需检索 | 星梦 mini summary（场内提炼） |
| Semantic Memory | 磁盘归档 | 慢、压缩存、永久 | PolarDB 长期事实 + 画像 |

**40 轮的 token 预算计算**：
- 平均每条 50 字 × 40 轮 × 2（user+AI）≈ 4000 字 ≈ 5500 token
- 模型 context 128K token，留给角色设定 ~3000 token，留给输出 ~2000 token
- 5500 token 是经过测试的折衷点，可通过 Nacos 热更新调整

**miniMerge 滚动收敛**解决跨批次语义重叠问题：

```
[A,B,C,D,E] → mergeMemories → M1
[M1,F,G,H,I] → mergeMemories → M2
...
```

第一层（PolarDB NONE 事件）解决单次写入内重复；第二层（miniMerge）解决跨批次语义级重叠。两者互补，不能只用一层。

**积累计数的实现：查数据库而非内存计数器**：

```sql
SELECT COUNT(*) FROM tb_memory_summary_task
WHERE scene_id = ? AND summary_type = 'mini'
  AND memory_summarized = false
  AND status IN ('COMPLETED', 'FAILED_DEGRADED')
```

用数据库行数计数而非 Redis 计数器，原因是记忆总结是异步 MQ 消费，进程重启后内存计数器归零，数据库持久化保证了状态不丢。

## 十一、服务间通信：Dubbo 3 Triple + Protobuf

### 选择

Java 微服务之间用 Dubbo 3 Triple Protocol（HTTP/2 + Protobuf），而非 REST + JSON。

### 核心依据

| 维度 | Dubbo Triple + Protobuf | REST + JSON |
|------|------------------------|-------------|
| 序列化 | Protobuf 二进制，性能高，体积小 | JSON 文本，性能略低 |
| 契约 | Protobuf IDL 强类型，编译期检查 | 无强制约束，字段可能漂移 |
| 服务发现 | Nacos 自动注册 + 负载均衡 | 需要手写 URL 或维护注册表 |
| 版本管理 | IDL 版本字段内置 | 需要 URL 版本（/v1, /v2）|
| 流式支持 | Triple 原生支持 Server Streaming（AI 流式推送） | 需要额外 SSE 方案 |

**API + Impl 分离模式**：
```
soul-haven-memory-service-api   → 定义接口（Maven 依赖）
soul-haven-memory-service        → 实现逻辑（运行时）
```

调用方只依赖 API jar，不接触实现，接口变更有 IDL 版本控制，避免版本漂移。

## 十二、可观测性设计

### 三维度追踪

**结构化日志**（每个节点统一格式）：
```
[workflow] execution step=PHASE1_SCAN detail={user_id:10001, save_id:"abc", upgrade_roles_count:2}
[workflow] execution step=PHASE3_PRODUCE detail={produced:5, inventory:3, fallback:0}
[workflow] execution step=WORKFLOW_END detail={success:true, total_produced:17}
```

**request_id 贯穿全链路**：每个请求生成 UUID，在 LangGraph 状态图所有节点间传递，日志可按 request_id 串联完整执行轨迹。

**环境变量调试开关**（不需要改代码）：

## 附：面试高频追问速答

**Q：为什么用 LangGraph 不用直接写 Python 函数？**
> LangGraph 的 StateGraph 让工作流「图化」：节点职责单一可独立测试，条件边让错误路由显式化，状态在节点间强类型传递。五阶段批处理工作流 9 个节点，没有 LangGraph 的错误路由，任何一个阶段失败都会让后续全部崩掉且无法定位到具体阶段。

**Q：MCP 和直接 REST 调用 Java 有什么区别？**
> 本质上 MCP 就是标准化的 REST，区别在于：MCP 协议让 LLM 可以自主决定调用哪个工具（ReAct 框架），而直接 REST 是代码写死的调用序列。我们用 ReAct Agent + MCP，意味着 Agent 可以根据任务动态决定先查角色信息还是先查库存，无需提前写死调用顺序。

**Q：PolarDB 记忆 API 和 Mem0 有什么关系？**
> PolarDB Memory API 是阿里云托管的 Mem0 等价实现：`POST /v1/memories`（addMemory） = Mem0 `add()`，`runId` = Mem0 `run_id`，`infer=true` 触发同样的 FACT_RETRIEVAL + UPDATE_MEMORY 双 Prompt 流程。选择 PolarDB 而非开源 Mem0 自建的原因：无需维护 embedding 模型，合并去重 pipeline 开箱即用，阿里云托管符合国内合规要求。

**Q：星梦批处理为什么要分 5 个 Phase 而不是一次性生成？**
> 五个 Phase 解决了五个独立问题：Phase1 标记升级角色（无 LLM，纯数据扫描）；Phase2 改写已有内容（不重新生产，节省 Token）；Phase3 按时间窗分配内容（库存优先，LLM 兜底）；Phase4 强制覆盖 Lv3+ 用户的全天时间窗（VIP 体验保障）；Phase5 补星事（增强体验的收尾）。如果一次性执行，某个步骤失败就无法知道是哪个环节出问题，且无法实现「库存优先」这类横向优化。

**Q：asyncio.Semaphore 和 Redis 分布式锁有什么区别，分别用在哪？**
> Semaphore 是**进程内**并发限制，控制单个 Serverless 实例内同时进行的 LLM/MCP 调用数量，防止 OOM；Redis 分布式锁是**跨进程**互斥，控制同一个业务对象（如同一个星梦会话）在多个服务实例间只有一个在处理，防止并发创建重复数据。两者层次不同，不能互相替代。

**Q：JSON 解析失败率从 8% 降到 0.5% 的关键是哪层？**
> 最主要的两层是「剥离 `<think>` 块」和「提取 Markdown 围栏」。DeepSeek 思维链模型会在 JSON 前输出大量 `<think>...</think>` 内容，直接 `json.loads` 当然失败；Qwen 系列模型在 system prompt 要求输出 JSON 时仍有概率加 ` ```json ``` ` 围栏。这两层处理掉了绝大多数失败，后续尾逗号修复和 json_repair 只是保险层。
