## DS-2 ShortChatMessage（用户消息 / AI 分片消息）
**方向**：写入 DB，也从 DB 读出  
**文件**：`soul-haven-short-chat-service/.../entity/app/ShortChatMessage.java`  
**表**：`tb_soul_haven_short_chat_message`（PARTITION BY HASH(user_id)）  
**说明**：用户消息和 AI 回复消息共用同一张表，靠 `senderType` 和 `status` 区分

```java
Long    id              // 自增主键（含分区键 user_id）
Long    userId          // 用户 ID
Long    saveId          // 存档 ID（世界线，多租户隔离键）
Long    characterId     // 角色 ID
String  sessionId       // 会话 ID

Integer direct          // 消息方向：0=用户发送 1=角色发送
Integer senderType      // 发送类型：0=用户 1=角色 2=系统

String  localMsgId      // 客户端本地消息 ID（幂等去重，与 DS-1.localMsgId 对应）
String  dynamicId       // Feed 动态 ID（透传自 DS-1）
Long    msgId           // 服务端消息 ID（Snowflake，全局唯一）

Integer msgType         // 消息类型：1=纯文本 2=富文本 3=自定义
Integer msgSubtype      // 子消息类型（扩展用）
String  content         // 消息正文（用户消息 or AI 回复文本）
String  prompt          // LLM 输入 prompt 快照（仅 AI 消息有值）
String  llmResponse     // LLM 原始输出 JSON 快照（仅 AI 消息有值）
String  llmContext      // LLM 上下文快照（含 guardrail 结果）

Integer isRead          // 已读：0=未读 1=已读（AI 已读代表 AI 已处理）
Instant readAt          // 已读时间（timestamptz）

Integer status          // 消息状态（关键枚举，见下）
                        //   0 = NORMAL         正常，可展示
                        //   1 = GENERATING      AI 占位中（空 content）
                        //   2 = MACHINE_REJECT  机审不通过
                        //   3 = FAILED          生成失败（退款后展示错误文案）
                        //   4 = FIREWALL        防火墙待审核
                        //   5 = WAITING_PUSH    延时分片，待定时推送
                        //  10 = DELETED         已删除

Integer extraType       // 额外类型：1=首条消息 2=AI占位消息 3=召回消息 4=长记忆泛化消息
Integer sourceType      // 来源：0=APP 1=后台 2=创作者 3=agent
Integer respond         // 点踩：0=否 1=是
Integer upvote          // 点赞：0=否 1=是
Integer aiUpvoteScore   // AI 情感判分（80-100，异步更新）
Long    relationUserMsgId // AI 消息关联的用户消息 ID（形成消息对）

Integer clientType      // 客户端类型
String  deviceId        // 设备 ID
String  clientIp        // 客户端 IP

Instant createTime      // 创建时间
Instant updateTime      // 更新时间
Instant sendTime        // 预期展示时间（App 按此排序；延时分片的未来时间）
Instant pushTime        // 实际推送时间（status=5 时为 null）

Long    quoteMsgId      // 被引用消息 ID
String  quoteSnapshot   // 引用内容快照（防原消息删除）
Integer quoteSenderType // 被引用消息发送者：0=用户 1=AI

Long    aiBatchId       // AI 回复批次 ID（同一批 LLM 调用生成的消息共享）
Integer aiBatchIndex    // 当前分片在批次内的序号（从 0 开始）
Integer aiBatchTotal    // 批次总分片数
Long    rollingBatchId  // Rolling 聚合批次 ID（对应 DS-11 的 batchId）
Integer isSummarized    // 是否已被记忆系统总结：0=否 1=是 2=失败待重试
```

**同一张表里的三类记录：**

| 类型 | senderType | status | extraType | content |
|------|-----------|--------|-----------|---------|
| 用户消息 | 0 | 0 | null | 用户原文 |
| AI 占位消息 | 1 | 1 | 2 | `""` (空) |
| AI 分片消息 | 1 | 0 or 5 | null | AI 回复某段 |

**content 解析逻辑（normalizeLlmReplyPayload，Orchestrator L836）：**
```
LLM 可能输出三种格式：
① JSON 对象：{"messages": ["第一段", "第二段"]}  → 提取 messages 数组
② JSON 对象：{"message": "..."} or {"content": "..."}  → 取单字段
③ 纯文本："今天还好啦..."  → 按换行符切分
④ 以上都失败 → JsonRepair 修复后重试
```

## DS-7 ShortChatMessage（AI 占位消息）
**说明**：写 DB 的时机：LLM 调用前，用于在 App 显示"正在输入"气泡  
**结构**：同 DS-2，关键字段值如下

```java
senderType  = 1          // AI 发送
```

**生命周期：**
```
INSERT(status=1, content="")
  → pushChatMessageAsRsp → App 显示"●●●"
  → LLM 调用中 ...
  → LLM 完成后：UPDATE(content=aiContent, status=0, extraType=2 保留)
  ↓
  若 LLM 失败：UPDATE(status=3·FAILED, content="系统异常，请稍后重试")
  若机审拒绝：UPDATE(status=2·MACHINE_REJECT, content="内容违规提示")
```

**记忆触发的查询逻辑**（ShortChatMemorySummaryTriggerServiceImpl L111）：
```sql
SELECT * FROM tb_soul_haven_short_chat_rolling_wait_log
WHERE user_id     = ?
  AND session_id  = ?
  AND ai_status   = 1    -- 只取 AI 成功回复的批次
  AND is_summarized = 0  -- 只取未总结的批次
ORDER BY id ASC
LIMIT ?

-- 当查到 >= triggerRoundCount(40) 条时，取前 publishRoundCount(20) 条触发一次 MQ
```

## DS-12 MemorySummaryReadyEventPayload

**说明**：记忆总结的 RocketMQ 事件体

```java
@NotNull
Integer sceneType        // 场景类型：1=SHORT_CHAT 2=GROUP_CHAT 3=STAR_DREAM 等

@NotBlank

Long    endCursor        // 终止 Rolling 批次 ID（对应 DS-11.id）

@NotBlank

                         // short_chat_summary_ready:{userId}:{saveId}:{sessionId}:{startCursor}:{endCursor}
```

**消费侧 MemorySummaryProcessor 收到后：**
```
① Redis tryAcquire(idempotencyKey)，TTL=7天，防重复消费
② 根据 sceneType 解析 SummarySceneType 枚举
③ Dubbo Generic Call 按 startCursor~endCursor 查 20 轮对话原文
④ 构建 AddMemoryRequest（见 PolarDB 调用结构）
⑤ POST /v1/memories → PolarDB（infer=true，同步等 ≤16s）
⑥ 写 tb_memory_summary_task 计数行
⑦ 若 unmerged mini 行数 >= 5 → 触发 mergeMemories
⑧ 异步触发画像提取
```

## 补充：PolarDB addMemory 请求 / 响应结构

这两个结构在 `soul-haven-memory-service/.../client/polardb/memory/dto/` 下。

**AddMemoryRequest：**
```java
String              runId       // 命名空间：userId__characterId（短对话）
                                //          roleId__saveId（星梦）
Boolean             infer       // true=让 PolarDB LLM 做事实提取+去重；false=直存原文（降级）
Boolean             asyncMode   // false=同步等待（心屿自控 16s 超时）
List<MemoryChatMessage> messages // 对话原文列表 [{role:"user/assistant", content:"..."}]
Map<String,String>  prompt      // {"FACT_RETRIEVAL_PROMPT": "xinyu-fact-retrieval-v2"}
String              userName    // 用户名（注入提示词）
```

**AddMemoryResponse.results[]（每条事实的处理结果）：**
```java
String id       // PolarDB 分配的记忆 ID（messageId）
String event    // ADD    = 新事实，写入向量库
                // UPDATE = 比已有版本更具体，覆盖
                // NONE   = 与已有记忆重复，丢弃
String memory   // 提取的事实文本（"林夏是产品设计师，赶 UI 改版项目"）
```

**MergeMemoriesRequest（miniMerge 触发时）：**
```java
List<String>       messageIds  // 5 条 mini 批次的 messageId
Boolean            deleteOld   // true=合并后删除 5 条源记忆向量
```
