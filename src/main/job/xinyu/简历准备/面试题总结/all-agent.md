# AI Agent 面试题总结

## 一、对话与 Prompt 工程

### 多轮对话中如何保持上下文不超限？

- 核心答案：滑动窗口 + 摘要压缩 + 选择性保留。
- 策略：
  - 滑动窗口：只保留最近N轮对话
  - 摘要压缩：对早期对话定期生成摘要
  - 选择性保留：保留含关键实体的对话轮次，丢弃闲聊内容
  - 重要程度打分：每轮对话打重要性分，保留高分轮次

### 什么是System Prompt？设计原则有哪些？

- 核心答案：System Prompt是设定模型角色、行为边界、输出格式的指令，优先级高于用户输入。
- 设计原则（RISE原则）：
  - Role：明确定义角色（"你是一个SQL专家"）
  - Instruction：清晰指令（"只输出SQL，不要解释"）
  - Structure：输出格式约束（"输出JSON格式"）
  - Example：给出示例（Few-shot）

## 二、大模型

### 如何避免大模型的幻觉？

从调用大模型的过程来说吧，组织上下文的过程，我们所谓的检索增强RAG 和提示词工程：

- 一个是获取精准的资料和实时信息的具体工具；
- 一个是做规定，提示词中通过cot或者示例的方式去约束他，不知道的就说不知道。

调用完了还可以做自我反思，或者别的模型评判，或者一些硬性要求的校验，都可以减少，但没办法避免。

## 三、Agent

### 什么是Agent？和大语言模型有什么区别？

LLM是Agent的"大脑"，提供推理和生成能力；Agent是LLM的"完整身体"，具备感知、规划、记忆、行动四个能力闭环。

一句话总结：Agent = LLM + 规划 + 工具 + 记忆

### Agent的核心组件有哪些？

### agent的设计模式有哪些

1. **ReAct（Reason + Act，推理‑行动模式）**
   目前构建 AI Agent 最核心、最基础的设计模式之一。
   一轮标准流程循环往复：Thought（思考） → Action（行动） → Observation（观测返回结果），循环直到信息充足、问题解答完毕，输出最终答案。
   - 优点：简单通用，适合绝大多数任务。
   - 缺点：复杂任务容易陷入循环，容易选错工具，容易目标偏移。

2. **Plan‑and‑Execute（规划‑执行模式）**
   先整体规划，再分步执行。
   - 优点：适合长链条复杂任务，减少模型瞎探索。
   - 缺点：计划容易一开始就错，后续全部跑偏。

3. **Reflexion（反思模式）**
   执行完一轮之后，模型回看历史：哪里做错了？哪里信息不足？进行修正。
   - 缺点：多一轮大模型调用，成本变高。

4. **Agentic RAG**
   Agentic RAG 可以多轮检索、改写 query。

5. **Multi‑Agent（多智能体模式）**
   常见 3 种协作模式：
   1. 辩论模式（Debate）：多个 Agent 持有不同视角，互相辩论，输出更客观结果。
   2. 分工协作模式：角色拆分，比如：规划 Agent、工具执行 Agent、评审 Agent、写报告 Agent。
   3. 管理者模式（Manager Agent）：一个总控 Agent，分配任务给各个子 Agent，汇总子 Agent 结果输出。
      - 优点：超复杂任务效果好；
      - 缺点：调用轮次多，成本高，协调逻辑复杂。

### 如何保证 Agent调用工具（Function Calling）的可靠性？

1. 结构定义层：强类型约束（json schema），工具描述清晰，消除歧义
2. 推理策略：cot、few-shot、rag 都是啥
3. 执行护栏：pydantic校验拦截
4. 自愈修复：错误回传机制（重新模型）、状态反思（重新规划）

### Agent 什么时候需要让用户介入？

- 信息不足 → 澄清
- 操作不可逆（发送邮件、支付、删除数据）
- 组织规则要求 → 审批
- 理解跑偏 → 纠错
- 风险或失败超阈值 → 接管

### 什么是 Agent 的可观测性（Observability）？怎么实现？

可观测性三要素：

| 维度 | 内容 | 工具 |
|------|------|------|
| Traces（链路追踪） | 完整的 Thought/Action/Observation 链路 | LangSmith、Langfuse、Arize |
| Metrics（指标） | Token 消耗、步数、延迟、成功率 | Prometheus、Grafana |
| Logs（日志） | 每步详细日志，可回放 | ELK Stack |

关键追踪内容：

- 每次 LLM 调用的输入/输出/耗时/Token
- 工具调用的参数/结果/耗时
- 错误和重试记录
- 最终任务状态

## 四、RAG

### RAG 各模块的优化策略有哪些

**流程**：文档解析 → Chunk 切片 → Embedding 向量化 → 向量库检索 → Rerank 重排序 → LLM 生成答案

**解析**：
- PDF解析器
- 图片ocr
- 噪声过滤：去除页眉、页脚、页码、广告、重复内容

**怎么存？切分的方法**（合理 Chunk 大小与重叠）：
1. Multi-representation Indexing（多表示索引）：提取摘要，摘要和原文绑定，摘要做向量化
2. RAPTOR（递归抽象处理树状检索）：它解决了一个传统RAG的根本性问题：如何同时回答低层次的具体问题和高层次的抽象问题？
3. token级别的：把每个token（词）都变成一个向量，保留了更细粒度的信息

**怎么查？查询优化**：
1. Multi Query - 多查询策略：语义相似但表达不同的查询
2. RAG-Fusion - 多查询结果融合策略：不仅生成多个查询，还使用了倒数排序融合（Reciprocal Rank Fusion, RRF）算法来合并结果
3. Decomposition - 问题分解策略：分步骤查询
4. Step Back问答回退策略：问题抽象化，例如"2000年出生的美国总统是谁？"- "历届美国总统的生日"
5. HyDE（假设性文档嵌入）

### 文档更新后怎么处理

先删除，后插入。删除要把整个文档的所有chunk都删掉（有个前提，在做切片的时候要关联文档的id，或者做标签记录）。

原因就是文档的修改会影响切片的边界。

### rag 怎么评估

- 检索质量
  - 召回率（该找到的文档，你找到了多少？）
  - 准确率（检索到的文档中，有多少是真正相关的？）
  - MRR（第一个正确答案排在第几位？）
- 生成质量
  - 忠诚度（有没有瞎编）、事实准确性、相关性
- 端到端业务评测

## 五、大模型微调

### 为什么需要微调

Prompt 约束能力有限，RAG 只解决知识补给。微调可以改变模型内在行为，比如说一些专业领域、垂直领域的专业术语的理解，或者需要稳定的结构化输出的情形。

- Prompt 只能临时引导，很难长期稳定约束模型输出规范，容易出现 JSON 格式错乱、漏调用工具、编造参数等 Agent 典型问题；
- RAG 负责补充外部知识，但无法改变模型内在思考逻辑；
- 微调通过修改模型权重，固化 Agent 的推理习惯、工具调用流程与输出格式，降低幻觉，提升复杂多轮任务的稳定性。

### 微调的原理

用数据集做反向传播，更新部分或全部权重，现在主流的方式就是lora，通过冻结基座去训练低秩矩阵，合并权重后改变模型的能力。

1. **PEFT 参数高效微调**
   - LoRA：冻结基座，仅训练 Attention 层 QKV/O 低秩矩阵，可训练参数量只有 0.1%‑2%
   - QLoRA：LoRA + 4/8bit 量化加载基座，单卡即可微调 7B/13B 模型，是我们项目最常用的方案。
   - P‑Tuning/Prompt Tuning：不改动模型权重，只训练输入侧虚拟软 token，参数量极小，但生成任务效果一般，更适合分类场景。

### llama factory 重要的核心参数

1. **学习率（Learning Rate）**
   调整原则：决定参数调整幅度，大则进步快易走偏，小则稳定但慢

2. **训练轮数（Epochs）**
   核心原理：指遍历训练数据次数，少则不熟、多则过拟合

3. **批量大小（Batch Size）**
   显存影响：批量越大显存占用越大；特点对比：每次更新用的样本数，大则快而粗、小则慢而细

4. **LORA秩（LORA Rank）**
   调整策略：模型没学会就调大秩
