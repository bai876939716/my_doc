# 简历逐条拆解与追问准备

> 对应文件：[`简历准备/简历内容.md`](../简历准备/简历内容.md)。每条按「原句 → 面试官可能怎么追问 → 建议回答（核心结论先行，再展开说）」准备，展开部分尽量用口语化表达，不堆代码细节，方便直接对着面试官讲出来。

## 项目介绍与架构总体思路

**原句**：系统采用 Java 微服务 + Python AI Agent 双层分工架构……两层通过 OpenAI 兼容 HTTP 协议解耦……Agent 不直接操作数据库，所有数据读写通过 6 个 MCP 服务完成。

**面试官可能怎么追问**：
- "为什么不让 Java 直接把数据接口暴露给 Python，而要多一层 MCP？"
- "如果 Python 侧要新增一个数据查询需求，流程是怎样的？"

**建议回答**：

核心结论：多这一层不是为了炫技，是为了把"AI 能拿到什么数据"这件事从内部实现细节里剥离出来，单独做成一份公开契约，这样两边团队可以各自独立演进，数据暴露范围也能被精确控制。

展开说：如果不这样做，Agent 要么直接连数据库、要么直接吃 Java 内部对象，这两种方式都会把"AI 能看到什么"变成"内部系统长什么样"的副产品——Java 团队想重构一下内部实现都得担心会不会影响到 AI 那边。现在的做法是每个业务域各自独立部署一个数据服务，对外只暴露一组明确声明好入参出参的工具，Agent 只认这份工具契约。新增一个查询需求，只要目标数据服务已经暴露了对应能力，Agent 这边只需要按约定的名字和参数调用就行，重启后还能自动发现新上线的工具；只有当这是一个全新的数据服务时才需要额外接一次连接配置。这跟微服务里用网关或者接口契约隔离内部实现是同一个思路，只是这里隔离的对象换成了 AI 层。

## 核心工作内容 1：三层分级记忆架构

**原句**：短期（最近 20 轮原文，PostgreSQL）+ 长期（PolarDB 向量引擎）+ 用户画像三层注入上下文；以 userId、characterId、roleId 等结构化字符串作为 PolarDB runId 命名空间，将短对话 / 群聊 / 星梦等 7 种场景彻底隔离。

**面试官可能怎么追问**：
- "这个隔离具体是怎么做到的，两个用户会不会串数据？"
- "为什么场景要分这么多种，不能统一处理吗？"
- "20 轮和你其他材料里说的 40 轮不一致，到底是多少？"

**建议回答**：

核心结论：隔离不是靠查询时加条件过滤出来的，而是从写入那一刻起，不同场景的记忆就被写进了完全不同的命名空间里，属于物理隔离，不是逻辑过滤。

展开说：每条记忆存进向量库时都带着一个命名空间标识，这个标识是用户 ID、角色 ID 等信息拼出来的字符串，不同业务场景（普通对话、群聊、剧情互动等）拼法各不相同，所以哪怕是同一个用户，他在不同场景下产生的记忆天然就落在不同的"抽屉"里，检索的时候也只会在对应的抽屉里找，不存在串到别的场景或者别的用户身上的可能。场景要分这么细，是因为总结的"维度"不一样——像群聊、多人剧情这种场景，既需要每个角色单独总结自己视角看到的内容，也需要对整个对话过程做一次整体总结，这两条总结是并行跑的两条完全不同的处理路径，没法合并成一种通用逻辑。至于轮次数字，不同材料里写的不完全一致，这类数字本来就是可配置调整的，被问到时不用纠结哪个是"标准答案"，坦然说这是可以通过配置调整的阈值，重点讲清楚"为什么要做这个截断、依据是什么"才是加分项。

## 核心工作内容 2：LLM 驱动的记忆事实提取与两级去重合并

**原句**：利用 PolarDB Memory API 驱动 LLM 对每条新事实做 ADD / UPDATE / NONE 三路决策，实现实时去重；引入 miniMerge 滚动收敛机制，以 PostgreSQL 行数触发合并，mergeMemories 语义融合；LLM 失败自动降级存原文并打标，XXL-Job 定时补跑 retry 接口。

**面试官可能怎么追问**：
- "为什么不是所有失败都重试？"
- "重试全部失败之后数据就丢了吗？"
- "两级去重具体是哪两级，有什么区别？"

**建议回答**：

核心结论：两级去重解决的是两个不同阶段的问题——第一级是"这条新信息该不该单独记一笔"，第二级是"攒了一堆零散记录之后要不要把它们捏合成一条更精炼的"。失败处理上，只有明确判断为临时性故障的错误才会重试，重试耗尽也不会丢数据，而是降级保底存原文，后续再补。

展开说：第一级去重发生在每次总结的当下，靠调用的记忆管理接口自带的模型判断能力，对每条新提取出来的信息决定是新增、更新已有记录、还是直接丢弃（因为已经有更完整的记录覆盖了它）。但只做这一级还不够，因为总结会越攒越多，产生大量零散的小结片段，所以还有第二级：某个场景下积累的未合并小结达到一定数量后，触发一次批量合并，把这些碎片语义上融合成一条更精炼的记录，同时删掉旧的碎片。至于失败处理，判断"要不要重试"的依据是有没有命中一份具体的错误类型清单——命中了才认为是网络抖动或者模型偶发异常这种大概率能恢复的问题，才重试；不在这份清单里的按正常结果处理，避免无脑重试浪费成本。就算重试全部失败了，也不会直接丢弃这条数据，而是把对话原文直接存进去（跳过用模型提取关键信息这一步），打上一个"待补"的标记，靠一个定时任务后续扫描这批记录重新尝试补一次事实提取——这是"先保数据不丢，把质量问题留给异步补偿"的思路。

## 核心工作内容 3：基于 LangGraph 构建多 Agent 编排框架

**原句**：5 类业务场景各设独立 Agent，StateGraph + add_conditional_edges 实现节点级错误路由与短路退出；统一封装 MCPClient，6 个 MCP 服务通过工具名路由表自动调度；asyncio.Semaphore 统一限制 LLM 与 MCP 并发。

**面试官可能怎么追问**：
- "错误路由具体怎么实现的？"
- "并发数是写死的还是能调？为什么 LLM 和 MCP 要分开限制？"

**建议回答**：

核心结论：整个项目约定了一套统一的规则——任何节点出错就在返回结果里带上错误信息，有一段专门的判断逻辑读这个信息决定流程是继续还是提前结束；并发方面，LLM 调用和数据查询调用因为占用的资源性质不同，分开各设一个可配置的并发上限，不共用一个阀门。

展开说：这套错误路由机制的好处是它是"约定"而不是写死的分支判断——每新增一个处理步骤，只要按这个格式返回错误信息，就自动接入了统一的错误处理，不需要在每两步之间手写一堆 if/else。这跟做接口设计时统一返回结构、用一层拦截逻辑统一处理错误码是同一个思路。并发这块，调用大模型的瓶颈主要是内存占用和上游模型服务的承受能力，调用数据服务的瓶颈是连接数和下游服务能扛住的压力，两种资源性质不同，如果合用一个限流会互相拖累——一个耗时长的大模型请求占着名额，会让本该很快返回的数据查询也被迫排队。这两个并发上限都是通过配置可以调整的，不是写死在代码里的常量，是结合部署的资源规格和实际压测反馈调出来的经验值。

值得主动提一句的细节：陌生角色内容生成那条工作流里，原本有一个独立的输出校验步骤，后来被改成合并到翻译那一步里顺带做——这是一个真实发生过的设计取舍（拆开职责更清晰、合并减少一次流程跳转），能主动讲出这种"设计是怎么演进的"，比只会说"我们用了 LangGraph"更有说服力。

## 核心工作内容 4：五阶段星梦日内容批处理流水线

**原句**：5 阶段流水线（扫描升级角色 → 批量改写旧内容 → 时间窗缺口分析 → 全覆盖补漏 → 星事钩子补充）保障全天 12 个时间窗内容全覆盖；采用"库存优先、LLM 兜底"策略，存量复用率 60%+，单用户每日 Token 成本降低约 40%；XXL-Job 调度多线程并行处理，支持失败自动重试。

**面试官可能怎么追问**：
- "库存优先具体是怎么判断的？"
- "这套流水线怎么防止被重复调度触发两次？"

**建议回答**：

核心结论："库存优先"落地成一套判断逻辑：先看当前一天划分出的各个时间段里，内容数量够不够、类型是不是够多样，够的话就直接跳过对应阶段的模型生产，不够才补，这样能省下大量没必要的调用成本。而且这套判断逻辑天然也是防重复执行的关键——如果任务被意外触发了两次，第二次执行时判断到"已经够了"就会自动跳过，不会重复生产。

展开说：具体流程是先扫描哪些角色关系升级了需要更新内容，再批量改写已经过时的旧内容，然后针对当天 12 个时间段做缺口分析（缺口不够才生产），最后做一次全覆盖补漏和补充关联剧情。真正体现"库存优先"的是缺口分析这一步之前的判断——不是无脑把 12 个时间段全部重新生产一遍，而是先统计现状，只对不达标的部分动用大模型生产，这也是为什么可以做到比较高的存量复用率、显著降低每个用户的 Token 成本。至于防重复触发，靠的不是一个简单的"是否执行过"的标记，而是每次执行前都重新计算一遍当前状态是否已经达标，这种基于当前业务状态做判断的方式比单纯打标记更稳健——即使标记因为某种原因失效了，只要状态判断逻辑本身准确，重复触发也不会导致重复生产。

## 核心工作内容 5：XML 结构化 Prompt 体系与六层 JSON 解析容错机制

**原句**：统一 12 节语义标签 XML 提示词，多版本并存管理，支持灰度切换；针对 DeepSeek 思维链模型输出 `<think>` 块、LLM 偶发尾逗号/截断等导致解析失败率约 8% 的问题，设计六层递进式容错，将解析失败率降至 < 0.5%。

**面试官可能怎么追问**：
- "六层具体是哪六层，说说看？"
- "为什么模型输出会带 think 标签？"

**建议回答**：

核心结论：这套容错本质上是"模型输出格式不稳定"这个问题的层层兜底方案，每一层针对一种具体的输出异常，不是随便加了几层过滤。

展开说：模型输出可能出现好几种情况需要处理——有些模型在走推理模式的时候会把自己的思考过程也写进正文里，需要先把这部分剔除掉，不然会干扰后面找 JSON 内容的逻辑；模型经常习惯性地用 Markdown 代码块包裹输出，需要先把这层包装剥掉；模型有时候会在 JSON 前后多写几句解释性的话，需要精确定位到真正的数据边界；再往后是标准解析，如果失败大概率是因为多打了个逗号或者内容被截断，先做一次简单修复再试一次；如果还是不行，最后交给一个专门的容错解析工具做更彻底的修复尝试。层数如果被问到跟简历上写的对不上，不用慌，坦然说这是持续迭代的一条容错链路，重点讲清楚"每一层在防什么问题"就够了，面试官真正想考察的是你是否理解"为什么模型输出解析要做这么多层兜底"，而不是背版本号。可以再补一句反思：这套多层容错本质上是被动的防御性做法，更彻底的解法是让模型在推理层面就保证输出结构合法，业务侧只需要一次基本校验兜底，这也是团队后续准备推进的改造方向，能体现你不只是"做了"，还"复盘过"。

## 核心工作内容 6：高可靠 Agent 调度体系（幂等、限流、异步解耦）

**原句**：RocketMQ At-Least-Once 场景下用 Redis SET NX（TTL 7 天）保障消费幂等；Redisson 分布式锁（Watch Dog 自动续期）防止星梦会话并发创建；星梦入口三级限流；多类后处理任务经 RocketMQ 异步并行剥离主链路，响应控制在 30ms 内。

**面试官可能怎么追问**：
- "为什么用这种方式做幂等，而不是数据库唯一索引？"
- "分布式锁的自动续期是怎么工作的？"
- "三级限流具体是哪三级？"

**建议回答**：

核心结论：幂等靠的是一次原子的"占坑"操作而不是数据库约束；分布式锁靠自动续期解决"业务处理时间不确定、锁提前过期"的问题；限流是按不同的滥用场景分层设计的，不是一刀切。

展开说：用占坑式的幂等而不是数据库唯一索引，是因为唯一索引方案需要"先插入、失败了再捕获异常"，在高频写入场景下会产生大量数据库层面的冲突开销；占坑操作是一次原子判断直接告诉你有没有抢到，而且自带过期时间，不需要额外清理，更适合"只需要判断处理没处理过，不需要长期留痕"的消费场景。分布式锁这边，因为业务处理时间不总是能提前预估准，如果锁的持有时间设死了，可能业务还没处理完锁就自动释放了，导致另一个请求也拿到了锁，出现并发问题；自动续期机制会在锁快要到期但持有者还在正常工作的时候自动把有效期续上，只有持有者真的宕机或者处理完毕主动释放，锁才会真正失效。限流是按滥用场景分层设计的——短时间内误触发靠一个较短的冷却时间挡住，一天之内滥用次数太多靠一个每日总量上限挡住，恶意脚本式的反复重试靠"一旦触发拒绝就冻结更长时间"这种升级惩罚挡住，三层各自应对不同的滥用模式，不是简单粗暴地设一个总阈值就完事。
