## 一、记忆的实现——让 AI 角色跨会话"记得你"

### 先说问题是什么

我们做的是情感陪伴，不是传统问答机器人。用户期待的体验是——今天跟角色聊了自己在赶一个 UI 改版项目、很累、喜欢喝芋泥波波，明天再打开 App，角色能自然地接上"改版还没完吗，今天买奶茶了没"。这个"记得你"的感觉是整个产品价值的核心。

但 LLM 本身是无状态的，每次推理只能看到当前传入的上下文。所以所有的"记忆"都必须由我们自己的系统管理，在每次对话前把正确的历史信息注入进去。

### 第一步：想清楚要注入什么

我们把用户相关信息拆成三层：

第一层是**短期记忆**，就是最近 40 轮的对话原文，存在 PostgreSQL 里，每次对话直接全量注入。这层解决的是当前对话的上下文连贯——用户这轮说了什么、AI 上轮怎么回应的，都要让 LLM 知道。

第二层是**长期记忆**，存在 PolarDB 向量库里。这是从历史对话里提炼出来的关键事实，比如"林夏是产品设计师""喜欢芋泥波波奶茶"。每次对话前做语义向量检索，TopK 召回 5 条最相关的事实注入进去。这层解决的是跨会话的记忆——用户一个月前说的事，只要语义相关就能被检索到。

第三层是**用户画像**，是从所有对话中提炼出来的结构化用户信息，比如职业、性格偏好、近期状态，存成 JSON 全量注入。这层的作用是让角色对用户有一个整体认知，不用每次都重新了解。

三层各有分工，拼在一起构成每次 LLM 看到的完整用户上下文。

### 第二步：解决"记忆怎么写进去"的问题

对话攒够 40 轮之后，系统会异步触发记忆提取——之所以用异步，是因为记忆写入不能阻塞当前对话的响应，用户不能等。通过 RocketMQ 发一个事件，memory-service 消费后去 PolarDB 执行 addMemory。

这里有一个细节很重要：PolarDB 的 Memory API 内部会用 LLM 做事实提取，把 40 轮原文变成几条结构化事实，同时对每条新事实做三路决策——ADD（新增）、UPDATE（覆盖旧的）、NONE（重复不存）。这就是第一层去重：避免同一个事实被反复写入。

但只有这一层去重还不够。随着时间推移，多批次之间还会有语义上的重叠——比如批次 3 写了"林夏是设计师"，批次 7 写了"林夏是产品设计师（UI 方向）"，后者更具体，应该合并替代前者。所以我们引入了 miniMerge 机制：PostgreSQL 里有一张任务记录表，每次 addMemory 成功都写一行；当未合并记录数积累到 5 条时，触发 mergeMemories，让 PolarDB 内部 LLM 把 5 批记忆做语义融合，5 批精简成 1 批，这 1 批再参与下一轮合并，形成滚动收敛。

（举个效果：用户聊了三个月，向量库里的记忆不会无限膨胀，而是不断被精炼，最终收敛成一份精华的高质量长期记忆。）

### 第三步：解决"记忆不能互相污染"的问题

这个问题比较容易被忽视，但我们早期也踩过。平台上同一个角色在不同场景下扮演的身份是不同的：在日常短对话里是真实的"祁深"，在星梦剧本里可能在扮演一个侦探、一个船长。剧本里用户说"我失业了刚从咖啡馆辞职"是剧本台词，如果这条记忆混进了日常对话的向量库，下次普通聊天时角色会问"你现在找到新工作了吗"，用户完全懵了。

解决方式是 runId 命名空间隔离。PolarDB 的所有查询都必须带 runId 过滤，我们把 userId、characterId、roleId、saveId 等业务字段组合成 runId——短对话的 runId 是 `userId__characterId`，单人星梦是 `roleId__saveId`，多人星梦是 `roleId__saveId`（多角色各自视角独立），群聊是 `sessionId`。系统里总共定义了 7 种场景类型，每种有自己的 runId 格式，向量检索时天然只在本场景的记忆空间里查，跨场景污染从根源上被切断。

### 第四步：保障记忆写入的可靠性

记忆写入有两种失败：LLM 调用超时或返回格式错误。这种情况我们做了降级——把原始对话原文直接 embedding 存入向量库，打上"待重试"标记，这样至少内容不丢。XXL-Job 定时扫描这些记录，调用 retry 接口重新跑 LLM 提取，最终保障所有记忆都能成功写入。

## 二、海量数据生成——每日千级个性化内容的成本与质量平衡

### 先说规模问题有多难

平台有将近 200 个 AI 角色。星梦功能要求每个用户每天对每个角色都有内容可以进入，全天按 12 个时间窗分布（早中午晚各有不同的场景氛围）。用户数乘以角色数乘以时间窗数，每日要生产的内容量是千级规模。

如果纯靠 LLM 实时生成，一是延迟不可接受，用户点进去等生成；二是 Token 成本爆炸；三是高峰时段并发打满模型网关，实时对话链路受影响。（上线初期我们确实遇到过早高峰批处理和实时对话抢 LLM 配额的问题，实时链路 P99 飙到 8 秒。）

### 核心策略：库存优先，LLM 兜底

我们设计了"库存优先、LLM 兜底"的策略。简单说就是：能复用的内容优先从库存里拿，库存里没有的才让 LLM 生成。

为什么可以复用？因为星梦内容是按场景和时段设计的——"清晨在咖啡厅等你"这类场景本身带有时间属性和氛围，同一个场景脚本对不同关系等级的用户是类似的，不需要每次都重新生成。关系等级升级时才需要把旧内容按新等级的语气改写一次。

这个策略让存量复用率做到了 60% 以上，只有剩下 40% 才真正调 LLM，单用户每日 Token 成本降低了约 40%。

### 五阶段流水线的设计逻辑

我们把每天 06:00（实际（后来调整到了 04:30）以避开早高峰）的批处理设计成 5 个阶段，顺序有讲究：

**Phase 1：扫描关系升级角色**。先查哪些角色昨天跟用户关系等级提升了。关系升级意味着旧内容的语气风格要改，否则一个已经 Lv4 的亲密角色还在用 Lv1 的客气语气，体验断层。

**Phase 2：批量改写升级角色的旧内容**。把这些角色的历史内容按新等级语气重新写一遍，存回库存。这步的输出是"改写后的库存"，Phase 3 可以直接用。

**Phase 3：12 时间窗分配 + 批量生产**。核心阶段。按时间窗遍历每个用户的每个角色，先查库存是否充足，够的直接用，不够的才调 LLM 生产，结果写入库存表。这一步内部用了多线程并行，XXL-Job 控制调度，支持失败自动重试。

**Phase 4：Lv3 以上角色全时段覆盖强制补漏**。对于关系深的角色，要保证全天 12 个时间窗都有内容，不能有空档。Phase 3 可能因为某种原因某个时间窗没生成，这一阶段强制兜底。

**Phase 5：星事钩子补充**。星事是星梦结束后在角色主页展示的"回忆动态"，相当于事后追记。对缺少星事的星梦内容逐条补生成。

（五个阶段跑完，整个系统每天典型的输出大概是：发现 5 个升级角色、改写 10 条旧内容、新生产 24 条、强制补漏 8 条、星事补 15 条，合计 50+ 条内容入库。）

### 模型选型也是成本控制的一部分

批处理用的是 deepseek-v4-flash 而不是 qwen3-max，原因很简单——批处理不是实时链路，对延迟不敏感，但量大，要省钱。flash 系列模型推理速度快、成本低，用于批量内容生产是合适的；qwen3-max 留给实时对话和开场白改写这种对质量要求高的场景。

## 三、模型输出稳定——LLM 不稳定与生产高可用的矛盾

### 问题的本质

LLM 的输出本质上是不可控的。你要求它输出 JSON，它可能在前面加一段解释；你用 DeepSeek 这类思维链模型，它会先输出一大段 `<think>...</think>` 推理过程再给正文；偶发情况下它会输出尾逗号、截断一半、甚至把数组括号少写一个。

（在上线前两个月的测试环境里，我们统计了一下，JSON 解析失败率大概在 8% 左右。8% 听起来不高，但乘以每日千级的调用量，每天有上百次内容生产失败，对内容覆盖率影响很明显。）

### 第一道防线：XML 结构化 Prompt，从源头减少输出混乱

我们统一设计了 12 个语义标签的 XML 格式提示词，把角色设定、用户画像、记忆、输出格式要求各归各位，结构清晰。LLM 面对结构清晰的 Prompt 输出更稳定，这是业内公认的经验。

多版本管理支持灰度切换——改 Prompt 不需要发布代码，在 Nacos 配置里切版本，可以先对 5% 的流量生效，观察没问题再全量推。这对 Prompt 迭代很重要，因为 Prompt 改动的影响面很难提前完全预测。

### 第二道防线：六层递进式 JSON 解析容错

这是核心的稳定性工程。我们写了一个统一的 JSON 解析工具，对 LLM 的原始输出做六层递进处理，每层失败才进入下一层：

**第一层：剥离 think 块。** DeepSeek 等思维链模型会在输出里包一层 `<think>...</think>`，里面是模型的推理过程，不是我们要的内容。第一层把这个块识别出来、去掉，留下真正的 JSON。

**第二层：去 Markdown 代码围栏。** LLM 经常把 JSON 包在 ` ```json ... ``` ` 里，这是 Markdown 格式，直接解析会失败。这层把围栏剥掉。

**第三层：数组边界定位。** 找到输出里第一个 `[` 和最后一个 `]`，直接截取这个范围，忽略前后多余的文字。

**第四层：标准 JSON 解析。** 走 `json.loads`，成功就返回。

**第五层：尾逗号修复。** LLM 偶发在数组或对象最后一个元素后面加逗号，这不是合法 JSON。这层用正则把尾逗号去掉，重新解析。

**第六层：json-repair 终极兜底。** 走 json-repair 这个开源库，它能处理更多不规范的 JSON 格式，包括部分截断的情况。

六层下来，解析失败率从 8% 压到了 0.5% 以下。剩下的 0.5% 通常是模型完全输出乱码或者内容被截断一半，这种情况记录日志、打标，（（后期我们接了一个告警，这类失败如果在某段时间内集中出现，会触发模型切换或人工排查。））

### 第三道防线：记忆写入的降级与补跑

记忆提取这条链路对 LLM 依赖很深，一旦 LLM 超时或者失败，如果直接丢弃就是记忆永久丢失。所以我们设计了降级路径：LLM 失败时，把原始对话文本直接以 `infer=false` 的方式存入向量库，不做事实提取，只是原文 embedding。这样内容至少保留了，虽然质量不如提炼过的事实，但不会凭空消失。

打标之后，XXL-Job 每 10 分钟扫描一次这些待重试记录，调 retry 接口重跑 LLM 提取，最多重试 3 次，间隔 5 秒。这套机制保障了记忆写入 SLA——只要模型服务最终恢复，所有记忆都会被正确提取，不依赖单次请求成功。

### 可靠性的系统化思路

说到底，LLM 应用的稳定性和传统服务不一样——传统服务要么成功要么报错，LLM 是"成功了但输出不对"。所以稳定性要从三个维度同时做：输入端（Prompt 结构化，减少模型输出混乱）、输出端（容错解析，尽可能把不规范输出解析成有用的结果）、流程端（降级 + 异步补跑，保障最终一致性）。三道防线不是冗余，而是针对三类不同的失败模式。

## 快速回顾（面试收口用）
