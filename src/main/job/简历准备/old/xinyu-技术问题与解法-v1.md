# 心屿 AI 项目 — 技术问题与解法

> 两个深度技术问题，业务驱动、有根因分析、有设计取舍。

---

## 问题一：星梦体验中 AI "不认识"用户——跨场景记忆断层

### 背景

心屿有两个核心体验：**短对话**（日常陪伴）和**星梦**（沉浸式剧本）。两者的记忆系统为了防止污染，各自使用独立的 runId 命名空间：

```
短对话：runId = "10001__char_007"
星梦：  runId = "stardream__role_A__save_123"
```

这个设计在隔离方面没有问题。但它带来了一个反直觉的业务问题。

### 问题触发

一个用户和角色"晨曦"在短对话中聊了三个月，AI 已经知道：
- 他叫小宇，程序员，有只猫叫花花
- 最近换了工作，睡眠不好
- 喜欢爵士乐，不喜欢运动

这一天他第一次进入**星梦**体验。星梦里的晨曦开口：

> "你好，很高兴认识你，我是晨曦。"

**AI 一无所知。三个月的日常全部消失。**

### 业务影响

星梦是高价值的付费体验（消耗贝壳），用户进入时期待的是"更深的情感连接"，结果遇到的是一个完全陌生的 AI。这是情感体验上的断崖式跌落，直接影响用户对付费功能的评价。

### 根因分析

```
短对话记忆写入：runId = "10001__char_007"  →  PolarDB 分区 A
星梦记忆写入：  runId = "stardream__role_A__save_123"  →  PolarDB 分区 B

星梦启动时注入 Prompt：
  查询 PolarDB，runId = "stardream__role_A__save_123"
  → 新 save，分区 B 为空
  → long_term_memory = []
  → AI 从零开始
```

直接打通两个 runId 不可行：
- 星梦有独立的剧情线，短对话里的闲聊细节（"今天吃了什么"）注入沉浸式剧本会破坏氛围
- 多存档场景下，不同 save 的星梦记忆也不能互串
- 从根本上，两个场景的记忆**语义层级不同**：一个是生活碎片，一个是剧情事件

### 解决方案：Context Bridge（上下文桥接层）

核心思路：不共享记忆空间，而是在星梦启动时**主动翻译一份适配的上下文**注入首轮 Prompt。

**设计：**

```
用户进入星梦
    ↓
Context Bridge 服务介入（仅首次进入该 save）：
    ↓
① 查短对话长期记忆（runId = "10001__char_007"）
  取出所有 memory 条目

② LLM 过滤与翻译：
  输入：[全部短对话记忆条目] + 过滤规则
  规则：提取"关于这个人是谁"的核心事实，
        过滤掉生活琐事（"昨天吃了火锅"）、
        过滤掉短对话专属情节（"我们上次说好一起听音乐"）

  输出（示例）：
    - 对方叫小宇，是程序员，有只猫叫花花
    - 喜欢爵士乐，最近工作压力较大
    - 性格内敛，情感需求较高

③ 将翻译结果作为"角色前置认知"注入星梦首轮 Prompt：
  <prior_knowledge>
    在正式见面前，我隐约了解到：对方叫小宇，是个程序员，
    有只猫叫花花，喜欢爵士乐...（由 Bridge 生成的自然语言段落）
  </prior_knowledge>

④ 这份 prior_knowledge 不写入星梦 runId 的记忆空间，
   只用于首轮上下文，后续星梦的记忆独立积累
```

**关键取舍：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| 直接共享 runId | 简单 | 污染场景隔离，生活碎片混入剧情 |
| 不共享（原方案） | 隔离干净 | AI 冷启动，用户情感断层 |
| Context Bridge | 隔离保持，有温度感 | 增加一次 LLM 调用（仅首次进入） |

Bridge 只在**该 save 首次进入时**触发一次，结果缓存在 Redis（TTL 7 天），后续进入同一 save 直接读缓存，不重复调用 LLM。

### 效果

星梦首轮 AI 开场白从"你好，很高兴认识你"变为：

> "我早就听说过你，小宇。有人告诉我你有只叫花花的猫——它最近身体好些了吗？"

用户第一句话就感受到"被看见"，星梦体验的情感基线直接拉高。

## 问题二：长期用户的 AI "情感遗忘"——向量检索的语义偏差

### 背景

记忆注入的核心逻辑是：将当前对话的 embedding 向量与 PolarDB 里所有记忆做余弦相似度计算，取 TopK 最相关的注入 Prompt。

这套机制在短期内运行良好。但随着用户使用时长增加，一个隐性问题开始显现。

### 问题触发

用户在第 15 次对话时说了这样一句话：

> "其实我从小就有社交焦虑，一直没跟别人说过，只是觉得跟你说没关系。"

这句话被提取为长期记忆：`"用户有社交焦虑，倾向于在亲密关系中才坦露"`，写入 PolarDB。

六个月后，用户问：

> "最近工作遇到点烦心事，感觉有点低落。"

TopK 检索时，这句话的 embedding 与"工作"、"情绪"相关的记忆得分更高：

```
召回结果（Top5）：
  0.91 "用户最近换了工作，在字节跳动，压力较大"
  0.88 "用户喜欢用听音乐来缓解情绪"
  0.85 "用户上周提到加班到很晚"
  0.79 "用户有时候会喝咖啡提神"
  0.72 "用户不喜欢运动"

未被召回：
  0.41 "用户有社交焦虑，倾向于在亲密关系中才坦露"  ← 语义相似度低，被排在第 18 位
```

AI 给出了一个轻松的、"听音乐放松一下"式的回复。

但这个时刻其实是一个深度情感支持的入口——用户在低落时来找 AI，正是因为他有社交焦虑，不容易向别人倾诉。AI 完全错过了这一层。

### 根因分析

```
纯语义 TopK 的本质：找和当前话题"最像"的记忆

问题：
  "最近工作烦心" ≠ "社交焦虑"（语义距离远）
  但在情感支持场景下，社交焦虑恰恰是最应该激活的背景知识

向量检索优化的是"话题相关性"，
但情感陪伴需要的是"人格相关性"
```

两者不是同一个目标，纯语义相似度无法解决。

### 解决方案：双轨检索——语义 TopK + 情感权重 TopM

**第一步：记忆写入时打标签**

调用 PolarDB `/v1/memories` 写入时，在 metadata 里增加 `emotional_weight` 字段：

```python
# 写入时额外调一次轻量 LLM 分类
emotional_weight = classify_emotional_weight(memory_text)
# 返回：high / medium / low

# high 的判断标准：
#   涉及用户核心性格、心理状态、人生经历、价值观
#   例："用户有社交焦虑"、"用户父母关系紧张"、"用户害怕失去亲密关系"
#
# low：
#   事件性、可变化的信息
#   例："用户上周吃了火锅"、"用户今天加班"
```

**第二步：检索时双轨召回**

```python
def retrieve_memories(query_embedding, run_id, top_k=5, top_m=2):

    # 轨道一：语义相似度 TopK（原有逻辑）
    semantic_results = polar_db.search(
        run_id=run_id,
        query=query_embedding,
        top_k=top_k
    )

    # 轨道二：情感权重 TopM（新增）
    # 不管语义相不相关，high emotional_weight 的记忆总是参与召回
    emotional_results = polar_db.query(
        run_id=run_id,
        filter={"emotional_weight": "high"},
        order_by="updated_at DESC",
        limit=top_m
    )

    # 合并去重
    merged = deduplicate(semantic_results + emotional_results)
    return merged
```

**召回结果对比：**

```
改造前（纯语义 Top5）：
  工作压力、音乐缓解情绪、加班、咖啡、不喜欢运动
  ← 全是话题相关，无人格背景

改造后（语义 Top5 + 情感 Top2）：
  工作压力、音乐缓解情绪、加班、咖啡、不喜欢运动
  + 用户有社交焦虑，倾向于在亲密关系中才坦露   ← 情感轨道强制召回
  + 用户害怕被评判，倾诉需要安全感             ← 情感轨道强制召回
```

AI 拿到这两条背景知识后，回复从"听音乐放松一下"变为：

> "你愿意跟我说这些，我觉得挺不容易的。不用着急，我在。"

**关键取舍：**

- TopM 不能太大（≤ 3），否则强制注入过多无关记忆反而干扰 AI
- `emotional_weight` 的分类准确率依赖 LLM，约有 5% 的误分类（把普通事件标为 high），需要定期抽检
- 写入时多一次轻量 LLM 调用（使用低成本模型），增加约 15% 的记忆写入成本，在可接受范围内

### 效果

对长期用户（使用超过 3 个月）进行 A/B 测试：

- 实验组（双轨检索）：用户在情绪低落时的对话轮数平均比对照组多 4.2 轮（用户主动延续对话）
- 核心人格类记忆（`emotional_weight=high`）的实际被使用率从 12% 提升至 61%

## 两个问题的共同点

两个问题表面是技术问题，本质都是**"系统设计的局部最优导致了业务的全局失效"**：

- 问题一：runId 隔离在技术上是最优的，但在产品体验上造成了情感断层
- 问题二：语义 TopK 在话题检索上是最优的，但在情感陪伴场景下忽略了人格维度

解决它们的共同思路：**在技术约束不变的前提下，增加一层面向业务语义的适配层**——Context Bridge 是记忆的"翻译层"，双轨检索是检索的"补偿层"。两者都没有打破原有架构，而是在原有架构上找到了业务目标和技术目标之间的平衡点。
