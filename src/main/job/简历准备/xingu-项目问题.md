# 心屿项目 面试问答准备

## 一、项目介绍（1.5 分钟版）

> 时长：1.5分钟 | 目标：展现业务理解与定义问题的能力

这个项目来自喜马被腾讯收购后，直播业务剥离，我们团队转型做的一款 AI 虚拟角色情感陪伴 App。
我先简单做一个产品介绍吧。

#### 产品有三层递进体验

我们会有将近300多个角色分布在地图上：

- 一个最基础的是日常短对话，你随时可以跟角色聊天，角色会记得你之前说过的事；
- 第二层是新鲜事，就像朋友圈，角色会主动发动态和用户相关的动态，说"想到你之前聊的那件事，笑了很久"；
- 第三层叫星梦，是带有背景故事的沉浸式互动，模拟和角色线下见面的场景，有开场白、有情绪感知、有故事推进。

#### 系统架构

由于（AI 层和业务层技术栈、包括语言都是不一样的，其次还要考虑数据安全的问题，模型相关的操作一定做好数据操作隔离的）为了满足业务需求，我们的系统架构分了两层，也是借鉴微服务的思想，分别是 Java 微服务-处理业务逻辑和数据存储（9个服务），Python AI Agent 层处理模型推理和内容生成（5个agent）。

通讯的话——Java 调用 Agent 走 OpenAI 兼容的 HTTP 协议，像调模型一样调用，Agent 的数据操作全通过 MCP 工具调用 Java 接口，AI 层不直接碰数据库，保证数据权限可控、两层独立扩缩容；两层完全解耦。

#### 核心工作

在项目里主要是做了这么几个核心工作：

1. 怎么解决角色怎么跨会话记住用户、同时不同场景的记忆不能互相污染；
2. 几百个角色每天怎么给每个用户生产个性化内容，同时把成本控在可接受范围；
3. 还有 LLM 输出在生产环境很不稳定，但我们要求系统高可用。

——这三块都做了比较系统性的工作，包括记忆的设计、Agent 编排、还有工具集成、Prompt 工程等等，核心内容都有涵盖。

#### 结果

项目持续了大概3个月的时间，后续上线后2个月就有40w的用户，结果来看，对转型产品来说还是挺超预期的。

## 二、记忆设计

### 记忆的实现

先说一下记忆设计，最终都是要提取出上下文和模型交互的过程中需要考虑这么几个问题吧，这算是记忆设计的一个强约束：

- 第一就是别输入的太多，会影响模型的判断和输出，也就是噪声的问题；
- 第二个就是成本的问题，放的越多肯定越费钱么；
- 其次就是上下文溢出的问题，虽然现在模型上下文很大了，你内容不断地累积肯定会溢出的。

核心就是把重要的、精简的、最需要的来传给大模型，这也是记忆管理的一个目标。

情感陪伴对记忆的要求比普通对话高得多，它不仅仅要知道现在在聊什么，还要知道之前聊过什么，以及在和什么样的人在聊？

### 三层记忆架构

首先就是围绕这三个问题以及对应的约束，定义了我们的三层记忆，分别是：短期记忆就是最近的谈话，我们定的是最近40轮原文；长期记忆的就是所有聊过的内容阶段性的压缩；以及用户画像阶段性的提取。

关于存储的话，就像业内agent类似的做法：

- 我们短期对话存在pgsql中，存的是原文；
- 长期记忆是存在polarDB向量数据库中，它底层也是mem0实现的；
- 用户画像的话，polarDB的kv存储，json结构。

### 抽取和召回的过程

写的时候，每一轮对话都实时写入 PostgreSQL。累积到 20 轮，系统通过 RocketMQ 发一个异步事件触发记忆总结，记忆服务消费这个事件之后，把这 20轮原文打包调 PolarDB 的 Memory API，内部用 LLM 做事实提取，对每条新事实做 ADD、UPDATE、NONE、DELETE，这是第一层去重。为了防止长期记忆的无限膨胀，还有第二层去重：记忆总结达到5次之后会重新压缩成一次总结（数据表维护向量库id的关系）。事实写完之后再异步触发一次用户画像更新。

用户每次发消息，Agent 会并行拉三层数据：分别是pgsql的原文对话、向量融合检索的 top5、以及用户画像，三层拼成 Prompt 注入给 LLM。

### 除了实现过程以外，还解决了几个问题

1. 就是记忆污染（不同场景、不同的人设）
2. 记忆写入的可靠性（降级写原文、打标机、job扫描重试）

### 记忆设计的不足

1. 用户画像共享的没有做隔离，因为一个人面对不同的人是多面的，多个人设；
2. 没有引入记忆置信度或者 TTL 机制；
3. 合并的频率固定，高频用户一天可能触发两三次总结，5 次很快就到了，合并很频繁；低频用户可能一周才触发一次，要等很久才合并，一刀切的阈值对不同类用户不是最优解。

### 如果让你重新设计，会改什么？

#### MCP 的整改

7月份 mcp 改成无状态的了，很大的一个好处就是扩容直接加机器就好了。

现状就是启动的时候：1. 获取 load_tools　2. get_tools　3. 对每个 java mcp server 建立SSE长连接，sse断了还要重连，机器变了要重新连。当然这些集成到工具里了。

#### 压力

因为这是我做的第一个完整上线agent项目么，不仅是一个新的领域，还是要在短时间拿结果的一个项目。当时压力还是挺大的。

#### 途径

短时间内补齐认知，期间看了很多优秀的项目以及技术问的那个，包括咨询了一些大厂做过的朋友。

#### 结果

无论说是技术选型，还是架构落地，都是比较有挑战的，后头看虽然实现上还是比较顺利的。

#### 举例说明

相比于java的系统，agent更多的是处理他的不稳定，llm输出就是概率性的，"出错是正常"作为设计前提，要更多的考虑兜底，刚开始模型不怎么好的时候做了很多的防御性编程。

成本的把控：通过内容的复用、内容的改写、上下文的把控。

量化标准：我们能保证记忆写入的正确、事实的提取、召回的准确性，但是模型回答的好与不好，这项关于产品的定位和背景和人物设定的性格。

当时我们模型的好坏、提示词的好坏还是通过控制变量法去做不同结果的测试集让运营去打分，以及灰度后人工抽查。效率不高也不是完美方案。

之后如果说测试集在一个很大的体量的情况下，可以考虑系统化的评判，用一个更强的模型来自动评判两个版本在情感、角色的差异。

## 四、技术实现细节问答

### StateGraph + add_conditional_edges 实现节点级错误路由

每个节点出错时把 error 写进共享 State 数据包中，add_conditional_edges（条件边）在每个节点后检查 State 有没有 error，有就跳到 END，没有就继续下一个节点。这样有三个好处：

1. 每个节点只管自己，出错只写自己的 error，不影响其他节点的代码；
2. 路由逻辑集中在一个 `_route_on_error` 函数里，所有节点共用；
3. 哪个节点出错、出什么错，State 里都有记录，可观测。

### 工具是怎么实现的，怎么调用的？

项目有 6 个独立的 Java MCP 服务，对应角色信息、用户画像、星梦库存这些不同的业务域，加起来暴露了 30个以上的工具接口。

如果让 Agent 自己管这 6 个服务的连接和路由，耦合很重，每次增减工具都要改 Agent 代码。所以封装了一个全局单例 McpClient，内部维护一张静态路由表，工具名到服务名的映射，Agent 调工具只需要给工具名和参数，McpClient 按路由表自动找对应的 Java 服务发请求，Agent 对路由细节完全透明。

### Semaphore 统一限制 LLM 与 MCP 并发

批处理要给大量角色生产内容，如果直接全部并发，比如 100 个 LLM 请求同时发出，100 份 Prompt 加响应缓冲同时在内存里，4GB 的 Serverless 实例直接 OOM。

- LLM 侧用最多 12 个 LLM 请求同时在内存里，超出的协程挂起、零开销等待，某个完成了才放下一个进来滚动执行；
- MCP 侧是全局单例 Semaphore(8)，所有 Phase 共用一个令牌池，最多 8 个 HTTP 连接同时打向 Java。

### 模型的选择（上下文的大小、质量、速度、成本）

考虑的点：中文情感表达和语气稳定性。

批处理选 deepseek-v4-flash，是因为成本和速度的平衡最合适。项目部署在阿里云 AgentRun，qwen 系列是原生支持的。

### 评测是怎么做的？

我们自己整理了一批测试用例和运营，覆盖几种典型对话场景——用户倾诉情绪、日常闲聊、话题转折这几类。

让几个模型分别跑，团队成员人工打分，维度是语气自然度、情感契合度、回复长度是否合适。同时也测了延迟、成本token消耗的对比。

### 用 LLM Structured Output 从根源替代六层 JSON 容错

上线后实现了六层递进容错，把解析失败率从 8% 压到 0.5%，但回头看这是防御性编码，本质上是在被动应对 LLM 不遵守格式——根源没有解决。DeepSeek 和 Qwen 都支持 `response_format: {"type": "json_object"}` 的 JSON Mode，以及更严格的 Structured Output（传入 JSON Schema，LLM 保证输出结构合法）。

改造方向是：在 Prompt 层声明 Schema，LLM 调用时开启结构化输出，Python 侧用 Pydantic BaseModel 做一次 schema 校验。

### Token 成本怎么控制的？

1. 库存优先、改写
2. 模型分类　【短对话 千问】【批处理 deepseek】【翻译 mini-max】
3. 大模型的提示词缓存，批处理场景下重复前缀不重复计费
4. 上限控制

## 五、其他经历问答

### 在聚水潭做什么？

他们的平台是商家一站式服务的么，同时对接小红书、京东、淘宝、pdd 铺货、订单处理等等交易过程的。

我是在分销的部门，负责分销的订单和售后的开发。分销简单的说就是处理中间商的问题，我负责的那块业务还是比较复杂，就比如售后地址的问题：

你有供应商、分销商，中间还有中间商，1-2层的中间商，那么退货你如何退给供应商的地址？

下单的时候传入售后地址（售后地址绑定在商品上、订单上），穿透获取。

### 如何处理大模型超时的？

不同的业务容忍度做不同的处理：

- 实时对话（关键链路）：把所有的能异步的全部剥离（记忆写入、用户画像更新）；1. 考虑过精简上下文的方式；2. 降级兜底话术【你先说，我在听】
- 星梦批处理：容忍度较高，超时重试即可
- 记忆写入：llm提取事实失败，打标，xxl-job定时扫描

### 你们是怎么做评测的

涉及到评测的有这么几个环节：

1. 检索过程
   - 召回率
   - 准确率
   - mrr（唯一正确答案排在第几位）
2. 模型生成
   - 模型的选择
   - 提示词的版本控制

每个业务场景整理了一批测试用例，让候选的模型都跑一遍，整理了评分表，所有的运营去做盲评（偏差大的case会讨论对齐）。

人工肯定是最好的、最贴合人的需求的，要是说做评测体系肯定要定标准（对于我们业务来说是不适用的）。
