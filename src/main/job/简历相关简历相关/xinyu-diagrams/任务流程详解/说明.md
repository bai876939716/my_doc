# 20 条星梦生产：任务处理全过程详解

**图：** [xinyu-task-flow.puml](./xinyu-task-flow.puml)

场景：小明（uid=1001）今天需要生产 20 条星梦内容（Phase 3）。

---

## 总览：任务经过哪些服务？

```
XXL-Job（调度）
  → Java ContentService（扫描用户）
  → PostgreSQL（活跃用户库）
  → RocketMQ（缓冲队列）
  → Java Consumer（多线程消费）
  → AgentRun Serverless（阿里云平台）
  → Python LangGraph Agent（业务逻辑）
  → McpClient（工具路由，进程单例）
  → LLM API（内容生成）
  → Java MCP Server / dream-service（写库）
```

---

## Step 1：定时触发

**服务：XXL-Job + Java ContentService + PostgreSQL**

06:00，XXL-Job 触发 Java ContentService。ContentService 查 PostgreSQL 拿到活跃用户列表（比如 1w 个 uid），然后往 RocketMQ 发消息——每个用户发 1 条，全部入队。

这一步几乎瞬间完成。RocketMQ 是纯缓冲，消息进去不代表任务开始处理。

---

## Step 2：Consumer 消费（系统真正的并发控制点）

**服务：Java Consumer 线程池**

Consumer 是一个多线程 Java 服务，每条线程的行为是：
1. 从 RocketMQ 取一条消息（uid=小明）
2. 发 HTTP POST 到 AgentRun，**同步阻塞等待**（等 3~5 分钟，等 Python 跑完）
3. 收到 200 响应后，回到第 1 步取下一条

关键：Consumer 线程数 C 决定同时有多少个用户在并发处理。**C 是整条链路吞吐的调节阀，不是 RocketMQ 的消息数量。**

```
C=50  → 同时 50 个用户并发
      → AgentRun 自动扩容 ceil(50÷10)=5 个实例
      → 每实例处理 10 个用户
```

---

## Step 3：AgentRun 实例启动 + McpClient 初始化

**服务：AgentRun Serverless（阿里云）+ Python 实例**

AgentRun 收到 HTTP 请求，创建一个 Python 进程实例（小明专属，2vCPU · 4GB）。

Python 启动后，LangGraph Agent 第一件事是初始化 McpClient：

```python
get_mcp_client()
# 首次调用触发 load_tools()
# 对 6 个 Java MCP Server 各建一个 HTTP 连接
# 调用 get_tools() 拉取工具定义列表
# 构建 _tool_map（工具名 → tool对象）
# 构建 _TOOL_ROUTING（工具名 → 服务名）
```

初始化完成后，McpClient 作为进程级单例存活，后续所有调用复用，不重建连接。

**单例作用域是当前 Python 进程（当前实例），不跨机器。**

---

## Step 4：Phase 1 — 扫描升级角色

**服务：Python Agent → McpClient → dream-service（Java MCP Server）**

```
Python Agent 调用:
  _invoke("queryUpgradePendingRoles", {uid: "小明"})

McpClient 内部做了什么:
  1. 查 _TOOL_ROUTING: queryUpgradePendingRoles → dream-service
  2. _get_mcp_invoke_semaphore(): 拿全局 MCP Semaphore(8)
  3. acquire(): 令牌 8→7
  4. tool.ainvoke(args): 发 HTTP 到 dream-service
  5. dream-service 返回: [{林诗雨, oldLv:1, newLv:2}]
  6. _coerce_mcp_result(): 解包 LangChain 包装格式 → 返回 dict
  7. release(): 令牌 7→8

数据流: Python → McpClient → HTTP → dream-service → HTTP 响应 → Python
```

整个 Phase 1 没有调 LLM，0 Token 成本。

---

## Step 5：Phase 3 — 20 条星梦生产（LLM Semaphore 控流）

**服务：Python Agent → LLM API（DeepSeek-Flash）**

```python
gather_bounded(20 个生产任务, limit=8)
# 在函数内部新建 asyncio.Semaphore(8)
# 这个 Semaphore 只属于本次调用，Phase 结束后销毁
```

**20 个任务的并发行为：**

| 时刻 | Task 状态 | 内存情况 |
|------|-----------|---------|
| 开始 | Task1~8 acquire() 成功 → 同时执行 | 8 份 Prompt(~400KB) + 8 个响应缓冲 |
| 开始 | Task9~20 acquire() 失败 → 协程挂起 | 0（协程栈帧字节级） |
| Task1 完成 | release() → Task9 立即唤醒 | 始终保持 ≤8 份 Prompt |
| Task2 完成 | release() → Task10 立即唤醒 | 始终保持 ≤8 份 Prompt |
| ... | 滚动执行 | 始终 ≤8 份 |

**为什么必须限流？**

```
不限流（全并发）:
  20 个协程同时跑 → 20 份 Prompt(~1MB) + 20 个流式响应缓冲
  总计可能 > 4GB 实例内存上限 → OOM 崩溃

限流 Semaphore(8):
  最多 8 份 Prompt + 8 个缓冲 → 安全可控
```

**LLM 数据流：**
```
Python 构建 Prompt（角色信息 + 时间窗 + 上下文）
  → HTTP POST 到 LLM API（DeepSeek-Flash）
  → 流式响应（SSE）
  → Python 拼装完整 content
  → 交给写库步骤
```

---

## Step 6：Phase 3 — 写库（MCP Semaphore 控流）

**服务：Python Agent → McpClient → dream-service**

每条 Task 生成内容后调写库接口：

```python
_invoke("saveDream", {"char": "林诗雨", "content": "...", "window": "W03"})
```

McpClient 内部：
```
acquire() MCP Semaphore(8)   ← 全局单例，Phase1~5 共用
  → HTTP POST → dream-service
  → dream-service 写 PostgreSQL
  → HTTP 200
release()
```

**为什么 MCP Semaphore 是全局单例（不像 LLM Semaphore 那样每批新建）？**

MCP Semaphore 限制的是 Java 端的 HTTP 连接池资源，这个资源跨 Phase 累积：

```
假如每批新建:
  Phase 3 的 8 个写库 + Phase 4 的 8 个写库 = 16 路 HTTP 同时打向 Java
  → Java 连接池被打满

全局单例:
  所有 Phase 共用同一个令牌池(8)
  任何时刻该实例最多 8 路 HTTP → Java 连接池稳定
```

**数据流：**
```
Python content
  → McpClient._invoke("saveDream")
  → HTTP → dream-service（Java MCP Server）
  → dream-service 内部 → 调 Java 业务接口 → 写 PostgreSQL
  → HTTP 响应
  → McpClient._coerce_mcp_result() 解包
  → Python：写库完成
```

---

## Step 7：汇总返回

**服务：Python → AgentRun → Java Consumer**

```
Python Agent 返回汇总 dict:
  {"phase3_produced": 20, "elapsed": 180}

AgentRun → HTTP 200 → Java Consumer Thread
Consumer 对 RocketMQ 发 ACK → 消息从队列删除
Consumer 取下一条消息 → 处理下一个用户
```

## 并发控制全景（同一实例内，小明的任务）

| 控制点 | 在哪里 | 限制什么 | 上限 | 为什么 |
|--------|--------|---------|------|--------|
| Consumer 线程数 C | Java Consumer | 同时处理的用户数 | 50（可配置） | 控制 AgentRun 实例扩容数量 |
| instanceConcurrency | AgentRun 平台 | 单实例并发任务数 | 10 | 1 个实例最多处理 10 个用户 |
| LLM Semaphore(8) | Python gather_bounded | 同时 in-flight 的 LLM 请求数 | 8 | 防内存溢出（Prompt + 响应缓冲） |
| MCP Semaphore(8) | Python McpClient | 同时 in-flight 的 MCP HTTP 请求数 | 8 | 防 Java 连接池耗尽 |

**跨实例的总量：**
```
LLM 总并发 = 实例数 N × 8
MCP 总并发 = 实例数 N × 8
（各实例 Semaphore 独立计数，互不影响）
```

---

## 两个 Semaphore 的本质区别（面试常问）

```
LLM Semaphore：每批次新建，用完销毁
  → 防的是内存：20 个 Prompt 同时在内存会 OOM
  → 每批隔离：Phase2 的 Semaphore 不会干扰 Phase3

MCP Semaphore：进程级全局单例，实例生命周期
  → 防的是连接：Java 端 HTTP socket 数量有限
  → 跨 Phase 共用：Phase3 写库 + Phase4 写库 合并计数，不超过 8
```
