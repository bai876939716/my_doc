## Q: StateGraph + add_conditional_edges 实现节点级错误路由

### 三个组成部分

**1. 每个节点出错写 error，不抛异常**

```python
async def node_generate(state, *, agent):
    try:
        raw = await invoke_feed_llm_raw(...)
        return {"llm_raw": raw}                      # 正常：只写业务字段
    except Exception as e:
        return {"error": f"模型调用失败: {e}",       # 出错：写 error 到 State
                "error_code": "LLM_FAILED"}
```

节点不抛异常，只把 error 写进共享 State。这样后续节点由条件边决定是否执行，而不是靠 try/catch 层层传递。

**2. 路由函数统一检查 State**

```python
def _route_on_error(state) -> Literal["end", "continue"]:
    return "end" if state.get("error") else "continue"
```

所有节点共用同一个路由函数，逻辑集中，不重复。

**3. 条件边挂在每个节点后面**

```python
g.add_conditional_edges(
    "generate",
    _route_on_error,
    {"end": END, "continue": "translate"},
)
```

每个节点执行完，条件边立即检查 State 里有没有 error，有就短路到 END。

### 执行路径（陌生角色 Feed）

```
正常：
  validate_params → generate → translate → persist → END

LLM 超时（generate 写 error）：
  validate_params → generate ─(error)→ END
  translate 和 persist 都不会跑，不会把脏数据写库

入参错误（validate_params 写 error）：
  validate_params ─(error)→ END
  LLM 根本没被调用
```

### 星梦批处理的差异

批处理是离线任务，出错跳到 `assemble_result` 而不是 END。即使 Phase3 失败，也要把 Phase1、Phase2 的结果返回给调用方，不能什么都不返回。普通 Feed 的 Agent 出错直接 END，两种行为在同一套条件边机制下靠不同的路由映射实现。

## Q: MCP 工具是怎么实现的，怎么调用的？

### 整体架构：6 个独立服务分散注册

| 服务 | 覆盖能力 |
|------|---------|
| user-service | 角色信息、羁绊等级、角色列表 |
| soul-user-service | 用户基础信息（昵称、性别） |
| dream-service | 星梦库存、日计划、星事 |
| profile-service | 用户画像 |
| short-service | 短期对话记录 |
| core-service | 星球世界观、地点信息 |

不是一个大 MCP Server 包所有接口，而是 6 个独立服务，各自维护自己的 URL 和连接，互不影响。

### 工具名路由表 `_TOOL_ROUTING`

静态字典，工具名 → 服务名，25+ 个工具全部在这里注册：

```python
_TOOL_ROUTING = {
    "characterDetail":        "user-service",
    "queryDailyPlan":         "dream-service",
    "getUserProfile":         "profile-service",
    "getAppShortChatMessage": "short-service",
    # ...共 25+ 个工具
}
```

Agent 调用时只用知道工具名，完全不感知背后是哪个 Java 服务。

### 初始化：启动时一次性建连

`McpClient` 是全局单例（模块级变量，进程内唯一），第一次调用 `get_mcp_client()` 触发 `load_tools()`。对每个已配置 URL 的服务创建 `MultiServerMCPClient`，拉取工具列表，构建两张表：

```python
client = MultiServerMCPClient(
    {server_key: {"transport": "streamable_http", "url": url}},
    tool_name_prefix=False,
)
tools = await client.get_tools()
# 结果写入 _tool_map（工具名 → tool对象）和 _tool_registry（工具名 → 服务名）
```

后续调用直接复用单例，不重新建连。单例作用域是进程（Serverless 实例），不跨机器。

### `_invoke()` 调用链

```
_find_tool(tool_name)           ← 查 _tool_map，找到 tool_object
↓
_get_mcp_invoke_semaphore()     ← 拿全局 Semaphore(8)，超过则挂起
↓
async with sem:
    tool.ainvoke(args)          ← HTTP 打到 Java MCP Server
↓
_coerce_mcp_result(raw)         ← 解包 LangChain text 格式
```

### 响应解包：`_coerce_mcp_result`

LangChain MCP 适配层把 Java 返回的 JSON 包成这样：

```
[{"type": "text", "text": "## Original Response\n{\"code\":0,\"data\":{...}}"}]
```

解包步骤：
```python
text = raw[0]["text"]
json_str = text.split("## Original Response\n", 1)[1]
return json.loads(json_str)["data"]
```

### Session 失效自动重连

Serverless 实例空闲后长连接 Session 可能过期。遇到 `session terminated` / `connection closed` 等错误时：

```python
if _needs_mcp_reconnect(e):
    await self.reload_tools()   # 丢弃旧连接，重新建连全部 6 个服务
# 指数退避 0.5s → 1s，然后重试 tool.ainvoke()
# 对 Agent 上层透明
```

## Q: asyncio.Semaphore 统一限制 LLM 与 MCP 并发，防止 Serverless 实例内存溢出

**见图：** [xinyu-mcp-semaphore-overview.puml](./xinyu-mcp-semaphore-overview.puml)

> 简历说"统一限制"，实际是两个独立 Semaphore，防护目标不同，这是面试中需要主动说清楚的关键点。

### 问题根源：批处理任务量大，直接全并发会 OOM

以 Phase 3 为例：需要生产 20 条星梦内容。

```python
# ❌ 危险写法：全部并发
await asyncio.gather(*[generate_dream(task) for task in tasks])

# 20 个协程同时运行 → 20 份完整 Prompt 同时在内存
# 每份 Prompt ~50KB，加上流式响应缓冲区
# 20 × (50KB Prompt + 响应缓冲) → 可能超出 4GB 实例内存上限 → OOM
```

### LLM 侧：gather_bounded 每批新建 Semaphore(8)

```python
async def gather_bounded(coroutines, *, limit=None):
    sem = asyncio.Semaphore(limit or get_llm_concurrency())  # 生产环境 = 8
    async def _run(coro):
        async with sem:   # acquire：令牌 >0 立即 -1；=0 协程挂起
            return await coro
    return list(await asyncio.gather(*(_run(c) for c in coroutines)))
```

**运行过程（20 个任务）：**

```
Task 1~8  → acquire() 成功，令牌 8→0，8 个 Prompt 同时在内存
Task 9~20 → acquire() 失败，协程挂起，0 内存 · 0 CPU

Task 1 完成 → release() → 令牌 0→1 → Task 9 立即唤醒
Task 9 → acquire() → 令牌 1→0 → 进入执行

如此滚动，内存中始终 ≤ 8 份 Prompt + 响应缓冲
```

**为什么每批新建，不复用？**

Phase2、Phase3、Phase4 各自调用 `gather_bounded`，每次新建独立 Semaphore，批次之间互不干扰。若复用，Phase2 未完成时 Phase3 的令牌也会被占用，产生意外阻塞。

### MCP 侧：全局单例 Semaphore(8)

```python
# mcp_client.py 模块顶层
_mcp_sem: asyncio.Semaphore | None = None

def _get_mcp_invoke_semaphore() -> asyncio.Semaphore:
    global _mcp_sem
    if _mcp_sem is None:                                    # 懒初始化
        limit = int(os.getenv("XINGMENG_MCP_CONCURRENCY", "8"))
        _mcp_sem = asyncio.Semaphore(limit)
    return _mcp_sem
```

模块级全局变量 = 该 Python 进程内只有一个实例，所有 Phase（1/2/3/4/5）的所有 MCP 调用共用同一个令牌池。

**效果：** 最多 8 路 HTTP 连接同时打向 Java，Java 连接池不会被耗尽。

**为什么是全局单例，不是每批新建？**

MCP 限的是 Java 端连接池资源，跨 Phase 累积的。若每批新建，Phase3 的 8 个 MCP 调用 + Phase4 的 8 个 MCP 调用同时发出 = 16 路，Java 仍然会被打满。全局单例确保同一实例内任何时刻总 MCP 连接 ≤ 8。

### asyncio.Semaphore 核心机制

`asyncio.Semaphore(n)` 内部维护一个计数器（初始值 = n）：

- `acquire()`：计数器 > 0 → 立即 -1，协程继续执行；= 0 → 协程放入等待队列，**挂起**（不占 CPU，内存仅协程栈帧，字节级）
- `release()`：计数器 +1，若等待队列非空，唤醒队首协程
- `async with sem:` = 进入时 `acquire()`，退出时自动 `release()`（即使异常也保证释放）

### 两个 Semaphore 对比

| | LLM Semaphore | MCP Semaphore |
|--|--|--|
| 上限 | 8（环境变量 `XINGMENG_LLM_CONCURRENCY`） | 8（环境变量 `XINGMENG_MCP_CONCURRENCY`） |
| 创建方式 | `gather_bounded` 调用时新建 | 模块级全局懒初始化，进程唯一 |
| 生命周期 | 本批次完成后 GC | 实例（进程）生命周期 |
| 防护目标 | 内存：Prompt + 流式响应缓冲区 | 连接数：Java 端 HTTP socket |
| 作用范围 | 单次批量调用内部 | 该实例所有 Phase 的所有调用 |
| 挂起位置 | `gather_bounded._run()` 的 `async with sem` | `McpClient._invoke()` 的 `async with sem` |

### 全链路并发数量关系

```
Consumer 线程数 C
    → AgentRun 实例数 N = ceil(C ÷ 10)
        → LLM 总并发 = N × 8（各实例独立 LLM Semaphore）
        → MCP 总并发 = N × 8（各实例独立 MCP Semaphore）

C=50  → N=5  → MCP=40 路  → Java 连接池配置 ≥ 40
C=200 → N=20 → MCP=160 路 → Java 连接池配置 ≥ 160
```

MCP Semaphore 保证的是单实例内不超 8 路，Java 连接池总压力由 Consumer 线程数（N）决定。
