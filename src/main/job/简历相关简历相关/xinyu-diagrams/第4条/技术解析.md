## Q: 批处理任务是怎么分发到机器上的？

**见图：** [01-batch-dispatch.puml](./01-batch-dispatch.puml)

### 三层分发链路

```
XXL-Job 06:00 触发
    └─ Java Handler → ContentGenerationService
         └─ DB 扫描活跃用户 → List<UserId>（例：500 个）
              └─ 每个用户 → 发一条 RocketMQ 消息（At-Least-Once）
                   └─ Java Consumer（多实例并行消费）
                        └─ 每条消息 → POST AgentRun HTTP API
                             └─ AgentRun Serverless 自动扩容
                                  ├─ Python 实例 1（user1，独立内存）
                                  ├─ Python 实例 2（user2，独立内存）
                                  └─ Python 实例 N（userN，独立内存）
```

### 为什么用 RocketMQ 而不是 Java 直接调 AgentRun？

- **解耦触发与执行**：Java Handler 扫描完用户即返回，不阻塞等任务跑完
- **不丢消息**：At-Least-Once 语义，Consumer 崩溃重启后消息还在队列里
- **背压控制**：Consumer 数量控制消费速率，防止同一时刻把 AgentRun 并发打满

### Python 实例为什么完全隔离？

AgentRun Serverless 每个 HTTP 请求对应一个独立函数实例（进程隔离）：
- 每个实例有自己的 `asyncio.Semaphore`（LLM=12, MCP=8）
- 某实例崩溃不影响其他实例
- 代价：Java MCP 侧总并发 = **实例数 N × 8**，Java 连接池需按此配置上限

### 幂等保障

RocketMQ At-Least-Once 可能重投（Consumer Rebalance 时）。用 Redis SET NX（key = `batch:{uid}:{date}`）保幂等：拿到锁才执行，已跑过的直接跳过。

## Q: 任务开启后，一步一步是怎么运行的？（以小明为例）

**见图：** [02-execution-scenario.puml](./02-execution-scenario.puml)

### 场景设定

用户：小明（uid=1001），3 个角色：
- 林诗雨 Lv1 → Lv2（昨晚刚升级）
- 陆承宇 Lv3
- 苏凛 Lv5

### Phase 1 — 扫描升级角色（无 LLM 调用）

```
_invoke("queryUpgradePendingRoles")  →  [{林诗雨, oldLv:1, newLv:2}]
_invoke("markOldDreamsConsumed")     →  清除林诗雨 Lv1 旧库存 5 条
```

MCP Semaphore 状态：每次调用 acquire → 1/8，完成 release → 0/8。

### Phase 2 — 改写旧星梦（5 条，LLM Semaphore 全部立即通过）

```python
gather_bounded(5 个改写任务, limit=12)
# 新建 Semaphore(12)，5 < 12，全部立即拿到令牌
# 5 路 LLM 同时发出
```

完成后每条结果写库，走 MCP Semaphore(8)，5 < 8，全部立即通过。

### Phase 3 — 批量生产（缺口 20 条，LLM Semaphore 触发排队）

```python
gather_bounded(20 个生产任务, limit=12)
# 新建 Semaphore(12)
# Task1~12  立即拿到令牌，12 路 LLM 同时发出
# Task13~20 阻塞在 acquire()，协程挂起，不占 CPU/内存
```

滚动行为：
```
Task1 完成 → release() → 令牌 +1
Task13 unblock → acquire() → 令牌 -1 → 发出第 13 个 LLM 请求
（始终 ≤12 个 LLM 在飞）
```

写库时多条结果竞争 MCP Semaphore(8)，最多 8 路 HTTP 同时打向 Java。

### Phase 4 — Lv3+ 全量补充（2 条，立即通过）

陆承宇 W07、W08 缺内容：

```python
gather_bounded(2, limit=12)  # 2 < 12，立即通过
```

### Phase 5 — 星事补充（8 条，立即通过）

```python
gather_bounded(8, limit=12)  # 8 < 12，立即通过
```

### 最终输出

```
phase1_upgraded:    1
phase2_rewritten:   5
phase3_produced:   20
phase4_coverage:    2
phase5_star_events: 8
total_elapsed:    ~180s
```

整个过程中：LLM Semaphore 保证内存不超，MCP Semaphore 保证 Java 连接不被打满。

## Q: Token 成本怎么控制的？

### 三个主要手段

**库存优先**：Phase 3 先查当前时间窗的库存，有现成内容直接复用，无需调 LLM。库存复用率 60% 以上，是成本控制最核心的机制。

**改写而非全量重写**：Phase 2 对关系升级的角色只改写旧内容的措辞，不重新生成完整星梦。同等效果下，改写比从头生成的 Token 消耗小得多，单用户日均成本降 ~40%。

**模型分级**：
- 批处理（第4条场景）：DeepSeek-V4-Flash，成本低、速度快
- 实时对话：Qwen3-Max，质量高、中文情感稳定
- 实时开场白改写：Qwen3-Max，< 2s 响应

### 其他手段

- **Prompt prefix cache**：系统 Prompt 内容固定，利用 LLM 接口的 prefix cache 特性，批处理场景下重复前缀不重复计费
- **精简上下文**：三层记忆只注入 Top5 向量召回 + 最近 40 轮原文，不是全量历史
