## Q: 五阶段流水线是怎么设计的？（以小明为例）

**见图：** [xinyu-pipeline-overview.puml](./xinyu-pipeline-overview.puml)

### 场景设定

用户：小明（uid=1001），3 个角色：
- 林诗雨 Lv1 → Lv2（昨晚刚升级）
- 陆承宇 Lv3
- 苏凛 Lv5

---

### Phase 1 — 扫描升级角色（无 LLM 调用，0 Token）

```
MCP queryUpgradePendingRoles  →  [{林诗雨, oldLv:1, newLv:2}]
MCP markOldDreamsConsumed     →  清除林诗雨 Lv1 旧库存 5 条
```

纯 MCP 查询，不调 LLM。扫描到升级角色才触发后续改写。

---

### Phase 2 — 批量改写旧内容

```python
gather_bounded(5 个改写任务)
# 并发改写林诗雨 Lv2 旧星梦的措辞
```

改写旧内容而非全量重生成，同等效果下 Token 消耗更小。

---

### Phase 3 — 时间窗缺口分析 + 库存优先生产

```python
# 分析 12 个时间窗，发现缺口 20 条
gather_bounded(20 个生产任务)
```

**关键：库存优先策略**

每个缺口任务先查当前时间窗的现有库存：

```
有库存 → 直接复用，0 Token 消耗（约 60% 的任务走这里）
无库存 → 调 LLM 生产新内容（约 40% 的任务走这里）
```

结果：20 条任务中约 12 条复用、8 条新生成。

---

### Phase 4 — Lv3+ 全量覆盖补漏

Lv3+ 用户（陆承宇）需保证 12 个时间窗全覆盖：

```python
gather_bounded(2)  # W07、W08 各 1 条，2 < 8，立即通过
```

---

### Phase 5 — 星事钩子补充

近期有特殊事件（星事）的角色需要额外内容：

```python
# 苏凛 Lv5 本次无星事缺口，跳过
```

### 最终输出

```

```

## Q: "库存优先、LLM 兜底"策略怎么理解？

### 核心思路

12 个时间窗内容一天内大量重复：不同用户看同一角色在同一时间窗的内容，有很高的相似性。把已生产的内容缓存进库存，下次需要时直接复用，不重新调 LLM。

### 复用率 60%+ 是怎么来的

库存命中的主要来源：
- **昨日库存**：角色当天库存若未消费完，次日同时间窗继续可用
- **跨用户复用**：多个用户共用同一角色内容时，先生产的直接给后来的用
- **Lv 未变**：角色等级未升级，内容配置不变，库存持续有效

命中率 60% 意味着只有 40% 的任务真正消耗 LLM。

### Token 成本降低 ~40% 的计算

```
全量生成：N 条任务 × 每条 Token 成本 = 基准
库存优先：60% 复用（0 Token）+ 40% 生成
降幅 ≈ 60%（复用率）× 100%（对应成本） = 60%
实际测量约 40%（部分任务改写成本低于全量生成）
```

## Q: Token 成本还有哪些控制手段？

### 三个主要手段

**库存优先（最核心）**：Phase 3 先查库存，有现成内容直接复用。复用率 60%+，是成本控制最核心的机制。

**改写而非全量重写**：Phase 2 对关系升级的角色只改写旧内容的措辞，不重新生成完整星梦。改写比从头生成 Token 消耗小得多。

**模型分级**：
- 批处理（离线）：DeepSeek-V4-Flash，成本低、速度快
- 实时对话：Qwen3-Max，质量高、中文情感稳定
- 实时开场白改写：Qwen3-Max，< 2s 响应

### 其他手段

- **Prompt prefix cache**：系统 Prompt 内容固定，利用 LLM 接口的 prefix cache 特性，批处理场景下重复前缀不重复计费
- **精简上下文**：三层记忆只注入 Top5 向量召回 + 最近 40 轮原文，不是全量历史

## Q: 失败怎么处理？重试机制是什么？

### 两层保障

**消息层（不丢任务）：** RocketMQ At-Least-Once 语义。Consumer 崩溃重启后，未 ACK 的消息重投，任务不丢。

**幂等保障（不重复执行）：** Redis SET NX，key = `batch:{uid}:{date}`。拿到锁才执行，已跑过的直接跳过，解决重投带来的重复问题。

**XXL-Job 自动重试：** 任务失败后 XXL-Job 可配置重试次数，整个批次失败时自动重新触发。
