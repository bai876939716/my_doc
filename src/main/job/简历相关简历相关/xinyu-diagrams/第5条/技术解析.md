## Q: 为什么要用 XML 结构化 Prompt？怎么管理多版本？

### 为什么用 XML

LLM 的 Prompt 不加结构会有几个问题：

- 角色定义、用户记忆、当前场景、输出格式要求混在一起，LLM 注意力分散
- 不同场景复用部分 Prompt 时，纯文本拼接边界不清晰，容易漏内容
- 上线后想改某一段，不知道从哪改、改了会不会影响其他段

XML 语义标签的好处是每段内容职责明确。12 节标签大致分三类：

**角色定义类**（静态，每次对话不变）
```xml
<role_name>苏凛</role_name>
<personality>冷静、克制、偶尔毒舌，内心细腻</personality>
<background>星球守护者，有不为人知的过去</background>
<speaking_style>简短有力，不废话，偶尔反问</speaking_style>
```

**上下文注入类**（动态，每次对话重新填充）
```xml
<short_memory>最近 40 轮对话原文</short_memory>
<long_memory>向量召回 Top5 事实</long_memory>
<user_profile>用户性格特征、当前情绪状态</user_profile>
<current_scene>当前星梦场景描述、进展状态</current_scene>
```

**输出约束类**（固定格式要求）
```xml
<output_format>必须返回 JSON，包含 reply / emotion / action 三个字段</output_format>
<length_limit>reply 不超过 80 字</length_limit>
<forbidden>不能提及现实世界、不能打破第四堵墙</forbidden>
```

### 多版本管理 & 灰度切换

每个 Agent 的 Prompt 在 Nacos 配置中心维护，key 格式为 `prompt:{scene}:{version}`，例如 `prompt:xingmeng:v3`。

版本切换流程：
```
新版 Prompt 写入 Nacos（prompt:xingmeng:v4）
    → Nacos 推送配置变更事件
    → Java 侧灰度路由：按 uid 哈希，10% 流量走 v4，90% 走 v3
    → 观察 v4 的解析成功率、用户反馈
    → 确认无问题后，全量切换到 v4
```

灰度期间两个版本同时运行，回滚只需要在 Nacos 改路由比例，不需要发版。

## Q: 六层 JSON 容错是怎么设计的？

**见图：** [xinyu-json-fallback.puml](./xinyu-json-fallback.puml)

### 问题根源：LLM 输出天然不稳定

要求 LLM 输出 JSON，它会按要求做，但不是每次都完美：

| 失败类型 | 原因 | 频率 |
|---------|------|------|
| `<think>` 块 | DeepSeek 思维链模型在 JSON 前输出推理过程 | 高（切 DeepSeek 后集中出现） |
| Markdown 围栏 | LLM 把 JSON 包在 ```json...``` 里 | 中 |
| 尾逗号 | `{"key": "val",}` 末尾多一个逗号 | 中 |
| 截断 | 输出超长被截断，JSON 不完整 | 低 |
| 引号问题 | 中文内容里有引号嵌套冲突 | 低 |

初始失败率 ~8%，主要集中在前两类。

### 六层递进处理逻辑

```python
def parse_llm_json(raw: str) -> dict:
    text = raw

    # 第1层：DeepSeek think 块剥离
    if "</think>" in text:
        text = text.split("</think>", 1)[1].strip()

    # 第2层：Markdown 围栏处理
    if "```json" in text:
        text = text.split("```json", 1)[1].split("```", 1)[0].strip()
    elif "```" in text:
        text = text.split("```", 1)[1].split("```", 1)[0].strip()

    # 第3层：JSON 边界定位
    start = text.find("{")
    end = text.rfind("}") + 1
    if start != -1 and end > start:
        text = text[start:end]

    # 第4层：标准解析
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        pass

    # 第5层：尾逗号修复
    fixed = re.sub(r",\s*([}\]])", r"\1", text)
    try:
        return json.loads(fixed)
    except json.JSONDecodeError:
        pass

    # 第6层：json-repair 兜底
    try:
        return json.loads(json_repair.repair(text))
    except Exception:
        logger.error("json_parse_failed", raw=raw)
        return FALLBACK_RESPONSE
```

### 为什么是六层，不是更少？

- 1~3 层是前处理，把文本清洗成"看起来像 JSON"的形态，几乎无成本
- 第 4 层是标准路径，大多数情况走这里就结束
- 第 5 层针对最常见的解析失败（尾逗号），一行正则，低成本
- 第 6 层是兜底，json-repair 库能处理结构损坏类问题，但有一定 CPU 开销，只在前几层都失败时调用
- 六层之后还失败，说明 LLM 输出完全无法修复，返回兜底话术而不是让用户看到报错

### 效果

| | 上线前 | 上线后 |
|--|--|--|
| 解析失败率 | ~8% | <0.5% |
| 主要失效原因 | think 块 + 尾逗号 | 极少数截断类 |
| 用户侧表现 | 偶发无响应/报错 | 极少感知，降级为兜底话术 |
