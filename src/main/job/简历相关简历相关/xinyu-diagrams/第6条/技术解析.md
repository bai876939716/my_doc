## Q: RocketMQ At-Least-Once 有哪些重投场景，幂等怎么保障？

### 三类必然重投场景

**Rebalance 窗口期：** Consumer 实例上下线时，Broker 重新分配 Queue 归属。窗口期内一条消息可能被旧 Consumer 拉走但还没 ACK，又被新 Consumer 拉到，导致同一条消息被两个实例同时处理。

**ACK 超时：** Consumer 拉到消息、处理完了，但 ACK 发回 Broker 时网络抖动丢包。Broker 没收到 ACK 判定消费超时，把消息重投给下一个 Consumer。

**Consumer 崩溃重启：** Consumer 处理到一半崩溃，未 ACK 的消息重新入队被其他实例消费。

这三类在 At-Least-Once 语义下是**必然发生**的，不是偶发，必须在业务侧做幂等。

### Redis SET NX 幂等方案

```python
key = f"batch:{uid}:{today}"                # 业务唯一键

async def consume(message):
    acquired = await redis.set(key, "1", nx=True, ex=7*24*3600)  # TTL 7天
    if not acquired:
        await message.ack()   # 已处理过，直接 ACK，跳过
        return

    await run_agent(uid)      # 拿到锁才真正执行
    await message.ack()
```

**TTL 为什么是 7 天？** 覆盖最长的重投窗口。RocketMQ 消息最大重试间隔约 2 小时，再加上极端网络分区情况，7 天足以覆盖所有重投场景，同时不会让 Redis 无限膨胀。

## Q: Redisson 分布式锁用在哪里，Watch Dog 是什么？

### 应用场景：防星梦会话并发创建

用户点击进入星梦时，系统要创建一个会话记录、初始化 LangGraph 状态、生成开场白。这个过程耗时 2~5 秒。

如果用户在这段时间内反复点击（或弱网下多次发起），多个请求同时进来，可能并发创建多个会话，导致数据混乱。

```java
RLock lock = redisson.getLock("xingmeng:session:" + uid);
boolean acquired = lock.tryLock(0, -1, TimeUnit.SECONDS);  // 不等待，立即判断
if (!acquired) {
    return Result.fail("星梦正在启动中，请稍候");
}
try {
    createXingmengSession(uid);
} finally {
    lock.unlock();
}
```

`tryLock(0, ...)` 表示拿不到锁立即返回，不等待，用户感知是"正在启动"的提示，不是卡住。

### Watch Dog 机制

普通分布式锁要预设 TTL，比如设 30 秒。如果任务超过 30 秒还没完成，锁自动释放，其他请求可能进来，产生并发问题。

Watch Dog 的做法：
```
lock.lock()                      ← TTL 默认 30 秒
    ↓
Watch Dog 后台线程启动
每 10 秒检查：锁持有方还活着？
    是 → 续期 TTL 重置到 30 秒
    否（进程崩溃）→ Watch Dog 停止 → TTL 自然倒计时 → 锁到期自动释放
```

不需要猜任务会跑多久，锁不会因为任务慢而提前失效，也不会因为进程死了而永远不释放。

## Q: 三级限流是怎么设计的？为什么需要三级？

**见图：** [xinyu-reliability-overview.puml](./xinyu-reliability-overview.puml)

### 三级覆盖不同的滥用模式

| 级别 | 规则 | 覆盖场景 |
|------|------|---------|
| 第 1 级 | 同一用户两次进入间隔 < 10 分钟，拒绝 | 用户误操作、页面抖动重复触发 |
| 第 2 级 | 单用户当天累计超 8 次，拒绝 | 正常用户的每日上限，防资源滥用 |
| 第 3 级 | 被拒绝后继续尝试，追加 5 分钟冻结 | 脚本/机器人高频重试 |

**为什么不用单一限流？**

- 只有第 1 级（冷却）：脚本可以按 10 分钟间隔慢慢刷，一天还是能刷很多次
- 只有第 2 级（日上限）：前 8 次的间隔没有限制，瞬间打满配额
- 第 3 级的意义：被 L1 或 L2 拒绝后还在试，说明是程序行为而不是真实用户，追加冻结可以有效拦截

### 实现

```python
async def check_rate_limit(uid: str) -> bool:
    now = time.time()

    # 第1级：冷却检查
    last_ts = await redis.get(f"rl:cooldown:{uid}")
    if last_ts and now - float(last_ts) < 600:
        await apply_freeze_if_needed(uid)   # 被拒后继续试 → 第3级冻结
        return False

    # 第3级：冻结检查（冻结优先于日上限检查）
    frozen_until = await redis.get(f"rl:freeze:{uid}")
    if frozen_until and now < float(frozen_until):
        return False

    # 第2级：日上限检查
    count = await redis.incr(f"rl:daily:{uid}:{today()}")
    if count == 1:
        await redis.expire(f"rl:daily:{uid}:{today()}", 86400)
    if count > 8:
        await apply_freeze_if_needed(uid)
        return False

    await redis.set(f"rl:cooldown:{uid}", now, ex=600)
    return True

async def apply_freeze_if_needed(uid: str):
    # 被拒绝且继续尝试 → 冻结 5 分钟
    await redis.set(f"rl:freeze:{uid}", time.time() + 300, ex=300)
```

## Q: 异步解耦是怎么做的，主链路怎么控制在 30ms 以内？

### 主链路只留一个阻塞点

用户发消息，主链路里真正必须同步等待的只有一件事：**LLM 推理返回结果**。

其他所有操作：记忆写入、画像更新、统计埋点、推送通知，全部从主链路剥离，发 RocketMQ 消息异步消费。

```
用户请求进来
    ↓
拉三层记忆（asyncio.gather 并行，~20ms）
    ↓
拼 Prompt，调 LLM（流式输出，首 token 返回即开始渲染）
    ↓
返回响应给客户端（30ms 内）

[异步] → RocketMQ
    ├─ 记忆写入 Consumer：mem0 事实提取 + 向量写库
    ├─ 画像更新 Consumer：用户情绪/兴趣更新
    └─ 埋点 Consumer：行为统计上报
```

**记忆写入为什么可以异步？**

记忆写入影响的是下一轮对话，当前这轮已经结束了。用户下一次发消息时，这一轮的记忆大概率已经写完了（Consumer 正常消费延迟 < 1 秒）。即使极端情况下写失败，有 XXL-Job 补跑机制兜底，最终一致性有保障。

### LLM 超时处理

流式输出下，超时点不同于非流式：
- **首 token 超时**（3 秒内没有任何输出）：说明 LLM 没有响应，直接返回兜底话术
- **中途断流**（已有部分输出，突然中断）：已输出的内容直接展示，末尾追加"...（网络不稳定，稍后继续）"，不让用户看到空屏

批处理场景超时则直接重试，XXL-Job 支持自动重跑，单个用户失败不影响其他用户。
