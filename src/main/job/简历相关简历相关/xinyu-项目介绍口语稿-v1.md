# 心屿项目介绍口语稿 v1

---

心屿是一个以 AI 虚拟角色为核心的情感陪伴产品，提供日常短对话、角色主动发布的个性化 Feed 动态、以及沉浸式 AI 剧本体验三种玩法。这个项目是我从 0 到 1 主导的，核心挑战可以归结为一句话：**怎么让 AI 既有温度又稳定、既个性化又控得住成本**。

围绕这个目标，我主要做了四个方向的工作。

**第一个是架构层面的分层设计。** 我们用 Java 微服务处理业务逻辑和数据持久化，用 Python 的 LangGraph 框架承担 AI 推理和内容生成，两层通过 OpenAI 兼容的 HTTP 协议解耦。这样设计的好处是 Java 侧完全不感知 AI 内部的实现细节，AI 层也不直接碰数据库，所有数据读写通过我们封装的 MCP 服务来完成。两层可以独立迭代、独立扩缩容，这个架构决策在后来频繁调整 Prompt 和更换模型的过程中省了很多麻烦。

**第二个是记忆系统。** LLM 本身无状态，用户聊了几个月 AI 还是一张白纸，这个体验对情感陪伴产品是致命的。我设计了三层分级记忆：最近 40 轮原文作短期记忆直接注入，长期的事实类信息通过 PolarDB 向量引擎按语义相关度召回，用户画像单独维护全量注入。同时用结构化的命名空间把短对话、星梦、群聊等七种场景的记忆彻底隔离，消除了跨场景污染的问题。

**第三个是内容生产的稳定性。** 我们用了三个不同的大模型，输出格式稳定性差异很大。DeepSeek 会输出大段思维链，LLM 偶发的尾逗号、截断，这些加在一起解析失败率大概在 8%。我们做了六层递进式容错——从剥离思维链、提取 Markdown 围栏、边界定位，到标准解析、尾逗号修复、最后 json-repair 兜底，把失败率压到了 0.5% 以下。Prompt 这边也建立了一套 12 节语义标签的 XML 模板体系，通过版本字符串管理多版本并存，支持灰度切换。

**第四个是星梦内容的批处理和成本控制。** 星梦是付费的沉浸式体验，用户进入时需要立刻看到内容，等不了实时生成。但每天全量生成 12 个时间窗的内容成本很高。我设计了一个五阶段流水线，核心策略是库存优先、LLM 兜底——先改写复用历史内容，改写比全新生成便宜很多，真正需要新生产的只有剩余的缺口。最终存量复用率稳定在 60% 以上，单用户每日 Token 成本降低了约 40%。

这四块做下来，让我对 LLM 工程落地有了比较完整的认知——不只是调接口，而是把记忆、编排、容错、成本这些问题系统性地做了一遍。
