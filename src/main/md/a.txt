项⽬技术栈：Java 微服务（SpringBoot / RocketMQ / PostgreSQL / Redis）、Python AI Agent
（LangGraph / LangChain / MCP / PolarDB 向量引擎）、阿里云 AgentRun Serverless
项目介绍： 心屿是公司战略转型的新产品，以 AI 虚拟角色为核心的沉浸式社交 App，用户通过日常对话与"星梦"（模拟线下见面的 AI 剧本互动）建立情感关系。
AI Agent 架构设计： Java 微服务层（业务逻辑 + 数据持久化）与 Python AI Agent 层（LLM 推理 + 内容生成）的两层拆分方案，两层通过 MCP（Model Context Protocol）HTTP 接口解耦，Agent 不直接操作数据库，所有数据读写通过 MCP 工具调用 Java Core 完成，AI 层与业务层可独立部署扩缩容；共设计了 6 个 MCP 服务（角色信息、用户信息、短对话历史、星梦库存、记忆画像、世界观数据）覆盖 Agent 全部上下文需求。
每日 AI 内容生产流水线（5 阶段批处理）：设计并实现每日 06:00 定时批处理，为所有活跃用户预生产当日星梦内容，分配至 12 个 2 小时时间窗（W01 清晨 ~ W12 黎明），保证用户全天随时进入都有内容。5 阶段流水线：Phase1 扫描昨日关系升级角色（无 LLM）→ Phase2 改写旧星梦适配新等级 → Phase3 时间窗分配 + 优先复用库存再补充生产 → Phase4 Lv3+ 高等级用户强制全天覆盖 → Phase5 补充星事钩子；Phase3 采用库存优先策略，现有内容复用率 60%+，显著降低 LLM Token 调用成本。
分层记忆系统（RAG + 向量检索）：设计实现短期记忆（最近 40 轮对话原文，PostgreSQL 存储，直接全量注入 Prompt）+ 长期记忆（PolarDB 向量引擎，事实提取 + 向量相似度检索 TopK 注入）+ 用户画像三层架构；记忆总结全程 RocketMQ 异步触发，不阻塞对话主链路；设计 miniMerge 滚动收敛机制，每积累 5 条 mini 记忆自动调 mergeMemories API 语义融合，合并结果继续参与下轮，防止记忆无序膨胀；全链路幂等：Redis 幂等键防 MQ 重复消费 + XXL-Job 每 10 分钟扫描 FAILED 记录重试 + 降级时 infer=false 存原文兜底。
提示词工程体系：统一采用 XML 结构化提示词，按语义拆分为 12 个标签块（系统信息、任务目标、角色设定、世界观配置、创作约束、红线禁止、输出格式等），版本化管理（v1.0 ~ v4.0），新版本新增函数而不覆盖旧函数；设计四层 JSON 解析兜底（剥离  推理块 → 提取 json 代码围栏 → 标准 json.loads → json_repair 终极修复），将 LLM 输出解析失败率从约 8% 降至 < 0.5%。
遇到的问题：
记忆无序膨胀导致向量检索噪音增多：随用户对话积累，向量库中出现大量语义相似的重复事实（如"用户是设计师"与"用户是产品设计师"同时存在），向量检索 TopK 召回噪音变多，AI 回复偶发逻辑矛盾。 解决方式：引入 miniMerge 滚动收敛机制——每次记忆总结成功后在 PostgreSQL 的 tb_memory_summary_task 表写入一行记录，通过查 DB 行数（而非内存计数器，规避服务重启丢失状态问题）触发合并，积累到 5 条后调用 PolarDB mergeMemories API，LLM 对 5 批记忆做语义融合（保留最具体版本、删除冗余），合并结果 messageId 写回 DB 继续参与下轮合并，形成滚动收敛；addMemory 阶段的 NONE 事件处理单次写入内的实时去重，两层机制协同，记忆精度显著提升。
多人星梦多角色记忆视角污染：多人星梦（用户 + 主角色 + N 配角）结束后需为每个角色生成各自视角的记忆，若共享同一份总结，角色 A 会"记住"只有角色 B 经历的情节，体验严重失真。 解决方式：设计 Fan-out 并行拆分机制，星梦结束后先触发会话级总结（sceneType=MULTI_STAR_DREAM），再并行 Fan-out 为 N 条角色维度总结任务（sceneType=MULTI_STAR_DREAM_ROLE_MEMORY），每条任务用第一人称视角 Prompt 从各自角度提炼记忆，写入各自独立的 runId = charX__saveId 命名空间，彻底隔离多角色记忆。
LLM 输出格式不稳定导致解析失败：DeepSeek R1 等思维链模型会在 JSON 前输出  推理块，部分模型在末尾生成多余逗号，极端情况下格式完全错乱，json.loads 解析失败率约 8%。 解决方式：四层解析兜底（剥离 think 块 → 提取 json 围栏 → 标准解析 → json_repair 修复），同时在提示词 <输出格式指南> 中明确禁止 Markdown 代码块输出，双管齐下将解析失败率降至 < 0.5%。

核心链路稳定支撑产品上线运营，内容生产成功率 99%+，实时改写链路 P99 < 2 秒
分层记忆架构使 AI 角色能跨数百轮对话"记住"用户关键事实，情感陪伴体验连续性显著提升
5 阶段批处理 + 库存复用策略，每用户每日 LLM Token 成本降低 40%+
