# 企业级知识库平台建设总体规划

| 项目信息 | 内容 |

---

## 一、项目概述

### 1.1 要解决的问题

企业知识当前普遍散落在各类载体中:共享网盘、聊天记录、个人电脑、离职员工的脑子里。由此产生三类典型损耗:找知识慢(重复劳动、重复踩坑)、知识不流动(部门墙)、知识会流失(人员变动)。本工程的目标是建设一个统一的企业知识库平台,让知识**存得进、管得住、找得到、用得起来**。

### 1.2 目标与范围

**本期范围内:** 文档全生命周期管理(上传、解析、组织、版本、审核、归档)、细粒度权限体系、全文检索、AI 智能问答(RAG)、智能辅助能力(自动摘要、自动打标、过期检测)、知识运营指标看板。

**本期范围外(远期演进):** 知识图谱、协同编辑(对接现有办公套件即可)、移动端原生 App(先做响应式 Web)、跨企业知识交换。

### 1.3 成功标准

上线 3 个月后达成:核心部门知识覆盖率 ≥ 80%(部门内高频使用文档已入库);月活跃用户占目标人群 ≥ 60%;AI 问答解决率(用户标记"已解决"占比)≥ 70%;平均检索时间从"问人"的半小时级降到 1 分钟级。指标口径在 Phase 0 与业务方共同确认。

### 1.4 干系人

发起方(公司管理层)、建设方(本项目组)、首批用户(建议选 IT 运维 + HR + 一个核心业务部门作为试点)、合规方(信息安全部门,私有化部署与权限设计需其背书)。

## 二、总体策略

### 2.1 为什么"知识管理为主、AI 为辅"是对的

AI 问答的效果上限由知识库的质量决定。文档不齐、权限混乱、版本过期的情况下上 RAG,只会得到"自信地答错"。因此本工程把主体投入放在知识管理的地基上——组织结构、权限、生命周期治理——AI 作为检索与消费的增强层,当地基成型后叠加,两者互相成就。

### 2.2 完全自研的收益与代价

收益:核心数字资产完全自主可控;权限模型与公司组织架构深度集成;AI 层可按需演进(今年接 RAG,明年可以接 Agent);无开源产品升级与定制冲突。代价:工期比二开长、需要持续投入工程人力。对应的缓解措施:严格 MVP 纪律、AI 辅助编码提效、架构上把"通用组件"(解析、检索)与"业务逻辑"解耦,必要时可替换。

### 2.3 三条建设原则

第一,先窄后宽:先在试点部门跑通全流程,再全面推广,避免"上线即荒废"。第二,每两周可见:以双周为节奏交付可演示的增量,向管理层持续证明进展。第三,治理先行:知识入库标准、Owner 责任制、审核流程在 Phase 0 就与管理制度一起设计——技术平台解决"能不能",管理制度解决"愿不愿"。

## 三、分阶段路线图

> 以下按 4-5 人团队估算。若实际投入 2 人及以下,Phase 1 范围裁剪为:上传 + 目录 + SSO + 全文检索(去掉审核流与版本对比),工期顺延 2-3 周。

### Phase 0:调研与蓝图设计(第 1-3 周)

**目标:** 把"建什么"定义到可开发、可验收的程度。

调研动作:访谈 5-8 个部门(每部门 30-60 分钟,了解知识在哪、痛点是什么、愿意贡献什么);盘点存量知识载体与规模(网盘目录、Wiki、聊天群文件);与信息安全部门确认权限与密级要求;确认试点部门。

设计输出:《需求规格说明书》《知识分类体系与元数据规范》(分类建议 2-3 层封顶,元数据含类型/密级/Owner/部门/有效期/状态)《权限模型设计》《接口契约草案(OpenAPI)》《验收标准》。

**里程碑 M1(第 3 周末):** 蓝图评审通过,需求规格冻结。此后需求变更走正式变更流程,防蔓延。

### Phase 1:知识管理基座(第 4-11 周)

**目标:** 不含 AI 的完整知识管理平台,这是整个工程的地基。

功能清单:多格式文档上传与解析(Office/PDF/Markdown/图片 OCR/压缩包)、空间-目录-文档-版本四级组织结构、元数据与标签体系、权限体系(SSO 对接 + 空间级 RBAC + 密级)、全文检索(ES + 中文分词,检索结果按权限过滤)、基础治理(草稿-审核-发布状态流、Owner 与有效期管理、过期提醒、归档)。

**里程碑 M2(第 7 周末):** MVP 内部演示——能完成"上传 → 组织 → 授权 → 检索"闭环。
**里程碑 M3(第 11 周末):** 试点部门内测上线,存量知识批量导入工具交付。

### Phase 2:AI 能力层(第 12-15 周)

**目标:** 在干净的地基上叠加 AI,复用公司 LiteLLM 网关(建 kb-service 虚拟 key,独立预算与用量观测)。

功能清单:RAG 问答(混合检索 + 重排 + 引用溯源到原文位置)、检索权限过滤(向量检索前按用户可见空间 pre-filter)、智能辅助(自动摘要、自动打标建议、相似/重复文档检测、临近过期检测提醒)、问答质量评测集(50-100 条标注问答对,量化 recall@k 与回答忠实度)。

**里程碑 M4(第 15 周末):** AI 问答公测,评测集指标达标(检索 recall@10 ≥ 85%,忠实度 ≥ 90%)。

### Phase 3:全面推广与持续运营(第 16 周起)

推广策略:试点部门复盘会 → 按部门分批推广 → 与高频场景绑定(新人 onboarding、项目复盘、IT/HR 常见问题)驱动知识入库。运营机制:知识贡献纳入可见的激励(贡献榜、优秀知识评选);季度知识新鲜度审计;指标看板月度通报。

**里程碑 M5(第 20 周末):** 全公司开放,v1.0 验收。

## 四、技术架构

### 4.1 总体分层

系统分为五层:接入层(Nginx 反向代理 + SSO 认证)、应用层(FastAPI 服务群 + Celery 异步任务)、数据层(PostgreSQL / MinIO / Elasticsearch / Redis)、AI 能力层(Embedding 服务 / Rerank 服务 / LiteLLM 网关 → 国内大模型)、运维层(Prometheus + Grafana + Loki 可观测体系)。总体架构见附图 `architecture.mermaid`。

### 4.2 技术选型清单

| 层次 | 选型 | 选型理由 | 演进备选 |
|---|---|---|---|
| 后端框架 | Python 3.12 + FastAPI | 与 AI 生态同语言,异步性能好,OpenAPI 文档自动生成 | — |
| 前端 | React 18 + TypeScript + Ant Design 5 | 企业中后台事实标准,组件覆盖表格/树/权限场景 | Vue3 + Element Plus(若团队更熟) |
| 元数据库 | PostgreSQL 16 | 知识条目、用户、权限、版本的事务一致性 | — |
| 向量检索 | pgvector(起步) | 与 PG 同库,支持元数据过滤,**检索层权限 pre-filter 的关键**;组件少运维轻 | 文档量超百万 chunk 后迁 Milvus |
| 对象存储 | MinIO | S3 兼容,私有云标配,存原始文件与解析产物 | — |
| 全文检索 | Elasticsearch 8 + IK 分词 | 中文 BM25 检索成熟方案 | OpenSearch |
| 异步任务 | Celery + Redis | 文档解析/向量化是重 IO 任务,必须异步化 | — |
| 文档解析 | Apache Tika(通用)+ MinerU(复杂 PDF/扫描件)+ LibreOffice headless(格式转换) | 中文 PDF 解析质量是 RAG 效果第一瓶颈,MinerU 对中文版面识别效果好 | Unstructured |
| Embedding | BGE-M3(TEI 私有化部署) | 中文效果领先,单模型同时输出稠密+稀疏向量,天然支持混合检索 | 网关侧 Embedding API |
| Rerank | BGE-reranker-v2-m3 | 与 BGE-M3 配套,检索精度提升显著 | — |
| LLM 接入 | **复用公司 LiteLLM 网关** | 建 kb-service 虚拟 key,独立预算;DeepSeek 主力,agent-main 组故障转移 | 直接接厂商 API(不推荐,失去统一管控) |
| 认证 | OIDC / LDAP 对接公司 SSO | 企业级刚需,不做本地账号体系 | — |
| 部署 | Docker Compose(开发与初期生产) | 与公司现有基建一致;组件规模可控 | 用户量上来后迁 K8s + Helm |
| 可观测 | Prometheus + Grafana + Loki | 指标、面板、日志三件套,私有云自建标准 | — |

### 4.3 与 LiteLLM 网关的集成

知识库 AI 层不直接持有任何厂商 API Key,统一走网关:为知识库创建 `kb-service` 虚拟 key,设置独立月度预算与 RPM 限额;问答、摘要、打标三类任务在网关侧分别建模型组(问答用 DeepSeek 主力,摘要/打标可用更便宜的轻量模型,成本分层);用量数据从网关的 Postgres 取,纳入运营看板。这样知识库的 AI 成本、审计、故障转移全部继承网关已有能力,零重复建设。

### 4.4 数据流概要

**入库流:** 上传 → MinIO 存原始文件 → Celery 任务调 Tika/MinerU 解析为结构化文本 + 版面信息 → 按标题层级切分(chunk 300-500 字,重叠 10-15%)→ BGE-M3 向量化 → 正文入 ES、向量入 pgvector,元数据(文档 ID、空间、密级、权限组)随行写入。

**查询流:** 用户提问 → 查询改写(可选)→ 并行 BM25(ES)+ 向量检索(pgvector,带权限 pre-filter)→ RRF 融合 → BGE-reranker 精排 → Top-K 进 LLM(附引用)→ 回答 + 原文定位引用。

## 五、核心模块设计

### 5.1 知识模型

四级结构:**空间(Space)→ 目录(Category)→ 文档(Document)→ 版本(Version)**。空间对应组织或职能域(如"运维知识空间""HR 政策空间"),是权限隔离的边界;目录限制在 2-3 层,宁可标签多、不要层级深;文档必须携带六项核心元数据:类型、密级、Owner、所属部门、有效期、状态(草稿/待审/已发布/已归档);版本保留完整历史,支持 diff 对比与回滚。

标签体系采用"受控标签 + 自由标签"双轨:受控标签由管理员维护(保证检索与统计口径一致),自由标签由用户添加(保证表达灵活性),AI 自动打标建议只在受控标签集内推荐。

### 5.2 权限模型

双维度控制:**空间级 RBAC × 文档密级**。角色设三个,不贪多——空间管理员(管成员与设置)、编辑者(增改文档)、查看者(只读)。密级分四级:公开、内部、秘密、机密,规则为"密级压过角色"(如查看者角色不能看"秘密"级文档,除非被单独授权)。权限判定结果缓存(Redis, TTL 5 分钟),避免每次检索全量计算。

**AI 检索的权限过滤是本设计的红线:** 必须在向量检索阶段就按用户可见空间做 pre-filter(pgvector 的元数据过滤),绝不允许"先检索后过滤"——否则低权限用户可通过提示词探测到无权访问的内容摘要。

### 5.3 RAG 质量保障

三个抓手:其一,解析质量优先——建立解析质量抽检机制,扫描件、表格类文档入库时标记"解析置信度",低置信度进人工校对队列;其二,评测集驱动——Phase 2 交付前建成 50-100 条标注问答对,每次检索策略调整跑回归评测(recall@10、MRR、回答忠实度),用数字说话;其三,反馈闭环——问答页的"有用/无用 + 点赞纠错"直接进入运营看板与评测集,持续迭代。

### 5.4 文档解析管道

解析器路由策略:Markdown/纯文本直接读取;Office 与常规 PDF 走 Tika;复杂版面 PDF(含表格、图文混排、扫描件)走 MinerU;图片走 OCR。解析产物统一为带版面结构的中间格式(段落、标题层级、表格、图片引用),存 MinIO 并随版本关联——切分与向量化永远基于中间格式而非原始文件,保证策略可重跑、模型可升级(换 Embedding 模型时全量重建索引不用重新解析)。

## 六、非功能需求

安全与合规:全链路私有化,数据不出 IDC;LLM 调用仅出 API 请求(文本出域,需在 Phase 0 与信息安全部门确认口径并写入制度);操作审计日志(谁在何时对什么文档做了什么)独立存储、不可篡改,保留期按公司制度;文件传输与存储加密(TLS + MinIO 服务端加密)。性能:检索 P95 < 1.5s,AI 问答端到端 P95 < 8s(流式输出首 token < 2s);单集群支撑 100 万文档、千万级 chunk。可用性:核心服务多副本,数据每日备份,恢复演练每月一次,RPO ≤ 24h / RTO ≤ 4h。

## 附录:名词表

RAG(检索增强生成):先检索相关知识片段、再交给大模型组织回答的技术模式。BM25:关键词全文检索算法,擅长精确词匹配。向量检索:按语义相似度检索,擅长"意思接近但用词不同"的查询。混合检索 + RRF:两种检索结果融合排序的方法。Rerank(重排):用精排模型对初筛结果二次排序,显著提升精度。Pre-filter:检索前按权限过滤,保证无权内容不进候选集。BGE-M3:开源中文 Embedding 模型。MinerU:开源中文文档解析工具。Embedding:把文本转为向量的模型,是语义检索的基础。
