# 场景题：mem0 的实体图谱是怎么存的？怎么构建的？

## 一句话答案

存储上是"图数据库 + 向量增强节点"——实体节点除了名字，还带一份 embedding，靠语义相似度做实体消歧；构建上是"两阶段 LLM 抽取（实体→关系）+ 向量相似度去重 + 类似向量记忆 ADD/UPDATE/DELETE/NOOP 的冲突决策 + Cypher MERGE 落库"。配套图示：`diagrams/03-mem0图谱构建流程图.puml`（流程图）。

---

## 一、怎么存：图数据库 + "向量增强"节点

- **存储后端**：`BaseGraphStore` 抽象层可插拔，默认用 Neo4j（也可以换 Memgraph 等兼容 Bolt 协议的图库），跟 `BaseVectorStore` 是并列的两套存储，不是从属关系
- **节点（Entity）**：不是普通图节点，是"向量增强节点"——每个实体节点除了 `name` 属性，还存了这个实体名称的 embedding 向量，图库侧建 vector index。这么做的目的是让实体消歧能用**语义相似度**而不是死板的字符串精确匹配（比如"猫"和"我养的猫"能被认成同一个实体）
- **边（Relationship）**：边带类型（比如"过敏于""喜欢""属于"），也会存关系的创建时间、来源记忆 ID 等属性，用于后续判断这条边要不要被更新或删除
- **多租户隔离**：节点和边都打上 `user_id`（可选 `agent_id`），所有 Cypher 查询都带这个过滤条件——是同一张图里靠属性过滤做逻辑隔离，不是每个用户开一个独立图库

## 二、怎么构建：两阶段 LLM 抽取 + 向量去重 + 冲突决策

```
新对话输入
   ↓
① 实体抽取（LLM调用）：结构化工具调用，让LLM输出这段话里的实体列表
   ↓
② 关系抽取（LLM调用）：结构化工具调用，抽出(实体A, 关系, 实体B)三元组
   例：(用户, 过敏于, 坚果)
   ↓
③ 实体消歧（向量相似度检索）：新实体名先做embedding，
   去图库里向量检索，找到语义相近的已有节点就复用，
   避免"猫"和"小猫"变成两个重复节点
   ↓
④ 冲突判定（LLM调用，四元决策，跟向量记忆的ADD/UPDATE/DELETE/NOOP同一套思路）：
   把新三元组和该实体已有的边一起交给LLM判断：
   全新关系→ADD / 更新旧关系→UPDATE（"是素食者"变"不吃素了"）/
   互相矛盾→DELETE旧边 / 完全重复→NOOP
   ↓
⑤ 落库：用 MERGE（不是 CREATE）保证幂等，按name+user_id匹配已有节点则更新、
   不存在则新建；关系类型因为Neo4j原生不支持参数化关系类型名，
   工程上通常要把关系名拼进Cypher字符串里再执行
```

## 三、检索时怎么用：图谱做多跳关联，跟向量检索互补

```
用户提问 → 同样先做一次实体抽取，抽出问题里提到的实体
        → 向量相似度匹配到图里对应的节点
        → 以该节点为起点做1~2跳图遍历（Cypher变长路径查询）
        → 取出关联的实体和关系，格式化成文本
        → 和向量库召回的"事实型"记忆一起注入Prompt
```

## 四、为什么要图谱 + 向量两套并存

- **向量记忆**是"陈述句"粒度的语义检索，擅长回答"直接相关的是什么"，但答不好需要**多跳推理**的问题（比如"我提过的那个也喜欢猫的朋友叫什么"——要先定位"朋友"这个实体，再看它关联的偏好）
- **图谱**把"实体-关系-实体"结构化出来，天然支持多跳查询，但对"这句话到底在说什么"的语义模糊性不如向量检索灵活
- Mem0 的设计是两者并存、检索时融合结果，各自补对方的短板；`enable_graph=True` 才会启用这条链路，不开的话就只有向量记忆这一层

## 面试话术小结

> Mem0 的实体图谱本质是"给图数据库的节点加了一层 embedding"，让实体识别和消歧能用语义相似度而不是精确字符串匹配；构建流程是"实体抽取→关系抽取→向量去重→LLM冲突决策→Cypher MERGE落库"五步，思路上和它的向量记忆 ADD/UPDATE/DELETE/NOOP 四元决策是一致的，只是决策对象从"一句话事实"变成了"一条关系边"。存在的意义是补齐向量检索答不好的多跳推理场景。
