# 场景题：xinyu 项目中 MCP 调用出现问题，有哪些处理机制？业内是怎么处理的？Harness 是怎么处理的？

## 一句话答案

xinyu 现状是"错误码分类（MCP_FAILED/MCP_NOT_CONFIGURED）+ LangGraph条件边终止本次调用 + 批处理层面Phase级尽力而为 + MCP客户端单例复用"，偏简单，没有自动重试和熔断；业内标准做法是"分类处理+重试幂等+熔断+降级+可观测性"全套；Harness 层面可以把 MCP 工具调用纳入统一的 Error Classifier / Retry Controller / Circuit Breaker 体系。配套图示：`diagrams/04-MCP调用与空结果处理流程图.puml`（流程图，同时覆盖"调用失败"和"05-记忆召回为空的处理机制.md"里的"调用成功但返回空"两种分支）。

## 一、xinyu 项目里 MCP 出问题时的真实处理机制（有据可查，不编造）

### 1. 错误码分类：MCP_FAILED / MCP_NOT_CONFIGURED

这是 LangGraph 错误码体系里专门给 MCP 相关问题分出来的两类（`02-系统架构介绍.md`、`03-数据模型说明.md`）：

| 错误码 | 触发场景 | 适用 Agent |
|--------|---------|-----------|
| `MCP_NOT_CONFIGURED` | 该 Agent 需要的 MCP 服务未配置/未初始化 | Stranger Feed |
| `MCP_FAILED` | MCP 工具调用本身失败（连接失败/超时/服务端报错） | Stranger Feed, Xingmeng |

### 2. LangGraph 条件边路由：出错即终止本次调用，不带脏数据往下走

```
节点内调用MCP出错 → state.error = MCP_FAILED
条件边检查error存在 → 路由到END
主流程不继续执行，不会拿着不完整/未验证的数据继续生成内容
```

这是 xinyu 通用的错误处理骨架（同一套机制也用于 `LLM_FAILED`/`PARSE_FAILED` 等其他错误码），MCP 失败只是被归到这套体系里的一类，没有专属的特殊逻辑。

### 3. 批处理场景的"尽力而为"：单点 MCP 故障不拖垮整体

`05-业务面试20问.md` 里明确写到：星梦每日批处理若某个 Phase **完全无法进入（比如 MCP 连接失败）**，做法是"记录该 Phase 的 error_code，**尝试继续执行后续 Phase**"——单个用户/单个 Phase 的 MCP 故障不会导致当天所有用户的内容生产全部失败。

### 4. MCP 客户端单例复用

`MultiServerMCPClient` 全局共享单例，不是每次请求都重新建连接（`02-系统架构介绍.md` 性能优化点）——减少因反复握手带来的额外失败概率和延迟。

### 5. 非关键 MCP 调用异步化，不拖慢主链路

开场白改写场景里，MCP 的日志记录调用是异步执行的，即使这类非关键写操作慢或失败，也不影响 < 2 秒的主链路延迟目标。

### 诚实说一句局限

文档里**没有**看到 MCP 调用失败时有自动重试（退避重试）机制，也没有熔断器、没有失败后降级读缓存数据的设计。如果面试官追问"具体重试策略/熔断阈值是什么"，最好直接说"目前主要靠错误码分类+条件边终止+批处理层面的尽力而为，没有做自动重试和熔断，这是我认为可以补的一块"——这个回答本身就展示了你知道更完整的方案长什么样。

## 二、业内通用是怎么处理工具调用（MCP/Function Call）失败的

| 机制 | 做法 |
|------|------|
| 分类处理 | 网络层（超时/连接失败）vs 协议层（工具不存在/参数不合法）vs 业务层（工具执行成功但业务规则不通过）分开处理，不能一刀切 |
| 重试与幂等 | 只读类工具调用可以安全指数退避重试；有副作用的写类调用必须带幂等键，防止重试造成重复副作用 |
| 超时与熔断 | 设置合理超时，连续失败达到阈值触发熔断，避免持续打一个已故障的 MCP Server |
| 降级策略 | 读类失败走本地缓存/兜底数据；写类失败进延迟重试队列或转人工 |
| 连接管理 | 连接池/单例复用（xinyu 已经做了这一点）+ 定期健康检查 |
| Schema 校验 | 调用前校验参数、调用后校验返回结构，防止"看似成功但数据不对"的静默错误 |
| 可观测性 | 每次调用打点（成功率/延迟/错误类型分布），是故障定位和 SLA 监控的基础 |

## 三、Harness 层面是怎么处理的

**Claude Code**：MCP 是 Tool Layer 的一部分，工具调用失败时，错误信息会被当作"工具执行结果"原样回填进 Agentic Loop 的上下文里，**模型自己看着错误决定下一步**（换个参数重试、换个工具、或者告诉用户做不了）——这是标准 ReAct 的自愈机制，Harness 本身不做自动重试判断，重试的"决策权"在模型手里。

**自建 LangGraph Harness**：MCP Client Pool 的调用结果同样先过 Error Classifier，可复用整套异常处理链路——

```
MCP调用超时/5xx  → Retry Controller 指数退避重试
MCP参数校验失败  → 错误回填给LLM要求自纠重新组装参数（限制自纠次数）
连续失败达阈值   → Circuit Breaker打开熔断
                  → 有降级路径就走降级（比如查不到最新关系等级，退化用批处理时缓存的旧等级）
                  → 没有就返回MCP_FAILED终止本次调用
```

**三者对比一句话**：xinyu 目前是"分类记录+批处理尽力而为"，偏简单；业内成熟实践是"重试+幂等+熔断+降级+可观测性"全套；Harness 理论架构（Claude Code的模型自愈 + 自建Harness的Retry/Circuit Breaker）提供了更完整的参考模型——这条链正好可以在面试里作为"如果让我优化 xinyu 的 MCP 容错，我会怎么做"的展开素材，比如给 MCP 调用也接入 Error Classifier + Circuit Breaker，读类工具失败时增加缓存兜底。
