# 场景题：记忆没有召回是怎么处理的？

## 一句话答案

要先分清"记忆没有召回"到底属于哪种场景——新用户天然没记忆（常态，不是故障）、记忆服务故障导致暂时性为空（有文档支撑，走降级兜底）、召回了但不相关/太旧（召回质量问题，走置信度衰减优化）——三种场景处理方式完全不同，不能混为一谈。配套图示：`diagrams/05-记忆三层架构图.puml`（架构图/组件图，展示三层记忆为什么能各自独立为空不阻塞彼此）、`diagrams/04-MCP调用与空结果处理流程图.puml`（流程图，"调用失败"与"调用成功但为空"两条分支）。

## 一、xinyu 项目里"记忆没有召回"的真实处理（分场景说）

先说清楚：xinyu 的文档里**没有一个专门叫"空召回处理"的章节**，下面分三种场景，标清楚哪些是文档原文、哪些是基于架构推导的。

### 场景一：新用户/新关系，记忆本来就是空的——这不是故障，是常态

这个场景文档没有专门讲，但可以从已确认的架构反推出来：三层记忆（短期40轮原文 / 长期记忆TopK / 用户画像）是**各自独立通过 MCP 读取、独立注入 Prompt 不同标签段**（`06-记忆系统设计.md`：Agent 通过 MCP 并行读取三者）。新用户第一次对话时，这三者天然都是空的，架构上应该是"某一层为空不影响其他层正常拼装 Prompt"——AI 依然能正常回复，只是没有"记得你"的效果，这本来就是 Lv0 陌生阶段的预期体验。

**如果被追问"具体代码怎么判断空值、Prompt模板怎么处理空标签"**：诚实说"文档里没写这个细节，这属于工程实现层面，合理推测是模板对空值做了省略处理，没有验证过具体代码"——比瞎编一个函数名安全得多。

### 场景二：记忆服务故障导致的"暂时性空"——这个有文档原文支撑

`06-记忆系统设计.md` 明确写了：

> 短期内无感知。短期记忆（40 轮原文）和用户画像仍正常工作，只是长期记忆不再更新。RocketMQ 消息持久化等待重新消费，XXL-Job 定时重试兜底。超过 40 轮的老用户在窗口滑过后，AI 可能"忘记"超出部分——这是唯一的实质影响。

这其实是同一个"三层独立、互不阻塞"的架构特性，只不过触发原因从"新用户天然没数据"变成了"PolarDB/RocketMQ 故障拿不到数据"——**处理方式是一致的：某一层拿不到就让它空着，不阻塞整体对话，靠 XXL-Job 每 10 分钟扫描重试兜底**。

### 场景三：真正意义上的"召回质量差"（不是空，是不准）

`07-记忆系统面试题精选.md` 提到的优化方向是应对这个问题：引入**置信度衰减**（按写入时间戳加权，近期事实权重高、旧事实降权），或引入 TTL（超过 N 个月的事实自动降级为"历史信息"标签）。这不完全是"召回为空"，而是"召回了但不够相关/太旧"，是同一话题下值得一起提的优化方向。

## 二、业内通用怎么处理 RAG/记忆检索为空

| 处理点 | 做法 |
|--------|------|
| 区分"真空"和"查询失败" | 检索服务本身报错返回的空 ≠ 语料库里真的没有匹配项，前者要重试/告警，后者才是合法的空结果，两者不能都当成"没有记忆"处理 |
| 相关性阈值过滤 | 即使 TopK 有结果，相似度分数低于阈值也要视为"无有效召回"，硬塞进 Prompt 反而会误导模型 |
| 提示词层面防幻觉 | 明确要求模型"没有相关记忆时按第一次交流处理，不要编造用户没说过的事"，这是防止空召回被模型"脑补"的关键一道防线 |
| 冷启动兜底 | 新用户/新会话可以用其他数据源兜底（产品通用引导语、注册时填的基础信息），而不是让 Prompt 里出现空标签 |

## 三、Harness 层面怎么处理

这里要区分两种性质完全不同的东西：**"MCP 调用失败"**和**"MCP 调用成功但返回空"**，很多人容易把这两个混为一谈，但在 Harness 里应该走完全不同的分支：

```
MCP调用失败（超时/5xx/连接断开）
   → 走 Error Classifier 的 MCP_FAILED 路径 → 重试 / 熔断（见04-MCP调用异常处理机制.md）

MCP调用成功但返回空结果（比如查到的记忆列表是[]）
   → 这不是异常，是合法状态
   → Prompt组装层要显式判断：该段落为空时做省略/替换成"暂无相关记忆"的占位说明
   → 绝不能把一个空数组直接序列化塞进Prompt，留下畸形的空标签让模型自己瞎猜
```

再往上一层，Harness 可以加一个**监控维度**：统计"某个 MCP 工具返回空结果的比例"，如果某个理论上大概率有数据的场景（比如老用户查长期记忆）空召回比例异常升高，这本身就是一个报警信号，说明可能是记忆服务真的出问题了，而不是用户真的没数据——这是把"空"和"故障"关联起来做可观测性的思路，而不是各管各的。

## 面试话术小结

> "记忆没有召回"不是一个单一问题，我会先反问/明确是哪种场景：新用户天然没数据（正常现象，不需要特殊处理，架构上三层记忆独立注入本身就能容忍）、服务故障导致的暂时性空（xinyu 有 XXL-Job 定时重试兜底）、还是召回了但不准（需要置信度衰减或 TTL 优化）。这三种场景背后的应对策略完全不同，笼统地问"怎么处理空召回"往往问的是这三个里的某一个，分清楚场景本身就是解决问题的第一步。
