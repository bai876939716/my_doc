# 场景题：Agent 生成 SQL 有哪些需要注意的问题？（精简版）

## 一句话答案

风险分三类——**安全类**（危险语句/越权/提示词注入）、**正确性类**（schema幻觉/隐式业务规则遗漏）、**性能类**（全表扫描/无LIMIT）。核心思路：凡是关乎数据安全边界的约束，不能只靠提示词写清楚，要在**执行层强制校验/注入**，不依赖模型自觉。

## 安全类

| 问题 | 解决方案 |
|------|---------|
| 危险语句：DDL、无WHERE的UPDATE/DELETE、多语句拼接 | AST静态解析（不用正则黑名单），只放行SELECT，检测多语句和WHERE缺失，命中直接拒绝 |
| 越权访问敏感字段 / 跨租户越权 | Schema白名单只暴露授权表字段；执行层**强制**注入租户/权限过滤条件，不管模型有没有写 |
| 执行账号权限过大 | 用只读账号 + 只读副本执行，物理层面杜绝写操作/DDL |
| 提示词注入篡改查询意图 | 区分"用户输入"与"系统指令"；查询结果里混入的指令性文本不当指令执行 |

## 正确性类

| 问题 | 解决方案 |
|------|---------|
| Schema幻觉（编造不存在的表/字段） | 把真实DDL/表结构作为上下文喂给模型，不靠训练记忆猜 |
| 自然语言歧义（"最近""活跃"等模糊表述） | 给出明确默认口径并在结果里注明，或主动追问澄清 |
| 隐式业务规则被漏掉（软删除标记、数据权限范围） | 执行层强制注入这些过滤条件，用户自然语言里不会主动提，不能靠模型自觉加 |
| 数据库方言差异 | 生成时明确指定目标数据库方言 |
| 复杂JOIN/子查询正确率低 | Few-shot提供历史优秀SQL样例；建评估集，用**执行结果**而非SQL文本比对 |

## 性能类

| 问题 | 解决方案 |
|------|---------|
| 无LIMIT导致海量数据返回 | 执行层自动追加/改写LIMIT上限 |
| 未走索引、全表扫描 | 执行前跑EXPLAIN预估扫描行数，超阈值转人工确认或拒绝 |
| 大表复杂JOIN拖垮数据库 | 设置查询超时，超时自动终止 |

---

## 兜底原则

- **AST解析**代替正则黑名单做语句类型/表字段校验
- **执行层强制注入**隔离条件（不信任模型输出）
- **只读账号+只读副本+超时+行数上限**做物理兜底
- **参数化执行**：具体值走参数绑定，不拼接进SQL文本
- **高风险查询转人工审批**，全程审计留痕

## 面试话术小结

> Agent生成SQL最大的风险不是语法写错，而是模型生成的SQL语法正确但缺少用户没明说、业务上必须有的约束（租户隔离/软删除）——这类规则必须在执行层强制注入，不能指望提示词。安全上用AST解析代替正则黑名单，配合只读账号和只读副本兜底；性能和准确率上用schema白名单+few-shot降低幻觉，建评估集用执行结果比对生成质量。
