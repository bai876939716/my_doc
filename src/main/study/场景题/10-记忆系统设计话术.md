# 记忆系统设计 — 面试话术整理

> 基于你自己对项目记忆设计的真实描述整理成面试话术，分三部分：① 可以直接背的完整话术（开场用）② 拆解成"设计动机→分层→写入→存储→召回→亮点"六段，方便面试官追问到哪一段就展开哪一段 ③ 对照业内记忆设计的8个维度做自查，诚实标注哪些覆盖了、哪些可以说是"优化方向"（不要在没做的地方硬编细节，被追问会露馅）。

---

## 一、可以直接背的完整话术（开场陈述）

> 记忆设计首先要想清楚几个强约束：一是噪声问题，塞给模型的上下文太多反而会干扰它的判断；二是成本问题，注入的内容越多调用成本越高；三是上下文溢出问题，历史内容会不断累积，窗口再大也会溢出。所以记忆管理的核心目标就是把最重要、最精简、最相关的信息传给大模型，而不是"能塞多少塞多少"。
>
> 基于这个目标，我们设计了三层记忆架构：**短期记忆**是最近40轮对话原文，直接存 PostgreSQL；**长期记忆**是聊天内容阶段性压缩提炼出的事实，存在 PolarDB 向量库里，底层是基于 mem0 实现的；**用户画像**是阶段性提取的用户特征，存 PolarDB 的 KV 结构，JSON 格式。
>
> 写入策略上，每轮对话实时写入 PostgreSQL，累积到一定轮次后通过 RocketMQ 发一个异步事件触发记忆总结，记忆服务消费事件后把这批原文打包调 PolarDB 的 Memory API，内部用 LLM 做事实提取，对每条新事实做 ADD/UPDATE/NONE/DELETE 四元决策，这是第一层去重。为了防止长期记忆无限膨胀，还有第二层去重——总结积累到5次后会重新压缩合并成一次总结，用一张关系表维护和向量库 ID 的映射。事实写完之后再异步触发一次用户画像更新。
>
> 召回的时候，用户每次发消息，Agent 会并行拉三层数据——PG 里的原文对话、向量检索出的 Top5 相关事实、以及用户画像，拼成 Prompt 一起注入给 LLM。
>
> 除了这套主流程，我们还专门解决了两个问题：一个是记忆污染——不同场景、不同人设之间的记忆必须隔离，不能串；另一个是记忆写入的可靠性——总结失败时降级先写原文，打标记，再用定时任务扫描重试，保证最终一致。

## 二、拆解成六段，按追问深度展开

### 第1段：设计动机（为什么这么设计，不是"我们随便定的"）

三个强约束——**噪声**（信息太多干扰模型判断）、**成本**（塞得越多越贵）、**上下文溢出**（历史内容持续累积迟早超限）。记忆管理的目标是"精简、重要、相关"，不是"全量塞入"。

### 第2段：为什么是这三层（分层依据）

业内经典范式是短时记忆/工作记忆/长期记忆三层。我们按围绕上面三个约束的思路，定义了适合自己场景的三层：短期记忆（最近40轮原文）解决"当前对话连贯性"；长期记忆（压缩事实）解决"跨会话的持久信息，同时控制体积"；用户画像解决"稳定的、每次都相关、不需要检索判断相关性的特征"。

**如果被追问"为什么没有单独做工作记忆（任务状态/中间结果）"**：我们的场景是对话式交互为主，不是复杂的多步骤任务执行型 Agent，暂时没有强需求要跟踪任务状态机和中间结果快照，这是按场景做的取舍，不是遗漏。

### 第3段：写入策略（什么时候存、存什么、怎么去重）

```
每轮对话 → 实时写入PostgreSQL（短期记忆，原文）
累积到N轮 → RocketMQ异步事件 → 记忆服务消费
         → 打包调PolarDB Memory API（底层mem0实现）
         → LLM做事实提取 → 每条新事实ADD/UPDATE/NONE/DELETE（第一层去重）
积累到5次总结 → 重新压缩合并成一次（第二层去重，防止无限膨胀）
             → 用关系表维护向量库ID映射
事实写完 → 异步触发一次用户画像更新
```

**关键点**：两层去重设计——第一层是单次总结内部的事实级去重（mem0 的 ADD/UPDATE/NONE/DELETE），第二层是跨多次总结的归并去重（防止"总结的总结"无限堆叠）。

### 第4段：存储设计（为什么每层用不同的存储）

| 层级 | 存储 | 为什么选这个 |
|------|------|-------------|
| 短期记忆 | PostgreSQL，存原文 | 结构化、按时间顺序查询、不需要压缩，保留原文保真度最高 |
| 长期记忆 | PolarDB 向量库（mem0实现） | 语义检索场景，需要按相关性做向量相似度召回 |
| 用户画像 | PolarDB KV/JSON | 结构相对固定，每次都要全量读取，不需要走相似度检索 |

**一句话**：不是所有记忆都要塞向量库——结构化、每次都相关的信息（画像）用 KV，需要按相关性筛选的用向量检索，原文这种要保真度的直接存关系型数据库。

### 第5段：召回与注入

用户每次发消息，**并行**拉取三层数据——PG 原文、向量 Top5、用户画像——拼成 Prompt 一起注入 LLM。强调"并行"是因为三次数据获取如果串行会显著增加延迟，这是一个具体的工程优化点。

### 第6段：两个额外解决的问题（最能体现深度，建议主动提）

**记忆污染**：不同场景、不同人设的记忆必须隔离，不能互相串（比如同一个用户和不同 AI 角色的记忆要分开，不能角色A"记得"角色B专属的对话内容）。做法是记忆命名空间按场景/人设维度隔离。

**写入可靠性**：记忆总结这个链路涉及 LLM 调用，可能失败。降级策略是——总结失败时先降级写入原文（不做提炼），打上标记，再用定时任务（job）扫描这些被标记的记录做重试补跑，保证记忆写入最终一致，不会因为某次 LLM 调用失败就永久丢失这段记忆。

## 三、对照业内记忆设计 8 个维度自查（加分项：证明你知道完整设计空间在哪）

| 维度 | 我们做了什么 | 诚实标注 |
|------|-------------|---------|
| 1. 记忆分层 | 短期/长期/画像三层，覆盖了短时记忆和长期记忆 | 没有单独做"工作记忆"（任务状态/中间结果），按场景取舍，对话式交互暂无强需求 |
| 2. 写入策略 | 实时写入+批量触发总结+两层去重+归属靠用户+角色/场景维度隔离 | 记忆时效性（比如用户地址、订单状态这类会过期的信息）目前**没有专门的过期标记机制**，是可以优化的方向 |
| 3. 检索策略 | 向量相似度检索Top5 | 目前主要是纯向量检索，**没有做关键词检索/元数据过滤的混合检索，也没有二次rerank**——纯向量检索容易召回语义相似但实际不相关的内容，这是已知的可优化点 |
| 4. Prompt注入 | 三层并行拼装注入 | 上下文窗口配额（系统提示/对话/记忆各占多少）以及**多条记忆互相矛盾时的冲突处理**，目前没有精细化的策略，可以说"这块比较依赖模型自己判断，还没有做显式的冲突消解逻辑" |
| 5. 遗忘/更新/删除 | ADD/UPDATE/DELETE四元决策已经覆盖了"更新旧信息"和"矛盾时删除旧记忆" | **没有基于时间的遗忘/衰减机制**（老记忆不会随时间自动降权或过期），**用户主动删除数据（合规场景）在向量库里怎么处理**目前没有明确讲到，这两点都是可以主动提及的优化方向 |
| 6. 安全与隐私 | 通过命名空间（用户+角色/场景维度）做了记忆隔离，避免跨场景/跨角色串用 | 没有提到**敏感信息脱敏/加密存储**、以及更严格的**跨用户访问权限校验**机制，如果被问到可以诚实说"目前主要靠命名空间隔离，没有做字段级脱敏" |
| 7. 可观测与调试 | （可结合项目里通用的execution_log/request_id体系提一句：每次记忆写入/召回的关键节点有日志） | **记忆专门的溯源（这条记忆是哪次对话生成的、这次为什么召回了它）和专门的召回质量评估机制**，如果没有做专门的评估集，建议诚实说"目前没有做记忆模块专门的效果评估，是可以补充的地方" |
| 8. 成本与性能 | 库存优先、批量处理等通用降本思路 | 记忆模块专门的**向量embedding调用成本、存储成本、高并发读写压力**方面，如果没有具体的量化数据或压测结果，不要编造具体数字，诚实说"没有针对记忆模块单独做过压测" |

**用法建议**：面试官如果问"记忆系统还有哪些可以优化的地方"，直接把上面"诚实标注"那一列拿出来讲——这比说"我们做得很完善"更让人信服，因为它证明你既懂完整的设计空间，又对自己项目的边界有清醒认知。

## 面试话术小结（收尾句）

> 我们的记忆设计核心是"用最小的、最相关的信息换取模型判断的准确性"，围绕噪声、成本、上下文溢出这三个约束展开。三层架构加两层去重解决了"存什么、怎么存不膨胀"的问题，并行召回加三层拼装解决了"怎么用"的问题，命名空间隔离和降级重试解决了"隔离"和"可靠性"这两个容易被忽视但很关键的工程问题。如果往下深挖，检索策略上的混合检索/rerank、遗忘机制、以及记忆模块专门的可观测性，是我认为这套设计目前还可以继续打磨的方向。
