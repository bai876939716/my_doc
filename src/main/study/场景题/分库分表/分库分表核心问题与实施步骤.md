# 分库分表核心问题与实施步骤

> 与 [订单分库分表设计.md](订单分库分表设计.md) 的关系：那份是"订单系统"这一个具体场景的面试话术；本文档是脱离具体业务的**通用方法论**——不管是订单、用户、商品还是账单表，做分库分表都要过一遍这十几个问题，再按标准步骤落地。两份可以配合看：具体场景遇到不会答的问题，回来这份找对应的通用解法。

## 一、要不要分：分库分表前必须想清楚的前提

分库分表是**成本极高、一旦上线很难回退**的架构改造，不是"数据量大了就该分"。落地前先过滤一遍：

- 存储本身不是瓶颈：现代 SSD + 大内存下，单表千万级数据依然能正常查询，别被"单表500万必分"的教条吓到；
- 优先级顺序：**SQL/索引优化 → 读写分离 → 硬件升级（加内存/换SSD）→ 缓存 → 分库分表**，分库分表是成本最高的最后手段；
- 真正该分的两个信号：① **连接数瓶颈**——高并发下单库连接池被打爆；② **运维 DDL 瓶颈**——千万级大表加字段/建索引锁表时间长到影响业务。只出现"数据量大但查询依然很快、运维也没出问题"，不构成分库分表的理由。

判断清楚"确实要分"之后，才进入下面的问题清单。

## 二、分库分表需要考虑的核心问题

### 2.1 分片键怎么选

**问题**：分片键（Sharding Key）选错，后面所有方案都要推倒重来——选错的典型表现是"选完之后发现最高频的查询场景恰好没法用这个字段路由"。

**怎么解决**：
- 原则：**选业务里查询频率最高、并发压力最大的那个查询维度**作为分片键，而不是选"看起来最唯一"的字段（比如订单场景选 `user_id` 而不是 `order_id` 自身，因为"用户查自己的单"远比"随机查一个订单"频繁）；
- 分片键要具备较高的**离散度**，避免某个取值集中了大量数据（比如按"省份"分片，人口大省数据量会远超小省，天然倾斜）；
- 分片键一旦选定，尽量伴随该表终生，中途更换分片键等同于重新做一次分库分表；
- 允许"次要维度用异构索引表/ES 兜底"，不要因为一个字段满足不了所有查询就否定整个分片方案（见 2.4）。

### 2.2 分片路由算法怎么选

**问题**：数据落到哪个库哪个表，靠什么算法算出来，直接决定了后续扩容难度和是否会有热点。

**怎么解决**，三种主流算法各自的取舍：

| 算法 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **范围分片**（按 ID/时间区间） | 扩容简单（加一个新区间即可）、天然支持范围查询 | 容易产生热点（新数据全部写入最新分片） | 时间序列数据、日志类表 |
| **哈希取模**（`hash(key) % N`） | 数据分布均匀，无明显热点 | **扩容是灾难**——分片数从 16 变 32，几乎所有数据的取模结果都会变，需要整体数据重新迁移 | 绝大多数 OLTP 业务表（订单、用户） |
| **一致性哈希** | 扩容时只影响相邻节点的数据迁移，不需要全量重算 | 实现复杂度高，需要额外维护虚拟节点防止分布不均 | 分片数变动频繁、追求平滑扩容的场景 |

工程实践中最常见的折衷是：**取模分片 + 提前规划好足够的分片数（比如一次到位分够 64/128 张表，分布在较少的物理库上）**，用"表内取模数固定不变、只调整表到库的物理分布"来规避取模算法扩容难的问题（见 2.10）。

### 2.3 全局唯一主键怎么生成

**问题**：分表后每张物理表各自的数据库自增 ID 会冲突（每张表都有一个 id=1），不能再用数据库自增主键。

**怎么解决**：
- **禁止用数据库自增 ID**；
- 常见方案对比：

| 方案 | 优点 | 缺点 |
|------|------|------|
| UUID | 实现简单，无需依赖任何组件 | 无序，作为主键会导致 B+树频繁分裂，索引性能差；不携带业务含义 |
| 雪花算法（Snowflake） | 趋势递增、性能高、不依赖存储 | **依赖机器时钟**，时钟回拨会导致 ID 重复或倒退 |
| 号段模式（美团 Leaf / 百度 UidGenerator） | 提前批量获取一段 ID 缓存在内存，性能极高，不受时钟回拨影响，ID 趋势递增 | 依赖一个中心化的号段服务，该服务本身要做高可用 |

- 金融、电商这类对 ID 严谨性要求高的业务，推荐号段模式（如 Leaf），规避雪花算法的时钟回拨风险。

### 2.4 非分片键查询 / 多维度查询怎么办

**问题**：按 A 字段分片后，用 B 字段查询（比如按用户ID分片，商家要按商家ID查）就没有路由依据，只能全库广播扫描，性能崩盘。

**怎么解决**，三套方案按场景选：
1. **异构索引表（双写冗余）**：为高频的第二查询维度单独建一套按该维度分片的库表，主库写入成功后异步同步过去，代价是要处理好两份数据的一致性（见 2.8）；
2. **ID 基因法**：把主分片键的哈希值编码进主键/业务单号里，这样即使拿到的是订单号，也能从号里直接解出分片位置，不用二次查询；只解决"单点精准查询"，解决不了批量多维筛选；
3. **MySQL + 搜索引擎（ES）混合架构**：把需要多字段任意组合筛选的复杂查询整体迁移到 ES，MySQL 只承载核心交易的增删改和精准点查，靠 Canal/MQ 做增量数据同步。

三套方案不是互斥的，实际系统里往往是"核心链路用①②兜底精准查询，复杂检索交给③"组合使用（可参考 [订单分库分表设计.md](订单分库分表设计.md) 的完整案例）。

### 2.5 跨分片 JOIN 怎么办

**问题**：两张表分到了不同的库甚至不同的物理机器上，数据库层面已经不支持跨库 JOIN。

**怎么解决**：
- **字段冗余**：把 JOIN 时需要用到的少量字段直接冗余一份存到主表里（比如订单表冗余商品名称，不用再关联商品表），空间换时间，是最常用也最简单的手段；
- **全局表/广播表**：像"省份字典表"这类数据量小、几乎不变、所有分片都需要关联查询的表，在每个分片库里都完整存一份，查询时各自在本地 JOIN，无需跨库；
- **应用层组装**：分两次查询——先查主表拿到关联字段的值集合，再用这批值去关联表查询，最后在应用代码里内存拼接，牺牲一点性能换取实现的确定性。

### 2.6 跨分片分页与排序怎么办

**问题**：`ORDER BY create_time LIMIT 100000, 20` 这类深度分页在单库单表下已经有性能问题，分片后每个分片都要各自排序、拉一批数据到应用层再二次归并排序，代价更高。

**怎么解决**：
- **业务规避**：产品层面禁止大页码跳页，只提供"上一页/下一页"，从产品设计上避免深度分页场景；
- **游标分页**：用 `id > 上次最后一条的id LIMIT N` 替代 `OFFSET`，配合索引可以规避每次都要扫描并丢弃前面的行，但排序字段要保证跨分片单调（通常要求排序字段本身携带时间或分片路由信息）；
- **复杂排序场景直接走 ES**：ES 天生支持跨分片的全局排序和分页，把这类场景从 MySQL 分片上剥离出去是最彻底的解法（同 2.4 方案三）。

### 2.7 跨分片聚合统计怎么办

**问题**：`COUNT(*)`、`SUM(amount)`、`GROUP BY` 这类聚合，单库能一条 SQL 搞定，分片后必须先在每个分片各自算一遍局部结果，再在应用层做二次汇总，且无法利用数据库本身的聚合优化。

**怎么解决**：
- **实时性要求不高**的报表类统计：用定时任务/离线计算把汇总结果预先算好写进一张汇总表（如按天/按用户维度的统计快照表），查询直接读汇总表，不现算；
- **准实时**统计：走 2.4 方案三的 ES/数仓链路，用 ES 的聚合能力（Aggregation）或者同步一份数据到 ClickHouse 之类的 OLAP 引擎做实时聚合；
- **确实要跨分片实时精确计算**（如账户余额扣减前的强校验）：只能应用层各分片并行查询后汇总，同时要评估这类查询能不能加缓存降低调用频率。

### 2.8 分布式事务 / 跨库数据一致性怎么办

**问题**：一次业务操作涉及多个分片（甚至多个异构库）的写入时，传统的单库事务不再生效，任何一步失败都可能导致数据不一致。

**怎么解决**，按一致性要求分级选择：
- **强一致（极少用）**：2PC/XA 事务、Seata AT 模式，性能损耗大，吞吐量低，只在强金融合规场景考虑；
- **最终一致（互联网主流选型）**：
  - **本地消息表 + MQ**：业务写库和写消息表在同一个本地事务里保证原子性，再由独立任务轮询消息表投递到 MQ，消费方处理失败靠 MQ 重试机制兜底；
  - **事务消息（如 RocketMQ 事务消息）**：用半消息机制保证"业务写库"和"消息投递"这两件事要么都成功要么都不发生，比本地消息表少一次轮询延迟；
  - **定时对账补偿**：无论用哪种方案，都需要一个兜底的定时对账任务，全量比对多个库之间的数据差异，发现不一致自动触发补偿重试，这是最终一致性方案里不可省略的最后一道防线。

### 2.9 数据倾斜 / 热点分片怎么办

**问题**：即使分片算法本身均匀，业务数据本身可能不均匀——比如按商家ID分片，头部大商家的订单量可能是普通商家的几百倍，导致这一个分片的数据量和访问压力远超其他分片。

**怎么解决**：
- 分片键设计阶段就要评估数据分布，避免选择天然倾斜度高的字段（如省份、性别）作为主分片键；
- 对已知的"超级大客户/超级热点"，可以做特殊路由——单独给这类大 Key 分配独立的分片资源，不和普通数据混在同一分片池里争抢；
- 结合缓存削峰：热点数据的读请求优先命中缓存，减少直接打到热点分片数据库的压力。

### 2.10 二次扩容 / 缩容怎么办

**问题**：业务量持续增长，最初规划的分片数量不够用了，怎么加分片、加库，同时不影响线上业务。

**怎么解决**：
- **不支持任意数量扩容**，主流做法是**成倍扩容**（比如从 16 库扩到 32 库），倍数扩容配合取模算法可以保证"旧分片里的数据，扩容后只会拆分到两个新分片里"，迁移范围可控，不是全量重新洗牌；
- 具体迁移流程见第三部分"实施步骤"里的数据迁移小节；
- 如果业务发展初期就能预判增长曲线，更省事的做法是**一次性规划出远超当前需求的表数量**（比如分够 64/128 张表），但只用少量物理库承载，后续物理层面扩容时只需要把部分表迁移到新库上，逻辑分片规则完全不变，彻底规避取模算法难扩容的问题。

### 2.11 中间件怎么选（客户端模式 vs 代理模式）

**问题**：分片路由这套逻辑总要有个地方实现，是让应用自己算，还是交给独立组件。

**怎么解决**，两种主流形态对比：

| 模式 | 代表产品 | 优点 | 缺点 |
|------|----------|------|------|
| 客户端模式（Client） | ShardingSphere-JDBC | 无额外网络跳转，性能损耗小；不用额外运维一层代理 | 和应用强绑定，多语言团队要各自实现/引入 SDK；升级路由规则要跟着应用一起发版 |
| 代理模式（Proxy） | MyCat、ShardingSphere-Proxy | 对应用完全透明，像访问单库一样访问代理；语言无关，多个业务系统可共用 | 多一跳网络开销；代理层本身要做高可用，否则变成单点瓶颈 |

- 团队技术栈单一（都用 Java）且追求极致性能：优先 Client 模式；
- 多语言异构系统、希望数据库层对业务完全透明：优先 Proxy 模式。

### 2.12 运维复杂度上升怎么应对

**问题**：分库分表后，原本"一个库"的运维工作变成了"N 个库"的运维工作，SQL 语法支持、备份、监控全部复杂化。

**怎么解决**：
- SQL 兼容性：中间件对跨库聚合、跨库 JOIN、部分窗口函数等语法支持有限，上线前要梳理业务里所有 SQL，逐条验证中间件是否支持，不支持的提前想好改造方案（拆分成多次查询、迁移到应用层处理）；
- 备份：从"备份一个库"变成"要保证 N 个分片备份点在时间上尽量对齐"，否则灾难恢复时各分片数据不在同一个时间切面上，会引发新的数据不一致；
- 监控：需要针对**每个分片**单独监控慢查询、连接数、磁盘使用率，同时监控**分片间的数据量/流量均衡度**，尽早发现新的热点分片。

## 三、实施步骤（从评估到上线的完整落地路径）

分库分表是一次不可轻易回滚的架构升级，落地要按下面的顺序走完整闭环，任何一步偷工减料都可能在上线后放大成事故。

### 第 1 步：容量评估与需求分析

- 摸清现状：当前数据量、QPS/TPS、慢查询与锁等待情况、连接数使用率；
- 预测未来（通常按 3~5 年）的数据增长曲线，倒推出需要的分片数量，避免刚上线不久又要扩容；
- 梳理业务里所有查询场景（不只是主链路，运营后台、报表、对账这些低频但存在的查询也要列出来），为后面"分片键怎么选""要不要建异构索引表"提供依据。

### 第 2 步：技术方案设计

- 确定分片键与分片算法（对照 2.1、2.2）；
- 确定全局主键生成方案（对照 2.3）；
- 针对梳理出的非主维度查询场景，确定是走异构索引表、ID基因法还是 ES（对照 2.4）；
- 确定分布式事务/一致性方案（对照 2.8）；
- 确定中间件选型（对照 2.11）。

### 第 3 步：中间件选型与环境搭建

- 完成中间件的选型对比（性能测试 + SQL 兼容性测试），落地到具体产品版本；
- 在测试环境搭建好目标分片数量的库表结构，跑通基础的分片路由。

### 第 4 步：新分片库表设计与建表

- 按照分片算法建好所有物理库表；
- 全局表（广播表）、异构索引表这类配套表结构一并建好；
- 建表阶段就把索引、字段类型和原表对齐，避免迁移后再发现结构不一致。

### 第 5 步：数据迁移方案设计与双写改造

- 应用代码改造为**同时写旧库和新分片库（双写）**，双写期间以旧库为准对外提供服务，新库只是同步写入验证；
- 全量迁移：把旧库存量历史数据一次性同步到新分片库（离线批量任务）；
- 增量追平：全量迁移期间产生的新增/修改数据，通过监听旧库 binlog（如 Canal）持续同步到新库，追平全量迁移和当前时刻之间的时间差。

### 第 6 步：数据校验

- 全量比对新旧库的数据量、关键字段是否一致（行数对比 + 抽样/全量 checksum 对比）；
- 发现差异定位是同步延迟导致的正常滞后，还是同步逻辑本身有 bug，逐一修复直至数据完全对齐。

### 第 7 步：灰度切流

- **先切读**：小流量把部分读请求路由到新分片库，观察结果是否和旧库一致、性能是否符合预期；
- **再切写**：读流量验证稳定后，逐步把写流量切到新分片库，此阶段仍保留双写（新库为主、旧库同步）作为回滚兜底；
- **全量切换**：读写流量全部稳定运行在新分片库一段时间（通常以周为单位观察）后，停止向旧库双写。

### 第 8 步：压测与性能验证

- 在灰度切流的同时或切流完成后，用生产等量或更高的流量做压测，验证分片后的连接数、QPS、慢查询是否达到设计目标；
- 重点验证 2.6、2.7 提到的跨分片分页/聚合场景在真实数据量下的表现，这类场景最容易在压测阶段暴露设计缺陷。

### 第 9 步：制定回滚预案

- 在切流的每个阶段之前，都要准备好"如果出问题，怎么在多长时间内切回旧库"的具体操作手册，而不是等出事故了再临时想办法；
- 双写阶段本身就是天然的回滚安全网，回滚预案的关键是明确"什么信号触发回滚""回滚指令谁来下""回滚后数据怎么对齐"。

### 第 10 步：旧库下线与长期运维

- 确认新分片库稳定运行足够长时间（通常一到两个业务周期，覆盖到月末结算、大促等特殊场景）后，才正式下线旧库，且下线前保留数据备份，不要立即物理删除；
- 建立分片维度的常态化监控（对照 2.12），定期评估各分片的数据量/流量是否均衡，为后续再次扩容提前预警。

## 四、面试精简答题模板

> 分库分表不是"数据量大了就上"，而是遇到连接数瓶颈或运维DDL瓶颈时的最后手段，落地要闭环考虑十几个问题：
>
> 1. **分片设计**：先按最高频查询场景选分片键，用取模算法保证分布均匀，配合提前规划好足够分片数（宽表窄库）规避后续扩容难题；
> 2. **主键与查询**：全局唯一ID用号段模式（美团Leaf）替代自增ID和雪花算法，规避时钟回拨风险；非分片键的查询靠异构索引表、ID基因法、ES三套方案分层解决；
> 3. **跨库难题**：JOIN靠字段冗余/全局表/应用层组装解决；分页排序靠游标分页或ES兜底；聚合统计靠预计算汇总表或OLAP引擎；
> 4. **一致性与扩容**：跨库事务采用最终一致性（事务消息+定时对账），拒绝重量级2PC；扩容采用倍数扩容+全量迁移+增量追平+数据校验+灰度切流的标准流程，全程业务无感知；
> 5. **落地节奏**：从容量评估、方案设计、双写改造、数据校验，到灰度切流、压测验证、回滚预案、旧库下线，每一步都要有明确的验证标准和回滚手段，不能一次性硬切。
