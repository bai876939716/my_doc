# Redis 与数据库一致性详解（面试专题）

配套图：`diagrams/06-redis-db-consistency.puml`（正向扣减链路的可靠同步与补偿、逆向回滚链路的幂等回滚）

## 核心结论

Redis 与数据库之间不存在真正的强一致性，秒杀场景的标准做法是接受"短暂不一致"，靠 **可靠消息 + 幂等设计 + 状态机 + 定时对账补偿** 实现**最终一致性**（BASE 理论，CAP 中偏向 AP）。强一致性方案（2PC/TCC/Saga）理论上可行，但需要同步等待多方确认，会显著拖慢响应时间，与秒杀"极致性能优先"的目标冲突，业界基本不采用。

---

## 一、通用缓存一致性模式（基础题）

大多数业务场景是"数据库为主，缓存为辅"，标准模式是 **Cache Aside（旁路缓存）**：

- 读：先读缓存，未命中则读数据库，并把结果回种缓存。
- 写：**先更新数据库，再删除缓存**（不是更新缓存）。

### 为什么删缓存而不是更新缓存

删除是懒加载思路，等下次真正被读到时再重新计算/回种；如果写操作频繁，每次都同步更新缓存是无谓的计算浪费，而且并发写时后写的可能被先写的覆盖，删除+懒加载能避免这种覆盖问题。

### 为什么是"先更新数据库，再删缓存"

反例——先删缓存再更新数据库：

```
线程A：删除缓存
线程B：读缓存miss，读数据库拿到旧值，写入缓存
线程A：更新数据库为新值
结果：缓存里永久是旧值，直到下一次写操作
```

"先更新数据库再删缓存"仍有一个理论上的极小概率窗口：

```
线程A：读缓存miss，读数据库拿到旧值，但还没来得及写入缓存
线程B：更新数据库为新值，删除缓存（此时缓存本来是空的，删除是空操作）
线程A：把（读到的）旧值写入缓存
结果：缓存又变成了旧值
```

这个窗口要求"读操作比写操作还慢"，正常场景下发生概率极低。彻底解决可以用：

- **延迟双删**：写请求执行时先删一次缓存 → 更新数据库 → sleep 一段时间（大于一次典型读请求耗时）→ 再删一次缓存，把窗口期内可能写脏的缓存兜底清掉。
- **订阅 binlog 异步同步（canal/databus 方案）**：业务代码只操作数据库，不直接操作缓存；canal 伪装成 MySQL 从库订阅 binlog，把数据变更事件发到 MQ，由消费者按数据库真实的变更顺序去删除/更新缓存。优点是业务代码完全不用管缓存操作、天然保证顺序性；缺点是有一定延迟、架构更复杂。

这套模式讲的是"数据库为主"场景，但秒杀库存场景是反过来的，见下一节。

## 二、秒杀场景：Redis 先写，数据库后写（架构反转）

秒杀库存承受不了直接打数据库的并发量，所以架构上把 Redis 作为**第一写入点**（承担高并发实时扣减判断），数据库作为**异步兜底和最终落地点**。一致性问题因此拆成两个方向。

### 方向一：正向扣减链路——Redis 扣成功了，数据库有没有跟上

链路：`Redis Lua 原子扣减成功 → 投递 MQ 消息 → 消费者异步扣数据库、建订单`。

风险点：消息丢失、消费者处理失败、消费者宕机，都可能导致"Redis 库存已经减了，但数据库没跟上"，出现幽灵库存（有名额被预扣，却没有对应订单）。

解决方案：

1. **MQ 可靠投递**：生产者开启发送确认（或使用事务消息），保证消息不会在发送阶段丢失。
2. **消费者手动 ACK**：只有业务处理成功（数据库事务提交成功）才确认消费，处理失败不 ACK，触发消息重新投递。
3. **重试 + 死信队列**：重试超过最大次数仍失败，转入死信队列，避免消息被无限重试阻塞后续消息。
4. **死信补偿**：定时任务扫描死信队列，对处理彻底失败的消息，把对应的 Redis 预扣库存和用户限购标记回滚，把名额还给其他人。
5. **数据库扣减本身失败的场景**：（一般发生在 Redis 和 DB 已存在偏差时）同样需要回滚已预扣的 Redis 库存，并让用户看到真实的失败结果，而不是让用户误以为抢到了。

### 方向二：逆向回滚链路——订单取消/超时了，Redis 库存有没有跟着还回去

订单取消需要同时回滚三样东西：数据库库存、Redis 库存、用户限购标记。这三步本身不是一个原子操作。做法：

1. **数据库侧用本地事务**：把"订单状态改为已取消"和"数据库库存加回"放在同一个事务里，保证这两步本身是原子的。
2. **状态机校验**：更新前用乐观锁/CAS 校验订单当前状态确实是"待支付"，防止和支付回调并发时把已支付订单误判为超时取消。
3. **事务提交后异步通知 Redis 回滚**：发一条携带订单 ID 的"库存回滚事件"到 MQ，由消费者执行 Redis 侧回滚（库存加回、删除限购标记）。
4. **幂等处理**：Redis 侧用订单 ID 记录"是否已经处理过这次回滚"，防止消息重复消费导致库存被多次加回——这种重复加回比超卖更隐蔽，因为它会让库存数字变得比实际更大，不会立刻报错，但会破坏数据的真实性。

### 方向三：定时对账补偿（最后一道防线）

定时任务核对：

```
Redis当前剩余库存 应等于 预热总库存 - 数据库中该商品的有效订单数(待支付+已支付)
```

- **DB 扣得比 Redis 多**（超卖风险）：说明前面几道防线失效，需要告警并转人工处理多出来的订单（业务补偿，如通知用户库存不足、自动退款或补偿优惠券）。
- **Redis 扣得比 DB 多**（幽灵库存）：说明存在预扣库存却没有生成订单的情况，触发库存回滚补偿，或反查 MQ 消费记录，把漏掉的消息重新投递消费。

对账周期建议动态调整：秒杀活动进行中用短周期（如每分钟一次）紧盯，活动结束后做一次最终核对。

## 三、为什么不用分布式事务

TCC、Saga、2PC 理论上能让 Redis 和数据库保持强一致，代价是每次写操作都要多次网络交互等待各参与方确认，响应时间和吞吐量会显著下降，与秒杀场景的核心诉求（扛住瞬时高并发、极速响应）直接冲突。而短暂的不一致（几秒到几十秒内被补偿修复）对整体业务的影响很小，用极端情况下个位数订单的人工补偿成本，换取几十倍的吞吐量提升，这笔账在秒杀场景下明显划算。

---

## 四、一句话总结（面试收尾）

> Redis 与数据库的一致性不是靠分布式事务保证的，而是"Redis 原子扣减做实时防线 + MQ 可靠投递保证扣减结果不丢 + 消费端幂等防止重复处理 + 状态机保证回滚不误伤 + 定时对账补偿兜底极端偏差"这一整套组合拳，本质是牺牲强一致性换取高吞吐，属于 CAP 中的 AP 选择、BASE 理论的最终一致性实践。
