## 一、设计目标与整体思路

秒杀场景的本质是：**瞬时流量远超系统正常承载能力（例如日常 QPS 几百，秒杀峰值 QPS 几十万），且写请求（下单）集中在极短时间窗口内争抢极少量资源（库存）**。设计目标可以概括为四个词：

1. **快**：页面/接口响应要快，减少用户等待，提升前端体验。
2. **稳**：系统不能被瞬时流量打垮，核心链路要能扛住峰值。
3. **准**：库存不能超卖，也不能少卖；限购规则不能被绕过（不超买）。
4. **一致**：Redis、消息队列、数据库三层数据最终要保持一致，异常要可追溯、可补偿。

对应的设计思路是经典的四板斧：

- **动静分离**：秒杀页面静态化 + CDN，避免动态请求打到后端。
- **削峰限流**：网关层限流（令牌桶/漏桶）+ 消息队列异步化，把瞬时脉冲流量削平、串行化。
- **热点前置**：库存预热到 Redis，用 Redis 承接绝大部分读写压力，数据库只做兜底和最终落地。
- **异步化 + 最终一致性**：下单流程异步化（先扣库存、再异步生成订单），数据库通过乐观锁/唯一索引兜底，配合对账补偿保证最终一致。

## 二、全链路架构

系统整体分为六层，详见 `diagrams/01-architecture.puml`：

| 层级 | 组件 | 作用 |
|---|---|---|
| 接入层 | CDN、Nginx、API 网关 | 静态资源加速、请求限流、鉴权、秒杀令牌校验 |
| 应用服务层 | 秒杀服务、订单服务、支付服务、库存服务 | 业务逻辑处理，秒杀服务只做"资格校验+库存预扣"，不直接写订单表 |
| 缓存与中间件层 | Redis 集群、消息队列 MQ、延迟队列 | 承接高并发读写、削峰、异步解耦、超时任务调度 |
| 存储层 | MySQL（主从/分库分表） | 最终数据落地，乐观锁/唯一索引兜底一致性 |
| 风控层 | 验证码、设备指纹、黑名单 | 拦截机器人和恶意刷单 |
| 运维层 | 监控告警、库存对账 | 发现并修复数据不一致 |

**关键设计取舍**：秒杀服务与订单服务是解耦的两个服务。秒杀服务只负责"极速判断能不能买"（毫秒级返回），真正的建订单、写数据库放到订单服务里异步完成。这样把"高并发抢购"和"事务性写库"两个矛盾的需求分开，各自用最适合的技术手段解决。

## 三、全链路详细流程

对应 `diagrams/02-full-link-sequence.puml`，完整链路分四个阶段：

### 阶段 1：活动预热（秒杀开始前）

- 提前把商品库存从数据库同步到 Redis：`seckill:stock:{goodsId} = 100`。
- 生成秒杀专属令牌（token）池，用户进入秒杀页时下发唯一 token，防止秒杀接口 URL 被提前扒出、被脚本直接绕过页面刷接口。
- 秒杀页面做静态化处理，尽量走 CDN，避免开场瞬间大量请求直接打到应用服务器。

### 阶段 2：用户下单

1. 用户带着秒杀令牌发起抢购请求，先经过网关层限流（令牌桶/漏桶算法），单用户、单 IP 都有频率限制。
2. 请求到达秒杀服务后，先做轻量校验（活动是否开始/结束、本地缓存的库存是否已经为 0，命中则直接拒绝，不再往下游打）。
3. 核心一步：用 **Redis + Lua 脚本**，把"判断库存是否大于 0"和"扣减库存"、"判断用户是否已购买"和"标记用户已购买"这两组操作分别封装为原子操作，一次 Lua 脚本执行同时完成库存扣减和限购标记，避免高并发下的竞态条件。
4. 只有 Lua 脚本返回成功（既有库存又未超限购），秒杀服务才会往消息队列 MQ 投递一条"下单消息"，并立即给用户返回"排队中，请稍后查看结果"（不是同步返回"下单成功"，因为订单还没真正落库）。
5. 订单服务异步消费 MQ 消息：先做幂等校验（防止消息重复投递导致重复下单），通过后用数据库乐观锁再扣一次库存（数据库兜底）、插入订单记录（唯一索引兜底限购），最后通过长轮询或 WebSocket 通知用户"下单成功"。

### 阶段 3：支付

- 用户在限定时间内（例如 15 分钟）完成支付，支付网关回调订单服务，订单状态从"待支付"流转为"已支付"。

### 阶段 4：超时兜底

- 用延迟队列（如 RocketMQ 延迟消息、Redis 过期事件监听）或定时任务扫描超时未支付订单。
- 超时后：订单状态改为"已取消"，同时把 Redis 库存加回去、释放该用户的限购标记、数据库库存也加回去，保证库存能被其他人继续购买。

订单完整的状态流转见 `diagrams/03-order-state-machine.puml`。

## 四、超卖问题与解决方案

对应 `diagrams/04-oversell-problem-and-solution.puml`。

### 什么是超卖

**超卖**指系统实际卖出的商品数量超过了真实库存数量，例如库存只有 1 件，却生成了 2 个成功订单。

### 产生原因

根本原因是"**查询库存**"和"**扣减库存**"这两步操作**不是原子操作**：

```
线程A: 查询库存 -> 库存=1，判断>0，可以买
线程B: 查询库存 -> 库存=1，判断>0，可以买
线程A: 扣减库存 -> 库存=0
线程B: 扣减库存 -> 库存=-1  （超卖！）
```

在高并发下，多个请求几乎同时读到了同一个"未扣减前"的库存值，都判断通过，都执行了扣减，导致库存被超卖。分布式环境下，多个服务实例各自持有本地缓存副本、或多个数据库连接并发操作同一行，都会放大这个问题。

### 解决方案（按防线顺序，通常组合使用）

1. **Redis + Lua 脚本原子扣减（第一道防线，也是性能最优的方案）**
   把"判断库存 > 0"和"库存减 1"写进一段 Lua 脚本，通过 Redis 单线程执行 Lua 脚本的特性保证这两步在 Redis 内部是原子的，不会被其他请求打断。这是秒杀场景的首选方案，因为 Redis 单机 QPS 可以达到几万到十几万，远高于直接打数据库。

2. **消息队列串行化（第二道防线，架构层面削峰兼防超卖）**
   只有 Redis 扣减成功的请求才会被投递到 MQ，真正的建订单操作由消费者串行处理（或者对同一商品的消息做分区保证顺序消费），从架构上避免了并发写数据库的场景。

3. **数据库乐观锁兜底（第三道防线，最终一致性保证）**
   即使有请求绕过了 Redis 直接打到数据库（例如 Redis 异常降级场景），数据库层面用条件更新语句本身的原子性兜底：
   ```sql
   UPDATE stock SET count = count - 1
   WHERE goods_id = #{goodsId} AND count > 0;
   ```
   这条 SQL 依赖数据库行级锁和 WHERE 条件，天然保证了"判断+扣减"的原子性，返回受影响行数为 0 就代表库存不足，扣减失败。相比 `SELECT ... FOR UPDATE` 悲观锁，这种写法不需要显式加锁，性能更好；也可以配合 `version` 字段做经典的乐观锁版本号校验。

4. **悲观锁 `SELECT ... FOR UPDATE`（备选方案，一般不作为秒杀首选）**
   直接锁行后再读再改，语义最直观，但秒杀场景下大量请求排队等锁，容易造成数据库连接池耗尽、响应时间飙升，通常只用于低并发场景或兜底极端情况。

5. **分布式锁（备选方案）**
   用 Redisson 等实现分布式锁，锁粒度是商品 ID，保证同一时刻只有一个线程能操作某个商品的库存。能保证正确性，但因为锁的存在，吞吐量不如 Lua 脚本原子操作，一般作为特殊场景（如库存操作逻辑复杂、无法用单条 Lua 脚本表达）的补充手段。

### 推荐组合

> **Redis Lua 原子扣减（实时拦截绝大部分请求）+ MQ 异步排队（削峰、串行化落库）+ 数据库乐观锁/条件更新（最终一致性兜底）+ 定时对账（发现并修复极端情况下的不一致）**

## 五、超买（超限购）问题与解决方案

对应 `diagrams/05-overbuy-limit-purchase.puml`。

### 什么是超买

**超买**指单个用户购买的数量超过了活动限购规则（例如"每人限购 1 件"），实际买到了 2 件甚至更多。这和超卖是两个维度的问题：超卖是"总量维度"的一致性问题，超买是"用户维度"的限购规则被绕过的问题。

### 产生原因

1. 前端没有做防重复提交，用户手抖多次点击，短时间内发出多个相同的下单请求。
2. 客户端网络重试、代理重放，导致同一个请求被后端处理了多次。
3. **限购校验和下单写入不是原子操作**：先查询"该用户是否已购买"，查询时还没查到记录，于是两个并发请求都通过了校验，都各自完成了下单。
4. 黄牛/羊毛党用多个账号、脚本模拟并发请求刷单。

### 解决方案（按防线顺序）

1. **前端防重复提交**：按钮点击后立即置灰、防抖，这一层只是体验优化，不可信，必须有后端兜底。

2. **幂等令牌（Token）机制**：用户进入秒杀页时，后端下发一个唯一 token；提交订单时携带这个 token，后端用 `SETNX` 消费 token（消费成功即删除/标记已用），同一个 token 只能成功消费一次，天然拦截重复提交和请求重放。

3. **Redis 用户维度限购原子标记（核心防线）**：用 `SETNX seckill:limit:{userId}:{goodsId}` 这种 key，未命中才允许该用户继续下单，命中说明已经购买过，直接拒绝。`SETNX` 本身就是 Redis 提供的原子操作，天然避免了"先查询再写入"这种非原子模式带来的竞态条件。

4. **数据库唯一索引（最后一道防线）**：在订单表上给 `(user_id, goods_id, activity_id)` 建唯一索引。即使前面所有防线都被绕过（比如极端并发或者 Redis 异常降级），第二条重复的 insert 语句会因为唯一约束冲突直接失败，从存储层面保证同一用户对同一活动只能有一条有效订单。

5. **验证码/风控识别（防机器人和黄牛）**：图形验证码、滑块验证、行为验证码识别自动化脚本；结合设备指纹、IP 频率、用户行为特征做风控评分，命中异常规则的账号/设备直接拉黑或限流，这一层解决的是"恶意大规模刷单"而不是普通用户的重复点击。

### 推荐组合

> **Redis 用户维度原子标记（第一时间拦截同用户重复下单）+ 幂等 Token（防重复提交/请求重放）+ 数据库唯一索引（最后的强一致性兜底）+ 验证码/风控（防脚本刷单）**

## 六、数据一致性兜底：对账与补偿

秒杀链路涉及 Redis、MQ、MySQL 三层存储，理论上任何一环都可能出现异常（网络抖动、机器宕机、MQ 消息丢失等），需要有兜底机制：

- **库存对账任务**：定时对比 Redis 库存与数据库库存，如果长期不一致（超过正常的短暂延迟窗口）则报警，人工或自动介入修复。
- **订单与库存联动对账**：以数据库订单表的实际成交数为准，反查 Redis 剩余库存是否等于"预热库存 - 实际成交数 - 未支付占用数"，发现偏差报警。
- **消息可靠性**：MQ 需要开启生产者确认（ACK）、消费者手动 ACK + 重试 + 死信队列，避免消息丢失导致"库存扣了但订单没生成"这种中间态长期存在。
- **超时释放**：延迟队列/定时任务保证"库存预扣了但用户没支付"的这部分库存最终一定会被释放回去，不会被永久占用。

## 八、面试高频问答

**Q1：为什么用 Redis + Lua 脚本而不是直接用分布式锁？**
Lua 脚本利用 Redis 单线程执行的特性，把多条命令封装成一个不可分割的原子操作，不需要额外的加锁/解锁开销，吞吐量更高；分布式锁需要额外的网络往返（加锁、业务处理、解锁），在高并发抢购场景下性能不如 Lua 脚本。分布式锁更适合业务逻辑复杂、无法用一段 Lua 脚本表达的场景。

**Q2：为什么要引入消息队列做异步下单？削峰具体体现在哪？**
秒杀开场瞬间的请求是脉冲式的（例如 1 秒内涌入 10 万请求），但数据库能承受的持续写入能力是有限的（例如 1 秒几千 TPS）。如果同步直接写数据库，瞬间的连接数和锁竞争会直接把数据库打垮。引入 MQ 后，请求在 Redis 层完成库存预扣即可快速返回，真正的建订单操作由消费者按数据库能承受的速率匀速消费，把"脉冲流量"变成了"平滑流量"，这就是削峰的本质。

**Q3：Redis 库存和数据库库存如何保证最终一致？**
Redis 库存是第一道防线，负责挡住绝大多数请求；数据库库存扣减用乐观锁/条件更新语句做最终兜底，保证即使有异常流量绕过 Redis，数据库层面依然不会超卖。再配合定时对账任务比对两边库存差异，发现异常及时报警和人工修复。完整展开（正向同步链路的可靠消息+死信补偿、逆向回滚链路的本地事务+幂等）见 [`06-redis-mysql-consistency.md`](06-redis-mysql-consistency.md)。

**Q4：如果 Redis 宕机了怎么办？**
需要提前做好降级预案：一是 Redis 采用集群/哨兵模式保证高可用，二是设计限流降级开关，Redis 不可用时可以直接对该秒杀活动限流甚至临时关闭入口，而不是让请求直接穿透到数据库，避免数据库被打垮；三是活动前的库存预热和压测要覆盖 Redis 故障演练。

**Q5：令牌桶和漏桶限流算法的区别？**
漏桶算法请求进入桶里排队，以固定速率流出，天然平滑输出速率，但无法应对突发流量（哪怕桶还有空间，超过速率也要排队）；令牌桶算法按固定速率往桶里放令牌，请求需要拿到令牌才能通过，桶里可以攒一定数量的令牌，因此能应对一定程度的突发流量（只要令牌够用可以瞬时放行一批请求），秒杀场景通常用令牌桶，因为它对合理的突发流量更友好。

**Q6：如何防止黄牛用脚本批量刷单？**
组合手段：图形验证码/滑块验证码识别自动化脚本；秒杀令牌+页面行为轨迹校验，防止直接跳过页面调接口；设备指纹和 IP 频率限制识别异常设备；账号维度的历史行为风控评分，命中异常规则的账号限流或拉黑；核心接口做好签名校验，防止请求被抓包重放。

**Q7：订单超时未支付如何自动处理？会不会有并发问题？**
用延迟队列（RocketMQ 延迟消息、RabbitMQ 死信队列）或定时任务扫描超时订单，触发关单逻辑：更新订单状态为已取消、Redis 库存加回、数据库库存加回、释放用户限购标记。这里也需要注意幂等：支付回调和超时关单可能并发触发，需要用订单状态机加乐观锁（例如"只有状态为待支付才能被关闭"）防止已支付的订单被误关闭。

**Q8：如何保证 MQ 消息不丢失、不重复消费？**
不丢失：生产者开启发送确认（ACK/事务消息），消费者手动 ACK（业务处理成功后才确认消费），失败消息进入重试队列，重试超限进死信队列人工介入。不重复消费：消费端基于消息唯一 ID（业务幂等键）做幂等校验，比如插入订单前先检查该消息 ID 是否已处理过（Redis 或数据库唯一索引），处理过直接丢弃，保证"至少一次投递 + 消费端幂等"等价于"精确一次"的业务效果。

**Q9：秒杀系统和普通电商下单流程最大的架构差异是什么？**
普通下单是同步流程：查库存、扣库存、建订单、支付，一步到位。秒杀因为瞬时并发极高，必须把"资格校验/库存预扣"和"建订单"拆成两个异步阶段，中间用 MQ 解耦，用户看到的"抢购成功"其实只是"库存预扣成功、正在排队生成订单"，这也是为什么秒杀页面经常会有"抢购成功，请稍后查看订单"这种提示的原因。

**Q10：这套方案中，哪个环节最容易成为瓶颈？如何进一步优化？**
最容易成为瓶颈的通常是 Redis 单 key 的热点问题（所有请求集中操作同一个库存 key）和数据库连接池。优化手段：库存可以做分片（把总库存拆成多个子 key，分散热点，代价是可能出现"总量够但某个分片扣不出来"的情况，需要有分片间调剂或余量回收逻辑）；数据库层面可以对订单表按用户 ID 或活动 ID 做分库分表；网关层面提前做好更严格的限流和排队，把流量控制在系统实际承载能力之内。
