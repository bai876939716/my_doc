# 场景题：数据库优化的完整技术实现路线

## 一句话答案

数据库优化不存在"标准答案"，只存在"这个流量/数据量级下该做什么"——**同一个优化手段在低流量场景是过度设计，在高流量场景是必需品**。下面用一个电商订单系统从 0 到亿级规模的演进路径，把每个阶段"遇到什么问题→做什么决策→为什么不做更重的方案"讲清楚，这比背一份优化清单更有说服力。

---

## 场景带入：电商订单系统的演进路径

| 阶段 | 日订单量 / QPS | 典型瓶颈现象 | 采取的决策 | 为什么不上更重的方案 |
|------|----------------|-------------|-----------|---------------------|
| **阶段0：MVP** | <1万单/日，QPS<10 | 无明显瓶颈 | 单库单表 + 基础索引（主键、常用查询字段） | 提前引入缓存/分库分表是过度设计，团队要花时间维护额外复杂度，但业务量根本用不上 |
| **阶段1：起量** | 1万~10万单/日，QPS 10~200 | 订单列表分页变慢，个别接口响应时间抬头 | `EXPLAIN` 定位慢查询，补齐/调整索引；引入 Redis 做详情页 Cache Aside 缓存 | 大部分读压力用缓存就能扛住，成本远低于任何架构改造 |
| **阶段2：增长** | 10万~100万单/日，QPS 200~2000 | 主库 CPU/IO 打满，写高峰期读请求也跟着变慢 | 一主多从做读写分离；慢查询专项治理；连接池参数调优（HikariCP） | 读写分离能把读压力从主库剥离，写压力还没到必须拆分表结构的量级 |
| **阶段3：规模化** | 100万~1000万单/日，QPS 2000~1万 | 单表数据量破亿，索引效率下降，DDL 变更长时间锁表风险高 | 垂直分库（订单库/用户库/商品库拆开）；历史订单冷热分离归档到历史库；下单链路接消息队列削峰（先入队异步落库） | 垂直拆分先解决"业务耦合"和"单库压力"，能撑住这个量级，还不需要动"单表怎么拆"这个更痛的手术 |
| **阶段4：超大规模** | 1000万+单/日，QPS 1万+ | 垂直拆分后的订单库单表还是过大，跨机房容灾要求出现 | 水平分库分表（按 user_id 哈希分片）；配套分布式 ID（雪花算法）；复杂查询/搜索接 ES 分流；多活架构 | 到这个量级，缓存和垂直拆分的收益已经用尽，水平分片是唯一出路——但要接受"跨分片聚合查询变复杂、需要在应用层二次汇总"这个代价，这也是为什么水平分片要放在最后一步 |

**这张表想说明的核心判断力**：面试官问"数据库怎么优化"，最怕的回答是"分库分表"张口就来。真实的决策顺序永远是——**先看现在的量级配不配得上这个方案的复杂度**，阶段0直接上分库分表是给自己找麻烦，阶段4还在死磕单库优化是在等着系统崩。

## 各阶段具体手段展开

### 阶段1的索引优化怎么做

- `EXPLAIN` / `EXPLAIN ANALYZE` 看执行计划：是否走索引、是否全表扫描、预估扫描行数
- 最左前缀原则：联合索引 `(a, b, c)` 只有查询条件从 a 开始才能用上
- 覆盖索引：索引本身包含查询所需字段，避免回表
- 避免索引失效：WHERE 条件里不要对索引列做函数运算或隐式类型转换
- 分页优化：深分页 `LIMIT 100000, 20` 改成游标分页 `WHERE id > 上次最大id LIMIT 20`

### 阶段2的缓存怎么做

- **Cache Aside**：读时先查缓存，未命中查库并回写；写时先更新库，再删除缓存（不是更新缓存）
- **缓存穿透**（查询不存在的数据）：布隆过滤器提前拦截 + 空结果短期缓存
- **缓存击穿**（热点 key 过期瞬间大量请求打库）：互斥锁重建 + 逻辑过期
- **缓存雪崩**（大量 key 同时过期）：过期时间加随机抖动
- **缓存一致性**：更新频繁、一致性要求高的场景，用订阅 binlog（canal）异步更新缓存，业务代码不用手写"更新库后删缓存"这行代码，从根本上避免遗漏

### 阶段3的垂直拆分与冷热分离

- 垂直拆分：按业务域拆库（订单/用户/商品），弱一致的跨库操作用消息队列异步保证最终一致（详见《02-防止消息丢失的完整技术方案.md》的本地消息表/事务消息方案）
- 冷热分离：近 3 个月订单留在主库，历史订单归档到单独的历史库/大数据平台，主库表体积可控，索引效率保持稳定
- 消息队列削峰：大促瞬时下单量远超数据库处理能力时，下单请求先落消息队列，由消费者按数据库能承受的速率异步落库，用队列长度换峰值处理能力

### 阶段4的水平分片怎么设计

- **分片键选择**：必须匹配主要查询模式（这里选 `user_id`，因为订单查询几乎都带用户维度），否则跨分片查询会很痛苦
- **分片策略**：Hash 分片分布均匀但扩容需要数据迁移；Range 分片易扩容但容易产生热点分片，两者各有取舍，也可以用一致性哈希降低扩容时的数据迁移量
- **分布式 ID**：自增 ID 在多分片场景下会冲突，需要雪花算法或号段模式生成全局唯一 ID
- **跨分片查询**：COUNT/SUM/ORDER BY 这类聚合查询没法在单个分片内完成，要么在应用层做"分片并行查询+二次汇总"，要么把这类复杂查询需求整体导到 ES 等异构存储，数据库只承担分片键精确查询这一种最擅长的场景

## 面试话术小结

> 我不会先入为主给出一个固定的优化方案，而是先确认当前的流量和数据量级——低流量阶段任何架构层手段都是过度设计，优化重心在 SQL 和索引；中等流量引入缓存和读写分离就够；到了单表数据量过亿、DDL 都变得高风险的规模才考虑垂直拆分；水平分库分表是成本最高、最不可逆的手段，只有在缓存和垂直拆分的收益都用尽、单库确实到了物理瓶颈时才会上，因为它会带来跨分片查询复杂度这个长期要还的技术债。
