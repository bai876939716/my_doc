# 场景题：怎么防止消息丢失？完整的技术方案

## 一句话答案

消息从"生产者发出"到"消费者处理完成"要经过三个阶段——**生产者→Broker→消费者**，每个阶段都有独立的丢失风险和对应方案；但真正的难点、也是面试官最爱深挖的点是**"业务落库"和"发消息"这两个动作怎么保证原子性**——这是本文重点展开的部分，用电商下单场景（创建订单 + 通知库存服务扣库存）贯穿讲清楚三种主流方案。三种方案各配一张时序图：`diagrams/01-本地消息表时序图.puml`、`diagrams/02-RocketMQ事务消息时序图.puml`、`diagrams/03-CDC监听binlog时序图.puml`。

---

## 全链路风险点总览

```
生产者 --发送--> Broker --存储--> Broker --投递--> 消费者 --处理--> 业务完成
   ↑丢失点1              ↑丢失点2                ↑丢失点3
发送失败没重试        消息还没刷盘就宕机      拿到消息就ack但处理失败/宕机
```

---

## 一、生产者阶段：确保消息真正送达 Broker

| 方案 | 说明 |
|------|------|
| 同步发送 + 确认 | 发送后等待 Broker 返回 ack，收到 ack 才算发送成功，失败则重试 |
| 异步发送 + 回调检测 | 性能更好，但要在失败回调里做重试和告警，不能只发不管 |
| 重试 + 幂等 | 重试可能导致 Broker 端重复收到同一条消息，生产者侧要给消息带上唯一业务 ID，方便下游去重 |

---

## 二、Broker 阶段：确保消息落盘后才算收到

| 方案 | 说明 | 权衡 |
|------|------|------|
| 同步刷盘（sync flush） | 消息写入磁盘成功才返回 ack | 可靠性最高，吞吐量和延迟受影响 |
| 异步刷盘（async flush） | 先写缓存，后台异步刷盘 | 吞吐量高，宕机时缓存中未刷盘消息会丢 |
| ack 策略（Kafka `acks`） | `acks=0` 不等确认 / `acks=1` 只等leader / `acks=all` 等所有ISR副本确认 | 核心业务用 `acks=all` |
| 主从同步复制（RocketMQ SYNC_MASTER） | 主节点写入后同步复制到从节点才返回成功 | 与 Kafka acks=all 同一思路 |

---

## 三、消费者阶段：确保处理完成后才确认

| 方案 | 说明 |
|------|------|
| 手动 ack，业务处理成功后再确认 | 而不是拉取到消息就自动 ack |
| 消费幂等设计 | 手动 ack 是 at-least-once 语义，消息可能重复投递，业务侧要幂等（唯一键判重） |
| 重试机制 + 死信队列（DLQ） | 消费失败重试N次（指数退避），仍失败进死信队列，避免"毒消息"阻塞后续消费 |

---

## 四、核心难点：怎么保证"发消息"和"落库"在一个事务里

**先讲清楚问题本质**：数据库和消息队列是两个独立系统，没法用同一个本地 ACID 事务同时保证"订单落库"和"消息发出"这两个动作。

- 如果**先落库再发消息**：落库成功后，发消息这一步可能因为网络抖动/MQ 不可用而失败 → 库里有订单，但库存服务永远不知道要扣库存，数据不一致
- 如果**先发消息再落库**：消息发出后可能被消费者秒级处理了，但落库这一步随后失败（主键冲突/网络分区）→ 库存已经被扣了，但源头订单根本不存在

这就是分布式事务问题在"消息可靠性"场景下的具体体现。业内主流有三种方案：

### 方案一：本地消息表（Local Message Table）

**核心思路**：把"待发送的消息"也存成一条数据库记录，和业务数据放在**同一个库、同一个本地事务**里一起提交——巧妙地把跨系统的分布式事务问题，转化成了同一个数据库内的本地事务问题。

**具体步骤（以下单为例）**：

```
1. order-service 在同一个数据库事务里执行两条 SQL：
   INSERT INTO tb_order (order_id, user_id, sku_id, status, ...) VALUES (...);
   INSERT INTO tb_local_message (msg_id, topic, payload, status, retry_count, create_time)
       VALUES (msgId, 'order.created',
               '{"orderId":"O1001","skuId":"S2001","count":2}',
               'PENDING', 0, now());
   -- 两条 INSERT 同一个事务 commit，要么都成功要么都失败

2. 独立的"消息投递任务"（定时轮询 tb_local_message，或者本地事务提交后立即触发一次异步投递作为"快速路径"，
   轮询作为兜底"慢路径"）扫描 status=PENDING 的记录：
       尝试真正发送到 MQ（RocketMQ/Kafka）
       发送成功 → UPDATE tb_local_message SET status='SENT' WHERE msg_id=?
       发送失败 → retry_count += 1，下次轮询继续重试；超过最大重试次数（比如10次）报警转人工介入

3. 消费方（inventory-service）消费到 order.created 消息后执行扣库存：
       先查本地"已处理消息表"（用 msgId 判重）
       没处理过 → 执行扣库存 + 把 msgId 写入已处理表（同一个本地事务）
       已处理过 → 直接忽略（应对消息重复投递）

4. 定期清理已 SENT 且超过保留期（比如7天）的本地消息记录，避免表无限增长
```

**关键设计点**：
- 投递任务本身也要考虑幂等：发送前检查状态仍是 `PENDING` 再发，或者干脆允许重复发送、靠消费侧的已处理表去重
- "快速路径 + 慢路径兜底"：本地事务 commit 成功后立即异步触发一次投递尝试（降低正常情况下的延迟），投递失败或者服务重启中断了，靠定时轮询任务最终兜底重试，保证消息"最终"一定会被投递出去

**优点**：不依赖 MQ 本身的特殊能力，任何消息队列都能用；实现原理简单，出问题时排查直观（直接查本地消息表状态）。

**缺点**：需要自己维护投递任务和消息表；纯轮询方式有一定投递延迟（配合快速路径可以缓解）。

### 方案二：MQ 原生事务消息（以 RocketMQ 为例）

**核心思路**：让消息队列本身提供"半消息（half message）"能力——消息先到 Broker 但对消费者不可见，等本地事务执行完，再告诉 Broker 这条消息到底要不要真正投递。

**具体步骤**：

```
① Half消息阶段
   order-service 先发送一条"半消息"给 RocketMQ Broker
   Broker 收到后标记为"不可投递"状态，下游消费者看不到这条消息

② 本地事务阶段
   RocketMQ SDK 收到 Broker 对半消息的 ack 后，立即触发本地事务执行回调
   在回调函数里执行本地DB事务：INSERT INTO tb_order (...)

③ 提交阶段
   本地事务执行结果决定半消息的最终命运：
   本地事务成功 → 调用 commit，通知 Broker 把消息标记为"可投递"，下游才能看到
   本地事务失败 → 调用 rollback，通知 Broker 丢弃这条半消息，永不投递

④ 回查机制（容错核心）
   如果第③步因为网络问题、或者订单服务在执行本地事务时刚好宕机，
   导致 Broker 没有收到明确的 commit/rollback 指令：
   Broker 会定期（比如每隔1分钟，最多回查若干次）主动回查订单服务：
       "这条半消息对应的本地事务，你完成了吗？"
   订单服务需要实现一个"回查接口"：
       根据消息里的业务标识（比如orderId）去查订单表，判断订单是否已创建成功
       订单已创建 → 告诉 Broker commit
       订单不存在 → 告诉 Broker rollback
   这样即使 commit/rollback 指令因为宕机丢失了，Broker 也能靠主动回查，
   最终把消息状态恢复到和真实业务状态一致

⑤ 下游消费者只会看到状态是"可投递"的消息，天然保证"消息可见 ⟺ 本地事务已成功"
```

**伪代码示意**：

```java
TransactionMQProducer producer = new TransactionMQProducer("order-producer-group");
producer.setTransactionListener(new TransactionListener() {

    // 收到Broker对half消息的确认后，执行本地事务
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            orderMapper.insert(order);
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    // Broker主动回查，业务方需要提供依据实际状态判断的逻辑
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        Order order = orderMapper.selectByMsgKey(msg.getKeys());
        return order != null ? LocalTransactionState.COMMIT_MESSAGE
                              : LocalTransactionState.ROLLBACK_MESSAGE;
    }
});

producer.sendMessageInTransaction(halfMessage, null);
```

**优点**：由 MQ 框架保证一致性，正常情况下没有轮询延迟；业务代码相对简洁，不需要自己维护消息表和投递任务。

**缺点**：依赖 MQ 本身支持事务消息（RocketMQ 原生支持得比较完善，原生 Kafka 的事务能力更偏向"生产者内多个分区的原子写入"，做这种"业务事务+消息发送"绑定的语义支持较弱）；必须实现"回查接口"，对业务代码有一定侵入性。

### 方案三：CDC 监听 binlog（canal / Debezium），业务代码零侵入

**核心思路**：业务代码完全不用关心"发消息"这件事，只管老老实实提交本地事务；下游靠订阅数据库的 binlog 变更日志来感知数据变化，自己转换成消息发出去。

**具体步骤**：

```
① order-service 只执行正常的本地事务：INSERT INTO tb_order(...)，不写任何"发消息"相关代码
② canal/Debezium 伪装成 MySQL 的一个从库，订阅主库的 binlog
③ tb_order 表有新增记录时，binlog 产生一条对应的 INSERT 日志
④ canal/Debezium 解析这条 binlog，转换成业务消息格式，发送到 Kafka/RocketMQ
⑤ inventory-service 消费这条消息，执行扣库存逻辑
```

**优点**：业务代码完全解耦"消息怎么发"这件事，从根本上杜绝"开发忘记写发消息代码/发消息代码里有bug"这类人为失误风险——只要数据落库了，消息一定会产生。

**缺点**：引入额外中间件（canal/Debezium）的部署和运维成本；消息内容是"这一行数据变成了什么样"，如果业务需要发送更丰富的语义信息（不只是这一行的增删改，比如需要关联查询组装出更复杂的通知内容），还需要在下游做额外的转换处理；实时性依赖 binlog 同步延迟（通常是秒级，不算太差）。

---

## 三种方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| 本地消息表 | 业务表+消息表同库同事务，独立任务轮询投递 | 不依赖特定MQ能力，实现简单、排查直观 | 需要自己维护投递任务和消息表；有一定投递延迟 | 通用场景，MQ不支持事务消息时的首选，也是最容易讲清楚原理的方案 |
| MQ事务消息 | Broker侧half消息+本地事务回调+回查机制 | 由MQ框架保证一致性，延迟低，业务代码相对简洁 | 依赖MQ支持（RocketMQ支持较好）；需要实现回查接口 | 高实时性要求、且MQ选型支持事务消息的场景 |
| CDC监听binlog | 数据库binlog驱动，业务代码零侵入 | 业务代码完全解耦，杜绝人为遗漏 | 额外中间件运维成本；消息语义受限于数据行变化 | 数据同步/异构系统同步类场景，或希望消息发送逻辑与业务代码彻底解耦的场景 |

---

## 端到端最终一致性的完整闭环（不只是发消息，还要保证下游真的处理成功）

只解决"消息一定发得出去"还不够，完整闭环还要考虑消费端和最终对账：

1. **消费端幂等**：无论哪种方案，消息投递语义都是 at-least-once，inventory-service 必须用消息里的 `msgId` 做已处理判重，防止重复扣库存
2. **消费失败的重试与死信**：扣库存失败（比如库存不足）要区分"业务性失败"（不该重试，直接进死信队列人工处理退款）和"系统性失败"（网络抖动等，应该重试）
3. **定时对账兜底**：核心链路（下单+扣库存）即使有上面这套机制，仍然建议加一个定时对账任务——定期扫描"订单状态=已创建但库存未扣减超过N分钟"的异常记录，主动触发补偿（重新发消息/人工介入），作为整条链路的最后一道防线，不完全迷信任何单一机制的100%可靠

---

## 面试话术小结

> 消息不丢是三段全覆盖的问题：生产者要发送确认，Broker 要同步刷盘/多副本确认，消费者要处理成功后才手动ack配合幂等。但真正的难点是"业务落库"和"发消息"这两个跨系统动作的原子性——本地消息表是把分布式事务转化成同库事务，最通用；RocketMQ事务消息是让MQ框架直接管这件事，延迟更低但依赖MQ能力；CDC监听binlog是让业务代码完全不用关心发消息这件事，从根源杜绝遗漏。三种方案我会根据MQ选型和业务对实时性、代码侵入度的要求来选，同时不管选哪种，都会再加一层定时对账兜底，不会只依赖单一机制。
