# 场景题：输入一大段文字，要和亿级别的字符串做精确匹配，方案怎么设计？

## 一句话答案

精确子串匹配（文本里有没有出现库里的哪些字符串）的标准方案是 **AC 自动机（Aho-Corasick）**：把亿级模式串构建成一棵带 fail 指针的 Trie，对输入文本做一次线性扫描就能同时命中所有模式串。真正决定这套方案能不能在生产环境用好的，是**内存怎么压缩到能常驻、词库怎么在不停机的情况下更新、以及怎么应对用户规避检测的各种变体攻击**——这三点才是这道题的深度所在，下面逐一给出可落地的实现方案。

> 说明：字符串匹配还有"存在性判断（布隆过滤器）""近似查重（SimHash）""语义相似（Embedding+ANN）"三种其他语义，这里不展开，只聚焦精确匹配这一种场景做深挖。

## 一、算法核心：Trie + fail 指针，具体怎么构建和匹配

### 1.1 构建阶段：Trie 插入 + BFS 计算 fail 指针

```
构建Trie（把每个模式串插入一棵前缀树）:
for each word in 词库:
    node = root
    for ch in word:
        if node.children[ch] 不存在:
            node.children[ch] = new TrieNode()
        node = node.children[ch]
    node.is_end = true
    node.output = [word]        # 这个节点代表一个完整命中的模式串

构建fail指针（按层用BFS，从根节点往下）:
queue = []
for child in root.children:
    child.fail = root            # 深度为1的节点，失配后只能回到根
    queue.push(child)

while queue 非空:
    curr = queue.pop()
    for (ch, child) in curr.children:
        f = curr.fail
        while f != null and ch 不在 f.children 中:
            f = f.fail
        child.fail = (f != null) ? f.children[ch] : root
        child.output += child.fail.output   # 关键：合并fail链上的output
                                             # 处理"词中词"，比如词库里同时有"敏感"和"感"，
                                             # 匹配到"敏感"这个节点时，也要能通过fail链带出"感"
        queue.push(child)
```

### 1.2 匹配阶段：对文本做一次线性扫描

```
match(text):
    node = root
    results = []
    for i, ch in enumerate(text):
        while node != root and ch 不在 node.children 中:
            node = node.fail        # 失配时沿fail指针回退，而不是从头重新开始扫
        if ch 在 node.children 中:
            node = node.children[ch]
        else:
            node = root
        if node.output 非空:
            for word in node.output:
                results.append((起始位置 = i - len(word) + 1, word))
    return results
```

**复杂度**：整个匹配过程是 O(文本长度)，和词库里有多少个模式串**无关**——词库大小只影响构建阶段的时间和内存，不影响在线匹配的时间复杂度。这是 AC 自动机相比"每个词单独做一次子串查找（复杂度是 文本长度×词库大小）"的根本优势。

## 二、内存优化：Double Array Trie 具体怎么省内存

普通指针版 Trie，每个节点要存一个 hashmap（或固定大小数组）做 children 索引，节点数量随词库线性增长，中文场景下字符集大，指针和对象头的开销会被放大到亿级规模就很可观。

**Double Array Trie（双数组 Trie，简称 DAT）** 用两个整型数组 `base[]` 和 `check[]` 编码整棵树，不用任何指针：

```
状态转移规则：next_state = base[state] + char_code
合法性校验：   check[next_state] == state 才说明这条转移真实存在（不是数组下标碰撞）

插入逻辑（简化描述）：
对当前状态 s，要为它的子节点字符集合 C 分配空间：
   寻找一个 base[s] 的取值，使得对每个字符 c 属于 C，
   位置 base[s]+c 在 check 数组里都还没被占用（或者恰好等于 s，说明可以复用）
   找到后，令 check[base[s]+c] = s，这就建立了 s 到子节点的一条边
```

**为什么省内存、还更快**：所有状态转移变成了两次数组下标运算（`base[state]+char` 定位，`check[]` 校验），不需要 hashmap 的哈希计算和链表/红黑树遍历，也不需要为每个节点单独分配对象——数组本身是连续内存，CPU 缓存命中率高，查找速度也比指针版 Trie 快。

**代价**：构建过程要做冲突探测和已分配位置的重定位，构建复杂度比普通 Trie 高很多；而且 DAT 不适合频繁地做增量插入/删除（每次插入都可能触发大范围的位置调整）——这也是下面第四节"为什么用离线全量构建+热替换"的直接原因。

## 三、亿级规模的分片部署架构

见 `diagrams/04-AC自动机分片架构图.puml`。假设敏感词库 5000 万条，单机内存放不下完整的 DAT，具体架构：

```
① 离线构建：按词的哈希值对16取模，把5000万词分成16个分片，每片约300万词
           每个分片单独构建一棵DAT，序列化成文件

② 部署：16个"敏感词过滤节点"，每个节点常驻加载自己负责的那1个分片

③ 在线匹配（关键特性——必须广播，不能按key路由）：
   网关收到待检测文本 → 同时广播到全部16个节点
   （因为一个敏感词可能落在任意分片里，不像一般的KV分片系统能按key算出该去哪个分片，
    这里必须让所有分片都参与一次匹配，是"分片存储换内存"必须付出的代价）
   每个节点各自扫描一遍文本，返回命中结果
   网关汇总16个节点的结果，返回给业务方

④ 分片数量的权衡：分片越多，单节点内存压力越小，
   但广播的节点数越多，网络开销和尾延迟（要等最慢的那个分片返回）越大，
   需要按词库规模和延迟SLA去调
```

## 四、热更新机制：为什么是"离线全量构建 + 双缓冲原子替换"

DAT 不适合频繁增删（第二节提到的构建代价问题），所以更新策略是：

```
离线任务：词库有变化 → 重新构建新版本的16个分片文件，打上版本号

在线节点内部：
   维护一个原子引用（比如AtomicReference）指向"当前生效的自动机对象"
   定时任务（比如每小时）检查文件版本号是否有更新
   有更新 → 在后台线程构建一个全新的自动机对象（不影响正在处理中的请求）
   构建完成 → 原子替换那个引用，指向新对象
   旧对象在没有请求再引用它之后，由GC自然回收

这样做的好处：
   任何一个正在处理中的请求，从始至终用的都是替换那一刻还没结束时的对象引用，
   不会出现"用一半新版本一半旧版本"的中间状态，也完全不需要重启服务
```

**紧急新增词的应急通道**：如果等不及下一次全量构建（比如临时需要立刻拦截一个新词），可以维护一个很小的"增量Trie"（体量小，普通指针Trie即可，不需要DAT这种重量级结构），实时生效；主DAT走定期全量重建，把增量词合并进去后清空增量Trie，两条通道的匹配结果取并集。

## 五、真实的生产环境难点：反规避（Anti-Evasion）处理

见 `diagrams/06-敏感词反规避处理流程图.puml`。**纯粹的精确子串 AC 自动机在生产环境远远不够**，因为真实用户会想办法规避检测，这才是这道题真正考察工程经验的地方：

| 规避手段 | 示例 | 应对方案 |
|---------|------|---------|
| 插入分隔符 | "敏 感 词" / "敏-感-词" / "敏.感.词" | 预处理阶段先做"分隔符/空白字符剥离归一化"，再送入AC自动机；剥离时要保留位置映射，方便命中后能定位回原文用于高亮/替换 |
| 同音字/谐音替换 | "敏感"→"悯感"/"敏杆" | 把文本转成拼音序列，词库也预先转换成拼音库，用**单独一棵拼音AC自动机**再匹配一次 |
| 形近字替换 | "敏"→"闵" | 维护形近字映射表，预处理阶段把形近字归一化替换为统一的代表字符 |
| 繁简混用 | 用繁体字绕过简体词库 | 统一转简体后再进入匹配管道 |

**工程上的组合拳（两条通道并行）**：

```
原始文本
   → 归一化预处理管道（去分隔符 → 繁简转换 → 形近字归一化）
   → 精确AC自动机匹配（高精度、直接拦截）
      同时
   → 转拼音序列 → 拼音AC自动机匹配（高召回，但误判率更高）

精确通道命中 → 直接拦截/替换为星号
拼音通道命中（精确通道未命中）→ 标记为"疑似违规"，走人工复核或额外规则二次确认，
   不直接拦截，避免拼音匹配的误判率过高导致大量正常内容被误伤
```

这个"高精度通道直接拦截 + 高召回通道转人工复核"的分层设计，是应对"既要防规避、又不能误伤太多正常用户"这个矛盾的标准工程思路。

## 面试话术小结

> 精确子串匹配用 AC 自动机是标准答案，但只说到这一步是不够的。真正的工程深度在三点：内存上用 Double Array Trie 把树结构压缩成两个整型数组，用数组下标运算代替指针查找；更新上因为 DAT 不适合增量修改，所以走"离线全量构建+原子引用替换"的热更新，不停机也不会出现新旧混用的中间状态；最容易被忽视但生产环境必须解决的是反规避——用户会用分隔符、谐音、形近字规避检测，需要一套"归一化预处理+精确通道直接拦截+拼音通道转人工复核"的分层管道，单纯的字面精确匹配在真实场景里覆盖率是不够的。
