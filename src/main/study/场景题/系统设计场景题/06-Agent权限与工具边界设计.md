# 场景题：Agent 怎么做权限管理？工具边界怎么划？

## 一句话答案

核心思路是**纵深防御（defense in depth）**：不能只靠"提示词里写不要做什么"这一层（最不可靠），要从工具定义（能调用哪些工具）、参数校验（能传什么参数）、执行环境隔离（沙盒）、业务规则硬校验（金额/资格类判定不让模型拍板）、人工审批（高风险操作兜底）五层叠加防护，任何一层被绕过，下一层还能兜住。

配套图示：`diagrams/08-Agent权限判定架构图.puml`（架构图/组件图）、`diagrams/09-Agent工具调用决策流程图.puml`（流程图）。

## 一、为什么 Agent 需要专门的权限设计

LLM 本身存在两个风险源：

1. **幻觉/误判**：模型可能"好心办坏事"，比如错误理解用户意图后调用了不该调用的工具
2. **被诱导（提示词注入）**：工具返回的数据里如果混入看起来像指令的文本，模型可能把数据当指令执行，相当于攻击者通过数据注入拿到了原本不该有的执行权限

权限设计的目标不是"完全阻止模型犯错"（做不到），而是**限制"一旦犯错，最坏能造成多大影响"（限制 blast radius，爆炸半径）**。

---

## 二、纵深防御的五层设计

见 `diagrams/08-Agent权限判定架构图.puml`，一次工具调用请求从模型发出到真正执行，要依次穿过这五层：

### 第一层：工具白名单（能调用哪些工具，系统层面预先注册）

Agent 能调用的工具集合是系统预先注册好的，模型只能在这个集合里选，**不能"发明"新的工具调用能力**。这是最基础的边界——不给模型的工具，无论提示词怎么诱导都调不出来。

### 第二层：参数级别的 Schema 校验

只限定"能调用哪个工具"还不够，还要限定"能用什么参数调用"。比如允许 Agent 查询数据库，但要通过参数 Schema 限定只能查特定表、特定字段，不能查询密码/身份证号这类敏感字段；允许执行 Bash 命令，命令内容本身还要过一层黑名单校验（禁止 `rm -rf /` 这类危险命令）。

### 第三层：操作分级 + 权限模式

把工具调用按"是否有副作用"分级：

| 操作类型 | 处理方式 |
|---------|---------|
| 只读查询类 | 通常可以自动放行 |
| 有副作用的写操作（写文件、发消息、执行代码） | 需要额外审批或限定在沙盒内执行 |
| 资金/高风险操作 | 必须强制人工审批，模型无权自主决定 |

具体判定顺序（参考 Claude Code 的 Permission Gate 设计）：**先查 deny 名单，命中直接拒绝；再查 allow 名单，命中直接放行；都未命中按当前权限模式处理**（默认询问用户 / 自动放行低风险操作 / 全部放行 / 只读模式下任何有副作用操作都不真正执行）。

### 第四层：沙盒隔离（Sandbox）

- **执行环境隔离**：Agent 执行的代码/命令在容器或虚拟机里运行，防止越权访问宿主机
- **网络隔离**：限制 Agent 能访问的网络范围（比如只能访问内网 MCP 服务，不能访问任意外网地址），防止数据外泄或被诱导发起 SSRF 攻击
- **文件系统隔离**：限制 Agent 能读写的目录范围，不给访问系统关键目录的权限

### 第五层：业务规则引擎硬校验（最后一道、也是最可靠的一道防线）

即使模型的工具调用参数完全符合 Schema，业务层仍然要做规则引擎二次校验。比如客服场景里，退款金额和资格判定绝不能只依赖"提示词里写了不能超额退款"，而要在真正执行退款动作前，由确定性的规则引擎重新校验一遍金额是否在允许范围内——**这一层不信任模型的任何输出，只信任规则引擎自己算出来的结果**。

## 三、多 Agent 场景下的权限传递：最小权限原则

见 `diagrams/09-Agent工具调用决策流程图.puml`。多 Agent 系统里容易犯的错误是"给所有 Agent 共享同一个大而全的工具箱"，正确做法是**每个 Agent 只拥有完成自己职责所需的最小工具集**：

```
意图识别Agent   → 只有分类能力，没有任何写权限
知识库检索Agent → 只有只读检索工具
订单查询Agent   → 只有只读查询工具
退款协商Agent   → 有查询工具 + 一个受限的"发起退款申请"工具（不是直接写库权限，
                  这个工具内部还要再过一次规则引擎校验才真正执行）
```

子 Agent/下游 Agent **不应该自动继承上游 Agent 的全部权限**，而是各自被显式授予自己需要的最小集合——即使某个 Agent 被攻破或者出现严重幻觉，影响范围也被限制在它自己的工具边界内，不会波及其他业务。

## 四、防止间接提示词注入扩大权限边界

工具返回的数据（网页内容、文档、数据库记录、历史备注）可能被恶意插入了看起来像指令的文本。防护要点：

1. **数据与指令分离标注**：提示词里明确把工具返回内容标注为"数据"而非"指令"，要求模型不得把数据内容中的指令性文本当作系统指令执行
2. **架构级兜底**：即使模型被诱导做出错误"决定"，只要执行层（第五层业务规则引擎）不认这个决定，实际的资金/数据操作就不会真正发生——这是防止提示词注入造成实际危害的根本手段，比"提示词写得多严谨"更可靠

---

## 五、工具边界（Tool Scoping）设计原则

- **职责单一**：一个工具只做一件明确的事。反例是设计一个 `execute_sql` 这种可以执行任意 SQL 的"万能工具"——一旦模型被诱导传入恶意 SQL，权限边界形同虚设；正确做法是拆成具体的、参数受限的查询工具（比如 `queryOrderById(orderId)`，而不是让模型自己拼 SQL）
- **输入输出 Schema 严格约束**：参数类型、取值范围、字符串长度都要有明确约束，防止模型传入意料之外的参数
- **工具描述精确但不过度授权**：工具的自然语言描述要准确说明能力边界，避免模型误解工具能力后尝试越界使用

## 六、业内参考

| 方案 | 权限设计要点 |
|------|-------------|
| Claude Code | Permission Gate（deny优先于allow）+ Hook（PreToolUse/PostToolUse可拦截）+ 多级权限模式（默认询问/自动放行/只读Plan模式） |
| AWS Bedrock Agents | Action Groups 可以绑定 IAM 角色，做到工具调用级别的最小权限授权，复用云厂商成熟的身份权限体系 |
| MCP 协议本身 | 协议层面由 Server 端决定暴露哪些工具能力，但协议本身不强制身份认证/授权，很多实现依赖传输层（如mTLS）或应用层自建的认证机制——这是当前 MCP 生态一个公认还在完善中的点 |
| 通用 Function Calling（OpenAI等） | 模型厂商本身不提供权限框架，权限校验完全靠调用方应用层自建 |

## 面试话术小结

> Agent 的权限设计不能指望"提示词写清楚就够了"，我会按纵深防御的思路分五层：工具白名单限定能调用什么、参数Schema限定能传什么、操作分级决定要不要人工审批、沙盒隔离限制执行环境、业务规则引擎在真正执行前做最后的硬校验——尤其是资金/高风险操作，绝不能只靠模型自己判断。多Agent场景下我会坚持最小权限原则，每个Agent只拿它职责需要的最小工具集，不共享大而全的工具箱，这样即使某个Agent出问题，影响范围也是可控的。
