# 短链接系统设计方案

## 一、业务背景与需求
### 1.1 业务背景
原始长链接存在长度过长、传播不便、易被截断、无法统计数据等问题。短链接系统可将冗长的URL压缩为6-8位短字符链接，广泛应用于短信营销、社群推广、广告投放、内容分享等场景，同时支持访问数据统计、链接有效期管控、防拦截等能力。

### 1.2 核心需求
- **核心功能**：长链接转短链接、短链接跳转原长链接
- **基础能力**：链接过期设置、重复长链接复用、唯一短链接不冲突
- **拓展能力**：访问量统计、IP溯源、访问时间记录、黑名单防恶意生成
- **性能要求**：高并发跳转、低延时响应、支持海量链接存储
- **安全要求**：防链接劫持、防恶意跳转、过期链接失效、防重复刷量

## 二、核心设计原理
### 2.1 短链接结构
标准短链接由 **域名 + 短码** 组成
示例：`shturl.cc/hFb7rtYwOo0PvX`
- 短码：6-8位大小写字母+数字（62进制组合）
- 6位短码容量：62⁶ ≈ 568亿，完全满足日常业务海量需求

### 2.2 长短链接映射关系
核心是建立 **短码 → 长链接**、**长链接 → 短码** 的双向映射，保证：
- 同一个长链接多次生成，返回同一个短链接（去重复用）
- 不同长链接，绝对不生成相同短码（全局唯一）

## 三、短码生成方案（核心难点）
### 3.1 自增ID转62进制（业界推荐方案）
#### 实现逻辑：
1. 数据库设置自增主键ID（1,2,3,4...递增）
2. 将十进制自增ID转换为 **62进制字符串**（0-9、a-z、A-Z）
3. 转换结果即为唯一短码，ID永不重复，短码永久唯一

#### 优点：
- 无碰撞、无需查重，性能极高
- 实现简单、稳定性强
- 天然有序，方便数据归档管理

#### 缺点：
- 短码有规律，可被遍历（可通过加盐、打乱字符集优化）

### 3.2 随机字符串生成（不推荐）
随机生成6位字符作为短码，需数据库查重。
- 问题：高并发下极易出现短码碰撞；每次生成都需要查询数据库查重，性能损耗大；数据量越大，碰撞概率越高，系统越慢

### 3.3 哈希算法（MD5+截断）
对长链接做MD5哈希，截取中间6位作为短码。
- 问题：存在哈希碰撞，不同长链接可能截断出相同短码；必须查重，高并发场景性能瓶颈明显

## 四、系统整体架构
### 4.1 架构分层
1. **接入层**：Nginx + 域名解析，承接所有短链接访问、生成请求，实现负载均衡
2. **业务层**：短链接生成服务、跳转服务、统计服务、过期管理服务
3. **缓存层**：Redis 缓存热点短链接映射关系、过期链接、访问限流数据
4. **存储层**：MySQL 持久化所有长短链接映射、创建时间、过期时间、创建人等数据

### 4.2 核心组件作用
- **Redis**：缓存高频访问的短链接，实现毫秒级跳转；缓存过期链接，拦截无效请求；实现接口限流防刷
- **MySQL**：持久化全量数据，兜底缓存失效场景；存储链接有效期、创建记录、统计数据
- **定时任务**：清理过期链接、归档历史数据、统计日/月访问数据

## 五、核心业务流程
### 5.1 短链接生成流程
1. 用户传入长链接、过期时间等参数发起生成请求
2. 系统先查询Redis/MySQL，判断该长链接是否已生成过短链接
3. 已存在：直接返回原有短链接，实现复用
4. 不存在：数据库生成自增ID，转换为62进制短码
5. 写入MySQL持久化映射关系、过期时间、创建时间
6. 写入Redis缓存映射数据，设置同步过期时间
7. 拼接域名返回最终短链接

### 5.2 短链接跳转流程（核心高并发场景）
1. 用户访问短链接，Nginx拦截请求，解析短码
2. 优先查询Redis缓存：短码是否存在、是否过期
3. 缓存命中且有效：直接302重定向到原长链接，记录访问日志
4. 缓存未命中：查询MySQL数据库
5. 数据库存在且有效：回写Redis缓存，执行重定向
6. 不存在/已过期：返回404/链接已失效提示
7. 异步统计：记录访问IP、时间、设备、访问次数

## 六、关键设计难点与解决方案
### 6.1 高并发跳转性能问题
**问题**：短链接访问量极大，纯查数据库会导致系统卡顿、超时
**解决方案**：Redis热点缓存 + 读写分离
- 99%的跳转请求走Redis缓存，实现毫秒级响应
- MySQL仅做持久化兜底，不承接高频查询
- 对永久有效、高频访问的短链接长期缓存，过期链接及时淘汰

### 6.2 链接过期自动失效
**解决方案**：Redis过期机制 + 定时任务兜底
- Redis缓存key设置和业务一致的过期时间，到期自动失效
- 定时任务每日扫描MySQL，清理过期链接数据，释放存储空间

### 6.3 长链接重复生成冗余问题
**解决方案**：长链接哈希去重
- 对长链接做MD5哈希，存入数据库唯一索引
- 生成前校验哈希值，相同长链接统一复用短链接，减少数据冗余

### 6.4 短码被遍历、安全性低问题
**解决方案**：打乱62进制字符集 + 加盐加密
- 不使用默认0-9a-zA-Z顺序，自定义打乱字符集，让自增短码无规律
- 支持私密短链接设置，需校验权限才可访问

### 6.5 高并发下自增ID竞争问题
**解决方案**：Redis批量预生成ID段
- 避免数据库自增ID高并发锁竞争
- 服务启动时从Redis批量获取ID段，本地缓存使用，提升生成性能

## 七、数据库核心表设计
### 短链接映射表（link_map）
|字段名|类型|说明|
|---|---|---|
|id|bigint|自增主键，用于生成短码|
|short_code|varchar(10)|短码，唯一索引|
|long_url|varchar(512)|原始长链接|
|url_md5|varchar(32)|长链接MD5，去重唯一索引|
|expire_time|datetime|过期时间，永久链接为null|
|create_time|datetime|创建时间|
|visit_count|int|累计访问次数|
|status|tinyint|状态：0-失效 1-正常|

## 八、性能优化方案
- **缓存优化**：热点链接常驻缓存，冷链接过期淘汰，节省内存
- **请求优化**：跳转使用302临时重定向，不缓存跳转结果，保证数据实时性
- **限流防刷**：Redis实现接口限流，防止恶意批量生成、刷访问量
- **数据归档**：定时迁移过期、历史无效数据，保证主表查询性能
- **域名优化**：短链接域名单独解析、独立服务器，减少主域名压力

## 九、常见问题总结
- **短码冲突**：优先使用自增ID转62进制，彻底解决碰撞问题
- **跳转卡顿**：检查Redis缓存命中率，优化热点数据缓存策略
- **链接永久有效**：过期时间置空，不设置Redis过期key
- **重复短链接生成**：通过长链接MD5索引去重复用
