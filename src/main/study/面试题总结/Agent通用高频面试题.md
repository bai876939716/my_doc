# Agent 通用高频面试题（补充篇）

> 与 [`面试题总结/all-agent.md`](../简历准备/面试题总结/all-agent.md) 互补，不重复已覆盖的内容（多轮对话管理、System Prompt 设计、幻觉、Agent 设计模式、Function Calling 可靠性、RAG 优化、微调、MCP 协议等）。每题「核心结论」先给一两句话的直接答案，「展开说」用口语化方式讲清楚原理，尽量不堆术语和代码，方便直接对着面试官讲。

## 一、Function Calling / Tool Use 底层机制

### 模型是怎么"决定"调用哪个工具的？

**核心结论**：模型不是在"执行代码判断"，而是在生成阶段被训练成能识别出"这轮该调用工具了"，并输出一段符合约定格式的结构化内容（工具名+参数），推理框架识别出这种格式后代替模型去真正执行调用。

**展开说**：工具的名字、描述、参数说明本质上是被塞进模型看到的上下文里的一段文字，模型是结合当前对话的意图，从这些描述里"猜"出哪个工具最匹配、该填什么参数，这是一个基于语义理解的生成过程，不是查表匹配。所以工具描述写得越清楚、参数命名越直白，模型选错工具、编造参数的概率就越低，这也是为什么维护一份清晰的工具文档在实际项目里很重要。多轮工具调用什么时候停：每轮生成完，框架都会检查这次输出里还有没有新的工具调用请求，有就继续执行、把结果喂回去让模型接着想，直到某一轮模型不再要求调用工具（判定为已经可以给出最终答案）或者到了最大轮次上限为止。

### 工具返回的结果特别大（比如查出来几千条记录），怎么处理？

**核心结论**：不会把全量结果原样塞给模型，要么只取最相关的一部分加一段统计摘要，要么让模型自己发起更精确的二次查询缩小范围。

**展开说**：常见做法有三种：一是只把最相关的一小部分结果放进上下文，剩下的用一句话概括数量和整体情况；二是让 Agent 自己意识到结果太多，主动发起一次带过滤条件或者分页的二次查询；三是在业务层面提前把返回的数据做精简，只保留后续真正用得上的字段，而不是把接口原始返回的所有字段都转发给模型。这几种方式的共同点是控制喂给模型的信息密度，避免因为塞进太多无关内容既浪费成本又干扰模型的判断。

### Agent 调用工具出错了，应该让它自己重试、还是直接报错给用户？

**核心结论**：要看错误的性质——如果是参数不对、权限不够这种确定性错误，重试没有意义，应该直接让模型换个方式处理或者告知用户；如果是网络抖动、超时这种偶发性错误，值得自动重试一两次。

**展开说**：这跟传统后端处理接口调用失败的判断逻辑是一样的，核心是先分类再决定怎么处理，而不是无脑重试或者无脑放弃。工程上通常还会给 Agent 一个"重试预算"，避免它在一个反复失败的工具上无限打转，浪费调用次数和时间；同时应该把失败信息以对模型友好的方式返回（说清楚是什么类型的错误），这样模型才有机会调整策略，比如换一个工具或者换一种参数组合，而不是重复同样的失败调用。

## 二、Agent 框架与架构选型

### 主流的几个 Agent 框架该怎么选？

**核心结论**：流程确定、需要精确控制分支和错误处理的生产场景，适合用图/状态机类型的框架；探索性强、靠多个角色互相协作把任务想清楚的场景，适合用多智能体对话类型的框架；想快速出一个原型，轻量的交接式框架上手最快。

**展开说**：图/状态机类型的框架心智模型是"节点加边"，开发者自己设计每一步该做什么、出错了去哪、哪些步骤可以并行，控制力最强，但前期建模成本也最高，适合业务流程本身就是确定的多步骤流水线；多智能体对话类型的框架心智模型是"让几个角色互相发消息驱动流程往前走"，适合角色分工天然靠讨论表达的场景，比如一个写代码一个审查代码，但流程不够显式，生产环境下想精确控制和调试会更吃力；轻量交接式框架提供的是简单的"一个 Agent 把任务交给另一个 Agent"的机制，适合快速验证想法，深度定制能力有限。选型的核心问题应该是"我的业务流程到底是确定的还是探索性的"，而不是看哪个框架更新、更火。

### 单 Agent 和多 Agent 协作，什么情况下该拆成多个 Agent？

**核心结论**：当一个任务里包含明显不同性质的子能力（比如"规划"和"执行"需要的思维方式完全不同），或者需要不同的工具集、不同的上下文时，拆成多个各自专注的 Agent 通常效果更好；如果只是简单的单步问答，硬拆成多个反而会增加协调成本和延迟。

**展开说**：拆分的好处是每个子 Agent 的 Prompt 更聚焦、更容易调优，各自需要的工具集也更清晰，不会互相干扰；坏处是 Agent 之间需要传递上下文、协调调用顺序，每多一次 Agent 间的交接都是一次额外的模型调用和潜在的信息丢失风险，成本和延迟都会上升。实际项目里的判断标准通常是看任务是不是天然可以按业务域拆分——比如内容生产和内容审核是两种完全不同的判断逻辑，拆成两个 Agent 各自专注，比让一个 Agent 同时兼顾生成和自我审核效果更稳定。

### 多个 Agent 之间怎么共享状态，会不会互相覆盖？

**核心结论**：通常有两种模式——一种是共享一份统一的状态对象，各个环节按约定的字段分别读写自己负责的部分；另一种是各自维护独立状态，只通过明确定义的消息传递结果，不共享底层数据结构。

**展开说**：第一种模式实现简单，但如果没有清晰的字段归属约定，容易出现两个环节都在改同一个字段导致互相覆盖的问题，需要靠约定（谁负责写哪个字段）来避免冲突；第二种模式更像传统的服务间调用，边界清晰，不会有意外覆盖的问题，但需要多传递一层数据、多一层序列化开销。选择哪种取决于协作的紧密程度——如果多个环节是在同一条流水线上顺序执行、后面步骤天然依赖前面步骤的完整上下文，用共享状态模式更自然；如果是相对独立的多个 Agent 协作，用消息传递模式边界更清楚。

### Agent 的"规划"能力具体是怎么实现的，是真的在做搜索算法吗？

**核心结论**：大部分实际落地的 Agent 规划，是靠模型直接生成一份分步骤的计划文本，不是在做严格意义上的搜索算法；只有少数对准确率要求极高、允许多花计算成本的场景，才会用到类似树搜索这种更复杂的规划方式。

**展开说**：最常见的规划方式是让模型一次性输出"先做什么、再做什么"这样一份步骤列表，然后按顺序执行，执行中发现问题再让模型重新规划——这本质上是利用模型自身的推理能力生成计划，而不是运行一个独立的搜索算法。更复杂的场景会用到类似"生成多条候选路径、评估哪条更优、选最优的往下走"这种思路，本质上是把经典的搜索算法思想（比如蒙特卡洛树搜索）和模型的生成、评估能力结合起来，这种方式效果通常更好但计算成本也高出好几倍，一般只用在对准确率要求很高、允许牺牲响应速度换质量的场景，日常大部分 Agent 应用用不到这么重的方案。

## 三、上下文工程进阶

### Prompt 缓存是怎么生效的，设计 Prompt 时要注意什么？

**核心结论**：如果新请求的开头一段内容和之前某次请求完全一样，服务商可以直接复用之前算好的中间结果，不用重新计算这部分，所以要把不变的内容放在最前面、把每次都变化的内容放在最后面，这样命中缓存的部分才能最大化。

**展开说**：如果把容易变化的内容（比如当前时间、具体的用户输入）插在整个提示词的中间位置，会导致它后面的所有内容都没法复用之前的计算结果，缓存效果大打折扣。实践中常见的做法是把固定不变的角色设定、工具说明、通用规则放在最前面，把每次调用都不一样的具体任务参数放在最后面。批处理这种场景特别适合利用缓存——因为大量请求会共享同一段很长的固定前缀，只有末尾的具体任务不一样，命中率天然就高，能明显降低整体调用成本和延迟。

### 上下文窗口已经做到百万级 token 了，是不是就不用再做上下文管理了？

**核心结论**：不是，窗口大不代表塞进去的内容都能被模型充分利用，而且按用量计费的情况下，无节制堆上下文会让成本线性上涨，所以"精简、相关、有信息密度"仍然是构造上下文时要遵守的原则。

**展开说**：已经有不少研究和实践观察显示，模型对特别长的上下文里"中间部分"信息的利用率会明显下降，也就是说放进去不代表模型真的会重视到，尤其是关键信息如果被埋在一堆无关内容中间，被忽略的概率会更高；另外无关信息越多，也越容易稀释模型对真正重要信息的注意力，反而拉低回答质量。所以即便窗口足够大，实际工程里仍然要做检索、筛选、摘要压缩这些工作，只把跟当前任务真正相关的内容喂给模型，而不是有多大窗口就塞多少内容进去。

### 上下文压缩具体有哪些常见手段？

**核心结论**：常见手段包括滑动窗口只保留最近内容、对早期内容做摘要压缩、按重要性打分筛选保留、以及把结构化信息单独抽取出来存成更紧凑的形式而不是保留原始文本。

**展开说**：滑动窗口是最简单直接的办法，只保留最近若干轮，牺牲的是对很久以前信息的记忆能力；摘要压缩是对滚出窗口的旧内容做一次总结，用一段更短的文字代替原始对话，保留大意但丢失细节；重要性打分是给每一轮内容打一个分，优先保留信息密度高的、丢弃闲聊性质的内容；结构化抽取则是把对话里的关键事实单独提炼成结构化的记录（比如用户的某个偏好、某个约定），后续直接注入这份精简的结构化信息，而不需要保留大段原始对话文本。实际项目里通常是这几种手段组合使用，而不是单选一种。

## 四、检索与向量系统

### 检索管道里 Embedding 模型和重排序模型分别起什么作用？

**核心结论**：Embedding 模型负责从海量内容里快速捞出一批看起来相关的候选（粗排），重排序模型再对这批候选做更精细的打分排序（精排），两者分工是"先快速缩小范围，再精细排序"。

**展开说**：Embedding 检索的优点是速度快，能在海量数据里快速定位到大致相关的一批结果，但因为计算方式相对简单，排序精度有限，容易出现"看起来相关但实际不是最匹配"的结果排到前面；重排序模型会对候选结果和查询做更细致的两两比对打分，排序质量明显更好，但计算量也大得多，只能用在已经被缩小到几十上百条的候选集合上，不可能对全量数据都跑一遍。这种"先粗后精"的两阶段设计，是在检索速度和检索精度之间找的一个平衡，纯粹依赖任何一边都有明显短板。

### 混合检索（关键词检索 + 向量检索）为什么比单一方式更好？

**核心结论**：关键词检索擅长精确匹配专有名词、编号这类"必须原文出现"的查询，向量检索擅长理解语义相近但字面不同的表达，两者结合能互相补足各自的短板。

**展开说**：纯向量检索有个常见问题——遇到一个很生僻的专有名词或者精确的编号查询时，语义相似度未必能把包含这个词的文档排到前面，因为向量表示的是整体语义而不是精确的字面匹配；纯关键词检索则完全不理解语义，用户换一种说法但意思一样的查询就搜不到。混合检索通常是把两种检索方式各自的结果按一定权重融合排序，兼顾"字面精确匹配"和"语义相关匹配"两种召回能力，这也是目前很多生产级检索系统的标配做法，而不是单纯依赖向量检索。

### 向量数据库怎么选，有哪些常见考量维度？

**核心结论**：主要看数据规模、查询延迟要求、和现有技术栈的集成成本、以及是不是需要跟结构化数据混合查询这几个维度，没有一个"最好"的选择，只有"最合适当前场景"的选择。

**展开说**：数据规模小、查询延迟要求高的场景，用内存索引效率高的方案更合适；数据规模特别大、可以接受稍微牺牲一点召回精度换内存占用降低的，可以考虑基于分桶聚类的索引方式；如果项目本身已经在用某个关系型数据库，而且需要经常把向量检索结果和结构化字段联合查询（比如既要语义相似又要满足某些业务条件过滤），直接用支持向量能力的关系型数据库扩展会比额外引入一个独立的向量数据库集成成本更低、运维也更简单——这也是不少团队优先考虑的方向。核心还是要先想清楚自己的数据规模、延迟要求、以及跟现有系统的耦合程度，再决定要不要额外引入一个专门的向量数据库。

### 文档切分（chunking）有哪些常见策略，切分不好会有什么问题？

**核心结论**：常见策略是按固定长度切、按语义边界（段落/章节）切、以及更高级的先生成摘要再和原文绑定检索这几种，切分不好最常见的问题是"一个完整的意思被切断在两个块里"，导致检索时召回的片段信息不完整。

**展开说**：按固定长度切分实现简单，但很容易把一句完整的话或者一个完整的论述切成两半，检索到其中一半会丢失上下文；按语义边界切分（比如按段落、按标题层级切）能更好地保持内容的完整性，但需要文档本身有比较清晰的结构才好操作；更高级的做法是给每个大的段落生成一份摘要，摘要单独做向量化用于检索定位，检索到摘要后再把对应的完整原文一起返回给模型，这样既保证了检索的精确度，又不会因为切分丢失上下文完整性。切分策略的选择本质上是在"检索粒度精细"和"内容完整性"之间找平衡，切得太细容易丢上下文，切得太粗又会让不相关的内容混进被检索到的片段里。

## 五、LLM 服务与网关工程（Java 背景的强项切入点）

### 一个支撑多个业务方、多个模型的 LLM 网关，核心要解决哪些工程问题？

**核心结论**：核心是路由（把请求发到合适的模型）、限流（防止某个业务方把资源占满）、降级熔断（主力模型出问题时自动切备用）、计费统计、以及统一的调用可观测性这五件事，这几乎和传统微服务网关要解决的问题是同构的。

**展开说**：路由是按业务场景的成本、延迟、质量要求，把请求分发到合适的模型，这是网关最基础的职责；限流要能分层做，既要有全局总量控制，也要能按业务方、按模型分别设置配额，避免某一方的流量把整体资源打爆；降级熔断是主力模型故障或者响应超时的时候，能自动切换到备用模型，或者返回一个兜底话术，保证整体服务不至于完全不可用；计费统计需要准确记录每次调用消耗的输入输出量，用于成本核算；可观测性则是统一记录每次调用的输入、输出、耗时、是否成功，方便后续排查问题和做效果评测。这些能力模式和传统的 API 网关高度相似，是 Java 背景的候选人最容易直接迁移复用的一块经验。

### 流式输出（打字机效果）底层是怎么实现的？

**核心结论**：模型本身是一个字一个字生成的，服务端通过一种能持续推送数据的长连接方式，每生成一点内容就立即推给客户端，而不是等全部生成完才一次性返回。

**展开说**：这种持续推送的机制让客户端可以实时看到内容逐步出现，而不是等待几秒钟然后突然全部显示出来，体验上差别很大。如果项目本身有自己的长连接推送通道，要做的事情本质上是把从模型服务收到的这种流式数据，转发到自己的长连接通道再推给最终的客户端，是一次协议层面的转发和中继。这里常见的追问是"如果中途网络断开怎么办"——通常做法是客户端记住已经收到内容的位置或者序号，重新连接后可以请求从断点继续获取剩余内容，这就要求服务端在生成过程中要能短暂保留住这部分状态，支持断点续传。

### 自己部署开源模型和直接调用商业模型 API，该怎么权衡？

**核心结论**：调用 API 的优势是免运维、按量付费、模型能力通常更强，适合快速验证和流量不稳定的场景；自己部署的优势是数据不出内网、长期大流量下成本更可控、可以针对特定场景做微调，但需要承担运维和推理性能优化的成本。

**展开说**：调用商业模型 API 几乎不需要考虑推理部署这些底层问题，团队可以把精力完全放在业务逻辑上，缺点是数据要经过第三方，对一些有合规要求的场景不适用，长期高流量下成本也可能更贵；自己部署需要处理推理服务本身的性能优化问题，比如怎么让多个请求共享计算资源提高吞吐（业内常说的连续批处理），怎么把生成过程中计算量不同的两个阶段分开处理来提高整体效率（业内常说的两阶段分离部署），这些都需要专门的推理框架和运维投入，但换来的是数据可控、大流量下边际成本更低、还能针对自己的场景做定制微调。实际项目里很常见的做法是两者结合——核心的、对合规和成本敏感的场景自建部署，长尾的、探索性的场景调用现成的 API，不是非此即彼的选择。

## 六、Agent 可观测性与评测体系

### 生产环境的 Agent 系统，除了打日志，还需要建立哪些可观测性能力？

**核心结论**：需要有能完整回放一次执行过程的链路追踪、可以拿来统计分析的结构化调用记录、聚合出来的关键指标（成本、延迟、成功率），以及对线上真实流量持续抽样评测的机制，缺一不可。

**展开说**：链路追踪解决的是"出问题了能不能一步步看清楚到底是哪一步错了"；结构化调用记录不是普通的文本日志，而是可以拿来做统计查询的数据，比如每次调用花了多少钱、多长时间、是否成功，这样才能做后续的分析和告警；聚合指标是把这些记录汇总成团队关心的关键数字，比如平均延迟、失败率、按场景拆分的成本，用于容量规划和异常发现；持续抽样评测则是防止"上线前测得好好的，上线之后模型或者数据悄悄变了，效果在不知不觉中变差"，需要有一个长期在跑的质量监控机制，而不是只在上线前测一次就不管了。

### 怎么设计一套可持续迭代的评测体系？

**核心结论**：至少要分层建立评测——针对单个环节（比如一次检索、一次工具调用）的准确性评测，和针对整体任务完成情况的端到端评测都要有，而且测试集要能覆盖典型场景、边界场景、以及历史踩过的坑，还要能反复复用来对比不同版本的效果。

**展开说**：只有一个笼统的"好不好"评分是不够的，因为出了问题很难定位到底是检索环节的问题还是生成环节的问题，分层评测能让你快速定位问题出在哪一层。测试集的构造不能只覆盖"正常情况"，还要专门收集边界情况和历史上出过问题的案例，作为回归测试，防止同样的问题反复出现。评测体系要有可复现性——固定测试集的版本、固定打分标准，每次改动 Prompt 或者换模型之后都跑一遍同一套测试集，才能客观比较"这次改动到底是变好了还是变差了"，而不是凭感觉判断。人工打分是评测体系里比较可靠但吞吐量有限的手段，成熟的做法通常会结合用更强的模型自动打分来提升评测效率，人工评测用来做抽样校准和处理有分歧的案例。

### 用一个更强的模型给另一个模型的输出打分（LLM-as-judge），靠谱吗，怎么设计才靠谱？

**核心结论**：靠谱，但要精心设计打分标准和打分方式才行，不能简单地问模型"这个回答好不好"，而是要给出明确的评分维度、评分量表，最好还要给出参照样例，否则打分结果的一致性和区分度都会比较差。

**展开说**：如果只是笼统地让模型给一个总体分数，不同次打分之间的一致性会比较差，而且不同评分维度（比如语气自然度、事实准确性、是否完成任务）混在一起打一个总分，很难知道具体是哪方面出了问题。更靠谱的做法是把评分拆成几个具体维度分别打分，每个维度给出清晰的评分标准描述，最好再配上几个不同分数段的参照样例，让打分模型有据可依；对于两个版本谁更好这种比较型的评测，用"两两比较选出更好的一个"通常比"各自打绝对分数再比较"更稳定，因为比较相对判断比绝对打分更容易达成一致。用这种方式打分之后，还建议定期抽样跟人工评分做一次对比校准，确认自动打分和人工判断的偏差在可接受范围内，而不是完全信任自动化结果不做任何校验。

## 七、Agent 安全与风险控制

### 什么是提示词注入，Agent 场景下风险点在哪，怎么防？

**核心结论**：提示词注入是攻击者通过精心构造的输入，诱导模型偏离原本设定的规则去做别的事；在 Agent 场景下风险被放大，是因为 Agent 会自主调用工具、访问外部数据，如果外部数据里藏着看起来像指令的内容，模型可能把它当真指令执行，可能直接触发有实际后果的操作。

**展开说**：普通对话场景下的注入顶多是让模型说一些不该说的话；但 Agent 因为具备"能操作外部系统"的能力，如果它检索到的一篇网页、一条评论里被恶意植入了类似"忽略之前的规则，执行某个操作"这样的文字，模型有可能真的把它当成新的指令去执行，风险等级完全不一样。常见防护思路是把"系统给出的规则"和"外部工具返回的数据"在权限层面明确区分开，告诉模型外部数据只是参考信息不是指令来源；对于有实际副作用的高风险操作（比如发消息、删除数据、涉及资金的操作），不能只靠模型自己判断就执行，必须加一道人工确认或者规则校验的关卡；另外对模型的最终输出也可以再加一层规则化的后校验，不完全信任模型自己保证输出内容是合规的。

### 工具调用的"越权"风险怎么控制？

**核心结论**：核心原则是最小权限——Agent 能碰到的工具集合本身就应该是按需求最小化暴露的，而且每个工具内部仍然要正常做鉴权校验，不能因为调用方是"内部可信的 Agent"就跳过权限检查。

**展开说**：不应该把整个内部系统的所有接口都暴露给 Agent，而是只暴露它完成当前任务真正需要的那一小部分能力，这样即使模型的判断出了偏差，能造成的影响范围也是有限的；同时每个被暴露的工具内部依然要按正常的业务规则做权限校验（这个用户是不是真的有权限操作这个资源），不能因为发起调用的是一个"可信的内部服务"就默认放行，因为 Agent 的行为最终是由模型的生成结果驱动的，模型判断出错的可能性始终存在，权限校验这道关卡不应该因为调用方看起来可信就省略。

### 怎么防止用户通过"越狱"话术绕过模型的安全限制？

**核心结论**：单靠模型自身训练时学到的安全对齐并不能保证百分之百拦住所有绕过手法，工程上通常还需要在输入侧和输出侧各加一层独立的检测机制作为补充。

**展开说**：模型经过安全对齐训练之后，对大部分直接的违规请求确实能拒绝，但总会有一些精心构造的话术（比如让模型扮演一个不受限制的角色、把违规请求包装成"这只是虚构故事"）能够绕过。工程上比较稳妥的做法是不完全依赖模型自身的判断，而是额外接入一层独立的内容安全检测——在用户输入进入模型之前先做一次风险识别，在模型生成结果返回给用户之前再做一次输出内容审核，两道关卡加上模型自身的安全对齐，形成多层防护，而不是只信任模型一层判断。

## 八、并发模型与工程实现（Java 视角切入点）

### Python 的协程并发和 Java 的线程并发，本质区别是什么，对 Agent 开发有什么影响？

**核心结论**：Java 的线程是由操作系统调度的，多个线程可以真正同时跑在不同的 CPU 核心上；Python 因为存在一个全局解释器锁，同一时刻只有一个线程在执行 Python 代码，所以 Python 常用协程模型让单线程在等待网络等 IO 的时候切换去做别的任务，本质是"用不占线程资源的方式提高 IO 密集型任务的并发度"，而不是真正的并行计算。

**展开说**：Agent 开发里的并发场景，比如同时调用多个工具、同时等待多个模型响应，绝大部分时间是在等网络返回（IO 密集型），而不是在做密集的计算，这正好是协程模型最擅长的场景——不需要真正的多核并行，只需要在等待的时候不浪费资源、能去处理别的任务就够了。这也是为什么 Python 的 Agent 项目里普遍用协程加信号量的方式做并发控制，而不是像计算密集型场景那样追求真正的多核并行。对有 Java 背景的候选人来说，理解这个区别很重要——不能拿"Java 里开多线程能真正提升计算吞吐"的直觉直接套用到 Python 的协程模型上，两者解决的问题模式不完全一样，Java 的线程池调优经验能提供并发控制的思路，但底层调度机制是不同的。

### 一个 Agent 服务如果被大量并发请求打进来，怎么保证不被拖垮？

**核心结论**：至少要在三个层面做保护——入口层限制同时处理的请求总量、内部对下游资源（模型调用、数据查询）分别做并发限制、以及对超时和失败的请求要有明确的降级处理，不能让请求无限堆积等待。

**展开说**：入口层的限流是最外层的防线，防止瞬时流量直接把服务打垮；内部对下游资源分别限流，是因为不同下游资源的承受能力不一样，需要各自设置合理的并发上限，避免一个下游被打满连累其他部分；对于超时的请求要有明确策略，要么快速失败返回一个降级结果，要么排队但设置合理的等待上限，不能让请求无限堆积占用资源导致整个服务响应越来越慢直至完全卡死。这几层保护本质上和传统后端服务应对突发流量的思路是一致的，只是这里保护的资源换成了模型调用和 Agent 内部的工具调用。

## 九、Token 与成本工程

### 除了压缩上下文，还有哪些常见的降低 Token 成本的手段？

**核心结论**：常见手段还包括按场景选用不同成本的模型（简单任务用便宜快的模型、复杂任务才用贵的模型）、利用提示词缓存降低重复前缀的计费、以及通过内容复用减少重复生成的次数。

**展开说**：不是所有任务都需要用最强最贵的模型去处理，很多结构清晰、难度不高的任务用一个更便宜更快的模型就能达到差不多的效果，按任务难度和质量要求分流到不同成本的模型，是控制整体成本很直接有效的手段；提示词缓存前面提过，靠设计固定不变的前缀内容来降低重复计费；内容复用则是从业务设计角度出发——如果某类内容本身有沉淀和复用的价值，先判断已有的存量是否够用，只有真正需要新内容的时候才调用模型生成，而不是每次都从零生成，这个思路虽然不是模型调用层面的技巧，但往往是成本优化里效果最明显的一环，因为它直接减少了调用次数本身。

### 怎么估算一个 Agent 功能上线后的模型调用成本？

**核心结论**：核心公式是"预计的调用频次 乘以 每次调用的平均输入输出量 乘以 对应模型的单价"，但容易被忽略的是要把重试、多轮工具调用这些"隐藏的额外调用"也算进去，不能只按理想情况下一次成功调用来估算。

**展开说**：估算的第一步是搞清楚这个功能大概会被调用多少次（取决于用户规模和使用频率），第二步是估算单次完整交互平均会产生多少输入和输出的量，第三步乘以对应模型的单价。容易被低估的地方是实际调用往往不是一次就结束的——工具调用可能要好几轮模型交互才能完成一个任务，失败重试也会产生额外的调用次数，这些都要计入总的调用量估算里，否则上线后实际成本会明显超出预期。比较稳妥的做法是先在小流量上线测一段时间，拿到真实的调用次数和平均消耗数据后再做准确的成本预测和后续的容量规划，而不是仅凭上线前的理论估算就下结论。
