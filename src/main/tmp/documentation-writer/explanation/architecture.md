# 解释:架构——一个部署单元,多个业务技能包

## 要解决的问题

门店一线员工要填的表单类业务(报修、报销、巡检……)共同点极高:多轮对话收集字段、字典校验、人工确认、落外部系统。如果每个业务起一个服务,运维成本线性增长;如果挤进一个服务但边界不清,业务逻辑会渗透进流程代码,最后谁也不敢动。

AgentServerCenter 的答案是一个部署单元承载多个「技能包」,用三层分离把「变」与「不变」隔开:

```
app/api/       接口层:五接口同形状路由,校验口径读技能包声明
app/core/      框架层:引擎/契约/存储/LLM 网关——业务无关,所有技能包共用
app/skills/    技能包:字段 schema + 字典 + 话术 + 工具 + 钩子,全是声明式配置
```

这套分离不是纸面约定:`tests/test_neutrality.py` 用一个假技能包跑通全链路,core 里任何一处对具体业务的耦合都会让测试变红。

## 引擎与技能包的边界

框架层的 LangGraph 引擎(`app/core/engine.py`)负责通用流程:打字轮(LLM 识别)→ 澄清 → 点选轮(0 LLM,纯字典校验)→ 确认卡 → 提交。技能包通过 `SkillDef`(`app/core/skill_contract.py`)声明自己:开场话术、上下文工具、建单工具、摘要槽位、快捷卡片、槽位 schema。

值得注意的设计是**校验口径的单一来源**:接口层对点选值、手机号、卡片的校验,全部从技能包声明推导(`app/api/routes.py` 的 `validate_message` 明确写着「这一层别再自己抄一份字段清单或手机号正则」)。换一个业务、改一个字典,接口层代码零改动——这正是三层分离能兑现的前提。

## 状态与持久化

会话的完整真相在 LangGraph State 里(`messages` 带 seq 单调编号、`slots`、`meta`),检查点后端二选一:memory(进程内,联调)或 postgres(检查点 + 活跃索引 + 归档表同库)。活跃索引 `rp:active:{uid}:{store_no}` 实现草稿恢复:重进门店报修页,按人+店找回未完成会话——键里带 store_no 是因为一人可能对应多店,跨店不许复用会话(`app/api/sessions.py`)。

终态(submit/abandon)自动归档到 `agent_session_archive` / `agent_message_archive`,数据核验与报表查这两张表;`summary_slot`(报修场景是 category)让归档行自带漏斗分析的分桶字段。

## LLM 的角色定位

入口 README 的一句话是这套架构的价值观:「LLM 负责识别与生成,程序负责流程,人负责确认。」LLM 只出现在打字轮的识别与话术生成;点选轮零 LLM 调用;最终落库前必有确认卡。这解释了为什么引擎里存在大量「不用模型」的路径——字典命中、卡片直达、降级向导都是纯程序逻辑,LLM 是增强而非依赖。

## 取舍

这套设计的代价:①框架层的契约(`skill_contract.py`)必须足够稳定,技能包需求变化会向上压框架;②「同形状路由」意味着新业务的接口形状被当前五接口范式约束;③单副本约束(见《LLM 无开关与单副本约束》)在放量前必须解决。换来的是:新业务接入成本≈写一份声明式配置,框架演进不碰业务、业务迭代不碰框架。
