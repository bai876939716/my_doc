# 解释:X-Uid 信任边界

## 现状

AgentServerCenter 自身**零鉴权**:不看 token、不验签名,身份完全信任请求头 `X-Uid`。服务端唯一的闸门是「有没有这个头」——缺失(或全空白)时五接口一律 401/`40101`,绝不兜底成匿名用户(`app/api/routes.py` 的 `_uid`)。这是 2026-11-18 审计 #1 之后的强制行为。

## 为什么敢零鉴权

因为信任边界画在了上游。部署形态里,本服务只经公司网关/ai-middle 转发层暴露,转发层以**认证结果替换注入** `X-Uid`(从 HTM-HEADER 取),客户端传来的值会被覆盖——伪造不了。鉴权是这个链路上游的职责,本服务重复做一遍没有增量价值。

这个约定的**硬性一半在服务端**:「缺 X-Uid 一律拒」执行的是「转发层必须注入身份」这条链路约定。如果服务端见缺就兜底成 `anonymous`,上游漏注入的故障会被静默吞掉,直到出事才暴露。

## 为什么曾经出过问题:anonymous 合流的后果

早期版本缺 `X-Uid` 会兜底成 `anonymous`,而草稿是按 `(uid, store_no)` 键存的。两个没身份的用户都会落进 `anonymous` 这同一格:A 填了一半退出,B 进来直接拿到 A 的现场——还能替 A 提交。这不是理论风险,是撤销该兜底的直接原因(来源:`routes.py` `_uid` docstring 的原话:「A 填一半、B 重进就拿到 A 的现场,还能替他提交」)。

所以现在匿名只剩一条显式通道:`ALLOW_ANONYMOUS=true`(仅限本地演示页),生产禁开——开了等于把所有无身份用户重新并成同一份草稿。

## 纵深防御的另外两道

1. **会话属主比对**(`_own`):每个会话建立即在 `context` 里记下 uid,后续所有按 sid 的操作都比对;不一致时回 **40401——与「会话不存在」同响**,避免有人拿这个接口探测别人的会话是否存在(来源:`routes.py:155-160`)。
2. **敏感值出口管控**:身份关联的手机号对外只出掩码(状态条/确认单/GET collected 同一口径,唯一实现 `app/core/redact.py`),明文只存在于服务端 State 与明道云建单链路。

## 边界与残留风险

这套模型的前提是「转发层确实替换而非透传 X-Uid」。一旦本服务被绕过网关直接暴露(比如测试环境误开公网),零鉴权就是零防线——因此部署侧必须保证 8000 端口不对公网开放。此外 `X-Uid` 是弱身份(仅标识、不鉴权),若未来接入更高敏业务(如涉及资金),需要上游提供可验证的身份凭证而非裸头。
