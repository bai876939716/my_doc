# 解释:LLM 无开关,与单副本约束

这两个约束看似无关,其实同源:都来自「宁可拒启动/限规模,不可静默错下去」的工程判断。

## LLM 无开关:真实调用是唯一路径

当前行为:`main.build_llm()` 永远构造真实的百炼网关,缺 `LLM_BASE_URL`/`LLM_API_KEY` 当场 `ValueError` 拒启动。曾经存在 `REAL_LLM_ENABLED` 开关,2026-11-18 删除(`app/main.py:85-93` 的 docstring 记录了这段历史)。

为什么删?因为「可关」的模型意味着系统里存在两条都算正常的路径:真模型路径和降级路径。运维上一旦配置出错,开关兜底会让服务带着降级质量静默跑着——用户感受到的只是「识别变笨了」,没人知道该去修配置。把「缺配置」从运行时静默降级升级为启动时显式失败,故障从「难以察觉的质量劣化」变成「明确拒起」,这是用可观测性换灵活性。

那要确定性、零 token 的运行怎么办?答案是**把桩放在外面,而不是开关放在里面**:测试用 `tests/conftest.py` monkeypatch 掉 `build_llm`,演示用 `poc/mock_llm_app.py` 换桩入口。桩的注入点是明确的、显式选择的,而不是一个环境变量悄悄切换的隐藏分支。

唯一保留的开关是 `REAL_ORDER_ENABLED`——它切的不是「真/假运行」,而是「建单写不写真值到明道云」,这是业务语义(测试单 vs 生产单),不是降级语义。

## 单副本约束:进程内状态划定规模上限

服务当前**只能单副本部署**,原因写在 `app/api/sessions.py`:

- `session_guard`(同 sid 图操作串行)与 `entry_guard`(同 uid+store_no 建会话/恢复/放弃串行)都是**进程内 threading.Lock**——两个副本各持各的锁,同一会话的并发消息会在两个副本上各拿一份旧快照跑图,后写的把先写的覆盖(代码注释里给了具体症状:电话改完又没了)。
- 建单幂等缓存同样在进程内。

代码已留好升级路径:多实例要强一致,换 PG advisory lock(`sessions.py` 的 TODO)。注意这不是疏漏而是**量级判断**:同步线程池 40 + 单副本,灰度几十人够用(README 容量口径);打字轮 LLM 5~8s、点选轮 0 LLM。放量前按模型 TPM 与并发重算,届时再落分布式锁——为一个尚未到来的规模提前引入分布式锁复杂度,违背本项目的克制风格。

## 两条约束的共同逻辑

把「会静默出错的设计」改成「会大声失败的设计」:LLM 配置缺失 → 拒启动;多副本会串会话 → 文档与 TODO 明示,不假装支持。系统的真实边界永远暴露在明面上,这是这个小服务最一致的一条工程价值观。
