# 数据模型

描述对象:app/core/state.py(黑板)与 app/core/pgstore.py(应用表 DDL)。

两类数据:随会话走的黑板(唯一持久化的业务数据形状)与 PG 里的三张应用表。memory 模式下黑板在进程内,重启即失。

## 黑板(会话检查点)

三条设计约束(模块开头声明):只放可序列化数据(附件存引用,本体在外部);只放恢复现场要用的字段(LLM 原始返回不进);槽位是已定稿事实,候选留在消息里(防幻觉的地基)。

顶层数据:技能包名与会话 id;本轮用户消息(崩溃重放用,用后可清);抽取产出(持久化以便崩溃后本轮不重复调 LLM);带出字段;槽位表(每格:值、来源、更新时间;来源三值:系统默认、AI 填、用户改,数据血缘可查);议程(待问必填槽名,答一个划一个,钩子失效会回填);当前焦点(议程首项的影子,对外输出零计算);消息列表(按 seq 单调递增,同 seq 覆盖,append-only 加重放合并);meta(路径分支、模式、连续失败计数、LLM 调用数、确认挂起位、安静位、序号发生器、订单结果、最近建单错误、挂起修改目标、会话起点 UTC);子表行预留(报修恒为空,为报销费用明细类业务预留)。

meta 里的确认挂起位是数据不是控制流:确认单展示中、等人核对修改提交,这张图没有 interrupt 挂起态可查。

## PG 应用表(幂等建表,postgres 模式首次就绪时执行)

| 表 | 主键 | 生命周期 |
|---|---|---|
| agent_active_index | key(rp:active:{uid}:{store_no}) | 每轮交互续期;TTL 七天;终态(提交或放弃)即删;过期由清理线程删 |
| agent_session_archive | sid | 终态写入,ON CONFLICT 覆盖;永久保留(摘要一行:状态、单号、类别摘要、LLM 调用数、消息数、起点、恢复次数、路径分支、最终模式、归档时间) |
| agent_message_archive | (sid, seq) | 随归档逐条写入,同键覆盖;永久保留 |

另有 langgraph 框架自己的检查点表(由 saver 的 setup 建,本仓代码不声明其结构;表结构属框架版本,未连库核实,见 unknowns.md)。迁移策略:CREATE IF NOT EXISTS 加一份 ALTER ADD COLUMN IF NOT EXISTS,新旧库都能跑;建表语句不会给已存在的表补列,靠 ALTER 兜。

## 数据出口口径

数据核验与报表查归档表(仓库 docs/ 有专门的查询指南);对外接口里声明显示形态的槽位只出显示形态(手机号掩码,与状态条、确认单同一份实现);日志里敏感值同口径。归档表的恢复次数取自活跃索引行,所以归档必须先于清索引(接口层已按此排序,幂等补档时索引已清则记零,代码注释自认可接受)。

## 明道云侧写入(外部数据)

建单写入报修工作表:文本五控件(门店名、门店编号、报修详情、联系人、手机号码)、日期控件、附件控件(必填)、类别级联控件(按叶子选项 rowId 写,拍平值反查,查无记 skipped)、大区下拉控件(按选项 key 写,名称精确反查,查无记 skipped)。三条已知不写入:紧急程度等 Dropdown 是流程字段只读(API 写会被静默丢弃);门店属性、地址、营业时间三格由明道云工作流回填,API 建的单这三格必空(不是缺陷,抓包实证);期望上门时间、影响营业两个字段表里没有对应控件(产品口径已删)。
