# 会话生命周期与留存

描述对象:app/api/sessions.py(注册表)、app/core/pgstore.py(PG 基建)、app/main.py 的 lifespan 装配。

会话由两样东西定位:检查点(LangGraph saver 管,黑板的持久化)与活跃索引(键 rp:active:{uid}:{store_no} 指向会话 id,一人多店不串会话)。键里带门店编号是硬约束:同一个人在不同门店各开各的会话。

## 建会话与恢复

统一入口是建会话接口:同一人同一店有没填完的活跃会话就恢复(续期索引、累计恢复次数、回放全部消息含用户气泡),换店或没有就新建。三种索引失效当场处理:指向的会话已出单(索引作废、另起新单)、索引悬空(检查点已过期被清、删索引按新建)、restart 标志(「重新开始」:在入口锁内先放弃再新建,单请求完成)。会话 id 是一百二十八位随机数,防猜测枚举。

## 两把锁(单副本约束的根)

同一会话的图操作排队(读改写全程持锁,防两条并发消息各拿旧快照互相覆盖);同一(人,店)的建会话、恢复、放弃排队(防前端退出没等完就并发建会话,把刚放弃的会话捞回来)。锁都在进程内、锁对象常驻不回收;多副本部署下这两把锁都失效,扩容前要先换分布式锁,这是代码注释与 README 双双点名的已知约束。

## 终态

两条路走到终态:提交成功(归档、清索引;重进等于新单)与主动放弃(归档、清索引、销毁检查点;已出单的会话放弃请求直接忽略,防止归档状态被改成放弃污染漏斗,也保住提交的幂等重放)。退出接口幂等:会话已经不在了就回 ok。memory 模式没有归档,终态数据随进程消失。

归档内容:会话摘要一行(状态、单号、类别摘要、LLM 调用数、消息数、起点、恢复次数、路径、是否降级完成)加消息逐条;重复归档按会话 id 覆盖不脏数据。恢复次数从活跃索引行读走,所以归档必须发生在清索引之前,接口层已按此排序。

## 过期清理(仅 postgres 模式)

活跃索引每轮交互续期,七天不动即过期。后台守护线程每半小时跑一轮:过期的索引行整 thread 删检查点加删行;归档早于 TTL 的会话只回收检查点,摘要与消息永久留在归档表。回收窗口只盖「刚到期」十四天的那段(免得每轮全量扫归档表);代价是停机超过十四天时中间到期的行不再回收,浪费存储不影响正确性。清理失败只警告,下一轮重试。

## 启动装配

lifespan 里做四件事:运行配置校验(真实建单开关开着则明道云四项必须齐)、技能包加载自检、构造 LLM 客户端(缺地址密钥当场拒启动,不静默降级)、按检查点模式装配(memory 零依赖;postgres 建池、挂就绪探针)。探针分离:活体只看进程,就绪看依赖;postgres 模式下建表、首轮清理、清理线程都挂在首次就绪上,启动时 PG 没连上也不影响进程起,转绿前不接流量。

## 身份与属主校验

身份闸门在 api 层:缺 X-Uid 一律 401,不兜底匿名;本地演示要匿名得显式开开关。属主校验比对建会话时写进 context 的 uid,不一致按「会话不存在」同响,防试探;老检查点没写过 uid 的放行。
