# 补偿任务执行器（CompensationTaskService）说明文档

## 1. 概述

补偿任务执行器是 `dis-aftersale-service` 中的通用异步任务补偿框架，用于处理因外部依赖失败、网络超时等原因导致的业务操作未完成场景。框架通过**策略模式 + 状态机**实现任务的自动重试与状态流转，具备分布式锁防重、CAS 乐观锁、游标分页、延迟重试等企业级特性。

**所属模块：** `com.jst.aftersale.task.compensation`

**核心类：**

| 类/接口 | 职责 |
|---------|------|
| `CompensationTaskService` | 服务接口，暴露执行入口 |
| `CompensationTaskServiceImpl` | 核心执行引擎，编排查询→分发→执行→状态流转 |
| `CompensationTaskProcessor` | 策略接口，定义具体任务的处理逻辑 |
| `CompensationTaskContext` | 处理器注册中心，按 taskType 路由到对应 Processor |
| `CompensationTaskLogDao` | 数据访问层，操作 `af_compensation_task_log` 表 |
| `CompensationTaskLogPo` | 任务记录实体 |
| `CompensationTaskConfig` | Nacos 动态配置（白名单等） |
| `CompensationTaskConfiguration` | 线程池 Bean 定义 |

## 2. 架构设计

### 2.1 整体架构图

> 详见 [架构图](补偿任务执行器-架构图.puml)

### 2.2 设计模式

| 设计模式 | 应用位置 | 说明 |
|---------|---------|------|
| 策略模式 | `CompensationTaskProcessor` 接口 | 不同任务类型实现各自的处理逻辑 |
| 工厂模式 | `CompensationTaskContext` | 根据 taskType 获取对应 Processor 实例 |
| 模板方法 | `CompensationTaskServiceImpl` | 统一的查询→锁→CAS→状态机流转骨架 |
| 状态机 | `processTasksInLoop` | 循环驱动状态转换直到终态 |

### 2.3 线程池设计

框架采用**双线程池**架构，查询与执行职责分离：

| 线程池 | Bean 名称 | 核心/最大线程数 | 队列容量 | 职责 |
|--------|-----------|---------------|---------|------|
| 查询线程池 | `compensationTaskSelectThreadPool` | 1/1 | 5000 | 从 DB 分批捞取待执行任务 |
| 工作线程池 | `compensationTaskWorkThreadPool` | 20/20 | 5000 | 执行具体补偿逻辑 |

两个线程池均使用 `CallerRunsPolicy` 拒绝策略，支持动态线程池（DTP）运行时调参。

## 3. 数据模型

### 3.1 数据库表：`af_compensation_task_log`

| 字段 | 类型 | 说明 |
|------|------|------|
| ID | VARCHAR | 主键 |
| CO_ID | VARCHAR | 公司 ID |
| UID | VARCHAR | 用户 ID |
| BATCH_NO | VARCHAR | 批次号（业务唯一标识） |
| RETRY_COUNT | INT | 已重试次数 |
| LAST_RETRY_TIME | DATETIME | 上次重试时间 |
| NEXT_EXECUTION_TIME | DATETIME | 下次可执行时间（延迟重试核心字段） |
| TASK_TYPE | VARCHAR | 任务类型（路由到对应 Processor） |
| STATUS | VARCHAR | 当前状态（WAITING/SUCCESS/FAIL 或自定义多步状态） |
| PARAM | TEXT | 任务参数（JSON） |
| VERSION | BIGINT | 版本号 |
| DELETED | TINYINT | 逻辑删除 |
| CREATED / CREATEBY | DATETIME/VARCHAR | 创建信息 |
| UPDATED / UPDATEBY | DATETIME/VARCHAR | 更新信息 |

### 3.2 通用状态枚举

```java
public enum CompensationTaskStatus {
    WAITING("WAITING"),   // 待处理
    SUCCESS("SUCCESS"),   // 已完成
    FAIL("FAIL");         // 已失败
}
```

> 复杂业务可自定义多步状态（如极速退款的多阶段状态），Processor 通过 `getWaitingStatus()` 声明哪些状态需要被捞取执行。

## 4. 执行流程

### 4.1 主流程时序图

> 详见 [执行流程时序图](补偿任务执行器-执行流程.puml)

### 4.2 流程说明

#### 阶段一：任务捞取（Select 线程池）

1. 定时任务触发 `executeCompensationTask(taskType)`
2. 通过 `@Async("compensationTaskSelectThreadPool")` 异步执行
3. 根据 taskType 从 `CompensationTaskContext` 获取对应 Processor
4. 循环分批查询（每批 100 条，游标分页 `lastId > ?`，条件 `NEXT_EXECUTION_TIME <= NOW()`）
5. 将每批任务提交到工作线程池

#### 阶段二：单任务执行（Work 线程池）

1. **白名单检查**：生产环境跳过白名单商家
2. **重试次数校验**：超限则标记失败 + 回调
3. **分布式锁获取**：Redis `SETNX`，Key = `dis::compensation::task:key{taskType}:{batchNo}:{coId}:{uid}`，TTL = 5min
4. **CAS 更新重试次数**：`WHERE id=? AND RETRY_COUNT=?`，失败说明已被其他节点处理
5. **状态机循环**（最多 20 轮）：
   - 调用 `processor.process(task, currentStatus)` 获取 nextStatus
   - 判断结果：失败 / 状态未变（延迟重试） / 成功 / 继续流转
6. **异常处理**：catch 后触发 `exceptionCallback`
7. **释放锁**：finally 中 `redis.delete(lockKey)`

## 5. 并发控制

### 5.1 分布式锁

```
Key 格式: dis::compensation::task:key{taskType}:{batchNo}:{coId}:{uid}
TTL: 5 分钟
获取方式: redis.opsForValue().setIfAbsent(key, "1", 5, MINUTES)
释放方式: redis.delete(key)（finally 块）
```

**设计考量：**
- 锁粒度到 `taskType + batchNo + coId + uid`，同一用户同一批次不会并发
- TTL 防止宕机死锁
- 不使用 Redisson 看门狗，任务执行超 5 分钟视为异常

### 5.2 CAS 乐观锁

```sql
-- 重试次数 CAS
UPDATE af_compensation_task_log 
SET RETRY_COUNT = RETRY_COUNT + 1, LAST_RETRY_TIME = NOW() 
WHERE id = #{id} AND RETRY_COUNT = #{retryCount}

-- 状态转换 CAS
UPDATE af_compensation_task_log 
SET STATUS = #{newStatus} 
WHERE ID = #{id} AND STATUS = #{currentStatus}
```

双重保障：分布式锁防跨节点重复，CAS 防同节点并发。

## 6. 重试机制

| 场景 | 处理方式 | 回调方法 |
|------|---------|---------|
| 超过最大重试次数 | 标记 FAIL | `maxRetryCountCallback` |
| 状态未改变（条件不满足） | 更新 `NEXT_EXECUTION_TIME`，等待下次捞取 | — |
| 处理异常 | 捕获异常，触发回调 | `exceptionCallback` |
| 状态机循环超 20 次 | 标记 FAIL | `spinCountLimitCallback` |
| 处理返回失败状态 | 标记 FAIL | `failCallback` |

**延迟重试**：当 `process()` 返回的 nextStatus 与 currentStatus 相同时，由 Processor 计算下次执行时间，避免无效轮询。

## 7. 扩展指南：如何新增一个补偿任务

### 步骤 1：定义任务类型

在对应的枚举类中新增任务类型常量。

### 步骤 2：实现 Processor

```java
@Component
@Slf4j
public class MyBusinessCompensationTaskProcessor implements CompensationTaskProcessor {

    @Override
    public String getTaskType() {
        return "MY_BUSINESS_TASK";
    }

    @Override
    public List<String> getWaitingStatus() {
        return Collections.singletonList("WAITING");
    }

    @Override
    public String failStatus() {
        return "FAIL";
    }

    @Override
    public Boolean isSuccess(String nextStatus) {
        return "SUCCESS".equals(nextStatus);
    }

    @Override
    public String process(CompensationTaskLogPo task, String currentStatus) {
        // 业务处理逻辑
        // 返回下一个状态
    }

    @Override
    public Boolean checkMaxRetryCount(CompensationTaskLogPo task) {
        return task.getRetryCount() < 10; // 最多重试 10 次
    }

    @Override
    public LocalDateTime nextExecutionTime(CompensationTaskLogPo task, String currentStatus) {
        // 指数退避或固定间隔
        return LocalDateTime.now().plusMinutes(5L * (task.getRetryCount() + 1));
    }
}
```

### 步骤 3：写入任务记录

在业务代码中，当需要补偿时插入一条记录：

```java
CompensationTaskLogPo task = new CompensationTaskLogPo();
task.setId(UUID.randomUUID().toString().replace("-", ""));
task.setCoId(coId);
task.setUid(uid);
task.setBatchNo(businessId);
task.setTaskType("MY_BUSINESS_TASK");
task.setStatus("WAITING");
task.setParam(JSON.toJSONString(bizParam));
task.setRetryCount(0);
task.setNextExecutionTime(LocalDateTime.now());
task.setDeleted(false);
task.setCreated(LocalDateTime.now());
compensationTaskLogDao.insert(task);
```

### 步骤 4：配置定时触发

在定时任务中调用：

```java
compensationTaskService.executeCompensationTask("MY_BUSINESS_TASK");
```

> Processor 通过 Spring 自动注入到 `CompensationTaskContext`，无需手动注册。

## 9. 性能优化要点

1. **游标分页**：使用 `lastId > ?` 替代 `OFFSET`，避免深度分页性能退化
2. **查询条件**：`NEXT_EXECUTION_TIME <= NOW()` 过滤未到执行时间的任务
3. **双线程池隔离**：查询不阻塞执行，执行不阻塞查询
4. **批量提交**：每 100 条作为一批提交到工作线程池
5. **循环上限**：外层最多 1000 批次，内层状态机最多 20 轮，防止无限循环
6. **动态线程池**：支持运行时通过 DTP 调整线程池参数
